## 쓰레드

애플리케이션 코드를 하나하나 순차적으로 실행하는 것은 쓰레드라고 한다.

```
프로세스는 프로그램 실행하는 것이고, 쓰레드는 프로그램 안에서 여러가지 일을 하는것
```

<br/>


자바 메인 메서드를 처음 실행하면 main이라는 이름의 쓰레드가 실행 된다.
- main()메서드를 실행하면 main 이라는 이름의 쓰레드가 실행 된다. (딱 하나!)

```
동시 처리가 필요하면 쓰레드를 추가로 생성
```

## 해결 방법은 ‘쓰레드 풀’ 이라는 것을 사용.

![이미지](/programming/img/서12.PNG)

이름 그대로 ‘풀장 == 수영장’ 같은 느낌이다.

<br/>

그 안에서 쓰레드가 수영하고 놀고 있다가, 요청 1번과 요청 2번이 온다.

그러면 이걸 ‘쓰레드 풀’ 한테 요청 하는 것이다.

1번과 2번이 “쓰레드 풀안에서 놀고 있는 쓰레드 주세요!” 말하는 것이다.

<br/>여기서 쓰레드 풀 안에는 쓰레드가 200개 있다고 가정하자.

그러면 두개를 빌려가서 ‘쓰레드 풀’ 에 있던 200개가 → 198개가 되는 것이다.

그러고 작업을 다 끝낸 뒤에 쓰레드를 죽이는 것이 아니고, ‘쓰레드 풀’ 에 반납하는 것이다.

<br/>즉, 정리하면  죽이고 생성하고 하는 것이 아니라, 

‘풀’ 안에 미리 만들어서 넣어 놓고 빌려쓰고, 반납하고 하는 것이다

<br/><br/>

## WAS의 멀티 쓰레드 지원 - 핵심

핵심은 WAS에 멀티 쓰레드 지원을 해준다는 것이다.


<br/>서블릿 코드 안에 비즈니스 로직만 짜면 되는 것이다.

고객이 10명이 오든 100명이 오든 멀티 쓰레드 관한 부분은 개발자가 설정만 하면 되는 것이다.

<br/>

```
‘쓰레드 풀’ 관리하고 ‘쓰레드 풀’ 생성 해주고 
 멀티 쓰레드 관련된 코드들은 전부 WAS가 처리해주는 것이다.
```

- 멀티 쓰레드에 대한 부분은 WAS가 처리

- 개발자가 멀티 쓰레드 관련 코드를 신경쓰지 않아도 됨
- 개발자는 마치 싱글 쓰레드 프로그래밍을 하듯이 편리하게 소스 코드를 개발
- 멀티 쓰레드 환경이므로 싱글톤 객체(서블릿, 스프링 빈)는 주의해서 사용

## 궁금증!

```java
스레드 풀이 스레드를 재사용한다는 게 무슨 뜻일까
```

크기 3인 풀에 작업 10개를 넣고, 어느 스레드가 처리했는지 이름을 모아봤다.

```java
ExecutorService pool = Executors.newFixedThreadPool(3);
for (int i = 0; i < 10; i++) {
    pool.submit(() -> names.add(Thread.currentThread().getName()));
}
```

<br/>

### 결과

```java
작업 10개를 처리한 스레드 = 3개
[pool-1-thread-3, pool-1-thread-2, pool-1-thread-1]
```

<br/>

10개를 처리했는데 스레드는 3개뿐이다.

<br/>

앞의 스레드 풀 설명 부분에서 본 대로,

스레드를 만드는 것 자체가 비싸서 미리 만들어두고 돌려쓰는 것이다.

<br/>

## 그래서 ThreadLocal 이 위험해진다

스레드가 재사용된다는 것은, 앞 요청의 흔적이 남을 수 있다는 뜻이다.

<br/>

스레드 하나짜리 풀에 두 작업을 넣어봤다.

```java
one.submit(() -> {
    holder.set("첫 번째 사용자");
    // holder.remove() 를 안 했다
});

one.submit(() -> {
    System.out.println(holder.get());
});
```

<br/>

### 결과

```java
요청 A 가 담아둔 값 = 첫 번째 사용자
요청 B 가 꺼낸 값   = 첫 번째 사용자   <- 남의 값이다
```

<br/>

두 번째 작업이 첫 번째 작업의 값을 그대로 읽었다.

<br/>

여기에 로그인 정보를 넣어뒀다면 남의 계정으로 동작하는 것이다.

앞의 싱글톤 패턴, 싱글톤 방식의 주의점 글에서 언급한 그 사고가 이렇게 난다.

<br/>

그래서 반드시 `finally` 에서 지워야 한다.

```java
try {
    holder.set(값);
    ...
} finally {
    holder.remove();
}
```

<br/>

## 지역 변수는 안전하다

두 스레드가 각자 10만 번씩 지역 변수를 더해도 문제가 없다.

```java
Runnable task = () -> {
    int local = 0;
    for (int i = 0; i < 100000; i++) local++;
};
```

<br/>

앞의 자바 메모리 구조 글에서 본 대로,

스택은 스레드마다 하나씩 있기 때문이다.

<br/>

## 필드는 그렇지 않다

같은 객체의 필드를 두 스레드가 10만 번씩 더해봤다.

```java
class Counter {
    int count;
    void inc() { count++; }
}
```

<br/>

### 결과

```java
20만이어야 하는데 실제 = 117332
```

<br/>

8만 번 넘게 사라졌다.

<br/>

`count++` 이 한 줄로 보이지만 실제로는 세 단계다.

```java
1. count 를 읽는다
2. 1 을 더한다
3. 다시 쓴다
```

<br/>

두 스레드가 같은 값을 읽으면 한 번의 증가가 사라진다.

<br/>

앞의 조회수 증가 문제를 다룬 글에서 본 것과 똑같은 구조다.

거기서는 `100번 실행 후 = 1` 이 나왔었다.

<br/>

## 그래서 싱글톤 빈에 상태를 두면 안 된다

앞의 서블릿 설명 내부 동작 글에서 본 대로,

서블릿도 스프링 빈도 하나만 만들어져서 모든 요청이 공유한다.

```java
@Service
public class OrderService {
    private int lastPrice;        // 이걸 하면 위의 결과가 실제로 일어난다
}
```

<br/>

## 스레드가 많다고 빨라지지 않는다

```java
CPU 코어가 8개인데 스레드가 200개면
-> 8개만 실제로 돌고 나머지는 기다린다
-> 그리고 계속 서로 자리를 바꾼다 (컨텍스트 스위칭)
```

<br/>

자리를 바꾸는 데도 비용이 든다.

레지스터를 저장하고 복원하고, CPU 캐시가 무효화된다.

<br/>

그래서 무작정 늘리면 오히려 느려진다.

<br/>

## 그럼 왜 코어 수보다 많이 두나

웹 요청은 대부분 기다리는 시간이기 때문이다.

```java
DB 조회를 기다린다
외부 API 응답을 기다린다
파일을 읽기를 기다린다
```

<br/>

기다리는 동안 CPU는 놀고 있으니, 다른 스레드가 일하면 된다.

<br/>

톰캣 기본값이 `200` 인 것도 그 때문이다.

```java
server.tomcat.threads.max=200
```

<br/>

앞의 커넥션 풀 글에서 본 것과 같이 봐야 한다.

```java
톰캣 스레드 200개 + DB 커넥션 10개
-> 스레드 190개가 커넥션을 기다린다
```

<br/>

스레드만 늘려도 커넥션이 부족하면 거기서 막히는 것이다.

병목은 항상 제일 좁은 곳에서 생긴다.
