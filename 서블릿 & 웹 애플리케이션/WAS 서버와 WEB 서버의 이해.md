## 웹 서버, 웹 애플리케이션 서버

웹이라는 것은 HTTP 기반으로 통신을 한다. -> (HTTP 메세지에 모든 것을 전송)

우리가 흔히 부르는 서버라는 것은 `WAS`라는 것이다.

HTTP 요청을 보내고 받는 서버가 WAS 이다.

<br/><br/>

## 웹 서버(Web Server) / WAS랑 다르다.

- HTTP 기반으로 동작하는 서버

- 정적(파일) HTML, CSS, JS, 이미지, 영상
- 대표적인 아파치 서버

<br/><br/>

## 웹 애플리케이션 서버(= WAS ‘와스’라고 부른다)

핵심은 프로그램을 코드를 실행해서 애플리케이션 로직을 수행 할 수 있다는 것이다.

웹 서버(Web Server)는 정적인 파일만 다루기 때문에 특정 사용자 마다 다르게 보여주는 등,,

다른 동적 기능들을 할 수 없었다. 하지만 웹 애플리케이션 서버(=WAS) '와스' 는 가능한 것이다.

<br/>

그리하여 사용자에 따라서 그 사람의 이름도 보여줄 수 있고, 다른 화면들도 보여줄 수 있는 것이다.

- 동적인 HTML 생성 가능

- HTTP API(JSON) 제공

- 서블릿, JSP, 스프링 MVC

- 대표적인 '톰캣'도 `와스` 서버라고 한다.




<br/><br/>

## 웹 서버, 웹 애플리케이션 서버(WAS) 차이

- 웹 서버는 정적 리소스(파일), WAS는 애플리케이션 로직

- WAS는 애플리케이션 코드를 실행하는데 더 특화

<br/><br/>

## 웹 시스템 구성: WEB -> WAS -> DB

일반 적으로 이런식으로 웹 시스템 구성을 한다.

1. 정적 리소스(웹서버)를 앞에 둔다.
    - 여기서 정적 리소스를 다 처리하는 것이다.(HTML, CSS, JS, 이미지 등..)

2. 첫번째를 수행하다 동적인 로직이 필요한 URL이라고 판단 되면 웹서버가 WAS로 넘긴다

3. 그렇게 WAS가 처리하고, 마지막으로 DB 데이터를 가져온 다음에 
    
    -> 웹서버(Web Server)에게 내려 주고 -> 유저에게 내려 주는 것이다.


<br/>

### 장점은 WAS는 엄청 중요한 애플리케이션 로직에 전담 할 수 있다는 장점이 있다.

- 업무를 분담 할 수 있다.


![이미지](/programming/img/서1.PNG)


- 정적 리소스만 제공하는 웹 서버는 잘 죽지 않음

- 애플리케이션 로직이 동작하는 WAS 서버는 잘 죽음 (이유 개발자들이 만들기 때문)

## 궁금증!

```java
스프링 부트는 웹 서버 없이 도는데 괜찮은가
```

내장 톰캣만 있으면 동작은 한다. 그래도 앞에 웹 서버를 두는 이유가 있다.

<br/>

```java
정적 파일을 대신 내려준다
여러 대의 WAS 로 요청을 나눈다
HTTPS 를 여기서 끊는다
WAS 가 죽었을 때 오류 페이지를 대신 보여준다
```

<br/>

`4번` 이 실무에서 크다.

WAS가 죽으면 브라우저에 연결 실패가 그대로 뜬다.

앞에 웹 서버가 있으면 `점검 중입니다` 화면을 보여줄 수 있다.

## 요즘은 그 자리가 다른 것으로 바뀌었다

```java
옛날  - 브라우저 -> Apache/Nginx -> 톰캣
지금  - 브라우저 -> CDN -> 로드밸런서 -> 애플리케이션
```

<br/>

`Nginx` 가 하던 일을 클라우드 서비스가 나눠 가져갔다.

```java
정적 파일  -> CDN (CloudFront 등)
부하 분산  -> 로드밸런서 (ALB 등)
HTTPS      -> 로드밸런서에서 끊는다
```

<br/>

역할이 사라진 게 아니라 자리만 옮긴 것이다.

<br/>

## HTTPS 를 앞에서 끊는다는 말

```java
브라우저 --HTTPS--> 로드밸런서 --HTTP--> 애플리케이션
```

<br/>

암호화를 푸는 일은 CPU를 꽤 쓴다.

그걸 앞에서 한 번만 하고, 내부망에서는 평문으로 보내는 것이다.

<br/>

이러면 애플리케이션이 자기가 HTTPS로 들어왔는지 모른다.

그래서 헤더로 알려준다.

```java
X-Forwarded-Proto: https
X-Forwarded-For: 실제 클라이언트 IP
```

<br/>

이 헤더를 안 보면 문제가 생긴다.

```java
request.getScheme()      -> "http" 가 나온다
redirect 를 만들면       -> http:// 로 만들어진다 -> 브라우저가 경고를 띄운다
```

<br/>

스프링 부트에서는 설정 한 줄로 이 헤더를 읽게 할 수 있다.

```java
server.forward-headers-strategy=native
```

<br/>

접속자 IP를 로그에 남길 때도 마찬가지다.

`request.getRemoteAddr()` 은 로드밸런서의 IP가 나온다.

실제 사용자 IP는 `X-Forwarded-For` 에 있다.

<br/>

## 정적 파일을 WAS 가 처리하면

앞의 멀티 쓰레드 글에서 본 스레드 풀을 정적 파일이 차지한다.

```java
이미지 100개가 있는 페이지 -> 요청 100개 -> 스레드 100개가 파일만 읽는다
```

<br/>

그동안 진짜 처리해야 할 요청이 대기하게 된다.

<br/>

`Nginx` 는 이런 일에 특화되어 있다.

스레드를 요청마다 만들지 않고 적은 수로 돌리는 구조라 훨씬 많이 처리한다.

<br/>

## WAS 라는 말이 애매해지고 있다

원래는 이런 뜻이었다.

```java
웹 서버 - 정적 파일만
WAS     - 프로그램을 실행해서 동적으로 만든다
```

<br/>

지금은 경계가 흐릿하다.

`Nginx` 도 모듈을 붙이면 프로그램을 돌릴 수 있고,

`Node.js` 처럼 웹 서버와 애플리케이션이 한 몸인 것도 있다.

<br/>

앞의 스프링이 뭔가 글에서 본 내장 톰캣도 그렇다.

```java
jar 하나 안에 서버가 들어 있다
java -jar app.jar 하면 그냥 뜬다
```

<br/>

서버를 따로 깔고 `war` 를 배포하던 방식이 거의 사라진 것이다.

<br/>

컨테이너로 배포하는 흐름과도 맞는다.

이미지 안에 다 들어 있어야 어디서든 똑같이 뜨기 때문이다.
