## 서버사이드 렌더링

### SSR - 서버 사이드 렌더링 : 서버에서 최종 HTML을 생성해서 클라이언트에 전달



```
예를 들면, 웹 브라우저에서 “주문 내역 주세요” 요청이 온다.

그러면 서버는 주문 디비를 조회 해서, HTML을 동적으로 생성한 다음에 (=JSP나 타임리프 같은걸로)

최종적으로 HTML을 서버에서 전부 만드는 것이다.
```

즉, HTML 만드는 과정을 서버에서 다 끝내고, 웹 브라우저는 단순하게 생성된걸 보여주기만 하면 되는 것이다.

("최종 결과물이 서버에서 전부 생성된다" 하여, 서버사이드 렌더링이라고 부른다.)

## 궁금증!

```java
CSR 과 SSR 을 무엇으로 고르나
```

첫 화면이 언제 보이는지와, 검색 엔진이 읽을 수 있는지가 갈린다.

<br/>

```java
SSR - 서버가 완성된 HTML 을 준다. 브라우저는 그리기만 하면 된다
CSR - 서버가 빈 HTML 과 자바스크립트를 준다. 브라우저가 데이터를 또 받아 그린다
```

<br/>

CSR의 첫 응답은 이렇게 생겼다.

```java
<html>
<body>
    <div id="root"></div>
    <script src="/app.js"></script>
</body>
</html>
```

<br/>

내용이 하나도 없다.

`app.js` 가 실행되고, 그게 다시 API를 불러야 화면이 생긴다.

<br/>

## 검색 엔진 문제

크롤러가 이 HTML을 받으면 볼 게 없다.

<br/>

요즘 구글 크롤러는 자바스크립트를 실행하기는 한다.

다만 그러려면 렌더링 큐에 들어가서 나중에 처리되고,

모든 검색 엔진이 그렇게 하는 것도 아니다.

<br/>

그래서 검색 유입이 중요한 서비스는 SSR을 쓴다.

```java
쇼핑몰 상품 페이지, 블로그, 뉴스   -> SSR
관리자 화면, 대시보드, 사내 도구   -> CSR
```

<br/>

로그인해야 보이는 화면은 어차피 검색이 안 되니 CSR로 해도 상관없는 것이다.

<br/>

## 요즘은 섞어 쓴다

```java
Next.js, Nuxt
```

<br/>

첫 요청만 서버에서 그려서 보내고, 그 다음부터는 CSR로 돈다.

<br/>

```java
첫 진입      -> 서버가 완성된 HTML 을 보낸다. 바로 보인다
그 뒤 이동   -> 자바스크립트가 데이터만 받아 갈아 끼운다. 깜빡임이 없다
```

<br/>

첫 화면 속도와 이후 반응성을 둘 다 가져가는 방식이다.

<br/>

## 하이드레이션이라는 단계가 있다

서버가 그려준 HTML은 껍데기다. 버튼을 눌러도 아무 일이 안 일어난다.

<br/>

자바스크립트가 로딩되고 나서 이벤트를 붙인다.

```java
HTML 이 보인다      -> 그런데 아직 안 눌린다
자바스크립트 로딩    -> 이제 눌린다
```

<br/>

이 사이에 사용자가 버튼을 누르면 반응이 없다.

`보이는데 안 눌리는` 구간이 생기는 것이다.

<br/>

## 백엔드 입장에서는 무엇이 달라지나

앞의 API 방식(json), @ResponseBody 글에서 본 그 차이다.

```java
SSR - 컨트롤러가 Model 에 담고 뷰 이름을 반환한다
CSR - 컨트롤러가 객체를 반환하고 그게 JSON 이 된다
```

<br/>

CSR이면 서버가 화면을 모른다.

`이 화면에 무엇이 필요한가` 를 프론트가 정하고, 서버는 데이터만 준다.

<br/>

그래서 API 설계가 더 중요해진다.

```java
화면 하나에 API 를 여러 번 부르게 되면 -> 느려진다
API 를 화면에 맞춰 만들면            -> 화면이 바뀔 때마다 서버를 고쳐야 한다
```

<br/>

이 둘 사이에서 균형을 잡는 게 실무의 고민이다.

<br/>

## 인증 방식도 갈린다

```java
SSR - 세션과 쿠키. 서버가 상태를 들고 있는다
CSR - 토큰. 클라이언트가 들고 다닌다
```

<br/>

앞의 세션 동작 방식 글과 JWT 글에서 본 그 차이다.

<br/>

CSR이라고 반드시 토큰을 써야 하는 것은 아니다.

같은 도메인이면 쿠키도 잘 동작한다.

<br/>

오히려 토큰을 `localStorage` 에 넣으면 XSS에 노출된다.

`HttpOnly` 쿠키는 자바스크립트가 못 읽으니 그쪽이 안전한 면도 있다.

<br/>

앞의 쿠키(Cookie) 글에서 본 그 옵션이다.

```java
HttpOnly - 자바스크립트가 못 읽는다. XSS 방어
Secure   - HTTPS 에서만 전송
SameSite - 다른 사이트에서 온 요청에는 안 보낸다. CSRF 방어
```

<br/>

도메인이 다르면 쿠키를 쓰기 까다로워서 토큰을 쓰는 경우가 많다.

`CSR 이니까 토큰` 이 아니라 `도메인이 다르니까 토큰` 인 것이다.
