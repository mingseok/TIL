## 절대 경로, 상대 경로

<br/>

## ‘절대 경로’ (전부 기입한 것 == `절대 경로`)

`절대 경로`란 최초의 시작점으로 경유한 경로를 전부 기입하는 방식이다.

- 윈도우 OS의 바탕화면에 위치한 `test.txt` 파일을 예를 들어보자.

- `test.txt`파일의 절대 경로는 최상위 루트 디렉토리인 **C** 디렉토리 로부터 시작되어야 한다.
    - `C:\Users\UserPwd\Desktop\test.txt`

```html
<html>
<head>
    <meta charset="UTF-8">
    <title>Title</title>
</head>
<body>
<form action="/save" method="post">
    username: <input type="text" name="username"/>
    age: <input type="text" name="age"/>
    <button type="submit">전송</button>
</form>
</body>
</html>
```

<br/>

시작 지점부터 목표 지점 까지의 어느 누가 봐도 절대적으로 이곳을 가리킬 수 있는 곳입니다.

만약, `<form action="/save" method="post">` 되어 있다면

http://localhost:8080/save 이렇게 들어가는 것이다.

<br/><br/>

## ‘상대 경로’

form태그에서 action이, ‘/’이 없이 그냥 ‘save’ 되어 있다면 ‘상대 경로’ 인 것이다.

(현재 파일이 존재하는 디렉토리를 기준으로 해당 파일까지의 위치를 작성한 경로.)

```html
<html>
<head>
    <meta charset="UTF-8">
    <title>Title</title>
</head>
<body>
<!-- 상대경로 사용, [현재 URL이 속한 계층 경로 + /save] -->
<form action="save" method="post">
    username: <input type="text" name="username"/>
    age: <input type="text" name="age"/>
    <button type="submit">전송</button>
</form>
</body>
</html>
```

<br/>

### 예시로)

현재 위치가 http://localhost:8080/members/new-form 라면

`<form action="save" method="post">` 했다면 

http://localhost:8080/members/`save` 이렇게 끝에만 변하는 것이다.
<br/>

## 궁금증!

```java
슬래시 하나 차이로 무엇이 달라지나
```

기준점이 달라진다.

```java
/css/main.css      -> 도메인 루트부터. 어디서 부르든 같은 곳
css/main.css       -> 지금 페이지의 위치부터
```

<br/>

`/members/1` 이라는 페이지에서 두 경로를 쓰면 이렇게 갈린다.

```java
/css/main.css   ->  https://site.com/css/main.css
css/main.css    ->  https://site.com/members/css/main.css
```

<br/>

상대 경로는 마지막 슬래시까지를 기준으로 삼는다.

`/members/1` 의 기준은 `/members/` 인 것이다.

<br/>

## 그래서 URL 이 바뀌면 깨진다

```java
/members         -> 기준은 /
/members/1       -> 기준은 /members/
/members/1/edit  -> 기준은 /members/1/
```

<br/>

같은 레이아웃을 쓰는데 페이지마다 CSS 경로가 달라져야 하는 것이다.

<br/>

그래서 정적 리소스는 절대 경로로 쓴다.

```java
<link rel="stylesheet" href="/css/main.css">
```

<br/>

## 그런데 절대 경로도 문제가 있다

앱이 하위 경로에 배포되면 깨진다.

```java
https://site.com/myapp/members
```

<br/>

여기서 `/css/main.css` 는 `https://site.com/css/main.css` 를 찾는다.

`/myapp` 이 빠져 있으니 `404` 다.

<br/>

그래서 컨텍스트 경로를 붙여야 한다.

```java
<link rel="stylesheet" th:href="@{/css/main.css}">
```

<br/>

타임리프의 `@{...}` 가 컨텍스트 경로를 앞에 붙여준다.

앞의 타임리프 URL 링크 표현식 글에서 본 그것이다.

```java
컨텍스트가 /       -> /css/main.css
컨텍스트가 /myapp  -> /myapp/css/main.css
```

<br/>

스프링 부트는 기본 컨텍스트가 `/` 라 차이가 안 보인다.

그래서 나중에 하위 경로로 배포할 때 갑자기 다 깨지는 일이 생긴다.

<br/>

## 리다이렉트에서도 같은 문제가 있다

```java
return "redirect:/members";        // 컨텍스트 경로가 붙는다
response.sendRedirect("/members"); // 안 붙는다
```

<br/>

앞의 리다이렉트, 디스패처 글에서 본 스프링의 `redirect:` 는 컨텍스트를 붙여준다.

서블릿의 `sendRedirect` 는 안 붙인다.

<br/>

같은 일을 하는 것 같은데 결과가 다른 것이다.

<br/>

## 점 두 개로 위로 올라가기

```java
../css/main.css      -> 한 단계 위로
../../css/main.css   -> 두 단계 위로
```

<br/>

`/members/1/edit` 에서 `../css/main.css` 는 `/members/css/main.css` 가 된다.

<br/>

브라우저가 이걸 계산해서 실제 URL을 만든 다음 요청을 보낸다.

서버는 이미 계산이 끝난 절대 경로를 받는 것이다.

<br/>

앞의 URI 와 웹 브라우저 요청 흐름 글에서 본 대로,

HTTP 요청 라인에는 절대 경로만 들어간다.

```java
GET /members/css/main.css HTTP/1.1
```

<br/>

`../` 라는 표기는 요청에 안 실린다.

<br/>

## 서버 쪽 파일 경로와 헷갈리지 않기

URL 경로와 파일 시스템 경로는 다른 얘기다.

```java
/css/main.css                      <- URL
src/main/resources/static/css/main.css   <- 실제 파일 위치
```

<br/>

스프링 부트가 `static` 아래를 URL 루트로 매핑해준다.

<br/>

파일을 다룰 때는 또 다른 함정이 있다.

```java
new File("data.txt")        // 현재 작업 디렉토리 기준. 실행 위치에 따라 달라진다
```

<br/>

IDE에서 실행할 때와 `java -jar` 로 실행할 때 기준이 달라진다.

그래서 상대 경로로 파일을 읽으면 배포하고 나서 안 찾아지는 일이 생긴다.

<br/>

클래스패스에서 읽는 게 안전하다.

```java
new ClassPathResource("data.txt")
```

<br/>

`jar` 안에 들어 있는 것도 이걸로 읽을 수 있다.
