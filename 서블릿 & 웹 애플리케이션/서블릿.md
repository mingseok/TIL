## 그리하여 서블릿을 사용하는 것이다.

서블릿이 녹색 부분을 제외한 나머지를 서블릿이 자동으로 처리해 주는 것이다.



<br/><br/>

## 서블릿 특징

![이미지](/programming/img/서4.PNG)

- `urlPatterns(/hello)` : `/hello` URL로 웹 브라우저에서 서버로 요청이 왔을때 `service()` 메서드가 실행이 된다.



- `HttpServletRequest` : HTTP 요청 정보를 편리하게 사용할 수 있게 도와주는 것이다.
    - 즉, 사용자가 입력한 이름 -> `kim` , 나이 -> `20` 인 데이터를 쉽게 꺼내서 사용할 수 있도록 해주는 것이다.


- `HttpServletResponse` : HTTP 응답 정보를 편리하게 제공할 수 있게 도와 주는 것이다. 
    - 즉, 개발자는 response 객체에다가 내가 원하는 데이터 넣으면 끝인 것이다.



<br/><br/>

## 전체적인 흐름

그림에 순서를 잘보자.

![이미지](/programming/img/서5.PNG)

1. url로 들어온다.

2. WAS는 Request, Response 객체를 새로 만들어서 서블릿 객체 호출 한다.

3. 개발자는 Request 객체에서 HTTP 요청 정보를 편리하게 꺼내서 사용한다.

3-1. 개발자는 Response 객체에 HTTP 응답 정보를 편리하게 입력한다.

3-2. 서블릿 컨테이너에서 끝나면 return 한다.

4~5. WAS는 Response 객체에 담겨있는 내용으로 HTTP 응답 정보를 만드는 것이다.

6. 그리하여 웹 브라우저로 반환 한다.

## 서블릿 컨테이너란?

WAS 안에는 서블릿을 지원하는 서블릿 컨테이너 라는 것이 있다.
- WAS안에서 서블릿 컨테이너가 ‘서블릿’ 객체를 자동으로 생성을 해주는 것이다.

    - 그리고 호출까지 해주며, 생명 주기가 있는데 WAS가 종료 될 때 서블릿을 같이 종료 시켜주는 것이다.


## 총 정리 서블릿 컨테이너

```
톰캣처럼 서블릿을 지원하는 WAS를 서블릿 컨테이너라고 한다
```

- 서블릿 컨테이너는 서블릿 객체를 생성, 초기화, 호출, 종료하는 생명주기를 관리한다.

- 서블릿 객체는 `싱글톤으로 관리`

    - 고객의 요청이 올 때 마다 계속 객체를 생성하는 것은 비효율

        - 이유는 `Service()` 로직 안에서만 만들기 때문이다.

    - 최초 로딩 시점에 서블릿 객체를 미리 만들어두고 재활용 한다.

    - `공유 변수 사용 주의`

    - 반대로 WAS는 계속 객체를 새로 생성하는 것이 맞다. 이유는 주문마다 다 다르기 때문이다.

- JSP도 서블릿으로 변환 되어서 사용

- `동시 요청을 위한 멀티 쓰레드 처리 지원`

## 궁금증!

```java
서블릿 객체가 하나뿐이라는 것을 어떻게 아나
```

`init()` 이 한 번만 불린다는 것으로 알 수 있다.

```java
public class MyServlet extends HttpServlet {

    @Override
    public void init() {
        System.out.println("init 호출");        // 첫 요청 때 한 번만
    }

    @Override
    protected void service(HttpServletRequest req, HttpServletResponse resp) {
        System.out.println("service 호출");     // 요청마다
    }
}
```

<br/>

요청을 백 번 보내도 `init` 은 한 번, `service` 는 백 번 찍힌다.

<br/>

## 생명주기가 네 단계다

```java
1. 로딩과 인스턴스화 - 클래스를 읽고 new 한다. 딱 한 번
2. init()           - 초기화. 딱 한 번
3. service()        - 요청마다
4. destroy()        - 서버 내릴 때. 딱 한 번
```

<br/>

앞의 @Primary, 빈 생명주기 콜백 글에서 본 스프링 빈의 생명주기와 모양이 같다.

```java
서블릿  - init() / service() / destroy()
스프링  - @PostConstruct / (메서드 호출) / @PreDestroy
```

<br/>

`만들고 -> 준비하고 -> 쓰고 -> 정리한다` 는 흐름은 어디서나 비슷하다.

<br/>

## 언제 만들어지는가

기본은 첫 요청이 올 때다.

```xml
<load-on-startup>1</load-on-startup>
```

<br/>

이걸 적으면 서버가 뜰 때 미리 만든다. 숫자는 순서다.

<br/>

앞의 빈 스코프 글에서 확인한 대로,

스프링은 반대로 기본이 미리 만드는 쪽이다.

```java
서블릿      - 기본은 지연 생성. load-on-startup 으로 미리 만들 수 있다
스프링 빈   - 기본은 미리 생성. @Lazy 로 미룰 수 있다
```

<br/>

스프링이 미리 만드는 이유는 설정 오류를 기동할 때 잡기 위해서다.

<br/>

## service() 가 doGet 을 부른다

```java
protected void service(HttpServletRequest req, HttpServletResponse resp) {
    String method = req.getMethod();
    if (method.equals("GET")) {
        doGet(req, resp);
    } else if (method.equals("POST")) {
        doPost(req, resp);
    }
    ...
}
```

<br/>

`HttpServlet` 안에 이 분기가 들어 있다.

그래서 우리는 `doGet` 만 오버라이딩하면 되는 것이다.

<br/>

앞의 템플릿 메서드 패턴 글에서 본 그 구조다.

```java
부모가 흐름을 잡고 (메서드를 골라 부르는 것)
자식이 빈칸을 채운다 (doGet 의 내용)
```

<br/>

`service()` 를 직접 오버라이딩하면 이 분기가 사라진다.

`doGet` 을 아무리 만들어도 안 불리게 되는 것이다.

<br/>

## 서블릿 하나로 다 처리하면

앞의 프론트 컨트롤러 패턴 소개 글에서 본 그 방향이다.

```java
@WebServlet(urlPatterns = "/*")
public class FrontControllerServlet extends HttpServlet { ... }
```

<br/>

스프링의 `DispatcherServlet` 이 이렇게 만들어진 것이다.

<br/>

그래서 스프링 MVC를 쓸 때 서블릿을 직접 만들 일이 거의 없다.

컨트롤러가 서블릿을 대신하는 것이다.

<br/>

```java
서블릿      - HttpServlet 을 상속해야 한다
컨트롤러    - 아무 클래스나 된다. @Controller 만 붙이면
```

<br/>

앞의 PSA(Portable Service Abstraction) 글에서 본 `POJO` 의 이득이다.

<br/>

## 서블릿 컨테이너가 하는 일

```java
서블릿 객체를 만들고 관리한다
요청이 오면 HttpServletRequest 를 만들어 넘긴다
응답이 끝나면 그것들을 버린다
동시 요청을 스레드로 처리한다
```

<br/>

`요청마다 객체를 만들어 넘기고 끝나면 버린다` 는 게 중요하다.

<br/>

앞의 리다이렉트, 디스패처 글에서 본 대로

`request.setAttribute()` 로 담은 값이 리다이렉트하면 사라지는 이유가 이것이다.

<br/>

앞의 멀티 쓰레드 글에서 확인한 대로

`Request` 는 요청마다 새로 만들어지니 안전하고,

서블릿 객체의 필드는 공유되니 위험한 것이다.

<br/>

## 요즘은 서블릿을 안 거치는 방식도 있다

```java
Spring WebFlux
```

<br/>

서블릿 스펙 대신 `Netty` 위에서 돈다.

`요청마다 스레드 하나` 를 안 쓰는 방식이다.

<br/>

앞의 스프링 MVC 구조 글에서 본 대로,

`DispatcherServlet` 대신 `DispatcherHandler` 가 그 자리에 있다.

<br/>

다만 코드가 어려워지고 디버깅이 힘들어서,

대부분의 서비스에서는 서블릿 기반으로 충분하다.

<br/>

자바 21의 가상 스레드가 나오면서 이 얘기는 또 달라지는 중이다.

`요청마다 스레드 하나` 를 유지하면서도 스레드가 싸지기 때문이다.
