## 문자열 연산

문자열 결합 연산자

ex) "10" + "개" = "10개"

<br/>


### MySQL에서는 CONCAT 함수로 문자열을 결합한다.

```sql
SELECT * FROM sample35;
```

| no | price | quantity | unit |
| --- | --- | --- | --- |
| 1 | 100 | 10 | 개 |
| 2 | 230 | 24 | 캔 |
| 3 | 1980 | 1 | 장 |

<br/>

### 출력

문자열 결합으로 단위를 연결해 결과 얻기

```sql
SELECT CONCAT(quantity,unit) FROM sample35;
```

| CONCAT(quantity,unit) |
| --- |
| 10개 |
| 24캔 |
| 1장 |

## SUBSTRING 함수

년, 월, 일을 각각 따로 추출해내고 싶은 경우들에서 사용하게 되는 것이다.

<br/>

앞 4자리(년) 추출

```sql
SUBSTRING('20140125001', 1, 4) -> '2014' 가져온다
```

<br/>

5째 자리부터 2자리(월) 추출

```sql
SUBSTRING('20140125001', 5, 2) -> '01' 가져온다
```

<br/><br/>

앞뒤로 여분의 스페이스가 있을 경우 이를 제거해주는 함수이다.

TRIM으로 스페이스 제거하기

```sql
TRIM('ABC    ') -> 'ABC' 으로 가져온다
```

## 궁금증!

```java
NULL 이 섞이면 연결 결과가 어떻게 되나
```

찍어봤다. 도시가 `NULL` 인 회원이 하나 있는 표다.

```sql
SELECT name || ' (' || city || ')' AS 표시 FROM member;
```

<br/>

### 결과

```java
김민석 (서울)
이영한 (부산)
박지성 (서울)
                <- 최민식 행. 통째로 비었다
한지민 (대구)
```

<br/>

이름까지 사라졌다.

<br/>

`NULL` 이 하나라도 끼면 결과 전체가 `NULL` 이 되기 때문이다.

앞의 검색 조건, NULL 값 글에서 본 `NULL + 무엇이든 = NULL` 이 문자열에도 적용된다.

<br/>

## 그래서 감싸줘야 한다

```sql
SELECT name || ' (' || COALESCE(city, '미입력') || ')' FROM member;
```

<br/>

`COALESCE` 를 안 쓰면 화면에 빈칸이 나오고,

`왜 이 회원만 이름이 없지` 를 한참 찾게 된다.

<br/>

## DB 마다 연결 방법이 다르다

```sql
표준 SQL, PostgreSQL, 오라클, SQLite   a || b
MySQL                                  CONCAT(a, b)
SQL Server                             a + b
```

<br/>

MySQL에서 `||` 는 기본 설정에서 논리 OR이다.

```sql
SELECT 'a' || 'b';      -- MySQL 에서는 0 이 나온다
```

<br/>

문자열을 숫자로 바꾸려니 둘 다 `0` 이 되고, `0 OR 0` 이 `0` 인 것이다.

<br/>

`PIPES_AS_CONCAT` 모드를 켜면 표준처럼 동작한다.

<br/>

## CONCAT_WS 가 NULL 을 다르게 다룬다

```sql
CONCAT('a', NULL, 'b')          ->  NULL
CONCAT_WS('-', 'a', NULL, 'b')  ->  'a-b'
```

<br/>

`WS` 는 `With Separator` 다.

구분자를 넣어주는 것이 주 목적인데, `NULL` 을 건너뛴다는 성질이 덤으로 유용하다.

<br/>

주소를 조립할 때 잘 맞는다.

```sql
CONCAT_WS(' ', city, street, detail)     -- 없는 항목은 알아서 빠진다
```

<br/>

## 문자열 함수에 함정이 하나 있다

```sql
SUBSTRING('안녕하세요', 1, 2)
```

<br/>

`1` 부터 시작한다. 프로그래밍 언어와 다르다.

```java
자바      "안녕하세요".substring(0, 2)     -> "안녕"
SQL       SUBSTRING('안녕하세요', 1, 2)     -> '안녕'
```

<br/>

두 번째 인자의 뜻도 다르다.

```java
자바  - 끝 위치 (exclusive)
SQL   - 길이
```

<br/>

`SUBSTRING(str, 2, 3)` 은 `2번째부터 3글자` 다.

<br/>

## LENGTH 가 바이트인지 글자인지

```sql
MySQL      LENGTH('안녕')     ->  6   (바이트)
MySQL      CHAR_LENGTH('안녕') ->  2   (글자)
오라클      LENGTH('안녕')     ->  2   (글자)
SQLite     LENGTH('안녕')     ->  2   (글자)
```

<br/>

MySQL의 `LENGTH` 만 바이트다.

<br/>

앞의 String 은 어떻게 저장될까 글에서 본 대로

UTF-8에서 한글 한 글자는 3바이트라 `6` 이 나온다.

<br/>

컬럼 길이를 정할 때도 이게 문제가 된다.

```sql
VARCHAR(10)
```

<br/>

MySQL 5.0부터는 글자 수라 한글 10글자가 들어간다.

그 전에는 바이트라 한글 3글자밖에 안 들어갔다.

<br/>

오래된 스키마에 `VARCHAR(50)` 인데 이름이 잘리는 경우가 이 잔재다.

<br/>

## 문자열 함수를 WHERE 에 쓰면 인덱스를 못 탄다

```sql
WHERE SUBSTRING(name, 1, 1) = '김'      -- 인덱스를 못 쓴다
WHERE name LIKE '김%'                    -- 인덱스를 쓴다
```

<br/>

인덱스에는 `name` 의 원래 값이 정렬되어 있지,

`SUBSTRING(name, 1, 1)` 의 결과가 정렬되어 있는 게 아니기 때문이다.

<br/>

앞의 LIKE, BETWEEN 글에서 확인한 그 차이다.

<br/>

컬럼을 함수로 감싸면 인덱스가 죽는다는 게 일반 규칙이다.

```sql
WHERE YEAR(created_at) = 2026                                  -- 못 쓴다
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01' -- 쓴다
WHERE UPPER(email) = 'A@B.C'                                   -- 못 쓴다
```

<br/>

요즘 DB는 함수 기반 인덱스를 지원해서 이걸 우회할 수 있다.

```sql
CREATE INDEX idx_year ON orders ((YEAR(created_at)));
```

<br/>

그래도 가능하면 컬럼을 그대로 두고 조건 쪽을 바꾸는 게 낫다.
