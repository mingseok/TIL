## 논리삭제

`삭제플러그` 같은 `열`을 미리 준비하여 사용한다.

실제 테이블 안에 데이터는 남아있지만, 참조할 때에는 `삭제플러그`가 삭제로 설정된 행을 제외하는 select 명령을 실행한다.

```
결과적으로는 해당 행이 삭제된 것처럼 보인다
```

<br/><br/>


## 상황에 맞게 선택하자.



### sns 서비스

사용자가 개인정보를 다루는 시스템에서는 사용자가 탈퇴한 경우 데이터를 삭제한다.

이때, 개인정보를 취급하는 마스터 테이블에서 삭제할 경우에는 물리삭제를 하는 편이 안전할 것이다.

개인정보의 유출을 미연에 방지하는 측면에서도 좋은 선택이라 할 수 있다.

<br/>

### 쇼핑 사이트

사용자가 주문을 취소할 경우에도 데이터를 삭제한다. 

이러한 경우에는 논리삭제 방법을 많이 사용한다.

<br/>

주문이 취소되었다고 해도 발주는 된 것으로, 해당 정보가 완전히 불필요한 것이라고는 말할 수 없기 때문이다.

이러한 데이터는 특히 주문 관련 통계를 낼 때 유용하게 사용할 수 있기 때문이다.

## 궁금증!

```java
논리 삭제를 하면 무엇이 번거로워지나
```

모든 쿼리에 조건이 하나씩 붙는다.

```sql
SELECT * FROM member WHERE deleted = false;
SELECT count(*) FROM member WHERE deleted = false;
SELECT * FROM member m JOIN orders o ON m.id = o.member_id WHERE m.deleted = false;
```

<br/>

하나라도 빼먹으면 지운 데이터가 화면에 나온다.

<br/>

그리고 조인할 때마다 양쪽에 다 붙여야 한다.

```sql
WHERE m.deleted = false AND o.deleted = false
```

## JPA 에서는 자동으로 붙일 수 있다

```java
@Entity
@SQLDelete(sql = "UPDATE member SET deleted = true WHERE id = ?")
@SQLRestriction("deleted = false")
public class Member { ... }
```

<br/>

`@SQLDelete` 는 `delete` 를 `update` 로 바꾼다.

`@SQLRestriction` 은 조회할 때 조건을 자동으로 붙인다.

<br/>

편한데 위험한 면도 있다.

<br/>

`삭제된 것까지 보고 싶다` 는 요구가 생기면 이 조건을 뺄 방법이 없다.

어드민 화면에서 곤란해지는 것이다.

## 유니크 제약이 깨진다

이게 제일 골치 아프다.

```sql
CREATE TABLE member (
    email VARCHAR(100) UNIQUE,
    deleted BOOLEAN
);
```

<br/>

`a@b.c` 로 가입했다가 탈퇴하고 다시 가입하려면 막힌다.

지운 행이 남아 있어서 유니크 제약에 걸리는 것이다.

<br/>

해결 방법이 몇 가지 있다.

```java
1. 탈퇴할 때 이메일을 바꾼다 (a@b.c -> deleted_123_a@b.c)
2. (email, deleted_at) 복합 유니크. NULL 은 중복을 허용하는 성질을 이용
3. 별도 테이블로 옮긴다
```

<br/>

`2번` 이 깔끔하다.

```sql
UNIQUE (email, deleted_at)
```

<br/>

살아 있으면 `deleted_at` 이 `NULL` 이라,

앞의 검색 조건, NULL 값 글에서 본 `NULL 은 서로 같지 않다` 는 성질 때문에

DB에 따라 여러 행이 허용되기도 한다.

<br/>

이 동작이 DB마다 다르니 확인하고 써야 한다.

MySQL은 `NULL` 이 여러 개 들어가고, SQL Server는 하나만 들어간다.

<br/>

## 인덱스가 비효율적이 된다

지운 데이터도 인덱스에 남는다.

```java
전체 100만 건 중 90만 건이 삭제 상태
-> 인덱스를 훑을 때 90%가 버려질 행
```

<br/>

부분 인덱스로 줄일 수 있다.

```sql
CREATE INDEX idx ON member(email) WHERE deleted = false;    -- PostgreSQL
```

<br/>

MySQL은 부분 인덱스가 없다.

그래서 오래된 삭제 데이터를 주기적으로 아카이브 테이블로 옮기기도 한다.

<br/>

## 그래도 논리 삭제를 쓰는 이유

```java
법적으로 일정 기간 보관해야 하는 데이터가 있다
실수로 지운 것을 복구할 수 있다
"누가 언제 지웠는가" 를 남길 수 있다
연관된 데이터가 참조 무결성을 잃지 않는다
```

<br/>

마지막이 실무에서 크다.

```java
회원을 물리 삭제하면 -> 그 회원의 주문 기록이 붕 뜬다
```

<br/>

주문 내역은 회계 자료라 지우면 안 되는데,

회원이 없으면 `누가 주문했는지` 를 알 수 없게 된다.

<br/>

## 절충안도 있다

```java
회원 정보는 논리 삭제하되, 개인정보만 비운다
```

<br/>

```sql
UPDATE member
SET name = '탈퇴회원', email = NULL, phone = NULL, deleted_at = NOW()
WHERE id = ?;
```

<br/>

개인정보 보호법상 파기 의무는 지키면서,

주문 내역의 참조는 살아 있게 하는 방식이다.

<br/>

앞의 개념적 데이터 모델링 글에서 본 대로,

`무엇을 지울 것인가` 가 아니라 `무엇을 남겨야 하는가` 부터 정하면 답이 나온다.
