## 데이터베이스 객체

테이블이나 뷰, 인덱스 등 데이터베이스 내에 정의하는 모든 것을 일컫는 말이다.

```
단순히, java 등등 객체지향 프로그래밍의 '객체'와 혼돈하는 경향이 있는데 틀렸다.
```

<br/>

지금까지 학습한 것 중에 객체에 해당하는 것은 테이블이였다. (행과 열이 저장)

하지만, `select`나 `insert` 등은 클라이언트에서 객체를 조작하는 SQL 명령이다.

```
데이터베이스 내에 존재하는 것이 아니므로 객체라 부를수 없다
```

<br/><br/>

### NOT NULL?

열이 `null`을 허용할 것인지를 지정한다.

`null`을 명시적으로 지정하거나 생략했을 경우는 `null`을 허용한다.

한편 `not null`이라고 지정하면 제약이 걸리면서 `null`이 허용되지 않는다.


```sql
create table sample62 (
    no integer NOT NULL,
    a varchar(30),
    b date
);

DESC sample62;
```


| Field | Type | Null | Key | Default | Extra |
| --- | --- | --- | --- | --- | --- |
| no | int(11) | NO |  | NULL |  |
| a | varchar(30) | YES |  | NULL |  |
| b | date | YES |  | NULL |  |


<br/><br/>

## 테이블 삭제

필요 없는 테이블은 삭제할 수 있다.

```sql
DROP TABLE 테이블명
```

<br/>

테이블 정의는 그대로 둔 채 데이터만 삭제할 때는 `DELETE` 명령을 사용한다.

하지만, `DELETE` 명령은 행 단위로 여러 가지 내부처리가 일어나므로 삭제할 행이 많으면 처리속도가 상당히 늦어진다.

```
그렇기에 모든 행을 삭제해야 할때 T'RUNCATE TABLE' 명령을 사용하면 빠른 속도로 삭제할 수 있다
```

## 궁금증!

```java
운영 중인 테이블에 컬럼을 추가하면 어떻게 되나
```

이게 실무에서 제일 조심해야 할 부분이다.

```sql
ALTER TABLE orders ADD COLUMN memo VARCHAR(255);
```

<br/>

MySQL 5.6 이전에는 이 한 줄이 테이블 전체를 복사했다.

그동안 쓰기가 막힌다. 천만 건이면 수십 분 동안 서비스가 멈추는 것이다.

<br/>

5.6부터 온라인 DDL이 생겨서 대부분 안 막힌다.

```sql
ALTER TABLE orders ADD COLUMN memo VARCHAR(255), ALGORITHM=INPLACE, LOCK=NONE;
```

<br/>

`LOCK=NONE` 을 명시하면 락이 필요한 작업일 때 아예 오류를 낸다.

`될 줄 알았는데 서비스가 멈췄다` 를 막아주는 것이다.

<br/>

## 작업마다 다르다

```java
컬럼 추가 (맨 뒤)      -> 대체로 온라인
컬럼 삭제              -> 테이블 재구축
컬럼 타입 변경         -> 테이블 재구축
인덱스 추가            -> 온라인
컬럼 이름 변경         -> 메타데이터만. 빠르다
DEFAULT 값 변경        -> 메타데이터만
```

<br/>

MySQL 8.0부터는 `ADD COLUMN` 이 즉시 끝나는 경우가 있다.

```sql
ALGORITHM=INSTANT
```

<br/>

메타데이터에만 기록하고 실제 행은 안 건드리는 방식이다.

<br/>

## 그래서 마이그레이션 도구를 쓴다

```java
Flyway, Liquibase
```

<br/>

`언제 무엇을 바꿨는지` 를 파일로 남기고 순서대로 적용한다.

<br/>

앞의 프로젝트 컨벤션에도 나오듯,

JPA의 `ddl-auto=validate` 와 같이 쓰면 스키마와 엔티티가 어긋나는 걸 기동할 때 잡는다.

```java
ddl-auto=create    - 운영에서 절대 금지. 테이블을 지우고 다시 만든다
ddl-auto=update    - 컬럼을 지우지는 않는다. 그래도 운영에서는 안 쓴다
ddl-auto=validate  - 확인만 한다. 운영은 이걸 쓴다
```

<br/>

`update` 가 위험한 이유는 무엇을 할지 예측이 안 되기 때문이다.

인덱스나 제약 조건은 제대로 안 만들어주는 경우도 많다.

<br/>

## 컬럼 순서에도 의미가 있다

```sql
ALTER TABLE member ADD COLUMN age INT AFTER name;
```

<br/>

중간에 넣으면 테이블을 재구축해야 한다.

맨 뒤에 붙이면 훨씬 싸다.

<br/>

그래서 운영 테이블에는 항상 뒤에 붙인다.

컬럼 순서가 지저분해져도 그게 낫다.

<br/>

## 제약 조건을 어디까지 걸 것인가

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    member_id BIGINT NOT NULL,
    amount INT NOT NULL CHECK (amount >= 0),
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (member_id) REFERENCES member(id)
);
```

<br/>

실무에서 의견이 갈리는 게 외래 키다.

```java
거는 쪽  - 데이터가 깨지는 걸 DB 가 막아준다
안 거는 쪽 - 락 범위가 넓어지고, 샤딩이나 대량 작업에 걸림돌이 된다
```

<br/>

외래 키가 있으면 자식 행을 넣을 때 부모 행에 락이 걸린다.

동시성이 높은 곳에서는 이게 병목이 되기도 한다.

<br/>

그래서 트래픽이 큰 서비스는 외래 키를 안 걸고

애플리케이션에서 확인하는 쪽을 택하기도 한다.

<br/>

## CHECK 제약은 오래 무시됐다

MySQL은 8.0.16 전까지 `CHECK` 를 문법만 받고 무시했다.

```sql
CHECK (amount >= 0)      -- 5.7 에서는 아무 일도 안 한다
```

<br/>

오류도 안 나고 그냥 안 걸린다.

`제약을 걸었다고 생각했는데 안 걸려 있는` 상태가 되는 것이다.

<br/>

지금은 제대로 동작한다.

<br/>

## 인덱스는 나중에 추가하는 게 낫다

대량 데이터를 넣을 때 인덱스가 있으면 느리다.

행을 넣을 때마다 인덱스도 갱신해야 하기 때문이다.

```sql
1. 인덱스 없이 테이블을 만든다
2. 데이터를 넣는다
3. 인덱스를 만든다
```

<br/>

앞의 인덱스 구조 글에서 본 대로,

B+트리를 한 번에 만드는 게 하나씩 넣으면서 재조정하는 것보다 훨씬 빠르다.

<br/>

## DROP 은 되돌릴 수 없다

```sql
DROP TABLE member;
```

<br/>

`DDL` 은 대부분 암묵적으로 커밋된다.

트랜잭션 안에서 실행해도 롤백이 안 되는 것이다.

<br/>

PostgreSQL은 예외라서 `DDL` 도 롤백된다.

MySQL과 오라클은 안 된다.

<br/>

그래서 운영에서 테이블을 지울 때는 이름을 바꿔두는 방식을 쓴다.

```sql
RENAME TABLE member TO member_backup_20260901;
```

<br/>

며칠 지켜보고 문제가 없으면 그때 지우는 것이다.

앞의 물리논리삭제 글에서 본 발상을 테이블 단위로 적용한 셈이다.
