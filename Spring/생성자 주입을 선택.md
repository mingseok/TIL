## 생성자 주입을 선택

## 불변

생성자 주입은 객체를 생성할 때 딱 1번만 호출되므로 이후에 호출되는 일이 없다. 

따라서 불변하게 설계할 수 있다.

<br/>

대부분의 의존관계 주입은 한번 일어나면 애플리케이션 종료시점까지 의존관계를 변경할 일이 없다. 

오히려 대부분의 의존관계는 애플리케이션 종료 전까지 변하면 안된다. (불변해야 한다.)

<br/>

수정자 주입을 사용하면, setXxx 메서드를 public으로 열어두어야 한다.

- 누군가 실수로 변경할 수 도 있다.

- 변경하면 안되는 메서드를 열어두는 것은 좋은 설계 방법이 아니다.

<br/><br/>

## final 키워드

생성자 주입을 사용하면 필드에 final 키워드를 사용할 수 있다. 

그래서 생성자에서 혹시라도 값이 설정되지 않는 오류를 컴파일 시점에 막아준다.

<br/>

수정자 주입을 포함한 나머지 주입 방식은 모두 생성자 이후에 호출되므로, 

필드에 final 키워드를 사용할 수 없다. 오직 생성자 주입 방식만 final 키워드를 사용할 수 있다.

<br/><br/>

## 정리

생성자 주입 방식을 선택하는 이유는 여러가지가 있지만, 

프레임워크에 의존하지 않고, 순수한 자바 언어의 특징을 잘 살리는 방법이기도 하다.

```
항상 생성자 주입을 선택해라
```

## 궁금증!

```java
정말 생성자 주입이 더 안전한지 직접 돌려봤다
```

순환 참조를 일부러 만들어놓고 두 방식을 비교했다.

```java
class CA { CA(CB b) {} }        // A 가 B 를 필요로 하고
class CB { CB(CA a) {} }        // B 가 A 를 필요로 한다
```

<br/>

### 결과

```java
--- 1) 순환 참조: 생성자 주입 ---
  UnsatisfiedDependencyException
  -> Error creating bean with name 'ca' ... Unsatisfied dependency

--- 2) 순환 참조: 수정자(setter) 주입 ---
  기동 성공. A 가 들고 있는 B = true
  -> 순환인데도 기동은 된다
```

<br/>

생성자 주입은 서버가 뜨다가 멈춘다.

수정자 주입은 아무 일 없이 기동된다.

<br/>

## 왜 이런 차이가 나는가

객체를 만드는 시점이 다르기 때문이다.

```java
생성자 주입 - 객체를 만들려면 B 가 필요하다 -> B 를 만들려면 A 가 필요하다 -> 막힌다
수정자 주입 - 일단 A 를 빈 채로 만든다 -> B 도 만든다 -> 그 다음에 서로 꽂아준다
```

<br/>

수정자 주입은 `만들기` 와 `채우기` 가 나뉘어 있어서 순환이 끊긴다.

<br/>

문제는 그게 좋은 게 아니라는 점이다.

순환 참조는 설계가 잘못된 신호인데, 그걸 덮어버리고 기동해버리는 것이다.

<br/>

앞의 SOLID 글에서 본 의존관계 역전 원칙이 깨진 상태를

서버가 알려주지 않고 넘어가는 셈이다.

<br/>

## 주입이 안 된 채로 쓰면

```java
SA lonely = new SA();      // 테스트에서 그냥 new 한 상황
lonely.work();
```

```java
NullPointerException <- 실행할 때야 터진다
```

<br/>

수정자 주입은 `new` 로 만들면 안이 비어 있다.

컴파일은 통과하고, 그 객체를 실제로 쓸 때야 터진다.

<br/>

생성자 주입이면 이 코드가 아예 컴파일이 안 된다.

```java
SA lonely = new SA();      // 컴파일 오류. 생성자가 SB 를 요구한다
```

<br/>

`무엇이 필요한지` 가 생성자 시그니처에 적혀 있기 때문이다.

<br/>

## final 을 붙일 수 있다

```java
private final MemberRepository memberRepository;

public MemberService(MemberRepository memberRepository) {
    this.memberRepository = memberRepository;
}
```

<br/>

앞의 final 키워드 글에서 본 대로, `final` 은 한 번 대입하면 못 바꾼다.

<br/>

수정자 주입은 `final` 을 못 붙인다. 나중에 대입해야 하기 때문이다.

그래서 누군가 실수로 중간에 바꿔버릴 수 있다.

```java
service.setMemberRepository(다른것);     // 운영 중에 갈아끼울 수 있다
```

<br/>

`final` 이면 이 메서드 자체가 존재할 수 없다.

<br/>

## 생성자가 하나면 @Autowired 를 생략할 수 있다

```java
@Component
public class MemberService {

    private final MemberRepository memberRepository;

    public MemberService(MemberRepository memberRepository) {   // @Autowired 없음
        this.memberRepository = memberRepository;
    }
}
```

<br/>

생성자가 하나뿐이면 스프링이 알아서 그 생성자를 쓴다.

<br/>

앞의 lombok 글에서 본 `@RequiredArgsConstructor` 를 붙이면 이것도 사라진다.

```java
@Component
@RequiredArgsConstructor
public class MemberService {
    private final MemberRepository memberRepository;
}
```

<br/>

`final` 필드만 모아서 생성자를 만들어주므로,

필드를 추가하면 생성자도 알아서 늘어난다.

<br/>

## 그럼 수정자 주입은 언제 쓰나

바뀔 수 있는 의존관계일 때다. 실무에서는 거의 없다.

<br/>

굳이 꼽자면 선택적 의존관계 정도인데, 그것도 생성자에서 처리할 수 있다.

```java
@Autowired(required = false)
public void setStat(StatCollector stat) { ... }
```

```java
public MemberService(MemberRepository repo, Optional<StatCollector> stat) { ... }
```

<br/>

결론은 생성자 주입 하나만 쓰면 된다는 것이다.

스프링 공식 문서도 그렇게 권한다.
