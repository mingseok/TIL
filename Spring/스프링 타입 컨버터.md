## 스프링 타입 컨버터

<br/>

## 왜 필요한가?

HTTP 요청으로 들어오는 값은 전부 문자열이다.

앞의 form 태그 글에서 요청을 직접 찍어봤을 때도 그랬다.

```java
GET /members?age=30

[본문] (없음)
```

<br/>

`30` 이 아니라 `"30"` 이라는 글자로 온다.

그런데 컨트롤러에서는 이렇게 받는다.

```java
@GetMapping("/members")
public String find(@RequestParam Integer age) {
    // age 는 이미 Integer 다
}
```

<br/>

누군가 중간에서 `"30"` 을 `30` 으로 바꿔준 것이다. 그 일을 하는 것이 타입 컨버터다.

<br/>

## 컨버터가 없다면

```java
@GetMapping("/members")
public String find(HttpServletRequest request) {
    String ageParam = request.getParameter("age");
    Integer age = Integer.parseInt(ageParam);        // 매번 직접 바꿔야 한다
}
```

<br/>

파라미터를 받을 때마다 이 변환 코드가 붙는다.

숫자면 `parseInt`, 날짜면 `LocalDate.parse`, `boolean` 이면 또 다른 코드가 필요하다.

<br/>

그리고 변환에 실패했을 때 처리도 매번 적어야 한다.

앞의 Validation 글에서 본 `typeMismatch` 오류가 자동으로 담기는 것도 컨버터 덕분이다.

<br/>

## 기본으로 되는 것들

`ConversionService` 를 직접 만들어서 무엇이 되는지 찍어봤다.

```java
DefaultConversionService service = new DefaultConversionService();

System.out.println(service.convert("10", Integer.class));
System.out.println(service.convert("true", Boolean.class));
System.out.println(service.convert("A,B,C", String[].class).length);
System.out.println(service.convert(Grade.GOLD, String.class));
System.out.println(service.convert("SILVER", Grade.class));
```

<br/>

### 결과

```java
"10" -> Integer  = 10
"true" -> Boolean = true
"A,B,C" -> String[] 길이 = 3
Grade.GOLD -> String = GOLD
"SILVER" -> Grade   = SILVER
```

<br/>

기본 타입은 물론이고 배열과 `enum` 까지 알아서 처리한다.

`"A,B,C"` 를 콤마로 잘라 배열로 만드는 것도 기본이다.

<br/>

`enum` 이 되는 것이 실무에서 꽤 유용하다.

```java
@GetMapping("/members")
public String find(@RequestParam Grade grade) { ... }
```

```java
GET /members?grade=GOLD
```

<br/>

문자열을 받아서 직접 `Grade.valueOf()` 를 부를 필요가 없다.

없는 값이 들어오면 변환에 실패하면서 `400` 이 나가니, 앞의 enum 글에서 본 타입 안전성이 여기까지 이어진다.

<br/>

## 궁금증!

```java
그럼 내가 만든 타입은 어떻게 될까?
```

`IpPort` 라는 클래스를 만들어서 변환을 시도해봤다.

```java
class IpPort {
    private final String ip;
    private final int port;
}
```

```java
service.convert("127.0.0.1:8080", IpPort.class);
```

<br/>

### 결과

```java
ConverterNotFoundException : 변환기가 없다
```

<br/>

당연히 안 된다. 스프링이 `127.0.0.1:8080` 이라는 글자를 어떻게 쪼개야 할지 알 수가 없다.

<br/>

## Converter 를 만들어 등록하면

```java
class StringToIpPortConverter implements Converter<String, IpPort> {
    @Override
    public IpPort convert(String source) {
        String[] split = source.split(":");
        return new IpPort(split[0], Integer.parseInt(split[1]));
    }
}
```

```java
service.addConverter(new StringToIpPortConverter());
IpPort ipPort = service.convert("127.0.0.1:8080", IpPort.class);
```

<br/>

### 결과

```java
등록 후 = IpPort(ip=127.0.0.1, port=8080)
```

<br/>

인터페이스 하나에 메서드 하나뿐이다.

```java
public interface Converter<S, T> {
    T convert(S source);
}
```

<br/>

`S` 에서 `T` 로 바꾼다는 것만 정해져 있고, 어떻게 바꿀지는 내가 정한다.

앞의 인터페이스 글에서 본 `무엇을 할 수 있는지만 정하고 방법은 안 물려준다` 가 그대로다.

<br/>

## 스프링 MVC 에 등록하기

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addFormatters(FormatterRegistry registry) {
        registry.addConverter(new StringToIpPortConverter());
    }
}
```

<br/>

이렇게 등록하면 컨트롤러 파라미터에서 바로 쓸 수 있다.

```java
@GetMapping("/ip-port")
public String test(@RequestParam IpPort ipPort) {
    // "127.0.0.1:8080" 이 IpPort 객체로 들어와 있다
}
```

<br/>

앞의 요청 매핑 헨들러 어뎁터 글에서 본 `ArgumentResolver` 가 값을 꺼낸 다음,

이 `ConversionService` 에게 타입 변환을 맡기는 구조다.

```java
ArgumentResolver  - 어디서 값을 가져올지 정한다 (파라미터인지 헤더인지 경로인지)
ConversionService - 가져온 문자열을 어떤 타입으로 바꿀지 정한다
```

<br/>

## Formatter 는 무엇이 다른가

`Converter` 와 비슷한데 용도가 좁다.

```java
Converter<S, T>  - 아무 타입에서 아무 타입으로. 범용
Formatter<T>     - 문자열과 객체 사이만. 대신 Locale 을 받는다
```

<br/>

```java
public interface Formatter<T> {
    T parse(String text, Locale locale) throws ParseException;
    String print(T object, Locale locale);
}
```

<br/>

`Locale` 이 들어가는 것이 핵심이다.

```java
1,000,000       <- 한국
1.000.000       <- 독일
2026-01-01      <- 한국
01/01/2026      <- 미국
```

<br/>

같은 숫자와 날짜를 나라마다 다르게 표기해야 할 때 `Formatter` 를 쓴다.

앞의 스프링 메시지 글에서 본 국제화와 같은 맥락이다.

<br/>

## 어노테이션으로 붙이는 방법이 더 많이 쓰인다

필드마다 형식이 다르면 `Formatter` 를 여러 개 만들어야 한다.

그래서 어노테이션으로 형식을 지정하는 방식이 따로 있다.

```java
public class Form {
    @NumberFormat(pattern = "###,###")
    private Integer price;

    @DateTimeFormat(pattern = "yyyy-MM-dd HH:mm:ss")
    private LocalDateTime createdAt;
}
```

<br/>

`AnnotationFormatterFactory` 라는 것이 이 어노테이션을 읽어서

그 필드에만 맞는 `Formatter` 를 만들어 쓴다.

<br/>

스프링 부트는 이 둘을 기본으로 등록해준다.

`LocalDateTime` 을 그냥 받을 수 있는 것이 이 덕분이다.

<br/>

## 컨버터가 적용되지 않는 곳

`@RequestBody` 에는 안 통한다. 이게 헷갈리기 쉬운 부분이다.

```java
@PostMapping("/api/items")
public String add(@RequestBody ItemRequest request) { ... }
```

<br/>

`@RequestBody` 는 앞의 HTTP 메시지 컨버터 글에서 본 대로 Jackson이 처리한다.

`ConversionService` 는 아예 안 거친다.

```java
@RequestParam, @ModelAttribute, @PathVariable -> ConversionService 를 탄다
@RequestBody                                   -> HttpMessageConverter (Jackson) 이 처리
```

<br/>

그래서 `IpPort` 를 JSON으로 받고 싶으면 `Converter` 가 아니라

Jackson의 `JsonDeserializer` 를 만들어야 한다.

<br/>

같은 `변환` 이라는 말이지만 담당하는 곳이 다르다는 것을 알아두면 헤매지 않는다.
