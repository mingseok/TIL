## 스프링이 뭔가?

스프링은 특정한 하나가 아니라, 여러가지 기술들의 모음이라고 말할 수 있다.

<br/>

먼저 스프링의 핵심인 `스프링 프레임워크`, 그리고 여러 기술들을 편리하게 사용해주는

`스프링 부트`, 그 외 `스프링 데이터` , `스프링 세션`, `스프링 시큐리티` 등이 있다.

<br/><br/>

## 가장 중요한 스프링 프레임워크

하나로 이루어진 것이 아니고, 여러개로 이루어져 있다.

<br/>

이런 것들을 전부 합하여 `스프링 프레임워크`라고 부른다.

1. 핵심 기술 : DI 컨테이너, AOP, 이벤트, 기타 등등이 있다.

2. 웹 기술 : MVC, 스프링 WebFlux
3. 데이터 접근 기술 : 트랜잭션, JDBC, ORM 지원
4. 기술 통합 : 캐시, 이메일, 원격접근
5. 테스트 : 스프링 기반 테스트 지원
6. 언어 : 코틀린, 그루비

<br/><br/>

## 하지만 스프링 프레임워크만 사용하는 것이 아니다.

스프링 프레임워크를 편리하게 사용할 수 있는 스프링 부트를 통해서 스프링 프레임워크를 사용한다. 

(스프링 부트는 스프링을 편리하게 사용하기 위해 지원하는 기술.)

<br/>

## 스프링 부트 장점

- Tomcat 같은 웹 서버를 내장해서 별도의 웹 서버를 설치하지 않아도 됨

- 빌드 구성을 위한 starter 종속성 제공
    - 즉, 라이브러리를 사용할 때 여러개 묶어서 사용해야 되는데, 그런 부분에 대해서
    
         편하게 하나만 사용하면 starter가 나머지 라이브러리도 같이 가져오는 것이다.
- 스프링과 외부 라이브러리 자동 구성
    - 즉, 외부 라이브러리 버전에 대해서 스프링이 체크해주는 것이다.

- 관례에 의한 간결한 설정

<br/>

```
기본적으로 스프링 부트는 꼭 스프링 프레임워크를 사용을 해서 도와주는 기술이지 
이것만 가지고 돌아가는 프로젝트가 아니다.
```

<br/><br/>

## 왜 스프링을 만들었을까? , 핵심은 뭐지?

- 스프링은 자바 언어 기반의 프레임워크
    - 자바 언어의 가장 큰 특징은 : 객체 지향 언어

즉, 스프링은 좋은 객체 지향 애플리케이션을 개발할 수 있게 

도와주는 프레임워크 이다.

## 부트가 없던 시절

앞의 서블릿 설명 내부 동작 글에서 본 `web.xml` 을 직접 써야 했다.

```xml
<servlet>
    <servlet-name>dispatcher</servlet-name>
    <servlet-class>org.springframework.web.servlet.DispatcherServlet</servlet-class>
</servlet>
<servlet-mapping>
    <servlet-name>dispatcher</servlet-name>
    <url-pattern>/</url-pattern>
</servlet-mapping>
```

<br/>

여기에 톰캣을 따로 깔고, `war` 를 말아서 그 안에 넣고, 라이브러리 버전을 하나씩 맞췄다.

<br/>

부트가 이걸 다 없앴다.

```java
@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

<br/>

```java
내장 톰캣          - 서버를 따로 안 깐다
자동 설정          - 라이브러리를 보고 필요한 빈을 알아서 등록
스타터 의존관계    - 버전 조합을 미리 맞춰둔 묶음
```

<br/>

## 스프링의 핵심은 결국 하나다

앞의 스프링 컨테이너, 스프링 빈 글에서 본 그것이다.

```java
객체를 누가 만들고 누가 연결할 것인가
```

<br/>

```java
// 스프링 없이
MemberRepository repository = new MemoryMemberRepository();
MemberService service = new MemberService(repository);
```

<br/>

내가 만들고 내가 연결한다.

구현체를 바꾸려면 이 코드를 고쳐야 한다.

<br/>

```java
// 스프링
@Service
public class MemberService {
    private final MemberRepository memberRepository;

    public MemberService(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }
}
```

<br/>

`나는 MemberRepository 가 필요하다` 만 적는다.

무엇을 넣을지는 컨테이너가 정한다.

<br/>

앞의 IoC (=제어의 역전) 글에서 본 그 뒤집힘이다.

<br/>

## 그래서 무엇이 좋아지는가

바꿔 끼우기가 쉬워진다.

```java
운영    -> JpaMemberRepository
테스트  -> MemoryMemberRepository
```

<br/>

`MemberService` 는 안 고친다. 어느 것이 들어와도 같은 코드다.

<br/>

앞의 SOLID 글에서 본 개방-폐쇄 원칙이 이걸 말한 것이다.

```java
확장에는 열려 있고 (새 구현체를 넣을 수 있다)
변경에는 닫혀 있다 (기존 코드는 안 고친다)
```

<br/>

## 자바로 웹을 만드는 방법이 스프링만 있는 건 아니다

```java
Jakarta EE      - 자바 표준. 스프링이 나온 이유이기도 하다
Quarkus, Micronaut - 기동이 빠른 쪽에 초점
Ktor            - 코틀린
```

<br/>

스프링이 처음 나왔을 때는 당시의 EJB가 너무 무겁다는 반발에서 시작했다.

`무거운 것 대신 평범한 자바 객체로 하자` 는 것이었다.

<br/>

앞의 PSA(Portable Service Abstraction) 글에서 본 `POJO` 라는 말이 그때 나온 것이다.

```java
Plain Old Java Object
= 특정 기술을 상속하거나 구현하지 않은 그냥 자바 객체
```

<br/>

지금은 스프링 자체가 커져서 그때의 EJB만큼 무겁다는 얘기도 나온다.

그래서 가벼운 쪽을 내세운 것들이 또 나오는 것이다.

<br/>

무엇이 정답이라기보다, 무거워지면 가벼운 것이 나오고

그게 또 커지면 다시 가벼운 것이 나오는 흐름이라고 보면 된다.
