## 궁금증!

```java
왜 매핑과 어댑터가 짝을 이루는가
```

하는 일이 다르기 때문이다.

```java
HandlerMapping - "이 URL 은 누가 처리하나" 를 찾는다. URL 이 기준
HandlerAdapter - "그 누구를 어떻게 부르나" 를 찾는다. 핸들러의 타입이 기준
```

<br/>

`spring-webmvc` 안에 짝으로 들어 있다.

```java
RequestMappingHandlerMapping   <-> RequestMappingHandlerAdapter
   @Controller + @RequestMapping 방식

BeanNameUrlHandlerMapping      <-> SimpleControllerHandlerAdapter
   Controller 인터페이스를 구현한 옛날 방식

SimpleUrlHandlerMapping        <-> HttpRequestHandlerAdapter
   정적 리소스 처리 등
```

<br/>

`DispatcherServlet` 은 각 목록을 순서대로 돌면서 물어본다.

```java
// 1단계
for (HandlerMapping mapping : 매핑목록) {
    HandlerExecutionChain handler = mapping.getHandler(request);
    if (handler != null) return handler;
}

// 2단계
for (HandlerAdapter adapter : 어댑터목록) {
    if (adapter.supports(handler)) return adapter;
}
```

<br/>

## HandlerExecutionChain 이라는 이름

`getHandler()` 가 돌려주는 것은 컨트롤러 하나가 아니다.

```java
HandlerExecutionChain
  - handler       : 실행할 컨트롤러
  - interceptors  : 그 앞뒤로 실행할 인터셉터들
```

<br/>

앞의 필터, 스프링 인터셉터 설명 글에서 본 그 인터셉터가 여기서 붙는다.

```java
인터셉터.preHandle() -> 어댑터.handle() -> 컨트롤러 -> 인터셉터.postHandle()
```

<br/>

그래서 인터셉터는 어느 핸들러인지 알 수 있고, 필터는 모른다.

필터는 `getHandler()` 가 실행되기 전에 지나가기 때문이다.

<br/>

## 어댑터 패턴이라는 이름

앞의 Handler vs HandlerAdapter 글에서 본 그 비유가 정확하다.

```java
콘센트(DispatcherServlet)는 한 가지 방식만 낸다
기기(컨트롤러)마다 부르는 법이 다르다
-> 어댑터가 사이에서 맞춰준다
```

<br/>

어댑터 덕분에 `DispatcherServlet` 은 이 메서드 하나만 알면 된다.

```java
ModelAndView handle(HttpServletRequest request, HttpServletResponse response, Object handler);
```

<br/>

새 모양의 컨트롤러가 생기면 어댑터를 하나 만들어 등록하면 끝이다.

`DispatcherServlet` 은 안 고친다.

<br/>

앞의 인터페이스를 왜 사용하는가 글에서 본 그 이득이다.

<br/>

`이미 배포된 것을 깨지 않으면서 새 방식을 추가한다` 는 방침이 이 목록에도 드러나 있다.

## RequestMappingHandlerAdapter 안이 제일 복잡하다

앞의 요청 매핑 헨들러 어뎁터 구조 글에서 본 대로,

이 어댑터 안에 또 한 겹이 있다.

```java
RequestMappingHandlerAdapter
  -> ArgumentResolver   (파라미터를 채운다. 20개쯤 있다)
       -> HttpMessageConverter  (본문 <-> 객체 변환)
  -> 컨트롤러 메서드 실행
  -> ReturnValueHandler (반환값을 처리한다)
       -> HttpMessageConverter
```

<br/>

컨트롤러 메서드의 파라미터를 마음대로 적을 수 있는 것이 이 구조 덕분이다.

```java
public String find(@PathVariable Long id,
                   @RequestParam String keyword,
                   HttpServletRequest request,
                   Model model,
                   Locale locale) { ... }
```

<br/>

순서를 바꿔도 되고 필요 없는 것은 빼도 된다.

리졸버 스무 개가 각자 자기 몫을 알아서 채워주기 때문이다.
