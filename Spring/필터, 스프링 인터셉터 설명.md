## 필터, 스프링 인터셉터 설명

<br/>

특정 URL이 들어 왔을땐, 인증을 할 것이고, 특정 URL이 아닐때는 하지 않는다.

```
ex : “특정 URL로 오는건 다 막아” 같은 이런것이 가능하다.
```

필터, 인터셉터를 사용하지 않는다면, 코드를 이렇게 작성해야 될 것이다.

모든 곳에 중복 코드를 작성해야 한다.

<br/>

그리하여 필터, 인터셉터를 사용하면 중복 코드 없이 한번에 해결 가능하다.

```java
@Controller
public class LoginController {

    @GetMapping("/...")
    public String loginForm(...) {

        // 로그인 여부 체크 로직

        return "login/loginForm";
    }

    @PostMapping("/...")
    public String loginV2(...) {

        // 로그인 여부 체크 로직

        return "redirect:/";
    }

    @PostMapping("/...")
    public String loginV3(...) {

        // 로그인 여부 체크 로직

        return "redirect:/";
    }
}
```

## 스프링 인터셉터 흐름

```
HTTP 요청 -> WAS -> 필터 -> 서블릿 -> 스프링 인터셉터 -> 컨트롤러
```

- 서블릿 : 디스패처 서블릿을 말하는 것이다.
  
- 스프링 인터셉터는 `디스패처 서블릿`과 `컨트롤러 사이`에서 컨트롤러 호출 직전에 호출 된다.
- 스프링 MVC의 시작점이 디스패처 서블릿이라고 생각하기.
  
- 스프링 인터셉터에도 URL 패턴을 적용할 수 있는데, 서블릿 URL 패턴과는 다르고, 매우 정밀하게 설정할 수 있다.
    

<br/><br/>

## 스프링 인터셉터 제한

`로그인 사용자 :` HTTP 요청 -> WAS -> 필터 -> 서블릿 -> 스프링 인터셉터 -> 컨트롤러

`비 로그인 사용자 :` HTTP 요청 -> WAS -> 필터 -> 서블릿 -> 스프링 인터셉터 →
                                 적절하지 않은 요청이라 판단, 컨트롤러 호출 X

```
그리하여, 로그인 여부를 체크하기에 딱 좋다.
```

<br/><br/>

```
HTTP 요청 -> WAS -> 필터 -> 서블릿 -> 인터셉터1 -> 인터셉터2 -> 컨트롤러
```

로그를 남기는 인터셉터를 먼저 적용하고, 

그 다음에 로그인 여부를 체크하는 인터셉터를 만들 수 있다

## 스프링 인터셉터 호출 흐름

![이미지](/programming/img/입문137.PNG)

- `preHandle` : 컨트롤러 호출 전에 호출된다. (더 정확히는 핸들러 어댑터 호출 전에 호출된다.)

    - `preHandle` 의 응답값이 `true` 이면 다음으로 진행하고, `false` 이면 더는 진행하지 않는다.

    - `false`인 경우 나머지 인터셉터는 물론이고, 핸들러 어댑터도 호출되지 않는다.

    - 그림에서 1번에서 끝이 나버린다.

- `postHandle` : 컨트롤러 호출 후에 호출된다.

    - (더 정확히는 핸들러 어댑터 호출 후에 호출된다.)

- `afterCompletion` : 뷰가 렌더링 된 이후에 호출된다.

<br/><br/>

## `postHandle` 와 `afterCompletion` 의 차이

개발을 잘 했는데, 핸들러(컨트롤러)에서 예외가 터진 것이다.

그러면 3번에서 4번으로 넘길때 예외가 터진 것을 넘기는 것이다.

```
이때, 디스패처 서블릿에서 postHandle 가 호출이 되지 않는다.

그리고 afterCompletion 같은 경우는 예외가 터지든 말든 항상 호출되는 것이다.
```

<br/>

![이미지](/programming/img/입문138.PNG)

그리하여 차이는 예외가 발생해도 호출된다 vs 안된다 의 차이인 것이다.

- 예외와 무관하게 공통 처리를 하려면 `afterCompletion()` 을 사용해야 한다.

- 예외가 발생하면 `afterCompletion()` 에 `예외 정보( ex )`를 포함해서 호출 해야 한다.

## `LoginController.class`

```java
@Slf4j
@Controller
@RequiredArgsConstructor
public class LoginController {

    @PostMapping("/login")
    public String loginV4(@Valid @ModelAttribute LoginForm form, 
                          BindingResult bindingResult, 
                          @RequestParam(defaultValue = "/") String redirectURL, 
                          HttpServletRequest request) {

        if (bindingResult.hasErrors()) {
            return "login/loginForm";
        }

        Member loginMember = loginService.login(form.getLoginId(), form.getPassword());

        if (loginMember == null) {
            bindingResult.reject("loginFail", "아이디 또는 비밀번호가 맞지 않습니다.");
            return "login/loginForm";
        }

        //로그인 성공 처리
        //세션이 있으면 있는 세션 반환, 없으면 신규 세션을 생성
        HttpSession session = request.getSession();
        
        //세션에 로그인 회원 정보 보관
        session.setAttribute(SessionConst.LOGIN_MEMBER, loginMember);

        return "redirect:" + redirectURL;

    }
}
```

## `LoginCheckInterceptor.class`

![이미지](/programming/img/입문139.PNG)

```java
@Slf4j
public class LoginCheckInterceptor implements HandlerInterceptor {

    /**
     * 인증 체크 로직
     */
    @Override
    public boolean preHandle(HttpServletRequest request,
                             HttpServletResponse response,
                             Object handler) throws Exception {

        String requestURI = request.getRequestURI(); // items

        // 세션이 있으면 있는 세션 반환, 없으면 신규 세션 생성
        HttpSession session = request.getSession();

        if (session == null || session.getAttribute(SessionConst.LOGIN_MEMBER) == null) {
            
            // 로그인 하지 않은 상태에서 items 요청하면 여기 로직으로 온다.
            // 세션이 있는지 없는지로 판단한다.

            log.info("미인증 사용자 요청"); //로그인으로 redirect

            response.sendRedirect("/login?redirectURL=" + requestURI);
            return false;
        }

        return true;
    }
}
```

## `WebConfig.class`

![이미지](/programming/img/입문140.PNG)

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(new LoginMemberArgumentResolver());
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoginCheckInterceptor())
                .order(1) // 첫번째 체인을 뜻한다.
                .addPathPatterns("/**") // 모든 경로에 대해서 로그인 체크를 한다.
                .excludePathPatterns("/", "/members/add", "/login",
                        "/logout", "/css/**", "/*.ico", "/error"); // 하지만, 여기 경로들은 로그인 체크를 하지 않는 것이다. 
                                                                   // 즉 프리패스.
    }

}
```

## 궁금증!

```java
필터와 인터셉터, 둘 다 있는데 언제 무엇을 쓰는 게 맞을까?
```

기준은 `스프링을 알아야 하는가` 다.

앞의 디스패처 서블릿 글에서 본 위치가 그 답이다.

```java
클라이언트
  -> 톰캣
       -> 필터 1 -> 필터 2                    <- 스프링을 모른다
            -> DispatcherServlet
                 -> 인터셉터 preHandle         <- 여기부터 스프링
                      -> 컨트롤러
                 -> 인터셉터 postHandle
            -> 뷰 렌더링
                 -> 인터셉터 afterCompletion
       -> 필터 2 -> 필터 1
```

<br/>

필터는 `DispatcherServlet` 바깥이다. 어느 컨트롤러가 처리할지 아직 정해지지도 않았다.

인터셉터는 `getHandler()` 가 끝난 뒤라서, 어느 핸들러인지 이미 안다.

```java
// 필터 - 요청과 응답만 있다
void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)

// 인터셉터 - 핸들러가 세 번째 파라미터로 온다
boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler)
```

<br/>

`handler` 를 받을 수 있으니 인터셉터에서는 이런 것이 가능하다.

```java
public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
    if (handler instanceof HandlerMethod handlerMethod) {
        LoginRequired anno = handlerMethod.getMethodAnnotation(LoginRequired.class);
        if (anno == null) return true;          // 어노테이션이 없으면 통과
    }
    // 로그인 확인
}
```

<br/>

메서드에 붙은 어노테이션을 보고 통과 여부를 정하는 것이다. 필터로는 이걸 못 한다.

<br/>

## 예외가 났을 때의 차이

`postHandle` 과 `afterCompletion` 의 차이가 여기서 제일 잘 드러난다.

```java
컨트롤러에서 예외 발생
  -> postHandle      : 호출되지 않는다
  -> afterCompletion : 호출된다. 예외가 파라미터로 넘어온다
```

<br/>

```java
void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                     Object handler, Exception ex)
```

<br/>

마지막 파라미터로 예외가 온다. 정상이면 `null` 이다.

그래서 로그 남기기나 자원 정리는 `afterCompletion` 에 둬야 한다.

앞의 try-catch-finally 글에서 본 `finally` 와 같은 자리인 것이다.

```java
postHandle      -> 정상일 때만. ModelAndView 를 손볼 수 있다
afterCompletion -> 예외가 나도 항상. 정리 작업용
```

<br/>

## 필터는 응답까지 바꿀 수 있다

필터의 `chain.doFilter()` 는 앞뒤가 다 열려 있다.

```java
public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
    // 요청 전 처리
    chain.doFilter(req, res);      // 여기서 안쪽 전체가 실행된다
    // 응답 후 처리
}
```

<br/>

`chain.doFilter()` 를 아예 안 부르면 요청이 안쪽으로 들어가지 않는다.

인터셉터의 `preHandle` 이 `false` 를 반환하는 것과 같은 효과다.

<br/>

그리고 `response` 를 감싸서 넘기면 응답 본문 자체를 바꿀 수 있다.

응답을 로그로 남기거나 압축하는 필터가 이 방식으로 동작한다.

```java
ContentCachingResponseWrapper wrapper = new ContentCachingResponseWrapper(res);
chain.doFilter(req, wrapper);
byte[] body = wrapper.getContentAsByteArray();     // 응답 본문을 읽는다
log.info("응답 = {}", new String(body));
wrapper.copyBodyToResponse();                      // 다시 진짜 응답에 써준다
```

<br/>

인터셉터는 이걸 못 한다. `postHandle` 시점에는 이미 응답이 나가고 있을 수 있기 때문이다.

<br/>

## 그래서 이렇게 나눈다

```java
필터가 맞는 일
  - 인코딩 설정 (컨트롤러에 닿기 전에 해야 한다)
  - CORS 처리
  - 요청/응답 로깅
  - 스프링 시큐리티 (인증 실패 시 컨트롤러를 찾기도 전에 막아야 한다)
  - 정적 리소스까지 포함해서 걸러야 하는 일

인터셉터가 맞는 일
  - 로그인 확인 (어느 컨트롤러인지 알아야 예외 경로를 정할 수 있다)
  - 권한 확인 (메서드의 어노테이션을 봐야 한다)
  - 요청 처리 시간 측정
```

<br/>

시큐리티가 필터로 되어 있는 것이 좋은 예다.

인증되지 않은 요청이 `DispatcherServlet` 까지 들어오기 전에 막아야 안전하기 때문이다.

<br/>

## 등록 방법도 다르다

```java
// 필터 - 서블릿 컨테이너에 등록한다
@Bean
public FilterRegistrationBean<LogFilter> logFilter() {
    FilterRegistrationBean<LogFilter> bean = new FilterRegistrationBean<>(new LogFilter());
    bean.setOrder(1);
    bean.addUrlPatterns("/*");
    return bean;
}

// 인터셉터 - 스프링 MVC 설정에 등록한다
@Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(new LoginCheckInterceptor())
            .order(1)
            .addPathPatterns("/**")
            .excludePathPatterns("/", "/login", "/css/**");
}
```

<br/>

인터셉터 쪽이 경로 설정이 훨씬 편하다.

`excludePathPatterns` 로 제외할 경로를 지정할 수 있고, `/**` 같은 패턴도 세밀하게 쓸 수 있다.

<br/>

필터의 `addUrlPatterns` 는 서블릿 스펙의 단순한 패턴만 지원한다.

제외 경로를 지정하는 기능이 아예 없어서, 필터 안에서 직접 `if` 로 걸러야 한다.

<br/>

원문의 `그리하여` 결론대로, 스프링 안에서 처리해도 되는 일이라면 인터셉터가 편한 이유가 이것이다.
