## 빈 스코프, 스코프와 프록시



스프링 빈이 스프링 컨테이너의 시작과 함께 생성되어서 `스프링 컨테이너`가 종료될 때까지 유지된다고 생각했다. 

이것은 `스프링 빈`이 기본적으로 `싱글톤 스코프`로 생성되기 때문이다.

```
스코프 : 빈이 존재할 수 있는 범위를 뜻한다.

프로토타입 : 대충 만들고 버릴것 같은 느낌이라고 생각하면 된다.
```

<br/><br/>

## 스프링은 다음과 같은 다양한 스코프를 지원한다.

`싱글톤` : 기본 스코프, 스프링 컨테이너의 시작과 종료까지 유지되는 가장 넓은 범위의 스코프이다.

`프로토타입` : 스프링 컨테이너 실행 되고, 빈의 생성과 의존관계 주입까지만 관여하고
더는 관리하지 않는 매우 짧은 범위의 스코프이다.

```
프로토타입의 핵심은 : 빈을 관리할 책임은 프로토타입 빈을 받은 클라이언트에 있다는 것이다.
```

그래서 `@PreDestory` 같은 종료 메서드가 호출되지 않는다.

<br/><br/>

## 정리

프로토타입 빈을 2번 조회 했어도, 완전히 다른 스프링 빈이 생성되고, 

초기화도 2번 실행된 것을 확인할 수 있다.

<br/>

싱글톤 빈은 스프링 컨테이너가 관리하기 때문에 스프링 컨테이너가 종료될 때 

빈의 종료 메서드가 실행되지만, 프로토타입 빈은 스프링 컨테이너가 생성과 

의존관계 주입 그리고 초기화 까지만 관여하고,
더는 관리하지 않는다

<br/>

그리고 초기화 까지만 관여하기에, 프로토타입 빈은 스프링 컨테이너가 종료될 때 

`@PreDestroy` 같은 종료 메서드가 전혀 실행되지 않는다.

<br/><br/>

## 웹 관련 스코프

스코프의 특징 웹 스코프는 웹 환경에서만 동작한다.

- 웹 스코프는 프로토타입과 다르게 스프링이 해당 스코프의 종료시점까지 관리한다.

<br/>

`request 스코프 :` HTTP 요청 하나가 들어오고 나갈 때 까지 유지되는 스코프, 각각의 HTTP 요청마다 

별도의 빈 인스턴스가 생성되고, 관리된다. 각각 다른 스프링 빈이 생성이 되어 사용된다.

![이미지](/programming/img/입문38.PNG)

<br/>

`session:` HTTP Session과 동일한 생명주기를 가지는 스코프

`application:` 서블릿 컨텍스트( ServletContext )와 동일한 생명주기를 가지는 스코프

`websocket:` 웹 소켓과 동일한 생명주기를 가지는 스코프

<br/><br/>

## 스코프와 프록시

사용 방법은 이렇다. 즉, 가짜(=프록시)를 만든다는 것이다.

밑에 처럼 코드를 작성하면 MyLogger 클래스 대한 가짜를 한개 만든다는 것이다.

```java
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class MyLogger {

    // ... 
```

다시 말해, 가짜 프록시 클래스를 만들어서 주입 시켜주는 것이다.

<br/>

이렇게 출력 시켜본다면 

```java
System.out.println("myLogger = " + myLogger.getClass());
```

내가 만든 것이 아니라, 스프링이 만든 것이 등록 되어 있다는 걸 알 수 있다.



Provider 처럼 동작한다고 알고 있으면 된다.

<br/>

![이미지](/programming/img/입문39.PNG)

### 가짜 프록시 객체는 요청이 오면 그제서야 내부에 진짜 빈을 요청하는 것이다.

다시 말해, 실제 사용할 시점이 되면, 그때 가져온다

<br/><br/>

## 그래서 왜 쓰는데?

프록시 객체 덕분에 클라이언트는 마치 싱글톤 빈을 사용하듯이 편리하게 `request scope`를 사용할 수 있다.

![이미지](/programming/img/입문40.PNG)

프록시가 아니였으면, 밑에 코드인 `request scope` 방식으로 사용했을 것이다.

```java
private final ObjectProvider<MyLogger> myLoggerProvider;
```

<br/><br/>

## 핵심

`Provider`를 사용하든, `프록시`를 사용하든 핵심은 진짜 객체 조회를 

꼭 필요한 시점까지 지연처리 한다는 점이다.

<br/>

단지 애노테이션 설정 변경만으로 원본 객체를 프록시 객체로 대체할 수 있다. 

이것이 바로 `다형성`과 `DI 컨테이너`가 가진 큰 강점이다.

## 궁금증!

```java
프로토타입 빈은 정말 관리를 안 해줄까
```

싱글톤과 프로토타입을 하나씩 만들어놓고 컨테이너를 띄웠다 닫아봤다.

```java
@Bean @Scope("singleton")  Single single() { return new Single(); }
@Bean @Scope("prototype")  Proto  proto()  { return new Proto(); }
```

<br/>

둘 다 `@PostConstruct` 와 `@PreDestroy` 를 붙여뒀다.

<br/>

### 결과

```java
  [singleton] init 호출              <- 컨테이너가 뜰 때 이미 만들어졌다
--- 싱글톤: 두 번 꺼내보기 ---
  s1 == s2 ? true

--- 프로토타입: 두 번 꺼내보기 ---
  [prototype] init 호출
  [prototype] init 호출              <- 꺼낼 때마다 만든다
  p1 == p2 ? false

--- 컨테이너 종료 ---
  [singleton] destroy 호출
  (프로토타입의 destroy 는 호출되지 않았다)
```

<br/>

세 가지가 한 번에 확인된다.

<br/>

## 1. 싱글톤은 미리 만들어진다

`getBean` 을 부르기 전에 이미 `init` 이 찍혔다.

컨테이너가 뜰 때 전부 만들어두는 것이다.

<br/>

그래서 설정이 잘못됐으면 서버가 뜨다가 멈춘다.

앞의 생성자 주입을 선택 글에서 본 순환 참조 오류도 이 시점에 나온다.

```java
운영 중에 터지는 것보다 뜰 때 터지는 게 낫다
```

<br/>

## 2. 프로토타입은 꺼낼 때 만든다

`init` 이 두 번 찍혔다. `getBean` 을 두 번 불렀기 때문이다.

<br/>

## 3. 프로토타입은 destroy 를 안 부른다

여기가 핵심이다.

<br/>

컨테이너가 프로토타입 빈을 **만들어주기만 하고 보관하지 않는다.**

```java
싱글톤    - 만들고 -> 보관하고 -> 종료할 때 정리한다
프로토타입 - 만들고 -> 넘겨준다. 끝
```

<br/>

그래서 자원을 쥐고 있는 객체를 프로토타입으로 두면 정리가 안 된다.

필요하면 직접 닫아야 한다.

```java
Proto p = ac.getBean(Proto.class);
try {
    p.use();
} finally {
    p.close();              // 내가 닫아야 한다
}
```

<br/>

앞의 try-with-resources 글에서 본 그 방식으로 처리하는 게 낫다.

<br/>

## 싱글톤 안에 프로토타입을 넣으면

여기서 자주 헷갈린다.

```java
@Component
public class SingletonBean {
    @Autowired
    private PrototypeBean prototypeBean;      // 주입은 한 번만 일어난다
}
```

<br/>

`SingletonBean` 이 만들어질 때 한 번 주입받고 끝이다.

그 뒤로는 계속 **같은** 프로토타입 객체를 쓴다.

<br/>

프로토타입인데 싱글톤처럼 동작하는 것이다.

<br/>

## 그래서 프록시를 쓴다

```java
@Bean
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
public PrototypeBean prototypeBean() { ... }
```

<br/>

이러면 주입되는 것이 진짜 객체가 아니라 가짜다.

<br/>

앞의 IoC (=제어의 역전) 글에서 본 CGLIB 이 여기서도 쓰인다.

```java
주입될 때   - 가짜(프록시)가 들어간다
메서드 호출 - 그때 컨테이너에서 진짜를 꺼내와서 넘긴다
```

<br/>

호출할 때마다 새 객체를 꺼내오니 프로토타입답게 동작하게 되는 것이다.

<br/>

## 웹 스코프도 같은 이유로 프록시를 쓴다

```java
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
```

<br/>

`request` 스코프는 요청이 들어와야 만들 수 있다.

그런데 싱글톤 빈은 컨테이너가 뜰 때 만들어지니, 그 시점에는 요청이 없다.

<br/>

```java
Scope 'request' is not active for the current thread
```

<br/>

프록시를 끼우면 이 문제가 풀린다.

주입 시점에는 가짜만 넣어두고, 실제로 부를 때 그 요청의 객체를 찾아가는 것이다.

<br/>

앞의 멀티 쓰레드 이해 글에서 본 대로 요청마다 스레드가 다르니,

`ThreadLocal` 로 지금 스레드의 요청을 찾아서 그것에 딸린 빈을 꺼낸다.

<br/>

## 스코프 종류

```java
singleton   - 컨테이너 하나에 하나. 기본값
prototype   - 꺼낼 때마다 새로
request     - HTTP 요청 하나마다
session     - 사용자 세션마다
application - 서블릿 컨텍스트마다
```

<br/>

실무에서는 `singleton` 이 거의 전부다.

<br/>

`request` 스코프는 요청별 로그 추적 같은 데 쓰는데,

요즘은 `MDC` 나 필터에서 처리하는 경우가 더 많다.
