## 객체지향 설계

메인 클래스는 숫자 ‘6’이 어떻게 처리 되는지 모르게 해야 한다.

그리하여 모든 과정은 통신으로만 하여 → 해당 객체에서 상태를 바꿔야 하는 것이다.

<br/><br/>

## 모르게 해야 되는 기준이 뭔데?

```java
Main 메서드에서 -> solution 메서드에서 -> calculation 메서드에서 -> ... 
```

기준은. `하나의 메서드는 하나의 일만 알아야 된다는 것이다.`

즉, solution 메서드에서는 객체 생성하는 일만 해야되고, 계산하는 부분에 있어서는 몰라야 된다는 것이다.

<br/><br/>

## 객체를 만들면.

객체를 만들면 필드변수가 있기에, 해당 숫자가 저장 되어 모든건 객체 안에서 필드변수 → ‘상태’를 처리해야 된다는 것이다.

(`객체 안에서`가 포인트이다) 그리하여 메서드들이 많은 것이다.

<br/><br/>

## 내가 만들어본 객체지향 설계 코드


```java
class Main {

    public static void main(String[] args) {
        Solution solution = new Solution();
        System.out.println(solution.solution(626331));
    }

    static class Solution {

        private static final int DIVIDE_VALUE = 2;
        private static final int MULTIPLE_VALUE = 3;
        private static final int ADD_VALUE = 1;
        private final Count count;

        public Solution() {
            this.count = new Count();
        }

        public int solution(final int num) {
            Number number = new Number(num);
            progress(number);
            return count.getValue();
        }

        private void progress(final Number number) {
            while (number.isNotOne() && count.canProgress()) {
                calculate(number);
            }
        }

        private void calculate(final Number number) {
            if (number.isEven()) {
                number.divide(DIVIDE_VALUE);
            } else {
                number.multiple(MULTIPLE_VALUE);
                number.add(ADD_VALUE);
            }
            count.add();
            if (count.canNotProgress()) {
                count.impossible();
            }
        }
    }

    static class Number {

        private long value;

        public Number(int value) {
            this.value = value;
        }

        public boolean isEven() {
            return value % 2 == 0;
        }

        public boolean isNotOne() {
            return !isOne();
        }

        public boolean isOne() {
            return value == 1;
        }

        public void multiple(int count) {
            this.value *= count;
        }

        public void add(int add) {
            this.value += add;
        }

        public void divide(int value) {
            this.value /= value;
        }

        @Override
        public String toString() {
            return "Number{" +
                "value=" + value +
                '}';
        }
    }

    static class Count {

        private static final int END_COUNT = 500;
        private int value = 0;

        public void add() {
            value++;
        }

        public boolean canProgress() {
            return 0 <= value && value < END_COUNT;
        }

        public boolean canNotProgress() {
            return value == END_COUNT;
        }

        public void impossible() {
            value = -1;
        }

        public int getValue() {
            return value;
        }
    }
}
```

## 궁금증!

```java
"모르게 한다" 는 기준을 어디에 두어야 할까
```

`그것이 바뀌었을 때 나도 바뀌어야 하는가` 로 판단하면 명확해진다.

```java
바뀌면 나도 바뀐다  -> 알고 있는 것이다 (의존한다)
바뀌어도 나는 그대로 -> 모르는 것이다
```

<br/>

앞의 인터페이스를 왜 사용하는가 글에서 실제로 확인한 그 차이다.

```java
class OrderService {
    private final KakaoPay kakaoPay = new KakaoPay();     // 알고 있다
}
```

<br/>

결제 수단이 늘면 `OrderService` 를 고쳐야 한다. 알고 있으니 같이 바뀌는 것이다.

<br/>

```java
class OrderService {
    private final PayClient payClient;                    // 모른다
}
```

```java
카카오페이로 10000원 결제
토스로 10000원 결제
테스트용 가짜 결제 10000원
```

<br/>

세 번 바뀌었는데 `OrderService` 는 한 글자도 안 바뀌었다.

<br/>

## 모르게 하는 방법이 몇 가지 있다

앞의 글들에서 나온 것을 모아보면 이렇다.

```java
인터페이스로 받는다     -> 구현이 바뀌어도 모른다   (앞의 인터페이스 글)
계산을 안으로 옮긴다     -> 내부 구조가 바뀌어도 모른다 (앞의 객체는 객체스럽게 글)
컬렉션을 감싼다         -> List 인지 Map 인지 모른다  (앞의 일급 컬렉션 글)
이름으로 주고받는다      -> 실제 대상이 바뀌어도 모른다 (앞의 뷰 리졸버 글)
```

<br/>

전부 `사이에 무언가를 끼워서 직접 알지 못하게` 하는 방식이다.

<br/>

## 그런데 모르는 것에도 비용이 있다

인터페이스를 하나 끼우면 파일이 하나 늘고, 코드를 따라가기가 어려워진다.

```java
payClient.pay(amount)      // 여기서 F12 를 누르면 인터페이스로 간다
                           // 실제 구현이 무엇인지는 설정을 봐야 안다
```

<br/>

그래서 구현이 하나뿐이고 앞으로도 하나일 것 같으면 굳이 인터페이스를 안 만들기도 한다.

<br/>

판단 기준은 `바뀔 가능성` 이다.

```java
결제 수단  - 바뀔 가능성이 높다        -> 인터페이스
날짜 계산  - 바뀔 일이 거의 없다       -> 그냥 클래스
```

<br/>

앞의 트레이드 오프 글에서 본 대로, 미리 다 나눠두는 것이 항상 이득은 아니다.

<br/>

## 객체를 만들면 무엇이 달라지는가

원문의 그 질문에 답하면, `책임을 둘 자리가 생긴다` 는 것이다.

```java
// 객체가 없으면 - 규칙이 흩어진다
if (money < 0) throw new IllegalArgumentException();
if (money % 1000 != 0) throw new IllegalArgumentException();
int count = money / 1000;
```

<br/>

이 검사를 쓰는 곳마다 적어야 하고, 한 군데라도 빠뜨리면 규칙이 깨진다.

<br/>

```java
// 객체를 만들면 - 규칙이 한 곳에 모인다
class PurchaseAmount {
    private static final int LOTTO_PRICE = 1000;
    private final int value;

    public PurchaseAmount(int value) {
        if (value < 0) throw new IllegalArgumentException("금액은 음수일 수 없습니다");
        if (value % LOTTO_PRICE != 0) throw new IllegalArgumentException("1000원 단위여야 합니다");
        this.value = value;
    }

    public int countOfLotto() {
        return value / LOTTO_PRICE;
    }
}
```

<br/>

앞의 객체지향 생활 체조 글의 `원시값 포장` 이 이것이다.

`PurchaseAmount` 가 존재한다는 것 자체가 `검증을 통과한 금액` 이라는 뜻이 된다.

<br/>

## 그래서 설계를 시작할 때 던지는 질문

```java
1. 이 데이터를 가진 것이 누구인가
2. 이 계산은 누가 해야 하는가       -> 그 데이터를 가진 쪽
3. 이 규칙이 깨지면 안 되는가        -> 그렇다면 생성자에서 막는다
4. 이것이 바뀌면 누가 같이 바뀌는가  -> 많으면 사이에 인터페이스를 끼운다
```

<br/>

앞의 클래스와 메소드의 사용 이유는 글에서 본 `메서드를 어디에 둘지는 그 데이터를 가진 쪽` 이

`2번` 에 해당한다.

<br/>

이 네 질문에 답하다 보면 클래스가 자연스럽게 나뉘고, 그 결과가 객체지향 설계다.

규칙을 외워서 적용하는 것보다 이 순서로 물어보는 편이 실제로는 더 잘 된다.
