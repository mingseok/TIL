## 메시지를 보낸다는 것

앞의 객체는 객체스럽게 사용한다 글에서 본 그 차이다.

```java
// 데이터를 꺼내서 내가 처리한다
if (member.getGrade() == Grade.VIP) {
    price = price * 90 / 100;
}

// 메시지를 보내고 결과만 받는다
price = member.discount(price);
```

<br/>

`어떻게 할인하는가` 를 `Member` 가 알고 있고, 나는 `할인해달라` 고만 한다.

<br/>

## 파라미터가 많아지는 것도 같은 신호다

```java
void order(String name, String address, String phone, int itemId, int count, int price)
```

<br/>

파라미터가 여섯 개면 대개 두 가지 중 하나다.

```java
1. 관련된 것들이 묶여 있지 않다   -> 객체로 묶는다
2. 메서드가 여러 일을 한다        -> 나눈다
```

<br/>

`1번` 이면 이렇게 바뀐다.

```java
void order(DeliveryInfo delivery, OrderItem item)
```

<br/>

앞의 객체지향 생활 체조 글의 `원시값 포장` 과 같은 해법이다.

`name, address, phone` 이 항상 같이 다닌다면 그건 이미 하나의 개념인 것이다.

<br/>

## 인스턴스 변수를 줄이라는 것

앞의 메소드, 필드, enum 작성을 위한 규칙 글에서 본 `boolean 네 개` 예시가 이유를 잘 보여준다.

```java
class Order {
    private boolean paid;
    private boolean shipped;
    private boolean canceled;
    private boolean refunded;
}
```

<br/>

조합이 `16` 가지인데 말이 되는 것은 몇 개 안 된다.

`enum` 하나로 바꾸면 있을 수 없는 상태가 아예 표현되지 않는다.

<br/>

## static 메서드를 언제 쓰는가

앞의 static 메서드와 일반 메서드의 차이점 글에서 본 기준이다.

```java
객체의 상태와 무관하게 결과가 정해지면  -> static
이 객체의 상태를 봐야 답이 나오면      -> 인스턴스 메서드
```

<br/>

정적 팩토리 메서드가 대표적인 `static` 의 쓰임이다.

```java
public static Lotto from(List<Integer> numbers) {
    return new Lotto(numbers);
}

public static Lotto auto() {
    return new Lotto(generateRandom());
}
```

<br/>

앞의 빌더 패턴 사용 이유 글에서 본 것처럼, 이름을 붙일 수 있다는 것이 이득이다.

`new Lotto(...)` 로는 `직접 넣은 것` 과 `자동 생성한 것` 을 구분할 수 없다.

<br/>

다만 `static` 을 남발하면 앞의 static 메서드 글에서 본 문제가 생긴다.

```java
LottoUtils.calculate(...)      // 테스트에서 갈아끼울 수가 없다
```

<br/>

`invokestatic` 은 컴파일 시점에 대상이 고정되어서, 가짜 구현을 넣을 방법이 없다.

<br/>

## 매직 넘버를 상수로

앞의 코딩 컨벤션 글에서 본 기준이 여기에도 적용된다.

```java
if (money < 1000)              // 1000 이 무엇인지 모른다
if (money < LOTTO_PRICE)       // 의미가 드러난다
```

<br/>

다만 무조건 빼는 것이 답은 아니다.

```java
for (int i = 0; i < 3; i++)    // 이 3 은 굳이 상수로 뺄 이유가 없다
```

<br/>

기준은 `그 값이 바뀔 수 있는가` 와 `이름이 없으면 뜻을 모르는가` 다.

<br/>

## 패키지 이름이 소문자인 이유

자바 관례이기도 하지만 실제 이유가 있다.

<br/>

패키지는 디렉터리로 만들어지는데, 윈도우와 맥의 파일 시스템은 대소문자를 구분하지 않는다.

리눅스는 구분한다.

```java
com.example.Order  와  com.example.order
```

<br/>

로컬에서는 같은 폴더로 보이는데 서버에서는 다른 폴더가 된다.

빌드는 되는데 배포하면 `ClassNotFoundException` 이 나는 상황이 생긴다.

<br/>

앞의 URI 글에서 본 `호스트는 대소문자를 안 가리고 경로는 가린다` 와 같은 부류의 함정이다.
