## 궁금증!

```java
개념 모델과 논리 모델과 물리 모델을 왜 나누나
```

바뀌는 이유가 다르기 때문이다.

```java
개념 - 업무를 그대로 그린다. DB 를 몰라도 이해된다
논리 - 표와 컬럼으로 옮긴다. 정규화를 한다
물리 - 실제 DB 문법으로 만든다. 타입, 인덱스, 성능
```

<br/>

앞의 MVC(=Model View Controller) 글에서 본 것과 같은 발상이다.

`자주 바뀌는 것과 안 바뀌는 것을 갈라놓는다.`

<br/>

업무 규칙은 잘 안 바뀌는데 인덱스는 자주 바뀐다.

<br/>

## 개념 모델에서는 이걸 정한다

```java
어떤 것들이 있는가          -> 엔티티 (회원, 주문, 상품)
그것들이 어떻게 엮이는가     -> 관계 (회원이 주문을 한다)
몇 대 몇인가                -> 카디널리티 (1:N, N:M)
반드시 있어야 하는가         -> 선택성 (주문에는 회원이 반드시 있어야 하나)
```

<br/>

`선택성` 이 나중에 `NOT NULL` 이 된다.

<br/>

앞의 검색 조건, NULL 값 글에서 본 `NULL` 문제들이

여기서 제대로 정하면 애초에 안 생긴다.

<br/>

## N:M 은 표로 못 만든다

```java
학생 -- 수강 -- 과목
```

<br/>

학생 하나가 여러 과목을 듣고, 과목 하나를 여러 학생이 듣는다.

<br/>

관계형 DB에는 이걸 직접 표현하는 방법이 없다.

그래서 중간 표를 만든다.

```sql
CREATE TABLE enrollment (
    student_id BIGINT,
    subject_id BIGINT,
    PRIMARY KEY (student_id, subject_id)
);
```

<br/>

앞의 다대다 매핑 글에서 본 그 이유다.

<br/>

그리고 중간 표를 만들고 나면 거기에 붙일 속성이 반드시 생긴다.

```sql
enrolled_at DATE,
grade CHAR(1)
```

<br/>

`수강 신청일` 과 `성적` 은 학생의 속성도 아니고 과목의 속성도 아니다.

`이 학생이 이 과목을 듣는다` 는 사실의 속성인 것이다.

<br/>

그래서 JPA의 `@ManyToMany` 를 실무에서 안 쓰는 것이다.

속성을 못 붙이니, 결국 중간 엔티티를 만들게 된다.

<br/>

## 식별 관계와 비식별 관계

```java
식별   - 부모의 키가 자식의 기본 키에 포함된다
비식별 - 부모의 키를 외래 키로만 갖고, 자식은 자기 키를 따로 둔다
```

<br/>

```sql
-- 식별
CREATE TABLE order_item (
    order_id BIGINT,
    line_no INT,
    PRIMARY KEY (order_id, line_no)
);

-- 비식별
CREATE TABLE order_item (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id BIGINT
);
```

<br/>

식별 관계는 계층이 깊어지면 기본 키가 계속 길어진다.

```java
회사 -> 부서 -> 팀 -> 사원
PK 가 (회사, 부서, 팀, 사원) 네 개가 된다
```

<br/>

조인할 때마다 컬럼 네 개를 비교해야 한다.

<br/>

그래서 실무에서는 비식별 관계에 대리 키를 쓰는 쪽이 우세하다.

앞의 기본 키 매핑 글에서 본 그 선택이다.

<br/>

## 정규화를 어디까지 할 것인가

앞의 정규화 글에서 본 대로 3차 정규형까지가 보통이다.

<br/>

그런데 개념 모델 단계에서 정규화를 걱정하면 안 된다.

<br/>

업무를 그대로 그리면 대개 자연스럽게 정규형에 가까워진다.

`하나의 사실을 한 곳에만 적는다` 는 게 업무를 제대로 이해한 결과이기 때문이다.

<br/>

성능 때문에 일부러 되돌리는 것은 물리 모델 단계의 일이다.

```sql
-- 주문 표에 회원 이름을 복사해둔다
orders.member_name
```

<br/>

이러면 조인 없이 목록을 그릴 수 있다.

대신 회원이 이름을 바꾸면 두 곳을 고쳐야 한다.

<br/>

앞의 이상 현상 글에서 본 갱신 이상을 일부러 감수하는 것이다.

<br/>

주문 시점의 이름을 남겨야 하는 경우라면 오히려 이게 맞다.

`이름을 복사한 것` 이 아니라 `그때의 이름을 기록한 것` 이 되기 때문이다.

같은 컬럼이라도 의미가 다른 것이다.

<br/>

## 이름 짓기가 절반이다

```java
member  vs  user  vs  customer  vs  account
```

<br/>

넷 다 쓰이는데 뜻이 조금씩 다르다.

<br/>

한 프로젝트 안에서 섞여 있으면 나중에 `이게 저건가` 를 계속 묻게 된다.

<br/>

앞의 클래스명, 메소드명, 변수명 규칙 글에서 본 원칙이

데이터 모델에서 더 중요해진다.

<br/>

코드는 고치기 쉽지만 컬럼 이름은 운영 중에 못 바꾸기 때문이다.

앞의 테이블 관리 글에서 본 대로 이름 변경 자체는 빠른데,

그 이름을 쓰는 코드와 쿼리를 전부 찾아 고쳐야 하는 게 문제다.

<br/>

그래서 처음에 용어집을 만들어두고 시작하는 게 좋다.

`이 프로젝트에서 회원은 member 라고 부른다` 를 정해두는 것이다.
