## 예외와 트랜잭션 커밋, 롤백

## 궁금증.

```
예외가 발생했는데, 내부에서 예외를 처리하지 못하고, 
트랜잭션 범위 밖으로 예외를 던지면 어떻게 될까?
```

<br/>

![이미지](/programming/img/입문270.PNG)

예외 발생시 스프링 트랜잭션 AOP는 예외의 종류에 따라 트랜잭션을 `커밋`하거나 `롤백`한다.

- 언체크 예외인 `RuntimeException`, `Error`와 그 하위 예외가 발생하면 트랜잭션을 `롤백`한다.

- 체크 예외인 `Exception`과 그 하위 예외가 발생하면 트랜잭션을 `커밋`한다.
- 물론 정상 응답(리턴)하면 트랜잭션을 커밋한다.

<br/><br/>

## 궁금증

```
스프링은 왜 체크 예외는 커밋하고, 언체크(런타임) 예외는 롤백할까?
```

스프링 기본적으로 `체크 예외`는 비즈니스 의미가 있을 때 사용하고, 

`런타임(언체크)` 예외는 복구 불가능한 예외로 가정한다.

- `체크 예외:` 비즈니스 의미가 있을 때 사용

- `언체크 예외:` 복구 불가능한 예외

<br/><br/>

## 비즈니스 예외라는 것이 무슨 뜻일까?

비즈니스 요구사항 주문을 하는데 상황에 따라 다음과 같이 조치한다.

1. `정상:` 주문 시 결제를 성공하면 주문 데이터를 저장하고 결제 상태를 완료로 처리한다.

2. `시스템 예외:` 주문 시 내부에 복구 불가능한 예외가 발생하면 전체 데이터를 롤백한다.
3. `비즈니스 예외:` 주문 시 결제 잔고가 부족하면 주문 데이터를 저장하고, 결제 상태를 대기로 처리한다.
    
    이 경우 고객에게 잔고 부족을 알리고 별도의 계좌로 입금하도록 안내한다.

<br/><br/>

## 비즈니스 예외(3번) 추가 설명

```
결제 잔고가 부족하면 시스템에 문제가 있어서 발생하는 시스템 예외가 아니다.
```

시스템은 정상 동작했지만, 비즈니스 상황에서 문제가 되기 때문에 발생한 예외이다.



고객의 잔고가 부족한 것은 시스템에 문제가 있는 것이 아니다. 

<br/>

오히려 시스템은 문제 없이 동작한 것이고, 비즈니스 상황이 예외인 것이다. 

이런 예외를 비즈니스 예외라 한다. 

<br/>

그리고 비즈니스 예외는 매우 중요하고, 반드시 처리해야 하는 경우가 많으므로 체크 예외를 고려할 수 있다.

## 궁금증!

```java
왜 하필 체크 예외는 커밋이고 언체크 예외는 롤백일까?
```

스프링이 예외를 두 종류로 나눠 본다는 뜻이다.

```java
언체크 예외 (RuntimeException, Error)
  -> "예상 못 한 시스템 문제다" 라고 본다 -> 롤백

체크 예외 (Exception)
  -> "예상하고 선언해둔 비즈니스 상황이다" 라고 본다 -> 커밋
```

<br/>

원문의 `비즈니스 예외` 가 이 구분의 근거다.

<br/>

## 커밋해야 하는 상황이 실제로 있다

주문을 받았는데 잔고가 모자란 경우를 생각해보면 이해가 된다.

```java
@Transactional
void order(Item item, Member member) throws NotEnoughMoneyException {
    orderRepository.save(new Order(item, member, "대기"));   // 주문은 남긴다

    if (member.getBalance() < item.getPrice()) {
        throw new NotEnoughMoneyException("잔고 부족");       // 체크 예외
    }
    // 결제 처리
}
```

<br/>

잔고가 모자란 것은 시스템 오류가 아니다. 충분히 있을 수 있는 정상적인 상황이다.

<br/>

이때 롤백해버리면 주문 기록이 사라진다.

`대기` 상태로 남겨두고 사용자에게 `입금하면 처리해드립니다` 라고 안내하려면 커밋되어야 한다.

```java
롤백해야 하는 경우 - DB 연결이 끊겼다, NPE 가 났다. 데이터가 망가졌을 수 있다
커밋해야 하는 경우 - 잔고 부족, 재고 부족. 그 사실 자체를 기록으로 남겨야 한다
```

<br/>

## 그런데 이 기본값이 사고를 부른다

체크 예외를 쓰면서 롤백을 기대하는 경우가 훨씬 많기 때문이다.

```java
@Transactional
void upload(MultipartFile file) throws IOException {
    fileRepository.save(new FileInfo(file.getName()));   // 저장
    file.transferTo(new File("/data/" + file.getName())); // 여기서 IOException
}
```

<br/>

`IOException` 은 체크 예외라 롤백이 안 된다.

파일 저장에 실패했는데 DB에는 파일 정보가 남는다.

<br/>

`IOException` 은 비즈니스 상황이 아니라 그냥 실패인데,

체크 예외라는 이유만으로 커밋되는 것이다.

<br/>

그래서 앞의 exception 글에서 본 대로, 실무에서는 대부분 언체크 예외를 쓴다.

기본 롤백 규칙과 의도가 맞아떨어지기 때문이다.

```java
언체크 예외를 쓰면 -> 기본값이 롤백이라 기대와 맞는다
체크 예외를 쓰면   -> rollbackFor 를 매번 적어야 한다
```

<br/>

## rollbackFor 로 바꿀 수 있다

```java
@Transactional(rollbackFor = Exception.class)
void upload(MultipartFile file) throws IOException { ... }
```

<br/>

반대로 언체크 예외인데 커밋하고 싶으면 이렇게 한다.

```java
@Transactional(noRollbackFor = NotEnoughStockException.class)
```

<br/>

다만 이걸 여기저기 붙이기 시작하면, 어느 메서드가 어떻게 도는지 알기 어려워진다.

`언체크 예외 + 기본값` 으로 통일하는 편이 읽기 쉽다.

<br/>

## 트랜잭션 밖에서 잡으면 어떻게 되는가

여기가 헷갈리기 쉬운 부분이다.

```java
@Service
class OrderService {

    @Transactional
    void order() {
        throw new RuntimeException();      // 롤백된다
    }
}

@Controller
class OrderController {

    void order() {
        try {
            orderService.order();
        } catch (RuntimeException e) {
            // 잡았지만 이미 롤백된 뒤다
        }
    }
}
```

<br/>

컨트롤러가 예외를 잡아도 롤백은 이미 끝난 상태다.

<br/>

앞의 AOP 글에서 본 프록시 구조를 떠올리면 당연하다.

```java
컨트롤러 -> 프록시 -> 진짜 order()
                        예외 발생
              프록시가 예외를 보고 롤백한다   <- 여기서 끝
        예외가 컨트롤러로 올라간다           <- 이미 롤백된 뒤
```

<br/>

예외가 프록시 경계를 넘어가는 순간 롤백 여부는 이미 정해진다.

컨트롤러의 `try-catch` 는 화면을 어떻게 보여줄지만 정할 수 있다.

<br/>

앞의 트랜잭션 전파 글에서 본 `UnexpectedRollbackException` 도 같은 원리다.

프록시가 먼저 판단하고, 우리 코드가 나중에 예외를 받는 순서다.
