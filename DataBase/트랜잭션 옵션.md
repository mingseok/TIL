## 트랜잭션 옵션

## rollbackFor

예외 발생 시 스프링 트랜잭션의 기본 정책은 다음과 같다.

언체크 예외인 `RuntimeException`, `Error` 와 그 하위 예외가 발생하면 롤백 한다.

<br/>

체크 예외인 `Exception` 과 그 하위 예외들은 커밋 한다.

이 옵션을 사용하면, 어떤 예외가 발생할 때 롤백할 지 지정할 수 있다.

```java
@Transactional(rollbackFor = Exception.class)
```

예를 들어서 이렇게 지정하면 체크 예외인 `Exception` 이 발생해도 롤백하게 된다. 

(하위 예외들도 대상에 포함된다.)

<br/>

`rollbackForClassName` 도 있는데, `rollbackFor` 는 예외 클래스를 직접 지정하고,

`rollbackForClassName` 는 예외 이름을 문자로 넣으면 된다.

<br/><br/>

## isolation

트랜잭션 격리 수준을 지정할 수 있다. 

기본 값은 데이터베이스에서 설정한 트랜잭션 격리 수준을 사용하는 `DEFAULT` 이다. 

<br/>

대부분 데이터베이스에서 설정한 기준을 따른다. 

애플리케이션 개발자가 트랜잭션 격리수준을 직접 지정하는 경우는 드물다.

```
DEFAULT : 데이터베이스에서 설정한 격리 수준을 따른다.
READ_UNCOMMITTED : 커밋되지 않은 읽기
READ_COMMITTED : 커밋된 읽기
REPEATABLE_READ : 반복 가능한 읽기
SERIALIZABLE : 직렬화 가능
```

<br/><br/>

## readOnly

트랜잭션은 기본적으로 읽기 쓰기가 모두 가능한 트랜잭션이 생성된다.

`readOnly=true` 옵션을 사용하면 읽기 전용 트랜잭션이 생성된다. 

<br/>

이 경우 등록, 수정, 삭제가 안되고 읽기 기능만 작동한다. 

```
(드라이버나 데이터베이스에 따라 정상 동작하지 않는 경우도 있다.) 
```

그리고 `readOnly` 옵션을 사용하면 읽기에서 다양한 성능 최적화가 발생할 수 있다.

<br/><br/>

## readOnly 옵션은 크게 3곳에서 적용된다.

<br/>

### 프레임워크

- `JdbcTemplate`은 읽기 전용 트랜잭션 안에서 변경 기능을 실행하면 예외를 던진다.
- `JPA(하이버네이트)`는 읽기 전용 트랜잭션의 경우 커밋 시점에 플러시를 호출하지 않는다.
    
    읽기 전용이니 변경에 사용되는 플러시를 호출할 필요가 없다. 
    
    추가로 변경이 필요 없으니 변경 감지를 위한 스냅샷 객체도 생성하지 않는다. 
    
    이렇게 JPA에서는 다양한 최적화가 발생한다.
    

<br/>

### JDBC 드라이버

```
참고로 여기서 설명하는 내용들은 `DB`와 `드라이버` 버전에 따라서 
다르게 동작하기 때문에 사전에 확인이 필요하다.
```

- 읽기 전용 트랜잭션에서 변경 쿼리가 발생하면 예외를 던진다.
- `읽기`, `쓰기`(마스터, 슬레이브) 데이터베이스를 구분해서 요청한다.
    
    읽기 전용 트랜잭션의 경우 읽기(슬레이브) 데이터베이스의 커넥션을 획득해서 사용한다.
    

<br/>

### 데이터베이스

데이터베이스에 따라 읽기 전용 트랜잭션의 경우 읽기만 하면 되므로, 내부에서 성능 최적화가 발생한다.

## 궁금증!

```java
readOnly = true 를 붙이면 정말 성능이 좋아질까?
```

원문의 `3곳에서 적용된다` 를 하나씩 보면, 각각 다른 이유로 이득이 있다.

<br/>

### 첫번째) 프레임워크 - JPA 의 변경 감지가 꺼진다

```java
@Transactional(readOnly = true)
public MemberResponse find(Long id) {
    Member member = memberRepository.findById(id).orElseThrow();
    return MemberResponse.from(member);
}
```

<br/>

`readOnly` 가 없으면 JPA는 조회한 엔티티의 복사본을 따로 들고 있는다.

트랜잭션이 끝날 때 원본과 비교해서 바뀐 것이 있으면 `UPDATE` 를 날리기 위해서다.

<br/>

이 복사본을 `스냅샷` 이라고 하는데, 조회한 엔티티마다 하나씩 만들어진다.

`1000` 건을 조회하면 `1000` 개의 복사본이 메모리에 생긴다.

<br/>

`readOnly = true` 면 어차피 안 바꿀 것을 아니까 스냅샷을 안 만든다.

메모리도 아끼고, 트랜잭션 끝날 때 비교하는 작업도 건너뛴다.

```java
readOnly 없음 - 엔티티마다 스냅샷 생성 + 종료 시 전부 비교
readOnly 있음 - 스냅샷 없음 + 비교 없음
```

<br/>

### 두번째) JDBC 드라이버 - 최적화 힌트를 준다

`Connection.setReadOnly(true)` 가 호출된다.

드라이버와 DB에 따라 다르게 동작하는데, 무시하는 경우도 있다.

<br/>

### 세번째) DB - 읽기 전용 트랜잭션으로 처리한다

DB가 알아주면 언두 로그를 안 만들 수도 있다.

앞의 MVCC 글에서 본 그 언두 로그다. 안 바꿀 거니까 되돌릴 기록도 필요 없다.

<br/>

## 그런데 실무에서 더 큰 이유는 따로 있다

읽기 전용 복제 DB로 라우팅할 수 있다는 것이다.

```java
쓰기 요청 -> 주 DB (master)
읽기 요청 -> 복제 DB (replica)
```

<br/>

`readOnly = true` 를 보고 어느 DB로 보낼지 정하는 방식이다.

조회 부하를 복제 DB로 넘기면 주 DB의 부담이 크게 줄어든다.

```java
@Transactional(readOnly = true)   // 이 표시 하나로 복제 DB 로 간다
public List<Item> findAll() { ... }
```

<br/>

성능보다 이쪽이 더 실질적인 이득이라, 조회 메서드에는 습관적으로 붙여두는 편이 좋다.

<br/>

## readOnly 인데 수정하면 어떻게 되는가

이게 헷갈리는 부분이다. 상황마다 다르다.

```java
@Transactional(readOnly = true)
public void update(Long id) {
    Member member = memberRepository.findById(id).orElseThrow();
    member.changeName("바뀐이름");        // 변경 감지가 꺼져 있으니 UPDATE 가 안 나간다
}
```

<br/>

예외도 안 나고 조용히 아무 일도 안 일어난다.

스냅샷이 없으니 바뀐 것을 감지할 방법이 없기 때문이다.

<br/>

그런데 명시적으로 `save()` 를 부르면 `UPDATE` 가 나갈 수도 있다.

DB가 읽기 전용을 강제하지 않으면 그냥 실행되어 버린다.

<br/>

`readOnly` 는 최적화 힌트지 안전 장치가 아니라고 보는 편이 맞다.

`이 메서드는 조회용이다` 라는 표시로 이해하는 것이 정확하다.

<br/>

## timeout 도 알아두면 좋다

원문에 없는 옵션인데 실무에서 중요하다.

```java
@Transactional(timeout = 3)     // 3초
```

<br/>

앞의 DB 락 글에서 본 대로, 락을 오래 잡으면 서버 전체가 느려진다.

`timeout` 을 걸어두면 그 시간을 넘길 때 트랜잭션이 강제로 롤백된다.

<br/>

특히 배치나 대량 갱신 작업에서는 걸어두는 편이 안전하다.

한 트랜잭션이 몇 분씩 락을 잡고 있으면 그동안 다른 요청이 전부 밀린다.

```java
rollbackFor - 어떤 예외에 롤백할지
isolation   - 얼마나 격리할지
readOnly    - 조회 전용인지
timeout     - 얼마나 오래 끌 수 있는지
propagation - 기존 트랜잭션이 있을 때 어떻게 할지
```

<br/>

다섯 개 중 실무에서 자주 쓰는 것은 `readOnly` 와 `propagation` 두 개다.

나머지는 기본값으로 두고, 문제가 생겼을 때 손대는 편이 낫다.
