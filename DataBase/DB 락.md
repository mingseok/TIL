## DB 락

## 문제점.

```
세션1이 트랜잭션을 시작하고 데이터를 수정하는 동안 아직 커밋을 수행하지 않았는데,
세션2에서 동시에 같은 데이터를 수정하게 되면 문제가 발생한다.
```

트랜잭션의 원자성이 깨지는 것이다.


<br/><br/>

## 문제 해결 방법.

세션이 트랜잭션을 시작하고 데이터를 수정하는 동안에는 커밋이나 롤백 전까지

다른 세션에서 해당 데이터를 수정할 수 없게 막아야 한다.

![이미지](/programming/img/입문224.PNG)

데이터베이스는 이런 문제를 해결하기 위해 락(Lock)이라는 개념을 제공한다.

<br/><br/>

## DB 락 - 조회

데이터를 조회할 때도 락을 획득하고 싶을 때가 있다. 

조회 시점에 락이 필요한 경우는 언제일까?

<br/>

트랜잭션 종료 시점까지 해당 데이터를 다른 곳에서 변경하지 못하도록 강제로 막아야 할 때 사용한다.

```
예를 들어서, 오늘 하루 정산 마감을 12시에 한다고 생각해보자.
마감을 진행하는데, 걸리는 시간은 30분정도의 시간이 걸린다. (계산 과정)
```

<br/>

그런데, 마감중에 어떤 개발자가 업데이트를 하는 것이다. → 여기서 문제가 발생하는 것이다.

돈과 관련된 매우 중요한 계산이어서 계산을 완료할 때 까지 다른곳에서 변경하면 안된다.

<br/>

그리하여 조회시에 락이 필요한 이유이다.

### 핵심은 조회시에도 락을 가져와서 동작한다는 것이다.

## 궁금증!

```java
"락이 돌아올 때까지 대기" 한다는데, 실제로 어떤 에러가 나고 얼마나 기다릴까?
```

SQLite로 두 세션을 동시에 띄워봤다.

<br/>

### 세션 A - 수정하고 커밋하지 않은 상태로 3초 대기

```sql
BEGIN IMMEDIATE;
UPDATE t SET v = 200 WHERE id = 1;
-- 아직 COMMIT 안 함
```

<br/>

### 세션 B - 같은 행을 수정 시도 (대기 시간 0.5초)

```sql
UPDATE t SET v = 300 WHERE id = 1;
```

<br/>

### 결과

```sql
A: 수정함, 아직 커밋 안 함
B: 지금 쓰기를 시도한다
B: Error: stepping, database is locked (5)
B: 읽기는 되는가 -> 100
A: 커밋 완료
최종 값 = 200
```

<br/>

세 가지가 보인다.

- `B` 의 쓰기는 막혔다. 대기 시간이 지나도 락을 못 얻어서 에러가 났다

- `B` 의 읽기는 됐다. 그런데 값이 `100` 이다
- 결국 `A` 의 값인 `200` 이 남았다. `B` 의 `300` 은 반영되지 않았다

<br/>

## 읽기가 200이 아니라 100인 것이 중요하다

`A` 는 이미 `200` 으로 바꿔놨는데 `B` 에게는 `100` 으로 보인다.

<br/>

커밋되지 않은 값을 남이 읽으면 안 되기 때문이다.

만약 `B` 가 `200` 을 읽고 그것으로 계산했는데 `A` 가 롤백해버리면,

세상에 존재한 적 없는 값으로 계산한 셈이 된다.

<br/>

원문의 `DB 락 - 조회` 부분이 이 얘기다.

읽기는 대개 락을 기다리지 않는다. 대신 `커밋된 마지막 값` 을 본다.

```java
쓰기 - 락을 기다린다. 못 얻으면 타임아웃
읽기 - 안 기다린다. 바뀌기 전 값을 본다
```

<br/>

## 락 타임아웃

원문의 `락이 돌아올 때까지 대기` 는 무한정 기다린다는 뜻이 아니다.

기다리는 시간에 한계가 있고, 넘으면 위처럼 에러가 난다.

```sql
-- MySQL
SET innodb_lock_wait_timeout = 50;    -- 기본 50초

-- PostgreSQL
SET lock_timeout = '5s';

-- SQLite
.timeout 500                          -- 밀리초
```

<br/>

무한정 기다리게 하면 안 되는 이유가 있다.

<br/>

기다리는 동안 그 요청은 스레드 하나를 붙잡고 있다.

앞의 서블릿 글에서 본 대로 요청 하나에 스레드 하나인데,

락을 기다리는 요청이 쌓이면 스레드 풀이 다 차서 서버 전체가 멈춘다.

```java
락을 오래 잡고 있는 트랜잭션 하나
-> 기다리는 요청이 쌓인다
-> 스레드 풀이 고갈된다
-> 락과 상관없는 요청까지 응답을 못 받는다
```

<br/>

그래서 트랜잭션은 짧게 유지해야 한다.

`@Transactional` 안에서 외부 API를 호출하면 안 되는 이유가 이것이다.

API 응답이 5초 걸리면 그동안 락을 5초 잡고 있게 된다.

<br/>

## 데드락

서로가 서로의 락을 기다리면 영원히 안 풀린다.

```java
A: 1번 행 락 획득 -> 2번 행 락 요청 (B 가 갖고 있어서 대기)
B: 2번 행 락 획득 -> 1번 행 락 요청 (A 가 갖고 있어서 대기)
```

<br/>

DB는 이걸 감지해서 한쪽을 강제로 롤백시킨다.

```java
Deadlock found when trying to get lock; try restarting transaction
```

<br/>

`try restarting transaction` 이라고 친절하게 알려준다.

죽은 쪽은 다시 시도하면 대개 성공한다.

<br/>

예방법은 간단하다. `항상 같은 순서로 락을 잡는` 것이다.

```java
// 위험 - 계좌 번호 순서가 요청마다 다르다
transfer(from, to) {
    lock(from); lock(to);
}

// 안전 - 항상 작은 id 부터 잠근다
transfer(from, to) {
    Long first = Math.min(from, to);
    Long second = Math.max(from, to);
    lock(first); lock(second);
}
```

<br/>

## 비관적 락과 낙관적 락

지금까지 본 것은 `비관적 락` 이다. 충돌이 날 거라고 보고 미리 잠근다.

```java
SELECT * FROM item WHERE id = 1 FOR UPDATE;    -- 조회하면서 락을 건다
```

<br/>

`낙관적 락` 은 잠그지 않는다. 대신 버전 컬럼을 두고 나중에 확인한다.

```java
UPDATE item SET stock = 9, version = 2
WHERE id = 1 AND version = 1;                  -- 그 사이에 안 바뀌었으면 1건 갱신
```

<br/>

갱신된 행이 `0` 건이면 그 사이에 누가 바꾼 것이다. 그때 예외를 던지고 다시 시도한다.

```java
비관적 락 - 충돌이 잦은 곳. 재고 차감, 좌석 예약
낙관적 락 - 충돌이 드문 곳. 게시글 수정
```

<br/>

충돌이 드문데 비관적 락을 쓰면 안 잠가도 될 것을 잠그느라 처리량이 떨어진다.

충돌이 잦은데 낙관적 락을 쓰면 재시도만 계속 하다가 더 느려진다.
