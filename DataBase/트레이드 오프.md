## 트레이드 오프

- DI, OCP를 지키기 위해 어댑터를 도입하고, 더 많은 코드를 유지한다

- 어댑터를 제거하고 구조를 단순하게 가져가지만, DI, OCP를 포기하고, ItemService 코드를 직접 변경한다.
    

```
결국 여기서 발생하는 트레이드 오프는 구조의 안정성 vs 단순한 구조와 
개발의 편리성 사이의 선택이다. 이 둘 중에 하나의 정답만 있을까? 그렇지 않다.

어떤 상황에서는 구조의 안정성이 매우 중요하고, 
어떤 상황에서는 단순한 것이 더 나은 선택일 수 있다.
```

<br/>

개발을 할 때는 항상 자원이 무한한 것이 아니다. 

그리고 어설픈 추상화는 오히려 독이 되는 경우도 많다.

<br/>

무엇보다 추상화도 비용이 든다. 

인터페이스도 비용이 든다. 

<br/>

여기서 말하는 비용은 유지보수 관점에서 비용을 뜻한다. 

이 추상화 비용을 넘어설 만큼 효과가 있을 때 추상화를 도입하는 것이 실용적이다.

현재 상황에 맞는 선택을 하는 개발자가 좋은 개발자라 생각한다.
<br/>

## 궁금증!

```java
DB 에서 마주치는 트레이드 오프에는 어떤 것들이 있을까?
```

지금까지 본 것들만 모아도 꽤 된다. 전부 `무엇을 포기할 것인가` 의 문제다.

<br/>

### 인덱스 - 읽기 속도 vs 쓰기 속도와 공간

앞의 DB 인덱스 글에서 실제로 재본 숫자다.

```java
조회 1000 번  : 3411 ms -> 37 ms   (92 배 빨라짐)
삽입 1 만 건  :   43 ms -> 51 ms   (조금 느려짐)
공간          : 테이블 3824 KB, 인덱스 2620 KB
```

<br/>

읽기를 얻는 대신 쓰기와 공간을 내준다.

조회가 많은 테이블이면 이득이고, 로그처럼 쓰기만 하는 테이블이면 손해다.

<br/>

### 격리 수준 - 정확성 vs 처리량

```java
SERIALIZABLE     - 가장 정확하다. 대신 오래 잠가서 느리다
READ COMMITTED   - 빠르다. 대신 같은 조회를 두 번 하면 값이 다를 수 있다
```

<br/>

### 정규화 - 정합성 vs 조회 성능

```java
정규화 - 같은 사실이 한 곳에만 있다. 대신 조인이 늘어난다
역정규화 - 조인이 준다. 대신 동기화를 계속 신경 써야 한다
```

<br/>

### 커넥션 풀 크기 - 동시 처리 vs 자원

```java
크게 잡으면 - 더 많은 요청을 동시에 받는다. 대신 DB 가 먼저 죽는다
작게 잡으면 - DB 가 안정적이다. 대신 대기가 생긴다
```

<br/>

### 락 - 안전 vs 처리량

```java
비관적 락 - 충돌을 확실히 막는다. 대신 기다린다
낙관적 락 - 안 기다린다. 대신 충돌하면 다시 해야 한다
```

<br/>

## 공통점이 하나 있다

전부 `무엇이 더 많은가` 에 답이 달려 있다는 것이다.

```java
조회가 많은가 쓰기가 많은가        -> 인덱스를 걸까 말까
충돌이 잦은가 드문가              -> 비관적 락인가 낙관적 락인가
정확성이 중요한가 속도가 중요한가   -> 격리 수준을 얼마나 올릴까
```

<br/>

그래서 정답이 정해져 있지 않다. 상황을 재보고 정해야 한다.

<br/>

이 말이 추상적으로 들리는데, 실제로는 `측정할 수 있다` 는 뜻이다.

```sql
EXPLAIN QUERY PLAN SELECT ...     -- 인덱스를 쓰는지
SHOW ENGINE INNODB STATUS;        -- 락 대기와 데드락이 얼마나 있는지
SELECT * FROM information_schema.PROCESSLIST;   -- 오래 도는 쿼리가 있는지
```

<br/>

앞의 글들에서 `EXPLAIN QUERY PLAN` 으로 인덱스가 쓰이는지 확인하고,

시간을 재서 `92 배` 라는 숫자를 얻은 것이 그 방법이다.

<br/>

## 어느 쪽으로 기울지 모를 때

의심스러우면 `되돌리기 쉬운 쪽` 을 고르는 편이 낫다.

```java
인덱스 - 나중에 만들 수도 있고 지울 수도 있다. 되돌리기 쉽다
역정규화 - 한 번 컬럼을 복사해두면 되돌리기 어렵다. 코드가 그것에 의존하게 된다
```

<br/>

정규화를 먼저 하고 필요할 때 역정규화하는 순서를 권하는 이유가 이것이다.

반대 순서로 가면 되돌리는 비용이 훨씬 크다.
