## 궁금증!

```java
왜 관계형이 아직도 기본인가
```

NoSQL이 나온 지 오래인데도 대부분의 서비스가 관계형으로 시작한다.

<br/>

이유가 몇 가지 있다.

```java
1. 트랜잭션이 확실하다
2. 스키마가 있어서 데이터가 안 깨진다
3. 조인으로 데이터를 조합할 수 있다
4. SQL 을 아는 사람이 많다
```

<br/>

`1번` 이 크다.

앞의 트랜잭션(Transaction) 글에서 본 ACID를 지켜주는 게 생각보다 어려운 일이다.

<br/>

돈이 오가는 곳에서는 이게 협상 대상이 아니다.

```java
계좌에서 빼고 -> 다른 계좌에 넣는다
중간에 실패하면 -> 둘 다 없던 일로
```

## 관계라는 말이 오해를 부른다

`테이블끼리 관계를 맺는다` 는 뜻으로 이해하기 쉬운데,

원래 `relation` 은 수학의 관계다.

<br/>

```java
relation = 표 그 자체
tuple    = 행
attribute = 열
```

<br/>

`회원 표` 하나가 이미 `relation` 이다.

`이름과 나이와 도시의 조합` 이라는 관계를 나타내는 것이다.

<br/>

외래 키로 표를 잇는 것은 그 위에 얹힌 얘기다.

<br/>

## 집합으로 다룬다는 게 핵심이다

```sql
UPDATE member SET grade = 'GOLD' WHERE age > 30;
```

<br/>

`30살 넘는 사람들` 이라는 집합에 한 번에 적용한다.

<br/>

프로그래밍 언어라면 이렇게 쓴다.

```java
for (Member m : members) {
    if (m.getAge() > 30) {
        m.setGrade(GOLD);
    }
}
```

<br/>

`어떻게 할지` 를 적는 것과 `무엇을 원하는지` 를 적는 것의 차이다.

<br/>

그래서 SQL은 선언형 언어로 분류된다.

`어떻게 찾을지` 는 옵티마이저가 정한다.

<br/>

앞의 실행 계획 글에서 본 대로,

같은 SQL이 상황에 따라 다른 방법으로 실행되는 것이 이 때문이다.

<br/>

## 그럼 NoSQL 은 언제 쓰나

관계형이 못 하는 것을 할 때다.

```java
스키마가 자주 바뀌거나 정해지지 않은 데이터   -> 문서 DB (MongoDB)
아주 빠른 조회, 캐시                        -> 키-값 (Redis)
관계 자체를 탐색해야 하는 것                 -> 그래프 DB (Neo4j)
로그처럼 계속 쌓이기만 하는 것               -> 시계열 DB
전문 검색                                   -> Elasticsearch
```

<br/>

`대신 쓰는 것` 이 아니라 `같이 쓰는 것` 이 보통이다.

<br/>

앞의 캐시 글에서 본 대로,

주 데이터는 관계형에 두고 Redis를 캐시로 앞에 두는 식이다.

<br/>

## 확장 방식이 다르다

```java
관계형  - 수직 확장이 기본. 서버를 키운다
NoSQL   - 수평 확장이 기본. 서버를 늘린다
```

<br/>

관계형이 수평 확장이 어려운 이유는 조인과 트랜잭션 때문이다.

<br/>

데이터가 여러 서버에 흩어져 있으면 조인이 네트워크를 타야 한다.

트랜잭션도 여러 서버에 걸쳐야 해서 훨씬 복잡해진다.

<br/>

그래서 관계형은 읽기만 늘리는 방식을 먼저 쓴다.

```java
쓰기는 한 대 (마스터)
읽기는 여러 대 (레플리카)
```

<br/>

대부분의 서비스가 읽기가 훨씬 많으니 이걸로 꽤 버틴다.

<br/>

## 요즘은 경계가 흐려지고 있다

```java
PostgreSQL, MySQL 이 JSON 컬럼을 지원한다
MongoDB 가 트랜잭션을 지원한다
```

<br/>

```sql
CREATE TABLE product (
    id BIGINT PRIMARY KEY,
    name VARCHAR(100),
    attributes JSON        -- 상품마다 다른 속성
);
```

<br/>

정형 데이터는 컬럼으로, 비정형은 JSON으로 두는 방식이 자주 쓰인다.

<br/>

앞의 정규화 글에서 본 원칙과 충돌하는 면이 있는데,

`모든 상품에 공통인 것` 과 `상품마다 다른 것` 을 나눠 담는 것이라

실용적인 절충으로 받아들여진다.

<br/>

다만 JSON 안의 값으로 검색하면 인덱스가 까다로워진다.

`무엇으로 검색할 것인가` 를 먼저 정하고 나누는 게 낫다.
