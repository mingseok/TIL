## 가장 중요한 곳은 어디일까?

바로, 핵심 비즈니스 로직이 들어있는 서비스 계층이다. 

시간이 흘러서 UI(웹)와 관련된 부분이 변하고, 데이터 저장 기술을 다른 기술로 변경해도, 

비즈니스 로직은 최대한 변경없이 유지되어야 한다.

<br/><br/>

### 서비스 계층을 특정 기술에 종속적이지 않게 개발해야 한다.

- 이렇게 계층을 나눈 이유도 서비스 계층을 최대한 순수하게 유지하기 위한 목적이 크다.
- 서비스 계층에서 데이터 접근 계층을 직접 접근하는 것이 아니라,
    
    인터페이스를 제공하고 서비스 계층은 이 인터페이스에 의존하는 것이 좋다.


<br/><br/>

## 정리

서비스 계층은 가급적 비즈니스 로직만 구현하고, 특정 구현 기술에 직접 의존해서는 안된다. 

이렇게 하면 향후 구현 기술이 변경될 때 변경의 영향 범위를 최소화 할 수 있다.

<br/><br/>

## MemberService

```java
import java.sql.SQLException;

@RequiredArgsConstructor
public class MemberService {

	 private final MemberRepository memberRepository;
	
	 public void accountTransfer(String fromId, String toId, int money) throws SQLException {
			 Member fromMember = memberRepository.findById(fromId);
			 Member toMember = memberRepository.findById(toId);
			
			 memberRepository.update(fromId, fromMember.getMoney() - money);
			 memberRepository.update(toId, toMember.getMoney() + money);
	 }
}
```

- MemberService 은 특정 기술에 종속적이지 않고, 순수한 비즈니스 로직만 존재한다.

- 특정 기술과 관련된 코드가 거의 없어서 코드가 깔끔하고, 유지보수 하기 쉽다.
- 향후 비즈니스 로직의 변경이 필요하면 이 부분을 변경하면 된다.

## 궁금증!

```java
서비스 계층에 순수 자바만 남기라는 게 왜 그렇게 중요할까?
```

`테스트할 수 있는가` 가 갈리기 때문이다.

<br/>

기술이 섞인 서비스는 이렇게 생긴다.

```java
@Service
public class MemberService {

    public void join(HttpServletRequest request) throws SQLException {
        String name = request.getParameter("name");          // 웹 기술
        Connection connection = dataSource.getConnection();   // JDBC 기술
        // ...
    }
}
```

<br/>

이 메서드를 테스트하려면 `HttpServletRequest` 를 만들고 DB를 띄워야 한다.

<br/>

기술을 걷어내면 이렇게 된다.

```java
@Service
@RequiredArgsConstructor
public class MemberService {
    private final MemberRepository memberRepository;    // 인터페이스

    public void join(String name) {
        if (memberRepository.existsByName(name)) {
            throw new DuplicateMemberException();
        }
        memberRepository.save(new Member(name));
    }
}
```

<br/>

앞의 DI 글에서 본 대로 순수 자바로 테스트할 수 있게 된다.

```java
MemberService service = new MemberService(new FakeMemberRepository());
service.join("민석");
```

<br/>

DB도 웹도 없이 비즈니스 규칙만 검증할 수 있다.

<br/>

## Repository 가 인터페이스여야 하는 이유

`MemberRepository` 가 구체 클래스면 위 테스트가 안 된다.

```java
public interface MemberRepository {
    void save(Member member);
    boolean existsByName(String name);
}
```

<br/>

이렇게 두면 구현을 갈아끼울 수 있다.

```java
JdbcMemberRepository   - 운영용
JpaMemberRepository    - JPA 로 바꿀 때
FakeMemberRepository   - 테스트용 (그냥 HashMap)
```

<br/>

앞의 인터페이스 글에서 본 결제 예제와 완전히 같은 구조다.

`쓰는 쪽 코드를 안 고치고 구현만 바꾼다` 는 목적도 같다.

<br/>

## 그런데 예외가 새어 나온다

인터페이스로 막아놨는데도 구멍이 하나 있다.

```java
public interface MemberRepository {
    void save(Member member) throws SQLException;    // JDBC 예외가 인터페이스에 있다
}
```

<br/>

`SQLException` 이 체크 예외라서 인터페이스 선언에 적어야 한다.

그러면 JPA로 바꿀 때 `SQLException` 이 안 나오니 인터페이스를 고쳐야 한다.

<br/>

앞의 exception 글에서 본 문제가 그대로 나온다.

`던지는 쪽의 사정을 받는 쪽이 알게 되는` 것이다.

<br/>

그래서 언체크 예외로 바꿔서 던진다.

```java
public interface MemberRepository {
    void save(Member member);        // throws 가 사라졌다
}
```

<br/>

앞의 PSA 글에서 본 `DataAccessException` 이 스프링이 제공하는 그 변환이다.

`SQLException` 을 잡아서 기술과 무관한 언체크 예외로 바꿔 던져준다.

<br/>

## 서비스가 트랜잭션 경계인 이유

`@Transactional` 은 서비스에 붙인다. 컨트롤러나 리포지토리가 아니다.

```java
@Service
public class OrderService {

    @Transactional
    public void order(Long memberId, Long itemId, int count) {
        Item item = itemRepository.findById(itemId);
        item.removeStock(count);                        // 재고 차감
        orderRepository.save(new Order(...));           // 주문 저장
    }
}
```

<br/>

`하나의 업무 단위` 가 서비스 메서드이기 때문이다.

재고 차감과 주문 저장은 같이 되거나 같이 안 되어야 한다.

<br/>

리포지토리에 붙이면 각각이 별개 트랜잭션이 된다.

재고만 줄고 주문은 안 되는 상황이 생긴다.

<br/>

컨트롤러에 붙이면 트랜잭션이 너무 길어진다.

앞의 DBCP 글에서 본 대로, 요청 처리 전체 동안 커넥션을 잡고 있게 된다.

```java
컨트롤러 - 너무 넓다. 화면 렌더링까지 트랜잭션에 들어간다
서비스   - 업무 단위와 일치한다
리포지토리 - 너무 좁다. 여러 개를 묶을 수 없다
```

<br/>

## 서비스가 얇아지면 오히려 문제다

```java
@Service
public class MemberService {

    public Member find(Long id) {
        return memberRepository.findById(id);     // 그냥 넘기기만 한다
    }
}
```

<br/>

이런 메서드만 잔뜩 있으면 서비스 계층이 있으나 마나다.

앞의 클래스와 메소드 글에서 본 대로, 로직이 다른 데로 흩어졌다는 뜻이다.

<br/>

대개 컨트롤러에 로직이 가 있는 경우다.

```java
@PostMapping("/orders")
public String order(@ModelAttribute OrderForm form) {
    Item item = itemService.find(form.getItemId());
    if (item.getStock() < form.getCount()) {          // 이 판단이 컨트롤러에 있다
        throw new IllegalStateException();
    }
    ...
}
```

<br/>

`재고가 모자라면 안 된다` 는 것은 업무 규칙이지 화면의 사정이 아니다.

서비스로 내려야 웹 없이 테스트할 수 있게 된다.
