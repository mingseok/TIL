## 일급 컬렉션이란?



`Collection`을 `Wrapping` 하면서, `Wrapping`한 `Collection` 외 다른 

멤버 변수가 없는 상태를 `일급 컬렉션`이라 한다.

```java
"이게 무슨 말일까?"
```

<br/>

### 변경 전 코드)

```java
public class Person {
    private String name;
    private List<Car> cars;
    // ...
}

public class Car {
    private String name;
    private String oil;
    // ...
}
```

<br/>

### 변경 후 코드) `Collection`을 `Wrapping`한다

```java
public class Person {
    private String name;
    private Cars cars;
    // ...
}

// List<Car> cars를 Wrapping
// 일급 컬렉션
public class Cars {
    // 멤버변수가 하나 밖에 없다!!
    private List<Car> cars;
    // ...
}

public class Car {
    private String name;
    private String oil;
    // ...
}
```

<br/>

위의 코드를 보면 일급 컬렉션은 그`(List<Car> cars)` 외 다른 멤버 변수가 없다.

```java
"이것이 일급 컬렉션이다"
```

<br/><br/>

## 왜 사용하지?

GS편의점에 아이스크림을 팔고 있다.

```java
public class GS편의점 {
    // 편의점에는 여러 개의 아이스크림을 팔고 있을 것이다.
    private List<IceCream> iceCreams;

    public GS편의점(List<IceCream> iceCreams) {
        this.iceCreams = iceCreams;
    }
    ...
}

public class IceCream {
    private String name;
    ...
}
```

<br/>

특이하게도 해당 편의점은 아이스크림의 종류를 `10가지` 이상 팔지 못한다고 한다.

그러면 우리는 `List<IceCream> iceCreams`의 size가 10이 넘으면 안되는 `검증`이 필요할 것이다.

```java
public class GS편의점 {
    private List<IceCream> iceCreams;

    public GS편의점(List<IceCream> iceCreams) {
        validateSize(iceCreams)
        this.iceCreams = iceCreams;
    }

    private void validateSize(List<IceCream> iceCreams) {
    	if (iceCreams.size() >= 10) {
            new throw IllegalArgumentException("아이스크림은 10개 이상의 종류를 팔지 않습니다.")
        }
    }
}
```

흠…그래서..? 뭐가 문제지?

<br/><br/>

## 이유는

만약 아이스크림뿐만 아니라 `과자`, `라면` 등 여러 가지가 있다고 가정해보자.

- 모든 검증을 GS편의점 ****`class`에서 할 것인가?

```java
validate아이스크림(아이스크림);
validate과자(과자);
validate라면(라면);
// ...더 추가 될수도?
```

<br/>

만약 `CU편의점` class에서도 동일한 것을 판다면 

`GS편의점` class에서 했던 검증을 또 사용할 것인가?

```java
public class GS편의점 {
    private List<IceCream> iceCreams;
    private List<Snack> snacks;
    private List<Noodle> Noobles;

    public GS편의점(List<IceCream> iceCreams ...) {
        validate아이스크림(아이스크림);
        validate과자(과자);
        validate라면(라면);
        // ...
    }
    // ...
}

public class CU편의점 {
    private List<IceCream> iceCreams;
    private List<Snack> snacks;
    private List<Noodle> Noobles;

    public CU편의점(List<IceCream> iceCreams ...) {
        validate아이스크림(아이스크림);
        validate과자(과자);
        validate라면(라면);
        // ...
    }
    // ...
}
```

<br/>

`List<IceCream> iceCreams`의 원소 중에서 하나를 **`find`**하는 메서드를 만든다고 가정해보자.

- `GS편의점` class와 `CU편의점` class 같은 메서드(find)를 `두번` 구현할 것인가?

```java
public class GS편의점 {
    private List<IceCream> iceCreams;
    // ...
    public IceCream find(String name) {
        return iceCreams.stream()
            .filter(iceCream::isSameName)
            .findFirst()
            .orElseThrow(RuntimeException::new)
    }
    // ...
}

public class CU편의점 {
    private List<IceCream> iceCreams;
    // ...
    public IceCream find(String name) {
        return iceCreams.stream()
            .filter(iceCream::isSameName)
            .findFirst()
            .orElseThrow(RuntimeException::new)
    }
    // ...
}
```

<br/>

이럴 경우 편의점 `class의 역할`이 무거워 지고, `중복코드` 가 많아진다.

```java
"이것을 해결해주는 것이 일급컬렉션이다."
```

`상태와 행위`을 각각 관리할 수 있다.

## 아이스크림을 `일급 컬렉션`으로 만들어 보자.

```java
public class IceCreams {
    private List<IceCream> iceCreams;

    public IceCreams(List<IceCream> iceCreams) {
        validateSize(iceCreams)
        this.iceCreams = iceCreams

    private void validateSize(List<IceCream> iceCreams) {
    	if (iceCreams.size() >= 10) {
            new throw IllegalArgumentException("아이스크림은 10개 이상의 종류를 팔지않습니다.")
        }
    }

    public IceCream find(String name) {
        return iceCreams.stream()
            .filter(iceCream::isSameName)
            .findFirst()
            .orElseThrow(RuntimeException::new)
    }
    // ...
}
```

## 그럼 편의점 class는 어떻게 달라질까?

```java
public class GS편의점 {
    private IceCreams iceCreams;

    public GS편의점(IceCreams iceCreams) {
        this.iceCreams = iceCreams;
    }

    public IceCream find(String name) {
        return iceCreams.find(name); // 핵심
    }
    // ...
}

public class CU편의점 {
    private IceCreams iceCreams;

    public CU편의점(IceCreams iceCreams) {
        this.iceCreams = iceCreams;
    }

    public IceCream find(String name) {
        return iceCreams.find(name); // 핵심
    }
    // ...
}
```

이런 느낌인 것이다.

`과자`랑 `라면` 등이 생겨도 **검증**은 `과자의 일급 컬렉션`과 `라면의 일급 컬렉션`이 해줄 것이다.

그리고 편의점 class가 했던 역할을 `아이스크림`, `과자`, `라면` 등 
각각에게 `위임`하여 `상태와 로직`을 관리 할 것이다.

<br/><br/>

## 정리하면

**`일급 컬렉션`**을 사용하면 `상태과 로직을 따로 관리`할 수 있기 때문에 

로직이 사용되는 `클래스의 부담`을 줄일 수 있고,  `중복코드`를 줄일 수 있다.

<br/>

## 궁금증!

```java
컬렉션을 감싸면 정확히 무엇이 좋아지는가
```

앞의 방어적 복사, Unmodifiable 글에서 돌려본 결과가 그 답의 절반이다.

```java
class Naive {
    private final List<String> names;
    Naive(List<String> names) { this.names = names; }
    List<String> getNames() { return names; }
}
```

```java
내부 상태 = [민석, 영한, 몰래추가]
```

<br/>

`final` 을 붙였는데도 밖에서 두 번이나 바꿨다.

<br/>

일급 컬렉션은 이 문제를 `감싸는 클래스를 하나 만들어서` 푼다.

```java
public class Names {
    private final List<Name> names;

    public Names(List<Name> names) {
        this.names = new ArrayList<>(names);        // 들어올 때 복사
    }

    public List<Name> getNames() {
        return List.copyOf(names);                   // 나갈 때도 막는다
    }
}
```

<br/>

## 그런데 그게 전부가 아니다

감싸는 것 자체보다 `규칙을 둘 자리가 생긴다` 는 것이 더 크다.

```java
// 감싸기 전 - 규칙이 흩어진다
List<Item> items = new ArrayList<>();
if (items.size() >= 10) {
    throw new IllegalStateException("장바구니는 10개까지");
}
items.add(item);
```

<br/>

이 검사를 담는 곳마다 적어야 한다. 한 군데라도 빠뜨리면 규칙이 깨진다.

<br/>

```java
// 감싼 뒤 - 규칙이 한 곳에 있다
public class Cart {
    private static final int MAX_SIZE = 10;
    private final List<Item> items;

    public void add(Item item) {
        if (items.size() >= MAX_SIZE) {
            throw new IllegalStateException("장바구니는 10개까지");
        }
        items.add(item);
    }
}
```

<br/>

`Cart` 를 통하지 않고는 담을 방법이 없으니 규칙이 반드시 지켜진다.

<br/>

## 계산도 안으로 들어온다

앞의 객체는 객체스럽게 사용한다 글에서 본 그 얘기가 여기서 이어진다.

```java
// 밖에서 계산
int total = 0;
for (Item item : cart.getItems()) {
    total += item.getPrice() * item.getCount();
}

// 안에서 계산
public int totalPrice() {
    return items.stream().mapToInt(Item::amount).sum();
}
```

<br/>

`getItems()` 를 쓸 일 자체가 없어진다.

컬렉션을 꺼낼 필요가 없으니 앞에서 본 방어적 복사 고민도 대부분 사라진다.

<br/>

## 이름이 생기는 것도 이득이다

```java
List<Item> items                  // 무슨 목록인지 타입만 알려준다
Cart cart                         // 장바구니라는 것을 이름이 알려준다
List<Lotto> lottos                // 로또 목록
Lottos lottos                     // 로또 묶음. 여기에 당첨 계산이 들어간다
```

<br/>

앞의 클래스명, 메소드명, 변수명 규칙 글에서 본 `자료형을 이름에 넣지 말라` 와 이어진다.

`List` 라는 자료형 대신 `Cart` 라는 개념을 쓰게 되는 것이다.

<br/>

## 그런데 항상 감싸야 하는 것은 아니다

클래스가 늘어나는 비용이 있다.

```java
감쌀 만한 경우
  - 그 목록에 규칙이 있다 (개수 제한, 중복 금지, 정렬 순서)
  - 그 목록으로 계산할 것이 있다 (합계, 통계)
  - 여러 곳에서 같은 방식으로 다룬다

감쌀 필요 없는 경우
  - 메서드 안에서 잠깐 쓰고 버리는 지역 변수
  - 화면에 뿌리기만 하는 조회 결과
```

<br/>

앞의 DTO 글에서 본 응답 객체 안의 `List` 를 굳이 감쌀 이유는 없다.

거기서는 그냥 데이터를 나르는 것이 전부이기 때문이다.

<br/>

## 필드가 하나여야 하는 이유

일급 컬렉션의 정의에 `컬렉션 필드 하나만 갖는다` 는 조건이 있다.

<br/>

필드가 둘이 되면 그 둘 사이의 관계까지 관리해야 해서 성격이 달라진다.

```java
public class Lottos {
    private final List<Lotto> lottos;       // 이것만 있다
}

public class LottoResult {
    private final List<Lotto> lottos;
    private final WinningNumber winning;     // 둘이 되면 일급 컬렉션이 아니다
}
```

<br/>

`LottoResult` 가 나쁘다는 것이 아니라, 그건 그냥 도메인 객체라는 뜻이다.

앞의 우아한 테크코스 글에서 본 `인스턴스 변수를 줄이자` 와도 이어진다.

필드가 하나면 그 클래스가 무엇에 대한 것인지 의심할 여지가 없어진다.
