## 왜 DB index로 B tree 계열이 사용되는가?



### 핵심

![이미지](/programming/img/입문517.PNG)

저런 block의 특성 때문에, DB index는 B tree를 사용하는 것이다.

- 왜? → 블록은 남은 공간까지 가져오기에, 노드 개수가 많은 B tree 특성을 사용하면 효율을 극대화 할 수 있기 때문이다.
    

```java
"핵심은, 데이터를 찾을 때 탐색 범위를 빠르게 좁힐 수 있는 것이다"
```

<br/><br/>

## B tree index vs AVL tree index 비교

- B tree index는 5차라고 생각하기.

- AVL 트리는 self-balancing BST (AVL 트리, 레드-블랙 트리) 등의 종류가 있다.

![이미지](/programming/img/입문518.PNG)

<br/>

### AVL 트리와 B tree(5차)를 비교하면 이렇다.

B tree(5차)가 성능 적인 측면에서 훨씬 빠르게 데이터를 조회가 된 걸 알 수 있다.

- `이유 1)` AVL tree index 는 자녀 노드 수 1~2개만 가질 수 있는데,

    - 5차 B tree index 같은 경우는 3~5개를 가질 수 있기 때문이다.

- `이유 2)` AVL tree index 는 각 노드가 하나의 데이터만 가질 수 있지만,

    - 5차 B tree index 같은 경우는 최소 2개에서 최대 4개까지 가질 수 있기 때문이다.

<br/><br/>

## secondary storage 장점

block의 특성 때문에도, B tree는 적합하다.

- 왜? → 블록의 특성은 남은 공간까지 가져 오는 것인데,
    
    노드 개수가 많은 B tree 특성을 사용하면 효율을 극대화 할 수 있기 때문이다.
    

![이미지](/programming/img/입문519.PNG)

<br/><br/>

## B tree 장점

4개의 level만으로 수 백만, 수 천만 개의 데이터를 저장할 수 있다.

- root 노드에서 가장 멀리 있는 데이터도 세 번의 이동만으로 접근 할 수 있다

- 엄청나게 많은 양의 데이터를 저장해야 될 때 데이터 베이스에서 인덱스로 사용하기에 가장 적합한 것이다.
    
- DB는 기본적으로 secondary storage에 저장된다.

    - 같은 기능을 수행 하더라도 secondary storage에 적게 접근하는 방식 더 좋은 방식이다.
        - 이유는? → secondary storage는 데이터를 처리하는 속도가 느리기 때문이다

- B tree index는 AVL tree index 에 비해 secondary storage 접근을 적게 하면서도, 데이터를 조회 할 수 있는 장점이 있다.
    
- B tree 노드는 block 단위의 저장 공간을 알차게 사용할 수 있다
<br/>

## 궁금증!

```java
해시 테이블이 O(1) 인데 왜 B tree 를 쓸까?
```

앞의 DB 인덱스 글에서 실행 계획을 찍어봤을 때 답의 절반이 나왔다.

```sql
-- 등호 조회
EXPLAIN QUERY PLAN SELECT * FROM member WHERE email = 'user99999@test.com';
`--SEARCH member USING INDEX idx_member_email (email=?)

-- 범위 조회
EXPLAIN QUERY PLAN SELECT * FROM member WHERE email > 'user5' AND email < 'user6';
`--SEARCH member USING INDEX idx_member_email (email>? AND email<?)

-- 정렬
EXPLAIN QUERY PLAN SELECT * FROM member ORDER BY email LIMIT 10;
`--SCAN member USING INDEX idx_member_email
```

<br/>

등호 말고도 범위 조회와 정렬에 인덱스가 쓰였다.

해시 인덱스였다면 이 둘은 못 쓴다.

<br/>

해시는 값을 흩어서 저장한다.

`user5` 와 `user6` 의 해시값은 아무 관계도 없어서, 사이에 무엇이 있는지 알 방법이 없다.

```java
해시 - 값 하나를 찾는 데는 최고. 순서 정보가 없다
B tree - 정렬된 상태로 저장된다. 범위와 정렬을 그대로 쓸 수 있다
```

<br/>

실무 쿼리에서 `WHERE date BETWEEN ...`, `ORDER BY created_at DESC` 같은 것이

`WHERE id = 1` 만큼이나 많다. 그래서 순서를 잃는 해시는 기본 선택지가 못 된다.

<br/>

## 두 번째 이유는 디스크다

이쪽이 더 근본적이다.

<br/>

메모리 자료구조는 `비교 횟수` 를 줄이는 것이 목표다.

디스크 자료구조는 `디스크를 몇 번 읽는가` 를 줄이는 것이 목표다.

<br/>

디스크는 메모리보다 수만 배 느리다.

비교를 100번 더 하더라도 디스크 접근을 1번 줄이는 쪽이 훨씬 이득이다.

<br/>

그리고 디스크는 한 번 읽을 때 한 덩어리씩 읽는다. `4KB` 나 `16KB` 단위다.

한 바이트만 필요해도 그 덩어리 전체가 올라온다.

<br/>

## 그래서 노드 하나를 그 덩어리 크기로 맞춘다

이진 트리는 노드마다 자식이 둘이다. `10만` 개면 높이가 `17` 이라 디스크를 `17` 번 읽는다.

<br/>

`B tree` 는 노드 하나에 키를 수백 개씩 담는다.

노드 하나를 디스크 한 덩어리에 딱 맞춰서, 한 번 읽으면 수백 개를 한꺼번에 얻는 것이다.

```java
노드 하나에 키 200 개를 담으면
  높이 1 -> 200 개
  높이 2 -> 4 만 개
  높이 3 -> 800 만 개
  높이 4 -> 16 억 개
```

<br/>

`16억` 건짜리 테이블도 디스크를 네 번만 읽으면 찾는다.

<br/>

이진 트리로 `16억` 개면 높이가 `31` 이다. 디스크 `31` 번과 `4` 번의 차이다.

```java
이진 트리 - 비교 횟수는 적지만 디스크를 많이 읽는다
B tree    - 비교는 더 하지만 디스크를 적게 읽는다
```

<br/>

## 실제로 얼마나 낮은가

앞의 실험에서 만든 `10만` 행짜리 인덱스가 좋은 예다.

```sql
member            3824 KB   (테이블)
idx_member_email  2620 KB   (인덱스)
```

<br/>

인덱스가 `2620 KB` 인데 페이지 크기가 `4KB` 라면 페이지가 `655` 개다.

이 정도면 높이가 `2~3` 이다. `10만` 행을 두세 번 읽으면 찾는다는 뜻이다.

<br/>

그래서 실무 테이블이 수백만 건이 되어도 인덱스 높이는 `3~4` 를 잘 안 넘는다.

건수가 열 배 늘어도 높이는 하나 늘까 말까다.

<br/>

## B+ tree 가 실제로 쓰이는 것이다

정확히는 `B tree` 가 아니라 `B+ tree` 다. 두 가지가 다르다.

```java
B tree  - 중간 노드에도 실제 데이터가 있다
B+ tree - 데이터는 맨 아래 잎 노드에만 있다. 중간은 길잡이 역할만 한다
```

<br/>

이렇게 하면 중간 노드에 키를 더 많이 담을 수 있다.

데이터를 안 담으니 같은 공간에 키가 더 들어가고, 그만큼 트리가 더 낮아진다.

<br/>

그리고 잎 노드끼리 옆으로 연결되어 있다.

```java
[100][200][300] -> [400][500][600] -> [700][800][900]
```

<br/>

범위 조회를 할 때 트리를 다시 안 타도 된다.

시작점을 한 번 찾고 나면 옆으로 쭉 따라가면 끝이다.

<br/>

앞에서 `email > 'user5' AND email < 'user6'` 가 인덱스를 탄 것이 이 구조 덕분이다.

`ORDER BY email` 이 정렬 없이 처리된 것도, 잎 노드가 이미 정렬 순서로 이어져 있어서다.

<br/>

## 해시 인덱스를 쓰는 곳도 있다

아예 안 쓰는 것은 아니다.

```java
MySQL MEMORY 엔진  - 해시 인덱스가 기본
InnoDB            - 자주 쓰이는 페이지에 대해 해시를 자동으로 만든다 (adaptive hash index)
Redis             - 애초에 해시 기반
```

<br/>

`등호 조회만 하고 범위도 정렬도 필요 없다` 는 것이 확실하면 해시가 더 빠르다.

다만 그런 경우가 드물어서 기본값이 못 되는 것이다.
