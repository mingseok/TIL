## 재시도와 지수 백오프

<br/>

## 실패하면 다시 하면 되지 않나

일시적인 실패는 다시 하면 된다.

```java
네트워크 순단
서버 재시작 중
DB 커넥션 잠깐 부족
```

<br/>

문제는 `어떻게 다시 하느냐` 다.

<br/><br/>

## 궁금증!

```java
클라이언트 200개가 동시에 재시도하면 서버는 어떻게 되나
```

서버가 2초 죽었다가 살아나는 상황을 만들었다. 클라이언트 200개가 실패하면 재시도한다.

서버가 살아난 직후 100ms 구간에 요청이 몇 개 몰렸는지 셌다.

<br/>

### 결과

```java
전략                          최대 동시요청    총 요청수
고정 간격 200ms                    200         2200
지수 백오프 (100,200,400..)         200         1200
지수 백오프 + 지터                   21         1394
```

<br/>

## 고정 간격 : 200 개가 한꺼번에

전부 같은 박자로 두드린다. 서버가 살아나는 순간 200개가 동시에 도착한다.

<br/>

막 살아난 서버는 캐시도 비어 있고 커넥션 풀도 안 찼는데, 그 순간 최대 부하를 받는다.

다시 죽는다. 다시 죽으면 200개가 또 같은 박자로 재시도한다.

<br/>

이걸 thundering herd라고 부른다. 소 떼가 한꺼번에 몰려오는 것이다.

<br/>

그리고 총 요청이 2200개다. 2초 동안 200개가 200ms마다 두드렸다.

죽은 서버에 헛요청을 2000개 보낸 것이다.

<br/>

## 지수 백오프 : 총량은 줄었지만

```java
1번 실패 -> 100ms 뒤
2번 실패 -> 200ms 뒤
3번 실패 -> 400ms 뒤
```

<br/>

간격이 두 배씩 늘어난다. 총 요청이 1200개로 줄었다.

<br/>

그런데 최대 동시 요청은 여전히 200이다.

200개가 같은 순간에 시작했으니 같은 순간에 1번 실패하고, 같은 100ms 뒤에 재시도하고, 같은 200ms 뒤에 재시도한다.

간격이 늘어도 박자는 같다.

<br/>

## 지터 : 박자를 흩어놓는다

```java
대기 시간 = 무작위(0 ~ 2^n × 100ms)
```

<br/>

같은 시점에 실패해도 다시 시도하는 시점이 제각각이 된다.

최대 동시 요청이 21개다. 10분의 1이다.

<br/>

`무작위` 하나가 서버 입장에서 열 배 차이를 만든 것이다.

<br/><br/>

## 세 가지 규칙

```java
1. 간격을 늘린다      - 지수 백오프. 죽은 서버에 헛요청을 줄인다
2. 무작위를 섞는다     - 지터. 몰림을 흩는다
3. 상한을 둔다        - 최대 횟수, 최대 간격. 영원히 재시도하지 않는다
```

<br/>


## 재시도하면 안 되는 것

```java
4xx 응답        - 내 요청이 잘못됐다. 다시 보내도 같다
멱등하지 않은 요청 - 결제, 주문 생성. 두 번 될 수 있다
타임아웃 뒤      - 성공했는지 모른다. 앞의 타임아웃 글에서 본 그 문제
```

<br/>

`5xx` 와 네트워크 오류만 재시도 대상이다.

<br/>

멱등하지 않은 요청은 멱등 키를 붙여서 서버가 중복을 걸러야 재시도할 수 있다.

앞의 요청 매핑 - API 예시 글에서 본 `POST 는 멱등이 아니다` 가 여기서 실제 문제가 된다.

<br/><br/>

## 재시도가 장애를 키우는 경우

```java
A 가 B 를 부르고, B 가 C 를 부른다. 각각 3번 재시도한다
C 가 죽으면
  B 는 C 에 3번 시도한다
  A 는 B 에 3번 시도하고, B 는 그때마다 C 에 3번 -> C 에 9번
  층이 하나 더 있으면 27번
```

<br/>

재시도가 층마다 곱해진다. 재시도 폭풍이라고 한다.

죽은 C에 원래 요청의 27배가 몰리고, C가 살아나려 해도 살아날 수 없다.

<br/>

그래서 재시도는 한 층에서만 한다. 보통 가장 바깥이다.

<br/><br/>

## 서킷 브레이커와 같이 쓴다

계속 실패하면 재시도 자체를 멈추는 것이다.

```java
최근 10번 중 5번 실패 -> 회로를 연다 -> 30초간 시도조차 안 하고 바로 실패 응답
30초 뒤 -> 한 번 시도해본다 -> 성공하면 회로를 닫는다
```

<br/>

죽은 서버에 헛요청을 보내지 않고, 내 스레드도 묶이지 않는다.

앞의 타임아웃 글에서 본 장애 전파를 여기서 끊는다.

<br/>

Resilience4j가 이걸 어노테이션으로 준다.

```java
@Retry(name = "api")
@CircuitBreaker(name = "api", fallbackMethod = "fallback")
```

## 정리

```java
재시도는 일시적 실패에만. 4xx 와 멱등하지 않은 요청은 제외
지수 백오프 + 지터 + 상한. 셋 다 있어야 한다
한 층에서만 재시도한다. 층마다 하면 곱해진다
계속 실패하면 서킷 브레이커로 재시도를 멈춘다
```

<br/>

앞의 생산자-소비자 문제와 배압 글에서 본 것과 같은 정신이다.

받는 쪽이 감당할 만큼만 보내야 하고, 재시도도 그 `보내는 양` 에 들어간다.
