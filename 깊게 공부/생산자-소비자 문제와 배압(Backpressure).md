## 생산자-소비자 문제와 배압(Backpressure)

<br/>

## 생산자-소비자 문제

한쪽은 데이터를 만들고 한쪽은 그것을 처리한다. 둘의 속도가 다르다.

```java
생산자 : 요청을 받아 큐에 넣는다        (빠르다)
소비자 : 큐에서 꺼내 DB 에 저장한다      (느리다)
```

<br/>

둘 사이에 큐를 둔다. 문제는 그 큐를 어떻게 다루느냐다.

<br/><br/>

## 두 가지 상황을 막아야 한다

```java
큐가 비었는데 소비자가 꺼내려 한다   -> 기다려야 한다
큐가 찼는데 생산자가 넣으려 한다     -> 기다려야 한다
```

<br/>

앞의 뮤텍스와 세마포어의 차이 글에서 본 대로, 이게 세마포어의 대표 용도다.

`빈 칸 개수` 와 `찬 칸 개수` 를 세마포어 둘로 세면 된다.

<br/>

자바에서는 그걸 만들어둔 것이 있다.

```java
BlockingQueue<T>
  put()   - 꽉 차면 자리가 날 때까지 기다린다
  take()  - 비었으면 들어올 때까지 기다린다
```

<br/><br/>

## 궁금증!

```java
큐 크기를 정하지 않으면 무슨 일이 생기나
```

생산자는 1ms에 하나 넣고, 소비자는 10ms에 하나 처리한다. 10배 차이다.

300개를 넣고 두 종류의 큐로 비교했다.

<br/>

### 결과

```java
[큐 크기 무제한]  LinkedBlockingQueue
  생산자가 300개 다 넣는 데 =  381 ms,  put() 에서 기다린 시간 합 =    1 ms
  큐에 쌓인 최대 개수 = 268 개

[큐 크기 10]  ArrayBlockingQueue(10)
  생산자가 300개 다 넣는 데 = 3515 ms,  put() 에서 기다린 시간 합 = 3107 ms
  큐에 쌓인 최대 개수 = 10 개
```

<br/>

## 무제한 큐

생산자는 0.4초에 끝났다. 신나게 다 넣었다.

그동안 소비자는 32개밖에 못 처리해서 268개가 큐에 쌓였다.

<br/>

300개라 별일 없어 보이지만, 이게 초당 1만 건 들어오는 서비스면 얘기가 다르다.

```java
1초에 1만 건 들어오고 1천 건 처리한다
-> 1초마다 9천 건이 쌓인다
-> 1분이면 54만 건
-> 메모리가 차오르고 OutOfMemoryError
```

<br/>

앞의 스레드 풀 글에서 본 `Executors.newFixedThreadPool 의 큐가 무제한이라 위험하다` 가 정확히 이것이다.

<br/>

문제는 터질 때까지 아무 경고가 없다는 점이다.

응답은 빠르고 에러도 없는데 메모리만 조용히 차오른다.

<br/>

## 크기 10 큐

생산자가 3.5초 걸렸다. 그중 3.1초를 `put()` 에서 기다렸다.

<br/>

큐가 10개로 차면 생산자가 멈춘다. 소비자가 하나 꺼내야 하나 넣을 수 있다.

생산자 속도가 소비자 속도에 강제로 맞춰진 것이다.

<br/>

이게 배압이다.

뒤에서 밀려오는 압력이 앞으로 전달되어, 받는 쪽이 감당할 만큼만 들어오게 되는 것이다.

<br/><br/>

## 배압이 전달되는 방식

`put()` 이 막히면 생산자 스레드가 멈춘다.

생산자가 웹 요청 처리 스레드였다면 그 요청이 느려진다.

요청이 느려지면 클라이언트가 다음 요청을 늦게 보낸다.

<br/>

```java
소비자 느림 -> 큐 꽉 참 -> 생산자 멈춤 -> 요청 응답 느림 -> 클라이언트가 덜 보냄
```

<br/>

느려지는 것이 나쁜 게 아니다. 터지는 것보다 훨씬 낫다.

느려지면 모니터링에 잡히고, 터지면 서비스가 없어진다.

<br/>

앞의 스레드 풀 글에서 본 `CallerRunsPolicy` 가 이 배압을 만드는 방법이었다.

큐가 차면 넘기려던 스레드가 직접 일하게 되니 넘기는 속도가 저절로 준다.

<br/><br/>

## 큐 크기를 얼마로 잡나

```java
너무 작다 -> 생산자가 자주 멈춘다. 소비자가 잠깐 느려질 때도 바로 막힌다
너무 크다 -> 배압이 늦게 온다. 그동안 메모리를 먹는다
```

<br/>

기준은 `소비자가 잠깐 느려지는 것을 얼마나 흡수할 것인가` 다.

```java
소비자가 최대 5초 느려질 수 있고, 초당 1000건 들어온다 -> 5000 정도
```

<br/>

그 이상 쌓이면 잠깐 느려진 게 아니라 뭔가 잘못된 것이니, 그때는 막히는 게 맞다.

<br/><br/>

## 자바 큐 종류

```java
ArrayBlockingQueue      - 크기 고정. 배열. 이 실험에 쓴 것
LinkedBlockingQueue     - 크기 지정 가능. 안 하면 무제한
SynchronousQueue        - 크기 0. 넣는 쪽과 빼는 쪽이 만나야 넘어간다
PriorityBlockingQueue   - 우선순위 순. 무제한
DelayQueue              - 시간이 되어야 꺼낼 수 있다
```

<br/>

`SynchronousQueue` 가 앞의 context switch vs Context 글에서 공 넘기기에 쓴 것이다.

큐가 아니라 손에서 손으로 직접 건네는 것이라, 스위치 비용을 재는 데 딱 맞았다.

<br/>

`Executors.newCachedThreadPool` 이 이걸 쓴다. 넣을 때 받을 스레드가 없으면 새로 만드니 스레드가 무한히 는다.

<br/><br/>

## 실무에서 배압이 있는 곳과 없는 곳

```java
Kafka 컨슈머   - 컨슈머가 poll 하는 만큼만 가져간다. 배압이 자연히 있다
RabbitMQ      - prefetch 로 한 번에 받을 개수를 제한한다
Reactor/RxJava - request(n) 으로 구독자가 개수를 요청한다. 배압이 규약에 들어 있다
HTTP 요청      - 없다. 클라이언트가 보내는 만큼 온다. 그래서 톰캣 스레드 풀과 큐가 그 역할을 한다
```

<br/>

마지막이 중요하다.

앞의 멀티 쓰레드 글에서 본 톰캣의 `acceptCount` 가 대기 큐 크기다. 기본 100이다.

스레드 200개가 다 바쁘고 큐 100개도 차면 그 뒤 접속은 거절된다.

<br/>

`거절` 이 배압의 마지막 형태다.

받아서 터지는 것보다 안 받는 게 낫다는 판단이다.

<br/>

앞의 옵저버 패턴 글에서 본 `@Async` 이벤트 리스너를 쓸 때 이 생각을 안 하면, 이벤트가 큐에 무한히 쌓이는 첫 번째 상황이 된다.

`@Async` 의 기본 실행기가 무제한 큐이기 때문이다.
