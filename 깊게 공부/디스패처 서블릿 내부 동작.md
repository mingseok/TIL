## 디스패처 서블릿 내부 동작

## Dispatcher-Servlet 의 동작 과정

디스패처 서블릿은 적합한 컨트롤러와 메소드를 찾아 요청을 위임해야 합니다. 

Dispatcher Servlet의 처리 과정을 살펴보면 다음과 같습니다.

![이미지](/programming/img/입문536.PNG)


<br/><br/>

### 1번) 클라이언트의 요청을 디스패처 서블릿이 받는다.

서블릿 컨텍스트(웹 컨텍스트)에서 필터들을 지나 스프링 컨텍스트에서 디스패처 서블릿이 가장 먼저 요청을 받게됩니다.

![이미지](/programming/img/입문537.PNG)

<br/><br/>

### 2번) 요청 정보를 통해 요청을 위임할 컨트롤러를 찾는다.

디스패처 서블릿은 요청을 처리할 핸들러(컨트롤러)를 찾고 해당 객체의 메소드를 호출합니다. 



따라서 가장 먼저 어느 컨트롤러가 요청을 처리할 수 있는지를 식별해야 하는데, 해당 역할을 하는 것이 바로 HandlerMapping입니다


<br/>


흔한 @Controller 방식은 RequestMappingHandlerMapping가 처리합니다. 

이는 @Controller로 작성된 모든 컨트롤러를 찾고 파싱하여 HashMap으로 <요청 정보, 처리할 대상> 관리합니다. 

<br/>

여기서 처리할 대상은 HandlerMethod 객체로 컨트롤러, 메소드 등을 갖고 있는데, 

이는 스프링이 리플렉션을 이용해 요청을 위임하기 때문입니다.

<br/>

그래서 요청이 오면 (Http Method, URI) 등을 사용해 요청 정보를 만들고, 

HashMap에서 요청을 처리할 대상(HandlerMethod)를 찾은 후에 HandlerExecutionChain으로 감싸서 반환합니다. 

<br/>

HandlerExecutionChain으로 감싸는 이유는 컨트롤러로 요청을 

넘겨주기 전에 처리해야 하는 인터셉터 등을 포함하기 위해서입니다.

<br/><br/>

### 3번) 요청을 컨트롤러로 위임할 핸들러 어댑터를 찾아서 전달한다.

이후에 컨트롤러로 요청을 위임해야 하는데, 디스패처 서블릿은 

컨트롤러로 요청을 직접 위임하는 것이 아니라 HandlerAdapter를 통해  위임합니다. 

<br/>

스프링은 HandlerAdapter라는 어댑터 인터페이스를 통해 어댑터 패턴을 

적용함으로써 컨트롤러의 구현 방식에 상관없이 요청을 위임할 수 있도록 하였습니다.

<br/><br/>

### 4번) 핸들러 어댑터가 컨트롤러로 요청을 위임한다.

핸들러 어댑터가 컨트롤러로 요청을 위임한 전/후에 공통적인 전/후처리 과정이 필요합니다. 

<br/>

대표적으로 인터셉터들을 포함해 요청 시에 @RequestParam, @RequestBody 등을 처리하기 위한 

ArgumentResolver들과 응답 시에 ResponseEntity의 Body를 Json으로 직렬화하는 등의 

처리를 하는 ReturnValueHandler 등이 핸들러 어댑터에서 처리됩니다. 


<br/>

ArgumentResolver 등을 통해 파라미터가 준비 되면 리플렉션을 이용해 컨트롤러로 요청을 위임합니다.

<br/><br/>

### 5번) 비지니스 로직을 처리한다.

이후에 컨트롤러는 서비스를 호출하고 우리가 작성한 비지니스 로직들이 진행됩니다.

<br/><br/>

### 6번) 컨트롤러가 반환값을 반환한다.

비지니스 로직이 처리된 후에는 컨트롤러가 반환값을 반환합니다. 

<br/>

응답 데이터를 사용하는 경우에는 주로 ResponseEntity를 반환하게 되고, 

응답 페이지를 보여주는 경우라면 String으로 View의 이름을 반환할 수도 있습니다. 

<br/>

요즘 프론트엔드와 백엔드를 분리하고, MSA로 가고 있는 시대에서는 주로 ResponseEntity를 반환합니다.

<br/><br/>

### 7번) 핸들러 어댑터가 반환값을 처리한다.

HandlerAdapter는 컨트롤러로부터 받은 응답을 응답 처리기인 

ReturnValueHandler가 후 처리한 후에 디스패처 서블릿으로 돌려줍니다. 

<br/>

만약 컨트롤러가 ResponseEntity를 반환하면 HttpEntityMethodProcessor가 

MessageConverter를 사용해 응답 객체를 직렬화하고 응답 상태(HttpStatus)를 설정합니다. 

<br/>

만약 컨트롤러가 View 이름을 반환하면 ViewResolver를 통해 View를 반환합니다.

<br/><br/>

### 8번) 서버의 응답을 클라이언트로 반환한다.

디스패처 서블릿을 통해 반환되는 응답은 다시 필터들을 거쳐 클라이언트에게 반환됩니다. 

이때 응답이 데이터라면 그대로 반환되지만, 응답이 화면이라면 

View의 이름에 맞는 View를 찾아서 반환해주는 ViewResolver가 적절한 화면을 내려줍니다.
<br/>

## 궁금증!

```java
"1번에서 필터들을 지나 디스패처 서블릿이 받는다" 는데, 필터와 인터셉터는 뭐가 다를까?
```

경계가 다르다. 필터는 서블릿 컨테이너 소속이고, 인터셉터는 스프링 소속이다.

```java
클라이언트
  -> 서블릿 컨테이너(톰캣)
       -> 필터 1 -> 필터 2                    <- 여기까지는 스프링을 모른다
            -> DispatcherServlet
                 -> 인터셉터 preHandle        <- 여기부터 스프링
                      -> 컨트롤러
                 -> 인터셉터 postHandle
            -> 뷰 렌더링
                 -> 인터셉터 afterCompletion
       -> 필터 2 -> 필터 1
  -> 클라이언트
```

<br/>

필터는 `DispatcherServlet` 보다 바깥에 있다.

그래서 필터에서는 어느 컨트롤러가 처리할지 아직 모른다. `HttpServletRequest` 만 있다.

<br/>

인터셉터는 `getHandler()` 가 끝난 뒤에 실행되기 때문에, 어느 핸들러인지 알고 있다.

```java
boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler)
```

세 번째 파라미터로 핸들러가 넘어오는 것이 그 증거다.

<br/>

```java
필터    - 스프링 밖. 인코딩, CORS, 로깅처럼 요청 자체를 다루는 일
인터셉터 - 스프링 안. 로그인 확인처럼 "어느 컨트롤러인지" 를 알아야 하는 일
```

<br/>

시큐리티가 필터로 구현된 이유도 여기 있다.

인증이 실패하면 컨트롤러를 찾기도 전에 막아야 하기 때문이다.

<br/>

## HashMap 으로 관리한다는 부분

원문의 `HashMap 으로 <요청 정보, 처리할 대상> 관리한다` 가 실제로 그렇다.

<br/>

`RequestMappingHandlerMapping` 은 애플리케이션이 뜰 때 한 번만 일한다.

```java
1. 모든 빈을 훑는다
2. @Controller 나 @RequestMapping 이 붙은 클래스를 고른다
3. 그 안의 메서드에서 @GetMapping, @PostMapping 을 찾는다
4. Map<RequestMappingInfo, HandlerMethod> 에 넣어둔다
```

<br/>

`RequestMappingInfo` 는 `URL 패턴 + HTTP 메서드 + 헤더 조건` 같은 것을 다 담은 키다.

요청이 올 때마다 컨트롤러를 새로 찾는 것이 아니라, 만들어둔 표에서 꺼내는 것이다.

<br/>

그래서 컨트롤러가 아무리 많아도 매핑 자체는 빠르다.

시작할 때 한 번 비용을 치르고, 그 뒤로는 조회만 한다.

<br/>

앞의 스프링 컨테이너 글에서 본 `미리 다 만들어둔다` 는 방침이 여기에도 적용되어 있다.

<br/>

## 예외가 나면 어디로 가는가

원문 흐름에서 안 나온 갈래가 하나 있다. 컨트롤러에서 예외가 터졌을 때다.

```java
doDispatch()
  try {
      핸들러 실행
  } catch (Exception e) {
      dispatchException = e;        // 잡아둔다
  }
  processDispatchResult(..., dispatchException)
      -> HandlerExceptionResolver 목록에게 물어본다
```

<br/>

예외가 나도 그 자리에서 위로 던지지 않고 일단 잡아둔다.

그리고 `HandlerExceptionResolver` 들에게 처리할 수 있는지 물어본다.

```java
ExceptionHandlerExceptionResolver   -> @ExceptionHandler 를 찾아서 실행
ResponseStatusExceptionResolver     -> @ResponseStatus 를 보고 상태 코드를 정함
DefaultHandlerExceptionResolver     -> 스프링 내부 예외를 상태 코드로 변환
```

<br/>

아무도 처리하지 못하면 그제서야 예외가 서블릿 컨테이너까지 올라가고,

톰캣의 기본 오류 페이지가 나온다.

<br/>

`@ExceptionHandler` 가 동작하는 것도 결국 `DispatcherServlet` 의 이 갈래 덕분이다.

앞의 프론트 컨트롤러 글에서 본 `갈아끼울 수 있는 자리` 중 하나가 이것이다.

<br/>

## 요청 하나에 스레드 하나

`8번` 이 끝나면 그 요청을 처리하던 스레드는 풀로 돌아간다.

<br/>

`DispatcherServlet` 도 앞의 서블릿 글에서 본 대로 하나뿐이다.

수백 개의 스레드가 같은 `DispatcherServlet` 객체의 `doDispatch()` 를 동시에 실행한다.

<br/>

그래서 `DispatcherServlet` 은 요청별 상태를 필드에 두지 않는다.

전부 메서드의 지역 변수로 다룬다.

```java
protected void doDispatch(HttpServletRequest request, HttpServletResponse response) {
    HandlerExecutionChain mappedHandler = null;    // 지역 변수
    ModelAndView mv = null;                        // 지역 변수
    ...
}
```

<br/>

컨트롤러와 서비스도 마찬가지다. 싱글톤이라 필드에 요청 데이터를 담으면 안 된다.

프레임워크 자신이 그 규칙을 지키고 있는 셈이다.
