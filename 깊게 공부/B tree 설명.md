### 특징

- 자녀 노드의 최대 개수를 늘리기 위해서 부모 노드에 key를 하나 이상 저장한다.

- 부모 노드의 key들을 오름차순으로 정렬한다.

- 정렬된 순서에 따라 자녀 노드들의 key 값의 범위가 결정된다.

- internal 노드의 key 수가 x개라면 자녀 노드의 수는 언제나 x + 1개이다.

```sql
"B tree는 BST를 일반화한 tree 라고도 말을 한다."
```

<br/><br/>

## B tree 용어 정리

최대 몇개의 자녀 노드를 가질 것인지가? B tree를 사용할 때 중요한 파라미터이다.

- `M : 각 노드의 최대 자녀 노드 수`

    - 최대 m개의 자녀를 가질 수 있는 B tree를 M차 B tree라 부른다.

        - 위 그림을 기준으로 말한다면 → 3차 B tree 라고 부르는 것이다.

- `M - 1 : 각 노드의 최대 key 수`

    - 간단하다. 3차 B tree라고 한다면 당연히 k는 두개가 될 것이기에 m-1인 것이다.

- `[M / 2] : 각 노드의 최소 자녀 노드 수`

    - [ ] → 무엇인가? 반올림을 해줘야 한다는 것이다.

- `[M/2]-1 : 각 노드의 최소 KEY 수`

    - root node는 제외한다.

```sql
"전체적으로 정리하면"
 M 파라미터만 우리가 정해주면 나머지 파라미터들은 자연스럽게 알아서 결정 되는 것이다.
```

## 궁금증!

```java
"균형을 유지한다" 는 게 왜 그렇게 중요할까?
```

균형이 깨지면 트리가 사실상 연결 리스트가 되기 때문이다.

<br/>

정렬된 값을 그냥 이진 탐색 트리에 넣으면 이렇게 된다.

```java
1 을 넣는다
  2 를 넣는다 -> 1 보다 크니 오른쪽
    3 을 넣는다 -> 오른쪽
      4 를 넣는다 -> 오른쪽

1 -> 2 -> 3 -> 4 -> ...
```

<br/>

한쪽으로만 길게 늘어진다. 높이가 곧 데이터 개수가 된다.

`10만` 개를 넣으면 높이가 `10만` 이라, 찾는 데 `10만` 번 비교해야 한다.

<br/>

DB 인덱스에서는 이런 일이 자주 일어난다.

`id` 처럼 자동 증가하는 값이 정확히 `이미 정렬된 순서로 들어오는` 경우이기 때문이다.

<br/>

## B tree 는 위로 자란다

일반 트리는 아래로 자란다. 새 값을 잎에 붙인다.

`B tree` 는 노드가 꽉 차면 가운데 값을 부모로 올려보내면서 위로 자란다.

```java
[10, 20, 30] 에 40 을 넣으려는데 자리가 없다
  -> 가운데 20 을 부모로 올린다
  -> [10] 과 [30, 40] 으로 쪼갠다

        [20]
       /    \
   [10]    [30, 40]
```

<br/>

부모가 꽉 차면 부모도 같은 방식으로 쪼개서 그 위로 올린다.

계속 올라가다가 뿌리까지 차면, 그때 뿌리가 쪼개지면서 높이가 하나 늘어난다.

<br/>

높이가 늘어나는 유일한 순간이 `뿌리가 쪼개질 때` 다.

그리고 그때는 모든 잎이 동시에 한 칸씩 내려가니, 균형이 저절로 유지된다.

```java
아래로 자라면 - 한쪽만 길어질 수 있다
위로 자라면   - 모든 잎이 항상 같은 높이다
```

<br/>

## 그래서 최악의 경우가 없다

어떤 순서로 넣든 높이가 같다.

앞의 B tree 인덱스 글에서 본 계산이 항상 성립하는 이유가 이것이다.

```java
노드 하나에 키 200 개면
  높이 3 -> 800 만 개
  높이 4 -> 16 억 개
```

<br/>

`1` 번부터 순서대로 넣어도, 무작위로 넣어도 높이는 같다.

정렬된 순서로 들어오는 `id` 인덱스가 문제없이 동작하는 근거다.

<br/>

## 노드가 반은 차 있어야 한다는 규칙

`B tree` 에는 `모든 노드는 최소 절반은 차 있어야 한다` 는 규칙이 있다.

<br/>

이게 없으면 노드마다 키가 하나씩만 들어 있는 상태가 될 수 있다.

그러면 노드 수가 늘어나서 트리가 높아지고, 디스크 읽기 횟수가 늘어난다.

```java
노드가 꽉 차 있으면 - 한 번 읽어서 많은 키를 본다
노드가 비어 있으면  - 여러 번 읽어야 같은 수의 키를 본다
```

<br/>

그래서 삭제할 때 노드가 절반 아래로 내려가면 옆 노드와 합치거나 빌려온다.

다음 글의 `데이터 삭제 방식` 이 그 이야기다.

<br/>

## 실무에서 이 규칙이 문제가 되기도 한다

`UUID` 를 기본 키로 쓰면 성능이 나빠진다는 얘기가 여기서 나온다.

```java
자동 증가 id  - 항상 마지막 노드에 추가된다. 그 노드만 건드리면 된다
UUID (랜덤)  - 어디에 들어갈지 모른다. 중간 노드를 쪼개는 일이 자주 생긴다
```

<br/>

중간을 쪼개면 그 페이지를 읽고 쓰고, 부모도 갱신해야 한다.

그리고 쪼개진 페이지들이 반만 찬 상태로 남아서 인덱스가 커진다.

<br/>

그래서 `UUID v7` 처럼 시간 순서가 들어간 형식을 쓰거나,

`id` 는 자동 증가로 두고 외부 노출용 UUID를 따로 두는 방식을 쓴다.

```java
id BIGINT AUTO_INCREMENT   -- 내부용. 인덱스 친화적
uuid CHAR(36) UNIQUE       -- 외부 노출용
```
