## 스핀락 vs 블로킹 락

<br/>

## 락을 못 잡았을 때 두 가지 선택

```java
스핀락   - 잡힐 때까지 그 자리에서 계속 시도한다. CPU 를 쓴다
블로킹 락 - 잠들고, 락이 풀리면 깨워달라고 한다. CPU 를 놓는다
```

<br/>

앞의 CAS 알고리즘 설명 글에서 본 `while (!compareAndSet(...))` 이 스핀이다.

앞의 Reentrant Lock과 synchronized의 차이 글에서 본 `BLOCKED` 상태로 들어가는 것이 블로킹이다.

<br/>

교과서의 기준은 이렇다.

```java
임계 영역이 짧다 -> 스핀. 금방 풀릴 텐데 잠들고 깨는 비용(2µs)이 더 크다
임계 영역이 길다 -> 블로킹. 오래 기다릴 텐데 CPU 를 태우면 낭비
```

<br/><br/>

## 궁금증!

```java
교과서대로 나오나
```

`AtomicBoolean` 으로 스핀락을 직접 만들어 `ReentrantLock` 과 비교했다. 스레드 4개, 코어 10개.

임계 영역 길이를 덧셈 횟수로 바꿔가며 재봤다.

<br/>

### 결과

```java
임계영역          스핀락      ReentrantLock
덧셈 0번          85 ms        19 ms    <- 블로킹 승
덧셈 10번         66 ms        16 ms    <- 블로킹 승
덧셈 100번        77 ms        49 ms    <- 블로킹 승
덧셈 1000번      352 ms       442 ms    <- 스핀 승
덧셈 10000번    3283 ms      3494 ms    <- 스핀 승
```

<br/>

교과서와 반대다. 짧을 때 블로킹이 이기고, 길 때 스핀이 이겼다.

<br/><br/>

## 왜 반대로 나왔나

두 가지가 겹쳤다.

<br/>

### 1. ReentrantLock 은 이미 스핀을 한다

`ReentrantLock` 은 못 잡았을 때 바로 잠들지 않는다.

```java
1. CAS 로 한 번 시도
2. 실패하면 잠깐 스핀
3. 그래도 안 되면 잠든다 (park)
```

<br/>

앞의 동시성 문제 해결 방법 글에서 본 `synchronized 의 경량 락 -> 중량 락` 단계와 같은 구조다.

`적응형 스핀` 이라고 부른다. 짧은 경합은 스핀으로 넘기고, 긴 경합만 잠든다.

<br/>

그래서 `블로킹 락` 이라고 부르는 것이 사실은 `스핀 조금 하다가 블로킹` 이다.

내가 만든 순수 스핀락이 이길 자리가 애초에 없었던 것이다.

<br/>

### 2. 순수 스핀은 캐시 라인을 두들긴다

```java
while (!spin.compareAndSet(false, true)) { }
```

<br/>

스레드 4개가 같은 `AtomicBoolean` 을 쉴 새 없이 CAS 한다.

앞의 거짓 공유(False Sharing) 글에서 본 그 캐시 라인 핑퐁이 여기서 최대치로 일어난다.

<br/>

락을 쥔 스레드가 임계 영역을 도는 동안, 나머지 셋이 그 캐시 라인을 계속 무효화시킨다.

락을 쥔 스레드도 느려지는 것이다.

<br/>

긴 임계 영역에서 스핀이 이긴 것은, 그 길이면 잠들고 깨는 비용이 상대적으로 작아지는데도 `ReentrantLock` 의 park/unpark 오버헤드가 조금 남기 때문이다. 차이는 5% 남짓이라 거의 같다고 봐도 된다.

<br/><br/>

## 코어보다 스레드가 많으면

```java
스레드 40개 (코어 10), 임계 영역 덧셈 100번
스핀락 = 408 ms, ReentrantLock = 48 ms    <- 8.5 배
```

<br/>

스핀이 재앙이 된다.

<br/>

락을 쥔 스레드가 코어를 뺏겨서 잠든 상태인데, 나머지 39개가 그 락이 풀리길 스핀하며 코어를 전부 쓰고 있다.

락을 쥔 스레드가 코어를 다시 받아야 풀리는데, 스핀하는 것들이 코어를 안 놓는다.

<br/>

앞의 CPU 스케줄링과 스레드 우선순위 글에서 본 스케줄러가 시간 조각이 끝나야 겨우 바꿔준다.

`락을 기다리는 것들이 락을 쥔 것을 굶긴다` 는 역설이다.

<br/><br/>

## 그래서 순수 스핀락은 어디에 쓰나

운영체제 커널 안이다.

```java
인터럽트 핸들러처럼 잠들 수 없는 곳
임계 영역이 명령어 몇 개 수준으로 보장되는 곳
코어 수만큼만 스레드가 있어서 위 역설이 안 생기는 곳
```

<br/>

애플리케이션 코드에서는 직접 만들 이유가 거의 없다.

`ReentrantLock` 과 `synchronized` 가 이미 `스핀 조금 -> 블로킹` 을 알아서 하고 있기 때문이다.

<br/>

앞의 CAS 알고리즘 설명 글에서 본 `AtomicInteger.incrementAndGet()` 은 스핀이 맞다.

그런데 그건 임계 영역이 `읽고 -> 더하고 -> CAS` 세 단계로 고정이라 조건이 맞는 것이다.

<br/><br/>

## 정리

```java
교과서    - 짧으면 스핀, 길면 블로킹
실측     - 짧아도 ReentrantLock 이 이긴다. 안에 이미 적응형 스핀이 있다
         - 코어보다 스레드가 많으면 순수 스핀은 8배 느리다
결론     - 직접 스핀락을 만들지 말고 JDK 락을 쓴다. 스핀은 JDK 가 필요한 만큼만 해준다
```

<br/>

앞의 ReadWriteLock과 StampedLock 글에서 본 것과 같은 교훈이다.

`이론상 유리한 락` 으로 바꾸기 전에 재봐야 한다.
