## 생성자를 왜 만들어야 하나요?

생성자는 클래스와 같은 이름의 메소드로, 인스턴스가 생성될 때 호출되는 메소드입니다.

명시적으로 생성자를 만들지 않아도 default로 만들어지며, 생성자는 파라미터를 다르게하여 오버로딩할 수 있습니다.

<br/>

## 생성자

생성자를 정의하지 않고도 인스턴스를 생성할 수 있는데, 이는 컴파일러가 `'기본 생성자'`를 제공하기 때문입니다.

컴파일러가 자바 소스파일을 컴파일 시에, 클래스에 생성자가 없다면 자동적으로 기본 생성자를 추가하여 컴파일한다.

<br/>

## 생성자의 특징

1. 생성자는 반환값이 없지만, 반환 타입을 `void`형으로 선언하지 않습니다.

2. 생성자는 초기화를 위한 데이터를 인수로 전달받을 수 있습니다.
3. 하나의 클래스가 여러 개의 생성자를 가질 수 있습니다.
    
    즉, 생성자도 하나의 메소드이므로, 메소드 `오버로딩`이 가능합니다

<br/>

## 생성자는 왜 필요한가요?

생성자는 자바 클래스의 객체를 생성하기 위해서 존재한다.

- `객체 초기화`
    - 생성자는 클래스의 객체를 초기화하는 역할을 합니다.
    - 객체가 생성될 때 필요한 초기화 작업을 수행할 수 있으며,
        
        필드를 초기화하고 객체의 상태를 설정하는 데 사용됩니다.
        
- `매개변수 전달`
    - 생성자를 통해 객체에 필요한 데이터나 매개변수를 전달할 수 있습니다.
        
        이를 통해 다양한 객체를 생성하고 다양한 초기화 옵션을 제공할 수 있습니다.
        
- `객체 유효성 검사`
    - 생성자 내에서 입력된 값들을 유효성 검사하고, 잘못된 값이 들어오는 것을 방지할 수 있습니다.
        
- `클래스의 불변성 유지`
    - 불변 클래스의 경우, 생성자를 통해 객체를 한 번 초기화하면 그 상태를 변경할 수 없도록 만들 수 있습니다.


<br/>

## 궁금증!

```java
"명시적으로 만들지 않아도 default로 만들어진다"고 했는데, 항상 그럴까?
```

항상은 아니다. 생성자를 하나라도 직접 만들면 기본 생성자는 사라진다.

```java
class Member {
    private final String name;

    Member(String name) {
        this.name = name;
    }
}

Member member = new Member();     // 될까?
```

<br/>

### 결과

```java
error: constructor Member in class Member cannot be applied to given types;
        Member member = new Member();
                        ^
  required: String
  found:    no arguments
```

컴파일이 안 된다.

컴파일러는 `생성자가 하나도 없을 때만` 기본 생성자를 넣어준다.

하나라도 직접 만들었다면 "필요한 생성자는 개발자가 다 적었겠지" 하고 손을 떼는 것이다.

```java
생성자를 하나라도 만들면 -> 기본 생성자는 안 만들어진다
기본 생성자도 필요하면  -> 직접 적어야 한다
```

<br/>

## 이걸 모르면 엉뚱한 데서 막힌다

JPA 엔티티에 생성자를 하나 만들었더니 갑자기 조회가 안 되는 경우가 있다.

JPA가 DB에서 읽어온 값으로 객체를 만들 때, 리플렉션으로 기본 생성자를 먼저 부르기 때문이다.

<br/>

`Jackson` 으로 JSON을 객체로 바꿀 때도 마찬가지다.

기본 생성자로 빈 객체를 만들어놓고 값을 하나씩 채워 넣는 방식이라, 기본 생성자가 없으면 실패한다.

```java
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Entity
class Member { ... }
```

엔티티에 이 어노테이션이 붙어 있는 이유가 이것이다.

`protected` 로 막아둔 것은, 프레임워크는 쓸 수 있게 열어두되 개발자가 실수로 빈 객체를 만들지는 못하게 하려는 것이다.

<br/>

## 생성자가 있으면 잘못된 객체를 아예 못 만든다

원문의 `객체 유효성 검사` 가 실제로 왜 중요한지는 `setter` 와 비교하면 확실하다.

```java
class Order {
    private int quantity;

    void setQuantity(int quantity) {
        this.quantity = quantity;
    }
}

Order order = new Order();      // 이 순간 수량이 0인 이상한 주문이 존재한다
order.setQuantity(3);           // 여기까지 와야 정상이 된다
```

<br/>

`new` 와 `setQuantity` 사이에는 아직 완성되지 않은 객체가 돌아다닌다.

그 사이에 누가 이 객체를 쓰면 수량 `0` 짜리 주문을 보게 된다.

<br/>

생성자로 받으면 그 틈이 아예 없어진다.

```java
class Order {
    private final int quantity;

    Order(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("수량은 1개 이상이어야 합니다");
        }
        this.quantity = quantity;
    }
}
```

<br/>

이제 `Order` 가 만들어졌다는 것은 곧 `수량이 1개 이상이다` 라는 뜻이 된다.

객체가 존재하는 모든 순간에 이 조건이 지켜지는 것이다.

```java
setter로 채우면 -> 완성되기 전의 객체가 존재한다
생성자로 채우면 -> 완성된 객체만 존재한다
```

<br/>

## 그런데 생성자가 여러 개면 헷갈린다

```java
new Member("민석", "서울", "010-1234-5678");
```

세 번째가 전화번호인지 주민번호인지 읽어서는 알 수 없다.

타입이 전부 `String` 이라 순서를 바꿔 넣어도 컴파일이 된다.

<br/>

이럴 때는 정적 팩토리 메서드로 이름을 붙여주거나,

```java
Member.of("민석", "서울", "010-1234-5678");
Member.withoutPhone("민석", "서울");
```

<br/>

빌더로 이름을 달아서 넘기면 읽기가 훨씬 낫다.

```java
Member.builder()
        .name("민석")
        .address("서울")
        .phone("010-1234-5678")
        .build();
```

생성자를 안 쓰는 것이 아니라, 생성자를 감싸서 이름을 붙여주는 것이다.

유효성 검사는 여전히 생성자 안에 있어야 한다.
