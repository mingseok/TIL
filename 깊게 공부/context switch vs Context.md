## context switch vs Context

<br/>

## context가 무엇인지 설명하시오

context란 process가 현재 어떤 상태로 수행되고 있는지에 대한 정보입니다.

해당 정보는 pcb에 저장합니다.

<br/><br/>

## Context

시분할 시스템에서는 한 프로세스가 매우 짧은 시간 동안 cpu를 점유하여 

일정부분의 명령을 수행하고, 다른 프로세스에게 넘긴다. 

<br/>

그 후 차례가 되면 다시 cpu를 점유하여 명령을 수행한다. 

따라서 이전에 어디까지 명령을 수행했고, register에는 어떤 값이 

저정되어 있었는지에 대한 정보가 필요하게 된다. 

<br/>

프로세스가 현재 어떤 상태로 수행되고 있는지에 대한 

총체적인 정보가 바로 context이다. → 
그럼 context 정보들은 어디에 저장되는거야? → pcb에 저장된다.

<br/><br/>

## context switch에 대해서 설명하시오

context switch란 한 프로세스에서 다른 프로세스로 cpu 제어권을 넘겨주는 것을 말한다.

이때 이전의 프로세스의 상태를 pcb에 저장하여 보관하고 

새로운 프로세스의 pcb를 읽어서 보관된 상태를 복구하는 작업이 이루어진다.
<br/><br/>

## 궁금증!

```java
컨텍스트 스위칭이 비싸다는데 얼마나 비싼가
```

두 스레드가 공을 주고받게 해서 재봤다.

한 번 왕복하면 스위치가 두 번 일어난다.

```java
SynchronousQueue<Integer> ping, pong;

// 스레드 A
ping.put(1); pong.take();      // 넘기고 -> 잠들고 -> 깨어난다

// 스레드 B
ping.take(); pong.put(1);      // 받고 -> 넘기고 -> 잠든다
```

<br/>

### 결과

```java
100,000 번 왕복 = 407 ms  ->  스위치 1번당 약 2.0 µs
```

<br/>

2마이크로초다.

덧셈 하나가 대략 1나노초니, 스위치 한 번에 덧셈 2000번 할 시간이 든다.

<br/>

한 번은 별거 아닌데 문제는 횟수다.

초당 수만 번 스위치가 일어나면 CPU 시간의 몇 퍼센트가 일이 아니라 `갈아타는 데` 쓰이는 것이다.

<br/><br/>

## 무엇을 저장하기에 2µs 나 드나

원문에 `이전 프로세스의 상태를 PCB에 저장한다` 고 적혀 있다.

그 `상태` 가 정확히 무엇인지가 궁금했다.

```java
1. 레지스터 값들       - PC, 스택 포인터, 범용 레지스터 십수 개
2. 메모리 매핑 정보     - 어느 가상 주소가 어느 물리 주소인지
3. 커널 자료구조 갱신   - 실행 큐에서 빼고 넣기
```

<br/>

`1번` 은 얼마 안 된다. 수십 개 값을 복사하는 것이다.

<br/>

비용은 눈에 안 보이는 곳에서 더 든다.

```java
캐시가 식는다      - 앞 프로세스가 채워둔 캐시가 새 프로세스에게는 쓸모없다
TLB 가 비워진다    - 주소 변환 테이블도 마찬가지
분기 예측이 어긋난다
```

<br/>

앞의 ‘메모리에 적재’ CPU의 연산 글에서 본 `순서대로 49ms, 무작위 324ms` 가 이 얘기다.

스위치 직후는 캐시가 비어 있으니 한동안 `무작위로 읽기` 상태로 도는 것이다.

<br/>

그래서 스위치 비용은 `저장하고 복원하는 시간` 이 아니라 `그 뒤로 한동안 느려지는 시간` 이 더 크다.

<br/><br/>

## 스택도 컨텍스트의 일부다

```java
Thread.currentThread().getStackTrace().length

main 만 있을 때   = 2 프레임
5단계 들어가면    = 8 프레임
```

<br/>

이 프레임들이 `어디까지 실행했고 어디로 돌아가야 하는지` 다.

<br/>

다만 스택은 복사하지 않는다. 스레드마다 자기 스택이 이미 따로 있어서, 스택 포인터 값 하나만 바꾸면 된다.

앞의 process를 설명해 주세요 글에서 본 `Stack 21개` 가 그것이다.

<br/>

레지스터는 CPU에 하나뿐이라 복사해야 하고, 스택은 메모리에 각자 있어서 가리키는 곳만 바꾸는 것이다.

<br/><br/>

## 스레드를 늘리면 느려지나 실험

CPU만 쓰는 일을 총량은 같게 두고 스레드 수만 바꿔봤다.

```java
스레드    10 개 (코어 10) = 191 ms
스레드   100 개 (코어 10) = 175 ms
스레드  1000 개 (코어 10) = 179 ms
```

<br/>

거의 안 느려졌다. 예상과 달랐다.

<br/>

이유가 있다.

스레드가 1000개여도 각자 200만 번씩 덧셈을 하니, 한 번 CPU를 잡으면 시간을 다 쓸 때까지 안 놓는다.

스위치가 일어나는 횟수 자체가 적은 것이다.

<br/>

`스레드가 많으면 느리다` 가 아니라 `스위치가 잦으면 느리다` 가 정확한 말이다.

<br/>

스위치가 잦아지는 조건은 이렇다.

```java
스레드들이 자꾸 잠들고 깨어난다 (락 경합, 짧은 I/O)
시간 할당량이 짧다
스레드 수가 코어 수보다 훨씬 많은데 전부 깨어 있다
```

<br/>

앞의 Sync 실험에서 `synchronized 186ms vs AtomicInteger 67ms` 였던 것이 이 차이다.

`synchronized` 는 락을 못 잡으면 잠들고, 그게 스위치를 만든다.

CAS는 잠들지 않고 다시 시도하니 스위치가 없는 것이다.

앞의 CAS 알고리즘 설명 글에서 이 부분을 이어서 본다.

<br/><br/>

## 프로세스 스위치와 스레드 스위치가 다르다

```java
프로세스 간 스위치 - 메모리 매핑까지 바뀐다. TLB 가 통째로 비워진다
스레드 간 스위치   - 같은 프로세스 안이면 메모리 매핑은 그대로. 레지스터와 스택 포인터만
```

<br/>

앞의 multi thread VS multi process 글에서 `멀티 스레드는 컨텍스트 스위칭 비용이 적다` 고 한 이유가 이것이다.

같은 집 안에서 방을 바꾸는 것과 집을 옮기는 것의 차이인 셈이다.

<br/>

위의 2µs 는 스레드 간 스위치를 잰 것이다.

프로세스 간이면 이보다 더 든다.
