## 빌더 패턴 사용 이유

생성과 관련된 디자인 패턴으로, 동일한 프로세스를 거쳐 다양한 구성의 인스턴스를 만드는 방법

객체를 생성 시, 생성자만을 사용할 때 발생할 수 있는 문제를 개선하기 위해 입니다.

<br/>

### 빌더 패턴을 사용해야 하는 이유

1. 필요한 데이터만 설정 가능하다.

2. 유연성을 확보할 수 있다.
3. 가독성을 높일 수 있다.

<br/>

### 예시를 위한 코드

```java
@NoArgsConstructor
@AllArgsConstructor
public class User {    
    private String name;
    private int age;
    private String email;
    private int phoneNumber;
}
```

<br/><br/>

## 1번) 필요한 데이터만 설정 가능하다.

예를 들어 User 객체를 생성해야 하는 상황에, 

`age라는 파라미터가 필요 없는 상황`이라고 생각해보자.

<br/>

생성자를 이용하는 경우라면 우리는 `age`가 없는 생성자를 새로 만들어야 한다.

```java
@NoArgsConstructor 
@AllArgsConstructor 
public class User { 
    private String name;
    private int age;
    private String email;
    private int phoneNumber;

    public User (String name, String email, int phoneNumber) {
        this.name = name;
        this.email = email;
        this.phoneNumber = phoneNumber;
    }
}
```

요구사항은 계속 변하게 되어있고, 반복적인 변경을 필요로 하면, 힘들고 시간 낭비이다. 

하지만 `빌더`를 이용하면 `동적`으로 이를 처리할 수 있다.

<br/><br/>

## 2. 유연성을 확보할 수 있음

생성자의 경우는 정해진 파라미터 순서대로 꼭 값을 넣어줘야한다. 

- 순서를 무시하고 값을 넣으면 에러가 발생하거나 엉뚱한데 값이 들어갈 수 있다.

하지만 빌더 패턴은 빌더의 필드 이름으로 값을 설정하기 때문에 굳이 순서를 

생각할 필요 없이 편하게 설정하면 된다.

<br/><br/>

### 3. 가독성을 높일 수 있음

빌더 패턴을 사용하면 매개변수가 많아져도 가독성을 높일 수 있다. 

생성자로 객체를 생성하는 경우에는 매개변수가 많아질수록 코드 리딩이 떨어진다. 

<br/>

클래스 변수가 4개 이상만 되어도 코드를 읽기 힘들어진다. 

하지만 다음과 같이 빌더 패턴을 적용하면 직관적으로 어떤 데이터에 

어떤 값이 설정되는지 쉽게 파악하여 가독성을 높일 수 있다.

```java
User user = User.builder()
             .name("김민석")
             .age(27)
             .email("alstjr706@naver.com")
             .phoneNumber(01012341234)
             .build();
```

<br/><br/>

## 정리

만약 아직 객체의 생성을 위해 생성자나 수정자 패턴 또는 

정적 메소드 패턴을 사용하고 있다면 롬복을 사용해 빌더 패턴을 적용하도록 하자.

<br/>

그리고 이렇게 필요한 데이터만 설정할 수 있는 빌더의 장점은 

생성자 또는 정적 메소드와 비교하여 테스트용 객체를 생성할 때 용이하게 해주고, 

불필요한 코드의 양을 줄이는 등의 이점이 있다.
<br/>

## 궁금증!

```java
@Builder 를 붙이면 실제로 무엇이 만들어지는 걸까?
```

컴파일해서 열어보면 클래스가 하나 더 생겨 있다.

```java
@Builder
public class User {
    private String name;
    private int age;
    private String email;
}
```

<br/>

### 컴파일 결과

```java
public class User {
  User(java.lang.String, int, java.lang.String);      // 모든 필드를 받는 생성자
  public static User$UserBuilder builder();           // 빌더를 만들어주는 static 메서드
}

public class User$UserBuilder {
  public User$UserBuilder name(java.lang.String);
  public User$UserBuilder age(int);
  public User$UserBuilder email(java.lang.String);
  public User build();
}
```

<br/>

`User$UserBuilder` 라는 별도 클래스가 생겼다.

값을 하나씩 받아서 자기 자신을 돌려주기 때문에 `.name().age().email()` 처럼 이어 쓸 수 있는 것이다.

<br/>

그리고 `build()` 가 마지막에 그 모든 값을 모아서 생성자를 부른다.

결국 생성자를 안 쓰는 게 아니라, 생성자를 부르기 전에 값을 모아두는 단계를 하나 끼운 것이다.

```java
빌더 없이 : new User("김민석", 27, "...")           <- 순서와 개수를 다 맞춰야 한다
빌더 있음 : 값을 하나씩 모은다 -> build() 가 대신 생성자를 부른다
```

<br/>

## 그런데 빌더에는 큰 약점이 하나 있다

필수값을 강제할 수 없다는 것이다. 직접 해봤다.

```java
User user = User.builder()
        .age(27)                // name 과 email 을 빼먹었다
        .build();
```

<br/>

### 결과

```java
name 없이도 만들어졌다 -> User@14dad5dc
```

<br/>

컴파일도 되고 실행도 된다. `name` 이 `null` 인 `User` 가 만들어진 것이다.

<br/>

생성자는 정반대였다. 앞의 생성자 글에서 본 것처럼,

인자를 빼먹으면 컴파일 자체가 안 됐다.

```java
생성자 -> 빼먹으면 컴파일 에러 (안전하지만 불편하다)
빌더   -> 빼먹어도 통과 (편하지만 위험하다)
```

<br/>

원문의 `필요한 데이터만 설정 가능하다` 는 장점이, 뒤집으면 이 약점이 된다.

`안 넣어도 되는 값` 과 `안 넣으면 안 되는 값` 을 구분해주지 않기 때문이다.

<br/>

## 그래서 생성자에 @Builder를 붙인다

클래스가 아니라 생성자에 붙이면, 그 생성자 안에서 검증을 할 수 있다.

```java
public class User {
    private final String name;
    private final int age;
    private final String email;

    @Builder
    private User(String name, int age, String email) {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("이름은 필수입니다");
        }
        this.name = name;
        this.age = age;
        this.email = email;
    }
}
```

<br/>

이제 `name` 없이 `build()` 하면 예외가 난다.

컴파일 시점은 아니지만, 잘못된 객체가 만들어지는 것은 막을 수 있다.

<br/>

생성자를 `private` 으로 막아둔 것도 포인트다.

빌더로만 만들 수 있게 해서 검증을 우회할 방법을 없앤 것이다.

```java
클래스에 @Builder      -> 모든 필드를 받는 생성자가 자동 생성. 검증할 자리가 없다
생성자에 @Builder      -> 내가 쓴 생성자를 쓴다. 검증을 넣을 수 있다
```

<br/>

## 필수값이 정말 필수라면 생성자가 나을 수도 있다

```java
User.builder()
    .name("김민석")
    .email("...")
    .build();

new User("김민석", "...");     // 이게 더 나을 때도 있다
```

<br/>

필드가 두세 개고 전부 필수라면 굳이 빌더를 쓸 이유가 없다.

빌더는 `선택적인 값이 많을 때` 빛을 본다.

<br/>

원문에서 `클래스 변수가 4개 이상만 되어도` 라고 한 기준이 대체로 맞다.

다만 세는 기준을 `필드 개수` 보다 `선택적인 필드 개수` 로 보면 더 정확하다.

<br/>

## 엔티티에 @Builder 를 붙일 때 주의할 것

```java
@Entity
@Builder                     // 클래스에 붙이면
public class Member {
    @Id @GeneratedValue
    private Long id;         // id 까지 빌더로 넣을 수 있게 된다
    private String name;
}
```

<br/>

`id` 는 DB가 만들어주는 값인데 빌더로 넣을 수 있게 되어버린다.

`Member.builder().id(999L)` 같은 코드가 컴파일되면 사고가 나기 쉽다.

<br/>

그래서 엔티티는 생성자에 붙이고, `id` 는 아예 파라미터에서 빼는 편이 낫다.

```java
@Builder
private Member(String name, String email) {   // id 가 없다
    this.name = name;
    this.email = email;
}
```

빌더로 만들 수 있는 것과 만들면 안 되는 것을 여기서 갈라놓는 것이다.
