## 뮤텍스와 세마포어의 차이

<br/>

## 뮤텍스

뮤텍스는 화장실이 하나 뿐이 없는 식당과 비슷하다. 

화장실을 가기 위해서는 카운터에서 열쇠를 받아 가야 한다는 것이다

<br/>

키(락)을 있으면 화장실에 사람이 없다는 뜻이다.

그 열쇠를 이용해 화장실에 들어갈 수 있다.

<br/>

그리고 나와서, 키를 돌려놨다면 기다리던 사람들 중 

맨 앞에 있는 사람이 키를 받을 수 있는것이다.

<br/><br/>

## 세마포어

세마포어는 손님이 화장실을 좀 더 쉽게 이용할 수 있는 레스토랑이다. 

세마포어를 이용하는 레스토랑의 화장실에는 여러 개의 칸이 있다. 

<br/>

그리고 화장실 입구에는 현재 화장실의 빈 칸 개수를 보여주는 전광판이 있다.

세마포어는 공통으로 관리하는 하나의 값을 이용해 상호배제를 달성한다.

<br/><br/>

## 뮤텍스 세마포어 차이

뮤텍스는 Lock을 사용해 하나의 프로세스나 쓰레드를 단독으로 실행하게 합니다. 

세마포어는 세마포어 변수만큼 자원에 프로세스가 접근할 수 있도록 합니다.

세마포어의 변수 → 자원의 개수를 나타내는 변수

<br/>

현재 수행중인 프로세스가 아닌 다른 프로세스가 세마포어를 해제할 수 있습니다.

하지만 뮤텍스는 락(lock)을 획득한 프로세스가 반드시 그 락을 해제해야 합니다.
<br/><br/>

## 궁금증!

```java
원문의 마지막 차이를 실제로 확인해봤다
```

```java
"뮤텍스는 락을 획득한 프로세스가 반드시 그 락을 해제해야 합니다"
"세마포어는 다른 프로세스가 해제할 수 있습니다"
```

<br/>

자바로 둘을 나란히 돌렸다.

```java
ReentrantLock lock = new ReentrantLock();
lock.lock();                                          // main 이 잡고
new Thread(() -> lock.unlock()).start();              // 다른 스레드가 푼다
```

```java
Semaphore sem = new Semaphore(1);
sem.acquire();                                        // main 이 잡고
new Thread(() -> sem.release()).start();              // 다른 스레드가 푼다
```

<br/>

### 결과

```java
다른 스레드가 ReentrantLock.unlock()  -> IllegalMonitorStateException
다른 스레드가 Semaphore.release()     -> 정상. 남은 허가 = 1
```

<br/>

뮤텍스는 예외가 나고, 세마포어는 그냥 된다.

<br/>

이게 그냥 규칙 차이가 아니다. 뮤텍스는 `소유자` 라는 개념이 있고 세마포어는 없다.

```java
뮤텍스   - "누가 잡고 있는가" 를 기억한다. 그 사람만 풀 수 있다
세마포어 - "몇 개 남았는가" 만 기억한다. 누가 늘리든 상관없다
```

<br/>

원문의 `카운터에서 열쇠를 받는다` 는 비유가 이것이다.

열쇠를 받은 사람만 돌려줄 수 있는 것이 뮤텍스고, 전광판 숫자는 누가 바꿔도 되는 것이 세마포어다.

<br/><br/>

## 그래서 쓰임새가 갈린다

세마포어는 `한 스레드가 잡고 다른 스레드가 푸는` 상황에 쓴다.

```java
생산자가 데이터를 넣고 -> release()  (허가를 하나 늘린다)
소비자가 데이터를 빼고 -> acquire()  (허가를 하나 쓴다)
```

<br/>

생산자와 소비자가 다른 스레드인데 하나의 세마포어를 주고받는다.

뮤텍스로는 이게 불가능하다. 생산자가 잡은 것을 소비자가 못 푸니까.

<br/>

이 경우 세마포어는 `상호 배제` 가 아니라 `신호` 로 쓰이는 것이다.

`데이터가 하나 준비됐다` 를 알리는 용도다.

<br/><br/>

## 세마포어(3) 에 실제로 3 명만 들어가나

```java
Semaphore s3 = new Semaphore(3);

// 스레드 10개가 각자
s3.acquire();
inside++;  peak = max(peak, inside);      // 지금 안에 몇 명인지 기록
sleep(100);
inside--;
s3.release();
```

<br/>

### 결과

```java
동시에 안에 있던 최대 인원 = 3
```

<br/>

10명이 몰렸는데 안에는 최대 3명이다.

원문의 `화장실 칸이 여러 개인 식당` 이 정확히 이것이다.

<br/>

실무에서 이 형태를 쓰는 자리가 있다.

```java
외부 API 를 동시에 최대 5 개만 부르게 제한
DB 커넥션 풀의 최대 개수
동시 다운로드 개수 제한
```

<br/>

앞의 커넥션 풀 글에서 본 HikariCP가 안에서 이런 식으로 개수를 관리한다.

`커넥션 10개` 는 곧 `허가 10개짜리 세마포어` 인 것이다.

<br/><br/>

## 재진입에서도 갈린다

```java
ReentrantLock lock;
lock.lock(); lock.lock();       // 같은 스레드가 두 번
lock.getHoldCount()             // = 2. 된다
```

```java
Semaphore bin = new Semaphore(1);
bin.acquire();
bin.tryAcquire()                // = false. 자기 자신도 막힌다
```

<br/>

세마포어는 `누가 잡았는지` 를 모르니, 같은 스레드가 다시 와도 남은 허가가 0이면 그냥 막는다.

<br/>

이래서 세마포어(1)을 뮤텍스 대신 쓰면 사고가 난다.

```java
void a() { sem.acquire(); b(); sem.release(); }
void b() { sem.acquire(); ...; sem.release(); }      // a() 안에서 부르면 여기서 영원히 멈춘다
```

<br/>

자기가 잡은 것을 자기가 기다리는 교착이다.

앞의 Reentrant Lock과 synchronized의 차이 글에서 본 대로, 뮤텍스는 재진입을 허락해서 이 문제가 없다.

<br/><br/>

## 이진 세마포어 ≠ 뮤텍스

허가가 1개인 세마포어를 이진 세마포어라고 부른다.

겉으로는 뮤텍스와 똑같이 동작하는 것 같지만 위에서 본 두 가지가 다르다.

```java
                이진 세마포어      뮤텍스
소유자          없음              있음
남이 풀기       된다              예외
재진입          안 된다           된다
우선순위 상속   없음              있는 구현이 많다
```

<br/>

마지막 줄은 운영체제 수준의 얘기다.

낮은 우선순위 스레드가 뮤텍스를 잡고 있는데 높은 우선순위 스레드가 기다리면,

잠깐 낮은 쪽의 우선순위를 올려서 빨리 끝내게 하는 것이다.

소유자를 아니까 가능하다. 세마포어는 누구를 올려야 할지 모른다.

<br/><br/>

## 언제 무엇을 쓰나

```java
공유 자원 하나를 지킨다          -> 뮤텍스 (synchronized, ReentrantLock)
동시 접근 개수를 N 으로 제한한다   -> 세마포어
다른 스레드에게 신호를 보낸다     -> 세마포어, 또는 CountDownLatch
```

<br/>

자바에서는 뮤텍스가 필요하면 `synchronized` 를 쓰고, 개수 제한이 필요하면 `Semaphore` 를 쓴다.

세마포어로 뮤텍스를 흉내내는 일은 하지 않는다. 위에서 본 재진입과 소유자 문제 때문이다.

<br/>

원문 비유에 하나만 덧붙이면 이렇다.

열쇠 하나짜리 식당에서 화장실에 들어간 사람이 안에서 다른 사람 열쇠를 대신 반납할 수는 없지만,

전광판 식당에서는 청소 직원이 지나가다 숫자를 올려놓을 수도 있다. 그게 세마포어의 성질이다.
