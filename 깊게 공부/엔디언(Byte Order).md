## 엔디언(Byte Order)

<br/>

## 정수 하나를 메모리에 어떻게 놓나

`int` 는 4바이트다. 4바이트를 메모리 4칸에 놓아야 하는데 순서가 두 가지다.

```java
빅 엔디언   - 큰 자리를 앞에. 사람이 숫자 쓰는 순서
리틀 엔디언 - 작은 자리를 앞에
```

<br/>

이름은 걸리버 여행기에서 왔다.

달걀을 큰 쪽부터 깨는 파와 작은 쪽부터 깨는 파가 싸우는 얘기다. 어느 쪽이 맞다는 게 없다는 뜻으로 붙였다.

<br/><br/>

## 궁금증!

```java
같은 숫자를 두 방식으로 쓰면 바이트가 어떻게 되나
```

```java
ByteBuffer.allocate(4).order(ByteOrder.BIG_ENDIAN).putInt(0x01020304)
ByteBuffer.allocate(4).order(ByteOrder.LITTLE_ENDIAN).putInt(0x01020304)
```

<br/>

### 결과

```java
0x01020304 를 빅 엔디언으로   = 01 02 03 04
0x01020304 를 리틀 엔디언으로 = 04 03 02 01
```

<br/>

정확히 뒤집힌다.

<br/>

같은 4바이트 `04 03 02 01` 을 빅 엔디언으로 읽으면 `0x04030201` 이라는 다른 숫자가 된다.

쓴 쪽과 읽는 쪽이 방식이 다르면 값이 통째로 바뀌는 것이다.

<br/><br/>

## 이 컴퓨터는 어느 쪽인가

```java
이 CPU 의 기본 = LITTLE_ENDIAN
```

<br/>

x86도 ARM도 리틀 엔디언이다. 요즘 CPU는 거의 전부 리틀이다.

<br/>

리틀이 하드웨어에 편한 이유가 있다.

```java
int 값 5 = 05 00 00 00 (리틀)
이 주소를 byte 로 읽으면 -> 05. 그대로 5 다
short 로 읽으면 -> 05 00. 그대로 5 다
```

<br/>

작은 타입으로 읽어도 시작 주소가 같다. 빅 엔디언이면 시작 주소를 옮겨야 한다.

<br/><br/>

## 자바는 빅 엔디언이다

```java
자바 ByteBuffer 기본 = BIG_ENDIAN
DataOutputStream.writeInt 도 빅 엔디언 고정
```

<br/>

CPU는 리틀인데 자바는 빅으로 쓴다.

<br/>

앞의 자바 가상머신(JVM) 글에서 본 `write once, run anywhere` 때문이다.

자바 프로그램이 파일에 쓴 정수를 다른 CPU의 자바 프로그램이 읽어도 같은 값이 나와야 한다.

CPU 순서를 따르면 이게 깨지니 JVM이 하나로 고정한 것이다.

<br/>

앞의 자바는 어떻게 실행되나요 글에서 본 `.class` 파일도 빅 엔디언이다.

`CA FE BA BE` 를 어느 컴퓨터에서 읽어도 같은 매직 넘버인 이유다.

<br/><br/>

## 네트워크도 빅 엔디언이다

TCP/IP 헤더의 포트 번호, 길이 같은 숫자는 전부 빅 엔디언으로 정해져 있다.

그래서 빅 엔디언을 네트워크 바이트 순서라고도 부른다.

<br/>

앞의 TCP 3 way handshake 글에서 본 패킷을 바이트로 뜯어보면 포트 `8080` 이 `1F 90` 으로 들어 있다.

리틀이면 `90 1F` 였을 것이다.

<br/>

C에서는 보낼 때마다 `htons()`, `htonl()` 로 바꿔야 한다.

자바는 기본이 빅이라 그냥 쓰면 된다. 자바 개발자가 엔디언을 잘 모르고도 지나가는 이유다.

<br/><br/>

## 그럼 언제 마주치나

자바 밖과 바이트를 주고받을 때다.

```java
C 프로그램이 만든 바이너리 파일 읽기     - 대개 리틀. order() 를 바꿔야 한다
게임 서버, IoT 장비 프로토콜            - 스펙에 명시되어 있다. 확인해야 한다
이미지 파일 포맷                       - BMP 는 리틀, PNG 는 빅
JNI 로 네이티브 메모리 직접 읽기          - CPU 순서
```

<br/>

```java
ByteBuffer buf = ByteBuffer.wrap(bytes).order(ByteOrder.LITTLE_ENDIAN);
int value = buf.getInt();
```

<br/>

`order()` 한 줄이면 되는데, 이걸 안 해서 값이 엉뚱하게 나오면 원인을 찾기가 어렵다.

`0x01020304` 를 기대했는데 `0x04030201` 이 나오면 뒤집힌 것이니 그때 의심하면 된다.

<br/><br/>

## UTF-8 에는 엔디언이 없다

UTF-8은 바이트 단위 인코딩이다.

한 글자가 여러 바이트여도 순서가 정의에 들어 있어서 뒤집힐 여지가 없다.

<br/>

UTF-16은 있다. 2바이트 단위라 빅과 리틀이 갈린다.

그래서 UTF-16 파일 앞에 `FE FF` 또는 `FF FE` 를 붙여서 어느 쪽인지 알린다. BOM이라고 부른다.

<br/>

앞의 char타입은 정수인가 글에서 본 자바 `char` 가 UTF-16이다.

JVM 안에서는 순서를 신경 쓸 필요가 없지만, `char[]` 를 바이트로 내보낼 때는 이 문제가 따라온다.

`String.getBytes(UTF_8)` 을 쓰는 것이 편한 이유 하나가 이것이다.
