## 가상 스레드(Virtual Thread)

<br/>

## 지금까지의 자바 스레드

```java
new Thread(...)      // 운영체제 스레드 하나와 1:1
```

<br/>

자바 스레드 하나가 운영체제 스레드 하나다. 플랫폼 스레드라고 부른다.

앞의 process를 설명해 주세요 글에서 본 대로 하나에 0.06ms, 스택 1MB 예약이다.

<br/>

앞의 스레드 풀 글에서 본 대로 I/O 작업은 스레드가 많을수록 빨랐다.

그런데 스레드를 무한히 늘릴 수는 없다.

<br/><br/>

## 궁금증!

```java
스레드를 몇 개까지 만들 수 있나
```

각자 1초 자고 끝나는 스레드를 개수를 늘려가며 만들었다.

<br/>

### 결과

```java
--- 1,000 개 ---
플랫폼 스레드 : 1,040 ms
가상 스레드   : 1,028 ms

--- 10,000 개 ---
플랫폼 스레드 : OutOfMemoryError: unable to create native thread
가상 스레드   : 1,037 ms

--- 100,000 개 ---
플랫폼 스레드 : OutOfMemoryError: unable to create native thread
가상 스레드   : 1,176 ms
```

<br/>

플랫폼 스레드는 1만 개에서 터졌다. 운영체제가 더 못 만들어준다.

가상 스레드는 10만 개를 만들어도 1.2초에 끝났다. 전부 동시에 1초를 잤다는 뜻이다.

<br/><br/>

## 어떻게 가능한가

가상 스레드는 운영체제 스레드가 아니다. JVM이 관리하는 객체다.

```java
가상 스레드 10,000 개가 실제로 쓴 운영체제 스레드(캐리어) = 10 개
```

<br/>

1만 개의 가상 스레드가 운영체제 스레드 10개 위에서 돌았다. 코어 수만큼이다.

<br/>

동작 방식이 이렇다.

```java
가상 스레드가 sleep() 이나 소켓 read() 로 멈추면
  -> 그 스레드의 스택을 힙에 저장하고
  -> 운영체제 스레드(캐리어)를 내놓는다
  -> 캐리어는 다른 가상 스레드를 태운다
깨어날 때가 되면
  -> 빈 캐리어를 받아 스택을 복원하고 이어서 돈다
```

<br/>

앞의 context switch vs Context 글에서 본 컨텍스트 스위치를 운영체제가 아니라 JVM이 하는 것이다.

커널을 안 거치니 앞의 시스템 콜과 유저 모드, 커널 모드 글에서 본 모드 전환 비용이 없다.

<br/><br/>

## 스택이 힙에 있다

플랫폼 스레드의 스택은 앞의 가상 메모리와 페이지 폴트 글에서 본 대로 미리 예약된 고정 영역이다.

가상 스레드의 스택은 힙에 있는 객체라 쓴 만큼만 차지하고, 늘어나면 늘어난다.

<br/>

그래서 10만 개를 만들어도 메모리가 터지지 않는다.

각자 실제로 쓴 스택 몇 KB만 힙에 있는 것이다.

<br/><br/>

## 무엇이 바뀌고 무엇이 안 바뀌나

코드는 안 바뀐다.

```java
Thread.ofVirtual().start(() -> {
    String r = httpClient.send(...);     // 평범한 Blocking 호출
    save(r);
});
```

<br/>

앞의 sync(동기) vs async(비동기) 글에서 본 `Blocking + Sync` 로 그냥 쓴다.

콜백도 없고 `CompletableFuture` 도 없다.

<br/>

그런데 실제로는 `httpClient.send()` 에서 멈추는 순간 캐리어를 내놓으니, 앞의 IO 모델 글에서 본 NIO처럼 운영체제 스레드를 아낀다.

<br/>

```java
읽기 쉬운 코드   = BIO 방식 그대로
자원 효율       = NIO 방식 수준
```

<br/>

둘을 동시에 가지는 것이 가상 스레드의 목적이다.

<br/><br/>

## 언제 이득이 없나

CPU 작업이다.

```java
앞의 스레드 풀 글: CPU 작업은 코어 수 이상 늘려도 안 빨라진다
```

<br/>

가상 스레드가 10만 개여도 캐리어는 10개다. 계산은 10개가 한다.

`기다리는 동안 캐리어를 내놓는다` 가 이득의 전부라, 기다리지 않는 작업에는 이득이 없다.

<br/>

그리고 풀에 넣으면 안 된다.

```java
Executors.newFixedThreadPool(200)  에 가상 스레드를 넣으면 -> 200개로 제한된다. 의미가 없다
Executors.newVirtualThreadPerTaskExecutor()              -> 작업마다 하나씩. 이게 맞는 사용법
```

<br/>

가상 스레드는 싸니까 재사용하지 않고 매번 만든다.

앞의 스레드 풀 글에서 본 `풀을 쓰는 이유` 두 가지 중 `생성 비용` 이 사라졀서, 남은 `상한` 은 세마포어로 따로 건다.

<br/><br/>

## 조심할 것 : 고정(pinning)

가상 스레드가 캐리어를 내놓지 못하는 경우가 있다.

```java
synchronized 블록 안에서 멈출 때    (자바 21~23)
네이티브 메서드 안에서 멈출 때
```

<br/>

이러면 캐리어에 붙잡혀서 플랫폼 스레드와 똑같이 동작한다.

자바 24부터 `synchronized` 안에서도 내놓을 수 있게 고쳐졌다. 위 실험은 자바 24라 문제가 없었다.

<br/>

앞의 Reentrant Lock과 synchronized의 차이 글에서 본 `ReentrantLock` 은 처음부터 문제가 없었다.

그래서 자바 21에서 가상 스레드를 쓰려면 `synchronized` 를 `ReentrantLock` 으로 바꾸라는 안내가 있었다.

<br/><br/>

## 스프링에서는

```java
spring.threads.virtual.enabled=true
```

<br/>

이 한 줄이면 톰캣이 요청마다 가상 스레드를 쓴다.

`server.tomcat.threads.max=200` 의 상한이 사실상 사라진다.

<br/>

다만 그 뒤의 DB 커넥션 풀은 그대로다.

앞의 커넥션 풀 글에서 본 대로 커넥션이 10개면 요청 1만 개가 들어와도 10개만 DB에 간다.

병목이 스레드에서 커넥션으로 옮겨가는 것이다.

<br/>

앞의 멀티 쓰레드 글에서 본 `병목은 항상 제일 좁은 곳에서 생긴다` 가 여기서도 그대로다.
