## JIT 컴파일러는 무엇인가요?

Java 소스 코드는 먼저 javac 명령을 통해 바이트코드(.class) 로 변환된다.

하지만 이 바이트코드는 CPU가 직접 이해할 수 있는 기계어가 아니다. 

따라서 실제로 프로그램이 실행될 때는 JVM 내부에서 한 번 더 변환하는 과정이 필요하다.

바로 이 바이트코드 → 기계어 변환을 실행 시점에 수행하는 주체가 JIT 컴파일러다.

```java
JIT = "동작 중인 코드를 빠르게 만들기 위해, 실행 시점에 기계어로 변환해주는 기술"
```

JIT 컴파일러는 이름은 ‘컴파일러’이지만, 실행 중에 동작하는 동적 변환 기술이라는 특징을 가진다.

정적인 컴파일과 달리, 실제로 프로그램이 어떤 방식으로 실행되는지 관찰한 뒤 자주 실행되는 코드(HotSpot) 를 선별하여 최적화한다는 점이 핵심이다.

<br/>

## 컴퓨터 프로그램 실행 방식 두 가지

### 1. 인터프리트 방식

- 코드를 한 줄씩 읽고 즉시 실행하는 방식

- 변환 과정을 실행할 때마다 반복하므로 간단하지만 속도가 느리다
- 예 : Python, JavaScript(초기), 쉘 스크립트

### 2. 정적 컴파일 방식

- 실행 전에 전부 기계어로 변환 → 실행

- 변환 비용은 딱 한 번만 발생
- 실행 속도가 매우 빠르지만, 실행 환경이나 플랫폼에 따라 빌드를 별도로 해야 하는 단점이 있다
- 예 : C, C++, Rust

<br/>

## 그렇다면 JIT는 무엇인가?

JIT는 위 두 가지 방식을 혼합한 형태라고 보면 가장 이해하기 쉽다.

- 기본적으로는 인터프리터처럼 바이트코드를 읽어 실행한다

- 하지만 실행 중 반복적으로 실행되는 코드를 탐지하면, 그 부분을 기계어로 변환하여 캐싱한다
- 이후부터는 인터프리트가 아닌 기계어로 바로 실행되므로 매우 빠르게 동작한다

초기 실행은 인터프리트로 하다가, 일정 시간이 지나면 컴파일된 기계어로 가속되는 구조다.

```java
인터프리트  +  런타임 컴파일(최적화)  = JIT
```

<br/>

## JIT 컴파일러의 장점

### 1. 실행 속도 향상

인터프리트 실행보다 기계어 실행이 훨씬 빠르기 때문에, 일정 시간이 지나면 정적 컴파일 언어에 가까운 속도가 나온다.

### 2. 런타임 정보 기반 최적화

정적 컴파일러는 실행 환경을 모른다.

하지만 JIT는 실행 중 실제 데이터를 보고 최적화를 수행하므로 더 정교한 최적화가 가능하다.

### 3. 플랫폼 독립성 유지

Java의 핵심 장점인 “Write Once, Run Anywhere” 를 그대로 유지하면서 속도까지 확보한다.

<br/>

## JIT 컴파일러가 없다면 어떻게 될까?

- Java는 바이트코드를 인터프리터로만 실행해야 한다 → 속도가 대폭 느려짐

- 루프 최적화, 인라이닝 같은 JVM의 고급 최적화가 작동하지 않음
- 고성능이 필요한 서버 애플리케이션, 빅데이터 엔진, 스트리밍 시스템에서 Java가 지금처럼 널리 쓰이지 못했을 가능성이 높다

<br/>

## 궁금증!

```java
"속도가 대폭 느려진다" 는 게 어느 정도일까?
```

JIT를 끄고 돌려볼 수 있다. `-Xint` 를 주면 인터프리터로만 실행한다.

```java
public class Run {
    public static void main(String[] args) {
        long start = System.currentTimeMillis();
        long sum = 0;
        for (int i = 0; i < 500_000_000L; i++) {
            sum += i % 7;
        }
        System.out.println("합 = " + sum + " / " + (System.currentTimeMillis() - start) + "ms");
    }
}
```

<br/>

### 결과

```java
$ java Run
합 = 1499999994 / 468ms

$ java -Xint Run
합 = 1499999994 / 4217ms
```

같은 코드인데 `9` 배 차이가 난다.

<br/>

## 어느 코드가 언제 컴파일되는지도 볼 수 있다

`-XX:+PrintCompilation` 을 주면 JIT가 일하는 것이 그대로 찍힌다.

```java
public class Jit {
    public static void main(String[] args) {
        long sum = 0;
        for (int i = 0; i < 50_000_000; i++) {
            sum += hot(i);
        }
        System.out.println(sum);
    }

    static int hot(int value) {
        return value % 7;
    }
}
```

<br/>

### 결과

```java
$ java -XX:+PrintCompilation Jit

13    1       3       java.lang.Object::<init> (1 bytes)
14    3       3       java.lang.String::hashCode (60 bytes)
16    8       3       Jit::hot (5 bytes)
18    9       4       Jit::hot (5 bytes)
18    8       3       Jit::hot (5 bytes)   made not entrant
```

<br/>

`Jit::hot` 이 세 번 등장한다. 가운데 숫자가 중요하다.

- `3` : 처음에 `3단계` 로 컴파일됐다

- `4` : 조금 뒤에 `4단계` 로 다시 컴파일됐다
- `made not entrant` : `3단계` 로 만든 것은 이제 안 쓴다고 버려진다

<br/>

## 단계가 나뉘어 있는 이유

JIT 컴파일러는 하나가 아니라 두 개다.

```java
C1 (client)  - 빨리 컴파일한다. 대신 최적화는 대충 한다.  -> 1~3단계
C2 (server)  - 오래 걸린다. 대신 최적화를 아주 세게 한다. -> 4단계
```

<br/>

처음부터 `C2` 로 세게 최적화하면 컴파일하는 시간이 오래 걸려서 시작이 느려진다.

그렇다고 `C1` 만 쓰면 오래 도는 코드에서 손해다.

<br/>

그래서 이렇게 한다.

```java
처음        -> 인터프리터로 실행하면서 몇 번 불리는지 센다
좀 불리면   -> C1으로 빠르게 컴파일해서 일단 속도를 올린다
아주 자주면 -> C2로 다시 제대로 컴파일하고, C1 것은 버린다
```

위 로그에서 `hot()` 이 `3단계` 를 거쳐 `4단계` 로 간 것이 이 과정이다.

이것을 `단계적 컴파일(Tiered Compilation)` 이라고 부른다.

<br/>

## 그래서 워밍업이라는 말이 나온다

서버를 막 띄웠을 때는 아직 아무것도 컴파일되지 않은 상태다.

`C2` 까지 올라가려면 코드가 수만 번은 불려야 한다.

<br/>

배포 직후 응답이 유독 느리다가 점점 빨라지는 것이 이 때문이다.

부하 테스트를 할 때 처음 몇 분치 결과를 버리는 것도 같은 이유다.

```java
JIT는 "실행해봐야" 최적화할 수 있다 -> 초반에는 느릴 수밖에 없다
```

<br/>

앞에서 성능을 잴 때 워밍업 반복을 먼저 돌리고 측정한 것도 이 때문이다.

워밍업 없이 재면 JIT가 일하기 전의 느린 속도를 재게 된다.

<br/>

## 최적화를 되돌리기도 한다

`made not entrant` 라는 말이 나온 김에 짚어두면, JIT는 최적화를 취소할 수도 있다.

<br/>

예를 들어 어떤 인터페이스의 구현체가 지금까지 하나뿐이었다면,

JIT는 `앞으로도 이것 하나겠지` 하고 메서드 호출을 아예 인라인해버린다.

<br/>

그런데 나중에 다른 구현체가 로드되면 그 가정이 깨진다.

그러면 컴파일해둔 기계어를 버리고 다시 인터프리터로 돌아간다. 이것을 `역최적화` 라고 한다.

<br/>

실행 중에 얻은 정보로 과감하게 최적화하고, 틀리면 되돌린다.

정적 컴파일러는 실행 정보를 모르니 이런 도박을 할 수 없다.

원문의 `런타임 정보 기반 최적화` 가 실제로는 이런 모양인 것이다.
