## B tree 데이터 삭제 방식

<br/>

## 두가지를 기억하자.

- 삭제는 항상 leaf 노드에서 발생한다.

- 삭제 후 최소 key 수보다 적어졌다면 재조정 해야 한다.

<br/>

### 재조정 절차 3가지 절차를 따른다.

즉, 삭제 후 최소 ‘key’ = ‘밑에 있는 노드’ key수 조건 보다 적어졌다면 밑에 순서를 따른다.

```jsx
1. key 수가 여유 있는 형제의 지원을 받는다.
2. 1번이 불가능하다면, 부모의 지원을 받고 형제와 합친다.
3. 2번 후 부모에 문제가 있다면 거기서 다시 1번, 2번을 반복하며 재조정한다.
```

<br/><br/>

## 정리

- 삭제는 항상 leaf(맨 밑 노드) 노드에서 진행한다.

- internal(맨 밑 노드가 아닌 노드들) 노드의 경우 선임자(나보다 적은 가장 큰 값)와 위치 바꾼 후 삭제한다.
    
- 삭제 후 최소 key 수보다 적어졌다면 재조정한다.

- 부모 지원을 받았을 경우에는 형제를 무조건 합쳐야 한다.

    - 부모 도움을 받고 부모쪽에서도 문제 발생 시 위 과정 반복하며 조정.

## 궁금증!

```java
실제 DB 도 이렇게 병합하고 재분배할까?
```

이론상으로는 그렇지만, 실무 DB는 대개 `안 한다`.

<br/>

MySQL InnoDB는 삭제할 때 그 자리를 `삭제 표시` 만 하고 그대로 둔다.

노드가 절반 아래로 내려가도 바로 병합하지 않는다.

```java
[10, 20, 30, 40]
  -> 20 을 삭제
[10, __, 30, 40]     -- 자리는 남아 있고 표시만 해둔다
```

<br/>

## 왜 안 하는가

병합이 비싸기 때문이다.

```java
병합하려면
  1. 옆 노드를 읽는다 (디스크 접근)
  2. 두 노드를 합쳐서 쓴다 (디스크 접근)
  3. 부모 노드에서 키를 지운다 (디스크 접근)
  4. 부모도 절반 아래로 내려가면 부모끼리 또 병합한다
```

<br/>

한 건 지웠을 뿐인데 디스크를 여러 번 읽고 써야 한다.

그리고 곧바로 다시 삽입되면 방금 병합한 것을 다시 쪼개게 된다.

<br/>

앞의 MVCC 글에서 본 이유도 있다.

```java
DELETE 를 해도 다른 트랜잭션이 아직 그 행을 보고 있을 수 있다
-> 지금 진짜로 지우면 안 된다
-> 표시만 해두고, 아무도 안 보게 되면 그때 정리한다
```

<br/>

이 정리 작업을 `퍼지(purge)` 라고 하고, 백그라운드 스레드가 따로 한다.

<br/>

## 그래서 인덱스가 부풀어 오른다

지운 자리가 계속 남아 있으면 인덱스 파일이 커진다.

```java
1000 만 건을 넣고 900 만 건을 지웠다
-> 남은 것은 100 만 건인데
-> 인덱스 크기는 1000 만 건 시절 그대로일 수 있다
```

<br/>

앞의 DB 인덱스 글에서 본 대로 인덱스가 크면 높이가 높아지고 읽기가 느려진다.

빈 자리가 많은 페이지를 계속 읽는 셈이라 낭비가 크다.

<br/>

이 상태를 `인덱스 단편화` 라고 한다.

<br/>

## 정리하는 방법

```sql
-- MySQL
OPTIMIZE TABLE member;
ALTER TABLE member ENGINE=InnoDB;    -- 테이블을 통째로 다시 만든다

-- PostgreSQL
VACUUM FULL member;
REINDEX TABLE member;
```

<br/>

전부 테이블이나 인덱스를 다시 만드는 작업이다.

그래서 그동안 테이블이 잠기고, 큰 테이블에서는 오래 걸린다.

<br/>

운영 중에 함부로 돌리면 안 된다.

`pt-online-schema-change` 같은 도구로 서비스를 멈추지 않고 하는 방법을 쓴다.

<br/>

## 애초에 안 지우는 방법

앞의 파티셔닝 글에서 본 방식이 여기서 다시 나온다.

```sql
-- 하나씩 지우면 삭제 표시가 쌓인다
DELETE FROM orders WHERE order_date < '2026-01-01';

-- 파티션을 통째로 지우면 단편화가 안 생긴다
ALTER TABLE orders DROP PARTITION p2025;
```

<br/>

파일을 통째로 버리는 것이라 빈 자리가 남을 일이 없다.

<br/>

대량 삭제가 예정된 데이터라면 처음부터 파티션을 나눠두는 것이 답이다.

`나중에 지울 것을 미리 분리해두는` 설계인 셈이다.

<br/>

## 소프트 삭제도 관련이 있다

실무에서 `deleted` 컬럼을 두고 실제로는 안 지우는 방식을 많이 쓴다.

```sql
UPDATE member SET deleted = true WHERE id = 1;
```

<br/>

복구할 수 있고 이력이 남는다는 장점이 있는데, 대신 데이터가 계속 쌓인다.

<br/>

그리고 모든 조회에 `WHERE deleted = false` 가 붙어야 한다.

이 조건을 빠뜨리면 지운 데이터가 화면에 나온다.

<br/>

인덱스도 이걸 고려해서 만들어야 한다.

```sql
CREATE INDEX idx_member_email ON member(deleted, email);   -- deleted 를 앞에
```

<br/>

앞의 DB 인덱스 글에서 본 카디널리티 얘기와는 반대로 보이는데,

`항상 붙는 조건` 이라면 앞에 두는 편이 낫다. 걸러낼 범위가 먼저 줄어들기 때문이다.
