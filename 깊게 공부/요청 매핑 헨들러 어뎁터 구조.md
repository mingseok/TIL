### HTTP 메시지 컨버터는 스프링 MVC 어디쯤에서 사용되는 것일까?

![이미지](/programming/img/입문101.PNG)

`@RequestMapping` 을 처리하는 핸들러 어댑터인

`RequestMappingHandlerAdapter` (=요청 매핑 헨들러 어뎁터)에 있다.

<br/><br/>

## `ArgumentResolver` 설명

![이미지](/programming/img/입문102.PNG)

- 컨트롤러로 넘어가기전 메서드의 매개변수들을 처리해주는 것이 바로 `ArgumentResolver` 이다

    - 애노테이션 기반의 컨트롤러는 매우 다양한 파라미터를 사용할 수 있다.

    - `Model`, `@RequestParam`, `@ModelAttribute` 등등 많다..

이렇게 유연하게 처리할 수 있는 이유가 바로 `ArgumentResolver` 이다

<br/><br/>

## 흐름은 이렇다.

1. `RequestMapping(=핸들러 어댑터)`가 `핸들러(=컨트롤러)` 쪽을 보고 필요한 것을 본다.

2. 필요한 것을 확인 후 → 핸들러 어댑터가 `ArgumentResolver` 한테 처리 할 수 있냐고 물어본다. 
3. 처리 할 수 있다면 `ArgumentResolver`가 생성해준다. 
4. 이중에서도 만약, HTTP 메시지 컨버터를 사용하는 (=`@RequestBody, 등..`)것이 있으면 
5. `ArgumentResolver` 안에 HTTP 메시지 컨버터를 사용해서 여러가지
6. 컨버터들을 루프로 돌면서 처리 할 수 있는 것을 찾는 것이다.
7. (반대로 반환 할때는 `@ResponseBody`, 등.. 이 되는 것이다)
8. 생성을 해줬다면 핸들러 어댑터가 핸들러에게 넘겨 주는 것이다.

![이미지](/programming/img/입문103.PNG)

## ReturnValueHandler 설명

메서드에서 반환 타입이 `String`일 경우도 있고, `void`일 경우도 있고, 

`@ResponseBody`에서 `String` 반환하고 이것저것 종류가 많다..

<br/>

그리하여 이것을 처리해 주는 애가 바로 `ReturnValueHandler` 이다.

```
컨트롤러에서 String으로 뷰 이름을 반환해도, 동작하는 이유가 바로 ReturnValueHandler 덕분인 것이다.
```

<br/><br/>

## 궁금증!

```java
ArgumentResolver 가 "여러 파라미터를 처리한다" 는데, 실제로 몇 개나 있을까?
```

`spring-webmvc` jar 안을 세어봤다.

```java
$ unzip -l spring-webmvc.jar | grep -c "MethodArgumentResolver.class"
20 개
```

<br/>

이름을 보면 어떤 파라미터를 맡는지 바로 보인다.

```java
RequestParamMethodArgumentResolver          -> @RequestParam
PathVariableMethodArgumentResolver          -> @PathVariable
ModelAttributeMethodProcessor               -> @ModelAttribute
RequestResponseBodyMethodProcessor          -> @RequestBody / @ResponseBody
ServletRequestMethodArgumentResolver        -> HttpServletRequest, Locale 등
SessionAttributeMethodArgumentResolver      -> @SessionAttribute
```

<br/>

파라미터 종류 하나에 클래스 하나씩이다.

`RequestMappingHandlerAdapter` 는 이 목록을 순서대로 돌면서 물어본다.

```java
for (리졸버 : 리졸버목록) {
    if (리졸버.supportsParameter(파라미터)) {     // "이거 네가 처리할 수 있어?"
        return 리졸버.resolveArgument(파라미터);   // "그럼 만들어줘"
    }
}
```

<br/>

원문의 `2번, 3번` 흐름이 이 반복문이다.

파라미터를 만들 수 있는 리졸버를 찾을 때까지 물어보고, 찾으면 만들어달라고 한다.

<br/>

## 그래서 파라미터를 마음대로 적을 수 있다

```java
@GetMapping("/members/{id}")
public String find(@PathVariable Long id,
                   @RequestParam String keyword,
                   HttpServletRequest request,
                   Model model,
                   Locale locale) { ... }
```

<br/>

순서를 바꿔도 되고, 필요 없는 건 빼도 된다.

컨트롤러 메서드가 이렇게 자유로운 형태일 수 있는 것은 리졸버 20개가 각자 자기 몫을 알아서 채워주기 때문이다.

<br/>

일반적인 자바 메서드라면 정해진 순서와 개수로만 부를 수 있다.

여기는 리플렉션으로 파라미터를 하나씩 보면서 값을 채운 다음, 그 배열을 넘겨서 호출하는 방식이다.

```java
Object[] args = new Object[파라미터개수];
for (int i = 0; i < 파라미터개수; i++) {
    args[i] = 맞는리졸버.resolveArgument(파라미터[i]);
}
method.invoke(컨트롤러, args);
```

## RequestBody 는 왜 컨버터를 한 번 더 거치는가

원문 `4~6번` 이 이 부분이다.

<br/>

다른 파라미터들은 URL이나 파라미터 이름에서 값을 꺼내면 끝난다.

그런데 `@RequestBody` 는 본문에 들어온 바이트 뭉치를 자바 객체로 바꿔야 한다.

```java
{"name":"민석","age":30}   ->   MemberRequest 객체
```

<br/>

이 변환은 본문 형식에 따라 다르다. JSON일 수도, XML일 수도, 그냥 문자열일 수도 있다.

그래서 `HttpMessageConverter` 라는 또 하나의 목록에게 물어본다.

```java
ByteArrayHttpMessageConverter        -> byte[]
StringHttpMessageConverter           -> String
FormHttpMessageConverter             -> form 데이터
AbstractJacksonHttpMessageConverter  -> JSON (Jackson)
```

<br/>

어느 컨버터를 쓸지는 요청의 `Content-Type` 헤더를 보고 정한다.

앞의 form 태그 글에서 본 `Content-type: application/x-www-form-urlencoded` 가 이럴 때 쓰인다.

```java
Content-Type: application/json                  -> Jackson 컨버터
Content-Type: application/x-www-form-urlencoded -> Form 컨버터
```

<br/>

반대로 응답할 때는 요청의 `Accept` 헤더를 보고 정한다.

`@ResponseBody` 가 붙은 반환값을 `ReturnValueHandler` 가 받아서, 다시 컨버터로 넘기는 구조다.

<br/>

## 정리하면 세 겹이다

```java
DispatcherServlet
  -> HandlerAdapter (RequestMappingHandlerAdapter)
       -> ArgumentResolver  (파라미터 채우기)
            -> HttpMessageConverter  (본문 <-> 객체 변환)
       -> 컨트롤러 메서드 실행
       -> ReturnValueHandler (반환값 처리)
            -> HttpMessageConverter  (객체 -> 본문 변환)
```

<br/>

원문 마지막의 `스프링은 모두 인터페이스로 제공한다` 가 이 구조를 지탱한다.

세 겹이 전부 인터페이스라서, 새로운 파라미터 형식이나 새로운 데이터 형식이 필요하면

구현체를 하나 만들어 목록에 끼워 넣으면 된다.

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(new LoginMemberArgumentResolver());   // 내가 만든 것을 끼운다
    }
}
```

<br/>

로그인한 회원을 컨트롤러 파라미터로 바로 받는 `@Login` 같은 어노테이션을

직접 만들 수 있는 것이 이 덕분이다.
