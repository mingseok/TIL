## CAS 알고리즘 설명



인자로 기존 값과 변경할 값을 전달합니다.



기존 값이 현재 메모리가 가지고 있는 값과 같다면 변경할 값을 반영하며 `true`를 반환한다.

반대로 기존 값이 현재 메모리가 가지고 있는 값과 다르다면 값을 반영하지 않고 `false`를 반환한다.

<br/>

## 여담이라고 하지만,

만약 `false`를 반환 했을때는 개발자의 요구사항에 따라 달라진다고 합니다.

- `while`문을 돌면서 `true`가 나올때까지 재시도하는 방법

- 몇번 시도하다가 `exception`을 터뜨리고 끝내는 방법

<br/>

### 원자성을 보장 할 수가 있습니다.

```java
"원자성이란?" 
여러개의 쓰레드가 있을 때 특정 시점에 어떤 메소드를
두개 이상의 쓰레드가 동시에 호출 못한다는 것입니다.

멀티 쓰레드 기반의 프로그래밍을 하게 되면 중요한 것이 바로 "원자성"의 보장입니다.
```

### CAS 알고리즘 사용 예

- 변수마다 동기화를 해줄 수 있는 특징 덕에 Atomic 클래스에 사용 됩니다.
    
    Atomic 자료형은 기본형인 int, long 등의 동기화를 보장해주는 자료형인데, 내부에서 CAS 알고리즘을 사용합니다.
    
- 또 `ConcurrentHashMap` 클래스에서도 사용되는데, 빈 버킷에 값을 넣을 때
    
    CAS 알고리즘을 사용함으로써 빠르게 처리해줄 수 있습니다.
    
    (이미 값이 들어있으면 synchronized를 사용.)

## 궁금증!

```java
CAS 를 직접 불러봤다
```

```java
AtomicInteger a = new AtomicInteger(10);

a.compareAndSet(10, 11);      // "지금 10 이면 11 로 바꿔라"
a.compareAndSet(10, 12);      // "지금 10 이면 12 로 바꿔라"
```

<br/>

### 결과

```java
값=10 일 때 compareAndSet(10 -> 11) = true,  지금 값 = 11
값=11 일 때 compareAndSet(10 -> 12) = false, 지금 값 = 11     <- 기대값이 틀려서 거부
```

<br/>

두 번째가 거부됐다. `10 이면` 이라는 조건이 이미 깨졌기 때문이다.

<br/>

이 `비교하고 -> 같으면 바꾸기` 가 CPU 명령어 하나로 실행된다.

그 사이에 다른 스레드가 끼어들 수 없다. 그래서 원자적이라고 하는 것이다.

<br/><br/>

## 실패하면 얼마나 다시 도나

원문에 `while 문으로 재시도한다` 고 적혀 있다. 그 횟수를 세어봤다.

```java
while (true) {
    int cur = v.get();
    if (v.compareAndSet(cur, cur + 1)) break;
    retries.incrementAndGet();                  // 실패했으니 센다
}
```

<br/>

스레드 4개가 50만 번씩.

```java
최종 값 = 2,000,000 (정답), CAS 실패 후 재시도 = 785,521 번
```

<br/>

200만 번 시도 중 78만 번이 첫 시도에 실패했다. 39%다.

<br/>

그런데 결과는 정확하고, 시간은 `synchronized` 의 1/3이었다.

```java
synchronized  = 186 ms
AtomicInteger =  67 ms
```

<br/>

앞의 동시성 문제 해결 방법 글에서 본 그 수치다.

<br/>

실패해도 잠들지 않고 그 자리에서 다시 하니, 앞의 context switch vs Context 글에서 잰 2µs 짜리 스위치가 한 번도 안 일어나는 것이다.

<br/><br/>

## 원문의 원자성 정의가 조금 어긋난다

```java
"두개 이상의 쓰레드가 동시에 호출 못한다는 것입니다"
```

<br/>

이건 상호 배제의 정의다. CAS는 오히려 반대로 동작한다.

<br/>

```java
상호 배제 - 한 번에 하나만 들어가게 막는다 (synchronized)
원자성    - 중간 상태가 관찰되지 않는다. 전부 되거나 전부 안 되거나
```

<br/>

CAS는 여러 스레드가 동시에 들어오는 것을 막지 않는다.

동시에 들어와서 동시에 시도하고, 하나만 성공하고 나머지는 실패를 알게 된다.

<br/>

`막아서 안전한 것` 과 `실패를 감지해서 안전한 것` 은 다른 방식이다.

CAS가 락 없이도 안전한 이유가 후자이기 때문이다.

<br/><br/>

## ABA 문제

CAS에는 알려진 구멍이 하나 있다.

```java
스레드 1: 값 A 를 읽는다.  잠깐 멈춤
스레드 2: A -> B 로 바꾼다
스레드 2: B -> A 로 다시 바꾼다
스레드 1: "A 이면 바꿔라" -> 성공한다. 그 사이 두 번 바뀐 것을 모른다
```

<br/>

값만 비교하니 `같은 값으로 돌아온 것` 과 `안 바뀐 것` 을 구분할 수 없다.

<br/>

정수 카운터에서는 문제가 안 된다. `10 -> 11 -> 10` 이어도 지금 10인 게 사실이니까.

<br/>

연결 리스트의 노드 참조처럼 `같은 주소지만 다른 객체` 가 올 수 있는 곳에서 문제가 된다.

노드를 빼고, 지우고, 같은 주소에 새 노드가 할당되는 경우다.

<br/>

해결은 버전 번호를 같이 비교하는 것이다.

```java
AtomicStampedReference<Node>
```

<br/>

`값 + 스탬프` 를 한 쌍으로 비교한다. 값이 같아도 스탬프가 다르면 실패한다.

<br/>

앞의 트랜잭션 글에서 본 낙관적 락의 `version` 컬럼과 같은 발상이다.

```java
UPDATE item SET stock = ?, version = version + 1
WHERE id = ? AND version = ?          <- 읽었을 때의 version 이어야 한다
```

<br/>

DB의 낙관적 락이 사실상 CAS인 것이다. `읽은 버전이면 바꿔라` 다.

<br/><br/>

## CAS 로 못 하는 것

변수 하나만 다룬다.

```java
if (balance >= amount) {
    balance -= amount;
}
```

<br/>

`balance` 를 읽어서 확인하고 빼는 두 단계를 하나로 못 묶는다.

`compareAndSet(balance, balance - amount)` 로 쓸 수는 있는데, `>= amount` 검사와 같이 원자적이지는 않다.

<br/>

여러 변수가 함께 바뀌어야 하면 락으로 간다.

<br/>

그래서 실무의 분업은 이렇다.

```java
AtomicInteger, AtomicLong     - 카운터 하나
AtomicReference               - 참조 하나를 통째로 교체
ConcurrentHashMap             - 안에서 CAS 와 synchronized 를 섞어 쓴다
synchronized / ReentrantLock  - 여러 값이 얽힌 것
```

<br/>

원문의 `ConcurrentHashMap 이 빈 버킷에는 CAS, 있으면 synchronized` 가 정확히 이 분업이다.

빈 자리에 넣는 것은 참조 하나 바꾸기라 CAS로 되고, 이미 있는 버킷을 고치는 것은 여러 노드가 얽혀서 락이 필요한 것이다.
