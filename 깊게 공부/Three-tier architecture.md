## Three-tier architecture / stored procedure


![이미지](/programming/img/입문449.PNG)


<br/>

## Presentation tier

- 사용자에게 보여지는 부분을 담당하는 tier

- html, javascript, css, native app 등등

<br/><br/>

## Logic tier

- 서비스와 관련된 기능과 정책 등등 비즈니스 로직을 담당하는 tier

    - e.g. 당근마켓의 비즈니스 로직

        - 회원 가입 / 탈퇴

        - 상품 리스트업 알고리즘

        - 상품 정보 업로드 기능

        - 상품 검색 기능

        - 메시지 기능

- application tier, middle tier 라고도 불린다

- java + spring, python + django 등등


<br/><br/>

## Data tier

- 데이터를 저장하고 관리하고 제공하는 역할을 하는 tier

- mysql, oracle, sql server, postgreSQL, mongoDB

    - e.g. 당근마켓의 데이터

        - 회원 정보

        - 상품 정보

        - 판매 / 구매 내역

        - 지역 정보

<br/><br/>

## Stored procedure를 사용한다는 것은?

- RDBMS에 저장되고 사용되는 절차이다.

- 주된 사용 목적은 비즈니스 로직 구현이다.

```java
"즉, Logic tier에서만이 아닌, 데이터 tier에서 비즈니스 로직이 존재할 수 있다는 것이다."
```

<br/><br/>

## stored procedure 장점

- `network traffic`을 줄여서 응답 속도를 향상시킬 수 있다.

    - 즉, network traffic이 한번만 발생 한다.

    - 이것이 가장 큰 장점이다.

    - 비즈니스 로직이 RDBMS에 있기에 가능.


<br/>

밑에 그림처럼, network traffic을 줄여서 응답 속도를 향상 시킬 수 있다는 것이다.

## stored procedure 단점 & 실무에서 쓰기에 조심스러운 이유

- `유지 보수 비용이 커진다`

    - 개발자들이 자바의 문법만 안다고 되는게 아니라, procedure 관련 문법도 알아야 된다.

- `DB 서버를 추가하는 것은 간단한 작업이 아니다`

    - 트래픽이 늘어나면 메모리가 초과 될 수도 있다.

        - 즉, procedure 는 서버들의 비즈니스 로직을 다 가지고 있으니
            
            할 일이 너무 많아져 메모리를 초과 할 수도 있다.
            
- `예상치 못한 문제의 영향을 최소화할 수 있다`
    - transparent 부분에서 예상치 못한 버그가 있었다면, 이전 버전으로 롤백 한다.

        - Logic tier에서 소스 코드를 통해서 비즈니스 로직을 관리 했다면? →
            
            `Logic tier`에서의 서버는 한대가 아니기 때문에 
            
            4대가 있다고 가정 한다면, 4분의 1만 피해를 본다는 뜻이 된다.

## 캐시를 써서 응답 속도를 향상 시킬 수 있다.

비즈니스 로직을 소스 코드에 두고도 응답 속도를 향상 시킬 수 있다

![이미지](/programming/img/입문452.PNG)

1. 만약, 같은 `id`의 호출에 대해서는 1차적으로 캐시에서 확인을 한다.

2. 확인하여 캐시에 있다면 → 그 정보를 바로 return 해주는 것이다.

```java
"응답 속도를 향상 시키면 DB 부하까지도 줄일 수 있는 장점이 있다."
```

그렇기에 어플리케이션과 디비 사이에 캐시를 두는 것은 좋은 선택인 것이다!

## Procedure 정리

- Procedure로는 복잡하고 유연한 코드를 작성하기는 어렵다

## 궁금증!

```java
3계층으로 나누면 실제로 무엇이 가능해질까?
```

`각 층을 따로 늘릴 수 있다` 는 것이 제일 큰 이득이다.

```java
Presentation tier - 브라우저, 앱
Logic tier        - 애플리케이션 서버
Data tier         - DB
```

<br/>

트래픽이 늘면 어느 층이 먼저 힘든지 보고 그 층만 늘린다.

```java
CPU 가 부족하다        -> 애플리케이션 서버를 늘린다 (쉽다)
DB 가 느리다          -> 복제를 붙이거나 스펙을 올린다 (어렵다)
```

<br/>

앞의 프로시저 글에서 본 판단이 여기서 나온다.

로직을 DB에 넣으면 `늘리기 어려운 층` 에 부하를 몰아넣는 셈이다.

```java
Logic tier - 서버를 열 대로 늘려도 상관없다. 상태가 없기 때문이다
Data tier  - 열 대로 못 늘린다. 데이터가 하나여야 하기 때문이다
```

<br/>

## 그래서 로직 계층은 무상태여야 한다

서버를 여러 대로 늘리려면, 어느 서버가 요청을 받아도 같은 결과가 나와야 한다.

<br/>

앞의 로그인 세션 글에서 본 문제가 정확히 이것이다.

```java
서버 A 에서 로그인 -> 세션은 A 메모리에만 있다
다음 요청이 B 로 가면 -> 로그인이 안 된 것으로 보인다
```

<br/>

세션은 상태다. 서버가 상태를 들고 있으면 무상태가 아니게 된다.

<br/>

그래서 상태를 밖으로 뺀다.

```java
세션을 Redis 에 저장한다  -> 어느 서버든 같은 곳을 본다
JWT 토큰을 쓴다          -> 서버가 아무것도 안 들고 있는다
```

<br/>

앞의 싱글톤 글에서 본 `스프링 빈에 상태를 두면 안 된다` 도 같은 이유다.

한 서버 안에서도, 여러 서버 사이에서도 같은 원칙이 적용된다.

<br/>

## 계층은 물리적 분리이고 레이어는 논리적 분리다

`tier` 와 `layer` 를 같은 말로 쓰는 경우가 많은데 원래는 다르다.

```java
tier  - 물리적으로 다른 머신에서 돈다
layer - 같은 프로세스 안의 논리적 구분
```

<br/>

스프링 애플리케이션 하나가 `Logic tier` 인데, 그 안에서 또 나뉜다.

```java
Controller - 웹 계층
Service    - 비즈니스 계층
Repository - 데이터 접근 계층
```

<br/>

앞의 MVC 글에서 본 그 구조가 `layer` 다. 전부 같은 JVM 안에서 돈다.

<br/>

## 의존 방향이 한쪽이어야 한다

층을 나눈 이득을 얻으려면 규칙이 하나 필요하다.

```java
Controller -> Service -> Repository        (O)
Repository -> Service                      (X)
```

<br/>

아래층이 위층을 알면 나눈 의미가 없어진다.

`Repository` 가 `HttpServletRequest` 를 알게 되면 웹 없이는 테스트도 못 한다.

<br/>

앞의 인터페이스 글에서 본 `구체적인 것을 알면 그게 바뀔 때마다 나도 바뀐다` 와 같은 얘기다.

<br/>

## 실제로 순환이 생기기 쉬운 곳

```java
@Service
class OrderService {
    private final PaymentService paymentService;
}

@Service
class PaymentService {
    private final OrderService orderService;     // 순환 참조
}
```

<br/>

같은 층 안에서 서로를 참조하는 경우다.

앞의 DI 글에서 본 대로, 생성자 주입이면 애플리케이션이 아예 안 뜬다.

<br/>

이때는 대개 `두 서비스가 공유하는 로직` 이 따로 있는 것이다.

그걸 별도 클래스로 빼거나, 앞의 `@EventListener` 글에서 본 이벤트로 방향을 끊는다.

```java
OrderService -> 이벤트 발행
PaymentService -> 이벤트 구독       (OrderService 를 모른다)
```

<br/>

## 요즘은 층이 더 늘어난다

```java
브라우저
  -> CDN (정적 파일)
  -> 로드 밸런서
  -> 애플리케이션 서버 (여러 대)
  -> 캐시 (Redis)
  -> DB (주 서버 + 복제 서버)
```

<br/>

기본 발상은 그대로다. `역할이 다르면 나누고, 나누면 따로 늘릴 수 있다` 는 것이다.

<br/>

층이 늘어날수록 네트워크 왕복도 늘어나서 응답이 조금씩 느려진다.

앞의 트레이드 오프 글의 관점으로 보면, 확장성을 얻는 대신 지연을 내주는 셈이다.
