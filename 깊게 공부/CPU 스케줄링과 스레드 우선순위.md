## CPU 스케줄링과 스레드 우선순위

<br/>

## 스케줄러가 하는 일

앞의 pcb는 무엇인가요 글에서 본 상태 분포가 있었다.

```java
712 S   <- 대기
  4 R   <- 실행 중이거나 실행 대기
```

<br/>

코어 10개에 준비된 것이 4개면 고민이 없다. 전부 돌리면 된다.

준비된 것이 코어보다 많을 때 `누구를 먼저 돌릴까` 를 정하는 것이 스케줄러다.

<br/><br/>

## 고전 알고리즘들

```java
FCFS   - 먼저 온 순서. 긴 작업 뒤의 짧은 작업이 오래 기다린다
SJF    - 짧은 작업 먼저. 평균 대기가 최소지만 얼마나 걸릴지 미리 알 수 없다
RR     - 시간을 잘라 돌아가며. 응답성이 좋다. 조각이 너무 짧으면 스위치 비용이 커진다
우선순위 - 높은 것 먼저. 낮은 것이 영원히 못 받을 수 있다 (기아)
```

<br/>

앞의 context switch vs Context 글에서 잰 스위치 2µs가 RR의 시간 조각을 정하는 기준이 된다.

조각이 1ms면 스위치 비용은 0.2%, 조각이 10µs면 20%다.

리눅스는 대략 몇 ms 단위로 잡는다.

<br/><br/>

## 실제 운영체제는 섞어 쓴다

```java
리눅스 CFS  - 각 스레드가 받은 CPU 시간을 기록하고, 가장 적게 받은 것부터 준다
              우선순위(nice)는 시간이 흐르는 속도에 가중치로 들어간다
macOS      - 우선순위 밴드를 나누고 그 안에서 시간 조각을 돌린다
```

<br/>

I/O를 기다리다 깨어난 스레드는 CPU를 거의 안 썼으니 앞줄에 선다.

키보드 입력을 처리하는 스레드가 계산 스레드보다 먼저 도는 이유다.

<br/><br/>

## 궁금증!

```java
자바의 Thread.setPriority() 가 실제로 먹히나
```

코어 10개에 스레드 20개를 만들어 CPU를 놓고 경쟁시켰다.

절반은 `MAX_PRIORITY`, 절반은 `MIN_PRIORITY` 다. 2초 동안 각자 몇 번 돌았는지 셌다.

<br/>

### 결과

```java
MAX_PRIORITY 그룹 총 반복 = 14,722,316,455
MIN_PRIORITY 그룹 총 반복 = 14,464,961,102   <- 1.02 배
```

<br/>

거의 차이가 없다. 2%다.

<br/>

우선순위를 최고와 최저로 벌렸는데 CPU를 받은 양이 같다.

이 운영체제에서 자바 우선순위는 사실상 무시된 것이다.

<br/><br/>

## 왜 안 먹히나

자바 우선순위는 1~10인데 운영체제마다 매핑이 다르다.

```java
리눅스  - 기본 설정에서 전부 같은 값으로 매핑된다. 무시
macOS  - 매핑은 되지만 스케줄러가 크게 반영하지 않는다
윈도우  - 어느 정도 반영된다
```

<br/>

리눅스는 `-XX:ThreadPriorityPolicy=1` 을 주고 root로 띄워야 반영된다. 실무에서 그렇게 안 한다.

<br/>

그래서 자바 문서도 우선순위를 `힌트` 라고 부른다.

`setPriority()` 에 의존하는 코드는 개발 컴퓨터에서 되는 것처럼 보이다가 서버에서 안 되는 것이다.

<br/><br/>

## 그럼 순서를 정하고 싶으면

애플리케이션 안에서 직접 정한다.

```java
PriorityBlockingQueue    - 큐에서 꺼내는 순서를 우선순위로
풀을 나눈다               - 급한 일 풀, 안 급한 일 풀. 앞의 스레드 풀 글의 격벽
크기를 다르게 준다         - 급한 풀에 스레드를 더 많이
```

<br/>

운영체제에게 부탁하는 대신 내가 통제할 수 있는 층에서 하는 것이다.

앞의 Reentrant Lock과 synchronized의 차이 글에서 본 공정 락도 같은 발상이다.

운영체제가 순서를 안 보장하니 `ReentrantLock(true)` 로 애플리케이션이 줄을 세운다.

<br/><br/>

## nice 는 프로세스 단위로 먹힌다

자바 스레드 우선순위는 안 먹히지만, 프로세스 우선순위는 먹힌다.

```java
$ nice -n 19 java -jar batch.jar       # 가장 낮은 우선순위로
$ renice -n 5 -p <pid>                 # 돌고 있는 것을 낮춘다
```

<br/>

앞의 pcb는 무엇인가요 글에서 본 `PRI`, `NI` 열이 이 값이다.

<br/>

같은 서버에서 배치와 API가 같이 돌면, 배치를 `nice 19` 로 띄워서 API 응답을 먼저 챙기는 데 쓴다.

낮추는 것은 누구나 되고 올리는 것은 root만 된다. 앞의 pcb 글에서 본 그 제한이다.

<br/><br/>

## 컨테이너에서는 CPU 를 나눠준다

```java
docker run --cpus=2         # 코어 2개 분량만
kubernetes resources.limits.cpu: "500m"    # 0.5 코어
```

<br/>

이건 우선순위가 아니라 할당량이다.

시간 조각을 재서 정해진 몫을 넘으면 그 컨테이너 전체를 다음 주기까지 멈춘다.

<br/>

`0.5 코어` 를 주면 100ms 주기 중 50ms만 돌고 50ms는 멈춘다.

이게 컨테이너에서 응답 시간이 튀는 원인이 되기도 한다.

CPU를 다 안 쓰는데 지연이 생기는 것이다.

<br/>

앞의 자바 가상머신(JVM) 글에서 본 대로 JVM은 `availableProcessors()` 로 이 제한을 읽어서 GC 스레드 수 등을 정한다.

제한을 안 걸면 호스트 코어 수를 전부 받아서 다른 컨테이너와 부딪힌다.

<br/><br/>

## 정리

```java
스케줄러는 준비된 것이 코어보다 많을 때 순서를 정한다
자바 setPriority() 는 대부분 무시된다. 실측 1.02 배
순서가 필요하면 큐, 풀 분리, 공정 락으로 애플리케이션이 직접 한다
프로세스 단위 nice 와 컨테이너 CPU 제한은 먹힌다
```
