## 인터페이스를 왜 사용하는가?

두가지 장점이 있다.

1. 인터페이스 중심의 설계를 통해 보다 명확한 프로그램 구성이 가능해 진다.

2. 서로 다른 객체에게 연관 관계를 부여하기 때문이다. (=다형성)
    - 즉, 업캐스팅이 가능하게 되는 것이다.

```
업캐스팅이란? 자식 객체를 부모 타입으로 해석하는 것이다.
```
<br/>

## 인터페이스와 다형성

```java
class SmartPhone implements Alarm, phone, Messanger {
    // 내부 생략 ..
}
```

`SmartPhone`은 알람 및 전화기, 또는 메신저 타입으로 해석(업캐스팅)될 수 있다.

<br/>

이렇게 하나의 객체가 다양한 타입으로 해석되는 것을 다형성이라고 한다.

```java
// 스마트폰 객체 생성
SmartPhone sp = new SmartPhone();

// 스마트폰을 다양하게 해석(업캐스팅 - 상위 타입으로 해석)
Alarm a = sp;     // 스마트폰은 알람이다.   (O)
phone p = sp;     // 스마트폰은 전화기이다. (O)
Messanger m = sp; // 스마트폰은 메신저이다. (O)
```

<br/>

## 궁금증!

```java
업캐스팅이 되면 뭐가 좋은 걸까? 그냥 그 클래스를 직접 쓰면 되는 것 아닌가?
```

`쓰는 쪽 코드를 안 고쳐도 되게` 만들기 위해서다.

주문할 때 카카오페이로 결제하는 코드를 인터페이스 없이 써보면 이렇게 된다.

```java
class OrderService {
    private final KakaoPay kakaoPay = new KakaoPay();

    void order(int amount) {
        kakaoPay.pay(amount);
    }
}
```

<br/>

여기에 토스 결제를 추가해달라는 요구가 들어오면 `OrderService` 를 뜯어고쳐야 한다.

필드도 바꾸고, `order()` 안도 바꾼다. 결제 수단이 늘어날 때마다 매번 그렇다.

<br/>

## 인터페이스를 끼우면 이렇게 바뀐다

```java
interface PayClient {
    void pay(int amount);
}

class OrderService {
    private final PayClient payClient;

    OrderService(PayClient payClient) {
        this.payClient = payClient;
    }

    void order(int amount) {
        payClient.pay(amount);       // 이 줄은 끝까지 안 바뀐다
    }
}

class KakaoPay implements PayClient {
    public void pay(int amount) {
        System.out.println("카카오페이로 " + amount + "원 결제");
    }
}

class TossPay implements PayClient {
    public void pay(int amount) {
        System.out.println("토스로 " + amount + "원 결제");
    }
}
```

<br/>

### 결과

```java
OrderService kakao = new OrderService(new KakaoPay());
kakao.order(10000);

OrderService toss = new OrderService(new TossPay());
toss.order(10000);
```

```java
카카오페이로 10000원 결제
토스로 10000원 결제
```

결제 수단이 몇 개가 늘어도 `OrderService` 는 한 글자도 안 바뀐다.

`OrderService` 는 `pay()` 를 부를 줄만 알지, 그게 카카오인지 토스인지는 아예 모르기 때문이다.

```java
구체적인 것을 알면 -> 그게 바뀔 때마다 나도 바뀐다
인터페이스만 알면 -> 뒤에서 뭐가 바뀌든 나는 그대로다
```

<br/>

## 테스트할 때 진가가 나온다

실제 결제를 붙여놓으면 테스트할 때마다 진짜 돈이 나간다.

인터페이스로 받아두면 가짜 구현을 하나 끼워넣으면 끝이다.

```java
class FakePay implements PayClient {
    public void pay(int amount) {
        System.out.println("테스트용 가짜 결제 " + amount + "원");
    }
}
```

```java
OrderService test = new OrderService(new FakePay());
test.order(10000);
```

```java
테스트용 가짜 결제 10000원
```

`OrderService` 를 테스트하려고 결제 서버를 띄울 필요가 없어지는 것이다.

<br/>

## 상속으로도 되지 않나?

부모 클래스를 두고 상속해도 업캐스팅은 된다. 그런데 두 가지가 걸린다.

<br/>

첫째, 자바는 클래스를 하나만 상속할 수 있다.

위의 `SmartPhone` 처럼 알람이면서 전화기이면서 메신저인 것은 상속으로는 못 만든다.

<br/>

둘째, 상속은 부모의 내부 구현까지 물려받는다.

부모가 필드를 하나 바꾸면 자식이 같이 깨질 수 있다. 이것을 결합도가 높다고 한다.

<br/>

인터페이스는 `무엇을 할 수 있는가` 만 정하고 `어떻게 하는가` 는 안 물려준다.

그래서 붙였다 뗐다 하기에는 인터페이스 쪽이 훨씬 가볍다.

```java
상속     -> "나는 무엇이다"     (is-a)
인터페이스 -> "나는 무엇을 할 수 있다" (can-do)
```

<br/>

스프링에서 `@Service` 를 인터페이스로 받고 구현체를 주입받는 구조가 딱 이것이다.

`OrderService` 가 `PayClient` 만 알고 있으면, 어떤 구현체를 넣을지는 스프링이 정해서 넣어준다.
