## CPU:

프로그램 코드가 실제로 실행되는 곳이다.

- 즉, 개발자가 작성한 프로그램이 있다면, 그 프로그램은 다른 관점으로 보면
    
    명령어들의 집합인 것이다. 그렇다면, 그 명령어들이 `CPU에 의해 실행`이 되는 것이다.
    
<br/><br/>

## Main memory(RAM):

실행 중인 프로그램의 코드들과 코드 실행에 필요한 혹은 그 결과로 나온 데이터들의 상주 하는 곳이다.

- 즉, 프로그램을 실제로 실행하게 되면 그 프로그램의 코드도 main memory에 있고,
    
    실행 전 데이터들과 실행 후 데이터들은 항상 main memory 에서 자리 잡고 있는 것이다.
    
- main memory는 `휘발성 메모리`라고도 불린다.
    - 이유는? → PC를 `OFF`하면 데이터가 날라가기 때문이다.

<br/><br/>

## Secondary storage(SSD or HDD):

프로그램과 데이터가 `영구적`(PC를 OFF해도 살아있음)으로 `저장`되는 곳이다.

실행 중인 프로그램의 데이터 일부가 임시 저장 되는 곳이다.

<br/>

### 데이터 일부가 임시 저장된다는 말은?

Main memory에서 데이터를 엄청나게 많아져 main memory에서 담지 못할 수도 있다. 

<br/>

그때, 담지 못하는 데이터들 중에서 `자주 사용되지 않는 애들은` Secondary storage으로 

내려서 여기서 `임시로 저장` 한다는 것이다. (스왑이라고 부른다.)

- 나중에 main memory가 필요하다고 하다면 그때 데이터를 올린다.

<br/><br/>

## Secondary storage 특징

- 데이터 베이스도 `Secondary storage`에 저장 된다.

- 데이터를 처리하는 속도가 느리다

- 데이터를 저장하는 용량이 가장 크다

- block 단위로 데이터를 `읽고 쓴다`

<br/><br/>

## block 이란?

`파일 시스템`이 데이터를 읽고 쓰는 논리적인 단위를 말한다

.e.g 밑에 있는 그림 처럼, 노란색 부분의 데이터를 읽어 오고 싶다면, 딱 저 데이터만 읽어올 수가 없다. 

<br/>

저 데이터를 포함하고 있는 블록의 남은 공간 마저 Main memory로 가져가게 되는 것이다. 

block안에 포함 된 필요 없는 데이터까지 전부 메인 메모리에서 가져가게 되는 것이다.

![이미지](/programming/img/입문516.PNG)

<br/>

## block의 단점은?

불필요한 데이터까지 읽어올 가능성이 있다.

## 궁금증!

```java
DB 를 공부하는데 왜 컴퓨터 시스템 이야기가 나올까?
```

DB의 설계 결정 대부분이 `디스크가 느리다` 는 사실에서 나오기 때문이다.

<br/>

각 저장 장치의 접근 시간을 비교하면 이렇다.

```java
CPU 레지스터    - 1 사이클 미만
L1 캐시         - 약 1 나노초
메모리          - 약 100 나노초
SSD            - 약 100 마이크로초   (메모리의 1000 배)
HDD            - 약 10 밀리초       (메모리의 10만 배)
```

<br/>

메모리와 디스크 사이에 수천 배에서 수만 배의 벽이 있다.

<br/>

## 그래서 DB 는 디스크 접근 횟수로 설계된다

앞의 B tree 글에서 본 판단이 여기서 나온다.

```java
이진 트리 - 비교 횟수는 적지만 디스크를 17 번 읽는다
B tree    - 비교는 더 하지만 디스크를 3~4 번 읽는다
```

<br/>

메모리에서 비교를 `1000` 번 더 하는 것보다 디스크 접근을 `1` 번 줄이는 쪽이 이득이다.

메모리 접근 `1000` 번이 `100` 마이크로초인데, 디스크 접근 `1` 번이 `100` 마이크로초이기 때문이다.

<br/>

## 페이지 단위로 읽는 것도 같은 이유다

디스크는 한 바이트만 읽을 수 없다. 한 덩어리씩 읽는다.

```java
InnoDB 페이지 크기 = 16 KB
```

<br/>

`4` 바이트짜리 `int` 하나가 필요해도 `16 KB` 가 통째로 올라온다.

<br/>

그러니 `이왕 올라온 김에 최대한 활용하자` 는 방향으로 설계가 간다.

앞의 B tree 글에서 본 `노드 하나를 페이지 크기에 맞춘다` 가 그 결론이다.

<br/>

앞의 배열 글에서 본 캐시 지역성 실험도 같은 원리다.

```java
행 먼저 (붙어 있는 순서대로) = 54 ms
열 먼저 (건너뛰면서)        = 282 ms
```

<br/>

읽는 값은 똑같은데 `가져온 덩어리를 얼마나 활용했는가` 로 다섯 배가 갈렸다.

<br/>

## 버퍼 풀이 존재하는 이유

디스크가 느리니 한 번 읽은 것은 메모리에 들고 있는다.

```java
innodb_buffer_pool_size = 서버 메모리의 70~80%
```

<br/>

DB 서버에 메모리를 많이 다는 이유가 이것이다.

자주 쓰는 데이터가 전부 메모리에 올라가 있으면 디스크를 거의 안 건드린다.

<br/>

앞의 DB 인덱스 글에서 `1000` 번 조회에 `37ms` 밖에 안 걸린 것도 이 덕분이다.

첫 번째만 디스크에서 읽고 나머지는 메모리에서 나왔다.

<br/>

## WAL 도 디스크 특성 때문에 나왔다

앞의 transaction 글에서 본 그 방식이다.

```java
COMMIT
  -> 로그 파일 끝에 순서대로 붙인다 (순차 쓰기, 빠르다)
  -> 데이터 파일은 나중에 천천히 반영한다 (임의 쓰기, 느리다)
```

<br/>

디스크는 `순서대로 쓰는 것` 과 `여기저기 흩어 쓰는 것` 의 속도가 크게 다르다.

HDD는 헤드를 움직여야 해서 수십 배 차이가 나고, SSD도 순차 쓰기가 더 빠르다.

<br/>

그래서 `빠른 방식으로 안전을 먼저 확보하고, 느린 정리는 미룬다` 는 구조가 나온 것이다.

<br/>

## 정리하면

```java
디스크가 느리다
  -> 접근 횟수를 줄여야 한다        -> B tree (낮은 트리)
  -> 한 번 읽은 것을 활용해야 한다   -> 페이지 단위, 캐시 지역성
  -> 한 번 읽은 것을 들고 있어야 한다 -> 버퍼 풀
  -> 순차 쓰기가 빠르다             -> WAL
```

<br/>

DB의 핵심 구조가 전부 이 한 문장에서 갈라져 나온 셈이다.
