## 타임아웃은 왜 반드시 걸어야 하나

<br/>

## 응답이 안 오면 얼마나 기다리나

```java
new Socket("10.255.255.1", 80);       // 타임아웃 없음
```

<br/>

운영체제 기본값만큼 기다린다. 리눅스는 약 2분, macOS는 75초다.

그동안 그 스레드는 아무것도 못 한다.

<br/><br/>

## 궁금증!

```java
타임아웃이 없으면 실제로 얼마나 묶이나
```

응답이 없는 주소(라우팅 불가 IP)에 접속을 시도했다.

<br/>

### 1. 타임아웃 없음

```java
5초 지났는데 스레드 살아 있나 = true
```

<br/>

5초를 기다렸는데 아직도 `connect` 안에 있다. 75초를 다 채울 것이다.

<br/>

### 2. connect 타임아웃 1초

```java
socket.connect(addr, 1000);
```

```java
1005 ms 만에 SocketTimeoutException: Connect timed out
```

<br/>

정확히 1초에 돌아왔다.

<br/>

### 3. 연결은 됐는데 응답을 안 주는 서버

```java
socket.setSoTimeout(1000);
socket.getInputStream().read();
```

```java
1002 ms 만에 read 타임아웃: Read timed out
```

<br/>

`connect` 는 성공했으니 `connect` 타임아웃은 아무 소용이 없다.

`read` 타임아웃을 따로 걸어야 한다.

<br/><br/>

## 타임아웃은 종류가 여럿이다

```java
connect timeout  - TCP 연결이 맺어지기까지
read timeout     - 연결 뒤 데이터가 안 올 때 (소켓 옵션 SO_TIMEOUT)
write timeout    - 보내는데 상대가 안 받아줄 때 (자바 소켓에는 없다. 별도 처리)
request timeout  - 요청 전체. connect + 여러 번의 read 합계
pool timeout     - 커넥션 풀에서 연결을 빌리기까지
```

<br/>

앞의 커넥션 풀 글에서 본 HikariCP의 `connectionTimeout` 이 마지막 것이다.

DB가 느린 게 아니라 풀에 빈 커넥션이 없어서 기다리는 시간이다.

<br/>

하나만 걸면 나머지에서 묶인다.

`RestTemplate`, `WebClient`, JDBC 드라이버 전부 이 값들을 따로 받는다.

<br/><br/>

## 안 걸면 무슨 일이 생기나

앞의 스레드 풀 글에서 본 톰캣 스레드 200개를 생각하면 된다.

```java
외부 API 가 응답을 안 준다 (죽은 게 아니라 느려진 것)
-> 요청마다 스레드 하나가 그 API 를 기다린다
-> 75초 × 초당 요청 수 = 묶이는 스레드 수
-> 200개가 전부 묶인다
-> 그 API 와 상관없는 요청도 스레드를 못 받는다
-> 내 서버가 죽은 것처럼 보인다
```

<br/>

외부 하나가 느려진 것이 내 서비스 전체의 장애가 된다. 장애 전파라고 한다.

<br/>

타임아웃이 3초였다면 묶이는 스레드가 25배 줄고, 3초 뒤에는 에러라도 돌려줄 수 있다.

`느린 실패` 보다 `빠른 실패` 가 낫다.

<br/><br/>

## 값을 얼마로 잡나

```java
그 호출이 정상일 때 걸리는 시간의 99% 지점 × 2~3
```

<br/>

평균이 아니라 99% 지점을 봐야 한다. 평균 50ms인 API가 가끔 500ms 걸리는 것은 정상이다.

500ms의 두세 배면 1~1.5초다.

<br/>

너무 짧으면 정상 요청을 실패로 만든다.

너무 길면 위의 장애 전파를 막지 못한다.

<br/>

앞의 재시도와 지수 백오프 글과 같이 봐야 한다. 타임아웃 뒤에 재시도하면 총 시간이 곱해진다.

```java
타임아웃 3초 × 재시도 3번 = 최악 9초
```

<br/>

이게 사용자가 기다릴 수 있는 시간 안이어야 한다.

<br/><br/>

## 타임아웃이 걸렸다고 요청이 취소되는 것은 아니다

```java
클라이언트: 3초 뒤 SocketTimeoutException. 포기하고 에러 응답
서버      : 아직 처리 중. 5초 뒤 결제 완료. 응답 보내는데 받는 사람이 없다
```

<br/>

클라이언트는 실패했다고 생각하고 서버는 성공했다.

앞의 체크 예외, 언체크(런타임) 예외 활용 글에서 본 `타임아웃은 성공했을 수도 있다` 가 이것이다.

<br/>

그래서 타임아웃 뒤 재시도는 멱등해야 한다.

앞의 요청 매핑 - API 예시 글에서 본 멱등 키가 여기서 필요해진다.

<br/><br/>

## 정리

```java
connect / read / pool 타임아웃을 전부 건다. 하나 빠지면 거기서 묶인다
값은 99% 지점의 2~3 배. 평균 기준으로 잡으면 정상을 실패로 만든다
타임아웃 × 재시도 횟수가 사용자 허용 시간 안이어야 한다
타임아웃 = 실패 확정이 아니다. 재시도는 멱등해야 한다
```

<br/>

`기본값을 믿지 않는다` 가 한 줄 요약이다.

기본값은 대개 `무제한` 이거나 `75초` 인데, 서비스에서 75초는 무제한과 같다.
