## ‘메모리에 적재’ / CPU의 연산

<br/>

## ‘메모리에 적재’ 에 대해서 설명해주세요

메모리는 CPU가 직접 접근할 수 있는 컴퓨터 내부의 기억장치 입니다.

program이 cpu에서 실행되려면 해당 내용이 memory에 적재된 상태여야만 합니다.

<br/>

프로그램이 하드디스크에 있을 때는 cpu가 직접 접근을 할 수 없지만 

메모리에 적재된 상태에서는 직접 접근을 해서 실행을 할 수 있는 상태가 됩니다.

<br/><br/>

## CPU의 연산하는 과정은?

어떤 코드를 읽어야 하는가를 정하는 것은 CPU 내부에 PC register에 저장되어 있습니다.

PC register에는 다음에 실행될 코드의 주소값이 저장되어 있습니다.

<br/>

즉, memory에 적재되어 있는 process code영역의 명령어 중 다음번 연산에서 

읽어야 할 명령어의 주소값을 PC register가 순차적으로 가리키게 되고, 

해당 명령어를 읽어와서 cpu가 연산을 하게 되면 process가 실행이 되는 것입니다.
<br/><br/>

## 궁금증!

```java
디스크에 있는 프로그램은 실제로 어떤 모습일까
```

컴파일한 클래스 파일을 바이트 단위로 열어봤다.

```java
$ xxd Hold.class | head -3

00000000: cafe babe 0000 0044 001a 0a00 0200 0307  .......D........
00000010: 0004 0c00 0500 0601 0010 6a61 7661 2f6c  ..........java/l
00000020: 616e 672f 4f62 6a65 6374 0100 063c 696e  ang/Object...<in
```

<br/>

그냥 바이트 덩어리다.

첫 네 바이트 `CA FE BA BE` 는 자바 클래스 파일임을 알리는 매직 넘버이고, 그 뒤로 상수 풀과 명령어가 이어진다.

<br/>

디스크에 있을 때는 이 상태로 그냥 놓여 있다.

CPU는 디스크에 직접 손을 뻗을 수 없으니, 이 바이트들을 메모리로 옮겨야 비로소 읽을 수 있게 되는 것이다.

<br/>

앞의 자바는 어떻게 실행되나요 글에서 본 `.class` 가 여기서 말하는 `적재되기 전의 프로그램` 이다.

<br/><br/>

## PC 레지스터가 가리키는 주소가 실제로 있나

`javap` 로 명령어를 꺼내보면 앞에 숫자가 붙어 있다.

```java
$ javap -c Hold

  0: aload_0
  1: invokespecial #1
  4: return

  0: ldc2_w        #7      // long 8000
  3: invokestatic  #9      // Thread.sleep
  6: return
```

<br/>

이 `0, 1, 4` 와 `0, 3, 6` 이 명령어의 위치다. 오프셋이라고 부른다.

<br/>

`aload_0` 은 1바이트라 다음이 `1` 이고, `invokespecial #1` 은 3바이트라 다음이 `4` 다.

명령어 길이만큼 주소가 앞으로 가는 것이 눈에 보인다.

<br/>

PC 레지스터는 이 숫자 중 하나를 들고 있다.

`지금 4번을 실행할 차례` 라고 기억하고 있다가, 실행하고 나면 다음 명령어 길이만큼 더해서 다음을 가리키는 것이다.

<br/>

JVM 안에서는 스레드마다 이 PC 레지스터를 하나씩 가진다.

앞의 자바 메모리 구조 글에서 본 `PC Register` 영역이 그것이다.

<br/><br/>

## 메모리에 있으면 다 같은 속도로 읽히나

이게 궁금해서 재봤다. 256MB 배열을 같은 횟수만큼 두 방식으로 읽었다.

```java
for (int i = 0; i < N; i++) sum += arr[i];          // 순서대로
for (int i = 0; i < N; i++) sum += arr[idx[i]];     // 무작위 순서로
```

<br/>

### 결과

```java
순서대로 읽기   =  49 ms
무작위로 읽기   = 324 ms     <- 같은 메모리, 같은 횟수인데 7배
```

<br/>

같은 메모리를 같은 횟수 읽었는데 7배가 갈린다.

<br/>

`메모리에 적재되면 CPU 가 직접 접근한다` 는 말이 틀린 것은 아닌데, 실제로는 그 사이에 캐시가 한 겹 더 있기 때문이다.

```java
CPU 레지스터  -> 1 사이클
L1 캐시       -> 몇 사이클
L2, L3 캐시   -> 수십 사이클
메인 메모리    -> 수백 사이클
디스크        -> 수백만 사이클
```

<br/>

CPU는 메모리에서 값 하나를 가져올 때 옆에 붙어 있는 것들을 한 줄(캐시 라인)로 같이 가져온다.

순서대로 읽으면 다음 값이 이미 캐시에 와 있어서 빠르고,

무작위로 읽으면 매번 메인 메모리까지 다시 다녀와야 해서 느린 것이다.

<br/>

건너뛰는 간격을 바꿔서 읽어보면 이 한 줄의 크기가 대충 보인다.

```java
 4 바이트씩 건너뛰기 : 46 ms
 8 바이트씩         : 28 ms
16 바이트씩         : 11 ms
32 바이트씩         :  5 ms
64 바이트씩         :  5 ms     <- 여기서부터 안 줄어든다
```

<br/>

읽는 개수는 절반씩 줄어드는데 시간은 어느 지점부터 안 줄어든다.

한 번 가져온 줄 안에서 몇 개를 읽든 비용이 같기 때문이다.

<br/>

앞의 선형 리스트 글에서 `ArrayList 가 LinkedList 보다 조회가 빠른 이유` 로 캐시를 얘기했었다.

노드가 메모리 여기저기에 흩어져 있으면 위의 `무작위로 읽기` 와 같은 상황이 되는 것이다.

<br/><br/>

## 정리하면 적재라는 말이 한 단계가 아니다

```java
디스크 -> 메모리 (운영체제가 한다. 프로세스 시작할 때)
메모리 -> 캐시   (CPU 가 알아서 한다. 읽을 때마다)
캐시 -> 레지스터 (명령어가 한다)
```

<br/>

`메모리에 적재되어야 실행된다` 는 첫 단계 얘기다.

거기서 끝나는 게 아니라, 실행되는 동안에도 계속 위로 끌어올리는 일이 반복되고 있다고 보면 된다.

앞의 자바 가상머신(JVM) 글에서 본 JIT 컴파일도 결국 `자주 쓰는 것을 더 위에 두려는` 같은 방향의 일이다.
