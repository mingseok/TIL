## 스레드 풀은 왜 쓰고 크기는 어떻게 정하나요?

<br/>

## 스레드 풀이란

스레드를 미리 만들어두고 일감이 오면 배정하고, 끝나면 없애지 않고 다음 일감을 기다리게 하는 것이다.

```java
ExecutorService pool = Executors.newFixedThreadPool(10);
pool.submit(작업);
```

<br/>

앞의 서블릿 글에서 본 톰캣이 요청을 이렇게 처리한다. 기본 200개다.

<br/><br/>

## 왜 매번 새로 만들지 않나

앞의 process를 설명해 주세요 글에서 잰 수치가 있다.

```java
스레드 100개 생성+종료 = 6 ms  (개당 0.06 ms)
```

<br/>

개당 0.06ms면 싸 보이지만, 초당 요청 1만 개면 0.6초가 스레드 만드는 데 든다.

그리고 만든 스레드는 스택 메모리를 잡는다. 기본 1MB씩이다.

<br/>

더 큰 이유는 상한이 없다는 점이다.

```java
요청마다 new Thread  -> 요청이 몰리면 스레드가 무한히 늘어난다 -> 메모리가 터진다
풀                  -> 최대 개수가 정해져 있다. 넘치면 줄을 세우거나 거절한다
```

<br/><br/>

## 궁금증!

```java
풀 크기를 얼마로 잡아야 하나
```

작업 성격을 둘로 나눠서 풀 크기별로 재봤다. 코어는 10개, 작업은 200개다.

<br/>

### CPU 작업 (각 작업 = 덧셈 2천만 번)

```java
풀   1 개 = 1381 ms
풀   5 개 =  282 ms
풀  10 개 =  183 ms     <- 코어 수
풀  20 개 =  178 ms
풀  50 개 =  184 ms
풀 200 개 =  213 ms     <- 오히려 느려진다
```

<br/>

코어 수까지는 줄고 그 뒤로는 안 준다. 200개로 가면 조금 느려진다.

<br/>

앞의 Multi process에 대해서 설명해 주세요 글에서 본 대로, 계산만 하는 일은 코어 수가 상한이다.

그 이상은 앞의 context switch vs Context 글에서 잰 스위치 비용만 더 든다.

<br/>

### I/O 작업 (각 작업 = 50ms 기다리기)

```java
풀   1 개 = 10729 ms
풀   5 개 =  2157 ms
풀  10 개 =  1075 ms
풀  20 개 =   540 ms
풀  50 개 =   221 ms
풀 200 개 =    73 ms     <- 계속 준다
```

<br/>

200개까지 계속 빨라진다. 작업 200개가 전부 동시에 기다리니 73ms에 끝난다.

<br/>

기다리는 동안 CPU를 안 쓰기 때문이다.

스레드 200개가 전부 `TIMED_WAITING` 이고 코어는 놀고 있다.

앞의 스레드의 상태 글에서 본 그 상태다.

<br/><br/>

## 그래서 공식이 있다

```java
스레드 수 = 코어 수 × (1 + 대기 시간 / 계산 시간)
```

<br/>

```java
계산만 한다 (대기 0)              -> 코어 수 × 1 = 10
계산 10ms, DB 대기 90ms           -> 10 × (1 + 9) = 100
계산 1ms, 외부 API 대기 99ms      -> 10 × (1 + 99) = 1000
```

<br/>

톰캣 기본 200개는 `요청 시간의 95%가 대기` 정도를 가정한 숫자인 셈이다.

<br/>

실무에서는 이 공식으로 시작점을 잡고 부하 테스트로 조정한다.

대기 시간이 얼마인지는 재봐야 알기 때문이다.

<br/><br/>

## 큐가 꽉 차면 어떻게 되나

풀에는 스레드 개수 외에 대기 큐가 있다.

```java
new ThreadPoolExecutor(2, 2, 0, SECONDS, new ArrayBlockingQueue<>(5));
```

<br/>

스레드 2개, 큐 5개에 작업 20개를 넣어봤다.

```java
받은 작업 = 7개 (실행 2 + 대기 5), 거절 = 13개  <- RejectedExecutionException
```

<br/>

7개까지만 받고 나머지 13개는 예외를 던졌다.

<br/>

거절 정책은 네 가지 중 고른다.

```java
AbortPolicy         - 예외를 던진다 (기본값)
CallerRunsPolicy    - 제출한 스레드가 직접 실행한다. 제출 속도가 자연히 느려진다
DiscardPolicy       - 조용히 버린다
DiscardOldestPolicy - 큐에서 제일 오래된 것을 버리고 넣는다
```

<br/>

`CallerRunsPolicy` 가 실무에서 자주 쓰인다.

앞의 생산자-소비자 문제와 배압 글에서 본 배압이 이걸로 생긴다.

일을 넘기는 쪽이 대신 일하게 되니 넘기는 속도가 저절로 처리 속도에 맞춰지는 것이다.

<br/><br/>

## Executors 가 만들어주는 풀들의 함정

```java
Executors.newFixedThreadPool(n)    - 스레드 n 개, 큐는 무제한
Executors.newCachedThreadPool()    - 스레드 무제한, 큐는 없음
Executors.newSingleThreadExecutor() - 스레드 1 개, 큐는 무제한
```

<br/>

`무제한` 이 문제다.

<br/>

`newFixedThreadPool` 은 큐가 무제한이라 작업이 몰리면 큐에 끝없이 쌓인다.

메모리가 차오르는데 예외는 안 나서, 한참 뒤에 `OutOfMemoryError` 로 터진다.

<br/>

`newCachedThreadPool` 은 스레드가 무제한이라 작업이 몰리면 스레드가 끝없이 늘어난다.

앞의 가상 스레드 글에서 본 `unable to create native thread` 가 여기서 난다.

<br/>

그래서 실무에서는 `ThreadPoolExecutor` 를 직접 만들어 둘 다 상한을 준다.

스프링의 `ThreadPoolTaskExecutor` 도 같은 이유로 `queueCapacity` 를 꼭 정하라고 한다.

<br/><br/>

## 풀을 나누는 이유

```java
DB 조회용 풀
외부 API 호출용 풀
파일 처리용 풀
```

<br/>

한 풀에 다 넣으면 하나가 느려질 때 전부 막힌다.

<br/>

외부 API가 응답을 안 주면 그 작업들이 스레드를 전부 쥐고 있어서, 아무 상관없는 DB 조회도 스레드를 못 받는다.

앞의 교착 상태(Deadlock) 글에서 본 `한 락이 막히면 전부 막힌다` 와 같은 모양이다.

<br/>

풀을 나누면 외부 API 풀만 막히고 나머지는 돈다.

격벽이라고 부른다. 배의 한 칸에 물이 들어와도 배가 안 가라앉게 칸을 나눈 것에서 온 말이다.

<br/><br/>

## 정리

```java
왜 쓰나    - 생성 비용을 아끼고, 개수에 상한을 두려고
크기       - 코어 수 × (1 + 대기/계산). 계산형은 코어 수, 대기형은 훨씬 크게
큐         - 반드시 상한을 둔다. Executors.newXxx 는 무제한이라 위험
거절       - CallerRunsPolicy 로 배압을 만드는 경우가 많다
분리       - 성격이 다른 일은 풀을 나눈다
```
