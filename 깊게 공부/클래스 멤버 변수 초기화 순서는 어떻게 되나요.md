## 클래스 멤버 변수 초기화 순서는 어떻게 되나요?

`static 변수 선언부` -> `필드 변수 선언부` -> `생성자 block`

1. `static 변수 선언부` : 클래스가 로드 될 때 변수가 제일 먼저 초기화 된다.

2. `필드 변수 선언부` : 객체가 생성될 때 생성자 block 보다 앞서 초기화 된다.
3. `생성자 block` : 객체가 생성될 때 가장 마지막에 실행된다.

<br/>

## 왜 이 순서인 것일까?

`static`은 클래스에 붙어 있고, 필드와 생성자는 객체에 붙어 있다.

클래스가 먼저 준비되어야 그 클래스로 객체를 찍어낼 수 있으니, 순서가 이렇게 될 수 밖에 없는 것이다.

```java
클래스 준비 (딱 한 번)  ->  객체 생성 (new 할 때마다)
```

그래서 `static` 쪽은 프로그램이 도는 동안 한 번만 실행되고,

필드와 생성자는 `new` 를 할 때마다 매번 다시 실행되는 것이다.

<br/>

## 그런데 초기화는 사실 두 번 일어난다

내가 적은 값이 들어가기 전에, JVM이 먼저 기본값으로 자리를 만들어 둔다.

- `int` -> `0`

- `boolean` -> `false`
- 참조형 -> `null`

메모리를 확보하면서 그 공간을 `0`으로 밀어버린다고 보면 된다.

그 다음에야 내가 적은 초기화식이 실행되어서 그 값을 덮어쓰게 되는 것이다.

```java
자리 만들기(기본값)  ->  내가 적은 값으로 덮어쓰기
```

<br/>

지역 변수는 초기화를 안 하면 컴파일 에러가 나는데, 필드는 초기화를 안 해도 그냥 쓸 수 있다.

이유가 바로 여기에 있다. 필드는 JVM이 기본값을 채워주지만,

지역 변수는 스택에 자리만 잡힐 뿐 아무도 채워주지 않기 때문이다.

<br/>

## 생각해보기 ex1)

출력 순서를 한번 맞춰보자.

```java
public class Main {
    public static void main(String[] args) {
        System.out.println("--- main 시작 ---");
        new Child();
        System.out.println("--- 두 번째 객체 ---");
        new Child();
    }
}

class Parent {
    Parent() {
        System.out.println("3. 부모 생성자");
    }
}

class Child extends Parent {

    static int staticField = log("1. static 필드 초기화식");

    static {
        log("2. static 초기화 블록");
    }

    int field = log("4. 인스턴스 필드 초기화식");

    {
        log("5. 인스턴스 초기화 블록");
    }

    Child() {
        log("6. 생성자 본문");
    }

    static int log(String message) {
        System.out.println(message);
        return 0;
    }
}
```

<br/>

### 결과

```java
--- main 시작 ---
1. static 필드 초기화식
2. static 초기화 블록
3. 부모 생성자
4. 인스턴스 필드 초기화식
5. 인스턴스 초기화 블록
6. 생성자 본문
--- 두 번째 객체 ---
3. 부모 생성자
4. 인스턴스 필드 초기화식
5. 인스턴스 초기화 블록
6. 생성자 본문
```

여기서 두 가지를 볼 수 있다.

부모가 있으면 내 필드보다 부모 생성자가 먼저 끼어든다는 것.

그리고 두 번째 객체를 만들 때는 `1번`, `2번`이 다시 실행되지 않는다는 것이다.

`static` 영역은 클래스가 로드될 때 이미 한 번 끝나버린 일이기 때문이다.

<br/>

## 컴파일러는 이 순서를 어떻게 만들어 두는가?

내가 적은 초기화식들이 실행 시점에 알아서 순서를 찾아가는 것이 아니다.

컴파일러가 이미 두 개의 메서드로 모아둔 상태로 `.class` 파일이 만들어진다.

- `<clinit>` : `static` 필드 초기화식 + `static` 블록을 모아둔 곳. 클래스 로딩 때 한 번 호출된다.

- `<init>` : 필드 초기화식 + 인스턴스 블록 + 생성자 본문을 모아둔 곳. `new` 할 때마다 호출된다.

위 `Child` 를 컴파일해서 `javap -c` 로 열어보면 이렇게 되어 있다.

```java
  Child();                                  // <init>
       1: invokespecial  Parent."<init>"    // 부모 생성자 먼저
       7: invokestatic   log                // 필드 초기화식
      10: putfield       field
      15: invokestatic   log                // 인스턴스 블록
      21: invokestatic   log                // 생성자 본문

  static {};                                // <clinit>
       2: invokestatic   log                // static 필드 초기화식
       5: putstatic      staticField
      10: invokestatic   log                // static 블록
```

생성자 본문에 아무것도 안 적었어도, 필드 초기화식과 인스턴스 블록이

이미 생성자 앞쪽에 끼워 넣어져 있다는 것을 볼 수 있다.

순서를 외우는 것이 아니라, 컴파일 시점에 이렇게 합쳐진다고 이해하면 편하다.

## 궁금증!

```java
"생성자는 JVM이 내부적으로 locking을 해서 thread-safe 하다"는 말은 맞을까?
```

아니다. 생성자에는 lock이 걸리지 않는다.

두 스레드가 동시에 `new` 를 하면 생성자 본문도 그냥 동시에 실행된다.

생성자 안에서 공유하는 값을 건드리면 동시성 문제는 똑같이 생기는 것이다.

<br/>

JVM이 lock을 잡는 쪽은 생성자가 아니라 `클래스 초기화` 쪽이다.

어떤 클래스의 `<clinit>` 이 실행되는 동안 다른 스레드가 그 클래스를 건드리면,

그 스레드는 초기화가 끝날 때까지 기다리게 된다.

```java
static 초기화 -> JVM이 클래스 단위로 락을 잡는다 (한 번만 실행되는 것을 보장)
생성자        -> 락 없음 (new 하는 만큼 동시에 실행된다)
```

<br/>

아래처럼 생긴 싱글턴이 `synchronized` 한 줄 없이도 안전한 이유가 이것이다.

```java
public class Singleton {

    private Singleton() {
    }

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

`getInstance()` 가 처음 불리는 순간에야 `Holder` 클래스가 로드되고,

그 초기화를 JVM이 락으로 지켜주기 때문에 `INSTANCE` 는 반드시 한 번만 만들어지는 것이다.

<br/>

## 생각해보기 ex2)

필드가 생성자보다 먼저 초기화된다는 것을 알고 나면, 이 코드의 결과도 예상이 된다.

```java
public class Main {
    public static void main(String[] args) {
        new Child();
    }
}

class Parent {
    Parent() {
        print();
    }

    void print() {
        System.out.println("부모의 print");
    }
}

class Child extends Parent {

    private String name = "민석";

    @Override
    void print() {
        System.out.println("이름 = " + name);
    }
}
```

<br/>

### 결과

```java
이름 = null
```

`민석` 이 아니라 `null` 이 나온다.

부모 생성자가 도는 시점은 아까 봤던 `3번` 이고, 자식의 `name` 이 채워지는 시점은 `4번` 이다.

부모 생성자가 `print()` 를 부를 때 자식의 `name` 은 아직 기본값 `null` 인 것이다.

<br/>

그런데 오버라이드 때문에 실제로 호출되는 것은 부모의 `print()` 가 아니라 자식의 `print()` 다.

아직 다 만들어지지도 않은 객체의 메서드를, 부모가 먼저 불러버린 셈이 되는 것이다.

```java
생성자에서 오버라이드 가능한 메서드를 호출하면 안 되는 이유
```
