## 프로시저(procedure)란?



데이터에 변경이 생겼을 때, 즉 DB에 `insert`, `update`, `delete`가 발생했을 때 

이것이 계기가 되어 자동적으로 실행되는 것을 프로시저를 의미합니다.

```java
'프로시저란?'
DB 내부에 저장된 일련의 SQL 명령문들을 하나의 함수처럼 실행하기 위한 쿼리의 집합
```

<br/>

여러 개의 컬럼을 조회하거나, 여러 개의 테이블을 조회하려고 할 때,

하나의 쿼리문으로 만들려면 복잡하고 긴 쿼리문이 생성한다.

이렇게, 긴 쿼리문을 사용하게 된다면 불편하기에 `프로시저`에 저장하여 호출한다.

<br/>

### 장점

- 하나의 요청으로 여러 SQL문을 실행시킬 수 있기 때문에 `네트워크 부하를 줄일 수 있다.`

- 특정한 기능을 변경 시 프로시저만 변경하면 되기에 기능 변경이 편리하다.

<br/>

### 단점

- 프로시저가 앱의 어디에 사용되는 지 확인이 어렵기에 유지보수가 어렵다.

- 문자나 숫자 연산에 프로시저를 사용하면 오히려 `C나 JAVA보다 처리 성능이 느리다.`
<br/>

## 궁금증!

```java
첫 문단에 있는 "insert, update, delete 가 계기가 되어 자동 실행" 은 트리거 아닌가?
```

맞다. 그 설명은 트리거의 정의다. 프로시저는 자동으로 실행되지 않는다.

```java
프로시저 - 내가 CALL 로 직접 부른다
트리거   - DB 가 알아서 부른다
```

<br/>

이 차이가 앞의 트리거 글에서 본 `보이지 않아서 위험하다` 는 문제로 이어진다.

프로시저는 부르는 코드가 어딘가에 있으니 추적이 되지만, 트리거는 안 보인다.

<br/>

## 프로시저를 만들고 불러보면

```sql
CREATE PROCEDURE transfer(IN from_id INT, IN to_id INT, IN amount INT)
BEGIN
    START TRANSACTION;
    UPDATE account SET balance = balance - amount WHERE id = from_id;
    UPDATE account SET balance = balance + amount WHERE id = to_id;
    COMMIT;
END;
```

```sql
CALL transfer(1, 2, 5000);
```

<br/>

`CALL` 로 명시적으로 부른다. 이게 트리거와 다른 점이다.

<br/>

## 원문의 장점을 다시 보면

`네트워크 부하를 줄일 수 있다` 가 원래 가장 큰 이유였다.

```java
애플리케이션에서 처리
  -> SELECT 로 데이터를 가져온다 (네트워크 왕복 1)
  -> 자바에서 계산한다
  -> UPDATE 를 날린다 (네트워크 왕복 2)
  -> 또 SELECT (왕복 3)
  ... 왕복이 계속 늘어난다

프로시저로 처리
  -> CALL 한 번 (네트워크 왕복 1)
  -> 나머지는 전부 DB 안에서
```

<br/>

네트워크가 느리고 서버 성능이 부족하던 시절에는 이 차이가 컸다.

<br/>

그런데 지금은 상황이 다르다.

```java
네트워크가 빨라졌다 (같은 데이터센터면 왕복 1ms 미만)
애플리케이션 서버는 늘리기 쉽다 (여러 대로 확장)
DB 는 늘리기 어렵다 (보통 한 대. 늘려도 복제일 뿐)
```

<br/>

부하를 DB로 몰아넣으면, 정작 늘리기 어려운 쪽이 먼저 한계에 부딪힌다.

<br/>

## 그래서 요즘은 잘 안 쓴다

원문의 단점에 몇 가지를 더 붙이면 이렇다.

```java
버전 관리가 안 된다   - DB 안에 있으니 git 에 안 들어간다. 누가 언제 고쳤는지 모른다
테스트가 어렵다      - 단위 테스트를 쓸 수가 없다. DB 를 띄워야 한다
이식성이 없다        - MySQL 문법과 Oracle 문법이 다르다. DB 를 바꾸면 다시 짜야 한다
디버깅이 어렵다      - IDE 지원이 약하고 중단점을 걸기 힘들다
확장이 안 된다       - 서버는 늘려도 DB 는 못 늘린다
```

<br/>

특히 `버전 관리가 안 된다` 가 크다.

앞의 트리거 글에서 본 문제와 같다. 소스 코드에 없는 로직이 있으면 파악이 안 된다.

<br/>

요즘은 프로시저를 쓰더라도 그 정의를 파일로 관리하고 마이그레이션 도구로 적용한다.

```java
db/migration/V3__create_transfer_procedure.sql
```

<br/>

이렇게 해두면 최소한 git 에는 남는다.

<br/>

## 그래도 쓸 만한 경우

`대량 데이터를 옮기거나 집계할 때` 는 여전히 프로시저가 낫다.

```java
1000 만 건을 애플리케이션으로 가져와서 계산 -> 네트워크와 메모리가 견디지 못한다
DB 안에서 처리 -> 데이터가 움직이지 않는다
```

<br/>

야간 배치로 통계를 만드는 작업이 대표적이다.

데이터를 밖으로 안 꺼내는 것이 훨씬 빠르다.

<br/>

앞의 프로시저와 트리거를 나누는 기준을 정리하면 이렇다.

```java
비즈니스 로직        -> 애플리케이션에 (버전 관리, 테스트, 확장)
대량 데이터 처리      -> 프로시저를 고려할 만하다
어떤 경로로든 지켜야 할 규칙 -> 트리거 (최후의 수단)
```
