## 가비지 컬렉션(G.C)가 무엇인가요?

GC는 JVM에서 메모리를 관리해주는 모듈입니다.

<br/>

## 크게 두가지로 나눌 수 있다

- `Minor GC`

    - `Heap` 영역의 `Young Generation`에서 발생하는 `GC`를 말한다

- `Major GC`

    - `Heap` 영역의 `Old Generation`에서 발생하는 `GC`를 말한다

앞으로 사용되지 않는 객체의 메모리를 `'Garbage'`라고 부른다

- 이런 `'Garbage'`를 정해진 스케줄에 의해 정리해주는 것을 `'GC'`라 부른다

<br/>

## GC가 왜 필요하지?

GC는 메모리 관리 기법 중 하나이다.

```java
프로그램이 "동적으로 할당했던 메모리 영역" 중 "필요 없게 된 영역"을 알아서 해제한다
```

위의 `“동적으로 할당했던 메모리 영역”` 은 → `Heap` 영역 메모리를 뜻하고

`“필요 없게 된 영역”` 은 → 어떤 변수도 가리키지 않게 된 영역을 의미한다

<br/>

### GC의 장점은?

- 개발자의 실수로 인한 메모리 누수를 막을 수 있다

- 해제된 메모리에 접근하는 오류를 막을 수 있다
- 해제된 메모리를 또 해제하는 이중 해제 또한 막을 수 있다

<br/>

### GC의 단점은?

- GC 작업은 순수 오버헤드

- 개발자는 언제 GC가 메모리를 해제하는지 모른다

<br/>

## 'GC' 를 제대로 이해하기 위해서는?

`‘Stop The World’` 를 이해 해야 한다.

- GC를 수행하기 위해 `JVM`이 멈추는 현상을 말한다

- GC가 작동하는 동안 GC관련 `Thread`를 제외한 모든 `Thread`는 멈춘다
- 일반적으로 `‘튜닝’`이라는 것은 이 시간을 최소화하는 것을 의미한다

```java
모든 쓰레드들의 작업을 중단 후 (Stop The World 과정) 
사용하지 않는 메모리를 제거(Mark and Sweep 과정)하고 작업이 재개됩니다.
```

<br/>

## GC의 종류로는?

- Serial GC

- Parallel GC → 자바 8버전에서 사용
- CMS GC
- G1 GC → 자바 9버전, 10버전 부터 사용 (디폴트)
- Z GC

```java
그럼, 이중에서 뭘 선택해야 하는데?
- 나의 어플리케이션에 서비스 특성에 맞는 GC를 선택하는것이 옳다
```

<br/>

## 궁금증!

```java
"어떤 변수도 가리키지 않게 된 영역" 이라고 했는데, 그걸 어떻게 알아낼까?
```

일일이 세어보는 것이 아니다. 반대로 `살아 있는 것부터 찾는다`.

<br/>

`GC Root` 라고 부르는 확실한 시작점들이 있다.

- 실행 중인 스레드의 스택 (지역 변수, 매개 변수)

- `static` 변수
- JNI로 넘긴 참조

<br/>

여기서 출발해서 참조를 타고 갈 수 있는 객체는 전부 `살아 있음` 으로 표시한다.

한 바퀴 다 돌고 나서 표시가 안 된 것들이 곧 쓰레기다.

```java
쓰레기를 찾는 게 아니라 -> 산 것을 찾고 -> 나머지를 전부 쓰레기로 본다
```

<br/>

이 방식을 `도달 가능성(Reachability)` 이라고 한다.

객체 A가 B를 가리키고 B가 A를 가리키는 순환 참조여도, 밖에서 아무도 A와 B를 안 가리키면 둘 다 쓰레기가 된다.

참조 개수를 세는 방식이었다면 이 둘을 영영 못 치웠을 것이다.

<br/>

## Mark and Sweep은 이 과정이다

원문에 이름만 나온 그 과정을 풀어보면 이렇다.

```java
Mark   : GC Root 에서 출발해 도달 가능한 객체에 표시를 한다
Sweep  : 표시가 안 된 객체를 치운다
Compact: 치우고 남은 것들을 앞쪽으로 몰아 붙인다
```

<br/>

`Compact` 가 필요한 이유는 치우고 나면 빈 칸이 군데군데 생기기 때문이다.

전체 여유 공간은 충분한데 연속된 자리가 없어서 큰 객체를 못 만드는 상황이 생긴다.

<br/>

앞에서 본 `Young` 영역은 `Compact` 를 따로 안 한다.

산 것만 빈 `Survivor` 로 통째로 옮기고 나머지를 비워버리니, 옮기는 것 자체가 정리가 되기 때문이다.

<br/>

## Stop The World를 눈으로 보기

`-Xlog:gc` 를 켜면 멈춘 시간이 그대로 찍힌다.

```java
[0.021s][info][gc] GC(0) Pause Young (Normal) 35M->1M(64M) 0.370ms
[0.024s][info][gc] GC(1) Pause Young (Normal) 30M->1M(64M) 0.189ms
```

<br/>

`Pause` 라고 적힌 것이 멈춘 구간이고, 뒤의 `0.370ms` 가 멈춘 시간이다.

`35M -> 1M` 은 GC 전후의 사용량이다.

<br/>

`Young` 쪽은 이렇게 밀리초도 안 걸린다. 문제는 `Old` 까지 훑을 때다.

힙이 크면 `Old` 를 한 번 훑는 데 수백 밀리초에서 초 단위까지 걸린다.

<br/>

```java
튜닝이란 = 이 Pause 줄을 짧게, 그리고 드물게 만드는 일
```

<br/>

## GC가 있어도 메모리 누수는 난다

`개발자의 실수로 인한 메모리 누수를 막을 수 있다` 고 했는데, 완전히 막아주지는 않는다.

GC는 `아무도 안 가리키는 것` 만 치우기 때문에, 계속 가리키고 있으면 손을 못 댄다.

```java
public class Leak {
    static final List<byte[]> CACHE = new ArrayList<>();   // static 이라 끝까지 산다

    public static void main(String[] args) {
        int count = 0;
        while (true) {
            CACHE.add(new byte[1024 * 1024]);
            count++;
            if (count % 10 == 0) {
                System.gc();                                // GC를 불러도
                System.out.println(count + "MB 담김 / 사용 중 = " + used() + "MB");
            }
        }
    }
}
```

<br/>

### 결과

```java
$ java -Xmx64m Leak

10MB 담김 / 사용 중 = 21MB
20MB 담김 / 사용 중 = 41MB
30MB 담김 / 사용 중 = 61MB
java.lang.OutOfMemoryError: Java heap space
```

<br/>

`System.gc()` 를 계속 불렀는데도 사용량이 줄지 않고 그대로 쌓여서 결국 터진다.

`CACHE` 가 `static` 이라 `GC Root` 에서 계속 도달 가능하기 때문이다.

<br/>

GC 입장에서는 이것들이 전부 `쓰는 중인 객체` 다. 개발자만 아는 `이제 안 쓸 것` 을 구분해줄 방법이 없다.

```java
GC가 막아주는 것   -> 다 쓴 객체를 안 지워서 생기는 누수
GC가 못 막는 것    -> 다 썼는데도 참조를 놓지 않아서 생기는 누수
```

<br/>

실무에서 나는 메모리 누수는 대부분 뒤쪽이다.

`static` 컬렉션에 계속 담기, 리스너를 등록만 하고 해제 안 하기, 캐시에 만료 시간을 안 두기 같은 것들이다.

<br/>

## GC 종류는 결국 무엇을 포기하느냐의 차이다

원문의 목록에 기준을 붙이면 이렇게 정리된다.

```java
Serial GC   - 스레드 하나로 청소. 단순하지만 멈춤이 길다. CPU 하나짜리 환경용
Parallel GC - 여러 스레드로 청소. 전체 처리량이 높다. 대신 멈춤은 여전히 길다
G1 GC       - 힙을 잘게 나눠 쓰레기 많은 구역부터 청소. 멈춤 시간을 목표치에 맞춘다
ZGC         - 대부분의 작업을 애플리케이션과 같이 돈다. 힙이 커도 멈춤이 밀리초 수준
```

<br/>

고르는 기준은 `처리량` 과 `멈춤 시간` 중 무엇이 더 중요한가다.

<br/>

배치 작업처럼 총 걸린 시간만 중요하면 `Parallel` 이 낫다. 중간에 좀 멈춰도 상관없다.

API 서버처럼 응답 시간이 중요하면 `G1` 이나 `ZGC` 가 낫다. 총 처리량은 조금 손해 봐도 멈춤이 짧아야 한다.

<br/>

지금 어떤 GC로 돌고 있는지는 이렇게 확인한다.

```java
$ java -XX:+PrintFlagsFinal -version | grep UseG1GC
bool UseG1GC = true
```

`Java 9` 부터 기본이 `G1` 이다. 원문에 적힌 대로다.
