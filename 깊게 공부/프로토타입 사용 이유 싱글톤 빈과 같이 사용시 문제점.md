## 프로토타입 사용 이유 / 싱글톤 빈과 같이 사용시 문제점

<br/>

## 프로토타입 사용 이유

사용자의 요청이 있을 때마다 매번 관련 있는 빈을 새로 생성하는 것은 비효율적이기 때문이다.

```java
때로는 빈을 싱글톤이 아닌 하나의 빈으로 "여러개의 객체를 만들어 사용"해야 할 때가 있다.
```

<br/>

프로토타입 빈은 컨테이너에게 빈을 요청할 때마다 매번 새로운 객체를 생성하여 반환해준다.



프로토타입은 싱글톤 타입의 스프링 빈과는 다르게 `빈 생성` → `의존관계 주입` → `초기화`까지만 관여 한다. 

<br/>

그 이후 스프링 빈을 클라이언트에 반환 했다면, 관리하지 않기에 

소멸 메서드 같은 것은 모두 클라이언트에서 관리해야 한다.

```java
"즉, 스프링 컨테이너가 그 주입된 프로토타입 빈을 관리하지 않는다"
```

<br/><br/>

## 프로토타입 빈의 특징 정리

- 스프링 컨테이너에 요청할 때마다 새로 생성된다.

- 스프링 컨테이너는 `빈의 생성`과 `의존관계 주입`, `초기화`만 관여한다.

- 종료 메소드가 호출되지 않는다.

- 프로토타입 빈은 해당 빈을 조회한 클라이언트가 관리해야 한다

<br/><br/>

## 싱글톤 빈에서 프로토타입 빈을 참조하는 경우

이 경우 문제가 발생할 수 있다.

싱글톤 빈의 인스턴스는 단 한번만 생성되고, 

그 때 프로토타입 빈의 주입도 이미 완료 되어 있는 상태이다

<br/>

그렇기 때문에, 싱글톤 빈 안의 프로토타입은 

주입 되고 나서, 인스턴스가 새로 생성되지 않는다는 것이다.

<br/>

이렇게 싱글톤 빈에서 프로토타입 빈을 참조할 때는 

인스턴스가 업데이트 되도록 해야 한다. → 어떻게? proxyMode 설정

<br/><br/>

## 업데이트 문제 해결 - proxyMode 설정

가짜 프록시 클래스를 만들어서 주입 시켜주는 것이다.

Proxy를 쓴다는 것은 대상 빈을 proxy로 감싼다는 것이다.

```java
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class MyLogger {
```

<br/>

proxyMode 속성은 설정하지 않으면 기본값을 `scopedProxyMode.DEFAULT`이다.

`DEFAULT`는 proxy를 사용하지 않는다는 옵션이고 proxy를 사용하려면 

클래스인 경우 `TARGET_CLASS`, 인터페이스일 경우 `INTERFACES`로 설정한다.

- `scopedProxyMode.DEFAULT` : Proxy를 사용하지 않음

- `scopedProxyMode.TARGET_CLASS` : Proxy를 사용한다 (클래스)

- `scopedProxyMode.INTERFACES` : Proxy를 사용한다 (인터페이스)

```java
"가짜 프록시 객체는 요청이 오면 그제서야 내부에 진짜 빈을 요청하는 것이다."
실제 사용할 시점이 되면, 그때 가져온다
```

<br/><br/>

## 그래서 왜 쓰는데?

프록시 객체 덕분에 클라이언트는 마치 싱글톤 빈을 사용하듯이 편리하게 `request scope`를 사용할 수 있다.

`Provider`를 사용하든, `프록시`를 사용하든 핵심은 진짜 객체 조회를 꼭 필요한 시점까지 지연처리 한다는 점이다.

```java
단지 애노테이션 설정 변경만으로 원본 객체를 프록시 객체로 대체할 수 있다.
```

<br/><br/>

## 웹 스코프의 특징

- 웹 스코프는 웹 환경에서만 동작한다.

- 웹 스코프는 스프링이 해당 스코프의 종료 시점까지 빈을 관리한다.
    
    따라서 종료 메소드가 호출된다.
    

<br/><br/>

## 웹 관련 스코프

- `request:` HTTP 요청 하나가 들어오고, 나갈 때까지 유지되는 스코프이다.
    
    각각의 `HTTP 요청`마다 별도의 빈 인스턴스가 생성되고, 관리된다.
    
    - e.g.) 동시에 여러 HTTP 요청이 오면 정확히 어떤 요청이 남긴 로그인지 구분하기 어렵다.
        
        이럴 때 사용하기 좋은 게 `request scope` 이다.
        
- `session:` 웹 세션이 생성되고 종료될 때까지 유지되는 스코프

- `application:` 웹의 서블릿 컨텍스트와 같은 범위로 유지되는 스코프

```java
- request 스코프
```

## 궁금증!

```java
"인스턴스가 새로 생성되지 않는다" 는 것을 직접 확인해보자
```

장바구니를 프로토타입으로 만들고, 싱글톤 빈이 그것을 필드로 갖게 해봤다.

```java
@Bean
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
Cart cart() { return new Cart(); }

class BadClient {
    final Cart cart;                       // 주입받아서 계속 들고 있는다

    BadClient(Cart cart) { this.cart = cart; }

    void add() { cart.add(); }
    int count() { return cart.count(); }
}
```

<br/>

### 결과

```java
--- 프로토타입 빈을 직접 꺼내면 ---
  a == b : false

--- 싱글톤이 프로토타입을 필드로 갖고 있으면 ---
  두 번 담은 뒤 개수 = 2
  다시 꺼내도 같은 카트 = true
```

<br/>

컨테이너에서 직접 꺼내면 매번 다른 객체가 나온다. 프로토타입이 맞다.

그런데 싱글톤 빈이 들고 있는 `cart` 는 계속 같은 객체다.

<br/>

이유는 시점 문제다.

```java
컨테이너가 뜰 때 -> BadClient 를 만든다 -> 그때 Cart 를 한 번 주입받는다 (여기서 끝)
그 뒤로는       -> BadClient 가 하나뿐이니 그 안의 Cart 도 하나뿐이다
```

<br/>

주입은 딱 한 번 일어나는 일이고, 프로토타입은 `요청할 때마다 새로 준다` 는 뜻이다.

요청을 한 번밖에 안 했으니 새로 받을 일도 없는 것이다.

<br/>

사용자 A의 장바구니에 담은 것이 사용자 B에게도 보이는 사고가 이렇게 난다.

원문의 `싱글톤 빈 안의 프로토타입은 인스턴스가 새로 생성되지 않는다` 가 이 모습이다.

<br/>

## ObjectProvider로 바꾸면

객체를 받아두는 대신, `필요할 때 달라고 부탁할 수 있는 창구` 를 받아두면 된다.

```java
class GoodClient {
    private final ObjectProvider<Cart> provider;

    GoodClient(ObjectProvider<Cart> provider) {
        this.provider = provider;
    }

    int addAndCount() {
        Cart cart = provider.getObject();    // 부를 때마다 새로 받는다
        cart.add();
        return cart.count();
    }
}
```

<br/>

### 결과

```java
  첫 번째 카트 개수 = 1
  두 번째 카트 개수 = 1
```

<br/>

두 번 불렀는데 둘 다 `1` 이다. 매번 새 카트를 받았다는 뜻이다.

`BadClient` 에서 `2` 가 나왔던 것과 비교된다.

<br/>

`ObjectProvider` 는 주입 시점에 객체를 받는 것이 아니라, `getObject()` 를 부르는 시점에 받는다.

주입 시점과 사용 시점을 떼어놓은 것이다.

```java
Cart 를 주입받는다             -> 주입 시점에 딱 한 번 받는다
ObjectProvider<Cart> 를 받는다 -> 쓰는 시점마다 새로 받는다
```

<br/>

## proxyMode 는 다른 방식으로 같은 문제를 푼다

원문에 나온 `proxyMode` 는 코드를 안 바꾸고 해결하는 방법이다.

```java
@Bean
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
Cart cart() { return new Cart(); }
```

<br/>

이렇게 하면 주입되는 것이 진짜 `Cart` 가 아니라 CGLIB 프록시다.

앞의 AOP 글에서 본 그 프록시와 같은 방식으로 만들어진다.

<br/>

프록시는 메서드가 불릴 때마다 컨테이너에게 진짜 `Cart` 를 새로 달라고 해서, 그쪽으로 넘긴다.

```java
cart.add() 호출
  -> 프록시가 가로챈다
  -> 컨테이너에게 Cart 를 새로 요청한다
  -> 받은 진짜 Cart 의 add() 를 부른다
```

<br/>

쓰는 쪽 코드는 `Cart cart` 그대로다.

`ObjectProvider` 처럼 코드를 고칠 필요가 없다는 것이 장점이다.

<br/>

대신 진짜 객체가 아닌 것이 주입되어 있어서, 디버깅할 때 헷갈릴 수 있다.

```java
ObjectProvider -> 코드가 명시적이다. 새로 받는다는 게 눈에 보인다
proxyMode      -> 코드가 안 바뀐다. 대신 뒤에서 일어나는 일이 안 보인다
```

<br/>

## 그런데 프로토타입은 잘 안 쓴다

실무에서 프로토타입 스코프를 쓰는 경우는 드물다.

요청마다 다른 상태가 필요하면 대개 이 둘 중 하나로 해결되기 때문이다.

<br/>

### 첫번째) 그냥 지역 변수로 만든다

```java
public void order(List<Item> items) {
    Cart cart = new Cart();       // 빈으로 만들 이유가 없다
    items.forEach(cart::add);
}
```

<br/>

의존성 주입이 필요 없는 단순한 객체라면 `new` 가 제일 간단하다.

빈으로 만드는 이유는 `무언가를 주입받아야 할 때` 인데, 장바구니는 그럴 일이 없다.

<br/>

### 두번째) 웹 스코프를 쓴다

요청 단위로 살아야 한다면 `request` 스코프가 더 정확하다.

```java
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
```

<br/>

요청이 시작될 때 만들어지고 응답이 끝나면 없어진다.

로그 추적기처럼 `한 요청 안에서만 공유되어야 하는 것` 에 맞는다.

```java
singleton  - 애플리케이션에 하나 (기본값)
prototype  - 요청할 때마다 새로. 만든 뒤로는 컨테이너가 관리하지 않는다
request    - HTTP 요청 하나마다 새로. 요청이 끝나면 소멸 콜백까지 불린다
session    - 사용자 세션마다 새로
```

<br/>

원문의 `종료 메소드가 호출되지 않는다` 는 프로토타입에만 해당한다.

`request` 스코프는 요청이 끝나는 시점을 컨테이너가 알기 때문에 소멸 콜백도 정상적으로 불린다.
