## 시스템 콜과 유저 모드, 커널 모드

<br/>

## CPU 는 두 가지 모드로 돈다

```java
유저 모드 - 일반 프로그램이 도는 모드. 할 수 있는 명령이 제한된다
커널 모드 - 운영체제가 도는 모드. 모든 명령을 쓸 수 있다
```

<br/>

일반 프로그램은 파일을 직접 못 읽는다. 디스크에 명령을 내리는 것은 커널 모드 명령이기 때문이다.

그래서 운영체제에 부탁한다. 그 부탁이 시스템 콜이다.

```java
프로그램 : "이 파일 읽어줘"  (유저 모드)
   -> 시스템 콜 -> 커널 모드로 전환
운영체제 : 디스크에 명령, 결과를 프로그램 메모리에 복사
   -> 유저 모드로 복귀
프로그램 : 결과를 받아 이어서 실행
```

<br/><br/>

## 왜 나눠놨나

프로그램 하나가 잘못 짜여도 컴퓨터 전체가 죽지 않게 하려는 것이다.

```java
프로그램이 디스크에 직접 쓸 수 있으면  -> 버그 하나로 파일 시스템이 깨진다
프로그램이 남의 메모리에 직접 쓸 수 있으면 -> 앞의 process 글에서 본 격리가 깨진다
```

<br/>

앞의 pcb는 무엇인가요 글에서 본 `PCB 는 커널 영역에 있다` 도 같은 이유다.

프로세스가 자기 우선순위를 고치는 것은 커널 모드 일이니 시스템 콜을 거쳐야 하고, 거기서 권한을 확인할 수 있다.

<br/><br/>

## 궁금증!

```java
시스템 콜 한 번에 얼마나 드나
```

같은 횟수만큼 불러서 한 번당 시간을 재봤다.

```java
평범한 자바 메서드 호출          =     2 ns
System.nanoTime()              =    13 ns   (커널 안 거치는 시계 읽기)
write(1바이트 -> /dev/null)      =   601 ns   <- 유저 모드 -> 커널 모드 -> 유저 모드
Files.exists() (stat 호출)      =  1026 ns
```

<br/>

메서드 호출은 2ns, 시스템 콜은 600ns다. 300배다.

<br/>

`/dev/null` 에 쓰는 것이라 디스크는 전혀 안 건드렸다.

600ns가 순수하게 `커널 모드로 들어가서 나오는` 비용인 것이다.

<br/>

`System.nanoTime()` 이 13ns인 것도 눈에 띈다.

시간을 읽는 것은 원래 커널 일인데, 자주 쓰는 것이라 운영체제가 커널을 안 거치고 읽을 수 있는 통로를 따로 만들어뒀다.

시스템 콜이 비싸다는 것을 운영체제 자신도 알고 있는 것이다.

<br/><br/>

## 그래서 버퍼를 쓴다

1MB를 1바이트씩 쓰는 것과 8KB 버퍼로 모아서 쓰는 것을 비교했다.

```java
1바이트씩 write() 100만 번     = 639 ms
BufferedOutputStream 로 같은 일 =  11 ms   (시스템 콜 128 번)
```

<br/>

58배 차이다.

<br/>

같은 1MB를 쓰는데, 시스템 콜을 100만 번 하느냐 128번 하느냐의 차이다.

`BufferedReader` 로 감싸서 쓰라고 하는 이유가 이 숫자다.

<br/>

`println` 을 반복문 안에서 백만 번 부르면 느린 것도 같은 이유다.

앞의 System.out.println() 내부 동작원리 글에서 본 대로 `println` 은 매번 `flush` 하니 매번 시스템 콜이다.

<br/><br/>

## 어떤 것이 시스템 콜인가

자바 코드에서 이런 것들은 전부 밑에서 시스템 콜을 한다.

```java
파일 읽기/쓰기           read, write, open, close
네트워크                 socket, connect, send, recv
메모리 더 받기           mmap, brk
스레드 만들기            clone
시간 읽기 (일부)         clock_gettime
프로세스 만들기          fork, exec
잠들기                  nanosleep
```

<br/>

앞의 process를 설명해 주세요 글에서 잰 `스레드 하나 0.06ms` 도 안에서 `clone` 시스템 콜을 하는 시간이다.

<br/>

반대로 이런 것은 시스템 콜이 아니다.

```java
계산
객체 생성 (힙 안에서. 힙이 모자라 늘릴 때만 시스템 콜)
메서드 호출
synchronized (경쟁이 없으면. 경쟁이 심해져서 잠들 때만 시스템 콜)
```

<br/>

앞의 동시성 문제 해결 방법 글에서 본 `synchronized 가 편향 락, 경량 락, 중량 락으로 단계가 있다` 는 것이

바로 `가능한 한 시스템 콜을 안 하려는` 노력이다.

CAS가 빠른 이유도 결국 커널을 안 부르기 때문이다.

<br/><br/>

## 모드 전환 때 무슨 일이 일어나나

```java
1. 레지스터를 저장한다
2. 커널 스택으로 바꾼다
3. 시스템 콜 번호를 보고 해당 커널 함수로 간다
4. 권한을 확인한다 (이 프로세스가 이 파일을 읽을 수 있나)
5. 일을 한다
6. 결과를 유저 메모리로 복사한다
7. 레지스터를 복원하고 유저 모드로 돌아간다
```

<br/>

앞의 context switch vs Context 글에서 본 컨텍스트 스위치와 닮았다.

둘 다 `지금 하던 것을 저장하고 다른 것으로 갈아탄다` 는 점은 같다.

<br/>

차이는 시스템 콜은 같은 프로세스 안에서 모드만 바꾸는 것이고,

컨텍스트 스위치는 다른 프로세스로 바꾸는 것이다.

<br/>

그래서 `Thread.sleep()` 을 부르면 둘이 연달아 일어난다.

```java
sleep 시스템 콜 (모드 전환)
  -> 커널이 이 스레드를 봉쇄 상태로
  -> 다른 스레드로 컨텍스트 스위치
```

<br/><br/>

## 이걸 알면 보이는 것들

```java
NIO 의 select() 가 왜 좋은가
   -> 소켓 1000개를 각각 read() 하면 시스템 콜 1000번. select() 하나로 준비된 것만 알려받는다

로그를 파일에 직접 쓰지 않고 비동기로 모으는 이유
   -> write() 시스템 콜을 요청 스레드에서 빼내려고

메모리 맵 파일 (MappedByteBuffer)
   -> 파일을 read() 대신 메모리처럼 접근. 시스템 콜 없이 페이지 폴트로 읽는다
```

<br/>

앞의 IO 모델 글에서 본 `BIO 1000 스레드 vs NIO 1 스레드` 의 차이가 결국 시스템 콜 횟수의 차이이기도 하다.
