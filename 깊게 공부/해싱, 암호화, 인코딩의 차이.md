## 해싱, 암호화, 인코딩의 차이

<br/>

## 셋을 헷갈리면 사고가 난다

```java
인코딩  - 표현 방식을 바꾼다. 누구나 되돌릴 수 있다. 보안 아님
해싱   - 고정 길이 값으로 바꾼다. 되돌릴 수 없다
암호화  - 키로 잠근다. 키가 있으면 되돌린다
```

<br/>

`비밀번호를 Base64 로 저장했다` 는 말이 나오면 이 셋을 구분 못 한 것이다.

<br/><br/>

## 궁금증!

```java
같은 문자열을 셋으로 처리해봤다
```

<br/>

### 1. 인코딩

```java
Base64("password123") = cGFzc3dvcmQxMjM=
되돌리기              = password123        <- 키 없이 누구나
```

<br/>

글자만 바뀌었다. 정보는 그대로 있다.

`cGFzc3dvcmQxMjM=` 를 보면 누구든 원문을 알 수 있다.

<br/>

Base64는 바이너리를 텍스트로 보내기 위한 것이다. 이메일 첨부, JSON 안의 이미지, JWT의 각 부분이 이것이다.

앞의 엔디언(Byte Order) 글에서 본 것처럼 `어떻게 표현하느냐` 의 문제일 뿐이다.

<br/>

### 2. 해싱

```java
SHA-256("password123") = ef92b778bafe771e89245b89ecbc08a4...   (항상 32바이트)
SHA-256("password124") = 33631376724e5d5480fa397dfcf03b66...   (한 글자 차이에 전부 바뀐다)
```

<br/>

입력이 아무리 길어도 32바이트다. 되돌릴 방법이 없다. 정보가 압축이 아니라 소실됐기 때문이다.

<br/>

같은 입력은 항상 같은 출력이다. 그래서 비밀번호 검증에 쓴다.

```java
가입: SHA-256(비밀번호) 를 저장
로그인: SHA-256(입력) 과 저장된 것을 비교
```

<br/>

원문을 저장하지 않으니 DB가 털려도 비밀번호가 바로 새지는 않는다.

<br/>

### 3. 암호화

```java
AES 암호문  = 25f976686a1cc69d2c3c6ce1274c70c3...
키로 복호화 = password123
```

<br/>

키가 있으면 돌아온다. 키가 없으면 안 돌아온다.

주민번호, 카드번호처럼 `나중에 원문이 필요한 것` 에 쓴다.

<br/><br/>

## 해싱이 빠르면 안 되는 이유

```java
SHA-256 100만 번 = 101 ms
```

<br/>

초당 1000만 번이다. GPU면 초당 수십억 번이다.

<br/>

비밀번호는 사람이 만든 것이라 경우의 수가 적다. 8자리 영문 숫자면 수백조 개인데, 초당 수십억이면 며칠이다.

`SHA-256 으로 해싱했으니 안전` 이 안 되는 이유다.

<br/>

그래서 비밀번호용 해시는 일부러 느리게 만든다.

```java
PBKDF2 반복   1,000 번 =   9 ms
PBKDF2 반복 100,000 번 =  42 ms
PBKDF2 반복 600,000 번 = 189 ms
```

<br/>

한 번 검증에 189ms면 사용자는 못 느낀다. 공격자는 한 번 대입에 189ms다.

초당 5번이다. 초당 1000만 번에서 5번으로 떨어진다.

<br/>

BCrypt, Argon2가 같은 원리다. 스프링 시큐리티 기본이 BCrypt다.

`cost factor` 를 올리면 두 배씩 느려진다. 하드웨어가 빨라지면 숫자를 올리면 된다.

<br/><br/>

## 소금(salt)

같은 비밀번호는 같은 해시다. 그래서 이런 공격이 된다.

```java
자주 쓰는 비밀번호 1억 개의 해시를 미리 계산해둔다 (레인보우 테이블)
털린 DB 의 해시와 대조한다
```

<br/>

사용자마다 무작위 값을 붙여서 해싱하면 막힌다.

```java
hash(salt + password)      // salt 는 사용자마다 다르고, 해시 옆에 그냥 저장한다
```

<br/>

같은 비밀번호도 사용자마다 다른 해시가 된다. 미리 계산한 표가 소용없어진다.

BCrypt는 결과 문자열 안에 salt가 들어 있어서 따로 저장할 필요가 없다.

<br/><br/>

## 암호화에서 조심할 것

```java
키 관리     - 키가 코드에 있으면 소스가 털릴 때 같이 털린다. 환경 변수나 KMS 에
IV / nonce  - 같은 키로 같은 평문을 두 번 암호화하면 같은 암호문이 나온다. 매번 다른 IV 를
모드       - AES/ECB 는 쓰면 안 된다. 블록마다 독립이라 패턴이 보인다. GCM 을 쓴다
```

<br/>

위 실험에서 `AES/GCM/NoPadding` 에 12바이트 무작위 IV를 쓴 것이 이 규칙들이다.

`GCM` 은 암호화하면서 무결성 검증까지 해서, 암호문이 변조되면 복호화가 실패한다.

<br/><br/>

## 정리

```java
비밀번호           -> 해싱. BCrypt/Argon2/PBKDF2. 되돌릴 필요가 없다
주민번호, 카드번호   -> 암호화. AES/GCM. 나중에 원문이 필요하다
바이너리를 텍스트로  -> 인코딩. Base64. 보안과 무관
```

<br/>

JWT를 보고 `암호화됐다` 고 생각하는 경우가 많은데, JWT의 본문은 Base64다.

누구나 열어볼 수 있다. 서명으로 `변조 여부` 만 확인하는 것이다.

민감한 정보를 JWT에 넣으면 안 되는 이유가 이것이다.
