## 분기 예측(Branch Prediction)

<br/>

## CPU 는 명령어를 한 줄씩 끝내지 않는다

앞의 ‘메모리에 적재’ CPU의 연산 글에서 `PC 레지스터가 다음 명령어를 가리킨다` 고 했다.

실제 CPU는 다음 명령어를 기다리지 않는다. 앞 명령어가 끝나기 전에 다음 것을 미리 시작한다.

```java
명령어 1 : 읽기 -> 해석 -> 실행 -> 저장
명령어 2 :        읽기 -> 해석 -> 실행 -> 저장
명령어 3 :               읽기 -> 해석 -> 실행 -> 저장
```

<br/>

공장의 컨베이어 벨트처럼 여러 명령어가 단계를 달리해서 동시에 흘러간다.

이걸 파이프라인이라고 한다.

<br/><br/>

## if 문이 파이프라인을 막는다

```java
if (x >= 128) sum += x;
```

<br/>

`x >= 128` 의 결과가 나와야 다음에 무엇을 실행할지 정해진다.

그런데 파이프라인은 결과가 나오기 전에 다음 명령어를 이미 넣기 시작해야 한다.

<br/>

그래서 CPU는 찍는다.

```java
"아마 참일 것이다" -> 참 쪽 명령어를 미리 넣는다
   맞았으면 -> 그대로 진행. 시간 손해 없음
   틀렸으면 -> 넣은 것을 전부 버리고 다시 시작. 파이프라인 길이만큼 손해
```

<br/>

이 찍기가 분기 예측이다.

<br/><br/>

## 궁금증!

```java
찍기가 틀리면 실제로 얼마나 느려지나
```

0~255 무작위 숫자 3200만 개에서 128 이상인 것만 더한다.

같은 숫자들을 정렬만 해서 다시 돌린다.

```java
for (int i = 0; i < N; i++) if (data[i] >= 128) sum += data[i];
```

<br/>

### 결과

```java
무작위 배열에서 if (x >= 128) 합산 = 127 ms
정렬된 배열에서 if (x >= 128) 합산 =  16 ms   <- 7.9 배
```

<br/>

같은 숫자, 같은 코드, 같은 횟수인데 순서만 달라서 8배가 갈렸다.

<br/><br/>

## 왜 정렬하면 빨라지나

정렬된 배열은 앞쪽 절반이 전부 `거짓`, 뒤쪽 절반이 전부 `참` 이다.

```java
거짓 거짓 거짓 거짓 ... 거짓 | 참 참 참 참 ... 참
```

<br/>

CPU가 `앞에 거짓이었으니 다음도 거짓` 으로 찍으면 계속 맞는다.

경계 한 번만 틀리고 나머지 3200만 번은 전부 맞는 것이다.

<br/>

무작위 배열은 참 거짓이 반반씩 아무 규칙 없이 섞여 있다.

어떻게 찍어도 절반은 틀린다. 1600만 번 파이프라인을 비우고 다시 채운 것이다.

<br/><br/>

## 분기를 없애면 순서가 상관없어진다

같은 일을 `if` 없이 산술로 바꿔봤다.

```java
int t = (data[i] - 128) >> 31;     // 128 미만이면 -1 (전부 1비트), 이상이면 0
sum += ~t & data[i];               // -1 이면 0 을 더하고, 0 이면 data[i] 를 더한다
```

<br/>

시프트와 비트 AND 로 조건을 산술로 바꾼 것이다.

<br/>

### 결과

```java
무작위 배열, 분기 없는 버전 = 22 ms
```

<br/>

정렬 안 했는데 정렬한 것과 비슷하게 나온다.

찍을 것이 없으니 틀릴 것도 없기 때문이다.

<br/>

이런 기법을 분기 제거라고 부른다.

컴파일러가 알아서 해주는 경우도 있고, JIT도 단순한 `if` 는 조건부 이동 명령으로 바꿔준다.

위 실험에서 JIT가 안 바꿔준 이유는 `sum += ` 이 있어서 단순 대입이 아니었기 때문이다.

<br/><br/>

## 예측기는 어떻게 찍나

옛날 CPU는 단순했다.

```java
뒤로 가는 분기 (반복문)  -> 참으로 찍는다. 반복문은 대개 계속 돈다
앞으로 가는 분기 (if)    -> 거짓으로 찍는다
```

<br/>

지금은 분기마다 최근 결과를 기억한다.

```java
이 주소의 if 는 최근에 참 참 참 거짓 참 참 참 거짓 이었다
-> 패턴이 있다. 다음은 참
```

<br/>

몇 천 개의 분기에 대해 각자 이력을 들고 있어서, 규칙이 있으면 거의 다 맞춘다.

무작위만 못 맞춘다. 규칙이 없으니까.

<br/><br/>

## 실무에서 이게 보이는 자리

```java
정렬된 데이터를 조건으로 거르기   -> 빠르다
해시맵처럼 무작위로 흩어진 데이터  -> 예측이 잘 안 된다
가상 메서드 호출 (다형성)        -> 어느 구현으로 갈지가 분기다
```

<br/>

세 번째가 재미있다.

```java
for (Shape s : shapes) s.area();     // shapes 가 Circle 만이면 빠르고, 섞여 있으면 느리다
```

<br/>

앞의 JIT 컴파일러 글에서 본 대로, JIT는 `여기서는 항상 Circle 이 온다` 를 보고 그 분기를 없애버린다.

그런데 갑자기 다른 타입이 오면 그 최적화를 버리고 다시 컴파일한다.

<br/>

앞의 퀵정렬 글에서 본 `합병 정렬보다 실제로 빠른 이유` 에도 이게 한 자리 차지한다.

퀵 정렬의 분할은 분기 예측이 잘 맞는 편이라 파이프라인이 덜 막힌다.

<br/><br/>

## 보안 문제가 되기도 했다

`잘못 찍어서 미리 실행한 명령어` 가 결과는 버려지지만 캐시에는 흔적을 남긴다.

그 흔적으로 읽어서는 안 될 메모리를 읽어내는 공격이 2018년에 공개됐다.

스펙터, 멜트다운이라는 이름이다.

<br/>

운영체제와 CPU가 이걸 막느라 성능이 몇 퍼센트 떨어졌다.

`빨라지려고 찍는다` 는 것이 `보안 구멍` 이 된 경우다.

<br/><br/>

## 정리

```java
CPU 는 if 의 결과를 기다리지 않고 미리 찍어서 진행한다
맞으면 공짜, 틀리면 파이프라인을 비우는 비용
규칙 있는 데이터는 잘 맞고, 무작위는 절반 틀린다 -> 8배 차이
분기 자체를 없애면 순서에 상관없어진다
```

<br/>

앞의 Big_O 글에서 본 대로 복잡도는 같은데 실측이 몇 배 갈리는 이유 중 하나가 이것이다.

`O(n)` 두 개가 같은 속도가 아닌 것이다.
