## 페이지 캐시 - 디스크를 읽는데 왜 메모리 속도인가

<br/>

## 파일을 읽으면 어디서 오나

디스크에서 오는 것 같은데 대개 메모리에서 온다.

<br/>

운영체제가 한 번 읽은 파일 내용을 메모리에 남겨둔다. 그것이 페이지 캐시다.

```java
첫 번째 읽기  : 디스크 -> 페이지 캐시 -> 프로그램       (느리다)
두 번째 읽기  : 페이지 캐시 -> 프로그램                 (메모리 속도)
```

<br/>

앞의 ‘메모리에 적재’ CPU의 연산 글에서 본 CPU 캐시가 메모리를 캐싱하듯, 페이지 캐시는 디스크를 캐싱한다.

<br/><br/>

## 궁금증!

```java
순차 읽기와 무작위 읽기가 디스크에서는 몇십 배 갈린다는데
```

512MB 파일에서 4KB 블록 1만 개를 순서대로, 그리고 무작위 위치로 읽었다.

<br/>

### 결과

```java
순차 = 9 ms, 무작위 = 12 ms
```

<br/>

거의 차이가 없다. 디스크 얘기가 아니었다.

<br/>

파일을 만들면서 쓴 512MB가 전부 페이지 캐시에 남아 있었기 때문이다.

읽기는 디스크에 가지도 않았다. 둘 다 메모리 접근이라 순차든 무작위든 비슷한 것이다.

<br/>

디스크까지 갔다면 이렇게 됐을 것이다.

```java
SSD   : 순차 수백 MB/s, 무작위 4KB 는 그 1/5 ~ 1/10
HDD   : 헤드가 움직여야 해서 무작위는 수십 배 느리다
```

<br/>

이 실험이 그걸 못 보여준 것 자체가 페이지 캐시의 존재 증명이다.

<br/><br/>

## 쓰기도 페이지 캐시로 간다

```java
write() 만                  =    8 ms   <- 페이지 캐시에 넣고 끝
write() + force() 매번       = 8536 ms   <- 매번 디스크까지
```

<br/>

앞의 fsync와 내구성 글에서 잰 수치다.

`write()` 가 8ms에 끝난 것은 디스크에 안 갔기 때문이다. 페이지 캐시에 적어놓고 돌아왔다.

<br/>

커널이 나중에 모아서 디스크에 내려보낸다. 보통 몇 초 뒤다.

그 사이 전원이 나가면 사라진다.

<br/><br/>

## 자바 힙 밖의 메모리다

```java
$ free -h (리눅스)

              total    used    free    buff/cache
Mem:           32G      8G      2G         22G
```

<br/>

`free` 가 2G밖에 없다고 놀라는 경우가 있다.

`buff/cache` 22G가 페이지 캐시다. 필요하면 바로 비워서 프로그램에 준다.

<br/>

`사용 가능한 메모리 = free + buff/cache` 로 봐야 한다.

<br/>

앞의 자바 가상머신(JVM) 글에서 본 `-Xmx` 를 정할 때 이게 걸린다.

```java
32GB 서버에 -Xmx 30g
-> 페이지 캐시가 2GB 뿐
-> 파일 읽기가 매번 디스크로 간다
-> 로그 쓰기, 정적 파일 서빙이 전부 느려진다
```

<br/>

힙을 키운다고 다 좋은 게 아니다. 페이지 캐시에 남겨줄 몫이 있다.

<br/><br/>

## Kafka 가 이걸 정면으로 쓴다

Kafka 브로커는 JVM 힙을 6GB 정도로 작게 잡는다. 서버 메모리가 64GB여도 그렇다.

<br/>

메시지를 힙에 안 두고 파일에 쓴다. 파일은 페이지 캐시에 있다.

```java
프로듀서 write() -> 페이지 캐시
컨슈머 sendfile() -> 페이지 캐시에서 바로 소켓으로
```

<br/>

앞의 zero-copy와 mmap 글에서 본 `sendfile` 이 페이지 캐시에서 직접 보낸다.

JVM 힙을 거치지 않으니 GC 부담도 없다.

<br/>

앞의 가비지 컬렉션(G.C) 글에서 본 대로, 힙이 크면 GC 정지가 길어진다.

Kafka는 `데이터를 힙에 안 두면 GC 문제가 안 생긴다` 로 그 문제를 피한 것이다.

<br/><br/>

## 캐시를 비우고 실제 디스크 속도를 보려면

```java
$ sync; echo 3 > /proc/sys/vm/drop_caches       # 리눅스. root 필요
$ purge                                          # macOS
```

<br/>

벤치마크할 때 이걸 안 하면 두 번째 실행부터 전부 메모리 속도가 나온다.

`첫 실행이 느리고 두 번째부터 빠르다` 는 현상이 대개 이것이다.

<br/>

앞의 자바 가상머신(JVM) 글에서 본 JIT 워밍업과 겹쳐서, 두 번째 실행은 두 가지 이유로 빠르다.

<br/><br/>

## 정리

```java
파일 읽기   - 대개 페이지 캐시에서 온다. 디스크 속도를 재려면 캐시를 비워야
파일 쓰기   - 페이지 캐시에 적고 돌아온다. 디스크에 가는 것은 fsync 나 커널의 주기적 flush
메모리 계산 - free 가 아니라 free + cache. JVM 힙에 다 주면 캐시가 없어진다
설계 활용   - Kafka 처럼 힙 대신 페이지 캐시를 데이터 저장소로 쓰는 방식이 있다
```
