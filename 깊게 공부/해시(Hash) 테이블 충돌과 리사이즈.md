## 해시(Hash) 테이블 충돌과 리사이즈

<br/>

## HashMap 이 O(1) 인 이유

키의 해시코드로 배열 인덱스를 바로 계산한다.

```java
int bucket = hash & (table.length - 1);
```

<br/>

```java
"hello".hashCode() = 99162322
용량 16 이면 버킷  = 99162322 & 15 = 2
```

<br/>

앞의 비트 연산 글에서 본 대로 용량이 2의 거듭제곱이라 `%` 대신 `&` 한 번이다.

<br/>

계산 한 번에 자리를 찾으니 데이터가 100만 개여도 같은 시간이다.

<br/><br/>

## 궁금증!

```java
해시가 전부 같으면 어떻게 되나
```

`hashCode()` 가 항상 1을 돌려주는 키를 만들어 5만 개를 넣고 5만 번 조회했다.

<br/>

### 결과

```java
해시가 잘 퍼짐 (record 기본)   =     2 ms
해시가 전부 1 (충돌 100%)     = 13303 ms     <- 6652 배
```

<br/>

5만 개가 전부 버킷 하나에 들어갔다.

`O(1)` 이 `O(n)` 이 됐다. 조회마다 5만 개를 훑는다.

<br/><br/>

## 자바 8 이 넣은 방어

한 버킷에 8개가 넘으면 연결 리스트를 레드-블랙 트리로 바꾼다.

앞의 노드 글에서 본 그 얘기다.

```java
연결 리스트  - O(n)
트리        - O(log n)
```

<br/>

그런데 위 실험은 트리로 바뀌었는데도 13초다.

<br/>

키가 `Comparable` 이 아니라서다. 트리는 키를 비교해서 좌우로 나눠야 하는데, 비교할 방법이 없으면 `System.identityHashCode` 로 억지 비교를 한다.

그것도 같으면 결국 전부 `equals` 로 확인한다.

<br/>

`hashCode` 를 잘못 만들면 트리도 못 구해준다는 뜻이다.

<br/><br/>

## 이게 공격이 된다

옛날 웹 서버들이 이걸로 당했다.

```java
HTTP 파라미터를 HashMap 에 담는다
공격자가 해시가 같은 파라미터 이름 수만 개를 보낸다
서버가 요청 하나에 CPU 를 몇 초씩 쓴다
```

<br/>

해시 충돌 공격이다. 2011년에 자바, PHP, 루비 전부 취약했다.

<br/>

자바 8의 트리 변환이 이 대응이다. 그리고 `String.hashCode` 를 예측 어렵게 바꾸는 것도 논의됐다.

<br/>

앞의 정규식 백트래킹 글에서 본 ReDoS와 같은 부류다.

`입력 하나로 서버 CPU 를 태우는` 공격이고, 자료구조의 최악 경우를 겨냥한다.

<br/><br/>

## 리사이즈

버킷이 차오르면 배열을 두 배로 늘린다.

```java
기본 용량 16, load factor 0.75
-> 13번째 넣을 때 32 로
-> 25번째 넣을 때 64 로
```

<br/>

`load factor` 가 `얼마나 차면 늘릴 것인가` 다. 0.75면 75%다.

<br/>

앞의 자료구조란 글에서 본 대로 꽉 채우면 충돌이 늘어서 느려지니, 25%는 비워두는 것이다.

<br/>

늘릴 때 모든 키의 자리를 다시 계산한다.

```java
hash & 15  ->  hash & 31       // 마스크가 바뀌니 버킷이 바뀐다
```

<br/>

100만 개면 100만 번 다시 계산해서 옮긴다. 이걸 rehash라고 한다.

<br/>

미리 크기를 알면 잡아두는 게 낫다.

```java
200만 개 put: 기본 용량 = 65 ms (리사이즈 17번), 미리 잡음 = 62 ms
```

<br/>

이 실험에서는 차이가 작았다. `Integer` 박싱 비용이 리사이즈보다 커서 묻힌 것이다.

큰 객체를 키로 쓰면 rehash가 `hashCode()` 를 다시 부르니 차이가 더 벌어진다.

<br/><br/>

## 리사이즈 중에 멀티 스레드로 넣으면

자바 7 이전 `HashMap` 은 리사이즈 중 두 스레드가 동시에 넣으면 연결 리스트가 원을 그리는 버그가 있었다.

`get()` 이 무한 루프에 빠진다. CPU 100%로 서버가 멈추는데 예외는 안 난다.

<br/>

자바 8에서 구조를 바꿔 이 버그는 없어졌지만, 여전히 `HashMap` 은 멀티 스레드에서 안전하지 않다.

값이 사라지거나 개수가 틀린다.

<br/>

앞의 자료구조란 글에서 본 대로 `ConcurrentHashMap` 을 써야 한다.

`ConcurrentHashMap` 은 앞의 CAS 알고리즘 설명 글에서 본 대로 빈 버킷은 CAS로, 있는 버킷은 그 버킷만 `synchronized` 로 잠근다.

리사이즈도 여러 스레드가 나눠서 한다.

<br/><br/>

## hashCode 를 만들 때

```java
equals 가 true 면 hashCode 도 같아야 한다      - 안 지키면 넣은 것을 못 찾는다
가능한 한 다르게 퍼져야 한다                    - 위 실험의 6652 배
바뀌는 필드로 만들면 안 된다                    - 넣은 뒤 바뀌면 다른 버킷에서 찾는다
```

<br/>

앞의 equals, hashCode 메서드는 왜 사용하나요 글과 앞의 Map 정리 글에서 본 규칙들이다.

<br/>

`Objects.hash(a, b, c)` 나 `record` 의 자동 생성을 쓰면 첫째와 둘째는 지켜진다.

셋째는 설계의 문제라 내가 지켜야 한다. 키는 불변이어야 한다.
