## 메모리 재정렬과 happens-before

<br/>

## 코드에 적은 순서대로 실행되지 않는다

```java
x = 1;
r1 = y;
```

<br/>

이 두 줄이 이 순서로 실행된다고 믿는다. 한 스레드 안에서는 그렇게 보인다.

그런데 다른 스레드가 보기에는 순서가 바뀔 수 있다.

<br/>

컴파일러와 CPU가 성능을 위해 순서를 바꾸기 때문이다.

```java
컴파일러 - 의존 관계가 없는 명령을 재배치한다
CPU     - 메모리 쓰기를 버퍼에 모아두고 나중에 내보낸다. 읽기가 먼저 끝날 수 있다
```

<br/>

`x = 1` 과 `r1 = y` 는 서로 상관없는 변수라, 한 스레드 안에서는 어느 순서로 해도 결과가 같다.

그래서 바꿔도 된다고 판단하는 것이다.

<br/><br/>

## 궁금증!

```java
정말 바뀌는 순간을 잡을 수 있나
```

두 스레드를 이렇게 돌렸다.

```java
스레드 A : x = 1;  r1 = y;
스레드 B : y = 1;  r2 = x;
```

<br/>

직관으로는 `r1 == 0 && r2 == 0` 이 불가능하다.

`r1 = y` 가 0을 읽었다면 B가 `y = 1` 을 아직 안 한 것이고, 그러면 B는 그 뒤의 `r2 = x` 를 할 때 A의 `x = 1` 을 봤어야 한다.

<br/>

### 결과

```java
일반 int : r1==0 && r2==0 = 1 번   (20만 번 넘게 돌려서)
volatile : r1==0 && r2==0 = 0 번   (20만 번 중)
```

<br/>

한 번 나왔다. 불가능하다고 생각한 조합이다.

<br/>

`x = 1` 이 저장 버퍼에 들어가 있는 동안 `r1 = y` 가 먼저 실행된 것이다.

같은 일이 B에서도 일어나면 둘 다 0을 읽는다.

<br/>

20만 번에 한 번이라는 빈도가 무섭다.

테스트에서는 절대 안 잡히고, 운영에서 하루에 한 번 이상한 값이 나오는 종류다.

<br/><br/>

## volatile 이 막는 것

`volatile` 을 붙이자 0번이 됐다.

<br/>

앞의 동시성 문제 해결 방법 글에서 `volatile 은 가시성을 해결한다` 고 했다.

정확히는 하나 더 한다. 재정렬을 막는다.

```java
volatile 쓰기 앞의 명령들은 그 쓰기보다 뒤로 밀리지 않는다
volatile 읽기 뒤의 명령들은 그 읽기보다 앞으로 당겨지지 않는다
```

<br/>

이걸 메모리 배리어라고 부른다. 그 지점을 넘어서 재배치하지 말라는 울타리다.

<br/><br/>

## happens-before

자바는 `어떤 경우에 순서가 보장되는가` 를 규칙으로 정해놨다.

```java
같은 스레드 안의 순서        - 코드 순서대로 보인다 (한 스레드 안에서는)
volatile 쓰기 -> 그 값의 읽기 - 쓰기 전에 한 일이 읽은 뒤에 전부 보인다
락 해제 -> 그 락의 획득       - synchronized 블록 안의 일이 다음 블록에서 보인다
Thread.start() -> 그 스레드의 첫 줄
스레드의 마지막 줄 -> join() 이 돌아온 뒤
```

<br/>

`A happens-before B` 면 A가 한 일을 B가 전부 볼 수 있다는 뜻이다.

<br/>

이 규칙에 없는 관계는 아무것도 보장이 안 된다.

위 실험의 일반 `int` 가 그 경우다. 두 스레드 사이에 아무 규칙도 없으니 무슨 순서로 보여도 자바 스펙 위반이 아니다.

<br/><br/>

## 실무에서 이게 물리는 자리

```java
// 초기화 완료 플래그
data = loadData();
ready = true;             // 다른 스레드가 ready 를 보고 data 를 읽는다
```

<br/>

`ready` 가 `volatile` 이 아니면, 다른 스레드가 `ready == true` 를 봤는데 `data` 는 아직 `null` 일 수 있다.

두 쓰기의 순서가 바뀌었기 때문이다.

<br/>

앞의 싱글톤 패턴 (Singleton Pattern) 글에서 본 이중 검사 락이 이 문제로 유명하다.

```java
if (instance == null) {
    synchronized (lock) {
        if (instance == null) {
            instance = new Singleton();      // 객체 할당 -> 생성자 실행 -> 참조 저장. 이 순서가 바뀔 수 있다
        }
    }
}
```

<br/>

참조가 먼저 저장되고 생성자가 나중에 돌면, 다른 스레드가 `반쯤 만들어진 객체` 를 받는다.

`instance` 를 `volatile` 로 선언해야 하는 이유다.

<br/><br/>

## 왜 이렇게 어렵게 만들었나

모든 메모리 접근에 순서를 강제하면 CPU가 느려진다.

앞의 ‘메모리에 적재’ CPU의 연산 글에서 본 캐시와 앞의 분기 예측 글에서 본 파이프라인이 전부 `순서를 바꿔서` 빠른 것이다.

<br/>

그래서 기본은 `순서 안 보장`, 필요한 곳만 `volatile` 이나 락으로 울타리를 치는 방식을 택했다.

<br/>

앞의 동시성  동기화 글에서 본 대로,

`synchronized` 나 `AtomicInteger` 를 쓰면 이 걱정을 안 해도 된다. 안에 배리어가 들어 있다.

`volatile` 없는 공유 변수로 스레드 간 신호를 보내는 코드만 조심하면 된다.
