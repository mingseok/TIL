## 가상 메모리와 페이지 폴트

<br/>

## 가상 메모리란

프로세스가 보는 주소와 실제 물리 메모리의 주소가 다르다.

프로세스는 자기가 메모리 전체를 혼자 쓰는 것처럼 보고, 운영체제가 그 주소를 실제 위치로 바꿔준다.

```java
프로세스가 보는 주소 (가상)  ->  페이지 테이블  ->  실제 메모리 주소 (물리)
```

<br/>

이 변환이 있어서 두 가지가 가능해진다.

```java
1. 프로세스마다 메모리가 격리된다. 남의 메모리 주소를 알아도 못 건드린다
2. 물리 메모리보다 큰 공간을 쓸 수 있다. 안 쓰는 부분은 디스크에 둔다
```

<br/>

앞의 process를 설명해 주세요 글에서 본 `프로세스는 메모리를 공유하지 않는다` 가 `1번` 으로 구현되는 것이다.

<br/><br/>

## 페이지

메모리를 일정한 크기로 잘라서 다룬다. 그 단위가 페이지다.

```java
$ getconf PAGESIZE
16384                  <- 이 맥은 16KB. 리눅스는 보통 4KB
```

<br/>

변환 테이블을 바이트 단위로 만들면 테이블이 메모리보다 커지니, 페이지 단위로 만드는 것이다.

<br/><br/>

## 궁금증!

```java
메모리를 "잡았다" 는 것과 "쓴다" 는 것이 다른가
```

JVM 힙을 3GB로 미리 잡고 띄웠다.

```java
$ java -Xms3g -Xmx3g VMem2
```

```java
RSS = 52 MB     <- 3GB 를 '예약' 만 했다. 물리 메모리는 안 썼다
```

<br/>

3GB를 달라고 했는데 실제 물리 메모리는 52MB만 쓰고 있다.

<br/>

운영체제가 `3GB 를 쓰겠다` 는 약속만 받아두고 실제로는 안 준 것이다.

이게 가상 메모리의 핵심이다. 주소는 있는데 뒤에 실제 메모리가 아직 없다.

<br/><br/>

## 실제로 건드리는 순간 올라온다

`malloc` 으로 1GB를 잡고, 페이지마다 1바이트씩 건드려봤다.

```java
allocateMemory(1GB) 직후 RSS      =   62 MB    <- 아직 안 올라왔다
페이지마다 1바이트 건드린 뒤 RSS   = 1087 MB    <- 이제 올라왔다
```

<br/>

잡을 때는 안 올라오고, 처음 쓸 때 올라온다.

<br/>

처음 쓰는 순간 CPU가 `이 주소에 실제 메모리가 없다` 는 것을 발견하고 운영체제를 부른다.

운영체제가 물리 메모리 한 페이지를 떼어서 연결해주고, 프로세스는 아무 일 없었던 것처럼 이어서 돈다.

이게 페이지 폴트다.

<br/><br/>

## 페이지 폴트 한 번에 얼마나 드나

같은 자리를 두 번 건드려서 첫 번째와 두 번째를 비교했다.

```java
첫 번째 (페이지 폴트 65,536 번) = 196 ms  ->  폴트 1번당 약 2.99 µs
두 번째 (이미 매핑됨)          =  84 ms  ->  2 배
```

<br/>

폴트 한 번에 약 3µs다.

앞의 context switch vs Context 글에서 잰 컨텍스트 스위치 2µs와 비슷하다.

둘 다 `운영체제를 불러서 다녀오는` 일이라 비용도 비슷한 것이다.

앞의 시스템 콜과 유저 모드, 커널 모드 글에서 본 모드 전환이 여기서도 일어난다.

<br/>

두 번째가 84ms인 것도 `0` 이 아니다. 앞의 ‘메모리에 적재’ CPU의 연산 글에서 본 캐시 미스 비용이다.

1GB를 16KB 간격으로 건드리니 캐시에 안 맞고 매번 메인 메모리까지 다녀온 것이다.

<br/><br/>

## 가상 크기와 실제 크기가 얼마나 다른가

```java
$ ps -o vsz=,rss=

VSZ(가상) = 429,923 MB, RSS(실제) = 1,082 MB
```

<br/>

가상 주소 공간이 430GB다. 이 컴퓨터 메모리보다 훨씬 크다.

실제로 쓰는 것은 1GB다.

<br/>

앞의 process를 설명해 주세요 글에서 본 `vmmap` 의 `VIRTUAL SIZE` 와 `RESIDENT SIZE` 차이가 이것이다.

`ps` 의 `VSZ` 는 약속한 크기, `RSS` 가 실제로 쓰는 크기다.

<br/>

메모리 사용량을 볼 때 `VSZ` 를 보면 착각한다. `RSS` 를 봐야 한다.

<br/><br/>

## 스왑 : 물리 메모리가 모자라면

```java
$ vm_stat

Pageins:   6816038
Pageouts:    42782
Swapins:         0
Swapouts:        0
```

<br/>

`Pageouts` 는 물리 메모리에서 디스크로 내려간 페이지 수다.

메모리가 부족하면 오래 안 쓴 페이지를 디스크에 쓰고 그 자리를 다른 프로세스에게 준다.

<br/>

그 페이지를 다시 쓰려 하면 페이지 폴트가 나고, 이번에는 디스크에서 읽어와야 한다.

```java
메모리에서 페이지 연결   -> 약 3 µs
디스크에서 읽어와 연결   -> 수 ms  (천 배 이상)
```

<br/>

스왑이 잦아지면 서버가 극단적으로 느려지는 이유다.

앞의 자바 가상머신(JVM) 글에서 본 `-Xmx` 를 물리 메모리보다 크게 잡으면 GC가 돌 때 힙 전체를 훑으면서 스왑이 폭발한다.

JVM 힙은 물리 메모리 안에 들어가게 잡아야 하는 것이다.

<br/><br/>

## 자바에서 이걸 알아야 하는 자리

```java
-Xms 를 -Xmx 와 같게 잡는 이유
   -> 힙이 커질 때마다 페이지 폴트가 나는 것을 피하려고. 대신 시작할 때 다 잡는다

-XX:+AlwaysPreTouch
   -> 위 실험의 '첫 번째 건드리기' 를 기동 시점에 미리 한다. 기동은 느려지고 운영 중 지연이 준다

컨테이너 메모리 제한
   -> RSS 기준으로 죽인다. VSZ 가 커도 상관없다
```

<br/>

앞의 process를 설명해 주세요 글에서 본 `Stack 21개 x 1MB` 도 대부분 가상이다.

스택은 예약만 되어 있고 실제로 깊이 들어간 만큼만 물리 메모리를 쓴다.

스레드 1000개가 1GB를 쓰는 것이 아닌 이유다.
