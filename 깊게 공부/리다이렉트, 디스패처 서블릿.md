## 리다이렉트, 디스패처 서블릿

리다이렉트는 페이지를 말 그대로 `새로고침` 하는 것이다. 

<br/>

### “왜 사용해?”

```java
"어차피 해당 페이지를 들어가면 페이지가 ‘새로고침’ 되는데 굳이?"
```

사용 이유는, 관리자 페이지에서 회원목록에 어떤 회원을 브론즈 등급에서 실버 등급으로 

`수정 후 저장 버튼을 누르면 바로 최신화`가 되어야 한다. → 그때 필요한게 `redirect:`이다.

`수정 후 다시 최신화 정렬` 같은게 필요하다면 `redirect:` 를 사용 하는 것이다.

<br/>

### e.g.)

휴대폰으로 영화를 결제하기 위해, 해당 사이트에 들어가 결제를 한다.

바로 결제를 진행하려고 하는데, 로그인을 진행하라는 팝업창과 동시에 로그인 화면으로 이동하게 된다. 
```
이런것이 → `redirect`
```

그리고 로그인에 성공하였다면, 다시 결제화면으로 돌아오게 된다.

<br/><br/>

## 디스패처 서블릿

HTTP 프로토콜로 들어오는 모든 요청을 `가장 먼저 받아` 적합한 컨트롤러에 위임해주는 `프론트 컨트롤러`라고 정의할 수 있다

```java
"디스패처 서블릿을 프론트 컨트롤러 라고도 부른다"
```

<br/>

클라이언트로부터 어떠한 요청이 오면 Tomcat(톰캣)과 같은 서블릿 컨테이너가 요청을 받게 된다.

그리고 이 모든 요청을 `프론트 컨트롤러`인 디스패처 서블릿이 가장 먼저 받게 된다.

<br/>

그러면 디스패처 서블릿은 `공통적인 작업을 먼저 처리한 후에` 

해당 요청을 처리해야 하는 `해당 컨트롤러를 찾아서 작업을 위임` 한다.

<br/><br/>

## 디스패처 서블릿의 장점

Spring MVC는 DispatcherServlet이 등장함에 따라 web.xml의 역할 많이 줄였다.

<br/>

과거에는 모든 서블릿을 URL 매핑을 위해 web.xml에 모두 등록해주어야 했지만, 

dispatcher-servlet이 해당 어플리케이션으로 들어오는 모든 요청을 핸들링 해주고 

공통 작업을 처리 하면서 편리하게 이용할 수 있게 되었다.

<br/>

우리는 컨트롤러를 구현해두기만 하면 디스패처 서블릿이 알아서 

적합한 컨트롤러로 위임을 해주는 구조가 된것이다.

<br/>

### 컨트롤러에서 뷰로 이동해야 되는 상황

```java
String viewPath = "/WEB-INF/views/new-form.jsp";
RequestDispatcher dispatcher = request.getRequestDispatcher(viewPath);
dispatcher.forward(request, response);
```

1. 그때 사용하는 것이 `request.getRequestDispatcher()` 이다.

2. `dispatcher.forward(request, response)` 해준다면 

3. 그제서야, 컨트롤에서 뷰로 호출 해주는 것이다.

<br/>

### 서버 내부에서 다시 호출이 발생한다.

클라이언트에서 서버로 호출을 하고, 그리고 서버 안에서 자기들끼리

서블릿 호출 되었다가 → jsp 호출하고 → jsp에서 응답을 만들어서 고객한테 보낸 것이다.

<br/>

### `forward()` 추가 설명

forward() 메서드는 대상의 자원으로 제어를 넘기는 역할을 합니다.

브라우저에서 `/a.jsp`로 요청했을 때 `a.jsp`에서 forward()를 실행하여 `b.jsp`로 제어를 넘길 수 있다.

<br/>

제어를 넘겨 받은 `b.jsp`는 처리 결과를 최종적으로 브라우저에게 출력한다.

브라우저 입장에서는 `/a.jsp`를 요청했지만 받은 결과는 `/b.jsp`의 결과이다.

<br/>

이때 HTTP 리다이렉트 방식과는 달리, 하나의 HTTP 요청 범위 안에서 동작이 이루어지는 것이다.

<br/><br/>

## 차이점

`리다이렉트는 url 주소가 달라지고, 포워드는 url 주소가 달라지지 않는다.`

![이미지](/programming/img/입문535.PNG)
<br/>

## 궁금증!

```java
"새로고침 한다" 고 했는데, 서버가 브라우저에게 정확히 뭘 보내는 걸까?
```

리다이렉트하는 작은 서버를 띄워놓고 응답을 그대로 받아봤다.

```java
$ curl -i -X POST http://localhost:18081/order -d "item=book"

HTTP/1.1 302 Temporary Redirect
Content-length: 0
Location: /order/done
```

<br/>

두 가지가 전부다.

- 상태 코드 `302`

- `Location` 헤더에 다음에 갈 주소

본문은 비어 있다. `Content-length: 0` 이다.

<br/>

브라우저는 이 응답을 받으면 화면에 아무것도 그리지 않고, `Location` 주소로 다시 요청을 보낸다.

<br/>

### 따라가게 해보면

```java
$ curl -L -X POST http://localhost:18081/order -d "item=book"

주문 완료 화면
[최종 URL] http://localhost:18081/order/done
```

<br/>

요청이 두 번 일어난 것이다.

```java
1. POST /order        -> 302 + Location
2. GET  /order/done   -> 200 + 화면
```

<br/>

여기서 중요한 점 하나. 두 번째 요청은 `POST` 가 아니라 `GET` 이다.

`302` 를 받으면 브라우저는 메서드를 `GET` 으로 바꿔서 다시 요청한다.

<br/>

## 그래서 중복 주문이 막힌다

원문의 `수정 후 저장하면 최신화` 보다 더 중요한 효과가 이것이다.

<br/>

리다이렉트 없이 `POST` 응답으로 바로 화면을 그려주면 이렇게 된다.

```java
POST /order  ->  200 + 주문 완료 화면
```

<br/>

이 상태에서 사용자가 새로고침을 누르면 브라우저는 `직전 요청` 을 다시 보낸다.

그 직전 요청이 `POST /order` 라서 주문이 한 번 더 들어간다.

<br/>

리다이렉트를 하면 브라우저의 마지막 요청이 `GET /order/done` 이 된다.

새로고침해도 조회만 다시 일어나니 안전하다.

```java
POST 후 바로 화면 -> 새로고침하면 POST 가 다시 간다 (중복 주문)
POST 후 리다이렉트 -> 새로고침하면 GET 이 다시 간다 (안전)
```

<br/>

이 흐름을 `PRG(Post-Redirect-Get)` 패턴이라고 부른다.

<br/>

## 302와 301의 차이

```java
301 Moved Permanently  - 영구히 옮겼다. 브라우저가 기억해두고 다음부터는 바로 새 주소로 간다
302 Found              - 잠깐 옮겼다. 매번 원래 주소로 물어본다
303 See Other          - POST 결과를 GET 으로 보러 가라는 뜻. PRG 에 가장 정확한 코드
307 Temporary Redirect - 302 와 같지만 메서드를 안 바꾼다. POST 는 POST 로 다시 간다
```

<br/>

`301` 은 브라우저가 캐시에 저장해버리기 때문에 조심해야 한다.

잘못 걸어두면 사용자 브라우저에 남아서, 서버를 고쳐도 계속 옛 주소로 간다.

<br/>

스프링의 `redirect:` 는 기본적으로 `302` 를 보낸다.

의미상으로는 `303` 이 더 정확하지만, 옛 브라우저 호환 때문에 `302` 를 쓰는 관행이 남았다.

<br/>

## 리다이렉트와 포워드는 다르다

이 둘을 헷갈리기 쉽다.

```java
return "redirect:/order/done";     // 리다이렉트
return "orderDone";                // 포워드 (뷰 이름)
```

<br/>

```java
리다이렉트 - 서버가 "저기로 다시 요청해" 라고 답한다
             요청이 두 번. 브라우저 주소창이 바뀐다

포워드    - 서버 안에서 다른 곳으로 넘긴다
             요청이 한 번. 주소창은 그대로다
```

<br/>

앞의 뷰 리졸버 글에서 본 `/WEB-INF/views/orderDone.jsp` 로 넘기는 것이 포워드다.

브라우저는 자기가 요청한 `/order` 에 대한 응답을 받았다고 생각한다.

<br/>

`/WEB-INF` 아래에 뷰를 두는 이유가 여기 있다.

이 경로는 브라우저가 직접 요청할 수 없고, 서버 내부 포워드로만 접근할 수 있다.

<br/>

## 디스패처 서블릿 입장에서 보면

리다이렉트든 포워드든 `render()` 단계에서 갈린다.

```java
doDispatch()
  -> 컨트롤러 실행
  -> 반환값이 "redirect:..." 로 시작하면 -> RedirectView -> 302 응답
  -> 그냥 뷰 이름이면                     -> ViewResolver -> 포워드
```

<br/>

`redirect:` 라는 접두사를 보고 `UrlBasedViewResolver` 가 `RedirectView` 를 돌려준다.

문자열 앞에 붙은 접두사 하나로 응답의 성격이 완전히 달라지는 것이다.
