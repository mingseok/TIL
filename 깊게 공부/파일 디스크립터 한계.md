## 파일 디스크립터 한계

<br/>

## 파일 디스크립터란

프로세스가 연 것들에 운영체제가 붙여주는 번호다.

```java
0 - 표준 입력
1 - 표준 출력
2 - 표준 에러
3 - 그 다음 연 것부터 순서대로
```

<br/>

이름은 `파일` 인데 파일만이 아니다.

```java
파일, 소켓, 파이프, 디바이스, 타이머, epoll 인스턴스 ...
```

<br/>

유닉스는 이것들을 전부 `읽고 쓸 수 있는 것` 으로 통일해서 같은 번호 체계로 다룬다.

앞의 IO 모델 글에서 본 소켓도 FD 하나다.

<br/><br/>

## 한계가 있다

프로세스마다 열 수 있는 FD 개수에 상한이 있다.

```java
$ ulimit -n
1048576             <- 이 맥의 소프트 리밋. 리눅스 기본은 1024 인 경우가 많다
```

<br/>

넘으면 이 예외가 난다.

```java
java.io.IOException: Too many open files
```

<br/>

서버 장애의 단골이다.

<br/><br/>

## 궁금증!

```java
실제로 몇 개에서 막히나
```

한 JVM 안에서 서버 소켓을 열고 클라이언트 소켓을 계속 만들어 접속했다.

<br/>

### 첫 시도 (ulimit 1048576)

```java
16347 번째 소켓에서 실패: Can't assign requested address
```

<br/>

FD가 아니라 다른 것이 먼저 말랐다. 포트다.

<br/>

클라이언트 소켓은 접속마다 임시 포트를 하나 받는다. macOS는 기본 범위가 약 1만6천 개다.

FD는 100만 개까지 되는데 포트가 1만6천 개에서 끝난 것이다.

<br/>

앞의 TCP 소켓 상태 글에서 본 대로, 이 포트들은 닫아도 `TIME_WAIT` 로 30초쯤 묶여 있다.

이 실험 뒤 `netstat` 을 보니 `TIME_WAIT` 가 32,699개였다. 다음 실험이 그것 때문에 실패했다.

<br/>

### 둘째 시도 (ulimit 을 256 으로 낮춰서)

```java
$ ulimit -H -n 256; ulimit -S -n 256
126 번째 소켓에서 실패: Too many open files
```

<br/>

126번째에서 막혔다. 256의 절반이다.

<br/>

접속 하나가 FD 두 개를 쓰기 때문이다.

```java
클라이언트 소켓       1개
서버가 accept 한 소켓  1개    (같은 JVM 이라 둘 다 내 것)
```

<br/>

`126 × 2 = 252` 에 JVM이 원래 열고 있던 것(jar, 표준 입출력, 라이브러리)을 더하면 256이다.

<br/>

하드 리밋까지 낮춰야 했던 이유가 있다.

JVM은 기동할 때 소프트 리밋을 하드 리밋까지 스스로 올린다. 소프트만 낮추면 JVM이 다시 올려버린다.

<br/><br/>

## 어디서 새나

```java
1. 스트림을 안 닫는다         - FileInputStream 을 열고 close() 를 안 함
2. 커넥션을 안 반납한다        - DB 커넥션, HTTP 클라이언트
3. 접속이 실제로 많다          - 롱 폴링, 웹소켓 수만 개
4. 로그 파일을 계속 새로 연다
```

<br/>

`1번` 이 제일 흔하다.

```java
FileInputStream in = new FileInputStream(f);      // close 없음
```

<br/>

앞의 IO 스트림 글에서 본 대로 스트림 하나가 FD 하나다.

GC가 언젠가 `finalize` 로 닫아주긴 하는데, 그 `언젠가` 가 오기 전에 한계에 닿는다.

앞의 가비지 컬렉션(G.C) 글에서 본 대로 GC는 메모리가 부족할 때 돌지, FD가 부족할 때 도는 게 아니다.

<br/>

`try-with-resources` 가 이걸 막는다.

<br/><br/>

## 진단하는 법

```java
$ lsof -p <pid> | wc -l                 # 이 프로세스가 연 FD 수
$ lsof -p <pid> | awk '{print $5}' | sort | uniq -c     # 종류별
```

<br/>

```java
REG    - 일반 파일
IPv4   - 소켓
FIFO   - 파이프
```

<br/>

어느 종류가 비정상적으로 많은지 보면 원인이 좁혀진다.

소켓이 수천 개인데 `CLOSE_WAIT` 상태면 앞의 TCP 소켓 상태 글에서 본 `내가 close 를 안 한 소켓` 이다.

<br/><br/>

## 한계를 올리는 것은 임시 조치다

```java
$ ulimit -n 65536
```

<br/>

서버를 띄우기 전에 올려두는 것이 관례다. 리눅스 기본 1024는 서버에 너무 작다.

`/etc/security/limits.conf` 나 systemd 의 `LimitNOFILE` 로 영구 설정한다.

<br/>

그런데 새는 코드가 있으면 올려도 시간만 늦춘다.

`Too many open files` 가 나면 한계를 올리기 전에 `lsof` 로 무엇이 쌓이는지 먼저 봐야 한다.

<br/>

앞의 IO 모델 글에서 본 대로,

접속 수만 개가 정상인 서비스면 한계를 올리고 NIO로 가는 것이 맞다. 그건 새는 게 아니라 실제로 많은 것이다.
