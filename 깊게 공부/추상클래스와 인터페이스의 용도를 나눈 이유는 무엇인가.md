## 추상클래스와 인터페이스의 용도를 나눈 이유는 무엇인가?

추상 클래스와 인터페이스는 서로 다른 목적과 사용 사례를 가지고 있다.

<br/>

## 차이가 뭔가?

추상 클래스는 `abstract` 지시자로 정의되어서, 추상 메서드가 하나 이상 포함되는 

클래스를 말하며, 서브 클래스가 이를 상속하고 확장하도록 한다는 점이다.


<br/>

인터페이스는 `interface` 지시자로 정의되어서, 모든 메서드가 추상메서드로 정의되게 됩니다.

- 인터페이스는 클래스가 어떤 역할을 수행할 수 있음을 선언하다는 점이다.

<br/>

### 그렇기에 둘의 차이는

- 추상 클래스는 상속을 받아서 재활용하고 확장시키는데 목적이 있고,
  
- 인터페이스는 함수 구현을 강제해서, 구현한 객체들이 같은 동작을 하는 것을 보장하는 것에 목적이 있습니다
    

<br/>

## 추상 클래스의 용도

- 추상 클래스는 클래스의 일반적인 특성을 공유하는데 사용됩니다.
    
    즉, 공통의 속성과 메서드를 추상 클래스에 정의하여 서브 클래스가 이를 상속하고 확장하도록 한다.
    
- 추상 클래스는 일부 메서드를 구현할 수 있다.
    
    따라서 추상 클래스 내에서 추상 메서드와 구현된 메서드를 모두 포함할 수 있다.
    
- 추상 클래스를 사용하면 코드 재사용과 확장이 용이하며,
    
    상속을 통해 기본 동작을 제공하고 하위 클래스에서 필요에 맞게 조정할 수 있다.
    
<br/>

## 인터페이스의 용도

- 인터페이스는 클래스가 특정 동작을 지원하거나 어떤 역할을 수행할 수 있음을 선언하는데 사용된다. 
    
- 인터페이스는 메서드 시그니처만을 정의하고, 해당 메서드를 구현하는 클래스가 어떤 클래스인지 신경 쓰지 않습니다.
    
- 인터페이스를 구현한 클래스는 여러 인터페이스를 동시에 구현할 수 있으며, 다중 상속을 지원하는 방법으로 사용된다.
    
- 인터페이스는 클래스 간에 일관성 있는 프로토콜을 정의하고, 다형성을 통해 객체들을 동일한 방식으로 다루는데 사용된다.
    
<br/>

## 정리하면,

추상 클래스는 상속을 통해 공통된 동작을 제공하고, 일부 메서드를 구현하며, 

하위 클래스가 재사용 및 확장을 할 수 있게 하는 것이다. 

<br/>

반면, 인터페이스는 클래스가 어떤 역할을 수행할 수 있음을 선언하고, 

클래스 간의 일관성 있는 프로토콜을 제공하며, 다중 상속과 다형성을 지원한다. 

<br/>

두 가지 개념은 서로 보완적인 역할을 하며, 코드 재사용과 유연성을 높이기 위해 사용된다.

<br/>

## 궁금증!

```java
"인터페이스는 모든 메서드가 추상 메서드"라고 했는데, Java 8부터는 아니지 않나?
```

맞다. `Java 8` 부터 `default` 메서드가 생기면서 인터페이스도 구현을 가질 수 있게 됐다.

```java
interface PayClient {
    void pay(int amount);                 // 추상 메서드

    default void payTwice(int amount) {   // Java 8 - 구현이 있다
        pay(amount);
        pay(amount);
    }

    static PayClient none() {             // Java 8 - static 메서드
        return amount -> { };
    }
}
```

<br/>

그러면 이제 추상 클래스와 뭐가 다른가 싶어진다.

둘 다 구현을 가질 수 있고, 둘 다 추상 메서드로 강제할 수 있게 되었으니까.

<br/>

## 그래도 남아 있는 차이는 두 가지다

인터페이스에 필드와 생성자를 넣어보면 바로 막힌다.

```java
interface Shape {
    private String name;
    Shape(String name) { }
}
```

```java
error: = expected
    private String name;
                       ^
error: <identifier> expected
    Shape(String name) { }
         ^
```

<br/>

- 인터페이스는 `상태(필드)` 를 가질 수 없다

- 인터페이스는 `생성자` 를 가질 수 없다

이 둘은 `Java 8` 이후로도 그대로다.

```java
동작은 물려줄 수 있게 열어줬지만 -> default 메서드
상태는 끝까지 못 물려주게 막았다  -> 필드와 생성자 금지
```

<br/>

상태를 여러 곳에서 물려받으면 답이 없어지기 때문이다.

두 인터페이스에 같은 필드가 있으면 구현 클래스 안에 그 필드가 몇 개인지 정할 수 없다.

자바가 클래스 다중 상속을 막은 것과 정확히 같은 이유다.

<br/>

## 그래서 실제 갈림길은 여기다

```java
공통으로 물려줄 "상태" 가 있는가?
   있다 -> 추상 클래스
   없다 -> 인터페이스
```

<br/>

## 추상 클래스가 어울리는 경우

여러 구현이 `같은 순서로 일하되 한 단계만 다른` 경우다.

```java
abstract class Report {
    private final String title;      // 상태를 가질 수 있다

    protected Report(String title) { // 생성자도 가질 수 있다
        this.title = title;
    }

    final void print() {             // 순서는 고정
        System.out.println("=== " + title + " ===");
        System.out.println(body());
        System.out.println("--- 끝 ---");
    }

    protected abstract String body();  // 이 부분만 자식이 채운다
}

class CsvReport extends Report {
    CsvReport(String title) { super(title); }
    protected String body() { return "이름,금액\n민석,1000"; }
}

class JsonReport extends Report {
    JsonReport(String title) { super(title); }
    protected String body() { return "{\"이름\":\"민석\",\"금액\":1000}"; }
}
```

<br/>

### 결과

```java
=== 월간 매출 ===
이름,금액
민석,1000
--- 끝 ---

=== 월간 매출 ===
{"이름":"민석","금액":1000}
--- 끝 ---
```

<br/>

제목을 찍고, 본문을 찍고, 끝 줄을 찍는 `순서` 는 부모가 쥐고 있다.

자식은 본문만 채운다. 순서를 실수로 바꿀 수가 없다.

<br/>

`print()` 에 `final` 을 붙인 것이 핵심이다. 자식이 순서를 덮어쓰지 못하게 막은 것이다.

이 구조를 `템플릿 메서드 패턴` 이라고 부른다.

<br/>

`title` 이라는 상태를 부모가 들고 있고 생성자로 받는데, 이건 인터페이스로는 못 한다.

<br/>

## 인터페이스가 어울리는 경우

서로 아무 관계도 없는 것들을 `같은 역할` 로 묶을 때다.

```java
class SmartPhone implements Alarm, Phone, Messenger { }
```

`SmartPhone` 은 알람이면서 전화기이면서 메신저다.

상속으로는 이 중 하나만 고를 수 있으니 애초에 불가능하다.

<br/>

`Comparable`, `Runnable`, `AutoCloseable` 같은 것들이 전부 이 부류다.

`무엇이다` 가 아니라 `무엇을 할 수 있다` 를 말하고, 상태는 하나도 물려주지 않는다.

```java
추상 클래스 -> "나는 무엇이다"        (is-a), 하나만 고를 수 있다
인터페이스  -> "나는 무엇을 할 수 있다" (can-do), 여러 개를 붙일 수 있다
```

<br/>

## 실무에서는 인터페이스를 먼저 고려하게 된다

상속은 한 번밖에 못 쓰는 자원이라서 아껴야 한다.

인터페이스로 될 것을 추상 클래스로 만들어두면, 나중에 다른 클래스를 상속해야 할 때 막힌다.

<br/>

그리고 추상 클래스는 부모의 구현에 자식이 묶인다.

부모 필드를 하나 바꿨을 뿐인데 자식이 깨지는 일이 생긴다.

<br/>

`상태를 물려줘야 하는 것이 확실할 때` 만 추상 클래스를 쓰고,

나머지는 인터페이스로 두는 쪽이 나중에 손댈 여지를 남겨둔다.
