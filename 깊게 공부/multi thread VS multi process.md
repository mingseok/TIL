## multi thread VS multi process



프로세스란 실행중인 프로그램을 뜻합니다.

<br/>

즉, 실행파일 형태로 존재하던 프로그램이 메모리에 적재되어 

CPU에 의해 실행 되는 것을 프로세스라고 합니다.

<br/>

### 프로세스 내에서도 각 용도에 따라 메모리 영역이 구분되어 있습니다.

- 코드 영역

    - 우리가 코드를 짜서 컴파일 한 이후에, 기계어로 번역된 코드들을 코드 영역

- 데이터 영역

    - 전역 변수, static 변수 경우는 데이터 영역에 저장을 하게  되는 영역

- 힙 영역

    - 런타임 중에 메모리 할당이 되는 동적 메모리 할당을 힙 영역에서 진행하게 된다.

- 스택 영역

    - 함수에서 쓰이는 지역변수나 매개 변수 이런 것들이 스택 영역에 저장 된다.

<br/><br/>

## 대부분의 사람들은

하나의 프로세스만 사용하기 보다는 여러 가지를 동시에 사용하고 싶어 한다!

![이미지](/programming/img/입문429.PNG)

<br/>

하지만, 한 프로세스가 실행되기 위해서는 `cpu`를 점유하고 있으면,

다른 프로세스들은 실행 상태에 있을 수가 없다.

```java
ex) 큰 용량의 메일을 보내는 중인데, 
    인텔리제이 켜면 보내고 있던 메일은 꺼져 버린다는 것이다.
```

<br/><br/>

## 그리하여

다수의 `프로세스`를 동시에 실행하기 위해 여러 프로세스를 `시분할`로 

짧은 텀을 반복하면서, 전환하며 실행 시키도록 한다는 것이다.

- `“왜?”` → CPU는 `하나`이기 때문이다.
    - `프로세스1`이 CPU로 갔다가 → 다시 준비 상태로 되고,
        
        `프로세스2`가 CPU로 갔다가 → 다시 준비 상태로 되는 것을 반복한다
        
    - 이것이, `컨테스트 스위칭` 이라고 한다.

```java
하지만, 이방법은 너무나 피곤하다. 그렇기에 나온것이 -> "스레드"
```

<br/><br/>

## 스레드 설명

스레드는 한 프로세스 내에서 나뉘어진 하나 이상의 실행 단위이다

하나의 프로세스 안에 다수의 스레드가 있을 때, 스레드끼리는 자원을 공유하고 있다.

<br/>

여기서, 스레드는 JVM에 `Code`, `Metaspace`, `Heap` 영역을 공통된 자원으로 사용한다.

- 각각의 스레드는 스택 부분만을 따로 가진다.

```java
이렇게 사용시 장점은?

공유되는 자원이 있기 때문에 이전처럼 "컨텍스트 스위칭"이 
일어날 때, "캐싱 적중률"이 올라간다는 것이다.

(쉽게 생각하면, 안에 있는걸 다빼고, 다시 다넣을 필요가 없다는 뜻)
```

<br/><br/>

## multi thread VS multi process

두 가지 모두 `“처리방식의 일종”`이라는 것이다.

- 즉, 한 어플리케이션에 대한 두가지 다른 처리방식에 대해서 공부한다 생각하기

<br/>

### 예를 들어,

여러 사용자가 `로그인`을 요청하는 상황이 있다고 생각해보자.

<br/>

한 `프로세스`는 매번 하나의 로그인만 
처리할 수 있기 때문에 동시에 처리할 수 없다.

<br/>

그리하여 `부모 프로세스`가 `fork()`를 한다. 

그리고 자식 프로세스를 여러 개 만들어서 일을 처리하도록 한다. 

(이때, 자식 프로세스는 부모와 별개로 `메모리 영역`을 확보한다.)

<br/>

반면 스레드는 한 프로세스 안에서 만들어진 `“실행 단위"`이다.

- 실행 단위 : `cpu core`에서 실행하는 하나의 단위이다.

    - 즉, `프로세스`의 하나 밖에 없는 `스레드`가 실행 단위가 되는 것이다.

```java
프로세스 내에서 분리하고, ->
여러 스레드로도 나누어진다면, 그것이 "멀티스레드"가 되는 것이다.
```

- ex) 내가 코드를 수정하는 동시에, 인텔리제이에서 추천 코드를 보여줄 때

- ex) 테스트코드를 돌리는 동시에 소스 코드도 수정해야 될 때

<br/>

이렇게 한 어플리케이션에 대한 `작업의 단위`가 나누어질때가 많다는 것이다.

이때 각각의 스레드가 그 작업들을 담당하게 되는 것이다.

<br/><br/>

## 차이점

### 멀티 프로세스

- `프로세스`는 독립적이기 때문에 `IPC`를 사용한 통신을 해야 한다

    - IPC : 각자의 방에 있다가 할 얘기가 있으면, 나와 얘기하고 다시 각자의 방으로 가는 것

- 자원이 소모적, 개별 메모리 차지
- `Context Switching` 비용이 크다

- 개별 독립적이기 때문에 동기화 작업에 신경을 덜 써도 된다.

<br/>

### 멀티 스레드

- 공유 자원이 많으므로 연결되어 있다.

    - 공유된 자원으로 메모리가 효율적이고 통신 비용도 절감 된다

- `Context Switching` 비용도 적다

<br/><br/>

## 컴퓨터는 왜 멀티 프로세스를 이용할까?

여러 창의 띄워 작업을 하다가, 이런 창이 뜨면 창 전체가 꺼져 버린다.

![이미지](/programming/img/입문430.PNG)

<br/>

### 이유가 뭐야?

멀티스레드를 이용했기 때문이다.

<br/>

스레드끼리 연결되어 있기 때문에 한 스레드, 즉, 한 탭에 문제가 생기면 

전체 프로세스에 영향이 가게 되는 것이기 때문이다.

<br/>

반면, 구글 크롬은 멀티프로세서를 이용하기 때문에 

멀티탭 간의 영향을 덜 받는다는 것이다.

<br/><br/>

## 정리

- 한 어플리케이션에 대한 작업을 동시에 하기 위해서는 `2가지` 처리 방식
     (멀티 프로세스, 멀티 스레드)이 있다.
    
- 동시에 실행이 되는 것처럼 보이기 위해서 실행 단위는 시분할로
     `cpu`를 점유하며 `context switching`을 한다
    
- 멀티 프로세스는 독립적인 메모리를 가지고 있지만 멀티 스레드는 자원을 공유한다.
<br/><br/>

## 궁금증!

```java
"자원을 공유한다" 와 "독립적이다" 를 코드로 확인해봤다
```

같은 `static` 변수를 자식 프로세스와 자식 스레드가 각각 바꾸게 했다.

```java
static int shared = 0;
```

<br/>

### 프로세스

```java
[부모 pid=71545] shared = 0
  [자식 pid=71546] shared 를 999 로 바꿈
[부모] 자식이 끝난 뒤 shared = 0     <- 그대로
```

<br/>

### 스레드

```java
  [스레드] shared 를 999 로 바꿈
[main] 스레드가 끝난 뒤 shared = 999  <- 바뀌어 있다
```

<br/>

같은 클래스, 같은 변수인데 프로세스는 각자 복사본을 갖고 스레드는 하나를 같이 쓴다.

<br/>

원문의 `스레드는 Code, Metaspace, Heap 을 공유하고 스택만 따로 가진다` 가 여기서 보인다.

`static` 변수는 힙(정확히는 메서드 영역)에 있으니 스레드끼리 보이는 것이다.

<br/><br/>

## 공유가 장점이자 단점이다

위 실험에서 스레드 쪽이 편해 보인다. 값을 넘기려고 뭘 하지 않아도 그냥 보인다.

<br/>

그런데 그게 곧 앞의 동시성  동기화 글의 문제다.

```java
4 스레드가 각자 50만 번 ++  = 965,305     <- 정답 200만
```

<br/>

같이 쓰니까 같이 망가진다.

프로세스는 이 문제가 없다. 공유하는 게 없으니 경쟁도 없다.

원문의 `개별 독립적이기 때문에 동기화 작업에 신경을 덜 써도 된다` 가 이 뜻이다.

<br/>

대신 프로세스는 값을 넘길 때마다 IPC를 거쳐야 한다.

```java
파이프, 소켓, 공유 메모리, 파일
```

<br/>

전부 직렬화해서 보내고 받아서 역직렬화한다.

스레드는 참조 하나 넘기면 끝나는 일을, 프로세스는 바이트로 바꿔서 통로로 밀어 넣어야 하는 것이다.

<br/><br/>

## 만드는 비용 차이

```java
스레드   100개 생성+종료 = 6 ms    (개당 0.06 ms)
프로세스  10개 생성+종료 = 40 ms   (개당 4.00 ms)
```

<br/>

60배가 넘는다.

<br/>

프로세스는 앞의 process를 설명해 주세요 글에서 본 `__TEXT`, `__DATA`, `Stack` 을 전부 새로 만든다.

스레드는 이미 있는 프로세스에 스택 하나만 더 붙인다.

<br/>

그래서 요청마다 프로세스를 만들던 옛 CGI 방식이 사라지고, 스레드 풀이 표준이 된 것이다.

<br/><br/>

## 컨텍스트 스위칭 비용 차이

원문에 `멀티 스레드는 컨텍스트 스위칭 비용이 적다` 고 적혀 있다.

앞의 context switch vs Context 글에서 잰 스레드 간 스위치가 약 2µs다.

<br/>

프로세스 간은 더 든다. 이유가 있다.

```java
스레드 간   - 레지스터와 스택 포인터만 바꾼다. 메모리 지도는 그대로
프로세스 간 - 메모리 지도까지 바꾼다. 주소 변환 캐시(TLB)가 비워진다
```

<br/>

원문의 `캐싱 적중률이 올라간다` 는 말이 이것이다.

같은 프로세스 안의 스레드는 같은 메모리를 보니, 앞 스레드가 캐시에 올려둔 것을 다음 스레드도 쓸 수 있다.

<br/><br/>

## 그럼 스레드가 항상 나은가

아니다. 크롬이 프로세스를 택한 이유가 원문에 있다.

```java
한 탭이 죽으면 -> 스레드였으면 브라우저 전체가 죽는다
             -> 프로세스라 그 탭만 죽는다
```

<br/>

공유하지 않는다는 것이 `격리` 라는 안전을 준다.

<br/>

그리고 보안이다.

탭 하나가 악성 사이트여도 다른 탭의 메모리를 읽을 수 없다.

스레드였으면 같은 힙이니 다 읽힌다.

<br/>

정리하면 선택 기준은 이렇다.

```java
빠르게 많이 만들고 값을 자주 주고받는다  -> 스레드
하나가 죽어도 나머지는 살아야 한다      -> 프로세스
서로 믿을 수 없는 코드를 돌린다         -> 프로세스
```

<br/><br/>

## 자바에서는 사실상 스레드다

JVM 하나가 프로세스 하나고, 안에서 스레드를 쓴다.

`ProcessBuilder` 로 자식 프로세스를 만들 수는 있지만 외부 명령을 부를 때 정도다.

<br/>

격리가 필요하면 JVM을 여러 개 띄운다. 서버를 여러 대 두는 것이다.

앞의 Multi process에 대해서 설명해 주세요 글에서 본 대로, 멀티 프로세스의 장점을 한 컴퓨터 안이 아니라 여러 컴퓨터로 가져가는 셈이다.

<br/>

그래서 자바 개발자에게 `멀티 프로세스 vs 멀티 스레드` 는 코드 안의 선택이 아니라 배포 구조의 선택이 된다.

```java
코드 안   - 스레드. 스레드 풀 크기, 동기화
배포 구조 - 프로세스. 인스턴스 수, 로드밸런서, 상태를 밖으로 빼기
```

<br/><br/>

## 가상 스레드가 경계를 다시 바꾼다

자바 21의 가상 스레드는 `가벼운 스레드` 다.

```java
플랫폼 스레드 - 운영체제 스레드 하나에 1:1. 만드는 데 0.06ms, 스택 1MB 예약
가상 스레드   - JVM 이 관리. 수백만 개도 만들 수 있다
```

<br/>

앞의 서블릿 글에서 본 `요청마다 스레드 하나` 를 유지하면서도 스레드가 싸진 것이다.

<br/>

기다리는 동안 운영체제 스레드를 내놓고, 깨어나면 다시 받는다.

앞의 Multi process 글에서 본 `기다리는 일에는 스레드를 많이` 를 훨씬 싸게 할 수 있게 된 것이다.
