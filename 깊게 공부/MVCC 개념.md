## MVCC 동작 설명

이제부터는 `write(x=50)` 되어 있는 것이 있다면 `write_lock(x)` 과정을 거쳐서 온다고 생각하자. 

즉, lock을 획득한 다음 동작하는 것이다.  (앞으로는 생략한다.)

![이미지](/programming/img/입문471.PNG)

1. `write_lock(x)`을 획득한 한다.

2. x의 값을 10에서 50으로 업데이트 해준다면 → 50이라는 값이 바로 `DB로 적용되는 것이 아니라,` 
    
    `다른 공간의 개념으로 x = 50이라는 공간에 써주게 된다.`
    
    (실제로, 어떻게 구현되는지는, 각각의 RDBMS마다 차이가 있다)
    
3. 그리고 트랜잭션1이 x를 read 한다면? → `DB에 저장되어 있는 X = 10의 값을 읽게 되는 것이다.`

```java
"mvcc의 중요한 특징은 commit된 데이터만 읽는다는 것이다"
```

<br/><br/>

### 추가 사항

![이미지](/programming/img/입문472.PNG)

`commit`을 진행하게 된다면 → `이제서야 DB에 x = 50으로 업데이트 된다.`

그리고 `commit`을 진행하면 `write_lock(x) 또한 반납하게 된다.`

<br/>

```java
"commit할때 lock을 반납하는 이유는?" -> recoverabillity를 위해서이다.
```

즉, 롤백 되는 경우를 생각했을때, 롤백이 잘 되도록 하기 위해서이다.



### 이어서 진행

![이미지](/programming/img/입문473.PNG)

<br/>

`read(x) → ?` 의 값은 어떤걸 가져올까?

- 이것은 트랜잭션1번의 아이솔레이션 레벨에 따라서 다르게 값을 가져오게 되는 것이다.

    - `만약, read committed라면?`

        - read committed이라면? → `read(x) ⇒ 50 을 읽는다.`

            - 사진속에는 50이라고 되어 있지만, 저때는 락공간에 따로 보관하고 있을때이다.

            - 그리하여 repeatable read이라면? → `read(x) ⇒ 10 을 읽는다.`

## MVCC 정리

데이터를 읽을 때 특정 시점 기준으로 가장 최근에 `commit`된 데이터를 읽는다

- 특정 시점이란? → 아이솔레이션 레벨에 따라 다르다.

    - 데이터 변화했다는 히스토리를 RDBMS가 내부적으로 관리해줘야 한다.

        - 그렇기에, MVCC는 추가적으로 저장 공간을 많이 쓰게 된다.

            - 즉, 이런 부분이 단점 될 수 있다.

- `장점이라면`, read와 write는 서로를 block하지 않는다.

    - 성능면에서 동시에 처리할 수 있는 트랜잭션이 더 늘어날 수 있다는 측면에서 장점이 되는 것이다.
        
    - 그렇기에, 현업에서는 mvcc를 사용하여 구현을 한다.

## locking read란?

![이미지](/programming/img/입문474.PNG)

트랜잭션1번의 아이솔레이션 레벨이 repeatable read라고 할지라도, 가장 최근의 commit된 데이터를 읽어 온다.

<br/>

### locking read 문법

```sql
select ... FOR UPDATE; // write/read 전용 락을 말한다.
select ... FOR SHARE;  // read 전용 락을 말한다.

e.g.)
select balance
from account
where id = 'x';
for update; // 이 부분이다!
```

만약, serializable 레벨이라면 → 일반적인 쿼리문에서 `for share;` 구문을 작성하지 않아도 

mysql이 알아서 for share 처럼 동작시키는 것이다.

## 궁금증!

```java
"버전을 여러 개 둔다" 는 게 실제로 무슨 이득을 주는 걸까?
```

읽는 쪽이 쓰는 쪽을 안 기다려도 된다는 것이다.

앞의 DB 락 글에서 한 실험이 그 증거다.

```sql
-- A 세션
BEGIN IMMEDIATE;
UPDATE t SET v = 200 WHERE id = 1;   -- 아직 커밋 안 함

-- B 세션
UPDATE t SET v = 300 WHERE id = 1;   -- 쓰기 시도
SELECT v FROM t;                     -- 읽기 시도
```

<br/>

### 결과

```sql
B: 쓰기 -> Error: database is locked
B: 읽기 -> 100
```

<br/>

쓰기는 막혔는데 읽기는 통과했다. 그것도 기다리지 않고 즉시.

<br/>

`A` 가 바꾼 값은 아직 커밋 전이라 `B` 에게 보이면 안 된다.

그렇다고 `B` 를 기다리게 하면 조회 하나 하려고 다른 트랜잭션이 끝나기를 기다려야 한다.

<br/>

그래서 `바뀌기 전 값을 따로 남겨두고 그것을 보여주는` 방식이 나온 것이다.

```java
락으로만 처리하면 -> 읽는 쪽도 기다려야 한다
버전을 남겨두면   -> 읽는 쪽은 옛 버전을 보면 되니 안 기다린다
```

<br/>

## 옛 버전은 어디에 남는가

MySQL InnoDB는 `언두 로그(undo log)` 에 남긴다.

```java
UPDATE t SET v = 200 WHERE id = 1

1. 실제 데이터에는 200 을 쓴다
2. 언두 로그에 "원래 100 이었다" 를 적어둔다
3. 그 행에 "누가 바꿨는지(트랜잭션 번호)" 를 표시해둔다
```

<br/>

다른 트랜잭션이 읽으러 오면 이렇게 판단한다.

```java
이 행을 바꾼 트랜잭션이 내가 시작하기 전에 커밋됐나?
  예   -> 지금 값을 보여준다
  아니오 -> 언두 로그를 따라가서 옛 값을 찾아 보여준다
```

<br/>

원문의 `MVCC 동작 설명` 이 이 판단 과정이다.

<br/>

## 그래서 언두 로그가 쌓이면 문제가 된다

트랜잭션이 오래 살아 있으면, 그 트랜잭션이 볼 수도 있는 옛 버전을 못 지운다.

```java
트랜잭션 A 가 한 시간째 안 끝남
-> 그 한 시간 동안 바뀐 모든 행의 옛 버전을 계속 들고 있어야 한다
-> 언두 로그가 계속 커진다
-> 디스크가 차거나, 읽을 때 언두를 길게 따라가느라 느려진다
```

<br/>

MySQL에서 긴 트랜잭션을 피하라는 이유가 이것이다.

앞의 DB 락 글에서 본 `락을 오래 잡으면 안 된다` 와는 다른 이유로, 역시 짧아야 한다.

```java
락 관점   -> 오래 잡으면 남이 기다린다
MVCC 관점 -> 오래 살면 옛 버전을 못 지운다
```

<br/>

## 그럼 쓰기끼리는 왜 여전히 막히는가

MVCC는 `읽기와 쓰기` 사이의 충돌만 없앤다.

`쓰기와 쓰기` 는 여전히 락으로 막아야 한다.

<br/>

같은 행을 둘이 동시에 바꾸면 하나는 사라질 수밖에 없기 때문이다.

버전을 여러 개 만들어도 최종적으로 남는 값은 하나여야 한다.

```java
읽기 vs 읽기 - 원래 안 부딪힌다
읽기 vs 쓰기 - MVCC 가 해결한다 (안 기다린다)
쓰기 vs 쓰기 - 락으로 막는다 (기다리거나 실패한다)
```

<br/>

위 실험에서 `B` 의 쓰기만 막히고 읽기는 통과한 것이 정확히 이 구분이다.

<br/>

## locking read 가 필요한 순간

원문 마지막의 `locking read` 가 왜 있는지도 여기서 나온다.

```java
// 재고 확인 후 차감
SELECT stock FROM item WHERE id = 1;      -- 10 개
if (stock >= 3) {
    UPDATE item SET stock = stock - 3 WHERE id = 1;
}
```

<br/>

MVCC 덕분에 `SELECT` 가 안 막힌다. 그런데 그게 오히려 문제다.

두 트랜잭션이 동시에 `10` 을 읽고 둘 다 `7` 로 만들어버릴 수 있다.

<br/>

이럴 때는 읽으면서 락을 걸어야 한다.

```sql
SELECT stock FROM item WHERE id = 1 FOR UPDATE;
```

<br/>

`FOR UPDATE` 를 붙이면 MVCC를 안 쓰고 최신 값을 락과 함께 읽는다.

앞의 DB 락 글에서 본 `비관적 락` 이 이것이다.

```java
그냥 SELECT        -> MVCC. 안 기다린다. 대신 읽은 값이 이미 옛것일 수 있다
SELECT FOR UPDATE  -> 락. 기다린다. 대신 읽은 값이 최신이고 남이 못 바꾼다
```

<br/>

읽은 값을 보고 판단해서 다시 쓸 거라면 `FOR UPDATE` 가 필요하다.

단순히 화면에 보여줄 거라면 그냥 `SELECT` 가 맞다.
