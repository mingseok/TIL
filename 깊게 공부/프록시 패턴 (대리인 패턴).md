## 프록시 패턴 (대리인 패턴)

<br/>

## 프록시 패턴 설명.

프록시는 객체를 다른 객체로 대체 할 수 있는 구조 디자인 패턴입니다. 

<br/>

프록시는 객체에 대한 접근을 제어하므로, 
객체의 요청이 


전달되기 전 또는 후로 무언가를 행동할 수 있도록 합니다.

<br/><br/>

## 프록시 패턴 예시

어느 정도 규모가 있는 회사 대표님은 만나기 어렵다.

<br/>

스케줄을 조율하거나 메시지를 남기거나 하는 등등 어지간한 일은 비서, 대리인을 통해 처리하게 된다.

회사 대표가 몸소 등장해야 하는 일은 그만큼 중요도가 있고, 권한이 필요한 경우일 것이다.

<br/>

프로그래밍에서 사용되는 클래스들 중에서도 인터넷에서 받아와야 해서 

시간이 걸리거나 메모리를 많이 차지하거나 하는 등의 이유로 객체로 

여럿 생성하기가 부담이 되는 것들이 있다.

<br/>

그럴때는 그 클래스의 프록시, 대리자 역할을 하는 클래스를 따로 두어서, 

가벼운 일은 그 비서가 처리하게 하는 것이다.

<br/>

대표가 직접 나와야 할 수 있는 무거운 작업을 할 때는 비로소 실제 클래스를 생산하여 사용하는 것이다.

<br/><br/>

## 사용 되는 곳은?

지연된 초기화(가상 프록시). 

- 무거운 서비스 객체가 항상 가동되어 있어 시스템 자원들을 낭비하는 경우이다

```java
앱이 시작될 때 객체를 생성하는 대신, 
객체 초기화를 실제로 초기화가 필요한 시점까지 지연할 수 있습니다.
```

<br/><br/>

## 장점

- 클라이언트들이 알지 못하는 상태에서 서비스 객체를 제어할 수 있습니다.

- 클라이언트들이 신경 쓰지 않을 때, 서비스 객체의 수명 주기를 관리할 수 있습니다.
- 개방/폐쇄 원칙. 서비스나 클라이언트들을 변경하지 않고도 새 프록시들을 도입할 수 있습니다.

<br/><br/>

## 단점

- 새로운 클래스들을 많이 도입해야 하므로 코드가 복잡해질 수 있습니다.

- 서비스의 응답이 늦어질 수 있습니다.
<br/>

## 궁금증!

```java
프록시를 매번 손으로 만들어야 하나
```

인터페이스에 메서드가 스무 개면 프록시도 스무 개를 적어야 한다.

전부 `real.method()` 를 부르는 똑같은 코드다.

<br/>

자바가 이걸 대신 만들어주는 기능을 갖고 있다.

```java
Service proxy = (Service) Proxy.newProxyInstance(
        Service.class.getClassLoader(),
        new Class[]{Service.class},
        (p, m, args) -> {
            long start = System.nanoTime();
            Object result = m.invoke(real, args);
            System.out.println("  [프록시] " + m.getName() + " 걸린 시간 측정됨");
            return result;
        });
```

<br/>

### 결과

```java
프록시 클래스 = $Proxy0
Service 를 구현했나? true
RealService 인가? false
  [진짜] 일을 한다
  [프록시] work 걸린 시간 측정됨
```

<br/>

`$Proxy0` 이라는 이름의 클래스가 실행 중에 만들어졌다.

내가 쓴 적 없는 클래스다.

<br/>

## 두 줄이 핵심이다

```java
Service 를 구현했나? true
RealService 인가?  false
```

<br/>

인터페이스는 구현했지만 진짜 클래스와는 아무 관계가 없다.

<br/>

그래서 이런 코드가 터진다.

```java
RealService real = (RealService) proxy;      // ClassCastException
```

<br/>

앞의 AOP 프록시 글에서 본 그 제약이다.

```java
JDK 동적 프록시 - 인터페이스가 있어야 한다. 인터페이스 타입으로만 받을 수 있다
CGLIB          - 클래스를 상속한다. 인터페이스가 없어도 된다
```

<br/>

스프링 부트는 기본으로 `CGLIB` 을 쓴다.

인터페이스가 없는 클래스도 많고, 구체 타입으로 주입받는 코드도 있기 때문이다.

<br/>

## 프록시가 붙으면 생기는 일들

```java
1. 클래스 이름이 바뀐다
2. 자기 자신을 부르면 프록시를 안 탄다
3. private 메서드에는 못 붙는다
4. final 클래스에는 못 붙는다
```

<br/>

`2번` 이 실무에서 제일 많이 물린다.

```java
@Service
public class OrderService {

    public void order() {
        save();              // 여기서 프록시를 안 탄다
    }

    @Transactional
    public void save() { ... }
}
```

<br/>

앞의 AOP 프록시 글에서 본 대로,

프록시는 밖에서 들어오는 호출만 가로챌 수 있다.

`save()` 는 `this.save()` 라서 프록시를 안 거친다.

<br/>

트랜잭션이 안 걸리는데 오류도 안 난다. 그냥 조용히 안 되는 것이다.

<br/>

## 프록시 패턴과 데코레이터 패턴

구조가 똑같은데 의도가 다르다.

```java
프록시   - 접근을 제어한다. 원본을 감춘다
데코레이터 - 기능을 더한다. 원본은 그대로 쓴다
```

<br/>

```java
프록시   -> 캐시, 권한 확인, 지연 로딩
데코레이터 -> 로그 추가, 압축 추가, 암호화 추가
```

<br/>

앞의 프록시 - 즉시 로딩과 지연 로딩 글에서 본 JPA 프록시가 전형적인 프록시다.

```java
member.getTeam()          -> 프록시. 아직 DB 를 안 봤다
member.getTeam().getName() -> 이때 조회한다
```

<br/>

`실제로 필요할 때까지 미룬다` 는 접근 제어다.

<br/>

자바 IO는 데코레이터 쪽이다.

```java
new BufferedReader(new InputStreamReader(new FileInputStream("a.txt")))
```

<br/>

한 겹씩 감싸면서 기능이 쌓인다.

앞의 스트림(Stream) 글에서 본 그 구조다.

<br/>

## 프록시를 만드는 세 가지 방법

```java
1. 직접 클래스로 만든다        - 메서드마다 위임 코드를 쓴다
2. JDK 동적 프록시            - 인터페이스가 있어야 한다
3. CGLIB                     - 상속으로 만든다
```

<br/>

`2번` 과 `3번` 을 쓰면 위임 코드를 안 써도 된다.

대신 `어느 메서드에 적용할지` 를 정하는 방법이 필요해진다.

<br/>

스프링 AOP가 그걸 해준다.

```java
@Around("execution(* com.example.service.*.*(..))")
```

<br/>

앞의 스프링 AOP 글에서 본 포인트컷이다.

`어디에 적용할지` 와 `무엇을 할지` 를 나눠 적는 것이다.
