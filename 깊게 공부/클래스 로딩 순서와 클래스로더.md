## 클래스 로딩 순서와 클래스로더

<br/>

## 클래스는 언제 메모리에 올라오나

프로그램 시작할 때 전부 올라올 것 같은데, 아니다. 처음 쓸 때 올라온다.

<br/><br/>

## 궁금증!

```java
"처음 쓸 때" 가 정확히 언제인가
```

`static` 블록에 출력을 넣어 초기화 시점을 찍었다.

```java
static class Lazy {
    static { System.out.println("[Lazy 클래스 초기화됨]"); }
    static int V = 7;
    static final int C = 3;
}
```

<br/>

### 결과

```java
Lazy 타입 변수 선언만 했다          -> 초기화 안 됨
Lazy.C (static final 상수) 읽기    -> 초기화 안 됨
Lazy.V (static 변수) 읽기:
  [Lazy 클래스 초기화됨]             <- 이 순간
```

<br/>

변수 선언은 초기화를 일으키지 않는다. `Lazy l = null` 은 타입 이름만 쓴 것이다.

<br/>

`static final` 상수 읽기도 안 일으킨다.

컴파일러가 `Lazy.C` 를 `3` 으로 바꿔버려서, 실행 시점에는 `Lazy` 를 찾아갈 일이 없다.

앞의 String 객체를 생성하는 방법과 내부 동작 원리 글에서 본 상수 폴딩이다.

<br/>

`static` 변수 읽기가 초기화를 일으킨다. 값이 실행 중에 정해지니 클래스가 준비되어야 한다.

<br/>

초기화를 일으키는 것들이 정해져 있다.

```java
new 로 인스턴스 생성
static 메서드 호출
static 변수 읽기/쓰기 (final 상수 제외)
Class.forName()
자식 클래스 초기화 (부모가 먼저)
```

<br/><br/>

## 부모가 먼저

```java
Child.hi();
```

```java
[Parent 초기화]
[Child 초기화]
```

<br/>

`Child` 의 `static` 메서드만 불렀는데 `Parent` 가 먼저 초기화됐다.

앞의 클래스 멤버 변수 초기화 순서는 어떻게 되나요 글에서 본 순서가 클래스 수준에서도 같다.

<br/><br/>

## 누가 로딩하나 : 클래스로더

```java
String.class.getClassLoader()         = null                  <- 부트스트랩
java.sql.Driver.class.getClassLoader() = PlatformClassLoader
Load.class.getClassLoader()           = AppClassLoader
그 부모                                = PlatformClassLoader
```

<br/>

세 층이다.

```java
부트스트랩   - JVM 내장. java.lang 같은 핵심. 자바 객체가 아니라 null 로 나온다
플랫폼      - JDK 의 나머지 모듈. java.sql 등
애플리케이션 - 내 클래스, 라이브러리 jar
```

<br/>

`-verbose:class` 로 찍어보면 실제로 그 순서로 올라온다.

```java
java.lang.ClassLoader
...
jdk.internal.loader.ClassLoaders$AppClassLoader
jdk.internal.loader.ClassLoaders$PlatformClassLoader
...
Load
Load$Lazy
Load$Parent
Load$Child
```

<br/>

내 클래스보다 클래스로더 자체가 먼저 로딩된다. 로더가 있어야 로딩할 수 있으니 당연하다.

<br/><br/>

## 부모 위임

클래스를 찾으라고 하면 자기가 먼저 찾지 않는다. 부모에게 먼저 물어본다.

```java
AppClassLoader: "java.lang.String 찾아줘"
  -> Platform 에게 넘긴다
    -> Bootstrap 에게 넘긴다
      -> Bootstrap 이 찾았다. 끝
```

<br/>

부모가 못 찾으면 그때 자기가 찾는다.

<br/>

이래서 내 프로젝트에 `java.lang.String` 을 만들어도 절대 로딩되지 않는다.

부트스트랩이 진짜 `String` 을 먼저 찾아서 돌려주기 때문이다.

<br/>

핵심 클래스를 바꿔치기해서 보안을 뚫는 것을 구조적으로 막는 것이다.

<br/><br/>

## 같은 클래스인데 다른 클래스

```java
클래스의 정체 = 클래스 이름 + 로딩한 클래스로더
```

<br/>

같은 `com.example.User` 를 다른 클래스로더 두 개가 각자 로딩하면, JVM은 다른 클래스로 본다.

```java
ClassCastException: com.example.User cannot be cast to com.example.User
```

<br/>

이름이 같은데 캐스팅이 안 된다는 예외다. 처음 보면 무슨 말인지 모른다.

<br/>

톰캣에 웹앱 여러 개를 띄우면 각 앱마다 클래스로더가 따로 있어서 이 문제가 생긴다.

같은 라이브러리를 두 앱이 각자 들고 있으면 다른 클래스다.

<br/>

앞의 스프링 컨테이너 글에서 본 스프링 부트가 `jar 하나에 앱 하나` 로 가는 이유 중 하나다.

클래스로더가 하나면 이 문제가 없다.

<br/><br/>

## Class.forName

```java
Class.forName("java.util.ArrayList")
```

<br/>

문자열로 클래스를 로딩한다. 컴파일할 때 그 클래스를 몰라도 된다.

<br/>

옛 JDBC가 이 방식이었다.

```java
Class.forName("com.mysql.jdbc.Driver");      // 로딩되면서 static 블록이 DriverManager 에 자기를 등록
```

<br/>

JDBC 4부터는 `ServiceLoader` 가 jar 안의 `META-INF/services` 를 읽어서 자동으로 한다.

앞의 JDBC 표준 인터페이스 글에서 본 `드라이버 jar 만 넣으면 된다` 가 이것이다.

<br/><br/>

## 언로딩

로딩한 클래스는 클래스로더가 GC 될 때 같이 사라진다.

부트스트랩과 앱 클래스로더는 JVM이 살아 있는 동안 안 사라지니, 내 클래스도 안 사라진다.

<br/>

앞의 자바 메모리 구조 글에서 본 메타스페이스가 계속 차는 경우가 이것이다.

클래스를 동적으로 계속 만드는 코드(프록시, 스크립트 엔진)가 새 클래스로더 없이 돌면 메타스페이스가 안 줄어든다.

<br/><br/>

## 정리

```java
로딩 시점   - 처음 실제로 쓸 때. 선언과 static final 상수는 안 일으킨다
순서       - 부모 클래스 먼저. 클래스로더 자체가 먼저
위임       - 자식 로더는 부모에게 먼저 묻는다. 핵심 클래스는 바꿔칠 수 없다
정체       - 이름 + 로더. 로더가 다르면 같은 이름도 다른 클래스
```
