## zero-copy와 mmap

<br/>

## 파일을 복사하면 복사가 네 번 일어난다

```java
in.read(buf);        // 디스크 -> 커널 버퍼 -> 유저 버퍼(buf)
out.write(buf);      // 유저 버퍼(buf) -> 커널 버퍼 -> 디스크
```

<br/>

같은 바이트가 커널과 유저 공간을 두 번 오간다.

앞의 시스템 콜과 유저 모드, 커널 모드 글에서 본 모드 전환도 두 번씩 일어난다.

<br/>

유저 공간에서 그 바이트를 건드릴 일이 없는데도 그렇다.

파일 서버가 파일을 그대로 내려보내는 것, 프록시가 받은 것을 그대로 넘기는 것이 다 이 경우다.

<br/><br/>

## zero-copy

유저 공간을 거치지 않고 커널 안에서 바로 옮기는 것이다.

```java
in.transferTo(pos, size, out);       // FileChannel
```

<br/>

리눅스의 `sendfile` 시스템 콜이 이걸 한다.

```java
디스크 -> 커널 버퍼 -> (커널 안에서) -> 소켓 버퍼 -> 네트워크
```

<br/>

유저 공간 복사 두 번이 사라진다. 시스템 콜도 한 번이다.

<br/><br/>

## 궁금증!

```java
얼마나 빨라지나
```

512MB 파일을 복사했다.

<br/>

### 결과

```java
read/write 8KB 버퍼 반복   = 545 ms
FileChannel.transferTo   = 155 ms     <- 3.5 배
```

<br/>

같은 파일, 같은 디스크인데 3.5배다.

<br/>

앞의 시스템 콜 글에서 시스템 콜 한 번이 600ns였다.

8KB 버퍼로 512MB를 옮기면 `read` 65,536번 + `write` 65,536번이다. 그것만 80ms다.

여기에 복사 2번 × 512MB가 더해진 것이 545ms고, `transferTo` 는 둘 다 없어서 155ms인 것이다.

<br/><br/>

## mmap : 파일을 메모리처럼

```java
MappedByteBuffer m = ch.map(READ_ONLY, 0, size);
m.get();                          // read() 를 안 부른다. 메모리 읽기다
```

<br/>

파일을 프로세스 주소 공간에 매핑한다.

앞의 가상 메모리와 페이지 폴트 글에서 본 페이지 테이블에 `이 주소 = 파일의 이 위치` 를 적어두는 것이다.

<br/>

그 주소를 읽으면 페이지 폴트가 나고, 커널이 파일에서 그 페이지를 올린다.

`read()` 시스템 콜을 안 부르는 대신 페이지 폴트로 읽는다.

<br/>

### 결과

```java
BufferedInputStream 1바이트씩 = 4569 ms
MappedByteBuffer (mmap)     =  463 ms     <- 10 배
```

<br/>

1바이트씩 `get()` 하는데도 10배 빠르다.

`BufferedInputStream` 도 8KB씩 미리 읽으니 시스템 콜은 적은데, `read()` 메서드 호출 자체의 층이 두꺼운 것이다.

`mmap` 은 배열 인덱스 접근과 다를 게 없다.

<br/><br/>

## mmap 의 진짜 장점은 공유다

같은 파일을 두 프로세스가 `mmap` 하면 같은 물리 페이지를 본다.

```java
프로세스 A 가 쓴 것을 프로세스 B 가 복사 없이 바로 본다
```

<br/>

앞의 process를 설명해 주세요 글에서 본 `프로세스는 메모리를 공유하지 않는다` 의 예외다.

IPC 중 가장 빠른 방법이 공유 메모리인 이유가 이것이다.

<br/>

Kafka가 이걸 쓴다.

```java
프로듀서가 쓴 로그 세그먼트 파일 -> 페이지 캐시에 있다
컨슈머에게 sendfile 로 보낸다   -> 유저 공간을 안 거친다
```

<br/>

Kafka가 JVM 힙을 작게 잡고 나머지를 운영체제 페이지 캐시에 맡기는 이유다.

앞의 페이지 캐시 글에서 이 부분을 이어서 본다.

<br/><br/>

## mmap 의 함정

```java
1. 언매핑을 제어할 수 없다   - MappedByteBuffer 는 GC 가 회수할 때 풀린다. 언제인지 모른다
2. 파일이 커지면 재매핑     - 매핑한 크기가 고정이다
3. 페이지 폴트 비용         - 처음 접근하는 페이지마다 3µs. 앞의 가상 메모리 글에서 잰 수치
4. 2GB 제한                - MappedByteBuffer 는 int 인덱스. 큰 파일은 나눠 매핑
```

<br/>

`1번` 이 실무에서 물린다.

매핑한 파일을 지우려는데 `파일이 사용 중` 이라고 안 지워진다. 언매핑이 안 됐기 때문이다.

<br/>

자바 22의 FFM API(`Arena`)가 명시적 해제를 제공해서 이 문제를 푼다.

<br/><br/>

## 정리

```java
read/write  - 유저 공간 경유. 바이트를 가공해야 할 때
transferTo  - 커널 안에서 이동. 파일을 그대로 보낼 때 (정적 파일 서빙, 프록시)
mmap        - 파일을 메모리로. 무작위 접근이 많을 때, 프로세스 간 공유할 때
```

<br/>

셋 다 `복사를 줄인다` 는 같은 목표다.

앞의 ‘메모리에 적재’ CPU의 연산 글에서 본 대로,

데이터를 옮기는 것이 계산보다 비싸기 때문에 옮기는 횟수를 줄이는 것이 성능의 핵심이 된다.
