## 템플릿 메서드 패턴



## 설명

어떤 같은 행동인 특정 작업들을 세부적으로 다양화하고자 할때 사용하는 패턴이다.

```java
약과를 만드는 가문이 있다.
1. 반죽을 만드는 과정.
2. 반죽을 기름에 튀기는 과정.
3. 시럽을 바르는 과정
```



위 3과정을 어떻게 하느냐에 따라 다양한 약과들이 만들어 진다.

<br/>

다양화된 방식을 각각 자식 클래스에서 오버라이드 한 방식으로 구현한 것을 말한다.

상속을 통해 부모 클래스의 기능을 확장할때 사용하는 방법이다.

<br/>

부모 클래스에서 변하지 않는 기능을 구현해두고 자식 클래스에서 확장할 기능을 구현하게 됩니다. 

자바에서는 추상 클래스를 사용해서 구현하는데 대표적으로 AbstractMap이 있습니다.

<br/><br/>

## AbstractMap은?

`AbstractMap`에서 공통된 기능을 정의하고 상속 받은 `HashMap`이나 

`TreeMap`에서 각각의 자료구조에 
맞게 `get()` 메소드를 다르게 구현하게 됩니다.

<br/><br/>

## 장점

- 중복 코드를 부모 클래스로 가져올 수 있습니다.
- 클라이언트들이 대규모 알고리즘의 특정 부분만 오버라이드 하도록 하여 

    그들이 알고리즘의 다른 부분에 발생하는 변경에 영향을 덜 받도록 할 수 있습니다.
    

<br/><br/>

## 단점

- 일부 클라이언트들은 알고리즘의 제공된
골격에 의해 제한될 수 있습니다.
    
- 템플릿 메서드들은 단계들이 더 많을수록 유지가 더 어려운 경향이 있습니다.
<br/>

## 궁금증!

```java
무엇이 고정이고 무엇이 열려 있는가
```

부모가 순서를 잡고, 자식이 빈칸만 채우는 구조다.

```java
abstract class Report {
    final void report() {          // final. 순서를 못 바꾼다
        System.out.println("헤더");
        body();                    // 여기만 자식이 채운다
        System.out.println("푸터");
    }
    abstract void body();
}
```

<br/>

### 결과

```java
헤더
{"data":1}          <- JsonReport
푸터
헤더
data,1              <- CsvReport
푸터
```

<br/>

두 자식 클래스가 `body()` 만 다르게 채웠는데 앞뒤는 똑같이 나온다.

<br/>

## final 을 붙이는 것이 중요하다

```java
final void report() { ... }
```

<br/>

`final` 이 없으면 자식이 `report()` 자체를 오버라이딩해서 순서를 바꿔버릴 수 있다.

그러면 패턴의 의미가 없어진다.

<br/>

앞의 final 키워드 글에서 본 `메서드에 붙은 final 은 오버라이딩 금지` 가 이럴 때 쓰인다.

<br/>

## 훅 메서드라는 것이 있다

자식이 선택적으로 끼어들 수 있는 자리다.

```java
abstract class Report {
    final void report() {
        System.out.println("헤더");
        body();
        if (needSummary()) {         // 훅
            summary();
        }
        System.out.println("푸터");
    }

    abstract void body();
    boolean needSummary() { return false; }    // 기본값을 준다
    void summary() {}
}
```

<br/>

`abstract` 가 아니라 기본 구현이 있는 메서드다.

필요한 자식만 오버라이딩하면 된다.

<br/>

## 상속이라는 게 문제다

템플릿 메서드는 상속으로 동작한다. 그래서 제약이 따라온다.

```java
1. 부모를 하나만 고를 수 있다
2. 부모가 바뀌면 자식이 전부 영향을 받는다
3. 자식이 부모의 protected 필드까지 알게 된다
```

<br/>

앞의 상속, 오버라이딩 글에서 본 그 결합도 문제다.

<br/>

`3번` 이 특히 안 좋다.

`body()` 만 채우면 되는데, 부모의 필드까지 볼 수 있으니 거기에 손을 대게 된다.

<br/>

## 그래서 전략 패턴을 대신 쓰기도 한다

같은 문제를 다르게 푼다.

```java
// 템플릿 메서드: 상속
abstract class Report { abstract void body(); }
class JsonReport extends Report { void body() { ... } }

// 전략 패턴: 조합
class Report {
    private final BodyWriter writer;
    Report(BodyWriter writer) { this.writer = writer; }

    void report() {
        System.out.println("헤더");
        writer.write();
        System.out.println("푸터");
    }
}
```

<br/>

앞의 스트래티지 패턴 글에서 본 그 방식이다.

```java
템플릿 메서드 - 상속으로 채운다. 컴파일할 때 정해진다
전략 패턴     - 조합으로 채운다. 실행 중에 바꿀 수 있다
```

<br/>

`Report` 하나로 여러 형식을 처리할 수 있다는 게 다르다.

<br/>

## 자바 8 이후로는 더 간단해진다

인터페이스도 기본 구현을 가질 수 있게 됐다.

```java
interface Report {
    default void report() {
        System.out.println("헤더");
        body();
        System.out.println("푸터");
    }
    void body();
}
```

<br/>

앞의 인터페이스의 Default Method 글에서 본 그것이다.

<br/>

클래스 상속을 안 써도 되니 `부모를 하나만 고를 수 있다` 는 제약이 풀린다.

다만 `final` 을 못 붙여서 순서를 강제하지는 못한다.

<br/>

## 실무에서 이미 쓰고 있다

```java
JdbcTemplate      - 연결, 예외 처리, 정리는 고정. 쿼리와 매핑만 내가
RestTemplate      - 요청, 응답 처리는 고정. URL 과 타입만 내가
TransactionTemplate - 시작, 커밋, 롤백은 고정. 안의 로직만 내가
```

<br/>

`Template` 이라는 이름이 붙은 것이 대부분 이 패턴이다.

<br/>

다만 스프링의 `Template` 들은 상속이 아니라 콜백을 받는다.

```java
jdbcTemplate.query(sql, (rs, rowNum) -> new Member(rs.getLong("id")));
```

<br/>

`템플릿 콜백 패턴` 이라고 부른다.

앞의 스프링 JdbcTemplate 글에서 본 그 구조다.

<br/>

상속 대신 람다를 넘기는 것이라, 클래스를 새로 안 만들어도 된다.

자바 8 이후로는 이 방식이 훨씬 편해진 것이다.
