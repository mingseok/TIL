## 롬복이 만드는 메소드들이 생성되는 시점은?



Java의 라이브러리로 반복되는 메서드를 `Anntation`을 사용해 자동으로 
작성해주는 아주 편리한 라이브러리이다.

<br/>

`Java`에서 보통 `Model`클래스나 `Entity` 같은 도메인 클래스 등에는 
여러 속성이 존재하고 

이들이 갖는 프로퍼티에 대해서 `Getter`, `Setter`, `생성자` 등을 매번 작성해줘야 하지만 

<br/>

Lombok을 이용한다면 어노테이션을 이용하는 것 만으로 

자동으로 `Getter, Setter, 생성자` 등의 코드를 작성해줘 번거로운 과정을 제거해 준다.

<br/><br/>

## 롬복 메서드 생성 시점은?

`Lombok`은 메소드를 `컴파일 하는 과정에 개입해서` 추가적인 코드를 만들어낸다.

```java
"필드 주입처럼 좀 편리하게 사용하는 방법"
```

<br/>

이것을 어노테이션 `프로세싱`이라고 하는데, 어노테이션 프로세싱은 

`자바 컴파일러가 컴파일 단계`에서 어노테이션을 분석하고 처리하는 기법을 말한다.
<br/>

## 궁금증!

```java
"컴파일 과정에 개입한다" 는 것을 눈으로 볼 수 있을까?
```

볼 수 있다. 소스에는 없는데 `.class` 에는 있는 것을 확인하면 된다.

```java
import lombok.Getter;
import lombok.RequiredArgsConstructor;

@Getter
@RequiredArgsConstructor
public class Member {
    private final String name;
    private final int age;
}
```

<br/>

메서드를 하나도 안 적었다. 이걸 컴파일해서 `javap` 로 열어보면 이렇다.

```java
public class Member {
  public java.lang.String getName();
  public int getAge();
  public Member(java.lang.String, int);
}
```

<br/>

게터 두 개와 생성자가 생겨 있다.

`.class` 파일에는 진짜로 메서드가 들어 있으니, 실행할 때는 롬복이 없어도 된다.

```java
컴파일할 때만 필요하다 -> 그래서 compileOnly / annotationProcessor 로 넣는다
```

`build.gradle` 에서 롬복을 `implementation` 이 아니라 이렇게 넣는 이유가 이것이다.

```java
compileOnly 'org.projectlombok:lombok'
annotationProcessor 'org.projectlombok:lombok'
```

<br/>

## delombok으로 보면 더 확실하다

롬복은 `내가 대신 적어준 코드` 를 출력해주는 기능도 있다.

```java
java -jar lombok.jar delombok Member.java -p
```

<br/>

### 결과

```java
public class Member {
    private final String name;
    private final int age;

    @java.lang.SuppressWarnings("all")
    @lombok.Generated
    public String getName() {
        return this.name;
    }

    @java.lang.SuppressWarnings("all")
    @lombok.Generated
    public int getAge() {
        return this.age;
    }

    @java.lang.SuppressWarnings("all")
    @lombok.Generated
    public Member(final String name, final int age) {
        this.name = name;
        this.age = age;
    }
}
```

<br/>

우리가 손으로 적었을 코드가 그대로 나온다.

`@lombok.Generated` 가 붙어 있어서 테스트 커버리지 도구가 이 코드를 제외할 수 있게 되어 있다.

<br/>

## 그런데 엄밀히 말하면 어노테이션 프로세싱이 아니다

원문에 `어노테이션 프로세싱` 이라고 되어 있는데, 여기에 사연이 하나 있다.

<br/>

원래 자바의 어노테이션 프로세서는 `새 파일을 만들 수는 있어도 기존 소스를 고칠 수는 없게` 되어 있다.

`QueryDSL` 이 `QMember` 같은 새 클래스를 만들어내는 것이 정석적인 사용법이다.

<br/>

그런데 롬복은 기존 클래스에 메서드를 끼워 넣는다. 규격상 허용되지 않는 일이다.

<br/>

롬복은 컴파일러 내부의 `AST(구문 트리)` 에 직접 손을 대는 방식으로 이걸 해낸다.

컴파일러가 소스를 트리 구조로 바꿔놓은 상태에서, 그 트리에 메서드 노드를 몰래 추가하는 것이다.

```java
정석적인 프로세서 : 소스를 읽고 -> 새 파일을 만든다
롬복             : 컴파일러 내부 구조에 끼어들어 -> 원래 클래스를 고친다
```

<br/>

그래서 롬복은 JDK 버전이 올라갈 때마다 종종 깨진다.

컴파일러 내부 구조가 바뀌면 같이 바꿔야 하기 때문이다.

JDK를 올렸는데 갑자기 게터를 못 찾겠다는 에러가 나면 대개 롬복 버전 문제다.

<br/>

## @Data는 조심해야 한다

편해 보여서 엔티티에 그냥 붙이는 경우가 많은데, 만들어내는 것이 생각보다 많다.

```java
@Data
public class Order {
    private Long id;
    private String name;
}
```

<br/>

일곱 줄짜리 소스인데 `javap` 로 열면 이렇다.

```java
public class Order {
  public Order();
  public java.lang.Long getId();
  public java.lang.String getName();
  public void setId(java.lang.Long);
  public void setName(java.lang.String);
  public boolean equals(java.lang.Object);
  protected boolean canEqual(java.lang.Object);
  public int hashCode();
  public java.lang.String toString();
}
```

<br/>

여기서 세 가지가 문제가 된다.

<br/>

### 첫번째) setter가 전부 열린다

`@Data` 는 모든 필드에 `setter` 를 만든다.

앞에서 봤듯이 아무 데서나 상태를 바꿀 수 있으면 불변식을 지킬 수가 없다.

<br/>

### 두번째) equals와 hashCode가 모든 필드를 쓴다

엔티티에 붙이면 `id` 가 없는 상태에서 저장하고 나면 `hashCode` 가 바뀐다.

앞에서 본 `Map 에 넣고 나서 키를 바꾸면 못 찾는` 상황이 그대로 재현된다.

<br/>

### 세번째) toString이 연관 객체를 따라간다

`Member` 가 `Team` 을 갖고 `Team` 이 `Member` 목록을 가지면 서로를 계속 따라간다.

앞의 DTO 글에서 본 `StackOverflowError` 가 여기서도 난다.

<br/>

그래서 엔티티에는 이렇게 최소한만 붙이는 편이 낫다.

```java
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Entity
public class Member { ... }
```

`@Data` 는 DTO처럼 정말 값만 담는 클래스에 쓰는 것이 맞다.
