## DBCP (DB connection pool)

요청이 한 두개가 아닌데, 매번 커넥션을 열었다가, 닫았다가 하는 과정은 시간적인 비용이 발생한다.

- 즉, `서비스 성능에 좋지 않다.`

![이미지](/programming/img/입문526.PNG)

<br/>

그렇게 생각하여, 나온 해결책이 DBCP 이다.

위 그림에서는 끊어주는 식으로 동작한 것이라면, 밑에 그림에서는 close가 

정말 연결을 끊어주는 것이 아니라, 커넥션 풀로 반납을 하게 되는 것이다.

![이미지](/programming/img/입문527.PNG)


<br/>

### 애플리케이션 서버를 띄울 때 DB 커넥션을 맺는다.

- 즉, 미리 DB 커넥션들을 만들어 놓는 것이다. (미리 연결 되어 있는 것이라고 생각하기)

```jsx
db를 들렸다가, 쿼리 응답을 받은 백엔드 서버는 커넥션을 처리해줘야 하는데,
여기서, 커넥션을 커넥션 풀로 반납한다고 생각하면 된다.

"커넥션 풀은 DBCP라고 부른다"
```
<br/>

## 궁금증!

```java
"시간적인 비용이 발생한다" 는데, 얼마나 드는 걸까?
```

같은 조회를 `매번 새로 연결해서` 와 `한 번 연결해서` 로 나눠 재봤다.

```java
매번 새로 연결 (200번) = 798 ms
한 번 연결해서 200번   =  27 ms
```

<br/>

`30` 배 차이다. 실제 쿼리는 똑같이 `200` 번 돌았는데도 그렇다.

<br/>

이 실험은 로컬 파일 DB라서 실제 환경보다 오히려 후한 편이다.

네트워크 너머의 DB에 연결하려면 이만큼이 더 든다.

```java
1. TCP 3-way handshake        (네트워크 왕복 1회)
2. DB 프로토콜 핸드셰이크
3. 아이디/비밀번호 인증        (네트워크 왕복 1~2회)
4. 세션 초기화 (문자셋, 타임존, 격리 수준 설정)
```

<br/>

DB가 다른 서버에 있으면 왕복 한 번에 수 밀리초씩 걸린다.

연결 하나 만드는 데 `10ms` 가 든다면, 초당 `1000` 개의 요청은 연결에만 `10` 초를 쓰는 셈이다.

<br/>

## 그래서 미리 만들어두고 빌려준다

원문의 `애플리케이션 서버를 띄울 때 미리 만들어놓는다` 가 이 문제의 해법이다.

```java
애플리케이션 시작 -> 커넥션 10 개를 미리 만들어둔다
요청이 오면       -> 풀에서 하나 빌려준다 (만드는 비용 0)
요청이 끝나면     -> 풀에 돌려준다 (끊지 않는다)
```

<br/>

`close()` 를 불러도 진짜로 안 끊는다는 것이 핵심이다.

<br/>

`DataSource.getConnection()` 이 돌려주는 것은 진짜 커넥션이 아니라 그것을 감싼 객체다.

`close()` 를 부르면 그 감싼 객체가 `진짜로 끊는` 대신 `풀에 반납` 한다.

앞의 AOP 글에서 본 프록시와 같은 발상이다.

```java
우리 코드   -> connection.close()
프록시      -> "닫으라는 건 알겠는데, 나는 풀에 돌려놓겠다"
진짜 커넥션 -> 그대로 살아 있다
```

<br/>

## 풀 크기는 몇 개가 적당한가

크게 잡을수록 좋을 것 같지만 아니다.

<br/>

커넥션 하나는 DB 쪽에도 자원을 잡는다.

DB가 감당할 수 있는 동시 연결 수를 넘으면 DB가 먼저 죽는다.

<br/>

그리고 커넥션이 많다고 처리량이 늘지 않는다.

DB가 실제로 동시에 처리할 수 있는 것은 결국 CPU 코어 수와 디스크 성능에 달려 있기 때문이다.

<br/>

HikariCP 문서가 권하는 계산식이 있다.

```java
커넥션 수 = (CPU 코어 수 × 2) + 디스크 개수
```

<br/>

코어 4개짜리 DB라면 `10` 개 정도다. 생각보다 훨씬 작다.

기본값도 대개 `10` 이다.

```java
spring.datasource.hikari.maximum-pool-size=10
```

<br/>

## 풀이 마르면 어떻게 되는가

빌려줄 커넥션이 없으면 요청은 대기한다.

정해진 시간 안에 못 얻으면 예외가 난다.

```java
SQLTransientConnectionException: HikariPool-1 - Connection is not available,
request timed out after 30000ms
```

<br/>

이 로그가 뜨면 커넥션이 부족한 것이 아니라 `누군가 오래 붙잡고 있는` 경우가 대부분이다.

<br/>

앞의 DB 락 글에서 본 것과 같은 원인이다.

```java
@Transactional
public void order() {
    orderRepository.save(order);
    externalApi.call();            // 여기서 3초
    // 그동안 커넥션을 붙잡고 있다
}
```

<br/>

트랜잭션이 시작되면 커넥션을 하나 잡고 끝날 때까지 안 놓는다.

외부 API 호출을 트랜잭션 안에 두면 그 시간만큼 커넥션이 묶인다.

<br/>

풀 크기를 키우면 잠깐 버티겠지만 근본 해결이 아니다.

트랜잭션을 짧게 만드는 것이 맞다.

```java
풀 크기를 키운다  -> 증상만 미룬다
트랜잭션을 줄인다 -> 원인을 없앤다
```

<br/>

## 커넥션이 살아 있는지도 확인해야 한다

풀에 오래 놀고 있던 커넥션은 이미 끊겨 있을 수 있다.

DB나 중간의 방화벽이 유휴 연결을 일정 시간 뒤에 끊어버리기 때문이다.

<br/>

빌려줄 때 살아 있는지 확인하지 않으면, 애플리케이션이 죽은 커넥션을 받아서 실패한다.

```java
spring.datasource.hikari.max-lifetime=1800000     # 30분마다 커넥션을 새로 만든다
spring.datasource.hikari.idle-timeout=600000      # 10분 놀면 정리한다
```

<br/>

`max-lifetime` 은 DB의 연결 유지 시간보다 짧게 잡아야 한다.

MySQL의 `wait_timeout` 이 `600` 초인데 `max-lifetime` 이 `1800` 초면,

DB가 먼저 끊어버린 커넥션을 애플리케이션이 계속 들고 있게 된다.
