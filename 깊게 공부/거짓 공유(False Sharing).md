## 거짓 공유(False Sharing)

<br/>

## 캐시 라인

앞의 ‘메모리에 적재’ CPU의 연산 글에서 본 대로, CPU는 메모리를 한 바이트씩 가져오지 않는다.

한 줄씩 가져온다. 그 줄이 캐시 라인이고 보통 64바이트다. 이 맥은 128바이트다.

```java
변수 하나를 읽으면 -> 그 옆의 변수들까지 같은 줄에 실려 캐시에 올라온다
```

<br/>

순서대로 읽을 때 빠른 이유였다. 다음 값이 이미 캐시에 있으니까.

<br/><br/>

## 코어마다 캐시가 따로 있다

```java
코어 1 - L1 캐시 - 캐시 라인 X 의 복사본
코어 2 - L1 캐시 - 캐시 라인 X 의 복사본
```

<br/>

두 코어가 같은 줄을 각자 들고 있다.

한쪽이 그 줄의 무언가를 바꾸면, 다른 쪽 복사본은 낡은 것이 된다.

그래서 CPU는 `이 줄은 이제 무효다` 를 다른 코어에게 알리고, 다른 코어는 그 줄을 다시 가져와야 한다.

<br/>

이걸 캐시 일관성 프로토콜이라고 한다.

앞의 동시성 문제 해결 방법 글에서 본 `volatile 이 다른 스레드의 변경을 보이게 한다` 가 이 위에서 동작하는 것이다.

<br/><br/>

## 궁금증!

```java
공유하지 않는 변수인데 옆에 붙어 있으면 느려지나
```

두 스레드가 각자 자기 변수만 1억 번 증가시킨다. 서로 남의 변수는 건드리지 않는다.

```java
static class Adjacent { volatile long a; volatile long b; }      // 나란히 붙어 있다

스레드 1 : for (...) adj.a++;
스레드 2 : for (...) adj.b++;
```

<br/>

그리고 두 변수 사이에 빈칸을 넣은 버전을 만들었다.

```java
static class Padded { volatile long a; long p1, ..., p15; volatile long b; }   // 120바이트 띄웠다
```

<br/>

### 결과

```java
a, b 가 메모리에서 나란히 붙어 있을 때   = 2677 ms
a, b 사이에 120바이트 빈칸을 넣었을 때   =  608 ms   <- 4.4 배
```

<br/>

빈칸을 넣었을 뿐인데 4.4배 빨라졌다.

<br/>

비교 기준으로 스레드 하나가 변수 하나를 1억 번 증가시키면 596ms다.

```java
스레드 1개, 변수 1개              = 596 ms
스레드 2개, 변수 2개 (띄움)        = 608 ms   <- 병렬이라 거의 같다
스레드 2개, 변수 2개 (붙음)        = 2677 ms  <- 하나일 때보다 4.5배 느리다
```

<br/>

스레드를 둘로 나눴는데 하나일 때보다 느려졌다.

<br/><br/>

## 왜 이런가

`a` 와 `b` 가 같은 캐시 라인에 있기 때문이다.

```java
코어 1 이 a 를 바꾼다 -> 그 줄 전체가 무효 -> 코어 2 의 복사본이 낡음
코어 2 가 b 를 바꾸려면 -> 그 줄을 다시 가져와야 한다 -> 그리고 바꾸면 코어 1 의 복사본이 낡음
코어 1 이 a 를 바꾸려면 -> 또 다시 가져온다
```

<br/>

서로 다른 변수를 건드리는데, 같은 줄이라 서로의 캐시를 계속 무효화하는 것이다.

공유하지 않는데 공유하는 것처럼 비용을 내니 `거짓 공유` 라고 부른다.

<br/>

빈칸을 넣으면 `a` 와 `b` 가 다른 줄에 들어가서 이 핑퐁이 사라진다.

<br/><br/>

## 실무에서 어디에 나오나

```java
스레드마다 카운터를 따로 두는데 배열에 나란히 넣은 경우
   long[] counters = new long[threadCount];      // counters[0] 과 counters[1] 이 같은 줄

객체 배열에서 스레드마다 다른 원소를 갱신하는 경우
```

<br/>

`스레드마다 따로 두면 경쟁이 없으니 빠르겠지` 하고 만든 구조가 오히려 느려지는 것이다.

앞의 동시성  동기화 글에서 본 `공유를 없애면 동기화가 필요 없다` 는 맞는데, 메모리에서도 떨어뜨려야 한다는 조건이 붙는다.

<br/><br/>

## 자바가 해결해준 것

```java
@jdk.internal.vm.annotation.Contended
```

<br/>

이 어노테이션을 붙이면 JVM이 앞뒤로 빈칸을 넣어준다.

내부용이라 일반 코드에서 쓰려면 `-XX:-RestrictContended` 옵션이 필요하다.

<br/>

JDK 안에서는 이미 쓰고 있다.

```java
ConcurrentHashMap 의 CounterCell   - 스레드마다 나눠 세는 카운터. @Contended 가 붙어 있다
ForkJoinPool 의 WorkQueue
Thread 의 난수 생성 필드
```

<br/>

앞의 CAS 알고리즘 설명 글에서 본 `AtomicLong` 의 `LongAdder` 버전이 이 기법을 쓴다.

```java
AtomicLong  - 변수 하나를 모든 스레드가 CAS. 경쟁이 심하면 재시도 폭증
LongAdder   - 스레드마다 칸을 따로 두고 (@Contended) 읽을 때 합친다
```

<br/>

경쟁이 심한 카운터는 `LongAdder` 가 훨씬 빠른 이유가 이것이다.

<br/><br/>

## 정리

```java
캐시는 줄 단위로 움직인다 (64~128 바이트)
다른 변수라도 같은 줄이면 한 코어의 쓰기가 다른 코어의 캐시를 무효화한다
그래서 "공유 안 하는 변수" 가 공유하는 것처럼 느려진다
해결은 빈칸으로 띄우기. JDK 는 @Contended 로 한다
```

<br/>

앞의 선형 리스트 글에서 `배열이 캐시에 잘 맞아서 빠르다` 고 했는데, 그 성질이 멀티 스레드에서는 거꾸로 함정이 되는 경우인 셈이다.
