## 실수 표현과 부동소수점

<br/>

## 0.1 은 2진수로 딱 떨어지지 않는다

```java
0.1 + 0.2 = 0.30000000000000004      (== 0.3 ? false)
```

<br/>

10진수 `1/3` 이 `0.3333...` 으로 끝나지 않는 것처럼, 2진수로 `0.1` 은 `0.0001100110011...` 로 끝나지 않는다.

<br/>

`double` 은 64비트라 어딘가에서 잘라야 한다.

```java
0.1 의 실제 저장값 = 0.1000000000000000055511151231257827021181583404541015625
```

<br/>

`0.1` 이라고 썼는데 저장된 것은 저 값이다. 조금 크다.

`0.2` 도 조금 크고, 둘을 더하면 오차가 눈에 보이는 자리까지 올라온다.

<br/><br/>

## 궁금증!

```java
오차가 어디까지 문제가 되나
```

<br/>

### 큰 수 옆의 작은 수는 사라진다

```java
1e16 + 1 = 1.0E16                          <- 1 이 사라졌다
double 이 정확히 표현하는 정수 상한 = 2^53 = 9007199254740992
9007199254740993 을 double 로 = 9007199254740992      <- 1 이 빠졌다
```

<br/>

`double` 은 유효 숫자가 약 15~16자리다. 그 이상은 반올림된다.

<br/>

앞의 데이터타입, 변수 글에서 본 자바스크립트의 `Number.MAX_SAFE_INTEGER` 가 정확히 이 `2^53` 이다.

자바스크립트는 숫자가 전부 `double` 이라 `long` ID를 JSON으로 보내면 여기서 깨진다.

<br/>

### 누적하면 쌓인다

```java
0.1 을 100만 번 더하면 = 100000.00000133288     (정답 100000)
BigDecimal("0.1") 로   = 100000.0
```

<br/>

한 번의 오차는 `10^-17` 인데 100만 번 쌓이니 `10^-6` 이 됐다.

금액을 `double` 로 누적하면 이렇게 된다.

<br/><br/>

## float 는 더 심하다

```java
0.1f (float) = 0.100000001490116119384765625
```

<br/>

`double` 은 `0.1000000000000000055`, `float` 는 `0.1000000015` 다.

`float` 는 32비트라 유효 숫자가 7자리다.

<br/>

`float` 를 쓸 이유가 거의 없다. 메모리가 절반이라는 것 말고는 전부 불리하다.

그래픽이나 머신러닝처럼 정밀도보다 개수가 중요한 곳에서만 쓴다.

<br/><br/>

## 금액은 BigDecimal 로

```java
new BigDecimal("0.1")     = 0.1                         <- 문자열로
new BigDecimal(0.1)       = 0.10000000000000000555      <- double 의 오차를 그대로 가져온다
```

<br/>

`BigDecimal` 을 써도 `double` 로 만들면 소용없다. 이미 오차가 들어간 값을 받는 것이다.

문자열이나 `BigDecimal.valueOf(double)` 을 써야 한다.

<br/>

앞의 Comparable과 Comparator 글에서 본 대로 `BigDecimal` 은 `equals` 와 `compareTo` 가 다르다.

```java
new BigDecimal("1.0").equals(new BigDecimal("1.00"))     -> false
new BigDecimal("1.0").compareTo(new BigDecimal("1.00"))  -> 0
```

<br/>

금액 비교는 `compareTo` 로 해야 한다.

<br/>

나눗셈은 `scale` 과 `RoundingMode` 를 정해줘야 한다.

```java
new BigDecimal("10").divide(new BigDecimal("3"))                          // ArithmeticException. 무한소수
new BigDecimal("10").divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP)  // 3.33
```

<br/>

`어디서 자를지` 를 안 정하면 자를 수가 없어서 예외가 나는 것이다.

<br/><br/>

## 정수로 다루는 방법도 있다

```java
1234 원  -> long 1234
12.34 달러 -> long 1234 (센트 단위)
```

<br/>

최소 단위를 정수로 저장하고 표시할 때만 나눈다.

`BigDecimal` 보다 빠르고 단순하다. 화폐 단위가 고정이면 이쪽이 낫다.

<br/>

앞의 자바스크립트(JS) 글에서 본 대로 자바스크립트는 `BigDecimal` 이 없어서 이 방법을 쓴다.

<br/><br/>

## 비교와 특수 값

```java
NaN == NaN                   -> false      (자기 자신과도 다르다)
0.0 == -0.0                  -> true
Double.compare(0.0, -0.0)    -> 1          (compare 는 구분한다)
1.0 / 0                      -> Infinity   (예외 아님. 정수 1/0 은 ArithmeticException)
```

<br/>

앞의 래퍼(wrapper) 클래스 글에서 본 `NaN` 얘기다.

`==` 로 `NaN` 을 확인할 수 없으니 `Double.isNaN()` 을 쓴다.

<br/>

`double` 끼리 같은지 비교할 때는 `==` 대신 허용 오차를 둔다.

```java
Math.abs(a - b) < 1e-9
```

<br/>

`0.1 + 0.2 == 0.3` 이 `false` 인 것을 봤으니, `==` 는 계산 결과에 쓰면 안 된다.

<br/><br/>

## 어디서 double 을 써도 되나

```java
좌표, 물리량, 통계, 확률    -> double. 근사값이 본질이다
금액, 수량, 비율(%)       -> BigDecimal 또는 정수. 정확해야 한다
```

<br/>

`정확한 값` 이 필요한 곳과 `근사값` 으로 충분한 곳을 나누는 것이다.

<br/>

DB도 같다.

```java
DOUBLE, FLOAT   -> 근사
DECIMAL(19, 4)  -> 정확. 금액 컬럼은 이것
```

<br/>

앞의 attribute data type 정의 글에서 본 대로 컬럼 타입을 정할 때 이 판단이 들어간다.

금액을 `DOUBLE` 로 만든 테이블은 나중에 합계가 안 맞는 문의를 받게 된다.

<br/><br/>

## 정리

```java
0.1 은 2 진수로 무한소수. double 은 근사값을 저장한다
유효 숫자 약 16 자리. 2^53 넘는 정수는 정확하지 않다
금액은 BigDecimal(문자열) 또는 최소 단위 정수. double 누적 금지
비교는 == 대신 오차 범위. NaN 은 isNaN()
```

<br/>

앞의 분기 예측 글에서 본 대로 CPU는 이 계산을 매우 빠르게 한다.

빠른 대신 정확하지 않은 것이라, 무엇이 필요한지에 따라 고르는 것이다.
