## IO 모델 - Blocking IO, NIO, 멀티플렉싱

<br/>

## 소켓에서 읽는다는 것

```java
InputStream in = socket.getInputStream();
int b = in.read();          // 데이터가 올 때까지 여기서 멈춘다
```

<br/>

상대가 아직 아무것도 안 보냈으면 `read()` 는 돌아오지 않는다.

앞의 sync(동기) vs async(비동기) 글에서 본 Blocking이다.

<br/>

멈춰 있는 동안 이 스레드는 아무것도 못 한다.

앞의 스레드의 상태 글에서 본 대로 자바에서는 `RUNNABLE` 로 보이지만, 실제로는 운영체제가 잠재우고 있다.

<br/><br/>

## 접속이 1000 개면

접속마다 `read()` 에서 멈춰 있는 스레드가 하나씩 필요하다.

```java
접속 1000 개 -> 스레드 1000 개 -> 대부분 read() 에서 잠들어 있다
```

<br/>

앞의 process를 설명해 주세요 글에서 본 대로 스레드 하나가 스택 1MB를 예약한다.

그리고 앞의 context switch vs Context 글에서 본 대로, 깨어나고 잠드는 데 스위치가 든다.

<br/>

접속 1만 개면 스레드 1만 개다. 앞의 가상 스레드 글에서 본 대로 여기서 `unable to create native thread` 가 난다.

<br/><br/>

## 궁금증!

```java
같은 일을 스레드 1000개로 하는 것과 1개로 하는 것을 나란히 돌려봤다
```

클라이언트 1000개가 동시에 접속해서 한 줄 보내고 그대로 돌려받는다.

<br/>

### BIO : 접속마다 스레드 하나

```java
while (true) {
    Socket s = ss.accept();
    new Thread(() -> { 읽고 -> 쓰고 -> 닫기 }).start();
}
```

<br/>

### NIO : 스레드 하나가 Selector 로 전부

```java
Selector sel = Selector.open();
serverChannel.register(sel, OP_ACCEPT);

while (true) {
    sel.select();                                  // 준비된 것이 생길 때까지만 기다린다
    for (SelectionKey k : sel.selectedKeys()) {
        if (k.isAcceptable()) { 접속 받고 -> OP_READ 로 등록 }
        else if (k.isReadable()) { 읽고 -> 쓰고 -> 닫기 }
    }
}
```

<br/>

### 결과

```java
[BIO]  응답 전부 받음 = 257 ms, 서버가 만든 스레드 = 1000 개  (접속 수만큼)
[NIO]  응답 전부 받음 =  91 ms, 서버가 만든 스레드 = 1 개, select() 호출 = 1312 번, 한 번에 최대 3 개 준비됨
```

<br/>

같은 일을 스레드 1000개가 하던 것을 1개가 했고, 오히려 더 빨랐다.

<br/><br/>

## select() 가 하는 일

`select()` 는 `등록된 소켓 중 지금 읽을 수 있는 것이 있나` 를 운영체제에 한 번에 물어보는 시스템 콜이다.

```java
소켓 1000개를 각각 read() -> 1000번 물어본다. 대부분 "아직 없다"
select() 한 번           -> "3번, 17번, 250번이 준비됐다" 를 한 번에 받는다
```

<br/>

앞의 시스템 콜과 유저 모드, 커널 모드 글에서 본 대로 시스템 콜 한 번이 600ns다.

1000개를 매번 물어보는 것과 준비된 것만 알려받는 것의 차이가 여기서 나온다.

<br/>

여러 소켓을 하나로 묶어 감시한다는 뜻에서 멀티플렉싱이라고 부른다.

리눅스에서는 `epoll`, macOS에서는 `kqueue` 라는 시스템 콜이 이 일을 한다. 자바 `Selector` 가 그 위에 얹혀 있다.

<br/>

위 실험에서 `select()` 가 1312번 불렸고 한 번에 최대 3개가 준비됐다.

접속이 순차적으로 들어와서 그런 것이고, 부하가 몰리면 한 번에 수백 개가 준비되어 호출 횟수는 더 준다.

<br/><br/>

## Non-Blocking 이 필요한 이유

NIO에서 소켓을 `configureBlocking(false)` 로 두는 이유가 있다.

```java
select() 가 "17번 준비됐다" 고 했는데
17번을 read() 하는 순간 데이터가 아직 다 안 왔으면 -> Blocking 이면 여기서 멈춘다
-> 스레드가 하나뿐이니 다른 999개도 전부 멈춘다
```

<br/>

Non-Blocking이면 `read()` 가 `지금 읽을 것 없음` 을 돌려주고 바로 다음으로 간다.

스레드 하나로 전부 처리하려면 그 하나가 절대 멈추면 안 되는 것이다.

<br/>

앞의 sync(동기) vs async(비동기) 글에서 본 네 조합 중, NIO는 `Non-Blocking + Sync` 에 `select` 라는 알림을 붙인 것이다.

`isDone()` 을 계속 물어보는 대신 운영체제가 준비된 것을 알려주니, 폴링의 CPU 낭비가 없다.

<br/><br/>

## 그럼 스레드 하나로 다 하나

핸들러 안에서 오래 걸리는 일을 하면 안 된다.

```java
else if (k.isReadable()) {
    읽고
    DB 조회 (100ms)          // 이 동안 나머지 999개가 전부 기다린다
    쓰고
}
```

<br/>

앞의 이벤트 글에서 본 자바스크립트의 `for 문 10억 번 돌리면 클릭이 안 된다` 가 정확히 이 상황이다.

<br/>

그래서 실제 NIO 서버는 이렇게 나눈다.

```java
I/O 스레드 몇 개  - select 하고 읽고 쓰기만. 절대 오래 걸리는 일 안 함
작업 스레드 풀    - DB 조회 같은 느린 일은 여기로 넘긴다
```

<br/>

Netty가 이 구조다. 스프링 WebFlux가 그 위에서 돈다.

<br/><br/>

## 그래도 톰캣은 왜 스레드 풀인가

톰캣도 접속 받는 부분은 NIO를 쓴다. 기본이 `Http11NioProtocol` 이다.

```java
접속 대기, 요청 읽기  -> NIO (스레드 몇 개)
요청 처리            -> 스레드 풀 200개 (여기서 컨트롤러가 돈다)
```

<br/>

컨트롤러 안에서 JDBC로 DB를 부르면 그게 Blocking이라, 그 스레드는 어차피 멈춘다.

전체를 Non-Blocking으로 하려면 DB 드라이버까지 전부 바꿔야 하는데, 그러면 앞의 sync(동기) vs async(비동기) 글에서 본 콜백 지옥이 온다.

<br/>

그래서 요청 처리는 `Blocking + 스레드 풀` 로 두고 코드를 쉽게 유지한 것이다.

접속 수백 개 수준에서는 이게 충분하다.

<br/><br/>

## 세 모델 정리

```java
BIO         - 접속마다 스레드. 코드 쉬움. 접속 수천 개에서 한계
NIO (멀티플렉싱) - 스레드 몇 개가 select 로 전부 감시. 접속 수만 개 가능. 코드 어려움
AIO         - 운영체제가 읽기까지 끝내고 알려준다. 자바 AsynchronousSocketChannel. 잘 안 쓰인다
```

<br/>

앞의 가상 스레드 글에서 본 가상 스레드가 이 셈법을 바꾼다.

`BIO 코드` 를 그대로 쓰는데 JVM이 안에서 `NIO` 처럼 운영체제 스레드를 아껴주기 때문이다.

BIO의 쉬운 코드와 NIO의 적은 스레드를 둘 다 가지려는 시도인 셈이다.
