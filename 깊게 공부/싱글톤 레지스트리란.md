## 싱글톤 레지스트리란?

<br/>

## 빈을 생성하는 방식 - 싱글톤 레지스트리

스프링은 기본적으로 별다른 `설정`을 하지 않으면, 

내부에서 `생성`하는 빈들을 모두 `싱글톤`으로 만든다.

<br/>

### 생각해보기.

```java
매번 클라이언트에서 요청이 올 때마다 서버에서 
각 로직을 담당하는 객체를 새로 만든다고 가정해보자.
```

요청 한 번에 `5개`의 빈을 새로 만든다고 가정했을 때,

초당 `500개`의 요청이 들어오면 `2500개`의 새로운 빈이 생성되는 것이다.

<br/>

아무리, 가비지 컬렉션이 있다 하더라도, 계속 누적되면 

그만큼 서버가 자원 소모를 많이 해야 하므로 비효율적인 방식이다.

<br/>

### 그리하여,

처음 `한번 생성`해두면 애플리케이션이 `종료`될 때까지 추가적인 

생성 작업이 필요 없는 것인데, 이것이 `싱글톤` 방식이며, 서버환경에서 권장하는 것이다.

<br/><br/>

## 싱글톤 레지스트리란?

기존 싱글톤 패턴의 단점을 보완하는 것이 `”싱글톤 레지스트리”` 라 한다.

기존 싱글톤 패턴의 단점 때문에 스프링에서는 직접 싱글톤 형태의 빈을 만들고 관리하는 기능을 제공한다.



```java
"이를 싱글톤 레지스트리(Singleton Registry)라고 한다."
```

<br/>

이는 기존에, 싱글톤을 구현하기 위한 코드인 `스태틱 메서드`와 `private 생성자`를 

사용해야 하는 클래스가 아니라, 평범한 `자바 클래스`를 `싱글톤`으로 활용하게 해준다.

<br/>

이 덕분에 `public 생성자`를 구현할 수 있어서 `생성자 파라미터`로 

의존관계 주입이 가능하고, 테스트 시 모의 객체도 생성이 가능하다.
<br/>

## 궁금증!

```java
"평범한 자바 클래스를 싱글톤으로 만들어준다" 는 게 어떤 방식일까?
```

`@Configuration` 이 붙은 설정 클래스를 꺼내보면 힌트가 나온다.

```java
AnnotationConfigApplicationContext context = new AnnotationConfigApplicationContext(AppConfig.class);
System.out.println(context.getBean(AppConfig.class).getClass().getName());
```

<br/>

### 결과

```java
demo.AppConfig$$SpringCGLIB$$0
```

<br/>

내가 만든 `AppConfig` 가 아니라 `AppConfig$$SpringCGLIB$$0` 이라는 처음 보는 클래스가 나온다.

스프링이 내 설정 클래스를 상속받은 자식 클래스를 실행 중에 만들어서 대신 등록해둔 것이다.

<br/>

## 그 자식 클래스가 하는 일

`@Bean` 메서드를 가로채서 `이미 만든 게 있으면 그걸 주는` 코드로 감싼다.

<br/>

이걸 확인하려고 `@Configuration` 이 있을 때와 없을 때를 비교해봤다.

```java
@Configuration
class WithConfiguration {
    @Bean Repo2 repo() { return new Repo2(); }
    @Bean ServiceA serviceA() { return new ServiceA(repo()); }   // repo() 를 직접 호출
    @Bean ServiceB serviceB() { return new ServiceB(repo()); }   // 여기서도 호출
}

class WithoutConfiguration {         // @Configuration 을 뗐다
    @Bean Repo2 repo() { return new Repo2(); }
    @Bean ServiceA serviceA() { return new ServiceA(repo()); }
    @Bean ServiceB serviceB() { return new ServiceB(repo()); }
}
```

<br/>

`Repo2` 의 생성자에 카운터를 넣어서 몇 번 만들어지는지 셌다.

<br/>

### 결과

```java
--- @Configuration 있음 ---
  설정 클래스 = WithConfiguration$$SpringCGLIB$$0
  A가 받은 repo == B가 받은 repo : true
  repo() 가 실제로 실행된 횟수 : 1

--- @Configuration 없음 ---
  설정 클래스 = WithoutConfiguration
  A가 받은 repo == B가 받은 repo : false
  repo() 가 실제로 실행된 횟수 : 3
```

<br/>

`@Configuration` 이 없으면 `repo()` 가 세 번 실행되고 객체도 세 개 만들어진다.

자바 코드로만 보면 이게 당연하다. 메서드를 세 번 불렀으니 세 번 도는 것이다.

<br/>

`@Configuration` 이 있으면 한 번만 실행된다.

CGLIB 자식 클래스가 `repo()` 호출을 가로채서, 두 번째부터는 컨테이너에 있는 것을 꺼내 주기 때문이다.

```java
repo() 호출
  -> CGLIB 자식이 가로챈다
  -> "repo 라는 이름의 빈이 컨테이너에 이미 있나?"
     있으면 -> 그걸 반환 (부모 메서드를 실행하지 않는다)
     없으면 -> 부모의 진짜 repo() 를 실행하고, 결과를 컨테이너에 넣어둔다
```

<br/>

## 이게 왜 "레지스트리" 인가

원문의 `스태틱 메서드와 private 생성자를 쓰지 않아도 된다` 는 부분이 여기서 이어진다.

<br/>

전통적인 싱글톤 패턴은 클래스 자신이 싱글톤이 되는 방법을 알고 있어야 한다.

```java
public class Service {
    private static final Service INSTANCE = new Service();

    private Service() { }               // 생성자를 막는다

    public static Service getInstance() {
        return INSTANCE;
    }
}
```

<br/>

이렇게 하면 문제가 몇 가지 생긴다.

- 생성자가 `private` 이라 상속도 못 하고 의존성을 주입받을 수도 없다

- 테스트할 때 가짜 구현으로 바꿔치기 할 수가 없다
- 클래스마다 이 코드를 반복해야 한다
- `getInstance()` 를 부르는 쪽이 구체 클래스를 직접 알게 된다

<br/>

스프링은 이걸 클래스 밖으로 빼냈다.

클래스는 평범하게 두고, `누가 몇 개인지` 는 컨테이너가 장부에 적어 관리한다.

```java
싱글톤 패턴     -> 클래스가 스스로 하나임을 보장한다
싱글톤 레지스트리 -> 클래스는 평범하고, 컨테이너가 하나만 만들어 들고 있는다
```

<br/>

`레지스트리` 는 장부라는 뜻이다.

`빈 이름 -> 객체` 를 적어둔 장부를 하나 두고, 요청이 오면 거기서 꺼내주는 것이다.

<br/>

실제로 그 장부는 `DefaultSingletonBeanRegistry` 안의 `Map` 하나다.

```java
private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);
```

<br/>

## 싱글톤이라서 조심할 것

객체가 하나뿐이라는 말은, 모든 요청이 같은 객체를 같이 쓴다는 뜻이다.

```java
@Service
public class OrderService {
    private int count;              // 위험하다

    public void order() {
        count++;                    // 여러 스레드가 동시에 건드린다
    }
}
```

<br/>

앞의 동시성 글에서 본 것과 똑같은 문제가 그대로 생긴다.

초당 수백 개의 요청이 같은 `count` 를 올리면 값이 어긋난다.

<br/>

그래서 스프링 빈에는 상태를 두지 않는다.

값이 필요하면 메서드의 지역 변수나 파라미터로 다룬다. 지역 변수는 스레드마다 따로이기 때문이다.

```java
빈이 가져도 되는 것 -> 안 바뀌는 것 (final 로 주입받은 의존성, 설정값)
빈이 가지면 안 되는 것 -> 요청마다 달라지는 것
```
