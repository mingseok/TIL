## 문자 인코딩과 한글 깨짐

<br/>

## 문자는 숫자로 저장된다

`가` 라는 글자에는 번호가 있다. 유니코드 `U+AC00`, 십진수 44032다.

앞의 char타입은 정수인가 글에서 본 그 번호다.

<br/>

그 번호를 바이트로 어떻게 적을지가 인코딩이다.

```java
UTF-8       - 영문 1바이트, 한글 3바이트. 가변 길이
EUC-KR      - 영문 1바이트, 한글 2바이트. 한글만 표현
UTF-16      - 대부분 2바이트, 이모지는 4바이트
ISO-8859-1  - 서유럽 문자만. 한글 표현 불가
```

<br/><br/>

## 궁금증!

```java
같은 문자열이 인코딩마다 어떻게 되나
```

`"한글A"` 를 네 가지로 바꿔봤다.

<br/>

### 결과

```java
UTF-8       =  7 바이트 : ed 95 9c  ea b8 80  41
EUC-KR      =  5 바이트 : c7 d1  b1 db  41
UTF-16      =  8 바이트 : fe ff  d5 5c  ae 00  00 41
ISO-8859-1  =  3 바이트 : 3f 3f 41
```

<br/>

`A` 는 전부 `41` 이다. 영문은 어디서든 같다.

<br/>

`한` 은 UTF-8에서 3바이트, EUC-KR에서 2바이트다. 같은 글자인데 바이트가 다르다.

<br/>

ISO-8859-1은 `3f 3f` 다. `?` 두 개다. 한글을 표현할 수 없어서 물음표로 바꿔버렸다.

정보가 이 순간 사라졌다.

<br/>

UTF-16 앞의 `fe ff` 는 BOM이다. 앞의 엔디언(Byte Order) 글에서 본 대로 바이트 순서를 알리는 표시다.

<br/><br/>

## 깨지는 순간

쓴 인코딩과 읽는 인코딩이 다를 때다.

```java
UTF-8 로 쓴 바이트를 EUC-KR 로 읽으면      = ��湲�A
UTF-8 로 쓴 바이트를 ISO-8859-1 로 읽으면  = íê¸A         <- 흔히 보는 모양
EUC-KR 로 쓴 바이트를 UTF-8 로 읽으면      = �ѱ�A
```

<br/>

같은 바이트인데 규칙을 다르게 적용하니 다른 글자가 나온다.

<br/>

`íê¸` 는 UTF-8 3바이트 `ed 95 9c` 를 1바이트씩 ISO-8859-1 글자로 읽은 것이다.

한글 한 글자가 알 수 없는 세 글자가 된다. 웹에서 `ã«ìí` 같은 게 나오면 이 경우다.

<br/>

`�` 는 `해석 불가` 를 뜻하는 대체 문자(U+FFFD)다.

<br/><br/>

## 한 번 깨지면 안 돌아온다

```java
깨진 문자열을 다시 EUC-KR 바이트로 = 3f 3f 3f 41     (원본 c7 d1 b1 db 41)
```

<br/>

깨진 것을 다시 인코딩하면 `?` 만 나온다.

<br/>

디코딩할 때 `�` 로 바뀌면서 원래 바이트가 사라졌기 때문이다.

`�` 는 `무엇이었는지 모른다` 는 뜻이라 되돌릴 정보가 없다.

<br/>

깨진 데이터가 DB에 들어갔으면 원본 바이트를 다시 받는 것 말고 복구 방법이 없다.

<br/><br/>

## 어디에서 깨지나

바이트가 글자로 바뀌는 모든 경계다.

```java
HTTP 요청 본문   -> Content-Type 의 charset. 없으면 기본값 (서블릿은 ISO-8859-1 이었다)
HTTP 응답        -> 서버가 붙인 charset 과 브라우저 해석
파일 읽기        -> new FileReader(f) 는 기본 인코딩. 명시하지 않으면 OS 따라 다르다
DB 연결          -> 커넥션 문자셋. MySQL 의 characterEncoding=UTF-8
DB 컬럼          -> 테이블 문자셋. utf8 vs utf8mb4
콘솔 출력        -> 터미널 인코딩
```

<br/>

앞의 HttpServletRequest, HttpServletResponse 글에서 본 `request.setCharacterEncoding` 을 `getParameter` 전에 해야 하는 이유가 이것이다.

한 번 ISO-8859-1로 디코딩되면 끝이다.

<br/><br/>

## 자바 18 부터 조금 편해졌다

```java
Charset.defaultCharset() = UTF-8
file.encoding = UTF-8, native.encoding = UTF-8
```

<br/>

자바 18 이전에는 `defaultCharset` 이 OS를 따라갔다. 윈도우는 `MS949`, 리눅스는 `UTF-8`.

같은 코드가 윈도우 개발 PC에서는 되고 리눅스 서버에서 깨지는 일이 흔했다.

앞의 자바 가상머신(JVM) 글에서 본 그 얘기다.

<br/>

18부터는 어디서든 UTF-8이 기본이다. 그래도 명시하는 습관이 낫다.

```java
new String(bytes, StandardCharsets.UTF_8)
str.getBytes(StandardCharsets.UTF_8)
Files.readString(path, StandardCharsets.UTF_8)
```

<br/><br/>

## length() 가 글자 수가 아니다

```java
"한글😀".length()       = 4      <- 3 이 아니다
codePointCount          = 3      <- 실제 글자 수
UTF-8 바이트 수          = 10
```

<br/>

이모지는 유니코드 번호가 `char` 하나(16비트)에 안 들어간다. `char` 두 개로 쪼개서 담는다. 서로게이트 쌍이라고 한다.

`length()` 는 `char` 개수라 4다.

<br/>

`substring` 으로 자르면 이모지 한복판에서 잘려서 깨진다.

글자 단위로 다루려면 `codePoints()` 를 써야 한다.

<br/>

DB `VARCHAR(10)` 이 바이트 기준이면 한글은 3글자밖에 못 들어간다.

MySQL의 `utf8` 은 3바이트까지만 지원해서 이모지가 안 들어간다. `utf8mb4` 를 써야 한다.

앞의 문자열 연산 글에서 본 그 함정이다.

<br/><br/>

## 정리

```java
글자는 번호, 인코딩은 그 번호를 바이트로 적는 규칙
깨짐 = 쓴 규칙과 읽는 규칙이 다름. 한 번 깨지면 복구 불가
경계마다 UTF-8 을 명시한다. HTTP, 파일, DB 연결, 컬럼
length() 는 char 수. 이모지는 2. DB 는 utf8mb4
```
