## 어댑터 패턴

<br/>

어댑터를 사용하여 호환되지 않는 인터페이스를 호환되도록 하는 패턴입니다.

향후에 인터페이스가 바뀌더라도 변경된 내용이 어댑터 안에 캡슐화되므로 수정할 필요가 없습니다.

![이미지](/programming/img/입문412.PNG)

<br/><br/>

## 이런 느낌

자동차와 수레(?)는 연관 지을 수 없는 두 객체인데, 어댑터를 통해 연관 관계를 만들게 된것이다.

![이미지](/programming/img/입문413.PNG)

참고 자료 : https://refactoring.guru/ko/design-patterns/adapter

<br/><br/>

## 장점

- 개방/폐쇄 원칙.

    - 기존의 클라이언트 코드를 손상시키지 않고

    - 새로운 유형의 어댑터들을 프로그램에 도입할 수 있습니다.

<br/><br/>

## 단점

다수의 새로운 인터페이스와 클래스들을 도입해야 하므로 코드의 전반적인 복잡성이 증가합니다.
<br/>

## 궁금증!

```java
어댑터를 왜 굳이 만드나
```

한쪽을 못 고칠 때 쓰기 때문이다.

```java
외부 라이브러리   - 내가 못 고친다
레거시 코드      - 고치면 다른 데가 깨진다
표준 인터페이스   - 고치면 안 된다
```

<br/>

양쪽 다 고칠 수 있으면 어댑터가 필요 없다. 그냥 맞추면 된다.

<br/>

## 자바 안에 실제 예가 있다

```java
InputStream in = new FileInputStream("a.txt");     // 바이트 단위
Reader reader = new InputStreamReader(in);         // 문자 단위로 바꿔준다
```

<br/>

`InputStreamReader` 가 어댑터다.

바이트를 다루는 것을 문자를 다루는 것처럼 쓰게 해준다.

<br/>

앞의 스트림(Stream) 글에서 본 그 구조다.

```java
바이트 스트림 - InputStream, OutputStream
문자 스트림   - Reader, Writer
그 사이       - InputStreamReader, OutputStreamWriter
```

<br/>

이름에 두 타입이 다 들어가 있다. `InputStream` 을 `Reader` 로 바꾼다는 뜻이다.

<br/>

`Arrays.asList()` 도 어댑터다.

```java
String[] array = {"a", "b"};
List<String> list = Arrays.asList(array);
```

<br/>

배열을 `List` 처럼 쓰게 해준다.

다만 진짜 `List` 가 아니라서 `add` 를 하면 터진다.

```java
UnsupportedOperationException
```

<br/>

배열은 크기가 고정이니 늘릴 방법이 없기 때문이다.

앞의 SOLID 글에서 본 `LSP` 위반의 또 다른 예이기도 하다.

<br/>

## 스프링에도 있다

```java
HandlerAdapter
```

<br/>

앞의 핸들러 매핑과 핸들러 어댑터 글에서 본 그것이다.

```java
DispatcherServlet 은 handle(request, response, handler) 하나만 안다
컨트롤러는 모양이 여러 가지다
-> 어댑터가 사이에서 맞춰준다
```

<br/>

```java
RequestMappingHandlerAdapter  - @Controller 방식
SimpleControllerHandlerAdapter - Controller 인터페이스 방식
HttpRequestHandlerAdapter     - 정적 리소스
```

<br/>

새 모양이 생기면 어댑터를 하나 추가하면 된다.

`DispatcherServlet` 은 안 고친다.

<br/>

## 두 가지 방식이 있다

```java
객체 어댑터 - 대상을 필드로 들고 있는다 (조합)
클래스 어댑터 - 대상을 상속한다
```

<br/>

자바는 다중 상속이 안 되니 클래스 어댑터를 쓰기 어렵다.

인터페이스 하나 + 클래스 하나까지만 되기 때문이다.

<br/>

그래서 보통 객체 어댑터를 쓴다.

```java
class Adapter implements Target {
    private final Adaptee adaptee;         // 들고 있는다

    public void request() {
        adaptee.specificRequest();          // 이름을 바꿔서 위임한다
    }
}
```

<br/>

앞의 상속보다 조합 글에서 본 그 이유와 같다.

조합이 더 유연하고, 대상이 바뀌어도 영향을 덜 받는다.

<br/>

## 실무에서 쓰는 자리

외부 서비스를 붙일 때 거의 항상 쓴다.

```java
interface PaymentGateway {              // 내가 정한 모양
    PayResult pay(long amount);
}

class TossAdapter implements PaymentGateway {
    private final TossClient tossClient;     // 토스가 준 SDK

    public PayResult pay(long amount) {
        TossPaymentResponse response = tossClient.confirm(...);   // 토스 방식
        return new PayResult(response.getPaymentKey(), ...);      // 내 방식으로 바꾼다
    }
}
```

<br/>

앞의 Java에서의 역할과 구현 글에서 본 그 자리다.

<br/>

이렇게 해두면 결제사를 바꿔도 `PaymentGateway` 를 쓰는 코드는 안 바뀐다.

어댑터만 하나 더 만들면 된다.

<br/>

그리고 외부 SDK의 타입이 내 코드 안쪽까지 안 들어온다.

`TossPaymentResponse` 가 서비스 층에 보이기 시작하면,

결제사를 바꿀 때 고칠 곳이 사방에 생기게 되는 것이다.
