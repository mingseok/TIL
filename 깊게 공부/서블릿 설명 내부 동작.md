## 서블릿 설명 / 내부 동작

클라이언트의 요청을 처리하고, 그 결과를 반환하는 Servlet 클래스의 구현 규칙을 지킨 자바 웹 프로그래밍 기술이다.

<br/>

Spring MVC에서 Controller로 이용되며, 사용자의 요청을 받아, 

처리한 후에 결과를 반환한다. (자바를 사용해 웹을 만들기 위해 필요한 기술)

![이미지](/programming/img/입문534.PNG)

<br/>

1. `사용자(Client)가 URL을 입력`하면 HTTP Request가 `Servlet 컨테이너로 전송`된다.

2. `요청 받은 Servlet 컨테이너`는 HttpServletRequest, HttpServletResponse 객체를 생성합니다.

3. web.xml을 기반으로 `사용자가 요청한 URL이 어느 서블릿에 대한 요청인지 찾는다.`

4. `해당 서블릿에서 서비스 메소드를 호출한 후,` GET, POST여부에 따라 doGet() 또는 doPost()를 호출한다.
    
5. doGet() 또는 doPost() 메소드는 `동적 페이지를 생성한 후 HttpServletResponse 객체에 응답`을 보낸다.
    
6. `응답이 끝나면 HttpServletRequest, HttpServletResponse 두 객체를 소멸`시킨다.

<br/><br/>

## Servlet Container(서블릿 컨테이너)

서블릿 컨테이너는 클라이언트의 요청(Request)을 받아주고 응답(Response)할 수 있게, 웹 서버와 소켓으로 통신합니다.

대표적인 예로 톰캣(Tomcat) -> 톰캣은 실제로 웹 서버와 통신하여 JSP(자바 서버 페이지)와 

Servlet이 작동하는 환경을 제공해줍니다.

```java
e.g.)
서블릿은 어떠한 역할을 수행하는 정의서라고 보면, 
서블릿 컨테이너는 그 정의서를 보고 수행한다고 볼 수 있다.
```
<br/>

## 궁금증!

```java
6번에서 "두 객체를 소멸시킨다" 고 했는데, 서블릿 자체도 매번 새로 만들어지는 걸까?
```

아니다. 서블릿은 딱 하나만 만들어져서 계속 재사용된다.

<br/>

소멸되는 것은 `HttpServletRequest`, `HttpServletResponse` 두 개뿐이다.

이 둘은 요청 하나에 대한 정보라서 요청이 끝나면 버려지지만, 서블릿은 남아 있는다.

```java
서블릿           -> 애플리케이션 시작 때 하나 만들고, 종료할 때까지 재사용
Request/Response -> 요청마다 새로 만들고, 응답 끝나면 버린다
```

<br/>

매 요청마다 서블릿을 새로 만들면 객체 생성 비용이 계속 든다.

요청이 초당 수백 개씩 들어오는 서버에서는 이게 그대로 부담이 된다.

<br/>

## 그러면 동시에 온 요청은 어떻게 처리하는가

서블릿 컨테이너가 스레드 풀을 들고 있다가, 요청 하나에 스레드 하나를 붙여준다.

```java
요청 A -> 스레드 1 -> 서블릿의 service() 실행
요청 B -> 스레드 2 -> 같은 서블릿의 service() 실행
요청 C -> 스레드 3 -> 같은 서블릿의 service() 실행
```

<br/>

객체는 하나인데 여러 스레드가 그 안의 메서드를 동시에 실행하는 구조다.

<br/>

그래서 서블릿에 필드를 두면 안 된다.

```java
public class BadServlet extends HttpServlet {
    private String name;                    // 모든 요청이 같이 쓴다

    protected void doPost(HttpServletRequest req, HttpServletResponse res) {
        name = req.getParameter("name");    // A가 넣은 값을
        // ...
        res.getWriter().write(name);        // B가 읽을 수 있다
    }
}
```

<br/>

`A` 요청이 `name` 에 값을 넣고 다음 줄로 가는 사이에 `B` 요청이 그 값을 덮어쓸 수 있다.

`A` 사용자 화면에 `B` 사용자의 이름이 뜨는 사고가 이렇게 난다.

<br/>

앞의 싱글톤 글에서 `스프링 빈에 상태를 두면 안 된다` 고 한 것과 완전히 같은 얘기다.

스프링 빈도 하나뿐이고 서블릿도 하나뿐이라, 문제의 모양이 똑같다.

```java
지역 변수 -> 스레드마다 스택이 따로라 안전하다
필드      -> 객체가 하나라 전부 공유된다. 위험하다
```

<br/>

## 서블릿의 생명주기는 세 단계다

```java
init()     - 서블릿이 처음 만들어질 때 딱 한 번. 무거운 준비 작업을 여기서 한다
service()  - 요청이 올 때마다. 여기서 doGet / doPost 로 나뉜다
destroy()  - 애플리케이션이 내려갈 때 딱 한 번
```

<br/>

원문의 `4번` 이 `service()` 단계다.

`service()` 안에서 요청의 메서드를 보고 `doGet()` 이나 `doPost()` 로 갈라준다.

<br/>

앞의 빈 생명주기 글에서 본 `생성 -> 초기화 콜백 -> 사용 -> 소멸 콜백` 과 모양이 같다.

무거운 준비는 처음 한 번만, 요청 처리는 매번 하는 구조다.

<br/>

## web.xml은 요즘 안 쓴다

원문 `3번` 의 `web.xml 을 기반으로` 는 옛날 방식이다.

<br/>

서블릿 3.0부터는 어노테이션으로 대신할 수 있게 됐다.

```java
@WebServlet(urlPatterns = "/members")
public class MemberServlet extends HttpServlet { }
```

<br/>

그리고 스프링을 쓰면 서블릿을 직접 만들 일이 아예 없어진다.

앞의 프론트 컨트롤러 글에서 본 대로, `DispatcherServlet` 하나가 `/` 로 들어오는 모든 요청을 받는다.

```java
web.xml 시절 : URL 마다 서블릿을 만들고 web.xml 에 등록
지금         : DispatcherServlet 하나가 다 받고, @RequestMapping 을 보고 나눠준다
```

<br/>

`web.xml` 을 안 쓰게 되면서 등록 정보가 코드 옆으로 옮겨온 셈이다.

XML 파일을 따로 열어보지 않아도 컨트롤러만 보면 어느 URL을 처리하는지 알 수 있다.

<br/>

## 서블릿 컨테이너와 웹 서버는 다른 것이다

원문의 비유를 조금 더 이어보면 이렇다.

```java
웹 서버        - HTML, 이미지, CSS 같은 정적 파일을 그대로 내려준다 (Nginx, Apache)
서블릿 컨테이너 - 자바 코드를 실행해서 결과를 만들어 내려준다 (Tomcat)
```

<br/>

톰캣은 사실 둘 다 할 수 있어서 경계가 흐릿하다.

다만 정적 파일은 `Nginx` 가 훨씬 빠르기 때문에, 실무에서는 앞에 `Nginx` 를 두는 구성을 많이 쓴다.

```java
브라우저 -> Nginx -> (정적 파일이면 여기서 바로 응답)
                 -> (자바가 필요하면 톰캣으로 넘김) -> DispatcherServlet -> 컨트롤러
```

<br/>

앞의 스프링 부트 글에서 본 `내장 톰캣` 은 이 톰캣이 라이브러리로 jar 안에 들어와 있다는 뜻이다.

서블릿 컨테이너를 따로 설치하지 않아도 `main` 메서드 하나로 이 흐름 전체가 뜬다.
