## 객체 헤더와 메모리 정렬

<br/>

## 객체 하나가 차지하는 것

```java
new Object()
```

<br/>

필드가 하나도 없는데 0바이트가 아니다. 헤더가 있다.

```java
마크 워드    - 해시코드, GC 나이, 락 상태     (8바이트)
클래스 포인터 - 어느 클래스의 객체인지          (4바이트, 압축 시)
```

<br/>

그리고 크기는 8의 배수로 맞춘다. 정렬이라고 한다.

<br/><br/>

## 궁금증!

```java
헤더가 정말 12바이트인가
```

`Unsafe.objectFieldOffset` 으로 첫 필드가 어디서 시작하는지 봤다. 그 앞이 헤더다.

<br/>

### 결과

```java
class OneBool { boolean b; }
  b 의 오프셋 = 12                <- 헤더 12 바이트

class Ref { Object o; }
  o 의 오프셋 = 12, 참조 크기 = 4  <- 압축 oop. 64비트인데 참조가 4바이트
```

<br/>

헤더 12바이트가 맞다.

<br/>

64비트 JVM인데 참조가 4바이트인 것은 압축 포인터 덕분이다.

힙이 32GB 미만이면 객체 주소를 8로 나눠서 32비트에 담는다. 객체가 8바이트 정렬이니 하위 3비트는 항상 0이라 버려도 된다.

<br/>

앞의 비트 연산 글에서 본 시프트가 여기 쓰인다. 저장할 때 `>> 3`, 읽을 때 `<< 3`.

<br/><br/>

## 필드 순서가 바뀐다

선언 순서대로 놓이지 않는다.

```java
class Mixed { boolean a; long l; boolean b; int i; }     // 선언 순서
```

<br/>

### 결과

```java
i   오프셋 12     <- int 가 먼저
l   오프셋 16     <- long 은 8 의 배수 자리에
a   오프셋 24
b   오프셋 25     <- boolean 둘이 뒤에 붙어 있다
```

<br/>

JVM이 크기순으로 다시 배치했다. `long -> int -> boolean` 이다.

<br/>

이유는 정렬이다. `long` 은 8의 배수 주소에 있어야 한 번에 읽는다.

선언 순서대로 `a(1) l(8)` 을 놓으면 `l` 을 8의 배수에 맞추려고 7바이트가 빈다.

크기순으로 놓으면 빈칸이 준다.

<br/>

앞의 ‘메모리에 적재’ CPU의 연산 글에서 본 대로,

CPU는 정렬 안 된 8바이트를 읽으려면 두 번 읽어서 합쳐야 한다. 그래서 정렬을 맞춘다.

<br/><br/>

## 크기 계산

```java
new Object()        헤더 12 -> 8 의 배수로 올림 -> 16 바이트
new OneBool()       헤더 12 + boolean 1 = 13 -> 16 바이트
new Mixed()         헤더 12 + int 4 + long 8 + boolean 2 = 26 -> 32 바이트
new int[0]          헤더 12 + 길이 4 = 16 바이트
new Integer(1)      헤더 12 + int 4 = 16 바이트
```

<br/>

`Integer` 하나가 16바이트다. `int` 는 4바이트다.

앞의 오토박싱 & 언박싱 글에서 본 `List<Integer> 가 int[] 보다 몇 배 크다` 가 이 계산이다.

<br/>

```java
int[1_000_000]        =  4MB
Integer[1_000_000]    =  4MB (참조 배열) + 16MB (Integer 객체들) = 20MB
```

<br/>

5배다. 캐시에도 5배 안 맞는다.

<br/><br/>

## 문자열은 더 비싸다

```java
String "a"
  String 객체   : 헤더 12 + hash 4 + hashIsZero 1 + coder 1 + value 참조 4 = 22 -> 24 바이트
  byte[] value  : 헤더 12 + 길이 4 + 'a' 1 = 17 -> 24 바이트
  합계 48 바이트
```

<br/>

한 글자 문자열이 48바이트다.

<br/>

앞의 String, StringBuffer, StringBuilder의 차이는 글에서 본 대로 문자열마다 객체 두 개가 생긴다.

로그 한 줄에 문자열 수십 개를 만들면 이게 전부 쌓이는 것이다.

<br/><br/>

## 이걸 알면 보이는 것들

```java
필드를 boolean 8개로 두는 것 vs int 하나에 비트 플래그
  -> boolean 8개 = 8바이트, int = 4바이트. 객체 수백만 개면 차이가 난다

Optional<Integer> 필드
  -> Optional 16 + Integer 16 = 32 바이트를 int 4 바이트 대신 쓰는 것

압축 oop 가 꺼지는 순간
  -> 힙을 32GB 넘게 잡으면 참조가 8바이트로 커진다. 힙을 키웠는데 담을 수 있는 객체가 줄어드는 역설
```

<br/>

마지막이 실무에서 만나는 것이다.

힙 31GB와 33GB 사이에서 실제 용량이 거꾸로 가는 구간이 있다.

<br/>

앞의 자바 가상머신(JVM) 글에서 본 `-Xmx` 를 정할 때 이 경계를 안다면 31GB 근처에서 멈추는 판단을 할 수 있다.

<br/><br/>

## 정확히 재고 싶으면

`JOL(Java Object Layout)` 이라는 도구가 있다.

```java
ClassLayout.parseClass(Mixed.class).toPrintable()
```

<br/>

위에서 `Unsafe` 로 한 것을 표로 예쁘게 보여준다.

객체 크기가 의심될 때 추측 대신 이걸로 찍어보면 된다.
