## database system 동작하는 방식

<br/>

## 데이터베이스란?

```java
"전자적으로 저장되고, 사용"되는 "관련있는 데이터"들의 "조직화된 집합"을 말한다.
```

### `database system`이란?

- database + DBMS + 연관된 applications

    - 줄여서 database라고도 부르기에, 문맥에 따라서 잘 파악해야 한다.

<br/><br/>

## `database system` 동작하는 방식

![이미지](/programming/img/입문417.PNG)

https://www.youtube.com/watch?v=aL0XXc1yGPs&list=PLcXyemr8ZeoREWGhhZi5FZs6cvymjIBVe

1. 처음에, `사용자`나 `개발자`가 있을 것이다.

2. 우린 개발자이기에, `애플리케이션 프로그램`을 만들었다.

3. 데이터 베이스에 접근하기 위한, 쿼리들을 `DBMS Software`에서 `쿼리`들을 받는다.

4. 그리고, 그 `쿼리`가 무엇을 의미하는지 `분석`한다.

5. `쿼리`가 `요청`한 게 무엇인지 `파악`이 되면, 그 요청을 처리하기 전에

6. 데이터가 어떤 형태로 되어 있는지에 대한 추가적인 정보를 알아야, 
    
    데이터를 `읽어` 올 수 있기에, 추가적인 정보를 확인한다.
    
7. 그, 추가적인 정보를 바탕으로 `실제 요청` 받은 데이터를 찾는다.
8. 찾았다면, `애플리케이션`으로 돌려주게 되는 것이다.

```java
이렇게 1 ~ 8번까지 동작하는 방식이 "database system"이 동작하는 방식이다.
```
<br/>

## 궁금증!

```java
SQL 한 줄을 던지면 DB 안에서 무슨 일이 일어날까?
```

크게 네 단계를 거친다.

```java
1. 파서       - SQL 문법이 맞는지 확인하고 구조로 바꾼다
2. 옵티마이저  - 어떻게 실행할지 계획을 짠다
3. 실행기      - 계획대로 데이터를 읽는다
4. 저장 엔진   - 실제로 디스크에서 페이지를 가져온다
```

<br/>

이 중 `2번` 이 관계형 DB의 핵심이다.

앞의 RDBMS 글에서 본 `무엇을 원하는지만 적으면 방법은 DB 가 정한다` 가 여기서 일어난다.

<br/>

## 옵티마이저가 하는 일을 직접 볼 수 있다

```sql
EXPLAIN QUERY PLAN SELECT * FROM member WHERE email = 'user99999@test.com';
```

<br/>

```sql
-- 인덱스가 없을 때
`--SCAN member

-- 인덱스를 만든 뒤
`--SEARCH member USING INDEX idx_member_email (email=?)
```

<br/>

우리가 던진 SQL은 똑같은데 계획이 바뀌었다.

옵티마이저가 `쓸 수 있는 인덱스가 생겼으니 그것을 쓰겠다` 고 판단한 것이다.

<br/>

## 어떻게 판단하는가

`통계 정보` 를 본다. 테이블마다 이런 것을 모아둔다.

```java
전체 행 수
컬럼별 값의 종류가 몇 가지인지 (카디널리티)
값의 분포 (히스토그램)
인덱스의 높이와 크기
```

<br/>

그리고 후보 계획마다 `비용` 을 계산해서 제일 싼 것을 고른다.

```java
전체 스캔        : 10만 페이지를 읽어야 한다 -> 비용 10만
인덱스 + 조회    : 인덱스 3번 + 데이터 1번   -> 비용 4
```

<br/>

그래서 통계가 틀리면 엉뚱한 계획을 고른다.

```sql
-- 통계 갱신
ANALYZE TABLE member;         -- MySQL
ANALYZE member;               -- PostgreSQL
```

<br/>

대량으로 데이터를 넣거나 지운 뒤에 갑자기 쿼리가 느려지면 이걸 의심해볼 만하다.

<br/>

## 인덱스가 있어도 안 쓰는 경우가 있다

이게 처음엔 이해가 안 된다.

```sql
SELECT * FROM member WHERE age > 20;    -- 전체의 90% 가 해당한다면?
```

<br/>

인덱스로 찾으면 `인덱스에서 위치를 찾고 -> 실제 데이터를 읽고` 를 `9만` 번 반복한다.

그냥 처음부터 끝까지 읽는 것보다 오히려 느리다.

<br/>

앞의 DB 인덱스 글에서 본 `카디널리티가 낮으면 효과가 없다` 가 이 얘기다.

옵티마이저는 통계를 보고 `이건 전체 스캔이 낫겠다` 고 판단한다.

```java
조회 결과가 전체의 몇 % 인가
  적으면 -> 인덱스
  많으면 -> 전체 스캔
```

<br/>

대략 `20~30%` 를 넘으면 전체 스캔이 유리해진다고 본다.

<br/>

## 저장 엔진 층이 따로 있는 이유

MySQL은 `4번` 을 갈아끼울 수 있게 만들어놨다.

```java
InnoDB  - 트랜잭션과 외래 키를 지원한다. 기본값
MyISAM  - 트랜잭션이 없다. 대신 단순하고 빠르다 (지금은 거의 안 쓴다)
MEMORY  - 메모리에만 저장한다. 서버가 죽으면 사라진다
```

<br/>

```sql
CREATE TABLE member (...) ENGINE=InnoDB;
```

<br/>

파서와 옵티마이저는 그대로 두고 저장 방식만 바꾸는 구조다.

앞의 three-schema 글에서 본 `내부 스키마` 를 실제로 갈아끼울 수 있게 만든 셈이다.

<br/>

앞의 PSA 글에서 본 인터페이스 구조와도 같다.

`무엇을 할 수 있는지` 는 저장 엔진 인터페이스가 정하고, 구현은 각자 다르다.

<br/>

## 버퍼 풀이 그 사이에 있다

`4번` 이 매번 디스크로 가지는 않는다. 메모리에 캐시를 둔다.

```java
데이터가 필요하다
  -> 버퍼 풀에 있나? 있으면 바로 준다 (메모리 접근)
  -> 없으면 디스크에서 읽어서 버퍼 풀에 올린다
```

<br/>

`innodb_buffer_pool_size` 가 그 크기다. 보통 서버 메모리의 `70~80%` 를 준다.

<br/>

앞의 DB 인덱스 글에서 조회를 `1000` 번 반복했을 때 `37ms` 밖에 안 걸린 것도 이 덕분이다.

같은 페이지를 계속 읽으니 두 번째부터는 메모리에서 나온다.

<br/>

그래서 성능 측정을 할 때는 캐시가 채워진 뒤의 값을 봐야 한다.

앞의 JIT 글에서 본 워밍업과 같은 얘기다.
