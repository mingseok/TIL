## 시간과 시계 - currentTimeMillis와 nanoTime

<br/>

## 시계가 두 개다

```java
System.currentTimeMillis()  = 1788332638996      // 1970-01-01 부터 지난 ms
System.nanoTime()           = 111115375770041    // 기준점이 임의. 차이만 의미 있다
```

<br/>

```java
currentTimeMillis - 벽시계. "지금 몇 시인가"
nanoTime          - 스톱워치. "얼마나 지났는가"
```

<br/>

이름만 다른 게 아니라 성질이 다르다.

<br/><br/>

## 벽시계는 뒤로 갈 수 있다

`currentTimeMillis` 는 운영체제 시계를 읽는다. 운영체제 시계는 조정된다.

```java
NTP 가 시계를 맞춘다      - 몇 초 앞뒤로 점프할 수 있다
관리자가 시간을 바꾼다
서머타임
가상 머신을 일시정지했다 재개
```

<br/>

경과 시간을 이걸로 재면 이런 일이 생긴다.

```java
long start = System.currentTimeMillis();
작업();
long elapsed = System.currentTimeMillis() - start;      // 음수가 나올 수 있다
```

<br/>

NTP가 그 사이 시계를 5초 뒤로 당겼으면 `elapsed` 가 -5000이다.

타임아웃 계산에 쓰면 영원히 안 끝나거나 즉시 끝난다.

<br/>

`nanoTime` 은 단조 증가가 보장된다. 절대 뒤로 안 간다.

앞의 타임아웃은 왜 반드시 걸어야 하나 글에서 본 타임아웃 구현은 전부 `nanoTime` 으로 되어 있다.

<br/><br/>

## 궁금증!

```java
해상도가 얼마나 다른가
```

100만 번 연속 호출해서 값이 안 바뀐 횟수를 셌다.

<br/>

### 결과

```java
currentTimeMillis 100만 번 중 값이 안 바뀐 횟수 = 999,975    <- 1000분의 1초 단위
nanoTime          100만 번 중 값이 안 바뀐 횟수 = 678,897    <- 수십 ns 단위
```

<br/>

`currentTimeMillis` 는 100만 번 불러서 25번 바뀌었다. ms 단위라 그렇다.

짧은 작업을 이걸로 재면 0ms가 나온다.

<br/>

`nanoTime` 도 매번 바뀌지는 않는다. 한 번 부르는 데 13ns 정도(앞의 시스템 콜 글에서 잰 값)인데 해상도가 그보다 조금 거칠다.

그래도 마이크로초 단위는 확실히 잰다.

<br/><br/>

## nanoTime 은 사람이 못 읽는다

```java
111115375770041
```

<br/>

이게 무슨 시각인지 아무도 모른다. JVM이 시작한 시점 근처의 임의 값이다.

두 JVM의 `nanoTime` 을 비교하는 것도 의미가 없다.

<br/>

그래서 용도가 갈린다.

```java
로그에 찍는 시각, DB 에 저장하는 시각, 만료 시각  -> currentTimeMillis / Instant
경과 시간, 타임아웃, 벤치마크                   -> nanoTime
```

<br/><br/>

## 저장은 UTC 로

```java
Instant (UTC)      = 2026-09-02T07:03:59Z
Asia/Seoul         = 2026-09-02T16:03:59
America/New_York   = 2026-09-02T03:03:59
```

<br/>

같은 순간인데 표시가 세 가지다.

<br/>

DB에 `LocalDateTime` 으로 `16:03:59` 를 저장하면, 서버가 미국으로 옮겨가는 순간 13시간이 틀어진다.

`Instant` 나 `UTC 기준 TIMESTAMP` 로 저장하고, 보여줄 때 사용자 시간대로 바꾼다.

<br/>

앞의 뷰 리졸버를 왜 사용하는가 글에서 본 것과 같은 원리다.

`저장하는 것` 과 `보여주는 것` 을 나눠야 한쪽이 바뀌어도 다른 쪽이 안 깨진다.

<br/><br/>

## 하루가 24시간이 아닐 때

```java
뉴욕 2026-03-08 01:30 + 1시간 = 03:30      <- 02:30 이 아니다
```

<br/>

그 날 새벽 2시에 서머타임이 시작되어 `02:00 ~ 02:59` 가 존재하지 않는다.

<br/>

`plusHours(1)` 은 맞게 계산했다. 시간대 규칙을 알기 때문이다.

직접 `+ 3600000` 을 하면 틀린다.

<br/>

```java
하루 = 24시간           - 서머타임 날은 23 또는 25시간
1분 = 60초              - 윤초가 있는 날은 61초
한 달 뒤 = +30일         - 1월 31일의 한 달 뒤는?
```

<br/>

날짜 계산을 직접 하면 이 경계에서 전부 틀린다. `java.time` 에 맡겨야 한다.

<br/><br/>

## 분산 시스템에서는 더 어렵다

서버 두 대의 시계는 같지 않다.

NTP로 맞춰도 수 ms 차이가 난다. 맞추기 전에는 초 단위로 다르다.

<br/>

그래서 `어느 이벤트가 먼저인가` 를 시각으로 판단하면 틀린다.

```java
서버 A 에서 10:00:00.005 에 생성
서버 B 에서 10:00:00.003 에 수정        <- B 시계가 5ms 느리면 실제로는 A 가 먼저
```

<br/>

순서가 중요하면 시각 대신 순번을 쓴다. DB의 자동 증가 값이나 버전 번호다.

앞의 CAS 알고리즘 설명 글에서 본 낙관적 락의 `version` 이 시각 대신 순번을 쓰는 이유이기도 하다.

<br/><br/>

## 정리

```java
경과 시간   - nanoTime. 뒤로 안 간다. 해상도 높다
현재 시각   - currentTimeMillis / Instant. 사람이 읽는다. 뒤로 갈 수 있다
저장       - UTC. 표시할 때만 시간대 변환
계산       - java.time 에 맡긴다. 직접 더하면 서머타임에서 틀린다
순서       - 시각으로 판단하지 않는다. 서버마다 시계가 다르다
```
