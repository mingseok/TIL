## 팩토리 메서드 패턴

<br/>

## 설명

객체를 직접 생성하지 않고 Factory(인터페이스) 객체를 사용하는 패턴입니다.

```java
팩토리 메서드는 
부모 클래스에서 객체들을 생성할 수 있는 인터페이스를 제공하지만,
자식 클래스들이 생성될 객체들의 유형을 변경할 수 있도록 하는 생성 패턴입니다.
```

<br/><br/>

## 예시)

모든 걸 직접 만들어서 프로그래밍하는 경우는 드물다.

스프링 같은 이미 현존하는 프레임워크 위에서 기존에 만들어진 라이브러리, 클래스들을 활용한다. 

<br/>

특정 종류의 기능들에 사용될 수 있는 클래스들의 종류가 많고 

복잡할 때, 이를 사용하는 개발자 측에서는 이들을 다 알 필요가 없다는 것이다.

```java
"약국에서 약사에게 증상만 얘기해줄때 처럼"
```

<br/>

이렇게 사용할 객체의 조건들만 인자로 넘겨주면, 이에 적절한 클래스를 찾아 

객체로 생성해 넘겨주는 일은 팩토리가 알아서 처리한다는 것이다.

<br/><br/>

## 장점

직접 객체를 생성하는 것을 막아줘서 
결합도를 낮춰주는 효과가 있습니다.

<br/>

`단일 책임 원칙`. 제품 생성 코드를 프로그램의 한 위치로 이동하여 코드를 더 쉽게 유지관리할 수 있습니다.

`개방/폐쇄 원칙`. 기존 클라이언트 코드를 훼손하지 않고 새로운 유형의 제품들을 프로그램에 도입할 수 있습니다.

<br/><br/>

## 단점

패턴을 구현하기 위해 많은 새로운 자식 클래스들을 도입해야 하므로 코드가 더 복잡해질 수 있습니다.
<br/>

## 궁금증!

```java
new 를 감추면 무엇이 좋아지나
```

만드는 방법이 바뀔 때 고칠 곳이 한 군데로 줄어든다.

```java
Member member = new Member(name, email);
```

<br/>

이 코드가 스무 군데 있는데 생성자에 필드가 하나 추가되면 스무 군데를 고쳐야 한다.

<br/>

```java
Member member = Member.create(name, email);
```

<br/>

정적 팩토리 메서드로 감싸두면 그 안만 고치면 된다.

<br/>

## 이름을 붙일 수 있는 것이 더 크다

생성자는 이름이 클래스 이름으로 고정이다.

```java
new Member(name, null)            // null 이 무슨 뜻인지 모른다
new Member(name, "GUEST")
```

<br/>

정적 팩토리 메서드는 이름으로 의도를 드러낸다.

```java
Member.createGuest(name)
Member.createFromNaver(profile)
```

<br/>

앞의 클래스명, 메소드명, 변수명 규칙 글에서 본 그 이득이다.

<br/>

그리고 파라미터가 같은 생성자를 여러 개 못 만드는 문제도 풀린다.

```java
Member(String name, String email)
Member(String name, String phone)      // 컴파일 오류. 시그니처가 같다
```

```java
Member.fromEmail(name, email)
Member.fromPhone(name, phone)          // 이름이 다르니 된다
```

<br/>

## 매번 새 객체를 안 만들어도 된다

생성자는 부르면 반드시 새 객체를 만든다.

```java
new Boolean(true)      // 매번 새로 만든다
Boolean.valueOf(true)  // 캐시된 것을 돌려준다
```

<br/>

앞의 박싱, 언박싱 글에서 본 `Integer.valueOf()` 의 캐시가 그것이다.

```java
Integer a = Integer.valueOf(100);
Integer b = Integer.valueOf(100);
a == b   ->  true      (-128 ~ 127 은 캐시)
```

<br/>

`new Integer(100)` 이 자바 9부터 deprecated 된 이유이기도 하다.

<br/>

## 하위 타입을 돌려줄 수 있다

```java
public static List<String> of(String... elements) {
    // 반환 타입은 List 인데 실제로는 다른 것이 온다
}
```

<br/>

```java
List.of()          -> ImmutableCollections.ListN
List.of("a")       -> ImmutableCollections.List12   (원소 1~2개 전용)
```

<br/>

원소 개수에 따라 다른 클래스를 돌려준다.

쓰는 쪽은 `List` 만 알면 되니 이걸 몰라도 된다.

<br/>

앞의 Java에서의 역할과 구현 글에서 본 그 구조다.

<br/>

## 팩토리 메서드 패턴은 이것과 조금 다르다

`GoF` 의 팩토리 메서드 패턴은 상속을 쓴다.

```java
abstract class Dialog {
    abstract Button createButton();       // 자식이 정한다

    void render() {
        Button button = createButton();
        button.draw();
    }
}

class WindowsDialog extends Dialog {
    Button createButton() { return new WindowsButton(); }
}

class MacDialog extends Dialog {
    Button createButton() { return new MacButton(); }
}
```

<br/>

`Dialog` 는 `Button` 인터페이스만 알고, 어느 버튼인지는 자식이 정한다.

<br/>

앞의 템플릿 메서드 패턴 글에서 본 구조와 닮았다.

```java
템플릿 메서드 - 자식이 "동작" 을 채운다
팩토리 메서드 - 자식이 "무엇을 만들지" 를 채운다
```

<br/>

둘 다 `부모가 흐름을 잡고 자식이 빈칸을 채운다` 는 같은 뼈대다.

<br/>

## 그래서 이름이 헷갈린다

```java
정적 팩토리 메서드 - Member.create(). GoF 패턴이 아니다
팩토리 메서드 패턴 - 상속으로 만들 것을 정한다. GoF 패턴
추상 팩토리 패턴   - 관련된 객체 묶음을 한 번에 만든다. GoF 패턴
```

<br/>

실무에서 `팩토리 메서드` 라고 하면 대부분 첫 번째를 말한다.

<br/>

스프링에서는 컨테이너가 팩토리 역할을 한다.

```java
BeanFactory
```

<br/>

앞의 스프링 컨테이너, 스프링 빈, BeanDefinition 글에서 본 대로,

`BeanDefinition` 을 보고 객체를 만들어주는 것이 그 이름 그대로 팩토리인 것이다.
