## process를 설명해 주세요



프로세스란 실행중인 프로그램을 뜻합니다.

즉, 실행파일 형태로 존재하던 프로그램이 메모리에 적재되어 

CPU에 의해 실행 되는 것을 프로세스라고 합니다.

<br/><br/>

## 프로세스의 메모리 영역에 대해 설명해주세요.

프로세스 내에서도 각 용도에 따라 메모리 영역이 구분되어 있습니다.

- code 영역은 실행한 프로그램의 코드가 저장되는 메모리 영역입니다.

- data 영역은 프로그램의 전역 변수와 static 변수가 저장되는 메모리 영역입니다.
- heap 영역은 런타임 중에 메모리를 할당 받아 동적으로 객체 생성을 하는 영역입니다.
- stack 영역은 함수 호출 시 생성되는 지역 변수와 매개 변수가 저장되는 영역입니다.
<br/><br/>

## 궁금증!

```java
프로세스가 정말 각자 메모리를 가지는지 확인해봤다
```

자바 프로그램에서 자식 프로세스를 하나 띄우고, 자식이 `static` 변수를 바꾸게 했다.

```java
static int shared = 0;

// 자식으로 실행되면
shared = 999;

// 부모는 자식을 띄우고 끝날 때까지 기다린 뒤 shared 를 찍는다
Process p = new ProcessBuilder("java", "Proc", "child").inheritIO().start();
p.waitFor();
```

<br/>

### 결과

```java
[부모 pid=71545] shared = 0
  [자식 pid=71546] shared 를 999 로 바꿈
[부모] 자식이 끝난 뒤 shared = 0     <- 그대로. 각자 복사본
```

<br/>

같은 클래스, 같은 변수 이름인데 부모의 값은 그대로다.

pid가 다르다는 것이 곧 `메모리 공간이 다르다` 는 뜻인 것이다.

<br/>

같은 실험을 스레드로 하면 반대가 된다.

```java
Thread t = new Thread(() -> shared = 999);
t.start(); t.join();
```

```java
[main] 스레드가 끝난 뒤 shared = 999     <- 바뀌어 있다
```

<br/>

이 둘의 차이가 앞의 multi thread VS multi process 글의 전부라고 봐도 된다.

<br/><br/>

## 메모리 영역이 실제로 나뉘어 있는지

`vmmap` 으로 돌고 있는 자바 프로세스의 메모리 지도를 봤다.

```java
$ vmmap --summary 71701

__TEXT          581.7M     <- 코드 영역. 실행 파일과 라이브러리의 명령어
__DATA           12.2M     <- 데이터 영역. 전역/정적 변수
MALLOC_SMALL     40.0M     <- 힙. 동적으로 할당한 것
Stack            43.6M     <- 스택. 스레드 21개 분량
STACK GUARD      56.6M     <- 스택 넘침을 잡는 경계
```

<br/>

교과서에 나오는 네 영역이 실제 이름으로 있다.

`__TEXT` 가 코드, `__DATA` 가 데이터, `MALLOC` 이 힙, `Stack` 이 스택이다.

<br/>

눈에 띄는 것은 `Stack` 이 21개라는 점이다.

`main` 하나만 돌리는 프로그램인데도 JVM이 GC 스레드, JIT 컴파일 스레드 같은 것을 여럿 띄우기 때문이다.

스택은 스레드마다 하나씩이니 21개가 되는 것이다.

<br/>

`STACK GUARD` 는 스택 바로 옆에 붙은 접근 금지 구역이다.

앞의 재귀함수 글에서 본 `StackOverflowError` 가 이 경계를 밟았을 때 나는 것이다.

<br/><br/>

## 프로세스 하나가 어디까지 쓸 수 있나

`__TEXT` 가 581MB인데 실제로 메모리에 올라온 것은 252MB였다.

```java
VIRTUAL SIZE   RESIDENT SIZE
   581.7M         252.5M
```

<br/>

프로세스가 `가질 수 있는` 주소 공간과 `실제로 올라와 있는` 물리 메모리가 다르기 때문이다.

<br/>

운영체제는 프로그램 전체를 한 번에 올리지 않는다.

실제로 실행되는 부분만 올리고, 안 쓰는 부분은 디스크에 두다가 필요할 때 가져온다.

<br/>

그래서 `메모리에 적재된 상태여야 실행된다` 는 말은 정확히는 `실행되는 그 부분이 적재되어 있어야 한다` 는 뜻이다.

앞의 ‘메모리에 적재’ CPU의 연산 글에서 본 것과 이어진다.

<br/><br/>

## 프로세스 하나가 얼마나 비싼가

만들고 끝내는 데 걸리는 시간을 재봤다.

```java
스레드   100개 생성+종료 = 6 ms    (개당 0.06 ms)
프로세스  10개 생성+종료 = 40 ms   (개당 4.00 ms, 가장 작은 명령 'true')
```

<br/>

프로세스 하나가 스레드 하나의 60배 넘게 든다.

<br/>

메모리 공간을 새로 잡고, 위에서 본 `__TEXT`, `__DATA`, `Stack` 을 전부 다시 만들어야 하기 때문이다.

스레드는 이미 있는 공간에 스택 하나만 더하면 된다.

<br/>

그래서 요청마다 프로세스를 만드는 방식은 오래전에 사라졌고,

앞의 멀티 쓰레드 글에서 본 대로 스레드 풀을 두는 방식이 자리 잡은 것이다.

<br/><br/>

## 자바에서는 프로세스를 잘 안 만든다

```java
new ProcessBuilder("java", ...).start()
```

<br/>

위 실험처럼 만들 수는 있는데 실무에서는 드물다.

<br/>

외부 명령을 실행해야 할 때 정도다.

```java
ffmpeg 로 영상 변환
git 명령 실행
파이썬 스크립트 호출
```

<br/>

같은 애플리케이션 안의 일을 나눌 때는 스레드를 쓴다.

프로세스를 나누는 결정은 보통 애플리케이션 안이 아니라 밖에서 한다.

서버를 여러 대 띄우거나 컨테이너를 여러 개 두는 것이 그것이다.

<br/>

앞의 WAS 서버와 WEB 서버의 이해 글에서 본 `Nginx 는 프로세스 여러 개, 톰캣은 스레드 여러 개` 가 그 두 방식이 실제로 갈린 예다.
