## NoSQL이란 무엇인가?

관계형 데이터 모델을 지양 하며 하거나 느슨한 스키마를 제공하는 저장소를 말한다.

<br/>

NoSQL은 기존 RDBMS 형태의 관계형 데이터베이스가 아닌 다른 형태의 데이터 저장 기술을 

의미하며, 관계형 데이터베이스의 한계를 극복하기 위한 데이터 저장소의 새로운 형태이다.

```java
"대량의 분산 된 데이터를 저장하고 조회하는데, 특화되었으며 스키마 없이 사용 가능"
```

<br/><br/>

## NoSQL의 장점

- RDBMS에 비해 저렴한 비용으로 분산처리와 병렬 처리 가능

- 비정형 데이터 구조 설계로 설계 비용 감소
- Big Data 처리에 효과적

- 가변적인 구조로 데이터 저장이 가능

- 데이터 모델의 유연한 변화가 가능

<br/><br/>

## NoSQL의 단점

- 데이터 업데이트 중 장애가 발생하면 데이터 손실 발생 가능

- 많은 인덱스를 사용하려면 충분한 메모리가 필요. 인덱스 구조가 메모리에 저장

- 데이터 일관성이 항상 보장되지 않음

<br/><br/>

## relational database의 문제점

- 첫번째) 만약, 테이블에 새로운 컬럼을 추가한다

- 세번째) 트랜잭션 ACID를 보장하려다 보니 DB 서버의 퍼포먼스에 좋지 않은 영향이 있다.

    - 즉, 아이솔레이션을 보장하기 위해서 엄밀히 하려고하다 보니, 그만큼 전체적인 처리량이 줄어드는 것이다.

## 궁금증!

```java
NoSQL 이 "스키마가 없다" 는 게 정말 장점일까?
```

반은 장점이고 반은 문제를 미루는 것이다.

<br/>

관계형에서 컬럼을 추가하려면 `ALTER TABLE` 을 해야 한다.

앞의 DDL 글에서 본 대로 이건 롤백도 안 되고, 큰 테이블에서는 오래 걸린다.

```sql
ALTER TABLE member ADD COLUMN age INT;    -- 1000만 행이면 수 분
```

<br/>

문서형 DB는 그냥 넣으면 된다.

```javascript
db.member.insertOne({ name: "민석", age: 30 });   // age 는 이 문서에만 있다
```

<br/>

여기까지는 확실히 편하다.

<br/>

## 그런데 검증이 사라진다

```javascript
db.member.insertOne({ name: "민석", age: 30 });
db.member.insertOne({ name: "영한", age: "서른" });    // 문자열이 들어갔다
db.member.insertOne({ nmae: "민수" });                 // 오타인데 그냥 들어간다
```

<br/>

셋 다 통과한다. DB가 아무것도 안 막는다.

<br/>

관계형이었다면 `age INT` 라고 적어둔 순간 두 번째가 거부되고,

없는 컬럼 `nmae` 는 세 번째에서 에러가 났을 것이다.

```java
스키마가 있다 - 넣을 때 막아준다. 대신 바꾸려면 ALTER 를 해야 한다
스키마가 없다 - 바로 넣을 수 있다. 대신 이상한 값이 들어가도 모른다
```

<br/>

그래서 결국 애플리케이션 코드에서 검사하게 된다.

`DB 가 하던 일을 코드가 대신 하는` 셈이라, 없어진 것이 아니라 옮겨간 것이다.

<br/>

## 읽을 때 더 어려워진다

한 번 이상한 데이터가 들어가면 읽는 쪽이 계속 방어해야 한다.

```javascript
// 이 필드가 있을 수도 없을 수도 있다
// 숫자일 수도 문자열일 수도 있다
const age = typeof doc.age === 'number' ? doc.age : parseInt(doc.age ?? 0);
```

<br/>

`스키마가 없다` 가 아니라 `스키마가 코드 여기저기에 흩어져 있다` 가 된다.

<br/>

그래서 요즘 문서형 DB들도 스키마 검증 기능을 넣었다.

```javascript
db.createCollection("member", {
   validator: { $jsonSchema: { required: ["name", "age"], properties: { age: { bsonType: "int" } } } }
});
```

<br/>

결국 스키마가 필요하다는 결론에 도달한 셈이다.

<br/>

## 진짜 차이는 확장 방식이다

스키마보다 이쪽이 더 본질적인 차이다.

```java
수직 확장 (scale-up)   - 서버 한 대를 더 좋게 만든다. CPU, 메모리를 늘린다
수평 확장 (scale-out)  - 서버 대수를 늘린다
```

<br/>

관계형은 수평 확장이 어렵다.

`JOIN` 과 트랜잭션이 문제다. 데이터가 여러 서버에 흩어져 있으면 조인하기가 아주 어렵다.

```java
member 는 A 서버, orders 는 B 서버
-> JOIN 하려면 네트워크로 데이터를 주고받아야 한다
-> 트랜잭션으로 묶으려면 두 서버가 합의해야 한다 (2단계 커밋)
```

<br/>

NoSQL은 애초에 `조인을 안 한다` 는 전제로 설계됐다.

필요한 것을 한 문서에 다 담아두니, 문서 하나만 있으면 되고 서버를 흩어놔도 상관없다.

```java
관계형  - 데이터를 나눠 저장하고 (정규화) 필요할 때 합친다 (조인)
문서형  - 같이 쓸 것을 한 덩어리로 저장한다. 합칠 일이 없다
```

<br/>

## 그 대가는 중복이다

같이 쓸 것을 한 덩어리로 담으면 앞의 정규화 글에서 본 문제가 그대로 생긴다.

```javascript
{ orderId: 1, member: { name: "민석", phone: "010-1111" }, item: "책" }
{ orderId: 2, member: { name: "민석", phone: "010-1111" }, item: "노트" }
```

<br/>

민석의 전화번호가 바뀌면 모든 주문 문서를 고쳐야 한다.

정규화 글에서 본 `수정 이상` 이다.

<br/>

그래서 선택은 이렇게 갈린다.

```java
쓰기가 많고 정합성이 중요하다   -> 관계형. 한 곳에만 적어둔다
읽기가 압도적으로 많고 양이 크다 -> 문서형. 중복을 감수하고 한 번에 읽는다
```

<br/>

앞의 트레이드 오프 글의 관점으로 보면, 이것도 결국 `무엇을 포기할 것인가` 의 문제다.
