## 클래스명, 메소드명, 변수명 규칙

<br/>

## 이름을 통해 의도를 드러낸다

나 자신, 다른 개발자와의 소통을 위해 가장 중요한 활동 중의 하나가 좋은 이름 짓기이다.

변수 이름, 함수(메서드) 이름, 클래스 이름을 짓는데 시간을 투자하자. 
 
<br/>
 
이름을 통해 변수의 역할, 함수의 역할, 클래스의 역할에 대한 의도를 드러내기 위해 노력하자. 

연속된 숫자를 덧붙이거나(a1, a2, ..., aN), 불용어(Info, Data, a, an, the)를 추가하는 방식은 적절하지 못하다.

<br/><br/>

## 축약하지 않는다

의도를 드러낼 수 있다면 이름이 길어져도 괜찮다.

누구나 실은 클래스, 메서드, 또는 변수의 이름을 줄이려는 유혹에 곧잘 빠지곤 한다.

<br/>

그런 유혹을 뿌리쳐라. 축약은 혼란을 야기하며, 더 큰 문제를 숨기는 경향이 있다.



클래스와 메서드 이름을 한 두 단어로 유지하려고 노력하고 문맥을 중복하는 이름을 자제하자. 

<br/>

클래스 이름이 Order라면 shipOrder라고 메서드 이름을 지을 필요가 없다. 

짧게 ship()이라고 하면 클라이언트에서는 order.ship()라고 호출하며, 간결한 호출의 표현이 된다. 

객체 지향 생활 체조 원칙 5: 줄여쓰지 않는다 (축약 금지)

<br/><br/>

## 변수 이름에 자료형은 사용하지 않는다

변수 이름에 자료형, 자료 구조 등을 사용하지 않는다.

```java
String carNameList = Console.readLine();
String[] arrayString = carNameList.split(",");
```
<br/>

## 궁금증!

```java
"이름이 길어져도 괜찮다" 와 "한 두 단어로 유지" 가 충돌하지 않나?
```

충돌하는 것처럼 보이는데, 기준이 다르다.

```java
길어져도 되는 것 - 의도를 드러내기 위해 필요한 단어
줄여야 하는 것   - 문맥이 이미 알려주는 중복된 단어
```

<br/>

원문의 `Order.ship()` 예시가 정확히 이것이다.

```java
order.shipOrder()     // Order 라는 것을 두 번 말한다
order.ship()          // 문맥이 이미 알려주고 있다
```

<br/>

`ship` 은 짧지만 의도가 안 줄어들었다. 중복만 없앤 것이다.

<br/>

반대로 이런 것은 길어도 된다.

```java
int d;                                  // 무슨 d 인지 모른다
int elapsedTimeInDays;                  // 길지만 의도가 다 드러난다
```

<br/>

## 문맥 중복이 실무에서 자주 나오는 자리

```java
class MemberService {
    void createMember() { }        // memberService.createMember()
    void create() { }              // memberService.create()      <- 이쪽이 낫다
}

class MemberRepository {
    Member findMemberById(Long id) { }    // 중복
    Member findById(Long id) { }          // 이쪽
}

class OrderDto {
    private Long orderId;          // orderDto.getOrderId()
    private Long id;               // orderDto.getId()            <- 이쪽
}
```

<br/>

호출하는 쪽에서 읽어보면 판단이 쉽다.

`memberService.createMember()` 를 소리내어 읽으면 `member` 가 두 번 들린다.

<br/>

## 자료형을 이름에 넣지 말라는 규칙

원문의 예시를 다시 보면 문제가 두 겹이다.

```java
String carNameList = Console.readLine();      // List 가 아닌데 List 라고 적었다
String[] arrayString = carNameList.split(","); // 자료형 자체가 이름이 됐다
```

<br/>

첫 번째가 더 위험하다. 이름이 거짓말을 하고 있다.

읽는 사람이 `List` 인 줄 알고 `.get(0)` 을 쓰려다 컴파일 에러를 만난다.

<br/>

두 번째는 이름이 아무것도 안 알려준다.

```java
String[] arrayString      // 무엇이 들어 있는지 모른다
String[] carNames         // 자동차 이름들이 들어 있다
```

<br/>

자료형은 IDE가 알려주고 컴파일러가 검사해준다.

이름은 `무엇이 들어 있는지` 를 알려주는 데 써야 한다.

<br/>

## 그런데 예외도 있다

같은 데이터를 형태만 바꿔 들고 있을 때는 자료형이 구분에 필요하기도 하다.

```java
String carNames = "pobi,crong";        // 원본 문자열
List<String> splitCarNames;            // 나눈 것
```

<br/>

이때도 자료형보다는 `상태` 를 이름에 담는 편이 낫다.

```java
String rawCarNames;
List<String> carNames;
```

<br/>

## 불용어를 피하라는 규칙

```java
MemberInfo, MemberData, MemberObject
```

<br/>

`Info` 와 `Data` 를 떼어내도 뜻이 안 바뀐다.

바뀌지 않는다면 붙일 이유가 없다.

<br/>

다만 실제로 구분이 필요한 경우가 있다.

```java
Member          // 도메인
MemberResponse  // API 응답    (앞의 DTO 글에서 본 그 구분)
MemberSaveForm  // 등록 폼     (앞의 검증 - Form 전송 객체 분리 글)
```

<br/>

이건 불용어가 아니다. `언제 쓰는 것인지` 를 알려주는 단어이기 때문이다.

`Info` 와 `Response` 의 차이가 여기에 있다.

<br/>

## boolean 이름 짓기

원문에 없는데 자주 걸리는 자리다.

```java
boolean flag;              // 무엇의 참거짓인지 모른다
boolean status;            // 참거짓처럼 안 들린다
boolean deleted;           // 지워졌는지
boolean isDeleted();       // 메서드는 is 를 붙인다
```

<br/>

필드는 `deleted`, 게터는 `isDeleted()` 가 자바 관례다.

앞의 API (json)방식 @ResponseBody 글에서 본 대로,

Jackson이 `is` 를 떼고 `deleted` 를 JSON 키로 만드는 것도 이 관례를 따르는 것이다.

<br/>

부정형은 피하는 편이 낫다.

```java
if (!isNotDeleted())      // 부정의 부정이라 읽기 어렵다
if (isDeleted())
```
