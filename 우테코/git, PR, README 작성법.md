## git, PR, README 작성법

<br/>

## 커밋 메시지를 의미 있게 작성한다

커밋 메시지에 해당 커밋에서 작업한 내용에 대한 이해가 가능하도록 작성한다.

<br/><br/>

## Pull Request를 보내기 전 브랜치를 확인한다

기능 구현 작업을 `fork`된 `Repository`의 `main branch`가 아닌, 기능 구현을 위해 새로 만든 브랜치에서 작업한 후 `PR`을 보낸다.

```
 이런식으로 가능하다는걸 배워 놓자.
```

<br/><br/>

## README.md를 상세히 작성한다

`README.md`는 소스코드에 앞서 해당 프로젝트가 어떠한 프로젝트인지 **마크다운**으로 작성하여 소개하는 문서이다. 

해당 프로젝트가 어떠한 프로젝트이며, 어떤 기능을 담고 있는지 기술하기 위해서 마크다운으로 작성하여 알아보기 쉽게 작성하자.

<br/><br/>


## space와 tab을 혼용하지 않는다

들여쓰기에 `space`와 `tab`을 혼용하지 않는다. 둘 중에 하나만 사용한다. 

확신이 서지 않으면 `pull request`를 보낸 후 들여쓰기가 잘 되어 있는지 확인하는 습관을 들인다.

<br/><br/>

## 기능 목록을 재검토한다

기능 목록을 클래스 설계와 구현, 함수(메서드) 설계와 구현과 같이 너무 상세하게 작성하지 않는다. 

클래스 이름, 함수(메서드) 시그니처와 반환값은 언제든지 변경될 수 있기 때문이다.

<br/>

너무 세세한 부분까지 정리하기보다 구현해야 할 기능 목록을 정리하는 데 집중한다.

**정상적인 경우도 중요하지만, 예외적인 상황도 기능 목록에 정리**한다. 

특히 예외 상황은 시작 단계에서 모두 찾기 힘들기 때문에 기능을 구현하면서 계속해서 추가해 나간다.

<br/><br/>

## 기능 목록을 업데이트한다

`README.md` 파일에 작성하는 기능 목록은 기능 구현을 하면서 변경될 수 있다. 

시작할 때 모든 기능 목록을 완벽하게 정리해야 한다는 부담을 가지기보다 기능을 구현하면서 문서를 계속 업데이트한다. 

죽은 문서가 아니라 살아있는 문서를 만들기 위해 노력한다.
<br/>

## 궁금증!

```java
"커밋 메시지를 의미 있게" 라는 게 구체적으로 어떤 모양일까
```

널리 쓰이는 형식이 하나 있다.

```
<타입>: <무엇을 했는지 한 줄>

<왜 그렇게 했는지>
```

<br/>

```
feat: 로또 당첨 통계 계산 기능 추가

당첨 번호와 구입한 로또를 비교해 등수를 매긴다.
보너스 번호는 5개가 일치할 때만 확인한다.
```

<br/>

`무엇을` 은 코드를 보면 알 수 있다. 그래서 본문에는 `왜` 를 적는다.

몇 달 뒤에 `이 조건은 왜 붙었지` 라고 물을 때 답이 되는 것은 본문 쪽이다.

<br/>

## 타입은 대개 이 정도로 쓴다

```
feat     - 기능 추가
fix      - 버그 수정
refactor - 동작은 그대로 두고 구조만 바꿈
test     - 테스트 추가나 수정
docs     - 문서
chore    - 빌드 설정, 의존성 같은 잡일
```

<br/>

`refactor` 를 따로 두는 것이 실무에서 꽤 유용하다.

`동작이 안 바뀌었다` 는 표시라, 리뷰할 때 볼 관점이 달라진다.

<br/>

## 커밋 단위가 메시지보다 중요하다

메시지를 잘 쓰려면 커밋이 잘 나뉘어야 한다.

```
git commit -m "로또 기능 구현"        # 파일 20개, 변경 500줄
```

<br/>

이러면 아무리 메시지를 잘 써도 나중에 되돌릴 수가 없다.

버그가 하나 발견됐을 때 그것만 골라 되돌릴 방법이 없는 것이다.

<br/>

`한 커밋에 한 가지 변경` 이 기준이다.

```
feat: 로또 번호 생성기 추가
test: 로또 번호 중복 검증 테스트 추가
refactor: 당첨 등수 판별을 enum 으로 옮김
```

<br/>

앞의 코딩 컨벤션 글에서 본 `한 함수가 한 가지 기능` 과 같은 발상이다.

단위가 작으면 이름 짓기가 쉬워지고, 이름이 어려우면 단위가 큰 것이다.

<br/>

## 브랜치를 확인하라는 규칙

원문의 그 항목이 실수하기 제일 쉬운 자리다.

```bash
git branch                 # 지금 어디 있는지
git log --oneline -5       # 무엇을 커밋했는지
git diff main...HEAD --stat  # main 과 비교해 무엇이 바뀌었는지
```

<br/>

PR을 열기 전에 이 세 줄을 확인하면 대부분의 사고를 막는다.

<br/>

제일 흔한 사고는 `main 에서 바로 작업한 것` 이다.

```bash
# 이미 main 에 커밋해버렸다면
git branch feature/lotto        # 지금 상태로 브랜치를 만들고
git reset --hard origin/main    # main 은 원격 상태로 되돌린다
git switch feature/lotto        # 브랜치로 옮겨간다
```

<br/>

두 번째는 `이전 작업이 섞여 들어간 것` 이다.

브랜치를 딸 때 최신 `main` 에서 따지 않으면, 남의 커밋이 내 PR에 들어간다.

```bash
git switch main
git pull
git switch -c feature/lotto     # 최신 main 에서 딴다
```

<br/>

## README 를 상세히 쓰라는 이유

리뷰어가 코드를 읽기 전에 읽는 문서이기 때문이다.

<br/>

무엇을 만들려 했는지 모르는 상태로 코드를 보면, 리뷰가 `이 코드가 맞나` 가 아니라

`이게 뭐 하는 코드지` 에서 시작한다.

<br/>

기능 목록이 있으면 리뷰어가 이렇게 볼 수 있다.

```
- [x] 로또 번호는 1~45 중 중복 없이 6개
- [x] 구입 금액은 1000원 단위
- [ ] 보너스 번호는 당첨 번호와 중복될 수 없다     <- 이건 아직 없구나
```

<br/>

## 기능 목록을 계속 업데이트하라는 규칙

원문의 마지막 두 항목이 사실 하나의 얘기다.

<br/>

처음 쓴 기능 목록은 대개 틀린다. 만들다 보면 빠진 것이 나오기 때문이다.

```
처음   - 로또를 구매한다
만들다가 - 구입 금액이 1000원으로 안 나누어떨어지면? 0원이면? 음수면?
```

<br/>

이 예외들이 앞의 테스트 코드 작성 규칙 글에서 본 `경계값` 이다.

기능 목록을 다시 볼 때마다 그것들이 드러나고, 그게 곧 테스트 목록이 된다.

<br/>

그래서 `기능 목록 -> 테스트 -> 구현` 순서가 자연스럽게 만들어진다.
