## 객체는 객체스럽게 사용한다

<br/>

## 객체의 상태 접근을 제한한다

인스턴스 변수의 접근 제어자는 private으로 구현한다.

```java
public class WinningLotto {
    private Lotto lotto;
    private Integer bonusNumber;

    public WinningLotto(Lotto lotto, Integer bonusNumber) {
        this.lotto = lotto;
        this.bonusNumber = bonusNumber;
    }
}
```


<br/><br/>


**Lotto** 클래스는 **numbers**를 상태 값으로 가지는 객체이다. 

그런데 이 객체는 로직에 대한 구현은 하나도 없고, **numbers**에 대한 getter 메서드만을 가진다.

```java
public class Lotto {
    private final List<Integer> numbers;
    
    public Lotto(List<Integer> numbers) {
        this.numbers = numbers;
    }

    public int getNumbers() {
        return numbers;
    }
}

public class LottoGame {
    public void play() {
        Lotto lotto = new Lotto(...);

        lotto.getNumbers().contains(number);
        
        // 당첨 번호와 몇 개가 일치하는지 확인한다.
        lotto.getNumbers().stream()...
    }
}
```

<br/><br/>



**Lotto**에서 데이터를 꺼내지(get) 말고 메시지를 던지도록 구조를 바꿔 데이터를 가지는 객체가 일하도록 한다.

```java
public class Lotto {
    private final List<Integer> numbers;

    public boolean contains(int number) {
        // 숫자가 포함되어 있는지 확인한다.
```

getter를 사용하는 대신 객체에 메시지를 보내자

위 객체의 **profitRate**와 **totalPrize**는 등수 별 당첨 내역(**result**)만 있어도 모두 구할 수 있는 값이다. 

<br/><br/>

따라서 위 객체는 다음과 같이 하나의 필드만으로 구현할 수 있다.

```java
public class LottoResult {
```

## 포비 캡틴(박재성님)은 이런 말을 하셨다.

```
상태를 가지는 객체를 추가했다면 객체가 제대로 된 역할을 하도록 구현해야 한다.
객체가 로직을 구현하도록 해야한다.

상태 데이터를 꺼내 로직을 처리하도록 구현하지 말고 
객체에 메시지를 보내 일을 하도록 리팩토링한다.
```

<br/><br/>

## getter를 무조건 사용하지 말라는 말은 아니다.

당연히 getter를 무조건 사용하지 않고는 기능을 구현하기 힘들것이다. 

출력을 위한 값 등 순수 값 프로퍼티를 가져오기 위해서라면 어느정도 getter는 허용된다. 

<br/>

그러나, Collection 인터페이스를 사용하는 경우 외부에서 getter메서드로 얻은 값을 통해 상태값을 변경할 수 있다.

```java
public List<Car> getCars() {
		return cars;
} (x)

public List<Car> getCars() {
		return Collections.unmodifiableList(cars);
} (o)
```

이처럼 `Collections.unmodifiableList()` 와 같은 `Unmodifiable Collecion` 을 사용해 외부에서 변경하지 못하도록 하는 게 좋다.
<br/>

## 궁금증!

```java
getter 를 쓰지 말라는 게 무슨 뜻인지 코드로 보면
```

`데이터를 꺼내서 밖에서 계산하지 말고, 계산을 안으로 옮기라` 는 뜻이다.

```java
// 꺼내서 밖에서 계산한다
int total = 0;
for (Item item : cart.getItems()) {
    total += item.getPrice() * item.getCount();
}
if (member.getGrade() == Grade.VIP) {
    total = total * 90 / 100;
}
```

<br/>

이 코드에는 두 가지 문제가 있다.

<br/>

### 첫번째) 같은 계산이 여기저기 생긴다

주문할 때, 장바구니를 보여줄 때, 결제할 때 전부 이 계산이 필요하다.

세 군데에 복사되고, 할인율이 바뀌면 세 군데를 다 찾아 고쳐야 한다.

<br/>

### 두번째) 계산 규칙이 아무 데도 안 적혀 있다

`할인은 어떻게 계산하는가` 라는 질문에 답할 클래스가 없다.

`Cart` 도 모르고 `Member` 도 모른다. 쓰는 쪽만 안다.

<br/>

## 계산을 안으로 옮기면

```java
class Cart {
    private final List<Item> items;

    public int totalPrice() {
        return items.stream()
                .mapToInt(Item::amount)
                .sum();
    }
}

class Item {
    private final int price;
    private final int count;

    public int amount() {
        return price * count;
    }
}

class Member {
    private final Grade grade;

    public int discount(int price) {
        return grade.discount(price);
    }
}
```

```java
int total = member.discount(cart.totalPrice());
```

<br/>

`getPrice()` 도 `getCount()` 도 안 쓴다.

계산이 그 값을 가진 클래스 안으로 들어갔다.

<br/>

앞의 클래스와 메소드의 사용 이유는 글에서 본 `메서드를 어디에 둘지는 그 데이터를 가진 쪽` 이 이 기준이다.

<br/>

## 앞에서 본 예제들이 전부 이 방식이었다

```java
item.removeStock(count);              // item.getStock() 을 꺼내지 않는다
member.changeName(name);              // member.setName() 이 아니다
order.cancel();                       // order.setStatus(CANCELED) 가 아니다
```

<br/>

앞의 게시판 수정, 삭제 글에서 본 `주문 취소` 얘기가 이 차이를 잘 보여준다.

```java
order.setStatus(CANCELED)     // 상태값 하나만 바꾸는 것처럼 보인다
order.cancel()                // 재고 복구, 결제 취소까지 안에서 처리한다
```

<br/>

## getter 를 아예 쓰지 말라는 것은 아니다

원문에서도 그렇게 적혀 있다. 화면에 보여줄 때는 꺼내야 한다.

```java
// 화면에 뿌릴 때는 어쩔 수 없다
model.addAttribute("name", member.getName());
```

<br/>

앞의 DTO 글에서 본 대로, 이럴 때는 DTO로 바꿔서 나가는 편이 낫다.

```java
return MemberResponse.from(member);
```

<br/>

`from` 안에서는 게터를 쓰지만, 그 한 군데로 모이니 나머지 코드는 깨끗해진다.

<br/>

## 판단 기준

```java
값을 꺼내서 "그 값으로 계산" 한다  -> 계산을 안으로 옮긴다
값을 꺼내서 "그냥 보여준다"       -> getter 를 써도 된다
```

<br/>

꺼낸 값으로 `if` 를 쓰거나 사칙연산을 하고 있으면 신호다.

그 판단은 그 값을 가진 객체가 해야 하는 일일 가능성이 높다.

```java
if (member.getGrade() == Grade.VIP) { ... }     // 밖에서 판단한다
if (member.isVip()) { ... }                      // 안에서 판단한다
```

<br/>

## 이게 앞의 상속 글과도 이어진다

앞의 상속 정의, 상속이 갖는 단점들 글에서 본 `CountingSet` 예제를 떠올려보면,

`HashSet` 의 내부 동작에 의존해서 문제가 생겼다.

<br/>

`꺼내서 밖에서 처리하는` 방식은 그것과 같은 성질의 문제를 만든다.

객체의 내부 구조를 밖이 알게 되어서, 내부가 바뀌면 밖도 같이 깨진다.

```java
cart.getItems() 를 쓰는 코드가 열 군데 있다
-> Cart 가 List 대신 Map 을 쓰도록 바꾸면 열 군데가 다 깨진다

cart.totalPrice() 만 쓴다
-> 내부를 바꿔도 밖은 안 바뀐다
```

앞의 인터페이스 글에서 본 `구체적인 것을 알면 그게 바뀔 때마다 나도 바뀐다` 와 같은 얘기다.
