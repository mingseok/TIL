## 자바 가상머신(JVM)

<br/>

## 자바 가상머신(JVM) 운영체제 위에서 동작한다.

- JVM은 운영체제로부터 할당받은 메모리 공간을 기반으로 자바 프로그램을 실행해야 한다.
- JVM은 운영체제로부터 할당받은 메모리 공간을 이용해서 자기 자신도 실행을 하고, 자바 프로그램도 실행을 한다.
    
<br/>


### 총 메모리 공간은 세개의 영역으로 구분한다

- 메서드 영역

    - 메서드의 바이트 코드, static 변수
- 스택 영역
    - 지역변수, 매개변수
- 힙 영역
    - 인스턴스(객체)

<br/>

## 바이트코드란?

- 바이트코드는 고급 언어로 작성된 소스 코드를
    
    가상머신이 이해할 수 있는 중간 코드로 컴파일한 것을 말한다.


<br/>

## 가상머신은

바이트코드를 각각의 하드웨어 아키텍처에 맞는 기계어로 다시 컴파일한다.

정리하자면, 자바 바이트코드는 자바 가상머신에 의해서 실행되는 코드이다.

<br/>

## 메서드 영역

- 메서드의 자바 바이트코드는 JVM이 구분하는 메모리 공간 중에서 `메서드 영역`에 저장된다.

- static으로 선언된 클래스 변수도 `메서드 영역`에 저장된다.

```java
public class JavaTest {

    // 메인 메서드도 static 이므로 메서드 영역에 저장
    public static void main(String[] args) { 
		
    }
}

class JVMTest {
    static int average = 0; // 메서드 영역 저장
    public void Run() { }
}
```

이 영역에 저장된 내용은 프로그램 시작 전에 로드되고, 프로그램 종료시 소멸된다.

<br/><br/>

## 스택 영역

- 매개변수, 지역변수가 할당되는 메모리 공간

- 프로그램이 실행되는 도중에 임시로 할당되었다가 바로 소멸되는 특징이 있는 변수가 할당된다.
- 이 영역에 저장된 변수는 해당 변수가 선언된 메서드 종료시 소멸된다.

![이미지](/programming/img/입문386.PNG)

<br/><br/>

## 힙 영역

- 인스턴스(객체)가 생성되는 메모리 공간

- JVM에 의한 메모리 공간의 정리(가비지 컬렉션)이 이뤄지는 공간
- 할당은 프로그래머가 소멸은 JVM이 처리한다
- 참조변수에 의한 참조가 전혀 이뤄지지 않는 인스턴스가 소멸의 대상이 된다
    - 따라서 JVM은 인스턴스의 참조관계를 확인하고 소멸할 대상을 선정한다.

![이미지](/programming/img/입문387.PNG)

<br/><br/>

## Garbage Collection에 대한 추가 설명

- GC는 한번도 발생하지 않을 수 있다.

- GC가 발생하면, 소멸의 대상이 되는 인스턴스는 결정되지만 이것이 실제 소멸로 바로 이어지지는 않는다.
- 인스턴스의 실제 소멸로 이어지지 않은 상태에서 프로그램이 종료될 수 있다.
- 종료가 되면 어차피 인스턴스는 소멸 된다.
<br/>

## 궁금증!

```java
JVM 이 지금 무엇을 하고 있는지 볼 수 있나
```

JDK에 딸려오는 명령들로 볼 수 있다.

```java
$ jps            - 돌고 있는 자바 프로세스 목록
$ jstat -gc PID  - GC 통계
$ jstack PID     - 스레드 덤프
$ jmap -histo PID - 힙에 어떤 객체가 몇 개 있는지
$ jcmd PID VM.flags - 지금 적용된 옵션
```

<br/>

서버가 느려졌을 때 제일 먼저 보는 게 `jstack` 이다.

<br/>

앞의 멀티 쓰레드 글에서 본 스레드들이 지금 무엇을 하는지 나온다.

```java
"http-nio-8080-exec-1" ... WAITING (parking)
    at jdk.internal.misc.Unsafe.park
    at com.zaxxer.hikari.pool.HikariPool.getConnection
```

<br/>

이렇게 나오면 커넥션 풀에서 막힌 것이다.

앞의 커넥션 풀 글에서 본 그 상황이 실제로 이렇게 보인다.

<br/>

## 힙 덤프를 뜨는 방법

메모리가 새는 것 같으면 덤프를 떠서 본다.

```java
$ jmap -dump:live,format=b,file=heap.hprof PID
```

<br/>

터졌을 때 자동으로 뜨게 할 수도 있다.

```java
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/
```

<br/>

`OutOfMemoryError` 는 재현이 어려우니 이 옵션을 미리 켜두는 게 낫다.

터진 순간의 힙이 파일로 남는 것이다.

<br/>

## JVM 이 세 부분으로 나뉜다

```java
클래스 로더  - .class 를 읽어서 메모리에 올린다
런타임 영역  - 힙, 스택, 메서드 영역
실행 엔진    - 인터프리터, JIT, GC
```

<br/>

앞의 클래스 로딩 순서 글에서 본 로딩 과정이 첫 번째다.

앞의 자바 메모리 구조 글에서 본 것이 두 번째다.

<br/>

세 번째가 재미있다.

```java
인터프리터 - 바이트코드를 한 줄씩 해석한다. 시작이 빠르다
JIT       - 자주 도는 것을 기계어로 컴파일한다. 나중에 빨라진다
```

<br/>

앞의 JIT 컴파일러 글에서 본 그 조합이다.

`둘 중 하나` 가 아니라 `처음엔 해석하다가 뜨거워지면 컴파일한다` 는 방식이다.

<br/>

## 그래서 서버는 처음이 느리다

배포 직후에 응답이 느리다가 점점 빨라지는 게 이것 때문이다.

<br/>

무중단 배포를 할 때 새로 뜬 인스턴스에 트래픽을 한꺼번에 보내면

JIT이 아직 안 돌아서 느리게 응답한다.

<br/>

그래서 천천히 늘려주는 설정을 쓰기도 한다.

```java
warm-up 요청을 몇 번 보내고 나서 로드밸런서에 붙인다
```

<br/>

## write once, run anywhere 라는 말

```java
.java  -> javac -> .class (바이트코드)
.class -> JVM   -> 기계어
```

<br/>

바이트코드까지는 어느 OS에서 만들든 같다.

그것을 각 OS의 기계어로 바꾸는 게 JVM이다.

<br/>

앞의 자바 파일 컴파일 과정 글에서 본 그 두 단계다.

<br/>

그런데 `run anywhere` 가 완전하지는 않다.

```java
File.separator      - 윈도우는 \, 리눅스는 /
줄바꿈 문자         - \r\n 과 \n
기본 문자 인코딩    - OS 설정을 따라간다
```

<br/>

앞의 한글이 깨지는 이유 글에서 본 그 문제다.

<br/>

자바 18부터 기본 인코딩이 `UTF-8` 로 고정됐다.

그 전에는 윈도우에서 만든 파일이 리눅스 서버에서 깨지는 일이 흔했다.

<br/>

## JVM 위에 자바만 있는 게 아니다

```java
Kotlin, Scala, Groovy, Clojure
```

<br/>

전부 바이트코드로 컴파일된다.

<br/>

그래서 코틀린에서 자바 라이브러리를 그대로 쓸 수 있는 것이다.

같은 바이트코드가 되고 나면 어느 언어에서 왔는지는 상관이 없다.

<br/>

스프링도 코틀린을 지원한다.

앞의 스프링이 뭔가 글에서 본 것들이 전부 바이트코드 수준에서 동작하기 때문이다.

<br/>

## JVM 이 여러 개다

```java
HotSpot   - 오라클, 오픈JDK. 표준
GraalVM   - 네이티브 이미지로 만들 수 있다
OpenJ9    - IBM. 메모리를 덜 쓴다
```

<br/>

`GraalVM` 의 네이티브 이미지가 요즘 얘기가 많이 된다.

```java
JVM 없이 도는 실행 파일로 만든다
기동이 밀리초 단위로 빨라진다
대신 빌드가 오래 걸리고 리플렉션에 제약이 생긴다
```

<br/>

앞의 리플렉션(Reflection) 글에서 본 대로,

스프링이 리플렉션을 많이 써서 이 제약이 걸린다.

<br/>

그래서 스프링 부트 3부터 `AOT` 처리를 지원한다.

빌드할 때 미리 리플렉션 대상을 찾아서 등록해두는 방식이다.

<br/>

서버리스처럼 자주 뜨고 지는 환경에서는 기동 속도가 중요해서 이 방향이 주목받는 것이다.
