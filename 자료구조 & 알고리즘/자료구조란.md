### 이건 어떤 원리로 올라오게 되는가??

즉, 사용자 입장에서는 이걸 자세한 내부 구조를 알 필요가 없다.

괜히 머리만 더 아플 뿐이다. 즉, 이걸 알아서도 안된다 !! 왜냐?? 내 머릿속만 복잡해 지기 때문이다.

<br/>

이런 것이 캡슐화의 의미이다.

![이미지](/programming/img/알잡2.PNG)

즉, 이 자료구조를 사용하는 사람은 자료구조가 어떻게 동작하는지 
알 필요가 없다는 것이고 캡슐 이란게 ‘알약’ 이다.<br/> 
이, 알약 안에 내부 구조와 내부 원리를 숨겨 놔야 되는 것이다. 
그리고 사용자는 볼 수 없어야 된다. 왜? “알 필요가 없으니깐”

<br/>

### 요약하자면 자료구조를 사용하는 사람은 내부적으로 어떻게 돌아가는지는 알 필요도 없고, 알아서도 안된다.

![이미지](/programming/img/알잡3.PNG)

<br/>

구조체 안에 선언된 변수를 ‘멤버변수’ 라고 말하고,

구조체 안에 선언된 함수를 ‘메소드’ 라고 부른다.

![이미지](/programming/img/알잡4.PNG)

물론 나는 안다. 왜? 내가 ‘설계자’ 니깐 그런데, 친구한테 이 기계를 알려준다면 상황이 어떤가?

친구는 내부 원리를 모를 것이다. 그냥 사용 방법만 알려주면 되는 것이다.
<br/>

## 궁금증!

```java
자료구조를 고르는 기준이 무엇인가
```

`무슨 연산을 자주 하는가` 다.

```java
인덱스로 자주 찾는다        -> ArrayList
앞뒤로 넣고 뺀다            -> ArrayDeque
중복 없이 담는다            -> HashSet
키로 찾는다                 -> HashMap
정렬된 상태를 유지한다       -> TreeMap, TreeSet
항상 최솟값을 꺼낸다         -> PriorityQueue
```

<br/>

`무엇을 담는가` 가 아니라 `어떻게 쓰는가` 가 기준인 것이다.

<br/>

## 실제 비용 차이를 재봤다

앞의 노드 글에서 본 측정이다.

```java
맨 앞 삽입 10만 번   ArrayList = 451ms,  LinkedList = 4ms
인덱스 조회 10만 번  ArrayList = 2ms,    LinkedList = 3986ms
```

<br/>

같은 `List` 인터페이스인데 100배 넘게 갈린다.

<br/>

앞의 Java에서의 역할과 구현 글에서 본 대로

인터페이스로 받으면 구현을 바꿔 끼울 수 있는데,

성능 특성은 완전히 다르다는 것을 알고 골라야 하는 것이다.

<br/>

## 시간과 공간을 맞바꾼다

```java
배열     - 조회 O(1), 삽입 O(n)
연결 리스트 - 조회 O(n), 삽입 O(1)
해시 테이블 - 조회 O(1), 대신 메모리를 여유 있게 쓴다
```

<br/>

앞의 해시(Hash) 글에서 본 `load factor 0.75` 가 그 여유다.

<br/>

칸을 꽉 채우면 충돌이 늘어서 느려지니, 25%는 비워두는 것이다.

<br/>

`빠르게 하려고 메모리를 더 쓴다` 는 게 자료구조의 기본 거래다.

<br/>

앞의 캐시 글에서 본 것도 같은 거래다.

<br/>

## 추상 자료형과 구현을 나눠 봐야 한다

```java
스택 (ADT)  -> ArrayDeque, LinkedList, 배열로 구현 가능
큐 (ADT)    -> ArrayDeque, LinkedList
```

<br/>

`스택` 은 `넣고 빼는 규칙` 을 말하는 것이지 구현이 아니다.

<br/>

앞의 스택 글에서 본 대로,

자바에는 `Stack` 클래스가 있는데 안 쓰는 게 낫다.

```java
Stack extends Vector      -> 모든 메서드가 synchronized. 느리다
Stack.get(0)              -> 인덱스 접근이 열려 있다. 스택이 아니게 된다
```

<br/>

`ArrayDeque` 를 쓰라고 자바 문서에도 적혀 있다.

<br/>

## 자바 컬렉션의 계층

```java
Collection
├── List   - 순서 있음, 중복 허용
├── Set    - 중복 없음
└── Queue  - 넣고 빼는 순서가 정해짐

Map        - Collection 이 아니다
```

<br/>

`Map` 이 `Collection` 을 상속하지 않는다는 게 특이하다.

<br/>

`Collection` 은 원소 하나를 다루는데 `Map` 은 쌍을 다루기 때문이다.

`add(E)` 를 어떻게 구현할지가 안 맞는다.

<br/>

앞의 SOLID 글에서 본 인터페이스 분리 원칙에 가깝다.

억지로 같은 인터페이스에 넣지 않은 것이다.

<br/>

## 스레드 안전한 것들이 따로 있다

```java
ArrayList   -> CopyOnWriteArrayList
HashMap     -> ConcurrentHashMap
ArrayDeque  -> ConcurrentLinkedDeque
```

<br/>

앞의 멀티 쓰레드 글에서 확인한 대로,

일반 컬렉션을 여러 스레드가 동시에 건드리면 값이 사라진다.

<br/>

`Collections.synchronizedList()` 로 감쌀 수도 있는데,

메서드마다 락을 잡아서 `ConcurrentHashMap` 보다 느리다.

<br/>

`ConcurrentHashMap` 은 버킷 단위로만 잠근다.

전체를 잠그지 않으니 동시에 여러 스레드가 다른 버킷을 건드릴 수 있는 것이다.

<br/>

## 처음부터 최적을 고를 필요는 없다

대부분 `ArrayList` 와 `HashMap` 으로 시작하면 된다.

<br/>

데이터가 수백 건이면 무엇을 써도 차이가 안 난다.

앞의 Big_O 글에서 본 대로 `n` 이 작으면 상수가 지배하기 때문이다.

<br/>

문제가 생겼을 때 무엇으로 바꿔야 할지를 아는 게 더 중요하다.

`무엇이 느린지` 를 재보고 바꾸는 순서인 것이다.
