## 기본값 타입

<br/>

## JPA의 데이터 타입 크게 2가지로 분류

### 엔티티 타입

- @Entity로 정의하는 객체이다.

- 데이터가 변해도 식별자로 지속해서 추적 가능하다
    - ex) 회원 엔티티의 키나 나이 값을 변경해도 식별자로 인식 가능하다.

<br/>

### 값 타입

- int, Integer, String처럼 단순히 값으로 사용하는 자바 기본 타입이나 객체이다.

- 식별자가 없고 값만 있으므로 변경시 추적 불가하다.
    - ex) 숫자 100을 200으로 변경하면 완전히 다른 값으로 대체가 되어 버린다.

<br/><br/>

## 값 타입 분류

- 기본값 타입

    - 자바 기본 타입(=primitive type)
    - 래퍼 클래스(Integer, Long)

    - String
- 임베디드 타입(embedded type, 복합 값 타입)
    - ex) x, y 좌표를 묶어서 사용하고 싶을때 사용한다.

- 컬렉션 값 타입(collection value type)

    - 자바 컬렉션에다가 기본값 타입 or 임베디드 타입을 넣어서 사용할 수 있는것

<br/><br/>

## 기본값 타입

- ex): String name, int age
- 생명주기를 엔티티의 의존
    - ex) 회원을 삭제하면 이름, 나이 필드도 함께 삭제
    
- 값 타입은 공유하면 안된다.
    - ex) 내 이름 변경시 다른 회원의 이름도 함께 변경되면 안되기 때문이다.
<br/>

## 궁금증!

```java
엔티티 타입과 값 타입을 나누는 기준이 "식별자" 라는 게 무슨 뜻일까
```

`이것이 그것과 같은가` 를 무엇으로 판단하느냐다.

```java
엔티티 - 식별자가 같으면 같은 것이다. 값이 달라져도 같은 것이다
값 타입 - 값이 같으면 같은 것이다. 식별자가 없다
```

<br/>

```java
Member member = ...;
member.changeName("바뀐이름");
// 이름이 바뀌었지만 여전히 같은 회원이다 (id 가 같으니까)

Address address = new Address("서울", ...);
// city 를 바꾸면 그건 다른 주소다
```

<br/>

앞의 equals, hashCode 글에서 본 `동일성과 동등성` 이 이 구분과 맞물린다.

```java
엔티티 - == 로 비교해도 된다 (앞의 영속성 컨텍스트 글의 동일성 보장)
값 타입 - equals 로 비교해야 한다
```

<br/>

## 값 타입을 공유하면 안 된다는 것

원문의 마지막 항목이 앞의 값 타입과 불변 객체 글에서 본 그 문제다.

```java
Address address = new Address("서울", "테헤란로", "12345");
member1.setHomeAddress(address);
member2.setHomeAddress(address);

member1.getHomeAddress().setCity("부산");     // member2 도 부산이 된다
```

<br/>

앞의 원시형과 참조형 타입에 대해 글에서 확인한 그 성질 때문이다.

```java
원시형 = 10
참조형 = 99
```

<br/>

참조형은 주소를 복사해서 나누니, 안을 고치면 양쪽 다 바뀐다.

<br/>

`int` 나 `String` 은 이 문제가 없다.

```java
int a = 10;
int b = a;        // 값 자체가 복사된다
b = 20;           // a 는 그대로 10
```

```java
String s1 = "서울";
String s2 = s1;
// String 은 불변이라 애초에 못 바꾼다
```

<br/>

앞의 String 객체가 불변인 이유 글에서 본 그 성질이 여기서도 이득이 된다.

<br/>

## 그래서 임베디드 타입은 불변으로 만든다

`int` 나 `String` 처럼 안전하게 만들려면 불변이어야 한다.

<br/>

앞의 임베디드 타입 글에서 본 대로 `setter` 를 없애면 된다.

```java
@Embeddable
public class Address {
    private String city;
    private String street;
    private String zipcode;

    protected Address() { }

    public Address(String city, String street, String zipcode) { ... }
    // setter 없음
}
```

<br/>

## 래퍼 클래스도 값 타입이다

원문의 분류에 `래퍼 클래스(Integer, Long)` 가 들어 있는데,

앞의 래퍼 클래스 사용 이유는 글에서 본 대로 이것도 불변이다.

```java
Integer a = 1;
a = 2;         // 2 라는 새 객체가 만들어진다. 원래 1 은 안 바뀐다
```

<br/>

그래서 공유해도 안전하다.

<br/>

다만 엔티티 필드에서 `int` 와 `Integer` 중 무엇을 쓸지는 다른 문제다.

앞의 래퍼 클래스 사용 이유는 글에서 본 대로 `null` 을 담을 수 있는지가 갈림길이다.

```java
private int age;        // 컬럼이 nullable 이면 null 을 받을 수 없어 터진다
private Integer age;    // null 을 받을 수 있다
```

<br/>

JPA 엔티티에서는 대개 래퍼 클래스를 쓴다.

DB 컬럼이 `NULL` 을 허용할 수 있고, 앞의 스프링 데이터 JPA 설명 글에서 본

`isNew` 판단도 식별자가 `null` 인지로 하기 때문이다.

```java
@Id
private long id;        // 0 이 기본값이라 isNew 판단이 안 된다
private Long id;        // null 이면 새 것
```

<br/>

## 생명주기가 엔티티에 의존한다는 것

```java
회원을 삭제하면 이름과 나이 필드도 함께 삭제된다
```

<br/>

당연해 보이는데, 임베디드 타입에서는 이게 의미가 있다.

```java
@Embedded
private Address homeAddress;
```

<br/>

`Address` 는 `member` 테이블의 컬럼으로 풀려 있다.

회원 행을 지우면 그 컬럼도 같이 사라진다. 따로 관리할 것이 없다.

<br/>

반면 앞의 값 타입과 불변 객체 글에서 본 값 타입 컬렉션은 별도 테이블이라,

지울 때 앞의 영속성 전이 CASCADE 글에서 본 문제가 생긴다.

```java
회원을 지우면 favorite_food 행도 지워야 한다
```

<br/>

JPA가 자동으로 해주기는 하는데, 그 순간 `DELETE` 가 여러 번 나간다.

값 타입 컬렉션을 잘 안 쓰는 이유가 여기에도 있다.
