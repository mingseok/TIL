## 즉시 로딩과 지연 로딩

결론부터 말하자면, 모든 연관관계는 지연로딩으로 설정해야된다. (외워야 하는 수준)

즉시로딩( EAGER )은 예측이 어렵고, 어떤 SQL이 실행될지 추적하기 어렵다. 


<br/>

특히 JPQL을 실행할 때 N+1 문제가 자주 발생한다.

실무에서 모든 연관관계는 지연로딩( LAZY )으로 설정해야 한다.

```java
@OneToMany, 등은 디폴트가 (fetch = FetchType.LAZY)로 되어 있다.

하지만, 문제는 @ManyToOne인 것이다.
@ManyToOne, @OneToOne 붙어있는 곳에는 모두 (fetch = FetchType.LAZY)로 직접 작성해줘야 하는 것이다.
```


<br/><br/>

## 지연 로딩

![이미지](/programming/img/입문371.PNG)

지연(=LAZY) 로딩으로 세팅이 되어 있으면, 프록시를 가져온다.

<br/><br/>

## 지연 로딩 LAZY을 사용해서 프록시로 조회

```java
@Entity
public class Member extends BaseEntity {

    // 생략..
    
    @ManyToOne(fetch = FetchType.LAZY) // 핵심
    @JoinColumn(name = "TEAM_ID")
    private Team team;
    
    // 생략..
}
```

<br/><br/>

## 지연 로딩 LAZY을 사용해서 프록시로 조회

```java
Team team = member.getTeam();
team.getName(); // 실제 team을 사용하는 시점에 초기화(DB 조회)
```

<br/><br/>

## 즉시 로딩 EAGER를 사용해서 함께 조회

```java
@Entity
public class Member extends BaseEntity {

    // 생략..
    
    @ManyToOne(fetch = FetchType.EAGER) // 핵심
    @JoinColumn(name = "TEAM_ID")
    private Team team;
    
    // 생략..
}
```

## 프록시와 즉시로딩 주의

- 모든 연관관계에서는 지연 로딩만 사용하자.

    - 실무에서는 즉시 로딩을 사용하면 안된다.
    
- 즉시 로딩을 적용하면 예상하지 못한 SQL이 발생
- 즉시 로딩은 JPQL에서 N+1 문제를 일으킨다.
- @ManyToOne, @OneToOne은 디폴트가 즉시 로딩이다 -> 그렇기에 직접 LAZY로 설정하기.
- @OneToMany, @ManyToMany는 기본이 지연 로딩

<br/>

## 궁금증!

```java
"즉시 로딩을 쓰지 마라" 는 게 왜 그렇게 강한 권고일까?
```

세 가지 문제가 겹친다.

<br/>

## 첫번째) 예상 못 한 쿼리가 나간다

```java
@ManyToOne(fetch = FetchType.EAGER)
private Team team;
```

<br/>

`Member` 하나만 조회했는데 `Team` 까지 같이 조회된다.

`Team` 이 또 다른 것을 `EAGER` 로 물고 있으면 그것까지 딸려온다.

<br/>

앞의 DB 인덱스 글에서 본 대로, 안 쓸 것을 읽는 것은 그냥 낭비다.

목록 화면에서 팀 이름을 안 보여주는데도 매번 조인이 붙는다.

<br/>

## 두번째) JPQL 에서 N+1 이 그대로 터진다

이게 제일 큰 이유다.

```java
List<Member> members = em.createQuery("SELECT m FROM Member m", Member.class)
        .getResultList();
```

<br/>

`EAGER` 니까 조인해서 한 번에 가져올 것 같은데 그렇지 않다.

```sql
SELECT * FROM member;                      -- 1번
SELECT * FROM team WHERE id = 1;           -- 회원 수만큼
SELECT * FROM team WHERE id = 2;
...
```

<br/>

JPQL은 우리가 적은 그대로 SQL로 바뀐다.

`SELECT m FROM Member m` 은 `SELECT * FROM member` 가 되고,

그 다음에 `EAGER` 라서 팀을 하나씩 채우러 간다.

<br/>

앞의 DB 접근(JPA) 글에서 본 `N+1` 이 정확히 이것이다.

`EAGER` 로 바꾸면 해결될 것 같은데 오히려 더 나빠지는 이유다.

```java
LAZY  - 안 쓰면 쿼리가 안 나간다. 쓰면 그때 나간다
EAGER - 쓰든 안 쓰든 나간다. 그것도 하나씩
```

<br/>

## 세번째) 끌 수가 없다

`LAZY` 는 필요할 때 `fetch join` 으로 한 번에 가져올 수 있다.

```java
SELECT m FROM Member m JOIN FETCH m.team
```

<br/>

`EAGER` 는 반대가 안 된다. `이번에는 안 가져와도 돼` 라고 말할 방법이 없다.

<br/>

그래서 `LAZY 로 두고 필요할 때 fetch join` 이 정석이 된다.

앞의 JPQL - 페치 조인 글에서 다루는 것이 그 방법이다.

<br/>

## 기본값을 확인해두면 실수가 준다

```java
@ManyToOne  - 기본값이 EAGER   -> 반드시 LAZY 로 바꿔야 한다
@OneToOne   - 기본값이 EAGER   -> 반드시 LAZY 로 바꿔야 한다
@OneToMany  - 기본값이 LAZY    -> 그대로 두면 된다
@ManyToMany - 기본값이 LAZY    -> 그대로 두면 된다
```

<br/>

`ToOne` 쪽이 `EAGER` 인 이유는 `하나뿐이니 같이 가져와도 되겠지` 라는 판단이었다.

그런데 위에서 본 문제 때문에 실무에서는 뒤집혔다.

```java
@ManyToOne(fetch = FetchType.LAZY)
private Team team;
```

<br/>

이걸 매번 적는 것이 번거로워서, 팀 규칙으로 정해두거나 검사 도구로 막기도 한다.

<br/>

## @OneToOne 은 LAZY 로 해도 안 될 때가 있다

이게 잘 안 알려진 함정이다.

```java
@OneToOne(fetch = FetchType.LAZY)
private Locker locker;
```

<br/>

연관관계의 주인이 아닌 쪽에서는 `LAZY` 가 안 먹는다.

<br/>

이유는 앞의 프록시 기초 글에서 본 구조에 있다.

프록시를 만들려면 `있는지 없는지` 를 알아야 하는데,

주인이 아닌 쪽은 외래 키를 안 갖고 있어서 조회해보기 전에는 알 수가 없다.

```java
Member 가 locker_id 를 갖고 있다 -> Member 쪽에서는 LAZY 가 된다
Locker 는 member_id 가 없다      -> Locker 쪽에서는 EAGER 로 동작한다
```

<br/>

`null` 인지 아닌지를 알아야 프록시를 넣을지 `null` 을 넣을지 정할 수 있기 때문이다.

<br/>

## 그래서 실무 규칙은 두 줄로 정리된다

```java
1. 모든 연관관계를 LAZY 로 둔다
2. 필요한 곳에서 fetch join 이나 EntityGraph 로 한 번에 가져온다
```

<br/>

앞의 엔티티 조회 DTO 조회 글에서 다루는 `쿼리 방식 선택 권장 순서` 가 그 다음 단계다.

`fetch join` 으로도 부족하면 DTO로 직접 조회하는 쪽으로 간다.
