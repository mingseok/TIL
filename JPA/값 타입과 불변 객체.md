## 값 타입과 불변 객체

```
값 타입은 복잡한 객체 세상을 조금이라도 단순화하려고 만든 개념이다. 
따라서 값 타입은 단순하고 안전하게 다룰 수 있어야 한다.
```

<br/>

## 기본 타입(primitive type)

```java
int a = 10;
int b = a; // 기본 타입은 값을 복사
b = 4; 
```

b에 4를 대입하더라도 a는 그대로 유지가 된다. → 즉, 값이 복사가 되어 넘어가는 것.

<br/><br/>

## 객체 타입



```java
Address a = new Address(“Old”);
Address b = a; // 객체 타입은 참조를 전달
b.setCity(“New”)
```

객체 타입은 참조(주소)를 복사해서 넘긴다. → 그 뜻은 한 인스턴스만 존재한다는 것이다.

그리하여 여기서의 a, b는 둘중 하나만 건드려도 둘다 변경되게 되는 것이다.


<br/><br/>

## 값 타입의 비교

- `동일성 비교`: 인스턴스의 참조 값을 비교, `==` 사용

- `동등성 비교`: 인스턴스의 값을 비교, `equals()` 사용
- 값 타입은 `a.equals(b)`를 사용해서 동등성 비교를 해야 함
- 값 타입의 `equals()` 메소드를 적절하게 재정의 한다.`(주로 모든 필드 사용)`

<br/><br/>

## 값 타입 컬렉션 대안

- 실무에서는 상황에 따라 값 타입 컬렉션 대신에 일대다 관계를 고려한다.

- 일대다 관계를 위한 엔티티를 만들고, 여기에서 값 타입을 사용한다.
- 영속성 전이 + 고아 객체 제거를 사용해서 값 타입 컬렉션 처럼 사용하자.

## 궁금증!

```java
값 타입을 공유하면 무슨 일이 생기는지 코드로 보면
```

앞의 원시형과 참조형 타입에 대해 글에서 확인한 그 차이가 그대로 나온다.

```java
원시형 = 10
참조형 = 99
바꿔치기 = 10
```

<br/>

값 타입인데 객체로 만들면 `참조형` 의 성질을 갖게 된다.

주소를 복사해서 나눠 가지니, 한쪽이 안을 고치면 다른 쪽도 바뀐다.

<br/>

```java
Address address = new Address("서울", "테헤란로", "12345");
member1.setHomeAddress(address);
member2.setHomeAddress(address);

member1.getHomeAddress().setCity("부산");     // member2 도 부산이 된다
```

<br/>

그리고 앞의 영속성 컨텍스트 글에서 본 변경 감지가 둘 다에 대해 동작해서,

`UPDATE` 가 두 번 나간다. 내가 하나만 바꿨는데 두 행이 바뀌는 것이다.

<br/>

## 값 복사로 막을 수 있을까

```java
Address copy = new Address(address.getCity(), address.getStreet(), address.getZipcode());
member2.setHomeAddress(copy);
```

<br/>

동작은 하는데 문제가 있다. `복사하는 것을 잊을 수 있다` 는 것이다.

```java
member2.setHomeAddress(address);        // 컴파일도 되고 실행도 된다
```

<br/>

앞의 방어적 복사, Unmodifiable 글에서 본 것과 같은 얘기다.

`규칙을 사람이 기억해야 하면 언젠가 깨진다.`

<br/>

## 그래서 불변으로 만든다

`setter` 를 없애면 애초에 못 바꾼다.

```java
@Embeddable
public class Address {
    private String city;
    private String street;
    private String zipcode;

    protected Address() { }

    public Address(String city, String street, String zipcode) { ... }
    // setter 없음. getter 만
}
```

<br/>

이제 공유해도 안전하다. 아무도 안을 못 고치기 때문이다.

앞의 불변 객체 글에서 본 `읽는 사람만 있으면 지킬 것이 없다` 가 그대로 적용된다.

<br/>

바꿔야 하면 통째로 갈아끼운다.

```java
member.changeAddress(new Address("부산", "해운대로", "54321"));
```

<br/>

## 필드에 final 을 못 붙이는 이유

```java
private final String city;      // JPA 에서는 안 된다
```

<br/>

앞의 엔티티 매핑 글에서 본 세 조건 중 하나다.

JPA가 리플렉션으로 값을 채우려면 필드가 `final` 이면 안 된다.

<br/>

그래서 `setter 를 안 만드는 것` 으로 대신한다.

문법으로 강제되지는 않지만 실질적으로 같은 효과를 낸다.

<br/>

## 값 타입 컬렉션은 쓰지 말라는 얘기

원문의 `값 타입 컬렉션 대안` 이 가리키는 부분이다.

```java
@ElementCollection
@CollectionTable(name = "favorite_food", joinColumns = @JoinColumn(name = "member_id"))
private Set<String> favoriteFoods = new HashSet<>();
```

<br/>

편해 보이는데 두 가지가 걸린다.

<br/>

### 첫번째) 하나만 바꿔도 전부 지웠다 다시 넣는다

```java
member.getFavoriteFoods().remove("치킨");
member.getFavoriteFoods().add("피자");
```

```sql
DELETE FROM favorite_food WHERE member_id = 1;      -- 전부 지운다
INSERT INTO favorite_food VALUES (1, '한식');
INSERT INTO favorite_food VALUES (1, '피자');
INSERT INTO favorite_food VALUES (1, '중식');
```

<br/>

값 타입에는 식별자가 없어서 `어느 행을 바꿀지` 를 정할 수가 없다.

그래서 전부 지우고 다시 넣는 것이다.

<br/>

원소가 `100` 개면 매번 `100` 번의 `INSERT` 가 나간다.

<br/>

### 두번째) 조회가 불편하다

`좋아하는 음식이 치킨인 회원` 을 찾으려면 JPQL로 다루기가 까다롭다.

<br/>

## 그래서 엔티티로 만든다

```java
@Entity
public class FavoriteFood {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    private Member member;

    private String food;
}
```

<br/>

식별자가 생기니 하나만 지우고 하나만 추가할 수 있다.

조회도 리포지토리로 자유롭게 할 수 있다.

<br/>

앞의 다양한 연관관계 매핑 글에서 본 `@ManyToMany 대신 중간 엔티티` 와 같은 결론이다.

`편한 기능이 있는데 실무에서는 안 쓰고 직접 엔티티를 만든다` 는 패턴이 반복된다.

<br/>

값 타입 컬렉션은 `정말 단순하고 개수가 적고 통째로 갈아끼워도 되는` 경우에만 쓴다.

주소 이력처럼 `추적해야 하는` 것은 전부 엔티티로 만드는 편이 맞다.
