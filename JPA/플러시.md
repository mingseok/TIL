## 플러시란?

영속성 컨텍스트의 변경내용을 데이터베이스에 반영하는 것이다.

즉, 쌓아뒀던 sql 쿼리들을 DB에 날려주는 과정을 말하는 것이다.

```
영속성 컨텍스트의 '변경사항'과 데이터 베이스를 맞추는 작업이라고 생각하자.
```

<br/><br/>

## 플러시 발생

데이터 베이스 트랜잭션이 커밋되면, 자동적으로 플러시가 발생한다고 생각하면 된다.

- 변경 감지

- 수정된 `‘엔티티 쓰기 지연 SQL 저장소’`에 등록
- `‘쓰기 지연 SQL 저장소’`의 쿼리를 데이터베이스에 전송 `(=등록, 수정, 삭제 쿼리)`

```
추가로 플러시를 한다고해서 1차캐시를 지우거나 그러지 않는다.

단지, '쓰기 지연 SQL 저장소'에 있는 업데이트 쿼리들이 쌓이고 
이것들을 데이터 베이스에 반영이 되는 과정이라고 생각하면 된다.
```

<br/><br/>

## 플러시 정리

- 영속성 컨텍스트를 비우지 않음

- 영속성 컨텍스트의 변경내용을 데이터베이스에 동기화
- 트랜잭션이라는 작업 단위가 중요 → 커밋 직전에만 동기화 하면 된다.

## 궁금증!

```java
플러시가 커밋할 때만 일어나는 게 아니다
```

세 가지 경우에 일어난다.

```java
1. 트랜잭션이 커밋될 때        (자동)
2. JPQL 쿼리를 실행하기 직전   (자동)
3. em.flush() 를 직접 부를 때  (수동)
```

<br/>

`2번` 이 잘 안 알려져 있는데 실무에서 중요하다.

<br/>

## 왜 쿼리 직전에 플러시하는가

```java
em.persist(new Member("민석"));       // 아직 DB 에 안 갔다

List<Member> members = em.createQuery("SELECT m FROM Member m", Member.class)
        .getResultList();             // 방금 저장한 민석이 나올까?
```

<br/>

JPQL은 SQL로 바뀌어서 DB로 나간다. 영속성 컨텍스트를 안 본다.

<br/>

플러시를 안 하면 방금 저장한 민석이 조회 결과에 없다.

내가 방금 넣은 것을 못 찾는 이상한 상황이 되는 것이다.

<br/>

그래서 JPA는 JPQL을 실행하기 전에 자동으로 플러시한다.

```java
쿼리 실행 요청
  -> 대기 중인 SQL 을 먼저 DB 로 보낸다 (플러시)
  -> 그 다음 쿼리를 실행한다
```

<br/>

## 그런데 find() 는 플러시를 안 한다

```java
em.persist(new Member("민석"));
Member found = em.find(Member.class, 1L);      // 플러시가 안 일어난다
```

<br/>

`find()` 는 앞의 JPA 설정, 적용, 핵심 글에서 본 `1차 캐시` 를 먼저 본다.

영속성 컨텍스트에 이미 있으니 DB에 갈 이유가 없고, 그러니 플러시할 이유도 없다.

```java
find()  - 1차 캐시를 본다. 플러시 안 함
JPQL    - DB 로 나간다. 플러시 함
```

<br/>

## 그래서 JdbcTemplate 과 섞으면 문제가 된다

앞의 JDBC 반복 문제 해결 글에서 본 그 상황이다.

```java
memberRepository.save(member);                    // 아직 DB 에 안 갔다
jdbcTemplate.query("SELECT * FROM member");       // 방금 저장한 것이 안 보인다
```

<br/>

`JdbcTemplate` 은 JPA의 대기열을 모른다. JPA도 `JdbcTemplate` 이 쿼리를 날린다는 것을 모른다.

<br/>

그래서 직접 플러시해야 한다.

```java
memberRepository.save(member);
entityManager.flush();
jdbcTemplate.query(...);
```

<br/>

앞의 DB 접근 테스트 방법 글에서 본 `테스트는 통과하는데 운영에서 터진다` 도 이것과 관련이 있다.

`UNIQUE` 제약 위반이 플러시 시점에 드러나기 때문에, 플러시가 안 되면 안 걸린다.

<br/>

## 플러시 모드를 바꿀 수 있다

```java
em.setFlushMode(FlushModeType.COMMIT);     // 커밋할 때만 플러시한다
```

<br/>

`2번` 을 끄는 것이다. 쿼리 직전 플러시를 안 한다.

<br/>

성능이 조금 좋아질 수는 있는데, 위에서 본 `방금 저장한 것이 안 보이는` 문제가 생긴다.

기본값인 `AUTO` 를 그냥 두는 편이 안전하다.

<br/>

## 플러시가 영속성 컨텍스트를 안 비운다는 것

원문에서 강조한 그 부분이 `clear()` 와의 차이다.

```java
flush()  - SQL 을 보낸다. 1차 캐시는 그대로
clear()  - 1차 캐시를 비운다. SQL 은 안 보낸다
close()  - 영속성 컨텍스트를 닫는다
```

<br/>

그래서 대량 처리에서는 둘을 같이 쓴다.

```java
for (int i = 0; i < 100000; i++) {
    em.persist(new Member("회원" + i));

    if (i % 1000 == 0) {
        em.flush();     // DB 로 보내고
        em.clear();     // 1차 캐시를 비운다
    }
}
```

<br/>

`clear()` 를 안 하면 영속성 컨텍스트에 `10만` 개가 쌓인다.

앞의 JPA 설정, 적용, 핵심 글에서 본 대로 스냅샷까지 같이 만들어지니 메모리가 두 배로 든다.

<br/>

`OutOfMemoryError` 가 나는 대량 배치의 흔한 원인이 이것이다.
