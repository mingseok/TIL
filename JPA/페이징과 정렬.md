## 페이징과 정렬

`org.springframework.data.domain.Sort` : 정렬 기능

`org.springframework.data.domain.Pageable` : 페이징 기능 (내부에 Sort 포함)


<br/>

## 특별한 반환 타입 3가지

- `org.springframework.data.domain.Page` : 추가 `count` 쿼리 결과를 포함하는 페이징

- `org.springframework.data.domain.Slice` : 추가 `count` 쿼리 없이 다음 페이지만 확인 가능 (limit + 1조회)

- `List` (자바 컬렉션): 추가 count 쿼리 없이 결과만 반환

<br/><br/>


## 페이징과 정렬 문법

```java
Page<Member> findByUsername(String name, Pageable pageable); //count 쿼리 사용

Slice<Member> findByUsername(String name, Pageable pageable); //count 쿼리 사용 안함

List<Member> findByUsername(String name, Pageable pageable); //count 쿼리 사용 안함

List<Member> findByUsername(String name, Sort sort);
```

<br/>

### Page 사용 예제 정의 코드

- 검색 조건: 나이가 10살

- 정렬 조건: 이름으로 내림차순

- 페이징 조건: 첫 번째 페이지, 페이지당 보여줄 데이터는 3건

```java
public interface MemberRepository extends Repository<Member, Long> {
    Page<Member> findByAge(int age, Pageable pageable);
}
```

<br/><br/>

## 궁금증!

```java
Page 와 Slice 중 무엇을 써야 할까?
```

`전체 개수를 세는가` 가 갈림길이다.

```java
Page<Member>  - 전체 개수를 센다. COUNT 쿼리가 한 번 더 나간다
Slice<Member> - 안 센다. 대신 다음 페이지가 있는지만 알려준다
List<Member>  - 아무것도 안 센다. 그냥 목록
```

<br/>

```sql
-- Page
SELECT * FROM member ORDER BY id LIMIT 10 OFFSET 0;
SELECT COUNT(*) FROM member;                          -- 이게 더 나간다

-- Slice
SELECT * FROM member ORDER BY id LIMIT 11 OFFSET 0;   -- 11개를 가져와서 다음 페이지 유무 판단
```

<br/>

`Slice` 는 `limit + 1` 개를 가져온다. `11` 개가 나오면 다음 페이지가 있는 것이다.

<br/>

## COUNT 가 비싼 이유

앞의 DB 인덱스 글에서 본 실행 계획으로 설명이 된다.

```sql
SELECT COUNT(*) FROM member WHERE deleted = false;
`--SCAN member
```

<br/>

조건에 맞는 행을 전부 세야 하니 인덱스를 타도 그 범위를 다 훑는다.

`1000만` 건이면 그것만으로 수 초가 걸린다.

<br/>

그래서 무한 스크롤에는 `Slice` 를 쓴다.

전체가 몇 개인지 안 보여주니 셀 이유가 없다.

<br/>

## OFFSET 도 뒤로 갈수록 느려진다

이게 잘 안 알려진 함정이다.

```sql
SELECT * FROM member ORDER BY id LIMIT 10 OFFSET 1000000;
```

<br/>

`100만` 개를 읽고 버린 다음 `10` 개를 준다.

`OFFSET` 은 건너뛰는 것이 아니라 `읽고 버리는` 것이기 때문이다.

<br/>

그래서 페이지 번호가 커질수록 느려진다.

`1` 페이지는 빠른데 `10만` 페이지는 몇 초가 걸린다.

<br/>

## 커서 방식으로 바꾸면 해결된다

```sql
-- OFFSET 방식
SELECT * FROM member ORDER BY id LIMIT 10 OFFSET 1000000;

-- 커서 방식
SELECT * FROM member WHERE id > 1000000 ORDER BY id LIMIT 10;
```

<br/>

앞의 DB 인덱스 글에서 본 대로, 범위 조건은 인덱스를 탄다.

```sql
`--SEARCH member USING INDEX (id>?)
```

<br/>

바로 그 지점으로 찾아가서 `10` 개만 읽는다. 몇 번째 페이지든 속도가 같다.

<br/>

대신 `5 페이지로 바로 가기` 가 안 된다. 앞 페이지의 마지막 값을 알아야 하기 때문이다.

```java
페이지 번호가 필요하다 (게시판)   -> OFFSET 방식
무한 스크롤이다 (피드, 타임라인)  -> 커서 방식
```

<br/>

## fetch join 과 페이징을 같이 쓰면 안 된다

컬렉션을 `fetch join` 하면서 페이징하면 이런 경고가 뜬다.

```java
HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory
```

<br/>

`메모리에서 처리했다` 는 뜻이다.

<br/>

이유는 앞의 엔티티 조회 DTO 조회 글에서 본 곱집합 문제다.

```java
주문 1건에 주문항목 3개
-> 조인하면 3 행이 된다
-> LIMIT 10 을 걸면 주문 3~4 건만 나온다
```

<br/>

행 수와 엔티티 수가 안 맞으니 DB에서 자를 수가 없다.

그래서 하이버네이트가 전부 읽어와서 메모리에서 자른다.

<br/>

`100만` 건이면 `100만` 건을 다 읽는다. `OutOfMemoryError` 가 나는 흔한 원인이다.

<br/>

해결은 앞의 엔티티 조회 DTO 조회 글에서 본 `2번` 이다.

```java
// ToOne 은 fetch join 해도 된다 (행이 안 늘어난다)
SELECT o FROM Order o JOIN FETCH o.member

// 컬렉션은 batch size 로 푼다
spring.jpa.properties.hibernate.default_batch_fetch_size=100
```

## Sort 를 파라미터로 받을 때 조심할 것

```java
Page<Member> findAll(Pageable pageable);
```

```java
GET /members?page=0&size=10&sort=name,desc
```

<br/>

정렬 컬럼을 클라이언트가 정할 수 있다.

앞의 MyBatis 설명, 설정 방법 글에서 본 `${}` 문제와 비슷한 성질이다.

<br/>

인덱스가 없는 컬럼으로 정렬하면 앞의 DB 인덱스 글에서 본 대로 임시 정렬이 일어난다.

```sql
|--SCAN member
`--USE TEMP B-TREE FOR ORDER BY
```

<br/>

악의적으로 무거운 정렬을 계속 요청하면 서버가 느려진다.

<br/>

그래서 허용할 컬럼을 정해두는 편이 안전하다.

```java
private static final Set<String> ALLOWED = Set.of("id", "name", "createdAt");
```
