## 서브 쿼리

쿼리 안에 쿼리를 넣는다는 뜻

쿼리dsl에서는 `com.querydsl.jpa.JPAExpressions` 사용 한다

<br/>

## JPA JPQL 서브쿼리의 한계점

`from` 절의 서브쿼리(인라인 뷰)는 지원하지 않는다

당연히 `Querydsl`도 지원하지 않는다

<br/><br/>

## ex) 나이가 가장 많은 회원 조회

```java
@Test
public void subQuery() {
    QMember memberSub = new QMember("memberSub");

    List<Member> result = queryFactory
            .selectFrom(member)
            .where(member.age.eq( // 1. 맴버의 나이가 같은데(eq()) 뭐랑 같나?
                    JPAExpressions // 서브 쿼리
                            .select(memberSub.age.max()) // 2. 맴버의 나이가 가장 큰사람
                            .from(memberSub)
            )) // 3. 결과적으로 where(member.age.eq(40)) 되는 것이다
            .fetch();
}
```

<br/><br/>

## ex) 나이가 평균 이상인 회원

`goe` 문법 사용

```java
@Test
public void subQuery() {
    QMember memberSub = new QMember("memberSub");

    List<Member> result = queryFactory
            .selectFrom(member)
            .where(member.age.goe( // goe --> '>='
                    JPAExpressions
                            .select(memberSub.age.avg()) // 평균
                            .from(memberSub)
            ))
            .fetch();
}
```

<br/><br/>

## in절 사용하기

```java
@Test
public void subQuery() {
    QMember memberSub = new QMember("memberSub");

    List<Member> result = queryFactory
            .selectFrom(member)
            .where(member.age.in(
                    JPAExpressions
                            .select(memberSub.age)
                            .from(memberSub)
                            .where(memberSub.age.gt(10)) // 10살 이상인 사람들 -> 20살, 40살 등등
            ))
            .fetch();
}
```

## 궁금증!

```java
JPA 서브쿼리에 제약이 있다는 게 무슨 뜻인가
```

`FROM` 절에 못 쓴다. 이것을 인라인 뷰라고 한다.

```sql
-- SQL 에서는 된다
SELECT * FROM (SELECT ... FROM member) sub WHERE ...
```

```java
-- JPQL 과 QueryDSL 에서는 안 된다
```

<br/>

이유는 앞의 객체지향 쿼리 언어(JPQL) 글에서 본 대로 JPQL이 엔티티를 대상으로 하기 때문이다.

`FROM` 에는 엔티티가 와야 하는데, 서브쿼리 결과는 엔티티가 아니다.

<br/>

`SELECT` 절 서브쿼리도 원래는 표준이 아니었다.

하이버네이트가 지원해서 쓸 수 있게 된 것이다.

```java
WHERE 절 - 표준. 쓸 수 있다
SELECT 절 - 하이버네이트가 지원한다
FROM 절   - 안 된다
```

<br/>

## FROM 절 서브쿼리를 푸는 방법

```java
1. 조인으로 바꿀 수 있으면 바꾼다
2. 쿼리를 두 번 나눠서 실행한다
3. 네이티브 SQL 을 쓴다
```

<br/>

`1번` 이 가능한 경우가 생각보다 많다.

`FROM` 절 서브쿼리를 쓰는 이유가 대개 `한 번에 다 하려다 보니` 인 경우가 많기 때문이다.

<br/>

앞의 엔티티 조회 DTO 조회 글에서 본 `권장 순서` 의 마지막이 `4. 네이티브 SQL` 이었다.

여기가 그 자리다.

<br/>

## JPAExpressions 로 서브쿼리를 만든다

```java
import static com.querydsl.jpa.JPAExpressions.select;

QMember sub = new QMember("sub");

queryFactory.selectFrom(member)
        .where(member.age.eq(
                select(sub.age.max()).from(sub)
        ))
        .fetch();
```

<br/>

앞의 조인 글에서 본 대로 별칭이 겹치면 안 되니 `sub` 를 새로 만든다.

정적 임포트한 `member` 를 안팎에서 같이 쓰면 같은 별칭이 되어 결과가 틀린다.

<br/>

## 서브쿼리가 성능에 미치는 영향

앞의 JPQL - 경로 표현식 글에서 본 `SIZE()` 가 좋은 예다.

```java
SELECT SIZE(t.members) FROM Team t
```

```sql
SELECT (SELECT COUNT(*) FROM member WHERE team_id = t.id) FROM team t
```

<br/>

팀마다 서브쿼리가 한 번씩 실행된다. 팀이 `100` 개면 `100` 번이다.

이것을 `상관 서브쿼리` 라고 한다. 바깥 행마다 다시 실행되기 때문이다.

<br/>

`GROUP BY` 로 바꾸면 한 번에 끝난다.

```java
queryFactory.select(team.name, member.count())
        .from(team)
        .leftJoin(team.members, member)
        .groupBy(team.id)
        .fetch();
```

<br/>

앞의 DB 인덱스 글에서 본 관점으로 보면,

`같은 데이터를 몇 번 훑는가` 가 `100` 번에서 `1` 번으로 준 것이다.

<br/>

## EXISTS 가 IN 보다 나을 때가 있다

```java
// IN
.where(member.id.in(select(order.member.id).from(order)))

// EXISTS
.where(select(order).from(order).where(order.member.eq(member)).exists())
```

<br/>

`IN` 은 서브쿼리 결과를 전부 만들어놓고 비교한다.

`EXISTS` 는 하나라도 찾으면 바로 멈춘다.

<br/>

주문이 `1000만` 건이면 `IN` 은 그 목록을 다 만들어야 한다.

`EXISTS` 는 첫 번째를 찾는 순간 끝난다.

<br/>

요즘 옵티마이저는 이걸 알아서 바꿔주기도 하는데, 항상 그런 것은 아니다.

앞의 database system 동작하는 방식 글에서 본 `EXPLAIN` 으로 확인해보는 것이 확실하다.

<br/>

## 서브쿼리 대신 애플리케이션에서 나누는 것도 방법이다

```java
List<Long> memberIds = queryFactory.select(order.member.id).distinct().from(order).fetch();
List<Member> members = queryFactory.selectFrom(member).where(member.id.in(memberIds)).fetch();
```

<br/>

쿼리가 두 번 나가지만 각각은 단순해진다.

<br/>

앞의 엔티티 조회 DTO 조회 글에서 본 `batch size` 가 만들어내는 형태와 같다.

`IN` 절 하나로 묶으면 왕복이 두 번이라 대개 감당할 만하다.

<br/>

다만 앞의 @Query, 값, DTO 조회하기 글에서 본 대로 `IN` 절 개수 제한이 있다.

`memberIds` 가 수만 개가 되면 이 방법도 못 쓴다.
