## 영속성 컨텍스트

‘엔티티를 영구 저장하는 환경’이라는 뜻.

지금까지 사용하였던, 이 코드는 사실 `DB`에 저장하는 것이 아니라

코드의 `‘entity'`를 → `‘영속성 컨텍스트'` 라는 곳에 `저장`하는 것이다.

```java
EntityManager.persist(entity);
```

엔티티 매니저를 생성을 하면, 그 안에 1 : 1 로 영속성 컨텍스트가 생성이 된다.

쉽게 설명하면, 눈에 보이지 않는 공간이 생긴다고 생각하기.

## 엔티티의 생명주기

- 비영속 : 영속성 컨텍스트와 전혀 관계가 없는 새로운 상태

- 영속 : 영속성 컨텍스트 관리되는 상태
- 준영속 : 영속성 컨텍스트에 저장되었다가 분리된 상태
- 삭제 : 삭제된 상태

<br/><br/>

## 비영속

`엔티티 매니저`에 아무것도 넣지 않는 상태. 

`member` 객체를 생성만 한 상태를 의미한다.

밑에 코드처럼 `세팅`만 한 상태를 말한다. (이런 것이 `jpa`와 관계가 없으므로 `비영속`이다)

```java
Member member = new Member();
member.setId(100L);
member.setName("HelloJPA");
```

## 영속

`em.persist(member)` 코드 처럼 `member`를 넣으면 `‘영속 상태’` 가 되는 것이다.

`‘영속 상태’`가 된다고 해서 바로 쿼리가 날라가는 것이 아니다.

- 그렇다면 언제? → `tx.commit()` 트랜잭션이 커밋하는 시점에 날라가게 되는 것이다.

```java
// 비영속
Member member = new Member();
member.setId(100L);
member.setName("HelloJPA");

EntityManagerFactory emf = Persistence.createEntityManagerFactory();
EntityManager em = emf.createEntityManager();

EntityTransaction tx = em.getTransaction(); // 트랜잭션 생성
tx.begin(); // 트랜잭션 시작

// 객체를 저장한 상태 (=영속)
em.persist(member);
```

## (영속성 컨텍스트) 엔티티 조회, 1차 캐시

map 형태로 저장이 된다. 

key는 `PK`인 → `member1` 이 된다. 벨류는 `persist()` 넣는 객체가 된다.

```java
//엔티티를 생성한 상태(비영속)
Member member = new Member();
member.setId("member1");
member.setName("회원1");

//엔티티를 영속
em.persist(member);
```

<br/>

![이미지](/programming/img/입문294.PNG)


<br/><br/>

## 이렇게 하여 장점은? → 1차 캐시에서 조회

`em.find`를 하게 되면, `DB`에 가서 찾는 것이 아니라, 먼저 `‘영속 컨텍스트'`에 가서 찾는 것이다.

```java
Member member = new Member();
member.setId("member1");
member.setUsername("회원1");

// 1차 캐시에 저장됨
em.persist(member);

// 1차 캐시에서 조회
Member findMember = em.find(Member.class, "member1");
```

<br/><br/>

## 만약, 영속 컨텍스트에 해당 1차 캐시가 없다면?

현재 `“member2”`가 없는 것이다. → 그림으로 설명

```java
Member findMember2 = em.find(Member.class, "member2");
```

<br/>

![이미지](/programming/img/입문295.PNG)

1. 처음 `‘1차 캐시’`라는 map에 “member2” 찾으려고 하는데 없다.

2. 그렇다면, `DB`로 가서 조회를 해온다.
3. 그리고 `DB`에서 조회 해온것을 `‘1차 캐시’`에 저장한다.
4. 그 다음, `member2`를 반환하게 되는 것이다.

```
이후에 'member2'를 다시 조회하게 되면 영속 컨텍스트에 있는 
'1차 캐시'에 있는걸 반환하게 되는 것이다.
```

<br/><br/>

## (영속성 컨텍스트) 영속 엔티티의 동일성 보장

예를 들어, 자바 컬렉션에서 똑같은 것을 가져와서 비교하면 똑같다!

```java
Member a = em.find(Member.class, "member1");
Member b = em.find(Member.class, "member1");

System.out.println(a == b); // 동일성 비교 true
```

<br/><br/>

## JPA에서도 보장을 해준다.

실행 시켜보면 true가 나온다.

즉, == 비교를 보장해준다는 것이다.

```java
Member findMember1 = em.find(Member.class, 101L);
Member findMember2 = em.find(Member.class, 101L);

System.out.println("result = " + (findMember1 == findMember2)); // true
```

### `em.persist(memberA);` 설명

1. `memberA`를 `persist()` 통해 넣으면, `memberA`가 `‘1차 캐시’`에 들어간다.

2. 그리고 동시에 JPA가 memberA의 엔티티를 분석해서 쿼리를 생성한다.
3. 그리하여 쿼리를 `‘쓰기 지연 SQL 저장소’` 라는 곳에 쌓아둔다.

<br/>

### `em.persist(memberB);` 설명

1. memberB도 1차 캐시에 넣는다.
2. 그리고 동시에 쿼리를 생성하여 `‘쓰기 지연 SQL 저장소’`에 차곡차곡 쌓아둔다.

<br/><br/>

## 그렇다면 언제 DB로 가게 되는 것일까?

commit() 하는 시점에 되는 보내지게 되는 것이다.

```
날라간다(=보내지다 등등) == ‘flush’(=플러시) 라고 부른다.
```

<br/>

![이미지](/programming/img/입문298.PNG)

1. commit() 명령한다.

2. 쌓아 뒀던 쿼리들을 모두 flush 한다.
3. 마지막 실제 데이터 베이스가 커밋 되는 것이다.

## 궁금증!

```java
영속성 컨텍스트 안이 실제로 어떻게 생겼을까?
```

핵심은 `Map` 두 개라고 보면 크게 틀리지 않는다.

```java
Map<EntityKey, Object> 1차 캐시      // 식별자 -> 엔티티
Map<EntityKey, Object[]> 스냅샷      // 식별자 -> 조회 시점의 필드 값 복사본
List<SQL> 쓰기 지연 저장소            // 아직 안 보낸 SQL
```

<br/>

앞의 JPA 설정, 적용, 핵심 글에서 본 세 가지 이득이 각각 이 셋에서 나온다.

```java
1차 캐시   -> 같은 것을 두 번 조회해도 쿼리가 한 번
스냅샷     -> 커밋할 때 비교해서 변경 감지
쓰기 지연  -> 모아뒀다 한 번에 보낸다
```

<br/>

## 동일성이 보장되는 이유

```java
Member a = em.find(Member.class, 1L);
Member b = em.find(Member.class, 1L);
a == b;         // true
```

<br/>

두 번째 `find` 는 `Map` 에서 꺼낸 것이라 같은 객체다.

<br/>

이게 없으면 앞의 equals, hashCode 글에서 본 문제가 매번 생긴다.

같은 회원인데 `==` 로 비교하면 `false` 가 나오니, `equals` 를 반드시 재정의해야 한다.

<br/>

영속성 컨텍스트 덕분에 `같은 트랜잭션 안에서는 == 로 비교해도 된다` 는 보장이 생기는 것이다.

<br/>

## 스냅샷이 두 배의 메모리를 쓴다

앞의 트랜잭션 옵션 글에서 본 `readOnly = true` 의 이유가 이것이다.

```java
1000 건을 조회하면
  -> 엔티티 1000 개
  -> 스냅샷 1000 개
  -> 총 2000 개가 메모리에 있다
```

<br/>

조회만 할 거라면 스냅샷이 필요 없다. `readOnly` 를 붙이면 안 만든다.

<br/>

앞의 플러시 글에서 본 대량 처리에서 `clear()` 를 부르는 이유도 같다.

`10만` 건을 넣으면 엔티티와 스냅샷이 `20만` 개가 되어 메모리가 터진다.

<br/>

## 준영속 상태가 되는 세 가지 경우

```java
em.detach(entity)   - 그 엔티티 하나만 관리에서 뺀다
em.clear()          - 전부 뺀다
em.close()          - 영속성 컨텍스트를 닫는다
```

<br/>

실무에서 제일 자주 만나는 것은 네 번째다. `트랜잭션이 끝날 때` 다.

<br/>

앞의 JPA 설정, 적용, 핵심 글에서 본 `LazyInitializationException` 이 여기서 나온다.

```java
@Transactional
public Order find(Long id) {
    return orderRepository.findById(id).orElseThrow();
}   // 여기서 트랜잭션이 끝나고 준영속이 된다

// 컨트롤러에서
order.getMember().getName();      // 예외
```

<br/>

## 준영속이면 변경 감지도 안 된다

```java
Member member = memberService.find(1L);    // 트랜잭션 밖으로 나왔다
member.changeName("바뀐이름");              // 아무 일도 안 일어난다
```

<br/>

예외도 안 나고 조용히 무시된다. 이게 더 찾기 어렵다.

<br/>

앞의 스프링 데이터 JPA 글에서 본 `merge` 가 이걸 다시 붙이는 방법인데,

```java
Member merged = em.merge(member);
```

<br/>

`merge` 는 넘긴 객체의 모든 필드로 덮어쓴다.

안 채운 필드가 `null` 로 들어가는 사고가 나기 쉬워서, 조회해서 바꾸는 방식이 안전하다.

<br/>

## 그래서 트랜잭션 경계가 중요하다

앞의 서비스 계층 글에서 본 `트랜잭션 경계는 서비스` 라는 원칙이

JPA에서는 `영속성 컨텍스트가 사는 범위` 이기도 하다.

```java
트랜잭션 시작 -> 영속성 컨텍스트 생성
  이 안에서만 1차 캐시, 변경 감지, 지연 로딩이 동작한다
트랜잭션 끝   -> 플러시 + 영속성 컨텍스트 종료
```

<br/>

그래서 앞의 JPA회원조회 글에서 본 대로,

트랜잭션 안에서 DTO로 바꿔서 나가는 것이 정석이 된다.
