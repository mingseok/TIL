## ON절

ex) 연관관계 없는 엔티티 외부 조인 → 회원의 이름이 팀 이름과 같은 대상 외부 조인

```java
@Test
public void join_on_relation() {
    em.persist(new Member("teamA"));
    em.persist(new Member("teamB"));
    em.persist(new Member("teamC"));

    List<Tuple> result = queryFactory
            .select(member, team)
            .from(member)
            .leftJoin(team).on(member.username.eq(team.name))
            .fetch();

    for (Tuple tuple : result) {
        System.out.println("tuple = " + tuple);
    }
}
```

<br/>

### 주의! 문법을 잘 봐야 한다.

`leftJoin()` 부분에 일반 조인과 다르게 엔티티 하나만 들어간다.

- 일반조인: `leftJoin(member.team, team)`

- `on`조인: `from(member).leftJoin(team).on(xxx)`

## 페치 조인

SQL조인을 활용해서 연관된 엔티티를 SQL 한번에 조회하는 기능이다. 

주로 성능 최적화에 사용하는 방법이다.

즉시로딩으로 `Member`, `Team` SQL 쿼리 조인으로 한번에 조회

```java
@Test
public void fetchJoinUse() throws Exception {
    em.flush();
    em.clear();
    Member findMember = queryFactory
            .selectFrom(member)
            .join(member.team, team).fetchJoin()
            .where(member.username.eq("member1"))
            .fetchOne();
}
```

## 궁금증!

```java
QueryDSL 의 조인이 JPQL 과 어떻게 대응되는가
```

일대일로 대응된다. 앞의 JPQL vs Querydsl 글에서 본 대로 결국 JPQL을 만들기 때문이다.

```java
// QueryDSL
queryFactory.selectFrom(member)
        .join(member.team, team)
        .where(team.name.eq("A팀"))
        .fetch();

// 만들어지는 JPQL
SELECT m FROM Member m INNER JOIN m.team t WHERE t.name = 'A팀'
```

<br/>

```java
join / innerJoin  - INNER JOIN
leftJoin          - LEFT OUTER JOIN
rightJoin         - RIGHT OUTER JOIN
join(엔티티)       - 세타 조인 (연관관계 없이)
```

<br/>

## fetchJoin 은 메서드 하나로 붙인다

```java
queryFactory.selectFrom(order)
        .join(order.member, member).fetchJoin()
        .fetch();
```

<br/>

앞의 JPQL - 페치 조인 글에서 본 그 동작이다.

`SELECT` 에 연관 엔티티의 컬럼까지 들어간다.

<br/>

그리고 같은 제약이 그대로 따라온다.

```java
컬렉션 fetchJoin 은 하나만 할 수 있다     -> MultipleBagFetchException
컬렉션 fetchJoin + 페이징은 메모리에서 처리된다
```

<br/>

앞의 페이징 API, 조인 글에서 본 것과 같다.

문법이 자바일 뿐 JPA의 제약을 벗어나지는 않는다.

<br/>

## on 절을 쓸 수 있다

```java
queryFactory.select(member, team)
        .from(member)
        .leftJoin(member.team, team).on(team.name.eq("A팀"))
        .fetch();
```

<br/>

앞의 페이징 API, 조인 글에서 본 `ON 과 WHERE 의 차이` 가 여기서도 중요하다.

```java
leftJoin ... on(조건)     -- 조인할 때 거른다. 왼쪽은 전부 나온다
leftJoin ... where(조건)  -- 조인 후 거른다. null 인 행이 탈락한다
```

<br/>

`LEFT JOIN` 을 쓰고 `WHERE` 로 오른쪽 조건을 걸면 사실상 `INNER JOIN` 이 된다.

`LEFT JOIN` 을 썼는데 결과가 예상보다 적으면 이걸 먼저 본다.

<br/>

## 연관관계 없는 조인

```java
queryFactory.select(member, team)
        .from(member)
        .leftJoin(team).on(member.name.eq(team.name))
        .fetch();
```

<br/>

`member.team` 이 아니라 `team` 을 바로 넘긴다.

매핑이 없어도 조건으로 붙일 수 있다.

<br/>

앞의 페이징 API, 조인 글에서 본 세타 조인인데,

`leftJoin` 을 쓸 수 있다는 것이 JPQL의 세타 조인보다 나은 점이다.

<br/>

JPQL의 `FROM A, B` 방식은 `INNER JOIN` 만 된다.

<br/>

## 같은 엔티티를 두 번 조인할 때

```java
QMember sub = new QMember("sub");

queryFactory.select(member, sub)
        .from(member)
        .join(sub).on(member.age.gt(sub.age))
        .fetch();
```

<br/>

앞의 Querydsl 설정 글에서 본 대로 생성자에 별칭을 넘겨 새로 만든다.

정적 임포트한 `member` 를 두 번 쓰면 같은 별칭이 되어 조인이 안 된다.

<br/>

## 조인이 늘어나면 성능을 봐야 한다

앞의 상속관계 매핑 글에서 본 `JOINED` 전략처럼,

조인이 다섯 개를 넘어가면 실행 계획을 확인해볼 만하다.

<br/>

앞의 DB 인덱스 글에서 본 대로 조인 컬럼에 인덱스가 없으면 그만큼 느려진다.

```sql
CREATE INDEX idx_member_team ON member(team_id);
```

<br/>

외래 키를 걸면 대개 인덱스가 자동으로 만들어지는데, DB마다 다르다.

MySQL은 만들어주고 PostgreSQL은 안 만들어준다.

`LEFT JOIN` 이 느리면 이걸 확인해보면 된다.
