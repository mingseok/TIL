## 임베디드 타입



- 주로 기본 값 타입을 모아서 만들어서 복합 값 타입이라고도 함

    - JPA는 임베디드 타입(embedded type)이라 함

- int, String과 같은 값 타입

<br/><br/>

## 회원 엔티티는

회원 엔티티를 설명할때는 간단하게 `이름`, `근무 기간`, `집 주소` 이렇게 추상적으로 설명한다.

즉, 밑에 테이블처럼 하나하나 설명하지는 않는다.

<br/>

그렇기에, 이름, 근무 시작일, 근무 종료일, 주소 도시, 주소 번지, 주소 우편번호를 가진다.

![이미지](/programming/img/입문376.PNG)

```
'근무 시작일', '근무 종료일' 2가지는 비슷하기에 묶어서 설명할 수 있다.
'주소 도시', '주소 번지', '주소 우편번호' 3가지도 묶어서 설명할 수 있다.
```

즉, 이렇게 묶어낼 수 있는 것이 `임베디드 타입`인 것이다.

<br/><br/>

## 임베디드 타입 사용법

- `@Embeddable`: 값 타입을 정의하는 곳에 표시

- `@Embedded`: 값 타입을 사용하는 곳에 표시
- 기본 생성자 필수이다.


<br/><br/>


## 임베디드 타입의 장점

- 재사용성

- 높은 응집도
- `Period.isWork()`처럼 해당 값 타입만 사용하는 의미 있는 메소드를 만들 수 있음
- 임베디드 타입을 포함한 모든 값 타입은, 값 타입을 소유한 엔티티에 생명주기를 의존함

<br/><br/>

## 임베디드 타입과 테이블 매핑

핵심은, DB쪽 테이블은 변하는게 없고, 엔티티쪽만 매핑들을 잘해주면 되는 것이다.

## 코드 확인

`Member.class`

```java
@Entity
public class Member {

    // 생략..

    @Embedded
    private Period period;
    
    @Embedded
    private Address address;
}
```

<br/>

`Period.class`

```java
@Embeddable
public class Period {
    private LocalDateTime startDate;
    private LocalDateTime endDate;
}
```

<br/>

`Address.class`

```java
@Embeddable
public class Address {
    private String city;
    private String street;
    private String zipcode;
}
```

<br/><br/>

## 임베디드 타입과 테이블 매핑

- 임베디드 타입은 엔티티의 값일 뿐이다.

- 임베디드 타입을 사용하기 전과 후에 매핑하는 테이블은 같다.
- 객체와 테이블을 아주 세밀하게 매핑하는 것이 가능하다.

```
잘 설계한 ORM 애플리케이션은 매핑한 테이블의 수보다 클래스의 수가 더 많다.
```

## 궁금증!

```java
임베디드 타입을 쓰면 테이블은 어떻게 되는가
```

테이블은 그대로다. 컬럼이 그대로 남고 객체만 묶인다.

```java
@Entity
public class Member {
    private Long id;
    private String name;

    @Embedded
    private Period workPeriod;      // startDate, endDate

    @Embedded
    private Address homeAddress;    // city, street, zipcode
}
```

```sql
CREATE TABLE member (
    id, name,
    start_date, end_date,        -- Period 가 풀린 것
    city, street, zipcode        -- Address 가 풀린 것
);
```

<br/>

그래서 매핑을 바꿔도 DB 마이그레이션이 필요 없다.

이미 있는 테이블에 나중에 적용할 수 있는 것이다.

<br/>

## 무엇이 좋아지는가

앞의 객체지향 생활 체조 글에서 본 `원시값 포장` 과 같은 이득이다.

```java
// 묶기 전
if (member.getStartDate().isAfter(member.getEndDate())) {
    throw new IllegalArgumentException();
}

// 묶은 뒤
class Period {
    public Period(LocalDate start, LocalDate end) {
        if (start.isAfter(end)) {
            throw new IllegalArgumentException("시작일이 종료일보다 늦을 수 없습니다");
        }
        ...
    }
}
```

<br/>

`시작일이 종료일보다 앞이어야 한다` 는 규칙을 둘 자리가 생긴다.

`Period` 가 존재한다는 것 자체가 그 규칙이 지켜졌다는 뜻이 된다.

<br/>

그리고 계산도 안으로 들어온다.

```java
public long days() {
    return ChronoUnit.DAYS.between(startDate, endDate);
}
```

<br/>

앞의 객체는 객체스럽게 사용한다 글에서 본 `계산을 안으로 옮긴다` 가 여기서도 적용된다.

<br/>

## 같은 타입을 두 번 쓰면 컬럼이 겹친다

```java
@Embedded
private Address homeAddress;

@Embedded
private Address companyAddress;      // city 컬럼이 두 번 필요하다
```

<br/>

```java
Repeated column in mapping for entity: Member column: city
```

<br/>

`@AttributeOverride` 로 이름을 바꿔줘야 한다.

```java
@Embedded
@AttributeOverrides({
    @AttributeOverride(name = "city", column = @Column(name = "company_city")),
    @AttributeOverride(name = "street", column = @Column(name = "company_street"))
})
private Address companyAddress;
```

<br/>

길어서 불편한데, 이런 상황이 자주 생긴다면 그건 별도 엔티티로 뺄 신호이기도 하다.

<br/>

## 임베디드 타입은 반드시 불변이어야 한다

앞의 값 타입과 불변 객체 글에서 다루는 그 이유다.

```java
Address address = new Address("서울", "테헤란로", "12345");

member1.setHomeAddress(address);
member2.setHomeAddress(address);     // 같은 객체를 공유했다

member1.getHomeAddress().setCity("부산");
```

<br/>

`member2` 의 주소까지 부산이 된다.

<br/>

앞의 영속성 컨텍스트 글에서 본 변경 감지가 두 회원 모두에 대해 동작해서,

`UPDATE` 가 두 번 나간다.

<br/>

그래서 `setter` 를 아예 안 만든다.

```java
@Embeddable
public class Address {
    private String city;
    private String street;
    private String zipcode;

    protected Address() { }          // JPA 용

    public Address(String city, String street, String zipcode) {
        this.city = city;
        this.street = street;
        this.zipcode = zipcode;
    }
    // setter 없음
}
```

<br/>

바꿔야 하면 새로 만들어서 통째로 갈아끼운다.

```java
member.changeAddress(new Address("부산", "해운대로", "54321"));
```

<br/>

앞의 불변 객체 글에서 본 `값을 바꿀 때마다 새 객체를 만든다` 가 이것이다.

<br/>

## equals 와 hashCode 를 반드시 재정의해야 한다

값 타입은 `주소가 같은가` 가 아니라 `내용이 같은가` 로 비교되어야 한다.

```java
new Address("서울", "테헤란로", "12345")
        .equals(new Address("서울", "테헤란로", "12345"));    // true 여야 한다
```

<br/>

앞의 equals, hashCode 글에서 본 대로 둘 다 재정의해야 한다.

하나만 하면 `Map` 이나 `Set` 에서 안 걸린다.

<br/>

그리고 필드가 전부 `final` 이거나 안 바뀌니, 앞의 equals, hashCode 글에서 본

`넣고 나서 필드를 바꾸면 못 찾는` 문제도 안 생긴다.

불변이 여기서도 이득이 되는 것이다.

<br/>

## @Embeddable 에도 기본 생성자가 필요하다

앞의 엔티티 매핑 글에서 본 것과 같은 이유다.

JPA가 리플렉션으로 만들어야 하기 때문이다.

```java
protected Address() { }
```

<br/>

다만 `@Embeddable` 은 프록시 대상이 아니라서 `private` 으로 해도 된다.

앞의 프록시 기초 글에서 본 대로 상속이 필요한 것은 `@Entity` 쪽이다.
