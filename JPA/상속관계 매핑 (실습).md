## 여기서 중요한 포인트

`Item.class` 를 상속 받은 `Album`, `Movie`, `Book`은 `BaseEntity.class` 를 상속 받을 필요가 없다.

왜? → `Item.class`는 이미 `extends BaseEntity`를 상속하고 있기에 어차피

`Album`, `Movie`, `Book` 들도 `BaseEntity`를 상속받게 되는 것이다.

## 궁금증!

```java
전략을 바꿔가며 실행해보면 SQL 이 어떻게 달라질까
```

같은 엔티티에 전략만 바꿔서 로그를 보면 차이가 한눈에 들어온다.

<br/>

### JOINED

```sql
-- 저장
INSERT INTO item (id, name, price, dtype) VALUES (?, ?, ?, 'B');
INSERT INTO book (item_id, author, isbn) VALUES (?, ?, ?);

-- 조회
SELECT i.id, i.name, i.price, b.author, b.isbn
FROM item i
LEFT JOIN book b ON i.id = b.item_id
WHERE i.id = ?
```

<br/>

`INSERT` 가 두 번, 조회에 조인이 붙는다.

<br/>

부모 타입으로 조회하면 자식 테이블을 전부 조인한다.

```sql
SELECT ... FROM item i
LEFT JOIN book b ON ...
LEFT JOIN movie m ON ...
LEFT JOIN album a ON ...
```

<br/>

자식이 열 개면 조인이 열 개 붙는다. 여기서 성능 문제가 시작된다.

<br/>

### SINGLE_TABLE

```sql
-- 저장
INSERT INTO item (id, name, price, dtype, author, isbn, director, actor)
VALUES (?, ?, ?, 'B', ?, ?, null, null);

-- 조회
SELECT * FROM item WHERE id = ?
```

<br/>

조인이 없다. 저장도 한 번이다.

<br/>

대신 `director` 와 `actor` 가 `null` 로 들어간다.

앞의 상속관계 매핑 글에서 본 `NOT NULL 을 못 건다` 는 문제가 이 로그에 그대로 보인다.

<br/>

### TABLE_PER_CLASS

```sql
-- 부모 타입으로 조회하면
SELECT * FROM (
    SELECT id, name, price, author, null as director FROM book
    UNION ALL
    SELECT id, name, price, null as author, director FROM movie
) WHERE id = ?
```

<br/>

`UNION ALL` 이 나온다. 자식이 늘어날수록 이 쿼리가 길어진다.

<br/>

## 실습에서 확인해볼 만한 것

### dtype 컬럼이 어떻게 채워지는가

```java
@DiscriminatorValue("B")
public class Book extends Item { }
```

<br/>

안 적으면 클래스 이름이 그대로 들어간다.

```sql
dtype = 'Book'
```

<br/>

짧게 하려고 `"B"` 를 적는 경우가 많은데, 나중에 DB를 직접 볼 때 `B` 가 뭔지 헷갈린다.

클래스 이름 그대로 두는 편이 읽기 낫다는 의견도 많다.

<br/>

### 부모가 abstract 여야 하는가

```java
@Entity
public abstract class Item { }
```

<br/>

`abstract` 가 아니어도 동작한다. 다만 `Item` 자체를 만들 수 있게 된다.

```java
em.persist(new Item("이름", 1000));      // 책도 영화도 아닌 것이 저장된다
```

<br/>

`dtype` 이 `Item` 인 행이 생기는데, 그게 무엇인지 아무도 모른다.

<br/>

앞의 생성자를 왜 만들어야 하나요 글에서 본 `완성되지 않은 객체가 존재한다` 와 같은 문제다.

`abstract` 로 두면 그 상태 자체가 표현되지 않는다.

<br/>

## 실습 뒤에 남는 판단

앞의 상속관계 매핑 글에서 본 기준을 실습 결과와 맞춰보면 이렇게 정리된다.

```java
자식이 2~3 개, 자식 컬럼도 몇 개 안 된다  -> SINGLE_TABLE 이 낫다
자식마다 컬럼이 많고 NOT NULL 이 필요하다  -> JOINED
자식이 열 개가 넘어간다                   -> 상속 매핑 자체를 다시 본다
```

<br/>

마지막이 중요하다. 자식이 너무 많으면 상속으로 푸는 것이 맞는지부터 의심해볼 만하다.

<br/>

앞의 추상클래스와 인터페이스의 용도를 나눈 이유는 무엇인가 글에서 본 대로,

`is-a` 가 정말 성립하는지가 기준이다.

`책` 과 `영화` 가 정말 `상품` 의 한 종류인지, 아니면 그냥 `카테고리` 하나로 충분한지 다시 보는 것이다.

```java
상속 매핑     - 자식마다 컬럼이 다를 때
category 컬럼 - 컬럼은 같고 분류만 다를 때
```
