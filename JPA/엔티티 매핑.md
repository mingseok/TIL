## 엔티티 매핑

- 객체와 테이블 매핑: `@Entity`, `@Table`

- 필드와 컬럼 매핑: `@Column`
- 기본 키 매핑: `@Id`
- 연관관계 매핑: `@ManyToOne`, `@JoinColumn`

<br/><br/>

## 객체와 테이블 매핑

제일 먼저 클래스랑 테이블을 매핑을 해야 한다.

<br/>

## @Entity

- `@Entity`가 붙은 클래스는 JPA가 관리 한다.

    - JPA가 관리하는 것을 `‘엔티티’`라고 부른다.

그리하여 `JPA`를 사용해서 `테이블`과 매핑할 `클래스`는 `@Entity` 필수이다.

<br/>

### 주의점

- 기본 생성자 필수이다.

- final 클래스, enum, interface, inner 클래스들은 사용하면 안된다.
- 저장할 필드에 final을 사용하면 안된다.


<br/>

### `@Entity` 이름을 지정할 수 있다.

디폴트값은 현재 클래스이다. → 단지, JPA가 내부적으로 구분하는 이름이다.

```java
@Entity(name = "Member1")
public class Member {

// ... 생략
```

<br/>

### 사용할 일이 있을 경우는?

같은 패키지에 같은 이름의 클래스가 있을 경우 사용하면 되는 것이다.

<br/><br/>

## @Table

`@Table`은 엔티티와 매핑할 테이블 지정한다.

이렇게 작성시. 데이터 베이스 테이블의 `“MBR”` 이라는 테이블과 매핑을 하게 되는 것이다.

```java
@Entity
@Table(name = "MBR")
public class Member {
// ... 생략
```

## 궁금증!

```java
@Entity 를 붙이면 무엇이 강제되는가
```

세 가지 조건이 붙는다. 하나라도 어기면 애플리케이션이 안 뜬다.

```java
1. 기본 생성자가 있어야 한다 (public 또는 protected)
2. final 클래스면 안 된다
3. 필드가 final 이면 안 된다
```

<br/>

전부 앞의 프록시 기초 글에서 본 이유 때문이다.

<br/>

`@Entity` 가 붙으면 하이버네이트가 그 클래스를 상속한 프록시를 만들 수 있어야 한다.

```java
class Member$HibernateProxy$abc123 extends Member {
    Member$HibernateProxy$abc123() {
        super();          // 기본 생성자를 부른다
    }
}
```

<br/>

`final` 클래스면 상속이 안 되고, 기본 생성자가 없으면 `super()` 를 못 부른다.

<br/>

## 그래서 record 를 엔티티로 못 쓴다

```java
@Entity
public record Member(Long id, String name) { }      // 안 된다
```

<br/>

앞의 DTO 글에서 본 `record` 는 필드가 전부 `final` 이고 클래스도 `final` 이다.

엔티티의 세 조건을 전부 어긴다.

<br/>

`record` 는 DTO 자리에 쓰는 것이 맞다.

```java
@Entity
public class Member { ... }                        // 엔티티는 클래스

public record MemberResponse(String name) { }      // DTO 는 record
```

<br/>

## 기본 생성자를 protected 로 막는 이유

```java
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@Entity
public class Member { ... }
```

<br/>

`public` 으로 두면 아무나 빈 객체를 만들 수 있다.

```java
Member member = new Member();      // 이름도 이메일도 없는 회원
```

<br/>

앞의 생성자를 왜 만들어야 하나요 글에서 본 `완성되기 전의 객체가 존재한다` 는 문제다.

<br/>

`protected` 로 두면 하이버네이트는 쓸 수 있고 개발자는 못 쓴다.

프레임워크는 리플렉션으로 접근하니 접근 제한자를 무시할 수 있기 때문이다.

<br/>

`private` 으로 하면 프록시가 `super()` 를 못 부르니 안 된다. `protected` 가 최소선이다.

<br/>

## @Table 의 name 을 왜 지정하는가

```java
@Entity
@Table(name = "member")
public class Member { }
```

<br/>

안 적으면 클래스 이름이 테이블 이름이 된다. 대개 그걸로 충분하다.

<br/>

적어야 하는 경우가 몇 가지 있다.

```java
1. 예약어와 겹칠 때 - Order 는 SQL 의 ORDER BY 와 겹친다
2. 이미 있는 테이블 이름이 다를 때 - 레거시 DB
3. 명명 규칙이 다를 때 - 클래스는 카멜, 테이블은 스네이크
```

<br/>

`1번` 이 실무에서 자주 걸린다.

```java
@Entity
public class Order { }        // CREATE TABLE order -> 문법 오류
```

```java
@Entity
@Table(name = "orders")
public class Order { }
```

<br/>

`user` 도 PostgreSQL에서 예약어라 자주 걸린다.

<br/>

## 이름 변환 규칙

스프링 부트는 기본으로 카멜을 스네이크로 바꿔준다.

```java
private String memberName;    ->    member_name
class OrderItem               ->    order_item
```

<br/>

이것을 `물리 명명 전략` 이라고 한다.

앞의 MyBatis 적용 글에서 본 `map-underscore-to-camel-case` 와 같은 일을 하는 것이다.

<br/>

그래서 `@Column(name = "member_name")` 을 일일이 적을 필요가 없다.

적어야 할 때는 규칙에서 벗어나는 이름일 때뿐이다.

```java
@Column(name = "user_nm")     // 규칙으로는 안 나오는 이름
private String userName;
```

<br/>

## @Entity 의 name 속성

원문의 `이름을 지정할 수 있다` 부분이다.

```java
@Entity(name = "Member")
```

<br/>

이건 테이블 이름이 아니라 `JPQL 에서 쓸 이름` 이다.

```java
SELECT m FROM Member m       // 여기의 Member
```

<br/>

패키지가 다른데 클래스 이름이 같은 엔티티가 두 개 있으면 충돌한다.

그때 하나를 다른 이름으로 바꿔주는 용도다.

```java
com.example.order.Item
com.example.stock.Item        // JPQL 에서 Item 이 겹친다
```

<br/>

실무에서 이런 상황이 나오면 이름을 바꾸는 것보다 클래스 이름 자체를 다르게 짓는 편이 낫다.

앞의 클래스명, 메소드명, 변수명 규칙 글에서 본 대로,

같은 이름이 두 개라는 것은 이름이 충분히 구체적이지 않다는 신호이기도 하다.
