## 기본 키 매핑 애노테이션

```java
@Id @GeneratedValue(strategy = GenerationType.AUTO)
private Long id; // int, Integer 둘다 사용하지 말고 Long을 사용해야 한다.
```

- `@Id` : 직접 할당

- `@GeneratedValue` : 자동 생성(DB가 만들어준다는 것이다)
    - `@GeneratedValue(strategy = GenerationType.*IDENTITY*)` : 전략

        - “난 모르겠고, DB가 알아서 해줘” 하는 것이다.

        - 이, *`IDENTITY`*전략을 사용하면 변수인 `id`에 값을 넣으면 안된다.
    - `@GeneratedValue(strategy = GenerationType.*SEQUENCE*)` : 전략
        - 오라클 같은곳에서 사용한다.

<br/><br/>

## 기본 키 제약 조건(=PK)

- `null`이 아님, 유일해야함, 변하면 안된다.

- 미래까지 이 조건을 만족하는 자연키는 찾기 어렵다.

    - 예를 들어, 주민등록번호도 기본키(PK)로 적절하지 않다.

- 권장 : Long타입 + 대체키 + 키 생성전략 사용하자.

## 궁금증!

```java
IDENTITY 와 SEQUENCE 중 무엇을 써야 할까?
```

DB가 무엇이냐에 따라 선택지가 갈린다.

```java
IDENTITY - MySQL 의 AUTO_INCREMENT. DB 가 INSERT 할 때 정해준다
SEQUENCE - Oracle, PostgreSQL 의 시퀀스. 미리 번호를 받아올 수 있다
TABLE    - 번호를 관리하는 테이블을 따로 둔다. 어느 DB 에서든 되지만 느리다
AUTO     - DB 방언을 보고 알아서 고른다
UUID     - Jakarta Persistence 3.2 에 추가됐다
```

<br/>

앞의 JPA API 를 확인해보면 실제로 이 다섯 가지다.

```java
public static final GenerationType TABLE;
public static final GenerationType SEQUENCE;
public static final GenerationType IDENTITY;
public static final GenerationType UUID;
public static final GenerationType AUTO;
```

<br/>

## IDENTITY 는 쓰기 지연이 깨진다

이게 실무에서 중요한 차이다.

<br/>

앞의 JPA 설정, 적용, 핵심 글에서 본 쓰기 지연은 이렇게 동작한다.

```java
em.persist(a);      // INSERT 를 안 보낸다
em.persist(b);      // 아직 안 보낸다
em.persist(c);      // 아직도 안 보낸다
                    // 커밋할 때 한 번에 보낸다
```

<br/>

그런데 `IDENTITY` 는 이게 안 된다.

```java
em.persist(member);     // 여기서 바로 INSERT 가 나간다
```

<br/>

이유는 앞의 영속성 컨텍스트 글에서 본 구조에 있다.

1차 캐시는 `식별자 -> 엔티티` 의 `Map` 이다. 식별자가 있어야 넣을 수 있다.

<br/>

`IDENTITY` 는 DB가 `INSERT` 를 실행해야 번호를 알려준다.

그러니 영속 상태로 만들려면 `INSERT` 를 지금 보낼 수밖에 없다.

```java
SEQUENCE - 번호를 먼저 받아온다 -> 식별자를 알고 -> INSERT 는 나중에
IDENTITY - INSERT 를 해야 번호를 안다 -> 지금 보낼 수밖에 없다
```

<br/>

## 그래서 배치에서 차이가 난다

앞의 플러시 글에서 본 대량 처리에서 이게 드러난다.

```java
spring.jpa.properties.hibernate.jdbc.batch_size=50
```

<br/>

`SEQUENCE` 면 `INSERT` 를 `50` 개씩 묶어서 한 번에 보낸다.

`IDENTITY` 면 묶을 수가 없다. 이미 하나씩 보낸 뒤이기 때문이다.

<br/>

`10만` 건을 넣을 때 이 차이가 크게 벌어진다.

<br/>

## SEQUENCE 도 매번 DB 에 물어보면 느리다

```java
@SequenceGenerator(name = "member_seq", sequenceName = "member_seq", allocationSize = 50)
```

<br/>

`allocationSize` 가 그 해법이다. 한 번에 `50` 개를 미리 받아온다.

```java
DB 에 한 번 물어본다 -> 1~50 번을 내가 쓰겠다
그 뒤 49 번은 DB 에 안 물어본다
```

<br/>

기본값이 `50` 인데, `1` 로 바꾸면 매번 물어봐서 느려진다.

<br/>

여러 서버가 같이 써도 안전하다. 각 서버가 다른 구간을 받아가기 때문이다.

<br/>

## UUID 를 기본 키로 쓰면

앞의 B tree 설명 글에서 본 그 문제가 생긴다.

```java
자동 증가 id - 항상 마지막 노드에 추가된다. 그 노드만 건드리면 된다
UUID (랜덤) - 어디에 들어갈지 모른다. 중간 노드를 쪼개는 일이 자주 생긴다
```

<br/>

쪼개진 페이지가 반만 찬 상태로 남아서 인덱스가 커진다.

앞의 DB 인덱스 글에서 본 대로, 인덱스가 크면 트리가 높아지고 읽기가 느려진다.

<br/>

그리고 앞의 relation database 글에서 본 대로 키가 길면 모든 보조 인덱스가 같이 커진다.

```java
id BIGINT       -> 8 바이트
UUID CHAR(36)   -> 36 바이트
```

<br/>

그래서 이렇게 나눠 쓰는 경우가 많다.

```java
id BIGINT AUTO_INCREMENT   -- 내부용. 인덱스 친화적
uuid CHAR(36) UNIQUE       -- 외부 노출용. 순번을 추측 못 하게
```

<br/>

`UUID v7` 처럼 시간 순서가 들어간 형식을 쓰면 위 문제가 상당히 줄어든다.

<br/>

## 기본 키의 조건

원문의 `기본 키 제약 조건` 을 다시 정리하면 이렇다.

```java
null 이면 안 된다
유일해야 한다
변하면 안 된다
```

<br/>

`변하면 안 된다` 가 실무에서 제일 중요하다.

<br/>

앞의 relation database 글에서 본 대로, 이메일이나 주민번호를 기본 키로 쓰면 안 되는 이유가 이것이다.

이메일은 사용자가 바꾸고, 주민번호는 정책이 바뀌면 저장하면 안 될 수도 있다.

<br/>

기본 키가 바뀌면 그것을 외래 키로 참조하는 모든 테이블을 같이 고쳐야 한다.

`의미 없는 값` 을 기본 키로 쓰는 이유가 바로 `의미가 없으니 바뀔 일도 없다` 는 것이다.
