## 결과 조회

<br/>

## `fetch()` : 리스트 조회, 데이터 없으면 빈 리스트 반환

```java
@Test
public void resultFetch() {
    List<Member> fetch = queryFactory
            .selectFrom(member)
            .fetch();
}
```

<br/><br/>


## `fetchOne()` : 단 건 조회

- 결과가 없으면 : `null`

- 결과가 둘 이상이면 : `com.querydsl.core.NonUniqueResultException` 에러


```java
@Test
public void resultFetch() {
    Member fetchOne = queryFactory
            .selectFrom(QMember.member)
            .fetchOne();
}
```

<br/><br/>

## `fetchFirst()` : limit(1).fetchOne()

- limit(1)을 걸면서 `fetchOne()`을 하는 것이다

```java
@Test
public void resultFetch() {
    queryFactory
            .selectFrom(member)
            .fetchFirst(); // limit(1).fetchOne() 같은 것이다
}
```


<br/><br/>


## `fetchResults()` : 페이징 정보 포함, `total count` 쿼리 추가 실행

```java
@Test
public void resultFetch() {
    QueryResults<Member> results = queryFactory
            .selectFrom(member)
            .fetchResults();

    results.getTotal();
    List<Member> content = results.getResults();
}
```

<br/><br/>


## `fetchCount()` : count 쿼리로 변경해서 count 수 조회

```java
@Test
public void resultFetch() {
    long total = queryFactory
            .selectFrom(member)
            .fetchCount();
}
```

## 궁금증!

```java
fetchOne 과 fetchFirst 는 무엇이 다른가
```

`결과가 여러 개일 때` 가 다르다.

```java
fetch()          - 목록. 없으면 빈 리스트
fetchOne()       - 하나. 없으면 null, 둘 이상이면 예외
fetchFirst()     - limit(1).fetchOne() 과 같다. 첫 번째만
```

<br/>

`fetchOne` 은 둘 이상이면 이 예외가 난다.

```java
NonUniqueResultException
```

<br/>

앞의 TypeQuery, Query, 프로젝션 글에서 본 `getSingleResult` 와 같은 성격이다.

다만 없을 때 예외가 아니라 `null` 을 준다는 것이 다르다.

```java
JPA 의 getSingleResult - 없으면 NoResultException
QueryDSL 의 fetchOne   - 없으면 null
```

<br/>

## null 을 그대로 받으면 위험하다

앞의 래퍼 클래스 사용 이유는 글에서 본 그 문제다.

```java
Member member = queryFactory.selectFrom(member).where(...).fetchOne();
member.getName();      // null 이면 NullPointerException
```

<br/>

그래서 `Optional` 로 감싸서 넘기는 편이 낫다.

```java
public Optional<Member> findByEmail(String email) {
    return Optional.ofNullable(
            queryFactory.selectFrom(member).where(member.email.eq(email)).fetchOne()
    );
}
```

<br/>

앞의 쿼리 메소드 글에서 본 대로 스프링 데이터 JPA는 이걸 기본으로 해준다.

QueryDSL은 직접 감싸야 한다.

<br/>

## fetchResults 와 fetchCount 는 없어졌다

`QueryDSL 5.0` 부터 deprecated 됐다.

```java
QueryResults<Member> results = queryFactory.selectFrom(member).fetchResults();  // 쓰지 말 것
long total = queryFactory.selectFrom(member).fetchCount();                      // 쓰지 말 것
```

<br/>

이유는 만들어주는 `COUNT` 쿼리가 정확하지 않을 때가 있기 때문이다.

<br/>

`GROUP BY` 나 `DISTINCT` 가 있으면 원래 쿼리를 감싸서 세야 하는데,

자동 생성이 그걸 제대로 못 하는 경우가 있었다.

<br/>

그래서 지금은 직접 두 번 쓴다.

```java
List<Member> content = queryFactory.selectFrom(member)
        .where(cond)
        .offset(pageable.getOffset())
        .limit(pageable.getPageSize())
        .fetch();

JPAQuery<Long> countQuery = queryFactory.select(member.count())
        .from(member)
        .where(cond);

return PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne);
```

<br/>

## PageableExecutionUtils 를 쓰는 이유

`COUNT` 쿼리를 항상 날리지 않기 위해서다.

```java
첫 페이지이고 결과가 페이지 크기보다 작으면 -> COUNT 를 안 날린다
마지막 페이지이면                        -> 안 날린다
그 외                                   -> 날린다
```

<br/>

앞의 페이징과 정렬 글에서 본 `COUNT 가 비싸다` 는 문제를 줄이는 것이다.

```sql
SELECT COUNT(*) FROM member WHERE deleted = false;
`--SCAN member
```

<br/>

조건에 맞는 행을 전부 세야 하니 `1000만` 건이면 그것만으로 수 초가 걸린다.

<br/>

`countQuery::fetchOne` 을 람다로 넘기는 것이 포인트다.

`필요할 때만 실행한다` 는 뜻이고, 필요 없으면 아예 안 부른다.

앞의 프로토타입 사용 이유 글에서 본 `ObjectProvider` 와 같은 발상이다.

<br/>

## COUNT 쿼리를 따로 최적화할 수 있다는 이득도 있다

```java
JPAQuery<Long> countQuery = queryFactory.select(member.count())
        .from(member)
        .where(cond);          // join 을 뺐다
```

<br/>

목록 조회에는 조인이 필요해도 개수를 셀 때는 필요 없는 경우가 많다.

`fetchResults()` 는 원래 쿼리를 그대로 감싸서 세니 이 최적화가 불가능했다.

<br/>

앞의 페이징과 정렬 글에서 본 대로,

`COUNT` 는 조건에 맞는 범위를 전부 훑으니 조인 하나를 빼는 것만으로도 차이가 크다.
