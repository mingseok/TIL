## `Category.class`

```java
@Entity
public class Category {

    @Id
    @GeneratedValue
    private Long id;

    private String name;

    @ManyToOne
    @JoinColumn(name = "PARENT_ID")
    private Category parent;

    @OneToMany(mappedBy = "parent")
    private List<Category> child = new ArrayList<>();

    @ManyToMany
    @JoinTable(name = "CATEGORY_ITEM",
            
            // 내가 조인하는 것은 이것이고
            joinColumns = @JoinColumn(name = "CATEGORY_ID"),
            
            // 반대쪽이 조인하는 것은 이거라고 하는것이다.
            inverseJoinColumns = @JoinColumn(name = "ITEM_ID") 
    )
    private List<Item> items = new ArrayList<>();
}
```

## N:M 관계는 1:N, N:1로

- 테이블의 N:M 관계는 중간 테이블을 이용해서 1:N, N:1

- 실전에서는 중간 테이블이 단순하지 않다.
- @ManyToMany는 제약: 필드 추가X, 엔티티 테이블 불일치
- 실전에서는 @ManyToMany 사용X
<br/>

## 궁금증!

```java
실습 코드에서 실제로 나가는 SQL 을 보면 무엇을 알 수 있을까
```

앞의 DB 접근(JPA) 글에서 본 설정을 켜두면 전부 보인다.

```java
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
logging.level.org.hibernate.orm.jdbc.bind=trace
```

<br/>

마지막 줄이 중요하다. `?` 자리에 들어간 값까지 찍어준다.

이게 없으면 `WHERE id = ?` 만 보이고 어떤 값으로 조회했는지 모른다.

## 실습에서 확인해볼 만한 것들

### 1) 연관관계 주인이 아닌 쪽을 바꾸면 UPDATE 가 안 나간다

```java
team.getMembers().add(member);
// 커밋해도 member 테이블에 UPDATE 가 없다
```

<br/>

앞의 연관관계 매핑 글에서 본 그 규칙이 로그로 확인된다.

`SQL 이 안 나가는 것` 을 눈으로 보면 훨씬 잘 기억된다.

<br/>

### 2) 지연 로딩이 언제 나가는지

```java
Member member = em.find(Member.class, 1L);
System.out.println("여기까지 SELECT 몇 번?");
System.out.println(member.getTeam().getName());
System.out.println("여기서 하나 더 나갔을 것이다");
```

<br/>

앞의 프록시 기초 글에서 본 대로 `getName()` 을 부르는 순간 나간다.

`getId()` 만 부르면 안 나간다는 것도 같이 확인해볼 만하다.

<br/>

### 3) N+1 이 실제로 몇 번인지

```java
List<Member> members = em.createQuery("SELECT m FROM Member m", Member.class)
        .getResultList();
for (Member m : members) {
    System.out.println(m.getTeam().getName());
}
```

<br/>

회원이 `10` 명이면 `SELECT` 가 `11` 번 찍힌다.

앞의 DB 접근(JPA) 글에서 본 그 문제를 로그로 세어보는 것이다.

<br/>

`fetch join` 으로 바꾸면 `1` 번이 된다.

```java
SELECT m FROM Member m JOIN FETCH m.team
```

## 실습에서 자주 만나는 예외들

### TransientPropertyValueException

```java
object references an unsaved transient instance
```

<br/>

앞의 연관관계 매핑 (코드) 글에서 본 저장 순서 문제다.

연관된 엔티티를 먼저 저장하지 않았을 때 난다.

<br/>

### LazyInitializationException

```java
could not initialize proxy - no Session
```

<br/>

앞의 영속성 컨텍스트 글에서 본 준영속 상태 문제다.

트랜잭션 밖에서 지연 로딩을 건드렸을 때 난다.

<br/>

### MultipleBagFetchException

```java
cannot simultaneously fetch multiple bags
```

<br/>

앞의 엔티티 조회 DTO 조회 글에서 본 컬렉션 두 개 `fetch join` 문제다.

<br/>

### StackOverflowError

앞의 DTO 글에서 실제로 확인한 양방향 `toString` 순환이다.

<br/>

이 네 가지가 JPA 실습에서 나오는 예외의 대부분이다.

메시지를 기억해두면 원인을 바로 좁힐 수 있다.

<br/>

## 실습을 테스트로 짜두면 더 낫다

```java
@Test
void 지연로딩은_사용할_때_쿼리가_나간다() {
    Member member = memberRepository.findById(1L).orElseThrow();
    assertThat(Hibernate.isInitialized(member.getTeam())).isFalse();

    member.getTeam().getName();
    assertThat(Hibernate.isInitialized(member.getTeam())).isTrue();
}
```

<br/>

앞의 프록시 기초 글에서 본 `isInitialized` 로 초기화 여부를 확인할 수 있다.

<br/>

로그를 눈으로 보는 것보다 이렇게 단언으로 적어두면,

나중에 설정을 바꿨을 때 동작이 달라진 것을 자동으로 알 수 있다.

앞의 테스트 코드 작성 규칙 글에서 본 `작은 단위의 테스트` 가 이런 용도로도 쓰인다.
