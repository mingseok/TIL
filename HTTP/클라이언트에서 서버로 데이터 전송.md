## 동적 데이터 조회

- 주로 검색, 게시판 목록에서 정렬 필터 (검색어)

- 조회 조건을 줄여주는 필터, 조회 결과를 정렬하는 정렬 조건에 주로 사용

- 조회는 GET 사용

- GET은 쿼리 파라미터 사용해서 데이터를 전달한다.

### `form<>`태그에서 “GET” 을 사용한다는 말은?

- 웹 브라우저가 GET 메서드로 바꾼다.

    - 메세지 바디를 사용하지 않는다.

    - 그리고 쿼리 파라미터에 넣는 것이다.

        - e.g.) `?username=kim&age=20` 넣어서 서버에 전달한다.

- 자동으로 form태그가 `GET이면 url 경로에 다가 넣고,` `post면 ‘메세지 바디’ 에다가 데이터를 넣게 되는 것이다.`

## 궁금증!

```java
네 가지 상황에서 실제 요청이 어떻게 다른지 보자
```

요청을 되돌려주는 서버로 확인했다.

<br/>

### 정적 데이터 조회 - 쿼리 없이 경로만

```java
GET /images/logo.png HTTP/1.1
Host: localhost:18080

[본문] (없음)
```

<br/>

주소만으로 무엇을 원하는지 다 표현된다. 추가로 보낼 것이 없다.

<br/>

### 동적 데이터 조회 - 쿼리 스트링

```java
$ curl --get --data-urlencode "name=민석" --data-urlencode "age=30" http://localhost:18080/members

GET /members?name=%eb%af%bc%ec%84%9d&age=30 HTTP/1.1
Host: localhost:18080

[본문] (없음)
```

<br/>

검색어나 정렬 조건이 URL에 붙는다.

앞의 리소스 식별 글에서 본 대로, 경로는 대상을 가리키고 쿼리는 그중 어떤 것을 원하는지를 말한다.

<br/>

### HTML form 전송

```java
$ curl -X POST http://localhost:18080/members/new --data-urlencode "name=민석" --data-urlencode "age=30"

POST /members/new HTTP/1.1
Content-type: application/x-www-form-urlencoded
Content-length: 30

[본문] name=%EB%AF%BC%EC%84%9D&age=30
```

<br/>

값이 URL에서 본문으로 옮겨갔고 `Content-Type` 이 붙었다.

<br/>

형식은 쿼리 스트링과 똑같이 `키=값&키=값` 이다.

그래서 앞의 `@RequestParam` 글에서 본 대로, 서블릿은 둘을 같은 방법으로 꺼낸다.

<br/>

### HTTP API 전송

```java
POST /api/members HTTP/1.1
Content-Type: application/json
Content-Length: 34

{"name":"민석","age":30}
```

<br/>

`Content-Type` 이 `application/json` 으로 바뀌었다.

<br/>

앞의 HTTP 메시지 컨버터 글에서 본 대로, 서버는 이 헤더를 보고 어느 컨버터로 읽을지 정한다.

```java
application/x-www-form-urlencoded -> Form 컨버터 -> @ModelAttribute
application/json                  -> Jackson    -> @RequestBody
```

<br/>

## form 이 못 하는 것

`form` 태그는 `GET` 과 `POST` 만 보낼 수 있다.

```html
<form method="PUT">     <!-- 안 된다. POST 로 처리된다 -->
```

<br/>

앞의 PUT, PATCH, DELETE 글에서 본 메서드들을 `form` 으로는 못 쓴다.

<br/>

그래서 옛날에는 이런 우회를 썼다.

```html
<form method="post">
    <input type="hidden" name="_method" value="PUT">
</form>
```

<br/>

서버가 `_method` 를 보고 진짜 메서드를 판단하는 방식이다.

스프링에도 `HiddenHttpMethodFilter` 라는 것이 있었다.

<br/>

지금은 자바스크립트로 직접 보내니 이런 우회가 필요 없다.

```javascript
fetch('/api/members/1', { method: 'PUT', ... })
```

<br/>

## 파일을 보낼 때는 형식이 또 다르다

```html
<form enctype="multipart/form-data" method="post">
```

<br/>

```java
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryABC

------WebKitFormBoundaryABC
Content-Disposition: form-data; name="name"

민석
------WebKitFormBoundaryABC
Content-Disposition: form-data; name="file"; filename="photo.jpg"
Content-Type: image/jpeg

(바이너리 데이터)
------WebKitFormBoundaryABC--
```

<br/>

`boundary` 라는 구분자로 여러 조각을 나눠 담는다.

<br/>

파일은 바이너리라 앞의 URI 글에서 본 퍼센트 인코딩으로는 담을 수 없다.

이미지 하나를 인코딩하면 크기가 세 배로 불어나기 때문이다.

<br/>

그래서 인코딩하지 않고 원본 그대로 보내되, 구분자로 경계를 표시하는 방식을 쓴다.
