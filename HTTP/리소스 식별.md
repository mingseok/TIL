## 리소스 식별



### 누군가 나에게 만들어라는 요청이 왔다.

- 회원 목록 조회

- 회원 조회

- 회원등록

- 회원 수정

- 회원 삭제

<br/><br/>

## 이름을 이렇게 작성 하였다.

![이미지](/programming/img/입문593.PNG)

```java
좋은 URI 설계일까? 핵심은 -> "리소스 식별이다"
```

<br/><br/>

## 핵심

`“회원을 조회 해라!”` → 라는 것이 리소스가 아니고, `“회원"이 리소스 인것이다.`

- 리소스의 의미는 뭘까?

    - 회원을 등록하고 수정하고 조회하는게 리소스가 아니다.

        - e.g.) 미네랄을 캐라 → `“미네랄”`이 리소스이다.

        - 회원이라는 개념 자체가 바로 리소스이다.

    - 리소스를 어떻게 식별하는게 좋을까?

        - 회원을 등록하고 수정하고 조회하는 것은 `모두 배제한다.`

        - 회원이라는 리소스만 식별하면 된다. → 회원 리소스를 URI에 매핑한다.

<br/><br/>

## 그렇다면, 이렇게 하면 되는 것인가?

이렇게 의문점이 생기는 것이다.

```java
- 회원 목록 조회 /members
- 회원 조회 /members/{id} -> 어떻게 구분해?
- 회원 등록 /members/{id} -> 어떻게 구분해?
- 회원 수정 /members/{id} -> 어떻게 구분해?
- 회원 삭제 /members/{id} -> 어떻게 구분해?
```

<br/><br/>

## 리소스와 행위를 분리하자.

미네랄과 미네랄 캐는 행위를 분리 해야 되는 것이다.

- URI는 리소스만 식별한다.

- 리소스와 해당 리소스를 대상으로 하는 행위를 분리하자.

    - 리소스 : 회원

    - 행위 : 조회, 등록, 삭제, 변경

- 리소스는 명사, 행위는 동사 (미네랄을 캐라)

```java
"행위(메서드)는 어떻게 구분하지?"
```

<br/><br/>

## 회원 관리 시스템을 만든다고 생각해보자.

“리소스로 식별하다” 가 중요하다.

항상 리소스를 식별해야지 리소스가 아닌 다른것은 식별하면 안된다.

<br/>

즉, `“미네랄을 캐다”` 에서 `“캐다”를 식별하면 안된다는 말이다.`

그렇다면 ‘캐다’ 를 하고 싶다면?

- `GET, POST, DELETE` 같은 `HTTP 메서드`를 사용하면 되는 것이다.

![이미지](/programming/img/입문594.PNG)

<br/><br/>

## 정리하자면 이렇다.

- “미네랄을 캐라” 를 떠 올리고

    - “캐라” 는 빼고, 미네랄만 가지고 리소스를 설계 하는 것이다.

    - “회원” = /members 컬렉션이기 때문에 복수 ‘s’

    - “주문” 이면 /orders 이렇게 하고, ****“상세” 같은 경우에는  /orders/안에 상세가 들어가게 하고
    
    - 이렇게도 안되면, 컨트롤러 url 들어가면 되는 것이다.
<br/>

## 궁금증!

```java
"리소스와 행위를 분리하자" 는 게 실제로 어디까지 지켜질까?
```

조회, 등록, 수정, 삭제까지는 깔끔하게 된다.

```java
GET    /members        - 목록
GET    /members/100    - 하나
POST   /members        - 등록
PATCH  /members/100    - 수정
DELETE /members/100    - 삭제
```

<br/>

행위는 메서드가 표현하고, 주소는 대상만 가리킨다.

<br/>

## 그런데 안 맞는 것들이 있다

```java
로그인, 로그아웃
비밀번호 재설정 메일 발송
주문 취소
장바구니 비우기
검색
```

<br/>

`로그인` 은 무슨 자원일까. `POST /logins` 라고 하면 어색하다.

<br/>

억지로 자원으로 만들면 이렇게 된다.

```java
POST /sessions          - 로그인 (세션이라는 자원을 만든다)
DELETE /sessions/현재    - 로그아웃
```

<br/>

말은 되는데 읽는 사람이 한 번에 이해하기 어렵다.

<br/>

## 그래서 동작을 드러내는 쪽을 택하기도 한다

```java
POST /members/login
POST /members/logout
POST /orders/100/cancel
POST /carts/current/clear
```

<br/>

이건 `리소스와 행위를 분리하라` 는 원칙을 어기는 것이다.

다만 읽기가 훨씬 쉽다.

<br/>

앞의 PUT, PATCH, DELETE 글에서 본 `부분 수정이 복잡하면 행위를 드러낸다` 와 같은 판단이다.

<br/>

## 판단 기준

```java
상태를 바꾸는 것이 명확한 CRUD 인가 -> 리소스 + 메서드
그 외의 동작인가                  -> 동작을 주소에 드러낸다
```

<br/>

`주문 취소` 는 `PATCH /orders/100 { "status": "CANCELED" }` 로 쓸 수도 있다.

<br/>

그런데 취소는 상태값 하나만 바꾸는 일이 아니다.

```java
재고를 되돌린다
결제를 취소한다
취소 메일을 보낸다
포인트를 회수한다
```

<br/>

`status` 를 바꾸는 것처럼 보이게 하면, 다른 상태값도 그렇게 바꿀 수 있을 것처럼 오해된다.

`cancel` 이라고 적어두면 `이건 특별한 동작이다` 가 드러난다.

<br/>

## 이름을 짓는 규칙

```java
복수형을 쓴다        /members   (O)    /member    (X)
소문자를 쓴다        /members   (O)    /Members   (X)
하이픈을 쓴다        /order-items (O)  /orderItems (X)
확장자를 안 쓴다     /members   (O)    /members.json (X)
동사를 안 쓴다       /members   (O)    /getMembers  (X)
```

<br/>

`소문자` 는 앞의 URI 글에서 본 이유다.

경로는 대소문자를 가려서 `/Members` 와 `/members` 가 다른 주소가 된다.

<br/>

`하이픈` 은 밑줄보다 읽기 쉽고, 검색 엔진이 단어 구분으로 인식한다.

<br/>

`확장자` 는 앞의 뷰 리졸버 글에서 본 `Accept` 헤더로 대신한다.

같은 주소에 `Accept: application/json` 을 보내면 JSON이 오게 하는 편이 낫다.

<br/>

## 계층을 어디까지 표현할까

```java
GET /members/100/orders       - 100 번 회원의 주문 목록
GET /members/100/orders/5     - 그중 5 번 주문
```

<br/>

여기까지는 자연스럽다. 그런데 더 깊어지면 곤란해진다.

```java
GET /members/100/orders/5/items/3/reviews/7
```

<br/>

읽기도 어렵고, 앞의 것들이 정말 필요한지도 의문이다.

`7번 리뷰` 는 그 자체로 유일하니 이렇게 쓰면 된다.

```java
GET /reviews/7
```

<br/>

계층은 두 단계까지만 두고, 그 아래는 독립된 자원으로 두는 것이 관리하기 편하다.

<br/>

## 조회 조건은 쿼리로

```java
GET /members?status=active&page=2&size=20&sort=createdAt,desc
```

<br/>

`상태가 active 인 회원` 은 새로운 자원이 아니라 `회원 중 일부` 다.

그래서 경로가 아니라 쿼리로 표현한다.

```java
경로 - 무엇을 가리키는가 (자원의 계층)
쿼리 - 그중 어떤 것을 원하는가 (필터, 정렬, 페이징)
```

<br/>

앞의 GET, POST 글에서 본 대로 조건이 너무 길어지면 URL 길이 제한에 걸린다.

그때는 `POST /members/search` 로 가는 타협을 한다.
