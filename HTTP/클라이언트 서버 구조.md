## 클라이언트 서버 구조

클라이언트와 서버 구조로 되어 있다.

단순하게 클라이언트가 메세지를 보내고 서버가 응답을 한다.

<br/>

## 핵심

비즈니스 로직이랑 같은 데이터 들은 모두 서버에 넣는다.

그리고 클라이언트는 `ui` 같은 곳에 집중을 하는 것이다.


<br/>

클라이언트는 복잡한게 없고, 그냥 단순하게 `ui` 어떻게 그려야 되는지? 
부분에만 집중하자.

반대로 서버도, 비즈니스 더 커진다면 그것만 고민하면 되고, 클라이언트는 손댈 필요가 없다

<br/>

## 중요한 것은

처음에 하나로 뭉쳐져 있었는데, 클라이언트와 서버로 나눴고, 클라이언트가 `request` 보낸다. 

서버 입장은 무조건 요청이 올 때까지 기다렸다가 클라이언트의 요청을 받고 움직이는 것이다.

![이미지](/programming/img/입문581.PNG)
<br/>

## 궁금증!

```java
"서버는 요청이 올 때까지 기다린다" 는 게 코드로는 어떤 모습일까?
```

직접 서버를 하나 띄워보면 그 구조가 그대로 드러난다.

```java
HttpServer server = HttpServer.create(new InetSocketAddress(18080), 0);

server.createContext("/", exchange -> {
    // 요청이 올 때마다 여기가 실행된다
    byte[] body = "응답입니다".getBytes(StandardCharsets.UTF_8);
    exchange.sendResponseHeaders(200, body.length);
    exchange.getResponseBody().write(body);
    exchange.close();
});

server.start();     // 여기서 대기 상태로 들어간다
```

<br/>

`server.start()` 이후로 우리 코드가 하는 일이 없다.

요청이 오면 그때 등록해둔 함수가 불린다.

<br/>

앞의 IoC 글에서 본 `내가 부르는 것이 아니라 불려진다` 가 여기서도 나타난다.

프레임워크가 아니라 네트워크 자체가 그 구조인 것이다.

<br/>

## 포트를 잡는다는 것이 곧 대기다

```java
new InetSocketAddress(18080)
```

<br/>

`18080` 번 포트를 잡고 `여기로 오는 것은 내가 받겠다` 고 OS에 등록하는 것이다.

앞의 PORT, DNS 글에서 본 대로, 포트는 컴퓨터 안에서 어느 프로그램인지를 가린다.

<br/>

이미 누가 그 포트를 쓰고 있으면 이런 에러가 난다.

```java
java.net.BindException: Address already in use
```

<br/>

스프링 부트를 두 번 띄웠을 때 나는 그 에러다.

<br/>

## 클라이언트가 먼저 요청한다는 전제

앞의 IP프로토콜 글에서 본 `NAT` 때문에 이 전제가 더 강해졌다.

```java
공유기 안의 기기는 밖에서 먼저 연결할 수가 없다
-> 반드시 안에서 먼저 나가야 한다
```

<br/>

그래서 서버가 클라이언트에게 먼저 알려주고 싶을 때 방법이 마땅치 않다.

<br/>

해결책이 몇 가지 있다.

```java
폴링(polling)   - 클라이언트가 주기적으로 물어본다. "새 거 있어?"
롱 폴링          - 물어보고 응답을 안 주고 기다린다. 생기면 그때 응답한다
웹소켓          - 연결을 열어두고 양방향으로 주고받는다
SSE             - 서버가 열린 연결로 계속 흘려보낸다 (단방향)
푸시 알림        - OS 제조사의 서버를 거쳐서 전달한다
```

<br/>

전부 `클라이언트가 먼저 연결을 연다` 는 것은 같다.

그 연결을 어떻게 활용하느냐가 다를 뿐이다.

<br/>

## 나눠서 얻는 것

원문의 `비즈니스 로직은 서버, UI 는 클라이언트` 가 실무에서 이런 이득이 된다.

```java
앱을 안 고치고 로직을 바꿀 수 있다
  - 할인 정책이 바뀌면 서버만 배포한다
  - 앱 심사를 다시 받을 필요가 없다

한 서버에 여러 클라이언트를 붙일 수 있다
  - 웹, iOS, 안드로이드가 같은 API 를 쓴다

각각 따로 늘릴 수 있다
  - 앞의 Three-tier 글에서 본 그 이득이다
```

<br/>

## 그런데 경계를 잘못 그으면 문제가 된다

로직을 클라이언트에 두면 안 되는 이유가 있다.

```java
// 클라이언트에서 계산
if (member.grade === 'VIP') {
    price = price * 0.9;
}
fetch('/orders', { body: { price: price } });    // 계산 결과를 보낸다
```

<br/>

브라우저 개발자 도구로 `price` 를 `0` 으로 바꿔서 보낼 수 있다.

<br/>

클라이언트에서 오는 값은 전부 조작될 수 있다고 봐야 한다.

```java
클라이언트가 보내도 되는 것 - 무엇을 원하는지 (상품 id, 수량)
서버가 정해야 하는 것      - 얼마인지, 할인이 되는지, 권한이 있는지
```

<br/>

앞의 Validation 글에서 화면 검증과 별개로 서버 검증이 필요한 이유가 이것이다.

화면 검증은 사용자 편의이고, 서버 검증이 진짜 방어선이다.
