## 비 연결성

- http는 기본이 연결을 유지하지 않는 모델이다.

- 일반적으로 초 단위의 이하의 빠른 속도로 응답한다.
- 1시간 동안 수천명이 서비스를 사용해도 실제 서버에서 동시에 처리하는 요청은 수십개 이하로 매우 작다
    
    - e.g.) 웹 브라우저에서 계속 연속해서 검색 버튼을 누르지는 않는다.
- 서버 자원을 매우 효율적으로 사용할 수 있다.

```java
"HTTP 지속 연결로 문제를 해결한다"
```
<br/>

## 궁금증!

```java
지금도 요청마다 연결을 끊을까?
```

아니다. `HTTP/1.1` 부터는 연결을 유지한다.

<br/>

`curl` 로 연결 단계별 시간을 재보면 연결 비용이 얼마나 되는지 보인다.

```java
$ curl -w "DNS 조회 : %{time_namelookup}s\nTCP 연결 : %{time_connect}s\n첫 바이트 : %{time_starttransfer}s\n" ...

DNS 조회 : 0.000011s
TCP 연결 : 0.000232s
첫 바이트 : 0.001041s
```

<br/>

같은 컴퓨터 안이라 `0.2ms` 밖에 안 걸렸다.

<br/>

인터넷 너머 서버라면 얘기가 다르다.

앞의 TCP 3 way handshake 글에서 본 대로 왕복이 세 번 필요하다.

```java
서울에서 미국 서버까지 왕복 200ms 라면
TCP 연결만 200ms
HTTPS 면 TLS 핸드셰이크가 더 붙어서 400~600ms
```

<br/>

페이지 하나에 요청이 `100` 개인데 매번 이러면 답이 없다.

<br/>

## 그래서 연결을 재사용한다

```java
Connection: keep-alive
```

<br/>

`HTTP/1.1` 부터는 이게 기본값이다. 명시하지 않아도 유지된다.

<br/>

```java
비 연결성 (HTTP/1.0)
  연결 -> 요청 -> 응답 -> 끊기
  연결 -> 요청 -> 응답 -> 끊기      (매번 연결 비용)

연결 유지 (HTTP/1.1)
  연결 -> 요청 -> 응답 -> 요청 -> 응답 -> ... -> 끊기
```

<br/>

## 그래도 무상태라는 성질은 그대로다

여기가 헷갈리기 쉬운 부분이다.

```java
연결을 유지한다 = TCP 연결을 안 끊는다        (전송 계층 이야기)
무상태다        = 요청끼리 아무 관계가 없다     (HTTP 계층 이야기)
```

<br/>

연결이 유지되어도 서버는 이전 요청을 기억하지 않는다.

같은 연결로 온 요청이든 다른 연결로 온 요청이든 똑같이 처리한다.

<br/>

앞의 Stateful, Stateless 글에서 본 성질은 연결 유지와 무관하게 지켜지는 것이다.

<br/>

## HTTP/1.1 의 한계

연결은 재사용하는데 `한 번에 하나씩` 만 주고받을 수 있다.

```java
요청 1 -> 응답 1 -> 요청 2 -> 응답 2 -> ...
```

<br/>

앞의 요청이 느리면 뒤의 요청이 줄을 서서 기다린다.

이것을 `HOL 블로킹(Head-of-Line blocking)` 이라고 한다.

<br/>

그래서 브라우저는 연결을 여러 개 연다. 보통 도메인당 `6` 개다.

`6` 개까지는 병렬로 받고, 그 이상은 기다린다.

<br/>

이미지가 `50` 개인 페이지가 느린 이유가 이것이다.

<br/>

## HTTP/2 가 이 문제를 푼다

연결 하나로 여러 요청을 동시에 주고받는다.

```java
HTTP/1.1 - 연결 6 개, 각 연결에서 하나씩 순서대로
HTTP/2   - 연결 1 개, 그 안에서 여러 개를 섞어서 동시에
```

<br/>

응답도 순서대로 안 와도 된다. 먼저 끝난 것부터 온다.

<br/>

앞에서 `curl` 이 알려준 버전을 보면 확인할 수 있다.

```java
$ curl -w "HTTP 버전 : %{http_version}\n" ...
HTTP 버전 : 1.1
```

<br/>

내가 띄운 간단한 서버는 `1.1` 이다. `HTTP/2` 는 대개 `HTTPS` 와 같이 쓴다.

<br/>

## 그런데 TCP 층의 문제는 남는다

`HTTP/2` 는 HTTP 층의 줄서기를 없앴는데, TCP 층에는 여전히 있다.

<br/>

패킷 하나가 유실되면 TCP가 그것을 다시 받을 때까지 뒤의 데이터를 안 넘겨준다.

연결 하나로 다 보내고 있으니, 그 한 번의 유실이 모든 요청을 멈춘다.

<br/>

그래서 `HTTP/3` 은 TCP를 버리고 UDP 위에 새로 만들었다.

앞의 TCP, UDP 글에서 본 그 UDP다.

```java
HTTP/1.1 - TCP. 연결당 하나씩
HTTP/2   - TCP. 연결 하나로 여러 개 (TCP 층 줄서기는 남음)
HTTP/3   - UDP(QUIC). 스트림마다 독립적이라 줄서기가 없다
```

<br/>

`비 연결성` 이라는 원래 설계에서 출발해서, 연결 비용을 줄이려는 방향으로 계속 발전해온 셈이다.
