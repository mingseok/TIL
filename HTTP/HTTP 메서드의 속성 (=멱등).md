## HTTP 메서드의 속성 (=멱등)

<br/>

## 멱등이란? (idempotent)

- 한번 호출하든 두번 호출하든 100번 호출하든 결과가 똑같다. 라고 생각하자.

- 멱등 메서드

    - GET: 한 번 조회하든, 두 번 조회하든 같은 결과가 조회된다.

    - PUT: 결과를 대체한다. 같은 요청을 여러번 해도 최종 결과는 같다.

    - DELETE: 결과를 삭제한다. 같은 요청을 여러번 해도 결과는 똑같다.

```java
"POST: 멱등이 아니다 -> 두번 호출하면 같은 결제가 중복해서 발생할 수 있다"
```

<br/><br/>

## 멱등을 사용하는 이유는?

- 자동 복구 메커니즘

    - e.g.) 서버가 타임아웃 등으로 정상 응답을 못주었을때,
        
        클라이언트가 같은 요청을 다시 해도 되는가? 에 판단 근거이다.
        

<br/>

### `delete` 를 생각한다면, `delete`를 호출 했는데, 서버에서 응답이 없다면?

- 잘 실행 되었는지, 아닌지 알 수가 없다.

그러면 다시 클라이언트가 자동으로 delete 를 재시도 할것이다.

<br/><br/>

## 이런 부분은 멱등하지 않는다.

멱등은 외부 요인으로 중간에 리소스가 변경되는 것 까지는 고려하지 않는다.

```java
사용자 1) : "GET" 요청 -> 나이 10
사용자 2) : "PUT" 요청 -> 나이 50

사용자 1) : "GET" 요청 -> 나이 50 -> "사용자2의 영향으로 데이터가 변경되었다"
```

<br/><br/>

## 중요) 응답 결과를 캐시에서 사용할 수 있을까?

만약에, 내가 웹브라우저에 이미지 큰 걸 요청한다.

그러면, 그 다음에 또 그 똑같은 리소스를 요청할 필요가 없는 것이다.

<br/>

똑같은 이미지를 또 다시 다운로드 받으려고 한다면 오래 걸릴 것이다.

```java
"이걸 내 로컬 pc에 저장을 하는 것이다. 이걸 캐시라고 한다"
```

여기서 get, head, post, patch는 캐시가 가능하다.

- 하지만, 실제로는 `get`, `head` 정도만 캐시로 사용한다.

- post, patch는 본문 내용까지 캐시 키로 고려해야 하는데, 구현이 쉽지 않다.
<br/>

## 궁금증!

```java
멱등이라는 성질이 실무에서 왜 중요한 걸까?
```

`재시도해도 되는가` 를 결정하기 때문이다.

<br/>

네트워크는 언제든 끊긴다. 요청을 보냈는데 응답을 못 받는 상황이 자주 생긴다.

```java
클라이언트: 요청을 보냈다
            ... 응답이 안 온다 ...
            서버가 처리했을까? 안 했을까?
```

<br/>

이때 판단이 갈린다.

```java
멱등한 메서드   - 다시 보내도 된다. 두 번 처리돼도 결과가 같다
멱등하지 않은 것 - 다시 보내면 안 된다. 두 번 처리될 수 있다
```

<br/>

## 그래서 GET 은 자동으로 재시도된다

브라우저, 프록시, 로드 밸런서가 `GET` 은 알아서 다시 보낸다.

```java
GET /members/1 을 두 번 보내도 -> 조회만 두 번 될 뿐
```

<br/>

`POST` 는 자동 재시도를 안 한다.

주문이 두 번 들어갈 수 있기 때문이다.

<br/>

앞의 PRG 글에서 본 브라우저의 `POST 를 다시 보내시겠습니까?` 경고도 이 때문이다.

브라우저가 `이건 멱등하지 않으니 함부로 못 보낸다` 고 판단한 것이다.

<br/>

## DELETE 가 멱등인 이유

처음엔 헷갈린다. 두 번 지우면 두 번째는 실패하지 않나 싶다.

```java
DELETE /members/1  -> 200 (지웠다)
DELETE /members/1  -> 404 (없다)
```

<br/>

상태 코드는 다르다. 그런데 멱등의 기준은 `응답이 같은가` 가 아니라 `서버 상태가 같은가` 다.

```java
한 번 지운 뒤의 상태 = 1번 회원이 없다
두 번 지운 뒤의 상태 = 1번 회원이 없다     (같다)
```

<br/>

결과 상태가 같으니 멱등이다.

<br/>

같은 이유로 `PUT` 도 멱등이다.

```java
PUT /members/1 { "name": "민석", "age": 30 }
```

<br/>

몇 번을 보내도 `1번 회원의 이름은 민석, 나이는 30` 이라는 상태가 된다.

<br/>

## PATCH 는 멱등하지 않을 수 있다

`PUT` 은 통째로 덮어쓰지만 `PATCH` 는 일부만 바꾼다.

```java
PATCH /members/1 { "name": "민석" }        -> 이건 멱등이다

PATCH /members/1 { "op": "increment", "field": "age" }   -> 멱등이 아니다
```

<br/>

`나이를 1 올려라` 같은 요청은 보낼 때마다 결과가 달라진다.

<br/>

그래서 `PATCH` 는 `멱등할 수도 있고 아닐 수도 있다` 로 분류된다.

어떻게 정의하느냐에 달렸다.

<br/>

## POST 를 멱등하게 만드는 방법

주문 API는 `POST` 라서 원래 멱등하지 않다.

그런데 네트워크가 끊기면 클라이언트는 재시도하고 싶어진다.

<br/>

이때 쓰는 것이 `멱등 키(Idempotency-Key)` 다.

```java
POST /orders
Idempotency-Key: a1b2c3d4-...
```

<br/>

서버는 이 키를 기억해뒀다가, 같은 키로 다시 오면 처리하지 않고 저장해둔 결과를 그대로 돌려준다.

```java
1차 요청 -> 주문 생성, 결과를 키와 함께 저장, 201 응답
2차 요청 (같은 키) -> 새로 만들지 않고 저장된 201 응답을 그대로 준다
```

<br/>

결제 API가 대부분 이 방식을 쓴다.

두 번 결제되는 것보다 나쁜 일이 없기 때문이다.

<br/>

앞의 PRG 글 마지막에서 언급한 방식이 이것이다.

<br/>

## 안전(safe) 은 또 다른 성질이다

```java
안전   - 서버 상태를 바꾸지 않는다        (GET, HEAD)
멱등   - 여러 번 해도 상태가 같다         (GET, HEAD, PUT, DELETE)
캐시가능 - 응답을 저장해뒀다 써도 된다     (GET, HEAD, 조건부로 POST)
```

<br/>

`안전` 하면 반드시 `멱등` 이지만 반대는 아니다.

`DELETE` 는 멱등이지만 상태를 바꾸니 안전하지는 않다.

<br/>

그래서 조회에 `POST` 를 쓰면 안 되는 이유가 여러 겹이다.

```java
캐시가 안 된다  -> 앞의 캐시 글에서 본 이득을 못 쓴다
재시도가 안 된다 -> 네트워크가 끊기면 그냥 실패한다
안전하지 않다고 취급된다 -> 프록시가 함부로 처리하지 않는다
```

<br/>

조회 조건이 너무 길어서 URL에 안 들어갈 때만 예외적으로 `POST` 를 쓴다.
