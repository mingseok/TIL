## HTTP 상태코드 소개 (4xx, 5xx)

4백대는 클라이언트가 잘못한 것.

```java
"4백대 오류는 복구 불가능하다"
```



즉, 클라이언트가 보낸 자체에, 문제가 있기 때문에 그 요청을 수정해서 보내야 되는 것이다.

<br/><br/>

## 4xx (클라이언트 오류)

- 클라이언트의 요청에 잘못된 문법등으로 서버가 요청을 수행할 수 없다.

- 오류의 원인이 클라이언트에 있다.

- 중요) 클라이언트가 이미 잘못된 요청, 데이터를 보내고 있기 때문에, 똑같은 재시도가 실패함

<br/><br/>

## 400 Bad Request

클라이언트가 잘못된 요청을 해서 서버가 요청을 처리할 수 없다.

- 요청 구문, 메시지 등 오류

- 클라이언트는 요청 내용을 다시 검토하고, 보내야 한다.

    - e.g.) 요청 파라미터가 잘못되거나, API 스펙이 맞지 않을때.

<br/><br/>

## 401 Unauthorized

클라이언트가 해당 리소스에 대한 인증이 필요하다.

- 인증 되지 않음

    - 인증: 본인이 누구인지 확인, (로그인)

    - 인가: 권한 부여

- 401 오류 발생시 응답에 www-authenticate 헤더와 함께 인증 방법을 설명

<br/><br/>

## 403 Forbidden

서버가 요청을 이해했지만 승인을 거부한다

- 주로 인증 자격 증명은 있지만, 접근 권한이 불충분한 경우이다.

    - e.g.) 어드민 등급이 아닌 사용자가 로그인은 했지만, 어드민 등급의 리소스에 접근한 경우

<br/><br/>

## 404 Not Found

요청 리소스를 찾을 수 없다.

- 요청 리소스가 서버에 없다

- 또는 클라이언트가 권한이 부족한 리소스에 접근할 시, 해당 리소스를 숨기고 싶을때


<br/><br/>

## 5xx (Sercer Error)

- 서버 문제로 오류 발생

- 서버에 문제가 있기 때문에 재시도 하면 성공할 수도 있다.

    - 복구가 되거나 등등.

<br/><br/>

## 500 Internal Server Error

서버 문제로 오류 발생, 애매하면 500 오류

- 서버 내부 문제로 오류 발생

- 애매하면 500 오류

<br/><br/>

## 503 Service Unavailable

서비스 이용 불가

- 서버가 일시적인 과부하 또는 예정된 작업으로 잠시 요청을 처리할 수 없다
<br/>

## 궁금증!

```java
4xx 와 5xx 를 잘못 구분하면 무슨 일이 생길까?
```

`누구 잘못인가` 가 뒤집혀서, 모니터링과 재시도 판단이 전부 어긋난다.

```java
4xx - 클라이언트 잘못. 같은 요청을 다시 보내도 또 실패한다
5xx - 서버 잘못. 같은 요청을 다시 보내면 성공할 수도 있다
```

<br/>

이 차이가 실무에서 이렇게 작용한다.

```java
알림       - 5xx 가 늘면 개발자를 깨운다. 4xx 는 안 깨운다
자동 재시도 - 5xx 면 다시 시도한다. 4xx 면 안 한다
로그 수준   - 5xx 는 error, 4xx 는 warn 이나 info
```

<br/>

## 그래서 잘못 쓰면 이렇게 된다

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResult> handle(Exception e) {
    return ResponseEntity.status(500).body(...);      // 전부 500
}
```

<br/>

사용자가 이메일 형식을 틀리게 넣은 것도 `500` 이 된다.

<br/>

그러면 새벽에 알림이 계속 울린다. 서버는 멀쩡한데 사용자가 오타를 낸 것뿐이다.

진짜 장애가 났을 때는 그 알림에 묻혀서 못 본다.

<br/>

반대로 DB 연결이 끊긴 것을 `400` 으로 내려주면, 아무도 장애를 모른다.

클라이언트는 자기 요청이 잘못됐다고 생각하고 재시도도 안 한다.

<br/>

앞의 API 예외 처리 글에서 예외 종류별로 핸들러를 나눈 이유가 이것이다.

```java
@ExceptionHandler(IllegalArgumentException.class)   -> 400
@ExceptionHandler(MemberNotFoundException.class)    -> 404
@ExceptionHandler(Exception.class)                  -> 500 (진짜 예상 못 한 것만)
```

<br/>

## 401 과 403 을 헷갈리기 쉽다

이름이 오해를 부른다. `401 Unauthorized` 인데 뜻은 `인증이 안 됐다` 이다.

```java
401 Unauthorized - 네가 누군지 모르겠다. 로그인해라
403 Forbidden    - 네가 누군지는 알겠는데, 권한이 없다
```

<br/>

```java
로그인 안 한 상태로 마이페이지 접근  -> 401
일반 회원이 관리자 페이지 접근      -> 403
```

<br/>

`401` 은 로그인하면 해결되고, `403` 은 로그인해도 해결이 안 된다.

<br/>

이 구분이 있어야 클라이언트가 다르게 대응할 수 있다.

```java
401 -> 로그인 화면으로 보낸다
403 -> "권한이 없습니다" 를 보여준다
```

<br/>

`403` 인데 로그인 화면으로 보내면, 로그인해도 계속 튕겨서 무한 반복이 된다.

<br/>

## 404 와 403 사이의 판단

없는 자원과 권한 없는 자원을 구분해서 알려주면 정보가 새어 나간다.

```java
GET /members/1  -> 403 (있는데 권한 없음)
GET /members/2  -> 404 (없음)
```

<br/>

이러면 `1번은 존재하고 2번은 없다` 는 사실이 밖으로 나간다.

회원 번호를 하나씩 훑어서 가입자 수를 알아낼 수 있다.

<br/>

그래서 민감한 자원은 권한이 없어도 `404` 를 준다.

`있는지 없는지도 알려주지 않는` 것이다.

<br/>

## 429 와 503 도 알아두면 좋다

```java
429 Too Many Requests - 너무 자주 요청했다. 잠깐 기다려라
503 Service Unavailable - 서버가 지금 처리할 수 없다. 잠시 후 다시
```

<br/>

둘 다 `Retry-After` 헤더로 언제 다시 오라고 알려줄 수 있다.

```java
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

<br/>

`503` 은 `5xx` 지만 서버 코드의 버그는 아니다.

점검 중이거나 과부하 상태라는 뜻이라, 재시도하면 성공할 가능성이 높다.

<br/>

앞의 DBCP 글에서 본 커넥션 풀 고갈 같은 상황이 `503` 에 해당한다.

`500` 으로 내리면 버그처럼 보이지만, 사실은 자원이 부족한 것이다.
