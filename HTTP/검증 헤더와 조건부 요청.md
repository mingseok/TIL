## 캐시 시간 초과

캐시 유효 시간이 초과해서 서버에 다시 요청하면 다음 두 가지 상황이 발생한다.

1. 서버에서 기존 데이터를 변경한다.

2. 서버에서 기존 데이터를 변경하지 않는다.

<br/><br/>

## 정리

- 캐시 유효 시간이 초과해도, 서버의 데이터가 갱신되지 않으면

- 304 Not Modified + 헤더 메타 정보만 응답한다 (바디X)

- 클라이언트는 서버가 보낸 응답 헤더 정보로 캐시의 메타 정보를 갱신한다.

- 클라이언트는 캐시에 저장되어 있는 데이터를 재활용 한다.

- 결과적으로 네트워크 다운로드가 발생하지만 용량이 적은 헤더 정보만 다운로드 한다.

- 매우 실용적인 해결책이다.

<br/><br/>

## 검증 헤더와 조건부 요청 - Modified 단점

`Last-Modified`, `If-Moditied-Since` 단점이 있다.

- 1초 미만 단위로 캐시 조정이 불가능하다.

- 날짜 기반의 로직 사용

- 데이터를 수정해서 날짜가 다르지만, 같은 데이터를 수정해서 데이터 결과가 똑같은 경우

- 서버에서 별도의 캐시 로직을 관리하고 싶은 경우

    - e.g.) 스페이스나 주석처럼 크게 영향이 없는 변경에서 캐시를 유지하고 싶은 경우.

<br/><br/>

## 다른 방식인 **`etag` 방법!!**

- ETag(=Entity Tag)

- 캐시용 데이터에 임의의 고유한 버전 이름을 달아둔다.

    - e.g.) ETag : `“v1.0”`, ETag : `“a2jiodwo”` 등

- 데이터가 변경되면 이 이름을 바꿔서 변경한다.

    - e.g.) ETag : `“aaaa”` → ETag : `“bbbb”`

- 진짜 단순하게 ETag만 보내서 같으면 유지, 다르면 다시 받기 하는 것이다.

## 검증 헤더와 조건부 요청 - 정리

`ETag`, `If-None-Match` 정리

- 진짜 단순하게 ETag만 서버에 보내서 같으면 유지, 다르면 다시 받는다.

- 캐시 제어 로직을 서버에서 완전히 관리

- 클라이언트는 단순히 이 값을 서버에 제공

- e.g.

    - 서버는 배타 오픈 기간인 3일 동안 파일이 변경되어도 ETag를 동일하게 유지
    
    - 애플리케이션 배포 주기에 맞추어 ETag 모두 갱신

## 궁금증!

```java
"데이터를 변경하지 않았다" 를 서버가 어떻게 알려주는지 직접 보자
```

검증 헤더를 붙여주는 서버를 띄워놓고 요청을 두 번 보내봤다.

<br/>

### 1) 처음 요청할 때

```java
$ curl -i http://localhost:18083/etag

HTTP/1.1 200 OK
Etag: "v1-abc123"
Content-length: 41
Cache-control: no-cache
```

<br/>

`ETag` 라는 값을 같이 내려준다. 이 데이터의 지문 같은 것이다.

브라우저는 본문과 함께 이 값도 저장해둔다.

<br/>

### 2) 다음에 다시 요청할 때

```java
$ curl -i -H 'If-None-Match: "v1-abc123"' http://localhost:18083/etag

HTTP/1.1 304 Not Modified
Etag: "v1-abc123"
```

<br/>

`304` 가 왔고 본문이 없다. `Content-length` 조차 없다.

<br/>

서버가 `네가 갖고 있는 게 최신이니 그대로 써라` 라고 답한 것이다.

브라우저는 캐시에 있던 본문을 꺼내서 화면에 보여준다.

<br/>

## Last-Modified 로도 같은 일을 한다

```java
$ curl -i http://localhost:18083/last-modified

HTTP/1.1 200 OK
Last-modified: Mon, 01 Sep 2026 00:00:00 GMT
Content-length: 41
```

```java
$ curl -i -H 'If-Modified-Since: Mon, 01 Sep 2026 00:00:00 GMT' http://localhost:18083/last-modified

HTTP/1.1 304 Not Modified
```

<br/>

같은 결과다. 다만 기준이 다르다.

```java
Last-Modified / If-Modified-Since - 마지막 수정 시각을 비교한다
ETag / If-None-Match              - 내용의 지문을 비교한다
```

<br/>

## ETag 가 더 정확한 이유

`Last-Modified` 는 시간 기준이라 한계가 있다.

```java
1. 초 단위까지만 있다. 같은 초에 두 번 바뀌면 구분이 안 된다
2. 내용은 그대로인데 파일을 다시 저장하면 시각이 바뀐다
   -> 안 바뀌었는데 다시 받게 된다
3. 파일 A 와 B 를 번갈아 배포하면 시각만 보고는 판단이 안 된다
```

<br/>

`ETag` 는 내용을 해시한 값이라 이런 문제가 없다.

내용이 같으면 값도 같고, 내용이 다르면 값도 다르다.

<br/>

그래서 요즘 정적 파일 서버는 대부분 `ETag` 를 쓴다.

<br/>

## 얼마나 절약되는가

`304` 는 헤더만 오간다.

```java
200 OK        - 헤더 + 본문 (이미지면 수백 KB)
304 Not Modified - 헤더만 (수백 바이트)
```

<br/>

이미지 `20` 개짜리 페이지를 새로고침하면, 캐시가 없을 때는 매번 몇 MB를 받는다.

검증 헤더가 있으면 `304` 스무 개만 오가니 수십 KB로 끝난다.

<br/>

다만 네트워크 왕복은 그대로 `20` 번 일어난다.

앞의 프록시 캐시 글에서 본 `max-age` 는 이 왕복 자체를 없애는 방식이다.

```java
max-age 로 캐시 - 요청 자체를 안 보낸다 (제일 빠르다)
검증 헤더로 캐시 - 요청은 보내되 본문은 안 받는다
캐시 없음       - 매번 다 받는다
```

<br/>

## no-cache 와 no-store 를 헷갈리지 말자

위 실험에서 `Cache-control: no-cache` 를 줬는데도 캐시가 동작했다.

이름이 오해를 부른다.

```java
no-cache - 캐시는 하되, 쓸 때마다 서버에 물어봐라 (검증 필수)
no-store - 아예 저장하지 마라 (민감 정보용)
```

<br/>

`no-cache` 는 `캐시하지 마라` 가 아니라 `캐시를 믿지 마라` 에 가깝다.

<br/>

정말 저장을 막으려면 `no-store` 를 써야 한다.

로그인 응답이나 개인정보가 들어간 페이지에 쓴다.

<br/>

## 실무에서는 파일 이름을 바꾸는 방식을 더 많이 쓴다

정적 파일에는 검증 요청조차 안 보내게 만든다.

```html
<script src="/js/app.a1b2c3d4.js"></script>
```

<br/>

파일 이름에 내용 해시를 넣고, 캐시를 아주 길게 잡는다.

```java
Cache-Control: max-age=31536000, immutable      # 1년
```

<br/>

파일이 바뀌면 이름 자체가 바뀌니 새 주소로 요청이 간다.

같은 이름이면 절대 안 바뀐다는 것이 보장되니 `1년` 을 걸어도 안전하다.

<br/>

`ETag` 와 `304` 는 그 이름을 바꿀 수 없는 것들에 쓰는 셈이다.
