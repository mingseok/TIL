## Stateful, Stateless

무상태 프로토콜 : 스테이스리스 라고 부른다.

<br/>

## Stateful : 상태를 유지한다.

e.g.) 아무 이상이 없는 대화이다.

```java
고객: 이 노트북 얼마인가요?
점원: 100만원 입니다.

고객: 2개 구매하겠습니다.
점원: 200만원 입니다. 신용카드, 현금중에 어떤 걸로 구매 하시겠나요?

고객: 신용카드로 구매하겠습니다.
점원: 200만원 결제 완료 되었습니다.
```

<br/>

## 하지만 이 대화를 보면 다르다.

```java
고객: 이 노트북 얼마인가요?
점원: 100만원 입니다.

고객: 2개 구매하겠습니다.
점원: "?" 무엇을 2개 구매 하시겠어요?

고객: 신용카드로 구매하겠습니다.
점원: "?" 무슨 제품을 몇개 신용카드로 구매하시겠어요?
```

<br/>

## 즉, 다른점은

점원은 노트북의 상태를 유지하고 있는 것이다.

다시 말해, 서버가 클라이언트의 이전 상태를 보존 하는 것이다. → `“상태 유지"`

<br/><br/>

## Stateless : 상태를 유지하지 않는다. (무상태)

```java
고객: 이 노트북 얼마인가요?
점원: 100만원 입니다.

고객: 2개 구매하겠습니다.
점원: 200만원 입니다. 신용카드, 현금중에 어떤 걸로 구매 하시겠나요?

고객: 신용카드로 구매하겠습니다.
점원: 200만원 결제 완료 되었습니다.
```

즉, `상태 유지`에서는 `점원`이 바뀌면 `장애`가 나는 것이다.

하지만 무상태에서는 고객이 필요한 데이터를 그때그때 다 보내는 것이다.

- 때문에, 중간에 점원이 바뀌어도 아무 문제 없는 것이다.

<br/><br/>

## 정리하면

- `상태 유지:` 중간에 다른 점원으로 바뀌면 안된다.

    - 중간에 다른 점원으로 바뀔 때 상태 정보를 다른 점원에게 미리 알려줘야 한다

- `무상태:` 중간에 다른 점원으로 바뀌어도 된다.

    - 갑자기 고객이 증가해도 점원을 대거 투입할 수 있다.

    - 갑자기 클라이언트 요청이 증가해도 서버를 대거 투입할 수 있다.

    - 무상태는 응답 서버를 쉽게 바꿀 수 있다. → 무한한 서버 증설 가능

## 실무에서의 한계

- 모든 것을 무상태로 설계 할 수 있는 경우도 있고 없는 경우도 있다.

    - 무상태: 로그인이 필요 없는 단순한 서비스 소개 화면

    - 상태 유지: 로그인

- 로그인한 사용자의 경우 로그인 했다는 상태를 서버에 유지

- 일반적으로 브라우저 쿠키와 서버 세션등을 사용해서 상태를 유지한다.

- 상태 유지는 최소한만 사용한다.

```java
"스테이리스를 기억하자"
서버 개발자들이 어려워하는 업무.

- 정말 같은 시간에 딱 맞추어 발생하는 대용량 트래픽
- 선착순 이벤트, 명정 KTX 예약, 학과 수업 등록
- 저녁 6시에 선착순 1000명 치킨 할인 이벤트 -> 수만명 동시 요청
```

## 궁금증!

```java
무상태로 만들면 정확히 무엇이 좋아지는 걸까?
```

`아무 서버나 응답해도 된다` 는 것이다. 그래서 서버를 마음대로 늘릴 수 있다.

```java
상태를 서버가 기억한다
  -> 그 서버에만 다시 가야 한다
  -> 그 서버가 죽으면 정보가 사라진다
  -> 서버를 늘려도 특정 서버에만 몰린다

상태를 클라이언트가 들고 온다
  -> 아무 서버나 처리할 수 있다
  -> 한 대가 죽어도 다른 대가 받는다
  -> 서버를 늘리면 그만큼 나눠 받는다
```

<br/>

앞의 Three-tier 글에서 본 `Logic tier 는 늘리기 쉽다` 가 이 성질 덕분이다.

<br/>

## 그런데 세션은 상태다

앞의 쿠키, 세션 글에서 본 구조를 다시 보면 문제가 보인다.

```java
쿠키에 담긴 것    : JSESSIONID=A1B2C3D4E5
서버가 들고 있는 것 : A1B2C3D4E5 -> Member(id=1)
```

<br/>

`서버가 들고 있는 것` 이 바로 상태다.

<br/>

그래서 서버를 두 대로 늘리면 문제가 생긴다.

```java
서버 A 에서 로그인 -> 세션은 A 의 메모리에만 있다
다음 요청이 B 로 가면 -> B 에는 그 세션이 없다 -> 로그인이 풀린다
```

<br/>

앞의 로그인 세션 글에서 본 그 문제다.

`쿠키를 쓰면 무상태` 라고 생각하기 쉬운데, 세션 방식은 반쪽만 무상태인 셈이다.

<br/>

## 해결 방법이 세 가지 있다

### 첫번째) 스티키 세션

같은 사용자를 항상 같은 서버로 보낸다.

```java
로드 밸런서가 쿠키나 IP 를 보고 A 로 갔던 사람은 계속 A 로 보낸다
```

<br/>

간단한데 문제가 많다.

```java
A 가 죽으면 그 사용자들은 전부 로그인이 풀린다
A 에만 사람이 몰려도 다른 서버로 못 넘긴다
배포할 때마다 세션이 날아간다
```

<br/>

### 두번째) 세션 저장소를 밖으로

```java
세션을 Redis 에 저장한다
-> 어느 서버든 Redis 를 본다
-> 서버는 다시 무상태가 된다
```

<br/>

스프링에서는 의존성 하나로 바꿀 수 있다.

```java
implementation 'org.springframework.session:spring-session-data-redis'
```

<br/>

앞의 PSA 글에서 본 것과 같은 구조다.

`HttpSession` 인터페이스는 그대로 두고 저장 위치만 갈아끼운 것이다.

<br/>

다만 상태가 사라진 것은 아니다. Redis로 옮겼을 뿐이다.

Redis가 죽으면 전부 로그아웃된다.

<br/>

### 세번째) 토큰 방식

아예 서버가 아무것도 안 들고 있는다.

```java
JWT 토큰 안에 { "memberId": 1, "role": "USER", "exp": ... } 가 들어 있다
서명이 붙어 있어서 위조하면 검증에 실패한다
```

<br/>

이러면 진짜 무상태가 된다. 서버는 서명만 확인하면 된다.

<br/>

앞의 쿠키 글에서 본 `memberId=1 을 그냥 담으면 위험하다` 는 문제를

`서명` 으로 푼 것이다. 값은 보이지만 고치면 서명이 안 맞는다.

<br/>

## 토큰 방식의 대가

무상태를 얻는 대신 잃는 것이 있다.

```java
강제 로그아웃이 어렵다 - 서버가 아무것도 안 들고 있으니 무효화할 방법이 없다
토큰이 커진다        - 매 요청에 실려간다. 앞의 쿠키 글에서 본 그 부담이다
정보가 옛것일 수 있다 - 권한을 바꿔도 토큰이 만료될 때까지 옛 권한으로 동작한다
```

<br/>

그래서 실무에서는 절충한다.

```java
액세스 토큰  - 짧게 (30 분). 무상태로 검증
리프레시 토큰 - 길게. 서버가 목록을 들고 있는다 (여기는 상태가 있다)
```

<br/>

로그아웃하면 리프레시 토큰을 지운다.

액세스 토큰은 최대 `30` 분이면 만료되니 그때까지만 버티면 된다.

<br/>

완전한 무상태는 어렵고, `상태를 최소한으로 줄인` 형태로 가는 셈이다.

<br/>

## HTTP 자체가 무상태인 이유

원문에서 다룬 그 성질이, 사실 위 모든 이야기의 출발점이다.

<br/>

`HTTP` 는 요청 하나가 끝나면 아무것도 안 남긴다.

그래서 서버를 늘리는 것이 쉽고, 인터넷이 이만큼 커질 수 있었다.

<br/>

로그인 같은 것은 그 위에 우리가 얹은 것이다.

그러니 무상태가 깨지는 지점이 항상 그 얹은 부분에서 생긴다.
