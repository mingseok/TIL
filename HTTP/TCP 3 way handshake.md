## TCP 3 way handshake

### 연결지향 - TCP 3 way handshake (”TCP 연결 되었어요” 말한다)

1. 클라이언트에서 서버로 SYN 을 보낸다

2. 서버에서 왔다고 확인하고 ACK(=”확인이요”) 라는 답이랑 다시 SYN을 클라이언트로 보낸다.

3. 그리고 클라이언트 입장에서 다시 왔다는 걸 확인 후 답장 ACK(=”확인이요”)를 서버에게 한다.

<br/>

이렇게 하면 클라이언트도 서버를 믿을 수 있고, 서버도 클라이언트를 믿을 수 있게 되는 것이다.

그러면 “우리가 연결이 되었구나” 라고 생각 하고, 마지막으로 데이터 전송을 하는 것이다.

<br/><br/>

## 중요한 것은 가상인 것이다.

중간에 얼마나 많은 중계소가 있는가 그것들을 전부 알 수 없으므로 “우리끼리 연결 되었구나” 생각하는 것이다.

## 순서 보장

기본적으로는 서버가 클라이언트한테 `“2번부터 다시 보내!!”` 말한다

그러면 클라이언트는 다시 2번부터 다시 보내는 것이다.

![이미지](/programming/img/입문555.PNG)

이 과정이 그냥 되는 것이 아니라, TCP/IP 패킷에 의해 가능하게 된 것이다.

출발지 ip, 목적지, 전송 제어, 순서, 검증 정보를 패킷에 같이 실어 보내기 때문이다.
<br/>

## 궁금증!

```java
핸드셰이크가 실제로 얼마나 걸릴까?
```

`curl` 이 단계별 시간을 알려준다.

```java
$ curl -w "DNS 조회 : %{time_namelookup}s\nTCP 연결 : %{time_connect}s\n첫 바이트 : %{time_starttransfer}s\n" http://localhost:18083/etag

DNS 조회 : 0.000011s
TCP 연결 : 0.000232s
첫 바이트 : 0.001041s
```

<br/>

같은 컴퓨터라서 `0.2ms` 다. 왕복이 사실상 없기 때문이다.

<br/>

인터넷 너머면 다르다. 왕복 한 번에 걸리는 시간이 그대로 곱해진다.

```java
서울 <-> 서울 서버 : 왕복 5ms      -> 핸드셰이크 약 5ms
서울 <-> 미국 서버 : 왕복 200ms    -> 핸드셰이크 약 200ms
```

<br/>

핸드셰이크는 왕복 `1.5` 번이다. `SYN` 보내고 `SYN+ACK` 받으면 연결이 성립하고,

마지막 `ACK` 는 데이터와 함께 보낼 수 있어서 반 번으로 친다.

<br/>

## HTTPS 면 더 걸린다

TCP 연결 위에 TLS 핸드셰이크가 또 붙는다.

```java
TCP 핸드셰이크   - 왕복 1 번
TLS 1.2 핸드셰이크 - 왕복 2 번
TLS 1.3 핸드셰이크 - 왕복 1 번  (개선됐다)
```

<br/>

미국 서버에 `HTTPS` 로 접속하면 데이터를 받기 전에 `400~600ms` 가 그냥 지나간다.

<br/>

그래서 앞의 비 연결성 글에서 본 `연결 재사용` 이 중요한 것이다.

한 번 맺어둔 연결을 계속 쓰면 이 비용을 한 번만 치른다.

<br/>

CDN을 쓰는 이유도 여기 있다. 사용자와 가까운 곳에 서버를 두면 왕복 시간 자체가 줄어든다.

<br/>

## 왜 두 번이 아니라 세 번인가

`SYN` 과 `SYN+ACK` 두 번이면 될 것 같은데 그렇지 않다.

<br/>

두 번이면 `클라이언트가 서버의 응답을 받았다` 는 사실을 서버가 모른다.

```java
클라이언트 -> SYN -> 서버
클라이언트 <- SYN+ACK <- 서버
                       서버 : "내 응답이 도착했나? 모르겠다"
```

<br/>

서버가 준비를 마쳤는데 응답이 유실됐다면, 서버는 헛되이 자원을 잡고 기다리게 된다.

<br/>

세 번째 `ACK` 가 있어야 양쪽 다 `상대가 내 신호를 받았다` 는 것을 확인한다.

```java
1. SYN     -> 클라이언트가 "연결하자" 라고 한다
2. SYN+ACK -> 서버가 "좋다. 나도 연결하자" 라고 한다
3. ACK     -> 클라이언트가 "확인했다" 라고 한다
```

<br/>

이제 양쪽 다 서로가 보내고 받을 수 있다는 것을 알게 된다.

<br/>

## 순서 번호를 맞추는 과정이기도 하다

`SYN` 은 그냥 신호가 아니라 시작 번호를 같이 보낸다.

```java
클라이언트 : "나는 1000 번부터 셀게"
서버       : "알겠다. 나는 5000 번부터 셀게"
클라이언트 : "알겠다"
```

<br/>

앞의 TCP, UDP 글에서 본 `순서 보장` 이 이 번호로 이뤄진다.

<br/>

패킷이 뒤섞여 도착해도 번호를 보고 원래 순서대로 맞춘다.

빠진 번호가 있으면 다시 보내달라고 한다.

<br/>

시작 번호를 `0` 이 아니라 무작위로 잡는 이유는 보안 때문이다.

번호를 예측할 수 있으면 남의 연결에 가짜 패킷을 끼워 넣을 수 있다.

<br/>

## SYN 플러딩

핸드셰이크의 구조를 악용하는 공격이 있다.

```java
공격자가 SYN 만 계속 보내고 마지막 ACK 를 안 보낸다
-> 서버는 연결마다 자원을 잡아두고 기다린다
-> 자원이 다 차면 정상 사용자가 연결을 못 한다
```

<br/>

원문의 `가상 연결` 이라는 말이 여기서 실감난다.

연결이라는 것은 물리적인 선이 아니라 양쪽이 들고 있는 상태일 뿐이라,

그 상태를 잔뜩 만들어 놓기만 해도 서버가 마비된다.

<br/>

`SYN 쿠키` 라는 방어법이 있다. 자원을 미리 안 잡고, 마지막 `ACK` 가 와야 잡는 방식이다.
