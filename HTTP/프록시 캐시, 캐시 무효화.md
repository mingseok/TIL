## Cache - Control

캐시 지시어

- `Cache - Control : public`

    - 응답이 public 캐시에 저장되어도 된다.

- `Cache - Control : private`

    - 응답이 해당 사용자만을 위한 것임, private 캐시에 저장해야 한다.(디폴트)

- `Cache - Control : s-maxage`

    - 프록시 캐시에만 적용되는 max-age

- `Age : 60 (http 헤더)`

    - 오리진 서버에서 응답 후 프록시 캐시 내에 머문 시간(초)

<br/><br/>

## 캐시 무효화 설명

```java
"캐시를 적용하지 않으면, 캐시가 적용되지 않은것이 아닌가?"
```

하지만, 답은 아니다. → 웹 브라우저들이 `GET 요청일 경우 캐시 해버리는 경우도 있다.`

<br/><br/>

## Cache - Control

확실한 캐시 무효화 응답.

- 이 페이지는 캐시가 되면 안돼!! 한다면 이걸 넣어줘야 한다.

    - `Cache - Control : no-cache`

        - 데이터는 캐시해도 되지만, 항상 원 서버에 검증하고 사용

    - `Cache - Control : no-store`

        - 데이터에 민감한 정보가 있으므로 저장하면 안된다.

            - (메모리에서 사용하고 최대한 빨리 삭제)

    - `Cache - Control : must-revalidate`

        - 캐시 만료후 최초 조회시 원 서버에 검증해야 한다.

        - 원 서버 접근 실패시 반드시 오류가 발생해야 한다. - 504에러

        - must-revalidate는 캐시 유효 시간이라면 캐시를 사용한다.

## 궁금증!

```java
캐시 무효화가 안 되면 실제로 어떤 사고가 나는가
```

두 가지 방향의 사고가 있다.

<br/>

### 첫번째) 안 바뀌어야 할 것이 안 바뀐다

앞의 캐시 기본 동작 글에서 본 그 상황이다.

```java
app.js 를 고쳐서 배포했다
-> 브라우저 캐시에 옛 app.js 가 남아 있다
-> 새로고침해도 옛 코드가 돈다
```

<br/>

### 두번째) 캐시되면 안 될 것이 캐시된다

이쪽이 훨씬 위험하다.

```java
Cache-Control: public, max-age=3600
```

<br/>

로그인한 사용자의 마이페이지에 이게 붙어 있으면,

프록시가 그 응답을 저장해뒀다가 다음 사람에게 그대로 준다.

<br/>

내 이름과 주문 내역이 남에게 보이는 사고다.

<br/>

## 그래서 기본값이 private 이다

```java
Cache-Control: private   - 브라우저만 저장한다 (기본값)
Cache-Control: public    - 프록시도 저장해도 된다
```

<br/>

`public` 은 `누가 요청해도 같은 응답` 인 것에만 붙인다.

```java
이미지, CSS, JS  -> public
로그인 후 페이지  -> private (또는 no-store)
```

<br/>

## 확실히 막으려면 세 개를 다 쓴다

원문의 캐시 무효화 헤더 조합이다.

```java
Cache-Control: no-cache, no-store, must-revalidate
Pragma: no-cache
Expires: 0
```

<br/>

왜 이렇게 여러 개를 겹쳐 쓰는가 하면, 오래된 클라이언트와 프록시 때문이다.

```java
Cache-Control - HTTP/1.1 부터의 표준
Pragma        - HTTP/1.0 시절 것. 아직도 이것만 보는 장비가 있다
Expires       - HTTP/1.0 시절 것. Cache-Control 이 있으면 무시된다
```

<br/>

셋 다 붙여두면 어느 시대의 장비를 만나도 캐시하지 않는다.

<br/>

## must-revalidate 가 있는 이유

`no-cache` 만으로는 부족한 경우가 있다.

```java
no-cache        - 쓸 때마다 서버에 물어봐라
must-revalidate - 물어봤는데 서버가 응답을 안 하면 캐시를 쓰지 말고 504 를 내라
```

<br/>

`no-cache` 만 있으면, 서버에 못 물어봤을 때 프록시가 옛 데이터를 그냥 줄 수 있다.

<br/>

잔액 조회 같은 것은 옛 데이터를 보여주느니 에러를 내는 편이 낫다.

`must-revalidate` 가 그 판단을 강제한다.

<br/>

## 프록시 캐시가 있는 곳

원문의 유튜브 예시를 조금 더 풀면 이렇다.

```java
원 서버는 미국에 하나 있다
한국 사용자가 매번 미국까지 다녀오면 -> 앞의 TCP 3 way handshake 글에서 본 200ms 왕복
한국에 프록시 캐시(CDN)를 두면      -> 5ms
```

<br/>

첫 번째 사람만 미국까지 다녀오고, 그 뒤로는 한국 캐시에서 나온다.

<br/>

`Cache-Control: public` 이 없으면 이게 안 된다.

프록시가 저장하면 안 되는 것으로 판단해서 매번 원 서버까지 간다.

<br/>

## 캐시를 지워야 할 때

CDN에 이미 저장된 것을 지우는 것을 `퍼지(purge)` 라고 한다.

```java
CDN 관리 콘솔에서 특정 경로를 지운다
```

<br/>

그런데 이게 즉시 반영되지 않고, 전 세계 노드에 퍼지는 데 시간이 걸린다.

<br/>

그래서 앞의 캐시 기본 동작 글에서 본 방식을 더 많이 쓴다.

```html
<script src="/js/app.a1b2c3d4.js"></script>
```

<br/>

지울 필요 없이 새 이름으로 요청하면 되니까 훨씬 확실하다.

`퍼지` 는 이름을 못 바꾸는 것에만 쓰는 마지막 수단인 셈이다.

<br/>

## Vary 헤더

한 주소인데 응답이 달라지는 경우가 있다.

```java
Accept-Language: ko  -> 한국어 페이지
Accept-Language: en  -> 영어 페이지
```

<br/>

프록시가 이걸 모르면 한국어 페이지를 영어 사용자에게 준다.

<br/>

`Vary` 로 `이 헤더에 따라 응답이 달라진다` 고 알려줘야 한다.

```java
Vary: Accept-Language
```

<br/>

앞의 스프링 메시지 글에서 본 국제화가 CDN 뒤에 있으면 반드시 필요한 헤더다.

`Vary: Cookie` 도 자주 쓰인다. 로그인 여부에 따라 화면이 다를 때다.
