## CloudFront - CDN과 서명 URL

<br/>

## CDN 이란

전 세계에 흩어진 서버(엣지)가 내 콘텐츠를 복사해두고 사용자 가까운 곳에서 준다.

```java
없을 때  - 미국 사용자 -> 서울 서버. 왕복 200ms
있을 때  - 미국 사용자 -> 미국 엣지. 왕복 10ms. 엣지에 없으면 서울 원본(오리진)에서 한 번 가져와 저장
```

<br/>

앞의 클라우드 컴퓨팅과 리전 글에서 본 리전 간 지연을 엣지가 흡수한다.

<br/>

CloudFront는 앞의 클라우드 컴퓨팅 글에서 본 대로 글로벌 서비스다. 리전이 없다.

<br/><br/>

## 오리진

CloudFront가 콘텐츠를 가져오는 원본이다.

```java
S3 버킷          - 정적 파일. 앞의 S3 글
ALB / EC2       - 동적 API
다른 HTTP 서버
```

<br/>

앞의 탄력적 IP 글의 장애가 이 오리진 설정에서 났다.

오리진을 EC2의 퍼블릭 DNS 이름으로 잡았고, 그 이름이 재시작 후 바뀌어서 CloudFront가 죽은 주소를 찌른 것이다.

<br/>

오리진은 안 바뀌는 이름이어야 한다. ALB의 DNS나 S3 버킷 도메인이 그렇다.

<br/><br/>

## 캐시

CloudFront의 핵심은 캐시다.

```java
Cache-Control: max-age=31536000     <- 1 년. 엣지가 1 년 동안 안 물어본다
Cache-Control: no-store             <- 캐시 안 함. 매번 오리진으로
```

<br/>

앞의 캐시 기본 동작 글과 앞의 검증 헤더와 조건부 요청 글에서 본 HTTP 캐시 규칙을 엣지가 따른다.

오리진이 응답에 붙인 `Cache-Control` 을 보고 얼마나 들고 있을지 정한다.

<br/>

정적 파일과 API가 갈린다.

```java
/static/app.3f2a1.js     -> 1 년 캐시. 파일명에 해시가 있어서 내용이 바뀌면 이름도 바뀐다
/api/orders              -> 캐시 안 함. 사용자마다 다르다
```

<br/>

파일명에 해시를 붙이는 이유가 캐시 때문이다.

`app.js` 를 1년 캐시하면 배포해도 사용자가 옛 파일을 본다. `app.3f2a1.js` 면 새 배포는 `app.9c8b2.js` 라 다른 URL이다.

<br/><br/>

## 캐시 무효화

급하게 바꿔야 하면 엣지의 캐시를 지운다. 콘솔이나 CLI에서 경로를 지정해 무효화를 만든다.

```java
/index.html      <- 이 파일만
/*               <- 전부
```

<br/>

앞의 프록시 캐시, 캐시 무효화 글에서 본 그 무효화다.

월 1000개까지 무료고 그 이상은 경로당 요금이 붙는다. `/*` 로 전부 지우는 것도 1개로 친다.

<br/>

무효화에 의존하는 것보다 파일명에 해시를 붙여 무효화가 필요 없게 하는 것이 맞다.

`index.html` 만 짧게 캐시하고 나머지는 해시로 가는 것이 정적 사이트의 표준이다.

<br/><br/>

## 동적 API 도 CloudFront 를 거치는 이유

캐시가 안 되는데 왜 거치나.

```java
HTTPS 종단     - 인증서를 CloudFront 에 두고 오리진과는 HTTP 로. 앞의 WAS 서버와 WEB 서버의 이해 글
DDoS 완화      - 엣지가 앞에서 받는다
같은 도메인     - /static 은 S3, /api 는 ALB 로. 사용자는 도메인 하나만 본다
```

<br/>

세 번째가 편하다. 앞의 Ajax 글에서 본 CORS가 아예 안 생긴다. 프론트와 API가 같은 출처다.

<br/><br/>

## 서명 URL / 서명 쿠키

앞의 S3 글에서 본 presigned URL의 CloudFront 버전이다.

```java
S3 presigned      - S3 에 직접. 파일 하나에 URL 하나
CloudFront 서명   - 엣지를 거친다. 캐시 이득을 받으면서 접근 제어. 쿠키로 여러 파일을 한 번에
```

<br/>

동영상 강의처럼 `결제한 사용자만, 일정 시간만` 볼 수 있어야 하는 콘텐츠에 쓴다.

<br/>

서명은 키 페어로 한다.

```java
개인키   - 내 서버에. URL 에 서명할 때 쓴다
공개키   - CloudFront 에 등록. 서명을 검증할 때 쓴다
```

<br/>

앞의 EC2 접속 글에서 본 SSH 키 페어와 같은 공개키 방식이다.

서버가 개인키로 서명하고, 엣지가 공개키로 확인한다. 개인키가 새면 누구나 유효한 URL을 만들 수 있으니 이 키 관리가 곧 콘텐츠 보안이다.

<br/>

동영상 스트리밍(HLS)에서는 `.m3u8` 재생 목록 안의 조각(`.ts`) 수백 개가 전부 접근 제어를 받아야 한다.

URL마다 서명하면 재생 목록을 다시 써야 하니, 서명 쿠키로 도메인 전체에 한 번 권한을 주는 쪽이 맞다.

<br/><br/>

## 오리진 접근 제어 (OAC)

S3를 오리진으로 쓸 때, S3 버킷은 비공개로 두고 CloudFront만 읽을 수 있게 한다.

```java
사용자 -> S3 직접 URL      -> 403
사용자 -> CloudFront URL   -> 200
```

<br/>

CloudFront를 우회해서 S3에 직접 붙는 것을 막는다. 캐시를 거치지 않으면 앞의 S3 글에서 본 데이터 전송 요금이 S3에서 직접 나가고, 서명 검증도 우회된다.

<br/><br/>

## 정리

```java
CDN       - 엣지에 복사. 사용자 가까운 곳에서. 지연과 원본 부하를 줄인다
오리진     - 안 바뀌는 이름으로. EC2 DNS 를 박아서 장애를 겪었다
캐시      - Cache-Control 을 따른다. 파일명에 해시를 붙여 무효화를 피한다
동적 API  - 캐시 안 해도 HTTPS 종단, 같은 도메인 이득
서명      - 개인키로 서명, 엣지가 공개키로 검증. 유료 콘텐츠 접근 제어
OAC       - S3 는 비공개, CloudFront 만 읽는다
```
