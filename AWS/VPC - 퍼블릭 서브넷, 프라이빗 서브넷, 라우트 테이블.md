## VPC - 퍼블릭 서브넷, 프라이빗 서브넷, 라우트 테이블

<br/>

## VPC 란

Virtual Private Cloud. AWS 안에 내가 그린 사설 네트워크다.

```java
VPC = 10.0.0.0/16 이라는 대역을 하나 잡는다
그 안에 서브넷을 나눈다
서브넷에 EC2, RDS 를 놓는다
```

<br/>

VPC 밖에서는 안이 안 보인다. 같은 AWS 계정이어도 VPC가 다르면 다른 네트워크다.

앞의 사설 IP, CIDR, 서브넷 계산 글에서 본 대역 계산이 여기서 쓰인다.

<br/><br/>

## 서브넷은 가용영역에 속한다

```java
VPC        - 리전 단위. 여러 가용영역에 걸친다
서브넷      - 가용영역 하나에만. 10.0.0.0/24 는 2a 에, 10.0.1.0/24 는 2b 에
```

<br/>

앞의 클라우드 컴퓨팅과 리전, 가용영역 글에서 본 대로 두 가용영역에 걸치려면 서브넷이 최소 두 개다.

<br/><br/>

## 퍼블릭과 프라이빗의 차이는 라우트 테이블이다

서브넷 자체에 퍼블릭/프라이빗이라는 속성은 없다.

그 서브넷에 붙은 라우트 테이블에 `인터넷 게이트웨이로 가는 길` 이 있으면 퍼블릭이다.

```java
퍼블릭 서브넷의 라우트 테이블
  10.0.0.0/16   -> local              (VPC 안은 직접)
  0.0.0.0/0     -> igw-xxxx           (나머지는 인터넷 게이트웨이로)

프라이빗 서브넷의 라우트 테이블
  10.0.0.0/16   -> local
  0.0.0.0/0     -> nat-xxxx           (나머지는 NAT 게이트웨이로) 또는 없음
```

<br/>

앞의 사설 IP 글에서 본 `0.0.0.0/0` 이 `나머지 전부` 다.

<br/>

라우트 테이블은 IP 패킷의 목적지를 보고 어디로 보낼지 정하는 표다.

앞의 IP 프로토콜 글에서 본 라우터가 하는 일을 VPC 안에서 하는 것이다.

<br/><br/>

## 인터넷 게이트웨이

VPC와 인터넷을 잇는 문이다. VPC에 하나 붙인다.

<br/>

그런데 게이트웨이만 있으면 안 된다. 서버에 공인 IP가 있어야 한다.

```java
퍼블릭 서브넷 + 공인 IP  -> 인터넷과 양방향 통신
퍼블릭 서브넷 + 공인 IP 없음 -> 라우트는 있는데 돌아올 주소가 없어서 안 됨
```

<br/>

퍼블릭 서브넷에 띄웠는데 인터넷이 안 되면 `퍼블릭 IP 자동 할당` 을 안 켰는지 본다.

<br/><br/>

## NAT 게이트웨이

프라이빗 서브넷의 서버가 인터넷으로 나가야 할 때 쓴다.

```java
apt update, yum install     - 패키지를 받아야 한다
외부 API 호출               - 결제사, 소셜 로그인
```

<br/>

프라이빗 서브넷은 공인 IP가 없어서 직접 못 나간다.

NAT 게이트웨이가 퍼블릭 서브넷에 앉아서, 나가는 요청의 출발 주소를 자기 공인 IP로 바꿔준다.

```java
EC2 (10.0.10.5) -> NAT (공인 IP 로 바꿈) -> 인터넷
인터넷 응답 -> NAT (10.0.10.5 로 되돌림) -> EC2
```

<br/>

집 공유기가 하는 일과 같다. 집 안 기기들이 공인 IP 하나를 나눠 쓴다.

<br/>

밖에서 안으로는 못 들어온다. 응답만 돌아온다.

`나갈 수는 있는데 들어올 수는 없다` 가 프라이빗 서브넷의 성질이다.

<br/>

NAT 게이트웨이는 비싸다. 시간당 요금과 처리한 데이터 요금이 따로 붙는다.

작은 프로젝트에서 이것만 월 4~5만원이 나가서 놀라는 경우가 있다. 앞의 AWS 비용 글에서 본다.

<br/><br/>

## 왜 나누나

```java
퍼블릭 서브넷   - ALB, NAT 게이트웨이, 배스천 호스트. 인터넷에서 접근되어야 하는 것만
프라이빗 서브넷 - 앱 서버(EC2). ALB 를 통해서만 들어온다
DB 서브넷      - RDS. 앱 서버에서만 접근. 인터넷 경로 자체가 없다
```

<br/>

DB를 프라이빗에 두면 비밀번호가 새도 인터넷에서 붙을 수가 없다.

앞의 보안 그룹과 NACL 글에서 본 보안 그룹이 한 겹이고, 라우팅이 없는 것이 또 한 겹이다.

두 겹 중 하나가 잘못되어도 다른 하나가 막는다.

<br/>

작은 프로젝트에서는 EC2를 퍼블릭에 두고 RDS만 프라이빗에 두는 경우가 많다.

ALB와 NAT 비용을 아끼려는 것인데, 그러면 EC2가 인터넷에 직접 노출된다. 보안 그룹을 더 조심해야 한다.

<br/><br/>

## VPC 안의 DNS

```java
10.0.0.2   VPC 의 DNS 서버 (서브넷의 두 번째 주소)
```

<br/>

앞의 사설 IP 글에서 본 예약 주소 중 하나다.

RDS 엔드포인트 `xxx.rds.amazonaws.com` 을 EC2 안에서 조회하면 이 DNS가 사설 IP를 돌려준다.

밖에서 조회하면 공인 IP가 나오거나 안 나온다. 같은 이름이 안팎에서 다른 답을 주는 것이다.

<br/>

앞의 EC2에서 RDS 연결 확인 글에서 `EC2 에서는 되는데 내 컴퓨터에서는 안 되는` 이유 중 하나가 이것이다.

<br/><br/>

## 기본 VPC

계정을 만들면 리전마다 기본 VPC가 하나씩 있다.

```java
172.31.0.0/16
가용영역마다 퍼블릭 서브넷 하나씩
인터넷 게이트웨이 붙어 있음
```

<br/>

전부 퍼블릭이다. 여기에 RDS를 띄우면 인터넷에 노출된다.

편해서 그냥 쓰게 되는데, 실제 서비스면 VPC를 직접 만들어 프라이빗 서브넷을 두는 게 맞다.

<br/><br/>

## 정리

```java
VPC          - 내 사설 네트워크. 대역 하나
서브넷        - 가용영역 하나에 속하는 조각
퍼블릭/프라이빗 - 라우트 테이블에 인터넷 게이트웨이 경로가 있느냐
NAT          - 프라이빗에서 밖으로 나가기만. 비싸다
배치         - 인터넷 노출이 필요한 것만 퍼블릭에. DB 는 프라이빗에
```
