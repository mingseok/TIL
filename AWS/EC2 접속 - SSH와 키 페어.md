## EC2 접속 - SSH와 키 페어

<br/>

## 비밀번호가 없다

EC2는 만들 때 비밀번호를 정하지 않는다. 키 페어를 쓴다.

```java
공개키  - 서버의 ~/.ssh/authorized_keys 에 들어간다. 공개되어도 된다
개인키  - 내 컴퓨터에만. .pem 파일. 유출되면 그 서버에 누구나 들어간다
```

<br/>

접속할 때 서버가 `공개키로만 풀 수 있는 문제` 를 내고, 내가 개인키로 풀어서 답한다.

개인키가 없으면 답을 못 만든다. 비밀번호처럼 추측할 것이 없다.

<br/>

앞의 해싱, 암호화, 인코딩의 차이 글에서 본 암호화의 한 형태다. 공개키 암호화라고 부른다.

<br/><br/>

## 접속 명령

```java
ssh -i my-key.pem ec2-user@<퍼블릭 IP 또는 DNS>
```

<br/>

```java
-i          개인키 파일
ec2-user    Amazon Linux 의 기본 사용자. Ubuntu 는 ubuntu
```

<br/>

사용자 이름을 틀리면 `Permission denied (publickey)` 가 난다. 키가 틀린 것처럼 보이는데 사용자가 틀린 것이다.

<br/><br/>

## chmod 400 을 하라는 이유

```java
$ chmod 400 my-key.pem
```

<br/>

`.pem` 을 받은 뒤 이걸 안 하면 SSH가 거부한다.

```java
Permissions 0644 for 'my-key.pem' are too open.
This private key will be ignored.
```

<br/>

다른 사용자가 읽을 수 있는 권한이면 개인키가 아니라고 보는 것이다.

`400` 은 소유자만 읽기다. `600` 도 된다.

<br/>

SSH 클라이언트가 파일 권한까지 검사한다는 것이 처음엔 의외인데, 개인키가 그만큼 중요하다는 뜻이다.

<br/><br/>

## 접속이 안 될 때 순서대로

```java
1. 보안 그룹에 22 번이 내 IP 에 열려 있나         -> timed out 이면 여기
2. 퍼블릭 IP 가 있나. 프라이빗 서브넷 아닌가       -> timed out
3. 키가 맞나. 인스턴스 만들 때 고른 키인가          -> Permission denied (publickey)
4. 사용자 이름이 맞나 (ec2-user / ubuntu)           -> Permission denied (publickey)
5. 키 파일 권한이 400 인가                          -> too open
```

<br/>

앞의 EC2에서 RDS 연결 확인 글에서 본 대로,

`timed out` 은 네트워크 층(1, 2)이고 `Permission denied` 는 인증 층(3, 4)이다. 오류 메시지가 어느 층인지 알려준다.

<br/>

`1번` 에서 집 IP가 바뀌어서 막히는 것이 제일 흔하다.

앞의 보안 그룹과 NACL 글에서 본 대로 `0.0.0.0/0` 으로 열고 싶어지는 순간이다.

<br/><br/>

## 키를 잃어버리면

인스턴스에 다시 들어갈 방법이 없다. AWS도 개인키를 안 갖고 있다.

```java
1. 인스턴스를 멈춘다
2. 루트 볼륨(EBS)을 떼어서 다른 인스턴스에 붙인다
3. 그 인스턴스에서 authorized_keys 에 새 공개키를 넣는다
4. 볼륨을 원래 인스턴스에 되돌리고 켠다
```

<br/>

앞의 EC2 글에서 본 `디스크는 별개 자원` 이라 가능한 방법이다.

되긴 하는데 번거롭다. 키는 잃어버리면 안 되고, 잃어버릴 것에 대비해 다른 접속 수단을 두는 게 낫다.

<br/><br/>

## 배스천 호스트

프라이빗 서브넷의 서버에는 공인 IP가 없어서 직접 SSH가 안 된다.

퍼블릭 서브넷에 작은 서버 하나를 두고 거기를 거친다.

```java
내 컴퓨터 -> 배스천 (퍼블릭) -> 앱 서버 (프라이빗)
```

<br/>

```java
ssh -J ec2-user@bastion ec2-user@10.0.10.5      # -J 가 점프 호스트
```

<br/>

배스천에만 22번을 열고, 앱 서버는 배스천의 보안 그룹에서만 22번을 받는다.

인터넷에 노출된 SSH가 한 곳으로 줄어든다.

<br/>

앞의 RDS 접속 글에서 본 SSH 터널링도 이 배스천을 거친다.

<br/><br/>

## Session Manager : 22 번 포트가 필요 없다

SSM Session Manager는 SSH 없이 브라우저나 CLI로 셸을 연다.

```java
인스턴스에 SSM 에이전트가 돌고 있고 (Amazon Linux 는 기본)
인스턴스에 IAM 역할이 붙어 있으면
-> 콘솔에서 "연결" 버튼. 또는 CLI 의 ssm start-session
```

<br/>

```java
22 번 포트를 안 연다. 보안 그룹에 인바운드가 하나도 없어도 된다
키 페어가 필요 없다. 잃어버릴 것이 없다
누가 언제 접속해서 무엇을 쳤는지 CloudTrail 과 로그에 남는다
접근 권한을 IAM 으로 준다. 퇴사하면 IAM 사용자를 지우면 끝
```

<br/>

앞의 IAM 글에서 본 대로 `누가 무엇을 할 수 있나` 를 한 곳에서 관리하게 된다.

키 파일을 팀원끼리 돌리는 것보다 훨씬 낫다.

<br/>

요즘은 이쪽이 권장이다. SSH는 SSM이 안 되는 상황의 대안이 됐다.

<br/><br/>

## 정리

```java
키 페어     - 공개키는 서버에, 개인키는 나에게. chmod 400
안 될 때    - timed out 은 네트워크, Permission denied 는 인증
배스천     - 프라이빗 서버로 가는 징검다리. SSH 노출을 한 곳으로
SSM       - 22 번 포트도 키도 없이 접속. IAM 으로 권한. 요즘 기본
```
