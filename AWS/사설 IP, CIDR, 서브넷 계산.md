## 사설 IP, CIDR, 서브넷 계산

<br/>

## 사설 IP 와 공인 IP

```java
공인 IP  - 인터넷에서 유일하다. 어디서든 이 주소로 찾아올 수 있다
사설 IP  - 내 네트워크 안에서만 쓴다. 인터넷에서 라우팅되지 않는다
```

<br/>

사설 대역은 세 개로 정해져 있다.

```java
10.0.0.0/8         10.0.0.0    ~ 10.255.255.255     (1600 만 개)
172.16.0.0/12      172.16.0.0  ~ 172.31.255.255     (100 만 개)
192.168.0.0/16     192.168.0.0 ~ 192.168.255.255    (6 만 개)
```

<br/>

집 공유기가 `192.168.0.x` 를 주는 것, AWS 기본 VPC가 `172.31.x.x` 인 것이 이 대역이다.

<br/>

같은 사설 IP가 전 세계 수백만 네트워크에서 동시에 쓰이고 있다.

내 VPC의 `10.0.1.20` 과 옆 회사 VPC의 `10.0.1.20` 은 다른 서버다. 서로 안 보이니 충돌이 아니다.

<br/><br/>

## CIDR 표기

```java
10.0.0.0/16
         └ 앞 16 비트가 네트워크. 나머지 16 비트가 호스트
```

<br/>

IP는 32비트다. `/16` 이면 앞 16비트는 고정이고 뒤 16비트가 바뀐다.

```java
2^16 = 65,536 개 주소
```

<br/>

숫자가 클수록 네트워크가 작다. `/24` 는 256개, `/28` 은 16개다.

<br/><br/>

## 궁금증!

```java
실제로 몇 개가 쓸 수 있는 주소인가
```

계산해봤다.

```java
10.0.0.0/16    주소 65,536개   범위 10.0.0.0 ~ 10.0.255.255    AWS 서브넷이면 사용 가능 65,531개
10.0.1.0/24    주소    256개   범위 10.0.1.0 ~ 10.0.1.255      AWS 서브넷이면 사용 가능    251개
10.0.1.0/28    주소     16개   범위 10.0.1.0 ~ 10.0.1.15       AWS 서브넷이면 사용 가능     11개
```

<br/>

AWS는 서브넷마다 5개를 예약한다.

```java
10.0.1.0    네트워크 주소
10.0.1.1    VPC 라우터
10.0.1.2    DNS 서버
10.0.1.3    미래 용도
10.0.1.255  브로드캐스트
```

<br/>

일반 네트워크는 2개(네트워크, 브로드캐스트)만 빼는데 AWS는 3개 더 뺀다.

`/28` 서브넷에 서버 16대를 넣으려다 11대에서 막히는 것이 이것이다.

<br/>

`/28` 이 AWS가 허용하는 가장 작은 서브넷이다. `/16` 이 가장 크다.

<br/><br/>

## 0.0.0.0/0 은 무엇인가

```java
0.0.0.0/0    앞 0 비트가 고정 = 아무 조건 없음 = 모든 주소
```

<br/>

앞의 VPC 글에서 본 라우트 테이블의 `0.0.0.0/0 -> 인터넷 게이트웨이` 가 `나머지는 전부 인터넷으로` 라는 뜻이다.

<br/>

보안 그룹에서 `0.0.0.0/0` 은 `전 세계 누구나` 다.

22번 포트를 `0.0.0.0/0` 에 열어두면 전 세계에서 SSH 시도가 들어온다. 실제로 몇 분 안에 로그에 찍힌다.

<br/>

`/32` 는 반대다. 32비트 전부 고정이니 주소 하나다.

```java
203.0.113.7/32    이 IP 하나만
```

<br/>

내 IP만 SSH를 허용할 때 이렇게 쓴다.

<br/><br/>

## VPC 를 서브넷으로 나누기

```java
VPC 10.0.0.0/16 을 /24 로 나누면 256 개
  10.0.0.0/24, 10.0.1.0/24, 10.0.2.0/24 ... 10.0.255.0/24
```

<br/>

가용영역 2개에 퍼블릭 1개, 프라이빗 1개씩이면 4개만 쓴다. 252개가 남는다.

넉넉하게 잡아도 된다. 사설 IP는 공짜다.

<br/>

관례로 이렇게 나눈다.

```java
10.0.0.0/24   퍼블릭 A     (ALB, NAT 게이트웨이)
10.0.1.0/24   퍼블릭 B
10.0.10.0/24  프라이빗 A   (EC2 앱 서버)
10.0.11.0/24  프라이빗 B
10.0.20.0/24  DB A         (RDS)
10.0.21.0/24  DB B
```

<br/>

앞의 VPC 글에서 왜 이렇게 나누는지 본다.

<br/><br/>

## 겹치면 안 된다

```java
10.0.1.0/24 와 10.0.1.128/25 겹치나? True
```

<br/>

같은 VPC 안에서 겹치는 서브넷은 만들 수 없다. 콘솔이 거부한다.

<br/>

VPC끼리도 문제가 된다.

```java
VPC A = 10.0.0.0/16
VPC B = 10.0.0.0/16      <- 둘을 피어링으로 연결하려면 못 한다
```

<br/>

두 VPC를 연결(피어링)하려는데 대역이 같으면 `10.0.1.20` 이 어느 쪽인지 라우터가 알 수 없다.

<br/>

나중에 다른 회사 VPC와 연결하거나 온프레미스와 VPN을 맺을 때 이 문제가 터진다.

그래서 처음부터 대역을 다르게 잡는다. `10.0`, `10.1`, `10.2` 처럼.

기본 VPC가 전부 `172.31.0.0/16` 인 것이 이래서 불편하다. 계정 두 개의 기본 VPC는 항상 겹친다.

<br/><br/>

## 링크 로컬 : 169.254.x.x

```java
169.254.169.254 -> 링크 로컬 (인스턴스 메타데이터 주소)
```

<br/>

사설도 공인도 아닌 특수 대역이다. 같은 링크 안에서만 통한다.

앞의 EC2 글에서 본 메타데이터 주소가 이 대역이다.

<br/><br/>

## 정리

```java
사설 IP     - 10/8, 172.16/12, 192.168/16. 인터넷에서 안 보인다
CIDR       - /n 은 앞 n 비트 고정. 숫자가 크면 네트워크가 작다
AWS 예약    - 서브넷마다 5개. /28 은 11개 사용 가능
0.0.0.0/0  - 모든 주소. 라우트에서는 "인터넷으로", 보안 그룹에서는 "누구나"
겹침       - 같은 VPC 안 불가. VPC 간 연결 시 문제. 처음부터 다르게
```
