## IAM - 사용자, 역할, 정책, 최소 권한

<br/>

## IAM 이란

Identity and Access Management. `누가 무엇을 할 수 있나` 를 정하는 곳이다.

```java
사용자(User)   - 사람 또는 프로그램. 비밀번호나 액세스 키를 가진다
그룹(Group)    - 사용자 묶음. 정책을 그룹에 붙이면 전원에 적용
역할(Role)     - 임시로 쓰는 신분. 사람이 아니라 서비스가 쓴다
정책(Policy)   - 무엇을 허용/거부하는지 적은 JSON
```

<br/>

앞의 클라우드 컴퓨팅 글에서 본 대로 IAM은 글로벌이다. 리전이 없다.

<br/><br/>

## 정책 문서

```json
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::my-bucket/uploads/*"
}
```

<br/>

```java
Effect    - Allow 또는 Deny
Action    - 서비스:동작. s3:GetObject, ec2:StartInstances
Resource  - 어느 자원에. ARN 으로. * 는 전부
```

<br/>

세 가지가 전부 좁을수록 안전하다.

```java
"Action": "s3:*",  "Resource": "*"                    <- 모든 버킷에 모든 것
"Action": "s3:GetObject", "Resource": ".../uploads/*"  <- 이 버킷 이 폴더 읽기만
```

<br/><br/>

## 평가 순서

```java
1. 명시적 Deny 가 하나라도 있으면 -> 거부
2. Allow 가 있으면 -> 허용
3. 아무것도 없으면 -> 거부 (기본)
```

<br/>

기본이 거부다. 적지 않은 것은 못 한다.

앞의 보안 그룹과 NACL 글에서 본 보안 그룹과 같은 방식이다.

<br/>

`Deny` 가 `Allow` 를 이긴다. 그룹에서 허용해도 개인 정책에 `Deny` 가 있으면 막힌다.

`이 계정에서는 절대 운영 DB 를 지울 수 없다` 같은 안전장치를 `Deny` 로 건다.

<br/><br/>

## 최소 권한

필요한 것만 준다.

```java
앱 서버      - 자기 버킷의 읽기/쓰기. EC2 를 만들거나 지울 권한은 없다
CI/CD       - 배포 대상 서버에 배포하는 것만
개발자       - 개발 환경 전체. 운영 환경은 읽기만
```

<br/>

처음에는 `AdministratorAccess` 를 주고 시작하기 쉽다. 되니까.

그런데 그 자격 증명이 새면 계정 전체가 넘어간다.

<br/>

앞의 액세스 키를 코드에 넣지 않는 법 글에서 실제로 겪은 일을 본다.

키가 유출됐는데 그 키가 최소 권한이었다면 피해 범위가 좁았을 것이다.

<br/>

정책을 좁히는 것이 귀찮은 이유가 있다. `무엇이 필요한지` 를 미리 알기 어렵다.

```java
IAM Access Analyzer   - 최근 90 일간 실제로 쓴 권한만 뽑아준다
CloudTrail            - 어떤 API 를 불렀는지 전부 기록
```

<br/>

넓게 주고 시작한 뒤 실제 사용을 보고 좁히는 방법이 있다.

<br/><br/>

## 루트 계정은 쓰지 않는다

계정을 만들 때의 이메일과 비밀번호가 루트다. 모든 권한이고 제한할 수 없다.

```java
1. MFA 를 건다
2. 액세스 키를 만들지 않는다 (있으면 지운다)
3. IAM 사용자를 만들어 그것으로 일한다
4. 루트는 결제 설정 같은 루트만 되는 일에만
```

<br/>

루트 자격 증명이 새면 계정을 통째로 잃는다. 되찾는 것도 AWS 지원팀과 며칠이다.

<br/><br/>

## 사용자와 역할의 차이

```java
사용자   - 영구 자격 증명. 비밀번호, 액세스 키. 사람용
역할    - 임시 자격 증명. 몇 시간 뒤 만료. 서비스용
```

<br/>

EC2에 붙이는 것은 역할이다. EC2 안에서 S3를 쓰려면 EC2에 `S3 읽기 역할` 을 붙인다.

앞의 EC2 글에서 본 메타데이터 주소에서 이 역할의 임시 자격 증명을 받는다.

<br/>

임시라는 것이 핵심이다. 새어도 몇 시간이면 죽는다.

<br/>

역할은 `누가 이 역할을 쓸 수 있나` 를 따로 정한다. 신뢰 정책이라고 한다.

```json
{ "Principal": { "Service": "ec2.amazonaws.com" }, "Action": "sts:AssumeRole" }
```

<br/>

`EC2 서비스가 이 역할을 쓸 수 있다` 는 뜻이다. 람다용 역할은 람다만 쓸 수 있다.

<br/><br/>

## 자주 보는 오류

```java
AccessDenied: User is not authorized to perform: s3:PutObject on resource: ...
```

<br/>

메시지에 답이 다 있다. 누가, 무엇을, 어디에 하려다 막혔는지.

```java
1. 그 사용자/역할에 붙은 정책에 그 Action 이 있나
2. Resource 의 ARN 이 맞나. 버킷 이름은 맞는데 /* 가 빠졌나
3. 어딘가 Deny 가 있나
4. 버킷 정책(자원 쪽 정책)이 막고 있나
```

<br/>

`4번` 이 헷갈린다. IAM 정책은 `사용자 쪽`, 버킷 정책은 `자원 쪽` 이다. 둘 다 허용해야 한다.

<br/><br/>

## 정리

```java
정책     - Effect / Action / Resource. 셋 다 좁게
평가     - Deny > Allow > 기본 거부
최소 권한 - 필요한 것만. Access Analyzer 로 실제 사용을 보고 좁힌다
루트     - MFA, 키 없음, 안 쓴다
역할     - 임시 자격 증명. EC2, 람다 같은 서비스에 붙인다. 사람은 사용자
```
