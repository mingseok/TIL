## RDS - 관리형 데이터베이스

<br/>

## EC2 에 MySQL 을 깔면 되지 않나

된다. 그런데 그 뒤가 일이다.

```java
백업을 매일 돌려야 한다. 어디에 저장하나
버전 패치를 해야 한다. 언제 내리나
디스크가 차면 늘려야 한다
서버가 죽으면 다른 데서 올려야 한다. 데이터는?
```

<br/>

RDS는 이걸 AWS가 한다. 나는 DB 안의 일만 한다.

```java
내 일     - 스키마, 쿼리, 인덱스, 사용자
AWS 일    - 운영체제, 패치, 백업, 복제, 장애 시 교체
```

<br/>

앞의 클라우드 컴퓨팅 글에서 본 IaaS와 PaaS 사이가 이것이다.

<br/>

대가는 두 가지다. 요금이 EC2에 직접 깔 때보다 높고, 운영체제에 접근할 수 없다. SSH가 안 된다.

<br/><br/>

## 자동 백업과 스냅샷

```java
자동 백업   - 매일 정해진 시간에. 보관 기간 1~35 일. 특정 시점으로 복구 가능
스냅샷     - 내가 원할 때 찍는다. 지우기 전까지 남는다
```

<br/>

특정 시점 복구가 핵심이다.

```java
"어제 오후 3시 12분 상태로 되돌려줘"
```

<br/>

앞의 fsync와 내구성 글에서 본 트랜잭션 로그를 계속 백업해두기 때문에 분 단위로 돌아갈 수 있다.

<br/>

복구는 새 인스턴스로 만들어진다. 기존 것을 덮어쓰지 않는다.

`실수로 DELETE 했다` 면 그 시점 직전으로 새 인스턴스를 만들고, 거기서 데이터를 꺼내 옮긴다.

<br/>

앞의 물리논리삭제 글에서 본 대로 논리 삭제를 해두면 이 복구 자체가 필요 없어지는 경우가 많다.

<br/><br/>

## Multi-AZ

다른 가용영역에 대기 서버를 하나 더 둔다.

```java
주 서버 (2a) <-- 동기 복제 --> 대기 서버 (2b)
```

<br/>

앞의 클라우드 컴퓨팅과 리전, 가용영역 글에서 본 대로 건물이 다르다.

주 서버가 죽으면 AWS가 대기 서버로 자동 전환한다. 1~2분 걸린다. 엔드포인트 DNS가 새 서버를 가리키게 바뀐다.

<br/>

동기 복제라 데이터 유실이 없다. 커밋이 양쪽에 다 쓰여야 돌아온다.

앞의 fsync 글에서 본 `복제 내구성` 이 이것이다.

<br/>

대기 서버는 읽기에도 못 쓴다. 순전히 장애 대비다. 요금은 두 배다.

<br/>

앱 쪽에서 신경 쓸 것이 하나 있다. 전환되면 기존 커넥션이 전부 끊긴다.

앞의 커넥션 풀 글에서 본 HikariCP가 죽은 커넥션을 감지해서 새로 맺어야 한다. `connectionTestQuery` 나 `validationTimeout` 이 그 설정이다.

<br/><br/>

## 리드 레플리카

읽기 전용 복제본이다. Multi-AZ와 목적이 다르다.

```java
Multi-AZ      - 장애 대비. 동기 복제. 읽기 불가
리드 레플리카  - 읽기 분산. 비동기 복제. 읽기 가능
```

<br/>

앞의 관계형 DB 글에서 본 `쓰기는 한 대, 읽기는 여러 대` 가 이것이다.

<br/>

비동기라 주 서버보다 조금 늦다. 보통 밀리초에서 초 단위다.

```java
주문을 저장하고 바로 목록을 조회하면 -> 레플리카에는 아직 없을 수 있다
```

<br/>

`쓴 직후 읽기` 는 주 서버로 보내야 한다. 앱에서 라우팅을 나눠야 하는 이유다.

<br/><br/>

## 파라미터 그룹

`my.cnf` 를 못 만지니 대신 이걸 쓴다.

```java
max_connections
character_set_server        -> utf8mb4
time_zone                   -> Asia/Seoul
innodb_buffer_pool_size
```

<br/>

기본 파라미터 그룹은 수정이 안 된다. 복사해서 내 것을 만들고 인스턴스에 붙인다.

<br/>

`character_set_server` 를 안 바꾸면 기본이 `latin1` 인 버전이 있어서, 앞의 문자 인코딩과 한글 깨짐 글에서 본 그 사고가 난다.

`time_zone` 은 기본이 UTC다. 앞의 시간과 시계 글에서 본 대로 UTC로 저장하는 게 맞는데, 앱이 `Asia/Seoul` 을 기대하면 9시간이 틀어진다.

<br/>

일부 파라미터는 재시작이 필요하다. `max_connections` 가 그렇다. 운영 중에 바꾸면 안 적용되고, 재시작 창에서 적용된다.

<br/><br/>

## 엔드포인트

RDS는 IP가 아니라 DNS 이름으로 접근한다.

```java
mydb.xxxxxxxx.ap-northeast-2.rds.amazonaws.com:3306
```

<br/>

Multi-AZ 전환이나 인스턴스 교체가 일어나면 이 이름이 새 서버를 가리키게 바뀐다.

앞의 탄력적 IP 글에서 본 `IP 를 박아두면 깨진다` 가 RDS에서는 처음부터 막혀 있는 것이다.

<br/>

앱 설정에는 항상 이 이름을 쓴다. 절대 IP를 조회해서 박지 않는다.

<br/>

JVM의 DNS 캐시도 신경 써야 한다. 앞의 Route 53 글에서 본 TTL을 JVM이 무시하고 오래 캐시하면, 전환 뒤에도 옛 IP를 찌른다.

`networkaddress.cache.ttl` 을 60초 정도로 두는 것이 관례다.

<br/><br/>

## 정리

```java
RDS      - DB 운영을 AWS 에 맡긴다. 스키마와 쿼리만 내 일. SSH 불가
백업     - 자동 백업으로 특정 시점 복구. 새 인스턴스로 복구된다
Multi-AZ - 장애 대비. 동기 복제. 요금 2배. 전환 시 커넥션 끊김
레플리카  - 읽기 분산. 비동기. 쓴 직후 읽기는 주 서버로
파라미터  - utf8mb4, time_zone 확인. 일부는 재시작 필요
엔드포인트 - DNS 이름. IP 박지 않는다. JVM DNS 캐시 TTL 확인
```
