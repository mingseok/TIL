## S3 - 객체 스토리지와 presigned URL

<br/>

## 파일 시스템이 아니다

S3는 객체 스토리지다. 폴더가 없다.

```java
버킷       - 최상위 이름. 전 세계에서 유일해야 한다
키(Key)    - 객체 이름. "uploads/2026/09/photo.jpg" 전체가 이름
객체       - 데이터 + 메타데이터
```

<br/>

`uploads/2026/09/` 라는 폴더는 없다. 키에 `/` 가 들어 있을 뿐이다.

콘솔이 `/` 를 기준으로 폴더처럼 보여주는 것이다.

<br/>

그래서 `폴더 이름 바꾸기` 가 없다. 그 접두사를 가진 객체를 전부 복사하고 지워야 한다.

<br/><br/>

## 왜 EC2 디스크에 안 두나

```java
EC2 디스크   - 그 서버에만 있다. 서버가 두 대면 한쪽에만. 서버가 죽으면 같이
S3          - 어느 서버에서든 같은 것. 서버와 수명이 분리된다. 내구성 99.999999999%
```

<br/>

앞의 무중단 배포 글에서 본 대로 서버를 갈아치우는 구조에서 서버 안에 파일을 두면 안 된다.

업로드 파일, 정적 파일, 백업, 로그가 전부 S3로 간다.

<br/>

앞의 process를 설명해 주세요 글에서 본 `상태를 밖에 둔다` 의 파일 버전이다.

<br/><br/>

## 객체는 통째로 다룬다

```java
PUT    - 객체 하나를 통째로 올린다
GET    - 통째로 받는다 (Range 로 일부만 가능)
DELETE
```

<br/>

파일 중간 한 바이트를 고칠 수 없다. 전체를 다시 올린다.

DB처럼 쓰려는 시도는 안 맞는다. `쓰고 나서 통째로 읽는` 것에 맞다.

<br/><br/>

## 접근 권한

기본이 전부 비공개다.

```java
버킷 정책        - 자원 쪽 정책. "이 버킷은 누가 무엇을 할 수 있나"
IAM 정책        - 사용자 쪽. 앞의 IAM 글
퍼블릭 액세스 차단 - 계정/버킷 단위 안전장치. 켜두면 실수로 공개 못 함
```

<br/>

버킷을 통째로 공개했다가 고객 데이터가 새는 사고가 자주 있었다.

그래서 `퍼블릭 액세스 차단` 이 기본으로 켜져 있다. 정적 사이트 호스팅이 아니면 끄지 않는다.

<br/><br/>

## presigned URL

비공개 객체를 `이 URL 을 가진 사람만, 정해진 시간만` 볼 수 있게 하는 방법이다.

```java
서버가 자기 자격 증명으로 서명한 URL 을 만든다
클라이언트는 그 URL 로 S3 에 직접 요청한다
만료 시간이 지나면 403
```

<br/>

## 궁금증!

```java
서명이 어떻게 위조를 막나
```

같은 원리를 HMAC으로 재현해봤다. 비밀키로 URL을 서명한다.

```java
/videos/lesson1.mp4?expires=1788400000   -> 서명 6yuYgSNeC6soQpR-...
/videos/lesson1.mp4?expires=1788999999   -> 서명 jdKZP36PfKfPUUxi...    (만료 시각만 바꿈)
/videos/lesson2.mp4?expires=1788400000   -> 서명 _bpfIZ02E3MddSOR...    (파일만 바꿈)
```

<br/>

한 글자만 바꿔도 서명이 전부 달라진다.

클라이언트가 만료 시각을 늘리거나 다른 파일 이름으로 바꾸면, S3가 다시 계산한 서명과 안 맞아서 거부한다.

<br/>

비밀키는 서버에만 있으니 클라이언트가 유효한 서명을 새로 만들 수 없다.

앞의 해싱, 암호화, 인코딩의 차이 글에서 본 HMAC이 이것이다.

<br/><br/>

## 업로드도 presigned 로

```java
클라이언트 -> 내 서버 -> S3        파일이 내 서버를 거친다. 서버 대역폭과 메모리를 먹는다
클라이언트 -> S3 (presigned PUT)   내 서버는 URL 만 발급. 파일은 직접 S3 로
```

<br/>

큰 파일 업로드에서 두 번째가 훨씬 낫다.

내 서버는 `업로드해도 되는 사람인지` 만 확인하고 URL을 준다. 파일은 안 만진다.

<br/>

앞의 스레드 풀 글에서 본 대로 톰캣 스레드가 큰 파일 업로드에 몇 분씩 묶이는 일이 없어진다.

<br/><br/>

## 정적 웹 호스팅

```java
버킷을 웹사이트로 설정 -> index.html 을 서빙
```

<br/>

앞의 HTML, HTTP API, CSR, SSR 글에서 본 CSR 프론트엔드가 이렇게 배포된다.

빌드 결과물을 S3에 올리고, 앞에 앞의 CloudFront 글에서 본 CDN을 붙인다.

<br/>

앞의 탄력적 IP 글의 장애에서 화면이 멀쩡했던 이유가 이것이다. 정적 파일은 S3에서 왔다.

<br/><br/>

## 정리

```java
객체 스토리지  - 버킷 + 키. 폴더 없음. 통째로 올리고 받는다
서버와 분리    - 파일은 서버 밖에. 서버를 갈아치워도 남는다
기본 비공개    - 퍼블릭 액세스 차단은 끄지 않는다
presigned URL - 비공개 객체를 시간 제한으로 공유. 서명으로 위조 방지. 업로드도 직접 S3 로
```
