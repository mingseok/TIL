## 액세스 키를 코드에 넣지 않는 법 - IAM Role과 자격 증명 체인

<br/>

## 액세스 키란

IAM 사용자에게 발급하는 프로그램용 비밀번호다.

```java
액세스 키 ID     - AKIA 로 시작하는 20 자. 공개되어도 그 자체로는 못 쓴다
시크릿 액세스 키  - 40 자. 발급 때 한 번만 보여준다. 이것이 비밀
```

<br/>

이 둘이 있으면 그 사용자의 권한으로 AWS API를 전부 부를 수 있다.

<br/><br/>

## 실제로 겪은 일

운영 서버가 쓰던 액세스 키가 유출됐다.

<br/>

키가 코드나 설정 파일에 들어 있으면 그 파일이 어디로든 갈 수 있다.

```java
깃에 커밋된다        - 공개 저장소면 몇 분 안에 봇이 긁어간다
로그에 찍힌다
설정 파일이 백업된다
스크린샷에 찍힌다
```

<br/>

깃에 한 번 올라간 키는 지워도 히스토리에 남는다. `git rm` 으로 안 없어진다.

키 자체를 폐기하는 것 말고 방법이 없다.

<br/>

앞의 IAM 글에서 본 최소 권한이 여기서 중요했다. 그 키가 할 수 있는 것이 피해 범위다.

<br/><br/>

## 해결 : 키를 없앤다

IAM 역할로 바꿨다.

```java
전    - EC2 안의 설정 파일에 액세스 키. 코드가 그 키로 S3 를 부른다
후    - EC2 에 IAM 역할을 붙인다. 코드에 키가 없다
```

<br/>

코드는 한 줄도 안 바꿨다. 이게 가능한 이유가 자격 증명 체인이다.

<br/><br/>

## 자격 증명 체인

AWS SDK는 키를 어디서 찾을지 순서가 정해져 있다.

```java
1. 코드에 직접 넘긴 것
2. 환경 변수         (액세스 키 ID / 시크릿 키 환경 변수)
3. 시스템 프로퍼티    aws.accessKeyId
4. 프로필 파일       홈 디렉터리의 .aws 폴더 안 credentials 파일
5. 컨테이너 자격 증명 (ECS)
6. 인스턴스 메타데이터 (EC2 의 IAM 역할)    <- 169.254.169.254
```

<br/>

위에서부터 찾다가 처음 나오는 것을 쓴다.

`DefaultCredentialsProvider` 가 이 순서를 돈다.

<br/>

앞의 EC2 글에서 본 메타데이터 주소가 6번이다.

EC2에 역할이 붙어 있으면, 1~5에 아무것도 없을 때 SDK가 알아서 6번에서 임시 자격 증명을 받는다.

<br/>

그래서 설정 파일에서 키를 지우기만 하면 됐다. 1~5가 비면 6으로 간다.

<br/><br/>

## 환경마다 다른 곳에서 나온다

```java
내 컴퓨터    - 프로필 파일의 개발용 자격 증명 (4번)
CI          - 환경 변수로 주입 (2번)
EC2         - IAM 역할 (6번)
ECS / 람다   - 컨테이너 자격 증명 / 실행 역할
```

<br/>

코드는 같다. 어디서 도는지에 따라 다른 곳에서 키가 나온다.

<br/>

앞의 PSA(Portable Service Abstraction) 글에서 본 것과 같은 구조다.

`키를 어디서 가져오는가` 를 추상화해서, 코드가 환경을 몰라도 되게 한 것이다.

<br/><br/>

## 임시 자격 증명이 왜 안전한가

```java
역할의 자격 증명   - 1~12 시간 뒤 만료. SDK 가 자동으로 갱신
액세스 키         - 폐기하기 전까지 영구
```

<br/>

역할의 자격 증명이 새도 몇 시간이면 죽는다.

그리고 EC2 안에서만 받을 수 있으니, 밖으로 가져가려면 그 몇 시간 안에 써야 한다.

<br/>

앞의 EC2 글에서 본 대로 이 주소를 지키는 것이 IMDSv2다. 토큰을 먼저 받아야 메타데이터를 읽을 수 있게 해서, SSRF로 한 번에 못 빼가게 한다.

<br/><br/>

## 그래도 키가 필요한 곳

```java
내 컴퓨터에서 개발할 때
AWS 밖의 서버 (다른 클라우드, 온프레미스)
CI 서비스
```

<br/>

여기서는 역할을 붙일 EC2가 없다.

<br/>

```java
내 컴퓨터       - IAM Identity Center(SSO) 로그인. 브라우저로 로그인하면 임시 자격 증명을 받는다. 영구 키를 안 만든다
GitHub Actions - OIDC 로 역할을 맡는다. 시크릿에 키를 안 넣는다
그래도 키를 써야 하면 - 90 일마다 교체. 최소 권한. 절대 코드에 안 넣는다
```

<br/>

앞의 IAM 글에서 본 `루트는 키를 만들지 않는다` 와 같은 방향이다. 영구 키를 만드는 자리 자체를 줄인다.

<br/><br/>

## 유출됐을 때

```java
1. 그 키를 즉시 비활성화 (지우기 전에 비활성화. 무엇이 깨지는지 본다)
2. CloudTrail 에서 그 키로 무슨 일을 했는지 본다
3. 만들어진 자원(인스턴스, 사용자, 키)을 찾아 지운다
4. 새 키 대신 역할로 바꾼다
5. 키가 어디에 있었는지 찾아 그 경로를 막는다 (git 히스토리, 로그)
```

<br/>

`1번` 을 지우기가 아니라 비활성화로 하는 이유는 되돌릴 수 있기 때문이다.

그 키를 쓰는 것이 어디 있는지 모르는 상태에서 지우면 서비스가 멈추는데 원인을 못 찾는다.

<br/>

깃에 올라간 키는 `git-secrets`, `gitleaks` 같은 도구가 커밋 전에 잡아준다.

한 번 겪고 나면 이걸 훅으로 건다.

<br/><br/>

## 정리

```java
액세스 키는 영구 비밀번호. 파일에 있으면 어디로든 간다. 실제로 새봤다
EC2 는 IAM 역할. 코드에 키가 없어진다. 코드 수정 없이 전환된다
자격 증명 체인이 환경마다 다른 곳에서 키를 찾아준다
임시 자격 증명은 새도 몇 시간이면 죽는다
키가 꼭 필요한 곳도 SSO, OIDC 로 영구 키를 피한다
```
