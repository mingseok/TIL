## 보안 그룹과 NACL

<br/>

## 보안 그룹은 인스턴스의 방화벽이다

```java
인바운드 규칙   - 들어오는 것 중 무엇을 허용하나
아웃바운드 규칙 - 나가는 것 중 무엇을 허용하나
```

<br/>

```java
인바운드
  TCP 22    from 203.0.113.7/32        내 IP 에서만 SSH
  TCP 8080  from sg-alb                ALB 의 보안 그룹에서만 앱 포트
아웃바운드
  전부 허용 (기본값)
```

<br/>

허용 규칙만 적는다. 적지 않은 것은 전부 막힌다.

<br/><br/>

## 상태를 기억한다 (stateful)

인바운드로 들어온 요청의 응답은 아웃바운드 규칙과 상관없이 나간다.

반대도 같다. 아웃바운드로 나간 요청의 응답은 인바운드 규칙과 상관없이 들어온다.

```java
EC2 가 외부 API 를 부른다 (아웃바운드 허용)
-> 응답이 돌아온다. 인바운드에 그 포트를 안 열어도 들어온다
```

<br/>

연결을 기억하고 있어서 그렇다.

앞의 TCP 소켓 상태 글에서 본 연결 상태를 보안 그룹도 추적하는 것이다.

<br/>

그래서 아웃바운드는 대개 전부 열어두고 인바운드만 조인다.

<br/><br/>

## 출발지를 IP 가 아니라 보안 그룹으로

```java
TCP 3306  from sg-app        <- "sg-app 을 가진 인스턴스에서 오는 것만"
```

<br/>

RDS의 보안 그룹에 앱 서버의 IP를 적는 대신 앱 서버의 보안 그룹 ID를 적는다.

<br/>

앱 서버가 늘어나거나 IP가 바뀌어도 규칙을 안 고친다.

앞의 탄력적 IP 글에서 본 대로 EC2의 사설 IP도 재생성하면 바뀐다. IP로 적어두면 그때 깨진다.

<br/>

앱 서버 -> DB, ALB -> 앱 서버, 배스천 -> 앱 서버 전부 이 방식으로 엮는다.

<br/><br/>

## 자주 하는 실수

```java
22 를 0.0.0.0/0 에 연다       - 전 세계에서 SSH 시도가 들어온다. 몇 분 안에 로그에 찍힌다
3306 을 0.0.0.0/0 에 연다     - DB 가 인터넷에 노출. 비밀번호 대입 공격의 대상
전체 포트를 열어놓고 잊는다    - "테스트하느라 잠깐" 이 영구가 된다
```

<br/>

`0.0.0.0/0` 은 앞의 사설 IP, CIDR 글에서 본 대로 `누구나` 다.

<br/>

집 IP가 바뀌면 SSH가 안 되는 게 귀찮아서 `0.0.0.0/0` 으로 열게 된다.

대안이 있다.

```java
배스천 호스트를 거친다
Session Manager 를 쓴다 (22 번 포트 자체가 필요 없다)
```

<br/>

앞의 EC2 접속 - SSH와 키 페어 글에서 본다.

<br/><br/>

## NACL : 서브넷의 방화벽

Network ACL. 보안 그룹과 비슷한데 세 가지가 다르다.

```java
                보안 그룹              NACL
적용 단위        인스턴스               서브넷
허용/거부        허용만                 허용과 거부 둘 다
상태            기억한다(stateful)      기억 안 한다(stateless)
규칙 평가        전부 확인               번호 순서대로. 첫 번째 맞는 것으로 끝
```

<br/>

## stateless 가 왜 문제인가

응답 트래픽도 규칙에 맞아야 한다.

```java
인바운드 80 을 열었다
-> 응답이 아웃바운드로 나가는데, 클라이언트 포트는 임시 포트(1024~65535)
-> 아웃바운드에 1024~65535 를 안 열면 응답이 안 나간다
```

<br/>

앞의 파일 디스크립터 한계 글에서 본 임시 포트가 여기서 튀어나온다.

NACL을 건드릴 때 이걸 빠뜨려서 `요청은 들어오는데 응답이 안 간다` 가 생긴다.

<br/>

기본 NACL은 전부 허용이라 보통 안 건드린다.

특정 IP를 명시적으로 차단해야 할 때(공격 IP) 보안 그룹은 거부 규칙이 없으니 NACL을 쓴다.

<br/><br/>

## 순서

```java
패킷 -> NACL (서브넷 경계) -> 보안 그룹 (인스턴스) -> 서버
```

<br/>

둘 다 통과해야 한다.

`보안 그룹은 열었는데 안 되면` NACL을 본다. `NACL 은 기본값인데 안 되면` 보안 그룹을 본다.

<br/>

앞의 EC2에서 RDS 연결 확인 글에서 본 대로 `timed out` 이면 이 층 어딘가에서 막힌 것이다.

<br/><br/>

## 보안 그룹은 VPC 에 속한다

다른 VPC의 보안 그룹은 참조할 수 없다(피어링하면 가능).

보안 그룹을 만들 때 VPC를 고르는 이유다. 기본 VPC에 만들어놓고 새 VPC의 인스턴스에 붙이려면 안 나온다.

<br/><br/>

## 정리

```java
보안 그룹   - 인스턴스 방화벽. 허용만. 응답은 자동. 출발지를 보안 그룹으로 지정
NACL       - 서브넷 방화벽. 허용/거부. 응답도 규칙 필요. 차단이 필요할 때
실수       - 22, 3306 을 0.0.0.0/0 에. "잠깐" 이 영구가 된다
```
