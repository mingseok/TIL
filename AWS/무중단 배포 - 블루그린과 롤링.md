## 무중단 배포 - 블루그린과 롤링

<br/>

## 그냥 재시작하면 무슨 일이 생기나

```java
1. 옛 프로세스를 죽인다              - 이 순간부터 요청이 거부된다
2. 새 jar 로 프로세스를 띄운다        - 스프링 부트 기동 10~30 초
3. 준비될 때까지                     - 여전히 거부
```

<br/>

서버 한 대에 프로세스 하나면 배포마다 수십 초가 비는 것이다.

앞의 시그널과 graceful shutdown 글에서 본 대로 `1번` 에서 진행 중인 요청까지 끊긴다.

<br/>

무중단 배포는 `옛 것이 살아 있는 동안 새 것을 준비하고, 준비되면 바꾼다` 는 한 가지 생각이다. 어디서 바꾸느냐가 방식의 차이다.

<br/><br/>

## 롤링 배포

서버가 여러 대일 때 한 대씩 교체한다.

```java
ALB -> [A v1] [B v1] [C v1]
ALB -> [A 제외] [B v1] [C v1]      A 를 ALB 에서 뺀다
ALB -> [A v2] [B v1] [C v1]        A 에 새 버전. 헬스체크 통과하면 다시 넣는다
ALB -> [A v2] [B 제외] [C v1]      B 차례
...
```

<br/>

앞의 ALB 글에서 본 헬스체크가 `준비됐나` 를 판정한다.

<br/>

ALB에서 뺄 때 바로 끊지 않는다. `등록 취소 지연(deregistration delay)` 동안 새 요청은 안 보내고 진행 중인 것은 끝나길 기다린다. 기본 300초다.

앞의 시그널 글에서 본 graceful shutdown을 로드밸런서 쪽에서도 하는 것이다.

<br/>

서버가 늘어나지 않으니 비용이 안 든다. 대신 배포 중에 v1과 v2가 섞여 있는 시간이 길다.

<br/><br/>

## 블루그린 배포

환경을 두 벌 둔다.

```java
블루 (v1) <- 트래픽
그린 (v2)    새 버전을 띄우고 헬스체크까지 확인

블루 (v1)
그린 (v2) <- 트래픽      한 번에 전환

블루 (v1)    잠시 두고, 문제 없으면 내린다. 문제 있으면 다시 블루로
```

<br/>

전환이 한 순간이고, 롤백이 `다시 블루로` 한 번이다. 롤링은 롤백도 한 대씩이다.

<br/>

두 벌이라 서버가 두 배로 필요하다. 전환 뒤 옛 것을 내리면 되니 항상 두 배는 아니다.

<br/><br/>

## 서버 한 대에서도 된다

실제로 이렇게 하고 있다.

```java
같은 EC2 안에
  블루 프로세스  :8081   systemd 유닛 하나
  그린 프로세스  :8082   systemd 유닛 하나
앞에 nginx 나 ALB 가 둘 중 하나를 가리킨다
```

<br/>

```java
1. 지금 트래픽을 받는 쪽(블루)을 확인한다
2. 반대쪽(그린)에 새 jar 를 놓고 systemd 로 띄운다
3. 그린의 헬스체크 경로를 200 이 나올 때까지 찌른다
4. 앞단이 그린을 가리키게 바꾼다
5. 블루를 내린다
```

<br/>

이 스크립트가 `jar 만 교체` 한다는 것을 알아둬야 했다.

systemd 유닛 파일의 JVM 옵션은 스크립트가 안 건드린다. 앞의 자바 메모리 구조 글에서 본 힙 덤프 옵션을 유닛에 넣었더니, 배포를 거듭해도 그대로 남는다.

무엇이 배포마다 바뀌고 무엇이 남는지를 알아야 `설정을 바꿨는데 왜 안 적용되나` 를 안 겪는다.

<br/>

서버 한 대에 두 프로세스가 동시에 뜨는 순간이 있으니 메모리가 두 배 필요하다.

앞의 EC2 글에서 본 `t3.small` 2GB에 스프링 부트 두 개는 빠듯하다. 스왑을 두거나 힙을 제한한다.

<br/><br/>

## 카나리 배포

전체가 아니라 일부 사용자에게만 새 버전을 보낸다.

```java
v2 에 5%  -> 에러율, 응답 시간을 본다 -> 문제 없으면 50% -> 100%
```

<br/>

앞의 ALB 글에서 본 가중치 타겟 그룹이나 앞의 Route 53 글에서 본 가중치 라우팅으로 한다.

앞의 CloudWatch 글에서 본 지표가 없으면 카나리는 의미가 없다. `문제 없으면` 을 판정할 근거가 지표다.

<br/><br/>

## 공통 전제 : 두 버전이 동시에 돈다

어떤 방식이든 v1과 v2가 동시에 살아 있는 순간이 있다.

<br/>

## 상태를 서버 밖에

```java
세션      - 서버 메모리 X. Redis 나 토큰으로
업로드 파일 - 서버 디스크 X. S3 로
캐시      - 로컬 캐시면 v1 과 v2 가 다른 것을 본다
```

<br/>

앞의 S3 글과 앞의 ALB 글의 고정 세션에서 본 얘기가 여기서 모인다.

서버를 갈아치울 수 있어야 무중단 배포가 되고, 갈아치우려면 서버 안에 상태가 없어야 한다.

<br/>

## DB 스키마는 하위 호환으로

v2가 컬럼을 지우면 아직 돌고 있는 v1이 그 컬럼을 읽다 죽는다.

```java
컬럼 삭제
  1 차 배포 - 코드에서 그 컬럼을 안 쓰게만 바꾼다. 컬럼은 남긴다
  2 차 배포 - 컬럼을 지운다

컬럼 추가
  1 차 배포 - 컬럼을 추가한다 (nullable 또는 기본값). 코드는 아직 안 쓴다
  2 차 배포 - 코드가 쓴다

컬럼 이름 변경
  새 컬럼 추가 -> 양쪽에 쓰기 -> 옛 컬럼 읽기 중단 -> 옛 컬럼 삭제. 네 단계
```

<br/>

앞의 attribute data type 정의 글에서 본 `NOT NULL` 컬럼을 기본값 없이 추가하면 v1의 INSERT가 전부 실패한다.

<br/>

앞의 Flyway 같은 마이그레이션 도구가 스키마 변경을 코드와 함께 배포하는데, `한 번에 다 바꾸는` 마이그레이션을 쓰면 무중단이 깨진다.

<br/>

## API 도 하위 호환으로

v2가 응답 필드 이름을 바꾸면, v1을 기준으로 만든 프론트가 깨진다.

필드는 추가만 하고, 지우는 것은 프론트가 다 넘어간 뒤에 한다.

<br/><br/>

## 정리

```java
원리       - 옛 것이 살아 있는 동안 새 것을 준비하고 바꾼다
롤링       - 한 대씩. 서버 추가 없음. 섞인 시간이 길다
블루그린    - 두 벌. 한 번에 전환. 롤백 한 번. 서버 한 대에서도 포트 둘로 가능
카나리     - 일부만 먼저. 지표가 있어야 의미
전제       - 상태는 서버 밖에. 스키마와 API 는 하위 호환. 두 버전이 동시에 돈다
```
