## 테이블 작성

```sql
# 맴버 테이블
create table members (
    id          int auto_increment,
    login_id    varchar(10) not null,
    member_pwd  varchar(80) not null,
    member_name varchar(10) not null,
    email       varchar(50) not null,
    join_date   datetime    not null, -- 만든 날짜.
    primary key (id)

);

# 프로필
create table profile (
    id            int auto_increment primary key,
    member_id     int not null,
    bio           varchar(25),
    url           varchar(30),
    profile_image mediumblob,
    CONSTRAINT FOREIGN KEY (member_id) REFERENCES members (id) ON DELETE CASCADE
    -- ON DELETE CASCADE 옵션을 적용하면 부모 테이블에서 row 를 삭제할 경우
    -- 연결된 자식 테이블의 row 가 함께 삭제 된다.
    -- 즉, 연결된 데이터를 한 번에 지울 수 있다.
);

# 게시판 테이블
CREATE TABLE post (
    id           int auto_increment,
    title        varchar(30) not null,
    content      varchar(50) not null,
    writer       varchar(30) not null,
    created_date datetime    not null,
    hit          int default 0,
    heart        int default 0,
    primary key (id)

);

# 댓글 테이블
create table comment (
    id       int auto_increment,   -- 댓글 일련번호
    post_id  int         not null, -- 댓글이 속한 게시글의 고유 번호
    writer   varchar(30) not null, -- 댓글 작성자의 이름
    content  varchar(50) not null, -- 댓글 내용
    date     datetime    not null, -- 댓글 작성 날짜
    primary key (id)
);

# 좋아요 테이블
create table likes (
    id        int auto_increment not null primary key,
    member_id int                not null,
    post_id   int                not null,
    FOREIGN KEY (member_id) REFERENCES members (id),
    FOREIGN KEY (post_id) REFERENCES post (id)
);
```

<br/>

## 궁금증!

```java
ON DELETE CASCADE 가 실제로 어떻게 동작하는지 보자
```

같은 구조를 만들어놓고 회원을 지워봤다.

```sql
CREATE TABLE members (id INTEGER PRIMARY KEY AUTOINCREMENT, login_id TEXT NOT NULL, member_name TEXT NOT NULL);
CREATE TABLE profile (id INTEGER PRIMARY KEY AUTOINCREMENT, member_id INTEGER NOT NULL, bio TEXT,
   FOREIGN KEY (member_id) REFERENCES members(id) ON DELETE CASCADE);

INSERT INTO members (login_id, member_name) VALUES ('minseok','민석'), ('younghan','영한');
INSERT INTO profile (member_id, bio) VALUES (1,'안녕'), (2,'반가워');

DELETE FROM members WHERE id = 1;
```

<br/>

### 결과

```sql
삭제 전 profile 수 = 2
1번 회원 삭제 후 profile 수 = 1
```

<br/>

`profile` 은 건드리지도 않았는데 한 줄이 같이 사라졌다.

주석에 적어둔 그대로 동작한다.

<br/>

## 그런데 이게 항상 좋은 것은 아니다

회원 탈퇴 한 번에 그 사람이 쓴 게시글과 댓글까지 전부 사라지면 곤란한 경우가 많다.

```java
게시글이 사라지면 -> 그 글에 달린 남의 댓글도 같이 사라진다
좋아요가 사라지면 -> 다른 사람 글의 좋아요 수가 갑자기 줄어든다
```

<br/>

그래서 실무에서는 대개 `소프트 삭제` 를 쓴다.

```sql
UPDATE members SET deleted = true WHERE id = 1;
```

<br/>

실제로 지우지 않고 표시만 해두는 것이다.

앞의 B tree 데이터 삭제 방식 글에서 본 그 방식이다.

```java
CASCADE 가 맞는 것   - 그 회원 것이 확실하고 남기면 의미가 없는 데이터 (프로필, 설정)
소프트 삭제가 맞는 것 - 남과 얽혀 있는 데이터 (게시글, 댓글, 주문)
```

<br/>

## 좋아요 테이블에 빠진 것이 있다

이 스키마에서 실제로 걸리는 지점이다.

```sql
create table likes (
    id        int auto_increment not null primary key,
    member_id int                not null,
    post_id   int                not null,
    FOREIGN KEY (member_id) REFERENCES members (id),
    FOREIGN KEY (post_id) REFERENCES post (id)
);
```

<br/>

`한 사람이 한 글에 좋아요는 한 번만` 이라는 규칙이 어디에도 없다.

<br/>

같은 값을 세 번 넣어봤다.

```sql
INSERT INTO likes (member_id, post_id) VALUES (2, 1);
INSERT INTO likes (member_id, post_id) VALUES (2, 1);
INSERT INTO likes (member_id, post_id) VALUES (2, 1);
```

<br/>

### 결과

```sql
같은 사람이 같은 글에 누른 좋아요 = 3
화면에 표시될 좋아요 수 = 3
```

<br/>

한 사람이 눌렀는데 좋아요가 `3` 이 된다.

<br/>

## 코드로 막으면 되지 않나

```java
if (!likeRepository.exists(memberId, postId)) {
    likeRepository.save(...);
}
```

<br/>

이렇게 해도 뚫린다. 앞의 Isolation 비정상적인 현상 글에서 본 문제와 같은 모양이다.

```java
A 요청: 있나? -> 없다
B 요청: 있나? -> 없다      (A 가 아직 저장 전이다)
A 요청: 저장
B 요청: 저장               -> 두 개가 들어갔다
```

<br/>

사용자가 버튼을 빠르게 두 번 누르면 실제로 이렇게 된다.

<br/>

## DB 에 제약을 걸어야 확실하다

```sql
CREATE UNIQUE INDEX uk_likes ON likes(member_id, post_id);
```

<br/>

이제 두 번째 시도가 실패한다.

```sql
INSERT INTO likes (member_id, post_id) VALUES (2, 1);
-> Error: UNIQUE constraint failed: likes.member_id, likes.post_id
```

<br/>

앞의 relation database 글에서 본 `애플리케이션에서만 검사하면 뚫린다` 가 이 얘기다.

<br/>

그리고 이 인덱스는 조회에도 쓰인다.

`내가 이 글에 좋아요를 눌렀나` 를 확인하는 쿼리가 그대로 이 인덱스를 탄다.

```sql
SELECT * FROM likes WHERE member_id = ? AND post_id = ?;
```

<br/>

앞의 DB 인덱스 글에서 본 대로, `UNIQUE` 제약은 인덱스로 구현되니 두 가지를 한 번에 얻는 셈이다.

<br/>

## 타입을 몇 가지 더 보면

```sql
member_pwd  varchar(80)      -- BCrypt 해시가 60 자라 넉넉하다. 잘 잡았다
profile_image mediumblob     -- 이미지를 DB 에 넣는 방식이다
content     varchar(50)      -- 게시글 본문이 50 자다. 너무 짧다
```

<br/>

`content` 는 실제로 쓰다 보면 바로 부딪힌다. `TEXT` 로 두는 편이 낫다.

<br/>

`profile_image` 를 DB에 넣는 것도 다시 볼 만하다.

```java
DB 에 넣으면   - 백업이 한 번에 된다. 대신 DB 가 커지고 조회가 느려진다
파일로 두면    - DB 는 경로만 갖는다. 대신 파일과 DB 를 따로 관리해야 한다
```

<br/>

이미지가 많아지면 대개 파일이나 S3 같은 저장소로 옮기고 DB에는 URL만 둔다.

앞의 DB 인덱스 글에서 본 대로, 테이블이 커지면 인덱스도 커지고 전체가 느려지기 때문이다.
