## 여기서 질문) `Service` 의 역할은 뭔가?

```
‘비즈니스 도메인 객체를 가지고 핵심 비즈니스 로직 구현한 것’
```

이라고 나와 있지만, 무슨말인지 와닿지 않는다

<br/>

### 내가 정리한 결론은.

`컨트롤러`는 명령만 내리는 역할이고, 

그 명령을 `서비스`가 받아서 일을 처리하고
 
`레파지토리`로 넘겨주는 것이다 

<br/>


(중간에서 수정할걸 하고, 하는 중간 다리 역할이다) 

<br/>

즉, 서비스는 컨트롤러가 시키는 걸 다하며, 

컨트롤러와 DB 사이에서 일하는 ‘애’ 라고 생각할수 있을것 같다

<br/>

### 예를 들자면, 

컨트롤러가 서비스한테 `“회원 아이디, 비밀번호, 주소 디비에 저장해줘”` 하는 것이다. 

그러면 서비스는 회원 아이디, 비밀번호, 주소 를 받고, 주소를 가공적으로 바꾸고 

싶다면 서비스에서 바꿔 주고 DB에 저장하는 것이다.  

<br/>

그리고 `‘할인 정책’` 같은 로직들도 전부 서비스에서 하는 것이다. 

<br/><br/>

### 7. 서비스 로직은 이렇다.

주석으로 설명이 다 되어 있다.

```java
@Service
@Transactional
@RequiredArgsConstructor
@Slf4j
public class MemberService {

    private final MemberMapper memberMapper;

    public void joinMember(MemberDto memberDto) {

        // 여기서 현재시간으로 로직 수정 한것이다.
        memberDto.setJoinDate(LocalDateTime.now());
        
        log.info(memberDto.getUserId()); // alstjr706
        
        memberMapper.joinMember(memberDto); // 디비에 보내는 코드이다.
    }
}
```

### 8. MemberMapper 로 보내면 여기서 xml로 가게 되는 것이다.

이유는? 마이바티스는 메서드 이름으로 연결 되기 때문.

<br/><br/>

## 여기서 중요한점은 앞부분 void는 반환 값이라는 것이다.

만약 `int boardCount();` , `List<Board> getList();` 있다면 반환 값은 `int`형이고, `List`인 것이다.

```java
@Repository
public interface MemberMapper {
// void는 반환 값이다. 
    void joinMember(MemberDto memberDto);
}
```

<br/><br/>

### 9. xml 코드이다.
- 해당 `id="joinMember"` 으로 연결 되어 DB에 저장이 되는 것이다.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mapper
        PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">

<mapper namespace="com.project.facegram.mapper.MemberMapper">
    <insert id="joinMember" parameterType="com.project.facegram.dto.MemberDto">
        insert into members
        (login_id, member_pwd, member_name, email, join_date)
        values(#{loginId},#{memberPwd},#{memberName},#{email},#{joinDate});
    </insert>
</mapper>
```

## 궁금증!

```java
"new MemberDto() 를 만들어 html 로 보낸다" 는 게 왜 필요한 걸까?
```

타임리프의 `th:object` 가 그 빈 객체를 필요로 하기 때문이다.

```java
@GetMapping("/sign-up")
public String signUpForm(Model model) {
    model.addAttribute("memberDto", new MemberDto());   // 빈 그릇을 보낸다
    return "member/sign-up";
}
```

```html
<form th:object="${memberDto}" th:action method="post">
    <input type="text" th:field="*{loginId}">
</form>
```

<br/>

`th:field="*{loginId}"` 가 이 세 가지를 한 번에 만들어낸다.

```html
<input type="text" id="loginId" name="loginId" value="">
```

<br/>

`id`, `name`, `value` 를 자동으로 채워주는 것이다.

앞의 form 태그 글에서 본 대로 `name` 이 있어야 서버로 넘어가는데, 그걸 대신 적어주는 셈이다.

<br/>

## 그래서 빈 객체라도 있어야 한다

`model` 에 안 담으면 `th:object="${memberDto}"` 가 `null` 을 가리킨다.

```java
Neither BindingResult nor plain target object for bean name 'memberDto' available
```

<br/>

`th:field` 가 `memberDto` 의 필드 목록을 봐야 `name` 을 만들 수 있는데,

객체가 없으니 무엇을 만들지 알 수가 없는 것이다.

<br/>

## 수정 화면에서는 이게 더 큰 이득이 된다

등록 화면에서는 빈 그릇이라 티가 안 나는데, 수정 화면에서는 확실하다.

```java
@GetMapping("/edit")
public String editForm(Model model, @AuthenticationPrincipal User user) {
    model.addAttribute("memberDto", memberService.getMember(user.getUsername()));
    return "member/edit";
}
```

<br/>

같은 HTML을 그대로 쓰는데 입력창에 기존 값이 채워져 나온다.

`th:field` 가 `value` 를 객체에서 꺼내 넣기 때문이다.

<br/>

앞의 검증 - Form 전송 객체 분리 글에서 본 `등록과 수정 뷰를 합칠까` 라는 고민이 여기서 나온다.

<br/>

## 검증 실패했을 때가 진짜 이유다

앞의 Validation, @Validated 글에서 본 그 상황이다.

```java
@PostMapping("/sign-up")
public String signUp(@Validated @ModelAttribute MemberDto memberDto,
                     BindingResult bindingResult) {
    if (bindingResult.hasErrors()) {
        return "member/sign-up";      // 다시 그 화면
    }
}
```

<br/>

`@ModelAttribute` 를 쓰면 스프링이 자동으로 모델에 담아준다.

그래서 화면으로 되돌아갈 때 사용자가 입력했던 값이 그대로 남아 있다.

<br/>

이게 없으면 검증에 한 번 실패할 때마다 입력창이 전부 비워진다.

<br/>

그리고 `th:field` 는 오류가 있으면 `value` 를 객체가 아니라

앞의 Validation 글에서 본 `rejectedValue` 에서 꺼내온다.

숫자 칸에 글자를 넣어서 변환에 실패했어도 사용자가 친 그대로 다시 보여줄 수 있는 이유다.

<br/>

## Service 의 역할은 무엇인가

원문에서 던진 질문이다. 앞의 서비스 계층 글에서 본 답과 이어보면 이렇다.

```java
Controller - HTTP 를 자바로 번역한다. 파라미터를 받고, 결과를 모델에 담는다
Service    - 비즈니스 로직. HTTP 를 모른다
Mapper     - 데이터 접근. 비즈니스 로직을 모른다
```

<br/>

`joinMember()` 가 하는 일이 서비스에 있어야 하는 이유는 이렇다.

```java
public void joinMember(MemberDto dto) {
    if (memberMapper.findByLoginId(dto.getLoginId()) != null) {
        throw new IllegalStateException("이미 있는 아이디");   // 업무 규칙
    }
    dto.setMemberPwd(passwordEncoder.encode(dto.getMemberPwd()));  // 업무 규칙
    dto.setJoinDate(LocalDateTime.now());
    memberMapper.save(dto);
}
```

<br/>

`중복이면 안 된다`, `비밀번호는 해시로 저장한다` 는 것은 화면과 상관없는 규칙이다.

<br/>

이걸 컨트롤러에 두면 앞의 서비스 계층 글에서 본 문제가 생긴다.

테스트하려면 `HttpServletRequest` 를 흉내내야 하고, API를 추가하면 같은 코드를 또 써야 한다.

<br/>

## 서비스가 그냥 넘기기만 하면 문제다

반대로 이런 서비스는 있으나 마나다.

```java
public MemberDto getMember(String loginId) {
    return memberMapper.findByLoginId(loginId);     // 그냥 전달만 한다
}
```

<br/>

앞의 서비스 계층 글에서 본 대로, 이런 메서드만 잔뜩 있으면 로직이 다른 데 가 있다는 신호다.

<br/>

다만 이 프로젝트 규모에서는 그것도 괜찮다.

계층을 미리 만들어두면 나중에 로직이 생겼을 때 넣을 자리가 이미 있기 때문이다.
