## 로직 설명

```java
private static final String COMMENT_PATH = "posts/post-view :: #comment-list";

    @PostMapping("comment/save/{postId}")
    public String commentSave(@PathVariable int postId,
                              @RequestParam String comment,
                              @AuthenticationPrincipal User user,
                              Model model) {

        Post post = postService.getPost(postId);

        Member loginMember = memberService.getMember(user.getUsername());

        commentService.commentSave(comment, postId, user.getUsername());

        Profile profile = settingsService.getMemberProfile(loginMember.getId());

        List<Comment> comments = commentService.getCommentList(postId);

        model.addAttribute("profile", profile);
        model.addAttribute("comments", comments);
        model.addAttribute("member", loginMember);
        model.addAttribute("post", post);

        return COMMENT_PATH;
    }
```

마지막 줄 `return COMMENT_PATH;` 하게 되면 변수 안에 들어 있는 값으로 이동 하게 되는 것이다.

<br/>

첫번째. posts/post-view 페이지로 이동하게 되고

두번째. posts/post-view 페이지 안에서  comment-list (div) 태그로 가게 된다.

연결 되는 부분은 (div) 태그 안에 `id="comment-list"` 로 연결 되는 것이다.

## 궁금증!

```java
@Builder 를 붙이면 실제로 무엇이 만들어질까?
```

앞의 빌더 패턴 사용 이유 글에서 `javap` 로 확인한 결과다.

```java
@Builder
public class User {
    private String name;
    private int age;
    private String email;
}
```

```java
public class User {
  User(java.lang.String, int, java.lang.String);      // 모든 필드를 받는 생성자
  public static User$UserBuilder builder();
}

public class User$UserBuilder {
  public User$UserBuilder name(java.lang.String);
  public User$UserBuilder age(int);
  public User$UserBuilder email(java.lang.String);
  public User build();
}
```

<br/>

`User$UserBuilder` 라는 클래스가 하나 더 생긴다.

값을 받을 때마다 자기 자신을 돌려주니까 `.name().age()` 처럼 이어 쓸 수 있는 것이다.

<br/>

## 그런데 빌더에는 약점이 있다

필수값을 강제할 수 없다. 직접 확인해봤다.

```java
User user = User.builder()
        .age(27)                // name 과 email 을 빼먹었다
        .build();
```

```java
name 없이도 만들어졌다 -> User@14dad5dc
```

<br/>

컴파일도 되고 실행도 된다.

<br/>

`CommentDto` 로 바꿔 보면 이런 일이 생긴다.

```java
CommentDto dto = CommentDto.builder()
        .content("댓글입니다")
        .build();               // postId 와 writer 를 빼먹었다
```

<br/>

`postId` 가 `0` 이고 `writer` 가 `null` 인 채로 저장이 시도된다.

DB의 `not null` 제약에서 걸리면 다행이고, 안 걸리면 이상한 데이터가 들어간다.

<br/>

## 생성자에 붙이면 검증할 자리가 생긴다

```java
public class CommentDto {
    private final int postId;
    private final String writer;
    private final String content;
    private final LocalDateTime date;

    @Builder
    private CommentDto(int postId, String writer, String content) {
        if (writer == null || writer.isBlank()) {
            throw new IllegalArgumentException("작성자는 필수입니다");
        }
        this.postId = postId;
        this.writer = writer;
        this.content = content;
        this.date = LocalDateTime.now();
    }
}
```

<br/>

생성자를 `private` 으로 막아두면 빌더로만 만들 수 있게 되어, 검증을 우회할 수 없다.

<br/>

`date` 를 생성자 안에서 채운 것도 포인트다.

빌더 파라미터에서 빼두면 밖에서 엉뚱한 시각을 넣을 수가 없다.

<br/>

## @Data 와 @Builder 를 같이 쓴 것

```java
@Data
@NoArgsConstructor @AllArgsConstructor
@Builder
public class CommentDto { ... }
```

<br/>

넷을 다 붙이면 만드는 방법이 세 가지가 된다.

```java
new CommentDto()                         // 빈 객체 + setter
new CommentDto(1, 1, "민석", "안녕", now)  // 순서대로
CommentDto.builder()...build()           // 빌더
```

<br/>

세 가지가 다 열려 있으면 어느 것을 써야 하는지 코드만 봐서는 알 수 없다.

<br/>

그리고 `@Data` 의 `setter` 때문에 빌더로 만든 뒤에도 값을 바꿀 수 있다.

앞의 프로필, 프로필 수정 글에서 본 그 문제다.

<br/>

## 그런데 프레임워크가 기본 생성자를 필요로 한다

앞의 생성자를 왜 만들어야 하나요 글에서 본 그 이유다.

```java
MyBatis 가 resultType 으로 객체를 만들 때 -> 기본 생성자 + setter
Jackson 이 JSON 을 객체로 바꿀 때        -> 기본 생성자 + setter
```

<br/>

그래서 완전히 불변으로 만들면 프레임워크가 못 만든다.

<br/>

절충안은 이렇다.

```java
@Getter
@NoArgsConstructor(access = AccessLevel.PRIVATE)     // 프레임워크만 쓸 수 있게
public class CommentDto {

    private int postId;
    private String writer;
    private String content;

    @Builder
    private CommentDto(int postId, String writer, String content) { ... }
}
```

<br/>

앞의 생성자를 왜 만들어야 하나요 글에서 본 `@NoArgsConstructor(access = PROTECTED)` 와 같은 발상이다.

프레임워크는 리플렉션으로 접근하니 `private` 이어도 쓸 수 있고, 개발자는 실수로 못 부른다.

<br/>

## MyBatis 는 setter 없이도 될 수 있다

생성자로 채우게 설정할 수 있다.

```xml
<resultMap id="commentMap" type="CommentDto">
    <constructor>
        <arg column="post_id" javaType="int"/>
        <arg column="writer" javaType="String"/>
        <arg column="content" javaType="String"/>
    </constructor>
</resultMap>
```

<br/>

이러면 `setter` 없이 불변 객체로 받을 수 있다.

앞의 MyBatis 적용 글에서 본 `resultType` 대신 `resultMap` 을 쓰는 방식이다.

적기가 번거로워서 잘 안 쓰지만, 불변을 지키고 싶다면 이 방법이 있다.
