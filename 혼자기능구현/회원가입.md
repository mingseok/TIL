     id          int auto_increment,
     login_id    varchar(10) not null,

     member_name varchar(10) not null,
     email       varchar(50) not null,

    private final MemberService memberService;

    @GetMapping("/main")
    public String main() {
        return "members/main";
    }

    @GetMapping("/sign-up")
    public String signup(Model model) {
        model.addAttribute("memberDto", new MemberDto());
        return "members/sign-up";
    }

    @PostMapping("/sign-up")
    public String signUp(@ModelAttribute MemberDto memberDto) {
    
        // @ModelAttribute 를 이용하여 html에 있는 MemberDto를 사용하는 것이다.
        memberService.joinMember(memberDto);
        return "redirect:/";
    }
}

## 첫번째) 아이디 중복 검사

```java
if (memberMapper.findByLoginId(loginId) != null) {
    throw new IllegalStateException("이미 있는 아이디");
}
memberMapper.save(member);
```

<br/>

앞의 좋아요 글과 조회수 글에서 본 것과 똑같은 구조다.

```java
A: 있나? -> 없다
B: 있나? -> 없다
A: 저장
B: 저장          -> 같은 아이디가 두 개 들어갔다
```

<br/>

`members` 테이블의 `login_id` 에 `UNIQUE` 가 없어서 실제로 들어간다.

```sql
CREATE UNIQUE INDEX uk_members_login_id ON members(login_id);
```

<br/>

앞의 relation database 글에서 본 대로, 이걸 걸어야 확실하다.

그리고 이 인덱스는 로그인할 때 아이디로 찾는 쿼리에도 그대로 쓰인다.

<br/>

## 두번째) 비밀번호를 그대로 저장하면 안 된다

```sql
member_pwd  varchar(80) not null
```

<br/>

`80` 자로 잡은 것을 보면 해시를 염두에 둔 것으로 보인다.

`BCrypt` 해시가 `60` 자라 딱 맞는다.

<br/>

앞의 로그인, 시큐리티 글에서 본 `PasswordEncoder` 가 그 일을 한다.

```java
member.setMemberPwd(passwordEncoder.encode(rawPassword));
```

<br/>

해시는 되돌릴 수 없어서, DB가 통째로 유출돼도 비밀번호 자체는 안 드러난다.

<br/>

여기서 `MD5` 나 `SHA-256` 을 쓰면 안 된다.

그것들은 너무 빨라서, 공격자가 초당 수십억 번 대입할 수 있다.

<br/>

`BCrypt` 는 일부러 느리게 만든 것이다.

한 번 계산하는 데 수십 밀리초가 걸리게 해서 대입 공격을 어렵게 만든다.

<br/>

## 세번째) 검증을 어디서 할 것인가

```java
@PostMapping("/sign-up")
public String signUp(MemberDto memberDto) {
    memberService.joinMember(memberDto);
    return "redirect:/login";
}
```

<br/>

`memberDto` 에 아무 값이나 들어와도 그대로 저장된다.

<br/>

앞의 Bean Validation 글에서 본 대로 어노테이션으로 막을 수 있다.

```java
public class MemberDto {

    @NotBlank(message = "아이디는 필수입니다")
    @Size(min = 4, max = 10)
    private String loginId;

    @NotBlank
    @Size(min = 8, message = "비밀번호는 8자 이상이어야 합니다")
    private String memberPwd;

    @NotBlank
    @Email
    private String email;
}
```

```java
@PostMapping("/sign-up")
public String signUp(@Validated MemberDto memberDto, BindingResult bindingResult) {
    if (bindingResult.hasErrors()) {
        return "member/sign-up";       // 입력 화면으로 되돌린다
    }
    ...
}
```

<br/>

앞의 Validation, @Validated 글에서 본 대로 `BindingResult` 를 받아야 화면으로 되돌릴 수 있다.

안 받으면 `400` 오류 페이지로 넘어간다.

<br/>

`@Size(max = 10)` 을 안 걸면 `varchar(10)` 컬럼에 넘치는 값이 들어가서 DB에서 에러가 난다.

앞의 attribute data type 글에서 본 것처럼, 컬럼 길이와 검증 규칙을 맞춰두는 편이 낫다.

<br/>

## 네번째) 회원가입 후 리다이렉트

```java
return "redirect:/login";
```

<br/>

앞의 PRG 글에서 본 그 패턴이다. 잘 되어 있다.

<br/>

이걸 안 하고 화면을 바로 그려주면, 새로고침할 때 가입이 또 시도된다.

`UNIQUE` 제약이 있으면 실패하니 데이터는 안 망가지지만, 사용자에게 에러 화면이 뜬다.

<br/>

## 다섯번째) join_date 를 누가 넣는가

```sql
join_date   datetime    not null
```

<br/>

`NOT NULL` 이라 반드시 값이 있어야 하는데, 자바에서 넣으면 서버 시각을 쓴다.

<br/>

서버가 여러 대이고 시간대 설정이 다르면 값이 어긋난다.

앞의 attribute data type 글에서 본 그 문제다.

<br/>

DB가 넣게 두면 항상 같은 기준이 된다.

```sql
join_date datetime NOT NULL DEFAULT CURRENT_TIMESTAMP
```

<br/>

또는 JPA를 쓴다면 `@CreatedDate` 로 프레임워크에 맡길 수 있다.

어느 쪽이든 `사람이 직접 안 넣는` 것이 실수를 줄인다.
