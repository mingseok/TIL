```java

```


게시판에 해당 번호인 `3번` 게시물을 들어가면

`3번`에 해당하는 `url` 주소를 타고 `3번` 게시물을 들어 갈 수 있다는 것

<br/>

다시 말해, 나는 `post-view.html`만 만들었지 

`post-view3.html` 이런 `html` 파일은  만들지 않았다는 점이다. 

<br/>

어떻게 저 url이 페이지 이동이 가능 한거지??

<br/><br/>

## 이유는

`model.addAttribute("post", postService.getPost(id));` 코드로

html 껍대기만 만들어 놓고 3번에 관한 

이름, 글, 조회수 등은 디비에서 꺼내 가져오는 것이다. 

<br/>


다시 말해,  글을 등록할때 번호 3을 저장 해놓고, 

필요한 순간 번호 3을 이용하여 나머지 이름, 글, 조회수 등의 

객체(열)을/를 가져와 html 껍대기에 이름, 글, 조회수 같은걸 뿌려주는 것이 였다.

## @RequestParam 과 @PathVariable 차이

둘 다 데이터를 받아오는 데에 사용한다

`@PathVariable`은 값을 하나만 받아올 수 있으므로, 

쿼리스트링 등을 이용한 여러 개 데이터를 받아올 때는 `@RequestParam`을 쓴다


<br/>




### @RequestParam 흐름

```html
<td>
   <a th:href="@{/view(id=${list.id})}">
       [[${list.title}]]
   </a>
</td>
```

<br/>

```java
// 게시판 상세 보기
@GetMapping("/post-view")
public String viewPost(Model model, @RequestParam int id) {
      model.addAttribute("post", postService.getPost(id));
      return "posts/post-view";
}

// 이렇게도 가능하다.
@GetMapping("/post-view")
public String viewPost(Model model, int id) {
      model.addAttribute("post", postService.getPost(id));
      return "posts/post-view";
}
```

<br/>

```java
@GetMapping("/login")
public String login(@RequestParam(required = false, value = "error") String error,
                    @RequestParam(required = false, value = "exception") String exception, Model model)        {

    model.addAttribute("error", error);
    model.addAttribute("exception", exception);

    return "/members/login";
}
```

<br/>

## 궁금증!

```java
"html 껍데기 하나로 3번 글도 5번 글도 보여준다" 는 것을 다시 정리해보면
```

앞의 MVC 요청 처리 내부 동작 글에서 본 그 구조가 바로 이것이다.

```java
(V) 뷰   - post-view.html 하나. 껍데기만 있다
(M) 모델 - 3번 글의 내용. 요청마다 다르다
(C) 컨트롤러 - id 를 받아서 조회하고 모델에 담는다
```

<br/>

```java
@GetMapping("/post-view")
public String postView(Model model, int id) {
    model.addAttribute("post", postService.getPost(id));
    return "posts/post-view";
}
```

<br/>

`return "posts/post-view"` 는 뷰 이름이다. 앞의 뷰 리졸버 글에서 본 논리 이름이다.

`id` 가 무엇이든 뷰 이름은 항상 같고, 모델에 담기는 내용만 달라진다.

<br/>

`post-view3.html` 을 안 만들어도 되는 이유가 이 분리 덕분이다.

<br/>

## URL 의 id 가 컨트롤러 파라미터로 들어오는 것

```java
http://localhost:8080/post-view?id=3
```

<br/>

앞의 요청 매핑 헨들러 어뎁터 글에서 본 `ArgumentResolver` 가 이 일을 한다.

```java
RequestParamMethodArgumentResolver 가
  "int id 라는 파라미터가 있네"
  -> 쿼리 스트링에서 id 를 찾는다 -> "3"
  -> 앞의 스프링 타입 컨버터 글에서 본 대로 int 로 바꾼다 -> 3
  -> 컨트롤러에 넘긴다
```

<br/>

`@RequestParam` 을 안 적어도 되는 이유도 앞의 `@RequestBody, @RequestParam` 글에 있다.

`int` 같은 단순 타입이면 스프링이 `@RequestParam` 으로 보기 때문이다.

<br/>

## 로그인한 사용자를 가져오는 방법

원문에서 `히든을 써야 되는가` 를 고민한 부분이 중요한 지점이다.

```html
<input type="hidden" name="writer" th:value="${loginId}">
```

<br/>

이렇게 하면 안 된다. 앞의 클라이언트 서버 구조 글에서 본 이유다.

<br/>

브라우저 개발자 도구로 `writer` 값을 남의 아이디로 바꿔서 보낼 수 있다.

그러면 남의 이름으로 글이 등록된다.

```java
클라이언트가 보내도 되는 것 - 제목, 내용
서버가 정해야 하는 것      - 누가 썼는지
```

<br/>

그래서 `@AuthenticationPrincipal` 로 서버가 직접 꺼내는 것이 맞다.

```java
@PostMapping("/new-post")
public String savePost(BoardDto boardDto, @AuthenticationPrincipal User user) {
    boardService.savePost(boardDto, user.getUsername());
    return "redirect:/post";
}
```

<br/>

이 값은 세션에서 나오는 것이라 클라이언트가 조작할 수 없다.

앞의 로그인 쿠키, 세션 글에서 본 대로, 쿠키에는 세션 ID만 있고 실제 정보는 서버가 들고 있다.

<br/>

## @AuthenticationPrincipal 도 ArgumentResolver 다

```java
AuthenticationPrincipalArgumentResolver
```

<br/>

스프링 시큐리티가 등록해두는 리졸버다.

앞의 로그인 쿠키, 세션 글에서 `직접 만들 수도 있다` 고 한 그 자리에 시큐리티가 미리 하나 끼워둔 것이다.

<br/>

## return "redirect:/post" 를 쓴 것

앞의 PRG 글에서 본 그 패턴이다.

```java
POST /new-post  -> 저장 -> 302 + Location: /post
GET /post       -> 목록 화면
```

<br/>

이걸 안 하고 목록 화면을 바로 그려주면, 사용자가 새로고침할 때 글이 또 등록된다.

<br/>

앞의 리다이렉트 글에서 실제 응답을 찍어봤을 때 확인한 그 동작이다.

```java
HTTP/1.1 302 Temporary Redirect
Location: /post
```

<br/>

브라우저가 이걸 받으면 메서드를 `GET` 으로 바꿔서 다시 요청하니, 새로고침해도 조회만 다시 된다.
