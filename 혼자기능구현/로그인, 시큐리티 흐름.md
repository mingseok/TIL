## 상황을 만들어 보겠다.

### 처음 한번은 무조건 저 메서드로 들어간다.

왜?? 메서드 매핑이 `@GetMapping("/login")` 이기 때문이다.

## 로그인 할때 id와 pwd가 틀린거 없이 잘 동작 했다면?

에러가 없으면 시큐리가 `html` 에서 바로 다음 화면으로 넘겨주는 것이다. 

하지만 `form` 태그가 있는거 같은데… 어떻게?

```html
<form class="needs-validation col-sm-6" action="#" th:action="@{/login}" 
			method="post" novalidate>
```

<br/>

`method="post"` 로 보내는게 있는데, 이건 시큐리티가 다 알아서 만들어서 밑에 사진처럼 동작하게 도와 주는 것이다.

![이미지](/programming/img/회원가입설명9.PNG)

`defaultSuccessUrl(”/”)` 메서드에 의해 [localhost:8080](http://localhost:8080) 으로 이동하게 되는 것이다.

<br/><br/>

## 만약, 로그인 할때 아이디와 비밀번호를 틀리게 작성 하였다면?

![이미지](/programming/img/회원가입설명10.PNG)

다시 말하지만 맨 처음 첫번째 일때는 `login.html` 로 아무 에러도 없이 이동한다.

그리고 시큐리티가 아이디와 비밀번호 둘 중 틀렸다고 한다면, 

다시 `form` 태그를 이용해 아까 왔던 `@GetMapping("/login")` 로 되돌아 가는 것이다.

<br/><br/>

## 그런데 궁금증이 있다.

### 왜?? `post` 인데 `get` 매핑으로 가는가?

이건 시큐리티가 다시 리턴 시켜주기 때문이다.

```html
<form class="needs-validation col-sm-6" 
			action="#" th:action="@{/login}" 
			method="post" novalidate>
```

<br/>

다시 여기로 리턴 되는 것이다.

```java
@GetMapping("/login")
public String login(@RequestParam(required = false, value = "error") String error,
                    @RequestParam(required = false, value = "exception") String exception, Model model)        {

        model.addAttribute("error", error);
        model.addAttribute("exception", exception);

        return "/members/login";
    }
```

<br/>

에러가 발생하면 여기 html 코드를 실행 시키는 것이다.

if문 사용. 만약 에러가 발생하지 않았다면 그냥 없는 코드 취급을 해버리는 것이다.

```html
<div th:if="${param.error}" class="alert alert-danger" role="alert" style="width: 1000px">
    <p><span th:text="${exception}">예외메시지</span></p>
    <p>
       비밀번호를 잊으셨다면, <a href="#" th:href="@{/find-password}">패스워드 찾기</a>를 이용해주세요.
    </p>
</div>
```

<br/><br/>

## 추가로

`resources` → `templates` → `membsrs` → `fragments.html` 에 보면 로그아웃 부분이 있다.

내가 로그아웃 로직을 만들지 않아도 시큐리티가 알아서 로그아웃 로직을 만들어 주는 것이다.

즉, 알아서 `post` 매핑해주고 알아서 다 해주는 것이다.

```html
<form class="form-inline my-2 my-lg-0" action="#" th:action="@{/logout}" method="post">
      <button class="dropdown-item" type="submit">로그아웃</button>
</form>
```

## 궁금증!

```java
로그인 실패했을 때 다시 로그인 화면이 뜨는 흐름을 정리하면
```

시큐리티가 리다이렉트를 쓴다. 앞의 리다이렉트 글에서 본 그 방식이다.

```java
1. POST /login (아이디, 비밀번호)
2. 시큐리티 필터가 인증을 시도한다 -> 실패
3. 302 + Location: /login?error   를 응답한다
4. 브라우저가 GET /login?error 로 다시 요청한다
5. 컨트롤러의 @GetMapping("/login") 이 실행된다
```

<br/>

원문의 `처음 한번은 무조건 저 메서드로 들어간다` 와 `실패해도 그리로 온다` 가

사실은 같은 `GET /login` 인데 쿼리 스트링만 다른 것이다.

```java
GET /login          -> 처음 진입
GET /login?error    -> 실패해서 되돌아옴
GET /login?logout   -> 로그아웃 후
```

<br/>

그래서 `@RequestParam(required = false)` 로 받는 것이다.

```java
@GetMapping("/login")
public String login(@RequestParam(required = false) String error, Model model) {
    if (error != null) {
        model.addAttribute("errorMessage", "아이디 또는 비밀번호가 올바르지 않습니다");
    }
    return "member/login";
}
```

<br/>

`required = false` 가 없으면 처음 진입할 때 `error` 파라미터가 없어서 `400` 이 난다.

<br/>

## 왜 리다이렉트를 쓰는가

앞의 PRG 글에서 본 그 이유다.

```java
POST 응답으로 바로 화면을 그리면
-> 사용자가 새로고침할 때 POST /login 이 다시 간다
-> 로그인 시도가 또 일어난다
```

<br/>

로그인은 몇 번 실패하면 계정을 잠그는 경우가 있으니, 이게 실제로 문제가 된다.

<br/>

## 왜 "아이디가 틀렸다" 고 안 알려주는가

원문의 `궁금증이 있다` 부분에 이어지는 답이다.

```java
"아이디가 없습니다"        -> 그 아이디가 없다는 사실이 알려진다
"비밀번호가 틀렸습니다"    -> 그 아이디는 있다는 사실이 알려진다
```

<br/>

아이디를 하나씩 넣어보면 가입된 아이디 목록을 알아낼 수 있다.

앞의 HTTP 상태코드 (4xx, 5xx) 글에서 본 `404 와 403 사이의 판단` 과 같은 얘기다.

<br/>

그래서 둘 다 같은 메시지를 준다.

```java
"아이디 또는 비밀번호가 올바르지 않습니다"
```

<br/>

시큐리티가 기본적으로 이렇게 동작한다.

`UsernameNotFoundException` 을 `BadCredentialsException` 으로 바꿔서 던지기 때문이다.

<br/>

```java
security.authentication.hide-user-not-found-exceptions=false
```

이 설정을 끄면 구분이 되는데, 그러면 위 문제가 생긴다.

<br/>

## 인증과 인가는 다르다

앞의 HTTP 상태코드 (4xx, 5xx) 글에서 본 `401 과 403` 이 이 구분이다.

```java
인증 (Authentication) - 네가 누구인지 확인한다 -> 로그인
인가 (Authorization)  - 그 사람이 이걸 할 수 있는지 본다 -> 권한
```

<br/>

시큐리티 설정에서도 담당하는 필터가 다르다.

```java
UsernamePasswordAuthenticationFilter  - 인증. 로그인 요청을 처리한다
FilterSecurityInterceptor             - 인가. 경로별 권한을 확인한다
```

<br/>

로그인은 됐는데 `403` 이 뜬다면 인가 쪽 설정을 봐야 한다.

<br/>

## 로그인 성공 후 어디로 갈까

```java
.defaultSuccessUrl("/post")
```

<br/>

이렇게만 두면 항상 `/post` 로 간다.

그런데 사용자가 원래 보려던 페이지가 따로 있었다면 그리로 돌려보내는 편이 낫다.

<br/>

시큐리티는 이걸 기억해둔다.

```java
1. 로그인 안 한 상태로 /post-view?id=3 접근
2. 시큐리티가 그 주소를 세션에 저장하고 /login 으로 보낸다
3. 로그인 성공
4. 저장해둔 /post-view?id=3 으로 돌려보낸다
```

<br/>

`defaultSuccessUrl("/post", false)` 처럼 두 번째 인자를 `false` 로 두면 이 동작이 살아난다.

`true` 로 두면 저장해둔 것을 무시하고 항상 `/post` 로 간다.

<br/>

앞의 로그인 쿠키, 세션 글에서 본 대로 이 저장도 세션에 들어간다.

세션이 상태라는 것이 여기서도 드러난다.
