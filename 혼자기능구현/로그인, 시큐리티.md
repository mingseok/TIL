## SpringSecurityConfig 클래스

```java
@Configuration
@EnableWebSecurity
public class SpringSecurityConfig extends WebSecurityConfigurerAdapter {

    // 이미지 부분
    @Override
    public void configure(WebSecurity web) throws Exception {
        web.ignoring() //보안필터를 적용할 필요가 없는 리소스 설정
                .requestMatchers(PathRequest.toStaticResources().atCommonLocations())
                .mvcMatchers("/image/**");
    }

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.authorizeRequests()
                .mvcMatchers("/", "/sign-up", "/login") // 보안 필터가 필요없는 경로 (=모든사람이 들어갈수 있는 곳)
                .permitAll();

        http.formLogin() // 로그인 인증 기능
                .loginPage("/login") // 내가 만든 로그인 페이지를 사용하겠다고 하는 것이다.
                .defaultSuccessUrl("/")
                .permitAll(); // 허가 한다 할때.
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
	// 비밀번호를 암호화 알아서 해준다.
        return PasswordEncoderFactories.createDelegatingPasswordEncoder(); 
    }
}
```

<br/>

## 설명

- `mvcMatchers("/", "/sign-up", "/login")`
    - 보안 필터가 필요 없는 경로, 모든 사람이 들어갈 수 있는 곳
    - `mvcMatchers()` 에 등록하지 않으면 시큐리티 로그인 창이 출력 된다.
        
        `메인 페이지`, `회원가입 페이지`, `로그인 페이지` 같은 곳에서 로그인 하라는 창이 뜨면 안된다. 

### 이유는?
        
사용자가 매우 불편하다. 


그렇기 때문에 `mvcMatchers()` 메서드를 사용하여 보안 필터가 필요 없는 경로를 지정해주는 것이다.

<br/>

- `permitAll()` : 허가 한다는 메서드이다.

- `loginPage("/login")` : 이렇게 등록하지 않으면 시큐리티가 자기가 직접 만든 로그인 화면을 보여주는 것이다.
    
- `defaultSuccessUrl("/")` : 로그인 성공 했을때 이동하는 url 이다.

## service 패키지 → MemberService 클래스 추가, 수정.

```java
@Service
@Transactional
@RequiredArgsConstructor
@Slf4j
public class MemberService implements UserDetailsService { // 시큐리티 사용하기 위한 인터페이스

    private final MemberMapper memberMapper;
    private final PasswordEncoder passwordEncoder;

    public void joinMember(MemberDto memberDto) {

        // 여기서 현재시간으로 로직 수정 한것이다.
        memberDto.setJoinDate(LocalDateTime.now());
        memberDto.setMemberPwd(passwordEncoder.encode(memberDto.getMemberPwd()));

        log.info(memberDto.getLoginId()); // alstjr706

        memberMapper.joinMember(memberDto); // 디비에 보내는 코드이다.
    }

    // 시큐리티 인터페이스 메서드
    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
    //username 매개변수가 디비에 있는 login_id 이다.

        // 여기는 디비에서 데이터를 찾고 온 값을 여기에 저장하는 것이다.
        Member member = memberMapper.getMember(username); // 로그인 아이디로 member를 찾음

        if (member == null) {
            throw new UsernameNotFoundException(username);
        }

        return User.builder()
                .username(member.getLoginId())
                .password(member.getMemberPwd())
                .roles("USER")
                .build();
    }
}
```

## 궁금증!

```java
"비밀번호를 알아서 uuid 로 만들어준다" 는 게 정확히 무슨 일일까?
```

`UUID` 가 아니라 `해시` 다. 둘은 다르다.

```java
UUID - 무작위로 만든 고유한 식별자. 입력과 아무 관계가 없다
해시 - 입력을 계산해서 만든 값. 같은 입력이면 항상 같은 값이 나온다
```

<br/>

비밀번호는 해시여야 한다. `UUID` 라면 로그인할 때 비교할 방법이 없다.

<br/>

```java
저장할 때 : encode("1234")  -> $2a$10$N9qo8uLOickgx2ZMRZoMye...
로그인할 때 : matches("1234", 저장된값) -> true
```

<br/>

## 그런데 BCrypt 는 같은 입력에 다른 값이 나온다

이게 헷갈리는 부분이다.

```java
encode("1234")  -> $2a$10$N9qo8uLOickgx2ZMRZoMye...
encode("1234")  -> $2a$10$abcdefghijklmnopqrstuv...     같은 비밀번호인데 다르다
```

<br/>

매번 무작위 값을 하나 섞어서 계산하기 때문이다. 이것을 `솔트(salt)` 라고 한다.

<br/>

그러면 어떻게 비교하느냐 하면, 그 솔트가 결과 문자열 안에 같이 들어 있다.

```java
$2a$10$N9qo8uLOickgx2ZMRZoMye...
 ^^  ^^ ^^^^^^^^^^^^^^^^^^^^^^
 |   |         |
 |   |         +-- 솔트 + 해시값
 |   +-- 반복 횟수 (2^10 = 1024 번)
 +-- 알고리즘 버전
```

<br/>

`matches()` 는 저장된 값에서 솔트를 꺼내서, 그 솔트로 입력을 다시 계산해서 비교한다.

<br/>

## 솔트가 왜 필요한가

솔트가 없으면 같은 비밀번호는 같은 해시가 된다.

```java
회원 A 의 해시 = 5f4dcc3b5aa765d61d8327deb882cf99
회원 B 의 해시 = 5f4dcc3b5aa765d61d8327deb882cf99     -> 둘이 같은 비밀번호를 쓴다
```

<br/>

DB가 유출되면 이 사실이 그대로 드러난다.

그리고 자주 쓰는 비밀번호의 해시를 미리 계산해둔 표로 한꺼번에 뚫린다.

<br/>

솔트가 있으면 같은 비밀번호라도 해시가 전부 달라진다.

미리 만들어둔 표가 쓸모없어지고, 한 명씩 따로 공격해야 한다.

<br/>

## 반복 횟수가 성능에 영향을 준다

`$2a$10$` 의 `10` 이 `2^10 = 1024` 번 반복한다는 뜻이다.

```java
new BCryptPasswordEncoder();      // 기본 10
new BCryptPasswordEncoder(12);    // 4096 번. 4 배 느리다
```

<br/>

일부러 느리게 만드는 것이 목적이다. 앞의 회원가입 글에서 본 그 이유다.

<br/>

다만 로그인할 때마다 이 계산이 도니, 너무 높이면 서버가 힘들어진다.

`한 번 계산에 100ms 정도` 가 되도록 맞추라고 권한다.

<br/>

## 시큐리티 설정에서 봐야 할 것

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

<br/>

앞의 스프링에서 빈을 등록하는 방법 글에서 본 `@Bean` 방식이다.

`BCryptPasswordEncoder` 는 남이 만든 클래스라 `@Component` 를 붙일 수 없다.

<br/>

요즘은 이걸 더 권한다.

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();
}
```

<br/>

이러면 저장된 값 앞에 알고리즘 이름이 붙는다.

```java
{bcrypt}$2a$10$N9qo8uLOickgx2ZMRZoMye...
```

<br/>

나중에 더 좋은 알고리즘으로 옮길 때, 옛 비밀번호를 그대로 두고 새 것만 새 방식으로 저장할 수 있다.

앞의 PSA 글에서 본 `인터페이스 뒤로 숨겨두면 갈아끼울 수 있다` 가 여기에도 적용된 셈이다.

<br/>

## 시큐리티가 필터로 동작한다는 것

앞의 필터, 스프링 인터셉터 글에서 본 그 위치다.

```java
클라이언트
  -> 톰캣
       -> 시큐리티 필터 체인      <- 여기서 인증을 확인한다
            -> DispatcherServlet
                 -> 컨트롤러
```

<br/>

인증되지 않은 요청은 `DispatcherServlet` 까지 가지도 않는다.

컨트롤러를 찾기도 전에 막는 것이 안전하기 때문이다.

<br/>

그래서 시큐리티 설정에서 경로를 열고 닫는 것이 컨트롤러와 별개로 동작한다.

컨트롤러를 만들어놨는데 `403` 이 나면 이 필터 설정을 먼저 봐야 한다.
