## 에러는 크게 2가지

- 컴파일 에러 (좋은 에러)

- 런타임 에러 (나쁜 에러)

<br/>

## 컴파일 에러

`‘좋은 에러’` 라고 부른다.

<br/>

ex) `String` 타입을 써야 되는데, `Integer` 타입을 사용 하였을 경우 컴파일 에러가 발생한다.

`‘좋은 에러’` 라고 부르는 이유는 → `빌드` 조차 안되기 때문이다.

- 개발자가 `IDE`에서 바로 확인 할 수 있기 때문이다.

```java
문제가 터지기 전에, 바로 인지 할 수 있기 때문이다.
```

<br/><br/>

## 런타임 에러

`‘나쁜 에러’` 라고 부른다.

### 런타임 에러는 2가지 종류가 있다.

- 애플리케이션을 띄울때 발생하는 `‘런타임 에러’`

- 고객이 직접 기능을 호출할때 발생하는 `‘런타임 에러’`

    - 이것이 가장 나쁜 오류이다.

<br/>

## 궁금증!

```java
Error 를 잡으면 안 되나
```

문법상으로는 잡힌다.

```java
try {
    ...
} catch (Error e) {          // 컴파일 된다
}
```

<br/>

그런데 잡아도 할 수 있는 게 없다.

<br/>

```java
OutOfMemoryError     - 메모리가 없다. 잡아서 무엇을 하겠는가
StackOverflowError   - 스택이 넘쳤다
NoClassDefFoundError - 클래스가 없다. 실행이 불가능하다
```

<br/>

앞의 GC 글에서 본 `OutOfMemoryError` 를 잡아본 적이 있다.

`catch` 블록 안에서 출력을 하려는 순간 또 터졌다.

메모리가 없으니 문자열 하나 만들 여유도 없는 것이다.

<br/>

## 잡으면 오히려 나빠진다

```java
try {
    ...
} catch (Throwable t) {       // Error 까지 잡힌다
    log.error("오류", t);
}
```

<br/>

`Throwable` 을 잡으면 `Error` 도 같이 잡힌다.

<br/>

`OutOfMemoryError` 가 났는데 서버가 안 죽고 계속 도는 상태가 된다.

메모리가 부족한 채로 요청을 받으니 응답이 이상해지고,

로그만 쌓이면서 원인을 못 찾게 되는 것이다.

<br/>

차라리 빨리 죽고 다시 뜨는 게 낫다.

```java
-XX:+ExitOnOutOfMemoryError
-XX:+HeapDumpOnOutOfMemoryError
```

<br/>

앞의 자바 가상머신(JVM) 글에서 본 그 옵션이다.

덤프를 남기고 종료하면, 재기동은 오케스트레이터가 해주고 원인은 덤프로 찾을 수 있다.

<br/>

## 계층 구조를 다시 보면

```java
Throwable
├── Error              - 시스템 문제. 잡지 않는다
└── Exception          - 애플리케이션 문제
    ├── RuntimeException - 언체크
    └── 나머지            - 체크
```

<br/>

앞의 예외 계층 글에서 다루는 그 구조다.

<br/>

`Exception` 을 상속했지만 체크가 아닌 것이 `RuntimeException` 인데,

이 위치가 좀 이상하게 느껴진다.

<br/>

`Exception` 아래에 있으니 `catch (Exception e)` 로 잡히기 때문이다.

```java
try {
    ...
} catch (Exception e) {       // NullPointerException 도 잡힌다
}
```

<br/>

체크 예외만 잡으려고 썼는데 버그성 예외까지 삼켜버리는 것이다.

<br/>

## 그래서 catch (Exception e) 를 조심해야 한다

```java
try {
    paymentClient.pay(amount);
} catch (Exception e) {
    log.warn("결제 실패, 무시하고 진행");
}
```

<br/>

`NullPointerException` 이 나도 `결제 실패` 로 기록된다.

<br/>

앞의 예외 포함과 스택 트레이스 글에서 본 대로,

원인이 가려지면 디버깅이 몇 배로 어려워진다.

<br/>

구체적으로 잡는 게 낫다.

```java
} catch (PaymentException e) {
```

<br/>

## Error 를 상속해서 만들 일도 없다

가끔 `내 프로그램에서는 이건 복구 불가능이니 Error 로 만들자` 는 생각을 한다.

<br/>

그런데 `Error` 는 JVM이 던지는 것이라는 관례가 있어서,

내가 만든 것을 `Error` 로 두면 다른 사람이 오해한다.

<br/>

복구 불가능한 것도 `RuntimeException` 으로 만드는 게 관례다.

<br/>

앞의 체크 예외, 언체크 예외 활용 글에서 본 그 판단이다.

```java
복구 가능한가 -> 아니오 -> 언체크 예외
```

<br/>

`Error` 인지 아닌지는 `JVM 이 던졌는가` 로 나뉘는 것이라고 보면 된다.
