## 예외 포함과 스택 트레이스

예외를 전환할 때는 꼭! 기존 예외를 포함해야 한다.

그렇지 않으면 스택 트레이스를 확인할 때 심각한 문제가 발생한다.

```java
@Test
void printEx() {
    Controller controller = new Controller();

    try {
        controller.request();
    } catch (Exception e) {
        //e.printStackTrace(); 이런 방법은 좋지 않다.
        log.info("ex", e); // 로깅으로 벙법으로 사용하기.
    }
}
```



로그를 출력할 때 마지막 파라미터에 예외를 넣어주면 로그에 스택 트레이스를 출력할 수 있다

예) `log.info("message={}", "message", ex)`이렇게 하면 스택 트레이스에 로그를 출력할 수 있다.

<br/><br/>

## 기존 예외를 포함하는 경우

```java
public void call() {
    try {
        runSQL();
    } catch (SQLException e) {
        throw new RuntimeSQLException(e); //기존 예외(e) 포함
    }
}
```

말하고 싶은 것은 꼭 인셉션 괄호에 예외를 포함 해야 된다는 것이다. → `RuntimeSQLException(e)`

그래야, 어디서 문제가 터진것을 알고 무슨 인셉션인지 알 수 있다.

<br/><br/>

## 궁금증!

```java
원인을 안 넘기면 무엇이 사라지나
```

두 코드를 비교하면 확실하다.

```java
} catch (SQLException e) {
    throw new ServiceException("조회 실패");       // 원인을 안 넘겼다
}
```

```java
} catch (SQLException e) {
    throw new ServiceException("조회 실패", e);    // 원인을 넘겼다
}
```

<br/>

앞의 것은 스택 트레이스가 여기서 끝난다.

```java
ServiceException: 조회 실패
    at MemberService.find(MemberService.java:20)
    at MemberController.find(MemberController.java:15)
```

<br/>

뒤의 것은 `Caused by` 가 붙는다.

```java
ServiceException: 조회 실패
    at MemberService.find(MemberService.java:20)
    ...
Caused by: java.sql.SQLException: Table 'member' doesn't exist
    at ...
    ... 15 more
```

<br/>

`테이블이 없다` 는 진짜 원인이 앞의 경우에는 통째로 사라진 것이다.

<br/>

## ... 15 more 라는 표시

같은 스택이 반복되는 부분을 줄인 것이다.

<br/>

`Caused by` 의 스택과 위쪽 스택이 겹치는 부분을 생략한다.

전부 찍으면 로그가 몇 배로 길어지기 때문이다.

<br/>

## 그래서 로그를 볼 때는 아래부터 본다

```java
가장 아래의 Caused by 가 진짜 원인이다
```

<br/>

`Caused by` 가 여러 겹으로 쌓이는 경우가 흔하다.

```java
ServiceException
Caused by: DataAccessException
Caused by: SQLException
Caused by: SocketTimeoutException      <- 진짜 원인
```

<br/>

앞의 스프링 예외 추상화 글에서 본 예외 변환이 이렇게 겹을 만든다.

각 층에서 자기 예외로 바꾸면서 원인을 물고 가는 것이다.

<br/>

## e.getMessage() 만 찍으면 안 된다

```java
log.error("오류: " + e.getMessage());
```

<br/>

메시지 한 줄만 남고 스택이 안 남는다.

<br/>

어디서 났는지를 모르니 로그를 봐도 소용이 없다.

<br/>

```java
log.error("오류", e);           // 예외 객체를 넘긴다
```

<br/>

`SLF4J` 는 마지막 인자가 `Throwable` 이면 스택 트레이스를 찍어준다.

<br/>

여기서 자주 하는 실수가 있다.

```java
log.error("주문 {} 처리 실패: {}", orderId, e);      // 스택이 안 찍힌다
```

<br/>

`{}` 자리에 들어가면 `toString()` 만 불린다.

<br/>

```java
log.error("주문 {} 처리 실패", orderId, e);          // 이렇게 써야 한다
```

<br/>

`{}` 개수보다 인자가 하나 많고 그게 예외면 스택을 찍는다.

<br/>

## printStackTrace 를 쓰면 안 되는 이유

```java
e.printStackTrace();
```

<br/>

`System.err` 로 나간다. 로그 파일에 안 남는다.

<br/>

앞의 로깅(Logging) 글에서 본 대로,

로그 레벨도 없고, 형식도 다르고, 파일 롤링도 안 된다.

<br/>

운영 서버에서는 이게 어디로 갔는지 찾기도 어렵다.

<br/>

## 예외를 삼키는 게 제일 나쁘다

```java
} catch (Exception e) {
    // 아무것도 안 함
}
```

<br/>

문제가 있었는데 아무 흔적이 안 남는다.

<br/>

나중에 데이터가 이상한데 원인을 찾을 방법이 없는 상태가 된다.

<br/>

의도적으로 무시하는 것이면 그것을 적어둬야 한다.

```java
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();      // 인터럽트 상태를 복원하고 종료
}
```

<br/>

`InterruptedException` 은 잡고 나서 반드시 다시 표시해줘야 한다.

안 그러면 상위에서 `이 스레드를 멈추라` 는 신호를 못 받는다.

<br/>

## 커스텀 예외에 생성자를 다 만들어두면 편하다

```java
public class ServiceException extends RuntimeException {

    public ServiceException(String message) {
        super(message);
    }

    public ServiceException(String message, Throwable cause) {
        super(message, cause);
    }
}
```

<br/>

두 번째가 없으면 원인을 넘길 방법이 없어진다.

<br/>

`Throwable` 이 그 필드를 들고 있다.

```java
private Throwable cause;
public Throwable getCause() { return cause; }
```

<br/>

`getCause()` 를 따라 내려가면서 원인 사슬을 프로그램으로 훑을 수도 있다.

```java
Throwable root = e;
while (root.getCause() != null) {
    root = root.getCause();
}
```

<br/>

특정 원인일 때만 다르게 처리해야 하는 경우에 쓴다.

스프링에는 이걸 해주는 유틸이 있다.

```java
NestedExceptionUtils.getMostSpecificCause(e)
```
