## 예외 계층

<br/>

![이미지](/programming/img/입문276.PNG)

- `Object:` 예외도 객체이다.
    - 모든 객체의 최상위 부모는 `Object` 이므로 예외의 최상위 부모도 `Object`이다.
- `Throwable:` 최상위 예외이다.
    - 하위에 `Exception` 과 `Error` 가 있다
- `Error:` 메모리 부족이나 심각한 시스템 오류와 같이 애플리케이션에서 복구 불가능한
    
    시스템 예외이다. 
    
    - 애플리케이션 개발자는 이 예외를 잡으려고 해서는 안된다.
    - `Exception`부터 필요한 예외로 생각하고 잡으면 된다.
    - 참고로 Error 도 `언체크 예외`이다
- `Exception:` 체크 예외
    - 애플리케이션 로직에서 사용할 수 있는 `실질적인 최상위 예외`이다.
    - `Exception` 과 그 하위 예외는 모두 컴파일러가 체크하는 `체크 예외`이다.
        - 단 `RuntimeException` 은 예외로 한다.
- `RuntimeException:` 언체크 예외, 런타임 예외
    - 컴파일러가 체크 하지 않는 `언체크 예외`이다.
    - `RuntimeException` 과 그 `자식 예외`는 `모두 언체크 예외`이다
    - `RuntimeException` 의 이름을 따라서 `RuntimeException` 과 그 `하위 언체크 예외`를
        
        `런타임 예외`라고 많이 부른다.

## 계속 예외 던지면?

![이미지](/programming/img/입문278.PNG)

- 자바 `main()` 쓰레드의 경우 예외 로그를 출력하면서 시스템이 종료된다.
- 웹 애플리케이션의 경우 여러 사용자의 요청을 처리하기 때문에 하나의 예외 때문에
    
    시스템이 종료되면 안된다. WAS가 해당 예외를 받아서 처리하는데, 주로 사용자에게 개발자가 지정한, 오류 페이지를 보여준다. 
    
    (서버가 죽지 않는다)

## 궁금증!

```java
catch 순서가 왜 중요한가
```

위에서부터 차례로 확인하기 때문이다.

```java
try {
    ...
} catch (Exception e) {           // 여기서 다 잡힌다
} catch (IllegalArgumentException e) {   // 여기까지 안 온다
}
```

<br/>

이건 컴파일 오류가 난다.

```java
exception IllegalArgumentException has already been caught
```

<br/>

부모를 먼저 잡으면 자식은 잡힐 일이 없으니 컴파일러가 막아주는 것이다.

<br/>

## 순서를 뒤집으면 된다

```java
} catch (IllegalArgumentException e) {    // 구체적인 것 먼저
} catch (Exception e) {                   // 넓은 것 나중
}
```

<br/>

앞의 SOLID 글에서 본 리스코프 치환 원칙의 실용적인 모습이기도 하다.

자식은 부모 자리에 들어갈 수 있으니, 부모로 잡으면 자식도 잡히는 것이다.

<br/>

## 여러 개를 한 번에 잡을 수 있다

```java
} catch (IOException | SQLException e) {
    log.error("입출력 오류", e);
}
```

<br/>

자바 7부터 된다.

<br/>

이때 `e` 의 타입은 두 예외의 공통 부모가 된다.

여기서는 `Exception` 이다.

<br/>

그래서 각각의 고유 메서드는 못 부른다.

```java
} catch (SQLException | IOException e) {
    e.getSQLState();      // 컴파일 오류. SQLException 에만 있다
}
```

<br/>

부모와 자식을 같이 적는 것도 안 된다.

```java
} catch (IOException | FileNotFoundException e) {   // 컴파일 오류
```

<br/>

`FileNotFoundException` 이 `IOException` 의 자식이라 중복이기 때문이다.

<br/>

## 계층을 만들 때의 기준

내 예외를 만들 때 어디에 붙일지가 고민이다.

```java
RuntimeException
└── ServiceException           - 프로젝트 공통 부모
    ├── MemberException
    ├── OrderException
    └── PaymentException
```

<br/>

공통 부모를 하나 두면 한 번에 잡을 수 있다.

```java
@ExceptionHandler(ServiceException.class)
public ResponseEntity<ErrorResponse> handle(ServiceException e) { ... }
```

<br/>

앞의 API 예외 처리 - @ExceptionHandler 글에서 본 그 처리다.

<br/>

## 예외 클래스를 몇 개나 만들 것인가

여기서 갈린다.

```java
방법 A - 예외마다 클래스를 만든다
   MemberNotFoundException, DuplicateEmailException, ...

방법 B - 하나에 코드를 담는다
   throw new ServiceException(ErrorCode.MEMBER_NOT_FOUND);
```

<br/>

`A` 는 타입으로 구분되니 `catch` 로 나눠 처리할 수 있다.

대신 클래스가 수십 개로 늘어난다.

<br/>

`B` 는 클래스가 하나다.

`enum` 에 메시지와 HTTP 상태를 같이 두면 응답을 만들기도 쉽다.

```java
public enum ErrorCode {
    MEMBER_NOT_FOUND(HttpStatus.NOT_FOUND, "회원을 찾을 수 없습니다"),
    DUPLICATE_EMAIL(HttpStatus.CONFLICT, "이미 사용 중인 이메일입니다");
}
```

<br/>

앞의 enum 글에서 본 `상수에 데이터를 붙일 수 있다` 는 성질을 쓴 것이다.

<br/>

실무에서는 `B` 를 쓰다가, 따로 처리해야 하는 것만 `A` 로 빼는 경우가 많다.

<br/>

## 스프링도 계층을 만들어뒀다

```java
DataAccessException
├── NonTransientDataAccessException      - 다시 해도 안 된다
│   ├── DataIntegrityViolationException  - 제약 조건 위반
│   └── BadSqlGrammarException           - SQL 문법 오류
└── TransientDataAccessException         - 다시 하면 될 수도 있다
    ├── QueryTimeoutException
    └── ConcurrencyFailureException
```

<br/>

앞의 스프링 예외 추상화, SQL 예외 변환기 글에서 본 그 구조다.

<br/>

`Transient` 와 `NonTransient` 로 나눈 게 실용적이다.

```java
} catch (TransientDataAccessException e) {
    재시도();            // 일시적인 문제니 다시 해볼 만하다
}
```

<br/>

무엇이 잘못됐는지가 아니라 `내가 무엇을 할 수 있는지` 로 나눈 것이다.

<br/>

예외 계층을 설계할 때 참고할 만한 기준이다.

`이 예외를 잡은 쪽이 무엇을 다르게 할 것인가` 를 생각하면,

굳이 안 나눠도 되는 것과 나눠야 하는 것이 갈린다.
